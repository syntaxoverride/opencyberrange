    Exercise 2.1: Anonymous Footprint

    Before You Begin

    Most domains today require authentication for any meaningful directory query. That default is comparatively recent. Migrations from older domain functional levels often preserve a legacy compatibility setting called Pre-Windows 2000 Compatible Access, a built-in group that, when it contains the well-known ANONYMOUS LOGON SID, lets unauthenticated callers read selected directory attributes. The artifact survives in production environments far longer than it should because removing it requires re-testing every legacy integration that depended on it. Exercise 2.1 asks you to find that artifact on Nordport's DC.

    You will not use credentials. You will use anonymous LDAP binds and SMB null sessions to enumerate as much of the directory as the misconfiguration exposes, then read the flag from the info attribute of a per-token user.

    Tools required: ldapsearch, rpcclient, smbclient, enum4linux-ng, netexec. All are pre-installed on Kali.

    Scenario

    Marcus Bell: "Before you steal a credential, find out what the company is giving you for free. Nordport upgraded their forest from 2012 R2 last year. Migrations leave bread crumbs. The Pre-Windows 2000 Compatible Access group is one of the loudest. Find out whether it still contains ANONYMOUS LOGON. If it does, half of the directory is yours without a single password guess."

    Your scope token is exposed as the environment variable OCR_SCOPE_TOKEN and shown in the lab dashboard. There is a per-token user account whose sAMAccountName contains your token. Find it via anonymous LDAP and read its info attribute.

    Credentials: none. The exercise is unauthenticated.

    Domain: corp.nordport.local Domain controller: corp-dc01

    Your Objectives

    • Verify whether anonymous SMB null sessions and anonymous LDAP binds work against corp-dc01
    • Use ldapsearch -x (no bind) to extract user, group, and OU lists
    • Use rpcclient -U "" to walk anonymous RPC interfaces
    • Locate the per-token user account whose sAMAccountName contains your scope token
    • Read the user's info attribute and submit the flag inside

    Authenticated vs Anonymous Surface

    The same DC presents two very different views depending on whether you bind with credentials or not. The comparison below shows what each surface yields on a typical migrated forest like Nordport.

    Capability Authenticated user Anonymous (legacy compat ON) Anonymous (modern hardened)
    (objectClass=user) enumeration yes yes rootDSE only
    Read description / info yes yes no
    Read memberOf yes usually no
    Read (objectClass=computer) yes partial no
    Read (objectClass=trustedDomain) yes yes no
    SMB share list (-L) yes usually no no
    RPC enumdomusers yes sometimes no

    Background: Why Anonymous Reads Used to Work

    Active Directory inherited a behavior model from Windows NT 4.0 where unauthenticated systems sometimes needed to enumerate the directory: NetBIOS browsers, downlevel print servers, certain monitoring tools, third-party single-sign-on integrations. Microsoft codified two compatibility surfaces:

    1. Pre-Windows 2000 Compatible Access built-in group (SID S-1-5-32-554). When ANONYMOUS LOGON (SID S-1-5-7) or the more permissive EVERYONE (S-1-1-0) is a member, unauthenticated callers gain pre-2000-style read access to user and group objects. The legacy group has read DACEs on most user attributes by default.
    2. dSHeuristics Bit 7 (fAllowAnonNSPI). A configuration value on CN=Directory Service,CN=Windows NT,CN=Services,CN=Configuration,.... When this 7th character of the string is 2, anonymous LDAP binds are permitted to query the directory. When it is 0 or absent, anonymous binds return only rootDSE.

    Modern Microsoft guidance is to leave both off. Migrations from 2003/2008/2012 to 2016/2019/2022 sometimes preserve them. A defender who runs Get-ADGroupMember "Pre-Windows 2000 Compatible Access" and finds ANONYMOUS LOGON should remove it and accept the risk of breaking any legacy integration that depended on it.

    What an anonymous client can see when both are misconfigured

    • All user objects via (objectClass=user)
    • All group objects via (objectClass=group)
    • All OUs via (objectClass=organizationalUnit)
    • Most user attributes: sAMAccountName, description, info, memberOf, userAccountControl, pwdLastSet, lastLogonTimestamp
    • The full domain SID via LDAP://<domain DN>
    • All trusts via (objectClass=trustedDomain)

    The combination is essentially the same data that an authenticated low-privileged user can see. The only difference is the attacker did not have to guess or steal a credential first.

    What does NOT work anonymously

    • Get-ADComputer-equivalent queries on (objectClass=computer) are usually filtered tighter; anonymous reads return little.
    • Group memberships (the member attribute on the group, not memberOf on the user) are sometimes hidden.
    • Any object explicitly DACL'd to require authentication.
    • SMB null session lookups against \\corp-dc01\C$ and other admin shares.

    Tool Primer

    ldapsearch with anonymous bind

    Drop -D and -w for an anonymous simple bind. -x selects the simple-bind mechanism rather than SASL (which would require Kerberos credentials).

    ldapsearch -x -LLL -H ldap://<dc_ip> \
  -b "DC=corp,DC=nordport,DC=local" \
  "(objectClass=user)" sAMAccountName description info

    Without authentication, the server applies the ACLs that grant access to ANONYMOUS LOGON and the Pre-Windows 2000 Compatible Access group. If anonymous binds are disabled, you get Invalid credentials immediately.

    rpcclient null session

    rpcclient -U "" -N <dc_ip>

    -U "" sets the username to empty. -N says "no password prompt." On the prompt:

    Command Effect (when null sessions allowed)
    srvinfo Server info
    enumdomusers List domain users (RID + sAMAccountName)
    enumdomgroups List domain groups
    lookupnames <name> Resolve a name to SID anonymously
    lookupsids S-1-5-21-...-500 Resolve a SID to name anonymously
    getdompwinfo Domain password policy

    Modern DCs reject most of these unless the legacy compatibility group is misconfigured. Try them all anyway.

    enum4linux-ng

    Wraps rpcclient, smbclient, and ldapsearch into one comprehensive scan. Excellent first pass.

    enum4linux-ng -A <dc_ip>

    -A runs every check (users, groups, shares, password policy, OS info, sessions). Results print by category.

    smbclient null session

    smbclient -L //<dc_ip>/ -N

    -L lists shares. -N skips the password prompt. Most DCs deny anonymous share enumeration even when LDAP allows anonymous reads; the layers are independent.

    Walkthrough

    Step 1: Confirm Your Scope Token

    Kali - Print scope token

    echo "$OCR_SCOPE_TOKEN"

    If empty, copy the value from the lab dashboard banner ("Your scope: xxxx") and export OCR_SCOPE_TOKEN=xxxx.

    Step 2: Probe Anonymous LDAP

    Kali - Anonymous bind probe

    ldapsearch -x -LLL -H ldap://<dc_ip> -s base "(objectClass=*)" namingContexts

    The query asks for rootDSE. Every LDAP server responds to this anonymously. If you get a response listing naming contexts (DC=corp,DC=nordport,DC=local, plus CN=Configuration,...), the server is reachable. The next test confirms whether deeper queries are allowed.

    Kali - Anonymous user enumeration

    ldapsearch -x -LLL -H ldap://<dc_ip> \
  -b "DC=corp,DC=nordport,DC=local" \
  "(objectClass=user)" sAMAccountName \
  | head -50

    What is different from the authenticated form (Exercise 1.1):

    Flag Effect
    -x Simple bind (required for anonymous; SASL needs credentials).
    -LLL Strip LDIF noise.
    -H ldap://<dc_ip> LDAP URL.
    (no -D) NO bind DN supplied: triggers anonymous bind.
    (no -w) NO password supplied.
    -b "DC=..." Search base.
    "(objectClass=user)" Return user objects.
    sAMAccountName Limit attributes to just the username.
    \| head -50 Cap output at 50 lines so a wide-open server does not flood your terminal.

    What you'll see:

    • If the legacy compat group + dSHeuristics bit 7 are misconfigured (Nordport), you get back a list of users with their sAMAccountName values.
    • If properly hardened, you get an Invalid credentials (49) error or only # search reference placeholders. The empty result is a feature, not a bug.

    Step 3: Pull Every User with Their Free-Form Attributes

    The 1.1 broad search showed description and info are where credentials and notes leak. From an anonymous standpoint, the same attributes are still readable when the legacy compat is in place. Pull the lot, save to file, then grep.

    Kali - Anonymous LDAP, all users, with description and info

    ldapsearch -x -LLL -H ldap://<dc_ip> \
  -b "DC=corp,DC=nordport,DC=local" \
  "(objectClass=user)" sAMAccountName description info \
  > anon_users.ldif
wc -l anon_users.ldif
head anon_users.ldif

    What each piece does:

    • The full ldapsearch command is the same as Step 2 plus the explicit attribute list (sAMAccountName description info). Without it the server returns ALL allowed attributes, ~50 per object, which is overkill.
    • > anon_users.ldif redirect output to a file. Convention is .ldif for LDIF-format dumps but the extension is informational only.
    • wc -l line count. A populated dump should be hundreds of lines (one block per user, ~5-7 lines per block).
    • head shows the first 10 lines so you can confirm the file structure looks right (LDIF is attribute: value per line, blank line between records).

    If the file is empty, the anonymous bind was silently rejected; revisit Step 2 with ldapsearch -x -d 1 ... (verbose) to see what is happening.

    Step 4: Filter to Your Token

    The dump contains your ghost_<token> user mixed in with all the other accounts. Filter the search server-side instead of grepping the dump locally.

    Kali - Anonymous LDAP filtered to your scope token

    ldapsearch -x -LLL -H ldap://<dc_ip> \
  -b "DC=corp,DC=nordport,DC=local" \
  "(sAMAccountName=*${OCR_SCOPE_TOKEN}*)" sAMAccountName info description distinguishedName

    What changed from Step 3:

    • "(sAMAccountName=*${OCR_SCOPE_TOKEN}*)" LDAP substring filter. The * wildcards mean "match any chars before/after my token". Bash expands ${OCR_SCOPE_TOKEN} first; the literal sent to the server is (sAMAccountName=*j001*) for token j001.
    • sAMAccountName info description distinguishedName four explicit attributes returned. distinguishedName includes the OU path, useful for understanding where a hidden user lives.

    The matching account is ghost_<token>. The info attribute contains the flag embedded in a migration note, like Migration trace from 2012R2: OCR{...}.

    Extract just the flag string with grep:

    Kali - Pull the OCR{} value out of the info attribute

    ldapsearch -x -LLL -H ldap://<dc_ip> \
  -b "DC=corp,DC=nordport,DC=local" \
  "(sAMAccountName=ghost_${OCR_SCOPE_TOKEN})" info \
  | grep -oE 'OCR\{[^}]+\}'

    What each piece does:

    • The ldapsearch is now exact-match on the full sAMAccountName (no wildcards) and returns only the info attribute.
    • | grep -oE 'OCR\{[^}]+\}' extract regex matches from stdin.
      • -o print only the matched text, not the whole line.
      • -E extended regex (so \{ is a literal brace).
      • 'OCR\{[^}]+\}' match OCR{ followed by 1+ characters that aren't }, then }.

    Submit the matched value on the platform.

    Step 5: Walk Anonymous RPC for Comparison

    You already have the flag. Spend the remaining time learning what else the misconfiguration exposes. RPC is a separate protocol on a separate set of ports (139/445); some calls succeed even when LDAP is locked down, others vice versa. Knowing both attack surfaces is the value of this exercise.

    Kali - rpcclient null session

    rpcclient -U "" -N <dc_ip>

    What each option does:

    • -U "" username is the empty string. With %, the password would follow; without %, no password is supplied.
    • -N no-password mode. Skips the prompt for an empty password. Together with -U "" this is the canonical "null session" connection.

    At the rpcclient $> prompt try these commands:

    Command What it calls under the hood Effect (when null sessions allowed)
    srvinfo SRVSVC NetServerGetInfo Server version, comment, capabilities.
    enumdomusers SAMR EnumDomainUsers List all users with RIDs.
    enumdomgroups SAMR EnumDomainGroups List all groups.
    getdompwinfo SAMR GetDomainPwInfo Password policy (min length, complexity flags, lockout).
    lookupsids S-1-5-21-...-500 LSARPC LsarLookupSids2 Resolve a SID to a name. RID 500 is always Administrator.

    Note which commands succeed and which fail. Modern DCs reject most SAMR null calls even when LDAP allows anonymous. The contrast (LDAP yields users, SAMR rejects) is the interesting forensic data.

    The domain SID prefix (S-1-5-21-XXXX-YYYY-ZZZZ) appears in the srvinfo response or in the rootDSE from Step 2. RID 500 = Administrator, RID 501 = Guest, RIDs 1000+ = user accounts.

    Step 6: Run enum4linux-ng for a Full Picture

    enum4linux-ng is a wrapper that runs the rpcclient + smbclient + ldapsearch enumeration in one shot. Useful when you want a complete picture without typing twenty commands. The output IS verbose; skim by section.

    Kali - One-shot anonymous enumeration

    enum4linux-ng -A <dc_ip> > anon_full.txt
less anon_full.txt

    What each option does:

    • -A "all checks": users, groups, shares, password policy, OS info, sessions, RID brute. Equivalent to specifying every flag individually. Default is no checks at all (just connection test); always pass -A for first-pass enumeration.
    • <dc_ip> target. Accepts a single IP or CIDR.
    • > anon_full.txt save to file; the output runs ~200-500 lines.

    Sections you should look at first:

    • OS Information: is this a DC, a member server, or a workgroup host?
    • Users: full list with RIDs.
    • Groups: local + domain groups.
    • Password Policy: min length, complexity, lockout threshold/duration. Critical for password spraying in Level 3.4.
    • Shares: readable shares with permissions masks.

    Compare what enum4linux-ng surfaces against what each underlying tool returned in the previous steps. The aggregator is convenient for reports; the underlying tools are necessary when you need precision.

    Blue Team Perspective

    Anonymous reads against a DC look like normal application traffic at the protocol level, which is exactly the problem. The detection signals that fire come from event subsystems most environments are not collecting unless someone explicitly enabled them.

    Activity Event ID Where it fires
    Anonymous logon to LDAP/SMB 4624 (logon type 3, account name ANONYMOUS LOGON) DC Security log
    Bulk LDAP queries 1644 (Directory Service Diagnostic) DC Directory Service log
    Null SAMR enumeration via rpcclient 4661 + 4662 with anonymous SID DC Security log
    Suspicious enumeration pattern MDI alert "Account enumeration reconnaissance" Defender for Identity

    What lights up first

    Microsoft Defender for Identity is tuned to spot anonymous SAMR enumeration almost the instant a tool calls enumdomusers against a DC. The alert "Account enumeration reconnaissance" fires within seconds and includes the source IP. A careful operator runs the LDAP probe first (less monitored), reads the data needed, and only escalates to RPC-based enumeration if the LDAP path is blocked.

    Hardening Note

    A modern domain has no business permitting anonymous reads. The remediation is well documented and rarely complicated; what makes it persist is fear of breaking a legacy integration nobody owns anymore.

    Practical anonymous-bind hardening

    • Audit Pre-Windows 2000 Compatible Access membership. Remove ANONYMOUS LOGON (S-1-5-7) and EVERYONE (S-1-1-0) unless a documented dependency exists.
    • Verify dSHeuristics position 7 is 0 or absent. View with dsquery * "CN=Directory Service,CN=Windows NT,CN=Services,CN=Configuration,DC=..." -attr dSHeuristics.
    • Set Network access: Allow anonymous SID/Name translation GPO to Disabled.
    • Set Network access: Restrict anonymous access to Named Pipes and Shares to Enabled.
    • Enable Defender for Identity on every DC and route alerts to the SIEM.
    • Enforce LDAP signing and channel binding (LDAPServerIntegrity = 2) so anonymous binds receive LDAP_STRONGER_AUTH_REQUIRED.

    Analysis Questions

    1. The Pre-Windows 2000 Compatible Access group exists for backwards compatibility with what specific behavior, and what concrete service does it sometimes still need to support today?

    Reveal Answer

    The group preserved the NT 4.0 behavior of allowing unauthenticated read access to user and group attributes so legacy NT services and downlevel clients could resolve names and SIDs without first establishing authenticated sessions. Today the most commonly cited "still need it" service is older RAS / RADIUS integrations and a handful of third-party SSO bridges that perform LDAP-based identity lookups before the user is authenticated. In well-managed modern environments the group is empty and any tool needing those reads is configured to bind as a service account. When you find ANONYMOUS LOGON still inside the group on a 2019 or 2022 domain, the most likely cause is an incomplete migration where someone added it temporarily and never re-tested its removal.

    2. The dSHeuristics attribute is one configuration string with several positional flags. Why does Microsoft model these as positional digits rather than a structured object, and what is the operational risk?

    Reveal Answer

    dSHeuristics predates structured AD configuration patterns. It was a quick way to expose tunables on the directory service object without adding new schema attributes for each. The string is a sequence of numeric digits, each digit is a separate boolean, and position is meaning. The operational risk is that operators editing one flag (often by hand, via adsiedit.msc) accidentally truncate or extend the string and silently change other flags. Position 7 is fAllowAnonNSPI. Position 9 is fSpecifyGUIDOnAdd. Mistyping by one character moves every flag after it. Defenders should read and write dSHeuristics only via tested scripts that preserve length and only edit the intended position.

    3. The combination of "anonymous LDAP allowed" and "anonymous SMB null session denied" is common. Why does the SMB layer get hardened first?

    Reveal Answer

    SMB null sessions historically exposed share enumeration, NetBIOS lookups, and the SAM RPC interfaces that allowed direct password policy queries and brute force attempts. The attack surface mapped one-to-one onto well-known internet worms (Conficker is the headline example). Microsoft hardened SMB null sessions by default starting in Windows 2003 SP1 and again in 2008, so contemporary DCs deny most anonymous SMB calls regardless of the Pre-Windows 2000 group membership. LDAP anonymous reads, by contrast, were considered safer (read-only, structured) and the hardening defaults shipped later. The result is the asymmetry you see in the field: anonymous LDAP yields a user list while anonymous SMB returns nothing useful.

    Key Takeaways

    • Anonymous bind testing is the highest-leverage probe in the first five minutes of an engagement against an unfamiliar AD.
    • Pre-Windows 2000 Compatible Access containing ANONYMOUS LOGON plus dSHeuristics bit 7 = 2 is the canonical misconfiguration.
    • The info attribute is read by ACLs that often differ from description; both are worth searching.
    • rpcclient -U "" -N and enum4linux-ng -A give you complementary views of which anonymous interfaces are still open.
    • A modern DC denies most anonymous SMB calls even when anonymous LDAP succeeds; do not assume one implies the other.

    Cheat Sheet Recap

    The four probes below are the unauthenticated touch a senior pentester runs reflexively on every new DC. Two minutes of effort, big payoff if the directory was migrated and never cleaned.

    Goal Command
    Probe rootDSE (always works) ldapsearch -x -LLL -H ldap://<dc> -s base "(objectClass=*)" namingContexts
    Anonymous user enumeration ldapsearch -x -LLL -H ldap://<dc> -b "<DN>" "(objectClass=user)" sAMAccountName description info
    Null SAMR session rpcclient -U "" -N <dc> then enumdomusers; enumdomgroups; getdompwinfo
    Aggregated unauthenticated scan enum4linux-ng -A <dc>

    Spaced Repetition

    Card 1: Anonymous LDAP One-Liner

    Q: Write the ldapsearch command that performs an anonymous bind against 10.10.10.10 and returns every user's sAMAccountName and info from corp.local.

    Answer 
    ldapsearch -x -LLL -H ldap://10.10.10.10 \
  -b "DC=corp,DC=local" \
  "(objectClass=user)" sAMAccountName info

    Drop -D and -w to bind anonymously. -x forces simple bind. If you get Invalid credentials, anonymous binds are disabled.

    Card 2: rpcclient Null Session Idiom

    Q: How do you start an rpcclient null session against a DC at 10.10.10.10?

    Answer 
    rpcclient -U "" -N 10.10.10.10

    -U "" sets the username to empty. -N skips the password prompt. Useful follow-on commands at the prompt: srvinfo, enumdomusers, enumdomgroups, getdompwinfo, lookupsids <sid>.

    Card 3: SID for ANONYMOUS LOGON

    Q: What is the well-known SID for ANONYMOUS LOGON, and which built-in group's membership most often re-enables anonymous directory reads when migrated?

    Answer

    S-1-5-7 for ANONYMOUS LOGON. The legacy group is Pre-Windows 2000 Compatible Access (S-1-5-32-554). When S-1-5-7 is a member of that group on a modern DC, anonymous directory reads work for any attribute the group has been granted. Defenders find it with Get-ADGroupMember "Pre-Windows 2000 Compatible Access" and remove ANONYMOUS LOGON after retesting legacy integrations.

    Card 4: dSHeuristics Bit for Anonymous LDAP

    Q: Which position in the dSHeuristics string controls fAllowAnonNSPI, and what value enables anonymous LDAP binds?

    Answer

    Position 7 (1-indexed; index 6 in zero-indexed code). Setting it to 2 enables anonymous LDAP binds. Setting it to 0 or leaving it absent denies them. The attribute lives on CN=Directory Service,CN=Windows NT,CN=Services,CN=Configuration,DC=... and is editable via adsiedit.msc. Always preserve string length when editing; positions matter.

    Card 5: enum4linux-ng First Pass

    Q: One command for an unauthenticated all-checks scan against a DC at 10.10.10.10.

    Answer 
    enum4linux-ng -A 10.10.10.10

    -A enables every check: users, groups, shares, OS info, password policy, sessions, RID brute. The output sections are clearly labeled; skim for the Users section first.
