    Exercise 9B: CryptoVault Recovery Operation

    Before You Begin

    Exercise 9B builds on the investigative skills from Exercise 9A by challenging you to recover encrypted data from a shared workstation using a corporate encryption policy. Where Exercise 9A investigated a web-accessible data breach across two servers, this exercise focuses on local forensic investigation on a single host. The skills you practiced in earlier exercises, reading file contents, examining configurations, and piecing together clues, all apply here. Your VPN must be connected and your terminal ready.

    Scenario

    CryptoVault Solutions is a cybersecurity consulting firm based in Austin, Texas. A senior consultant, Marcus Webb, departed the company abruptly two weeks ago. His laptop has been reimaged, but his encrypted backups remain on the shared analyst workstation.

    Your manager, Diana Reeves (Director of Operations), explains: "Marcus was working on a sensitive internal audit before he left. The audit report is in one of his encrypted backup files, but we can't access it. Our company has a standard recovery procedure for encrypted data: the passphrase format is documented in our internal policy. I need you to follow the recovery process, decrypt the correct file, and retrieve the audit report."

    Diana provides SSH credentials for the analyst workstation. She reminds you that company policy dictates the passphrase construction method: you should not need to brute force anything. "Everything you need is on that workstation."

    SSH credentials: analyst / CV_4n4lyst_2024#

    Your Objectives

    • Connect to the analyst workstation via SSH
    • Enumerate the departed employee's files and directories
    • Identify the encryption method from shell history artifacts
    • Locate and interpret the company encryption recovery policy
    • Reconstruct the passphrase using policy format, employee records, and contextual clues
    • Decrypt the correct file and retrieve the assessment finding
    • Assemble and submit the flag

    Background: Digital Forensics and Data Recovery

    When an employee leaves an organization, encrypted files may remain on shared systems. Recovering that data without the employee's cooperation requires a structured forensic approach: identify what encryption was used, find the key material or recovery policy, and apply it to the correct file. The recovery operation in this exercise is controlled and policy-driven, not a brute force attack.

    Shell History as a Forensic Artifact

    Linux systems record commands in history files (typically ~/.bash_history). These files persist after user sessions end and can reveal exactly which tools, options, and file paths a user worked with. In forensic investigations, shell history is one of the first artifacts examined because it provides a timeline of user activity without requiring access to the data itself.

    Encryption Tool Identification

    Different encryption tools use different formats, algorithms, and key derivation methods. A file encrypted with openssl cannot be decrypted with gpg, and vice versa. Before attempting decryption, an investigator must identify which tool was used. Misidentifying the tool wastes time and produces misleading error messages rather than plaintext.

    Policy-Based Key Recovery

    Many organizations implement passphrase construction policies that allow authorized personnel to reconstruct encryption keys from employee records. The passphrase follows a documented format combining company identifiers, employee IDs, and date components. While convenient for business continuity, this approach creates a recoverable, and potentially predictable, key derivation method.

    Tool Primer: SSH, openssl, and Common Forensic Commands

    SSH for remote access:

    ssh <username>@<target_ip>

    You have used SSH in previous exercises. The -o StrictHostKeyChecking=no flag can be added if the host key prompt interferes with your connection.

    openssl for symmetric decryption:

    openssl enc -<algorithm> -d -pbkdf2 -in <encrypted_file> -pass pass:<passphrase>
    Flag Purpose
    enc Use the symmetric encryption subcommand
    -aes-256-cbc Algorithm (AES-256 in CBC mode)
    -d Decrypt (instead of encrypt)
    -pbkdf2 Use PBKDF2 key derivation (modern standard)
    -in Input file path
    -pass pass: Supply passphrase on the command line (no space after pass:)

    File exploration commands:

    Command Purpose
    ls -la /home/ List all home directories with permissions
    ls -la /home/<user>/ List a specific user's files including hidden files
    cat <file> Read file contents
    cat ~/.bash_history Read a user's command history
    find /home/<user>/ -type f List all files recursively under a directory
    file <filename> Identify file type (text, encrypted data, etc.)

    ssh analyst@<target_ip>

    Step 2: Read the Analyst's README

    Read the analyst README on the workstation

    Check your home directory for any briefing documents left by management. Run this in the SSH session you just opened on the workstation.

    cat ~/README.txt

    The README.txt file provides context about the recovery operation and confirms your objectives. Read it carefully: it reinforces what Diana Reeves told you in the scenario briefing.

    Step 3: Enumerate the Departed Employee's Home Directory

    List home directories on the workstation

    Determine what user accounts exist on the workstation by listing home directories.

    ls -la /home/

    You should see your own home directory (analyst) and the departed employee's directory.

    List the departed employee's files including hidden ones

    Navigate to the departed employee's home directory and list all files, including hidden ones.

    ls -la /home/mwebb/

    Note the files and subdirectories present. Hidden files (those starting with .) are often the most forensically interesting because they include configuration files and shell history.

    Step 4: Examine the Shell History

    Read the departed employee's shell history

    The .bash_history file records commands the departed employee ran. The history is your primary clue for identifying the encryption method.

    cat /home/mwebb/.bash_history

    Read the history carefully. Look for commands that reference encryption tools (openssl, gpg, zip), specific algorithms, and file names. One entry should reveal exactly which tool and algorithm was used to create the encrypted backup, including the input filename and output filename.

    Record the encryption command you found: you will need the tool name, algorithm, and any flags to construct your decryption command later.

    Step 5: Examine the Employee Record

    Read the employee record file

    Look for personnel files that contain identifying information about the departed employee.

    cat /home/mwebb/employee-record.txt

    The employee-record.txt file contains the employee's full name, employee ID, role, and separation date. Record the employee ID: it follows a specific format that will be needed for passphrase reconstruction.

    Step 6: Explore Desktop and Documents

    List the Desktop and Documents directories

    Check the departed employee's Desktop and Documents directories for additional clues.

    ls -la /home/mwebb/Desktop/
ls -la /home/mwebb/Documents/

    Read any files you find. One file in particular contains a note that points you toward the company's encryption standard policy. The note is the breadcrumb trail: the employee left a reference to where the passphrase construction rules are documented.

    Read the sticky note left on the Desktop

    Open the note the employee left behind. It points to where the passphrase construction rules are documented.

    cat /home/mwebb/Desktop/sticky_note.txt

    Step 7: Locate and Read the Company Encryption Policy

    Read the company encryption policy

    The sticky note referenced a company policy location. Navigate to that path and read the encryption standard.

    cat /etc/company-policy/encryption-standard.txt

    The encryption-standard policy document is the key to the entire exercise. It defines:

    • Which encryption tools the company uses and for what purpose
    • The exact passphrase format for internal backups
    • What each component of the passphrase represents
    • Where to find each component value

    Read the policy thoroughly. The passphrase format uses a template with multiple fields that you need to fill in from the evidence you have already gathered.

    Step 8: Reconstruct the Passphrase

    Using the policy's passphrase format, substitute the values you found:

    • Company Prefix: Stated directly in the policy (case-sensitive)
    • Employee ID: From the employee record file (Step 5)
    • Year: The four-digit year when the backup was created: determine this from the evidence you have collected (shell history timestamps, employee record dates, file dates)

    Common Mistake: Wrong Year

    Students frequently use the current year or the employee's separation year. Think carefully about when the backup was created, not when the employee left. Look at the evidence for date clues: the bash history entry, the employee record dates, and the file modification times all provide context.

    Assemble the passphrase by combining all three components in the format specified by the policy, with the correct separators. Once you have it, plug it into the decryption command.

    Decrypt the audit backup with openssl

    Run the decryption on the workstation where the encrypted file lives. The -pass pass: flag is how you supply a passphrase to openssl on the command line. There is no space between pass: and the passphrase value.

    openssl enc -aes-256-cbc -d -pbkdf2 \
  -in /home/mwebb/audit_backup.enc \
  -pass pass:<YOUR_PASSPHRASE>

    Replace <YOUR_PASSPHRASE> with the passphrase you just assembled: the three components joined with the correct separators. A correct passphrase prints the decrypted audit report to your terminal; a wrong one prints a bad decrypt error.

    Flag Format

    The flag is a single token revealed by decrypting the backup file:

    OCR{token}

    Step 9: Decrypt and Capture the Flag

    Run the command you constructed above. If the passphrase is correct, the decrypted content will print to your terminal and contain the assessment flag in OCR{...} format.

    If you see bad decrypt errors, double-check:

    • Is the company prefix exactly as written in the policy (case-sensitive)?
    • Is the employee ID in the correct format?
    • Is the year correct (creation year, not separation year)?
    • Are the separators correct (dashes, not underscores)?

    Step 10: Avoid the Red Herrings

    The workstation contains additional encrypted files in /opt/recovery/ that are not the target. These decoy files use different encryption methods (GPG, password-protected ZIP) and random passphrases that do not follow the company policy. They exist to test whether you follow the evidence trail methodically or waste time on files that do not match the investigation objective.

    If you explored /opt/recovery/ and tried to decrypt files there, that is okay: recognizing that those files use different encryption methods is part of the forensic process. The key insight is that the bash history pointed to a specific file encrypted with a specific tool, and the company policy only covers that tool's passphrase format.

    Analysis Questions

    1. The company's passphrase recovery policy uses a predictable format: {Prefix}-{ID}-{Year}. Why is a predictable passphrase construction method a security weakness, even when the policy is stored internally?

    Reveal Answer

    A predictable passphrase format reduces the key space from billions of possible combinations to a small, enumerable set. Anyone who reads the policy, current employees, contractors, attackers who compromise the intranet, can reconstruct passphrases for any employee's encrypted files. The security of the encrypted data depends entirely on the secrecy of the policy document rather than the strength of the passphrase itself. Relying on a secret construction rule violates Kerckhoffs's principle: a cryptographic system should be secure even if everything about the system except the key is public knowledge. A better approach would use randomly generated passphrases stored in a centralized key management system with access controls and audit logging.

    2. Marcus's .bash_history revealed the exact encryption command he used. Several other files on the workstation used GPG with random passphrases. Why does identifying the correct encryption tool matter, and what would happen if you tried to decrypt an openssl file with GPG?

    Reveal Answer

    OpenSSL and GPG use fundamentally different file formats, key derivation methods, and encryption wrappers. An openssl-encrypted file starts with a Salted__ header and uses PBKDF2 (or the older EVP_BytesToKey) to derive the encryption key from the passphrase. A GPG-encrypted file uses the OpenPGP format with its own key derivation and packet structure. Attempting to decrypt an openssl file with gpg produces an error like "gpg: no valid OpenPGP data found" because GPG cannot parse the openssl format. Identifying the correct tool is a prerequisite for successful decryption: no amount of correct passphrases will work if you are using the wrong tool.

    3. The analyst account could read Marcus's home directory and files despite being a different user. What file permission setting would have prevented this cross-user access, and why is it important during employee offboarding?

    Reveal Answer

    Setting the home directory to chmod 700 (owner read/write/execute only) would prevent any other non-root user from listing or reading files inside it. The default permissions on many Linux distributions allow group or world read access to home directories (755 or 750), which means any user on the system can browse another user's files. During employee offboarding, this is critical because the departing employee's files may contain sensitive data, credentials, encryption keys, or proprietary information. Best practice is to restrict home directory permissions to 700 at account creation and to either archive or securely delete the departing employee's files as part of the offboarding checklist, rather than leaving them accessible on shared systems.

    Key Takeaways

    • Shell history (.bash_history) is a forensic artifact that reveals exactly which commands a user ran, including encryption tools, algorithms, and file paths: it is one of the first files an investigator should examine
    • Policy-based passphrase construction creates a recoverable but predictable key derivation method; convenient for business continuity but exploitable by anyone who reads the policy
    • Encryption tool identification is essential before attempting decryption; openssl and GPG use different formats, key derivation methods, and command syntax, and using the wrong tool produces errors rather than plaintext
    • Red herrings (GPG files, unrelated encrypted archives) test whether you follow evidence methodically or waste time on files that do not match the investigation objective
    • Cross-user file access on shared workstations is a common misconfiguration; restrictive home directory permissions (chmod 700) prevent one user from reading another's files, which is critical during offboarding when departing employees may leave sensitive data behind
