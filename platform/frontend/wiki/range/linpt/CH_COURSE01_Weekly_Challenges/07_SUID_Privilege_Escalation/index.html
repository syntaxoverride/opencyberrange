    Exercise 7: SUID Privilege Escalation

    Before You Begin

    Weeks 4 through 6 focused on web exploitation; directory traversal, injection flaws, and authentication bypasses against HTTP services. Week 7 shifts to post-exploitation, where you already have a foothold on a Linux system and need to escalate your privileges. Your VPN must be connected and your terminal open before you proceed.

    Scenario

    Meridian Data Corp, a data analytics firm in Portland, Oregon, contracted your team at Vanguard Offensive Security for an internal penetration test. Phase 1 of the engagement (initial access) is complete; your team obtained SSH (Secure Shell) credentials for a low-privilege developer account on one of their build servers through a phishing exercise.

    Your task for Phase 2 is privilege escalation. The credentials you have belong to the "developer" account, which has standard user permissions. Your objective is to escalate to root and recover the system flag stored in /root/.

    Riley Park (IT Security Manager) mentioned during the scoping call: "Our dev team has been installing various tools on these servers. I'm fairly sure the permissions are fine, but honestly nobody has audited them in months. If you find a way to root, document the exact misconfiguration so we can remediate."

    Standard rules of engagement apply. Document your escalation path.

    Your Objectives

    The following list outlines what you need to accomplish during the lab. Each objective maps to one or more walkthrough steps below.

    • Enumerate the target system for privilege escalation vectors
    • Identify SUID binaries using standard Linux enumeration techniques
    • Distinguish between normal and misconfigured SUID permissions
    • Exploit a SUID misconfiguration to escalate privileges to root
    • Capture the flag from /root/flag.txt

    Background: SUID Permissions and Privilege Escalation

    Linux controls file access through a permission model based on three categories: owner, group, and others. Each category can be granted read (r), write (w), and execute (x) permissions. You can view these permissions with ls -l, which displays them as a 10-character string like -rwxr-xr-x.

    Beyond the standard read/write/execute bits, Linux supports a special permission called the SUID (Set User ID) bit. When the SUID bit is set on an executable, that program runs with the permissions of the file's owner rather than the user who launched it. The SUID bit appears as an s in the owner's execute position; for example, -rwsr-xr-x indicates the SUID bit is active and the file is owned by root.

    Several system utilities legitimately need the SUID bit. Programs like passwd, ping, and su require root-level access to function correctly, so they ship with SUID enabled by default. The danger arises when a binary that was never intended to have SUID receives it through a misconfiguration. If an attacker finds such a binary, they can use its built-in features to execute commands as root, read protected files, or spawn a root shell.

    Understanding the SUID mechanism is essential for both attackers and defenders. An attacker looks for misconfigured SUID binaries as a fast path to root. A defender audits SUID binaries regularly and removes the bit from anything that does not require it.

    Tool Primer: Finding SUID Binaries

    The primary tool for locating SUID binaries on a Linux system is the find command with permission-based filtering. The following command searches the entire filesystem for files with the SUID bit set.

    Find every SUID binary on the system

    Run this on the target after you have a shell. The filter matches files where the SUID bit is set, which is the fast first check in Linux privilege escalation.

    find / -perm -4000 -type f 2>/dev/null

    The result is a list of file paths, each a binary that runs with its owner's permissions; compare the list against the known-good baseline to spot anything unusual.

    Each part of the command serves a specific purpose:

    • find /: start searching from the root of the filesystem
    • -perm -4000: match files where the SUID bit (octal 4000) is set
    • -type f: restrict results to regular files (not directories or links)
    • 2>/dev/null: suppress "Permission denied" errors for directories you cannot read

    Sample output:

    /usr/bin/passwd
/usr/bin/chfn
/usr/bin/chsh
/usr/bin/newgrp
/usr/bin/su
/usr/bin/find
/usr/bin/mount
/usr/bin/umount

    Most of the binaries in the list above are expected; passwd, su, mount, and umount are standard SUID programs on nearly every Linux distribution. The entry that should raise a red flag is /usr/bin/find. The find utility does not need elevated privileges for its normal purpose (searching for files), and it has the ability to execute arbitrary commands through its -exec flag.

    GTFOBins is a curated online resource (gtfobins.github.io) that documents Unix binaries which can be exploited to bypass security restrictions. When you discover an unusual SUID binary, search GTFOBins for known escalation techniques. The site provides copy-paste commands for dozens of common utilities.

    Walkthrough

    Step 1: Launch the Exercise

    Open the platform in your browser and start the exercise environment. You need the target server running before you can connect over SSH.

    • Navigate to Exercises and locate the Week 7 challenge
    • Click Launch on "SUID Privilege Escalation"
    • Wait for the status to change to Running
    • Note the target IP displayed in the Active Lab View

    Step 2: SSH into the Target as Developer

    Your team obtained credentials for the developer account during Phase 1. Use SSH to connect to the build server with these credentials.

    SSH into the build server

    Replace <target_ip> with the IP address shown in the Active Lab View. When prompted for a password, enter the developer credential.

    ssh developer@<target_ip>

    When prompted for a password, enter:

    M3r1d1an_D3v#

    A successful login drops you into a shell on the target as the developer user.

    After logging in, confirm your identity and check your privileges.

    Confirm your identity on the target

    Run these on the target shell you just opened to verify the account and its group memberships.

    whoami
id

    The whoami command should return developer, and the id command will show your user ID (UID), group ID (GID), and group memberships. Note that you are a standard user with no special group memberships; you cannot run sudo or access /root/ directly.

    Step 3: Enumerate SUID Binaries with find

    Now that you have confirmed your access level, search the filesystem for binaries with the SUID bit set. SUID enumeration is one of the first checks in any Linux privilege escalation methodology.

    Enumerate SUID binaries

    Run the SUID search on the target. The 2>/dev/null suppresses permission-denied noise so only the file paths print.

    find / -perm -4000 -type f 2>/dev/null

    Review the output carefully. You will see a list of file paths, each representing a binary that runs with its owner's permissions. Write down every binary in the list; you will need to compare them against what is normal in the next step.

    Step 4: Identify the Misconfigured Binary

    Compare the SUID binaries you found against the set of programs that normally carry the SUID bit. Standard SUID binaries include passwd, su, mount, umount, chfn, chsh, and newgrp. Any binary outside that expected set deserves investigation.

    You should notice that /usr/bin/find has the SUID bit set. Verify the permissions and owner.

    Verify the find binary permissions

    Inspect the binary on the target to confirm the SUID bit and its owner.

    ls -la /usr/bin/find

    The output will look similar to:

    -rwsr-xr-x 1 root root 320160 ... /usr/bin/find

    The s in the owner's execute position confirms the SUID bit is active, and the file is owned by root. The find command includes an -exec flag that can run arbitrary commands; and because of the SUID bit, those commands will execute with root privileges.

    Step 5: Exploit SUID find to Get a Root Shell

    The find binary's -exec flag runs a specified command for each file matched. By combining -exec with a shell invocation, you can spawn a shell that inherits the elevated effective UID (User ID). The -p flag on /bin/sh preserves the effective UID instead of dropping it.

    Spawn a root shell through SUID find

    Run this on the target. The -exec flag launches /bin/sh -p, and because find is SUID root the shell keeps root's effective UID.

    find . -exec /bin/sh -p \; -quit

    Breaking down the command:

    • find .: search the current directory (the search target does not matter here)
    • -exec /bin/sh -p \;: for each matched file, execute /bin/sh with the -p flag
    • -quit: stop after the first match so only one shell is spawned

    After running the command, verify that you now have root privileges.

    Confirm root privileges

    Check your effective identity in the new shell.

    whoami
id

    The whoami command should return root, and the id output should show euid=0(root), confirming that you are operating with root-level permissions.

    Step 6: Read the Flag

    With root privileges, you now have access to the /root/ directory. Read the flag file stored there.

    Read the root flag

    Print the flag file from the root home directory, now readable thanks to your root shell.

    cat /root/flag.txt

    The flag follows the OCR{...} format. Copy the entire string exactly as it appears; you will need it for submission.

    Step 7: Interpret the Results

    Review what you accomplished and why each step mattered. The enumeration phase revealed that /usr/bin/find had the SUID bit set, which is not part of the default configuration on most Linux distributions.

    The find binary is dangerous with SUID because it includes the -exec flag, allowing execution of arbitrary commands. When find runs as root (due to SUID), every command launched through -exec also runs as root. A single misconfigured permission turned a routine file-search utility into a full root-access vector.

    In a real engagement, you would document the exact binary path, its permissions, the exploit command, and a remediation recommendation. Riley Park asked for precisely that information so the Meridian Data Corp team can remove the SUID bit from /usr/bin/find and audit the rest of their servers.

    Analysis Questions

    Consider the following questions to deepen your understanding of SUID-based privilege escalation. Each answer appears directly below the question.

    1. Why does the -p flag matter when spawning a shell through a SUID binary?

    Reveal Answer

    Without -p, most modern shells (including bash and sh) will drop the effective UID back to the real UID as a security measure. The -p flag tells the shell to preserve the effective UID, which means the root privileges inherited from the SUID binary remain active. Omitting -p would result in a shell running as the developer user, defeating the escalation.

    2. An administrator removes the SUID bit from /usr/bin/find but does not check the rest of the system. Why is that response incomplete?

    Reveal Answer

    Other binaries on the system may also have inappropriate SUID permissions. A thorough remediation requires auditing every SUID binary against a known-good baseline and removing the bit from anything that does not require it. Automated tools like linpeas or manual find sweeps should be run on every server in the environment, not just the one that was exploited.

    3. Name two other common Linux binaries that, if given the SUID bit, could be exploited for privilege escalation.

    Reveal Answer

    Common examples include vim (which can spawn a shell from within the editor using :!sh), python (which can execute arbitrary code including os.system("/bin/sh")), cp (which can overwrite sensitive files like /etc/shadow), and bash (which can be invoked with -p to preserve elevated privileges). GTFOBins documents escalation techniques for dozens of binaries.

    Key Takeaways

    • The SUID bit allows a binary to run with its owner's privileges, which means a root-owned SUID program gives any user root-level execution
    • SUID enumeration with find / -perm -4000 is one of the first checks in any Linux privilege escalation workflow; always compare results against a known-good baseline
    • GTFOBins is an essential reference for determining whether a SUID binary can be exploited, and it provides ready-made escalation commands for common utilities
    • A single misconfigured permission on one binary can undermine an otherwise well-secured system; regular auditing is the primary defense
    • Remediation requires more than fixing the one binary you found; a full audit across all servers in the environment is necessary to prevent similar misconfigurations elsewhere
    • Week 8 builds on the post-exploitation theme by exploring additional privilege escalation vectors beyond SUID, including cron jobs and writable scripts
