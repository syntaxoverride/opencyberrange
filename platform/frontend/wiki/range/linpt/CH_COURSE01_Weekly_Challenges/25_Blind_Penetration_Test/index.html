    Challenge 9B: Blind Penetration Test

    Before You Begin

    Exercise 9A walked you through a full penetration test with detailed guidance at every step. Challenge 9B uses the same multi-phase attack methodology but removes the safety net. You will face a different target environment, a different vulnerability class, and a different company, but the kill chain structure is identical: reconnaissance, initial access, credential discovery, lateral movement, and privilege escalation.

    Your VPN must be connected and your terminal open before continuing. Challenge 9B has a 90-minute time limit and hints are locked for the first 30 minutes. Use the first 30 minutes to work independently using the skills you have built over Weeks 1 through 9.

    Scenario

    Apex Meridian Group is a mid-size management consulting firm headquartered in Charlotte, North Carolina. They are preparing for a federal contract bid and require an independent security assessment of their infrastructure before submission. Your firm has been engaged for a black-box penetration test.

    Your point of contact is Daniel Reeves, Director of IT: "We have a public-facing web server that hosts our corporate site and a document download portal. Behind that sits our backend application server that handles internal processing. The backend should only be reachable by our operations team: not from the outside."

    Two target servers make up the engagement scope: a web server exposed on port 80, and a backend application server running SSH on port 22. Three assessment markers are distributed across the infrastructure. Retrieve all three and assemble the final flag to demonstrate complete compromise.

    Your Objectives

    • Enumerate services across both target systems using port scanning
    • Identify and exploit a directory traversal vulnerability in the web application's file download feature
    • Discover sensitive configuration files containing backend credentials
    • Retrieve the first assessment marker from the web server
    • Pivot laterally to the backend server using discovered SSH credentials
    • Retrieve the second assessment marker from the backend server
    • Escalate privileges on the backend server to achieve root access
    • Retrieve the third assessment marker and assemble the complete flag
    • Submit the flag in OCR{...} format

    Background: Directory Traversal Attacks

    Exercise 9A exploited command injection: a vulnerability where the server executes attacker-supplied input as an operating system command. Challenge 9B introduces a different vulnerability class: directory traversal (also called path traversal).

    Directory traversal occurs when a web application accepts a filename or path as user input and uses it to read files from the filesystem without properly validating the input. If the application does not restrict the input to a specific directory, an attacker can use ../ sequences to navigate up the directory tree and read files outside the intended folder.

    Consider a file download endpoint that works like this:

    http://example.com/download?file=report.pdf

    The server reads /var/www/documents/report.pdf and returns it. But if the application does not sanitize the file parameter, an attacker can request:

    http://example.com/download?file=../../../etc/passwd

    The server resolves the path as /var/www/documents/../../../etc/passwd, which simplifies to /etc/passwd, and returns the system's password file. The ../ sequences climb out of the documents directory one level at a time until reaching the filesystem root.

    Directory traversal is particularly dangerous because it provides read access to any file the web server process can read. Configuration files, environment files, SSH keys, and application source code are all potential targets. While command injection gives you the ability to execute commands, directory traversal gives you the ability to read files, and files often contain credentials that enable the next phase of the attack.

    The following diagram compares the two attack types:

    graph TD

    B -->|"Command Injection"| C["Server executes input<br/>as OS command"]
    B -->|"Directory Traversal"| D["Server reads file<br/>at attacker-chosen path"]
    C --> E["Arbitrary command execution"]
    D --> F["Arbitrary file read"]

    Both vulnerabilities result from the same root cause: trusting user input without validation. The difference is what the application does with that input: passes it to a shell (command injection) or passes it to a file-read function (directory traversal).

    Walkthrough

    Phase 1: Reconnaissance

    Step 1: Launch the Exercise and Note Both Target IPs

    Open the platform in your browser and start the exercise environment. Like Exercise 9A, this lab deploys two servers, so you will see two IP addresses in the Active Lab View.

    • Navigate to Exercises and locate Apex Meridian Group: Blind Penetration Test
    • Click Launch and wait for the status to change to Running
    • Note both target IPs displayed in the Active Lab View: one for the web server and one for the backend server
    • Record both IPs before proceeding

    Daniel Reeves described a public-facing web server and an internal backend server. Your attack path starts at the web server and works inward: the same pattern as Exercise 9A, but with a different vulnerability to exploit.

    Step 2: Scan Both Servers

    Begin with port scans to identify exposed services on each server.

    Scan the web server

    Scan the web server first to confirm the exposed HTTP service.

    nmap <webserver_ip>

    You should see port 80 open with an HTTP service: the corporate site and document download portal that Daniel mentioned.

    Scan the backend server

    Now scan the backend server to find its remote access service.

    nmap <backend_ip>

    The backend server should show port 22 open with an SSH service. The engagement layout mirrors Exercise 9A: a web application as the entry point and SSH as the lateral movement path.

    Record both scan results. The attack surface is clear: exploit the web application on port 80 to find credentials, then use those credentials to SSH into the backend on port 22.

    Phase 2: Initial Access via Directory Traversal

    With reconnaissance complete, you know the web server hosts a web application on port 80. Your next task is to explore the application, identify file-handling functionality, and test for directory traversal.

    Step 3: Explore the Web Application

    Load the web application

    Load the web application in your browser or use curl to examine it from the command line.

    curl http://<webserver_ip>/

    Examine the response for clues about the application's functionality. Daniel Reeves mentioned a "document download portal": look for links, endpoints, or references to file download features. Web applications that serve files to users are prime candidates for directory traversal if they pass filenames through URL parameters.

    Step 4: Identify the Download Endpoint

    Explore the application to find the file download feature. Look for URLs that include a file parameter or similar: these indicate the server reads a file based on user input.

    Probe the download endpoint

    Test the /download endpoint to confirm it reads a file based on the file parameter.

    curl http://<webserver_ip>/download?file=test

    The response should indicate that the endpoint expects a valid filename. The file parameter is the input you will manipulate: if the server does not validate it, you can traverse outside the intended directory.

    Step 5: Test for Directory Traversal

    Test for directory traversal with /etc/passwd

    Test whether the application sanitizes the file parameter by using ../ sequences to climb out of the document directory. Start with a well-known file that exists on every Linux system.

    curl "http://<webserver_ip>/download?file=../../../../etc/passwd"

    If the application is vulnerable, the response will contain the contents of /etc/passwd: a list of user accounts on the web server. The presence of this file in the response confirms that the server reads files at whatever path you specify, without restricting access to the documents directory.

    How many ../ sequences do you need?

    The number of ../ sequences depends on how deep the documents directory is in the filesystem. Using more ../ than necessary is harmless: once you reach the filesystem root (/), additional ../ sequences have no effect. If three levels does not work, add another ../ and try again. Four levels is typically enough for most web application layouts.

    Phase 3: Credential Discovery

    You now have arbitrary file read access on the web server through the directory traversal vulnerability. The next objective is to find credentials that grant access to the backend server. Think about where applications store their configuration: environment files, config directories, and application settings are common locations.

    Step 6: Locate Configuration Files

    Web applications typically store their configuration in files within or adjacent to the application directory. Common locations include:

    • .env files (environment variables)
    • config/ directories (application configuration)
    • settings.py, config.ini, app.env (framework-specific config files)

    Use the directory traversal to explore the web server's filesystem. Since the documents directory is likely inside the application directory, you may only need to traverse up one or two levels to reach configuration files.

    Read the application config via traversal

    Try reading configuration files relative to the document root.

    curl "http://<webserver_ip>/download?file=../config/app.env"

    Examine the output for variables containing SSH credentials for the backend server. You should find a username and password pair formatted as environment variables.

    Think like a developer

    Developers store secrets in configuration files because it is convenient. Environment files (.env, app.env) are the most common location for database passwords, API keys, and SSH credentials. When you gain file read access to a server, configuration directories are always the first place to check.

    Examine the output for variables containing SSH credentials for the backend server. You should find entries that specify a username and password, formatted as environment variables with names that reference the backend system.

    Record both the username and password: you will use them in the next phase to establish an SSH connection to the backend server.

    Step 7: Retrieve the First Assessment Marker

    Retrieve the first marker via traversal

    The first assessment marker is also stored on the web server in a location accessible through the directory traversal. Look for marker or assessment files in the same area where you found the configuration.

    curl "http://<webserver_ip>/download?file=../config/assessment_marker.txt"

    Record the marker value: this is the first of three tokens you need to assemble the final flag.

    Phase 4: Lateral Movement

    With valid SSH credentials for the backend server, you can now pivot from the web server to the internal infrastructure: exactly as you did in Exercise 9A.

    Step 8: SSH to the Backend Server

    SSH to the backend server

    Use the credentials discovered in Step 6 to connect to the backend server over SSH.

    ssh <username>@<backend_ip>

    Replace <username> with the SSH user from the configuration file, and <backend_ip> with the second target IP from the Active Lab View. When prompted, enter the password you extracted.

    Confirm your privilege level on the backend

    After logging in, confirm your identity and assess your privilege level on the backend server.

    whoami
id

    The whoami command should return the username you logged in with, and the id output should show a standard user account. You are on the backend server, but you do not yet have root access.

    Step 9: Retrieve the Second Assessment Marker

    Read the second marker from the home directory

    The second marker is accessible to the user you logged in as. Check the user's home directory on the backend server.

    ls -la ~
cat ~/marker.txt

    Record the marker value alongside the first one from the web server.

    Phase 5: Privilege Escalation

    You have user-level access on the backend server, but the final assessment marker requires root privileges. Apply the same privilege escalation methodology from Exercise 9A.

    Step 10: Enumerate SUID Binaries

    Enumerate SUID binaries on the backend

    Search the filesystem for binaries with the SUID bit set: the same technique you used in Exercise 9A and learned in Week 7.

    find / -perm -4000 -type f 2>/dev/null

    Review the output and compare it against the standard set of SUID binaries. Look for anything unusual: a binary that does not normally have the SUID bit set is your escalation vector.

    Verify the suspicious binary permissions

    Verify the permissions on any suspicious binary you spotted.

    ls -la /usr/bin/<suspicious_binary>

    The -rwsr-xr-x permission string with root as the owner confirms the SUID bit is active. The s in the owner's execute position means this binary runs with root privileges regardless of who invokes it.

    Step 11: Exploit the SUID Binary to Escalate to Root

    Exploit the SUID binary for a root shell

    If you find the same SUID binary from Exercise 9A, the same exploitation technique applies. Use the -exec flag to spawn a root shell, and remember the -p flag to preserve the elevated privileges.

    find . -exec /bin/sh -p \; -quit

    The -p flag prevents the shell from dropping the inherited root privilege.

    Verify the root escalation

    Verify the escalation succeeded.

    whoami
id

    The whoami command should return root, and the id output should show euid=0(root).

    Step 12: Retrieve the Final Assessment Marker

    Read the final root-owned marker

    With root privileges, read the third and final marker.

    cat /root/flag.txt

    Record the marker value. You now have all three assessment markers:

    • Marker 1: from the web server's configuration directory (via directory traversal)
    • Marker 2: from the user's home directory on the backend server
    • Marker 3: from /root/flag.txt on the backend server (requires root)

    Assemble the three markers into the final flag using the OCR{...} format as indicated by the lab instructions.

    Analysis Questions

    1. Exercise 9A used command injection for initial access, while Challenge 9B used directory traversal. Both gave you access to sensitive information on the web server. Compare the two vulnerability types: which one gives the attacker more capability, and why might directory traversal still be considered equally dangerous in practice?

    Reveal Answer

    Command injection gives the attacker more raw capability because it allows execution of arbitrary commands, reading files, writing files, starting reverse shells, and modifying system configuration. Directory traversal is limited to reading files that the web server process has permission to access. However, directory traversal is equally dangerous in practice because the files it exposes (credentials, SSH keys, configuration secrets) frequently enable the attacker to gain full command execution through other means, such as SSH login with discovered credentials. The end result, full system compromise, is the same; the path is just different.

    2. Daniel Reeves stated that the backend server "should only be reachable by our operations team." Your assessment proved that an external attacker can reach it by pivoting through the web server. Propose two architectural changes that would prevent the lateral movement you performed, even if the web server is fully compromised.

    Reveal Answer

    First, implement network segmentation with firewall rules that prevent the web server from initiating SSH connections to the backend server. The web server should only communicate with the backend through a tightly scoped API, not through general-purpose protocols like SSH. Second, replace password-based SSH authentication with certificate-based authentication managed through a bastion host with multi-factor authentication. Even if an attacker discovers a password in a configuration file, it would be useless without the corresponding SSH certificate and access to the bastion host.

    3. You exploited the same SUID binary escalation technique from Exercise 9A. If this were a real engagement and you reported this finding, the client might fix only the specific SUID binary you exploited. Explain why this response would be insufficient and what a thorough remediation plan should include.

    Reveal Answer

    Fixing one SUID binary addresses a single symptom, not the root cause. A thorough remediation plan should include: (1) a full audit of all SUID and SGID binaries across every server, removing the SUID bit from any binary that does not require it; (2) implementing a regular audit schedule to detect new SUID binaries introduced by software updates or misconfigurations; (3) deploying a file integrity monitoring solution to alert on permission changes; and (4) applying the principle of least privilege to service accounts so that even if an attacker gains access as the deploy user, the account has minimal capabilities beyond its intended function.

    Key Takeaways

    • Directory traversal exploits applications that pass user-controlled filenames to file-read operations without validation: the ../ sequence lets an attacker navigate the filesystem and read any file the server process can access
    • Blind assessments test your ability to select the right technique at each phase without guidance: recognizing vulnerability types from application behavior is a core penetration testing skill
    • Configuration files are high-value targets in any file-read vulnerability: .env, app.env, and config/ directories frequently contain plaintext credentials that enable lateral movement
    • The same privilege escalation vectors appear across different environments: SUID binary exploitation is a transferable skill that applies to any Linux system with misconfigured permissions
    • Attack chain documentation (reconnaissance → exploitation → lateral movement → escalation) is the standard structure for penetration test reports and should be practiced in every engagement
