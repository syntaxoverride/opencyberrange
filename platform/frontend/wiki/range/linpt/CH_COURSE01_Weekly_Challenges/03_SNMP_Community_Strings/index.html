    Exercise 3: SNMP Community Strings

    Before You Begin

    Weeks 1 and 2 covered TCP-based port scanning and service enumeration using Nmap. Those scans rely on the TCP handshake to detect open ports; but not every network service uses TCP. Some critical management protocols run over UDP (User Datagram Protocol), which means a standard Nmap scan will miss them entirely. Your VPN must be connected and your terminal open before proceeding.

    Scenario

    Greystone Manufacturing operates a production facility in Pittsburgh, Pennsylvania. Their operational technology (OT) team recently deployed a network monitoring gateway to track equipment status across the factory floor. The gateway runs SNMP (Simple Network Management Protocol) for network management.

    Karl Weber, the OT Security Lead, is skeptical about the assessment: "SNMP is for monitoring; there is nothing sensitive there. We use the standard community string. The gateway sits on an internal network anyway."

    Your job is to prove otherwise. The SNMP service may expose more system information than Karl expects. Three assessment tokens have been embedded in the SNMP MIB (Management Information Base) data. Extract all three tokens using SNMP enumeration tools, combine them into the flag, and submit it.

    Your Objectives

    • Discover the SNMP service on the target using a UDP port scan
    • Enumerate system information using the default community string
    • Query specific OIDs (Object Identifiers) to extract embedded tokens from sysDescr, sysLocation, and sysContact
    • Perform a full SNMP walk to observe all available data
    • Combine the three tokens into the flag and submit it

    Background: SNMP and Community Strings

    SNMP (Simple Network Management Protocol) is a protocol used to monitor and manage network devices; routers, switches, servers, printers, and industrial control systems. Network administrators rely on SNMP to collect information such as CPU load, interface status, system uptime, and configuration details. SNMP operates over UDP port 161, which is why standard TCP scans do not detect it.

    Every SNMP-enabled device organizes its data in a tree structure called a MIB (Management Information Base). Each piece of data in the MIB tree has a unique address called an OID (Object Identifier), written as a dotted series of numbers. For example, the OID 1.3.6.1.2.1.1.1.0 points to sysDescr, which contains a text description of the device. Other common OIDs include sysLocation (1.3.6.1.2.1.1.6.0), which stores the device's physical location, and sysContact (1.3.6.1.2.1.1.4.0), which stores the administrator's contact information.

    Access control in SNMPv1 and SNMPv2c relies on community strings: plain-text passwords sent with every request. The default read-only community string on most devices is public. Many administrators never change the default, which means anyone on the network can query the device for its full MIB tree. Attackers use default community strings to harvest system details, network topology, and sometimes credentials or configuration data without any authentication.

    Tool Primer: snmpwalk

    snmpwalk: query the MIB tree

    The snmpwalk command queries an SNMP agent and retrieves data from its MIB tree. The tool "walks" through the tree starting at a given OID and returns every value beneath it. Below is the basic syntax you will use in the lab.

    snmpwalk -v2c -c public <target_ip> <OID>

    Each flag serves a specific purpose:

    • -v2c: use SNMP version 2c (the most common version on older and OT devices)
    • -c public: set the community string to public
    • <target_ip>: the IP address of the target device
    • <OID>: the starting point in the MIB tree (omit to walk the entire tree)

    Sample output when querying sysDescr:

    SNMPv2-MIB::sysDescr.0 = STRING: Greystone ICS Gateway v2.4; Token: <redacted>

    The output shows the OID name on the left (sysDescr.0) and the value on the right. The STRING: prefix indicates the data type. When you see Token: followed by a value, that value is one of the three tokens you need to extract.

    Step 2: Discover SNMP with a UDP Scan

    Scan UDP port 161 for SNMP

    Standard Nmap scans use TCP and will not detect SNMP because the protocol runs on UDP port 161. You need to run a UDP scan with the -sU flag to find it.

    nmap -sU -p 161 <target_ip>

    Replace <target_ip> with the IP shown in the Active Lab View. UDP scans are slower than TCP scans because UDP has no handshake; Nmap must wait for a response or a timeout for each probe. Targeting a single port (-p 161) keeps the scan fast.

    Expected output:

    PORT    STATE SERVICE
161/udp open  snmp

    The result confirms that SNMP is listening on UDP port 161. A state of open means the port responded to the probe. If you see open|filtered, the port may still be accessible; proceed with snmpwalk to confirm.

    Step 3: Query sysDescr and Extract Token 1

    Query sysDescr for token 1

    The sysDescr OID (1.3.6.1.2.1.1.1.0) contains a text description of the device. Query it using snmpwalk with the public community string.

    snmpwalk -v2c -c public <target_ip> 1.3.6.1.2.1.1.1.0

    The output will include a description of the Greystone ICS Gateway along with an embedded token. Look for the text following Token: in the response. Write down the token value; you will need it later to assemble the complete flag.

    Step 4: Query sysLocation and Extract Token 2

    Query sysLocation for token 2

    The sysLocation OID (1.3.6.1.2.1.1.6.0) stores the physical location of the device. Query it with the same community string.

    snmpwalk -v2c -c public <target_ip> 1.3.6.1.2.1.1.6.0

    The response will include location information about the Greystone facility and a second embedded token after Token:. Record the token value alongside your first token.

    Step 5: Query sysContact and Extract Token 3

    Query sysContact for token 3

    The sysContact OID (1.3.6.1.2.1.1.4.0) holds the administrator's contact information. Query it the same way.

    snmpwalk -v2c -c public <target_ip> 1.3.6.1.2.1.1.4.0

    The output will contain contact details and a third token after Token:. You now have all three tokens needed to build the flag.

    Step 6: Perform a Full SNMP Walk

    Walk the full system subtree

    Now that you have extracted the three tokens, run a full walk of the system subtree to see what else the SNMP agent exposes. Understanding the full scope of SNMP exposure is a key assessment skill.

    snmpwalk -v2c -c public <target_ip> system

    The system keyword tells snmpwalk to start at the top of the system MIB group and walk through every OID beneath it. Scroll through the output and observe the types of information available; system uptime, hostname, object IDs, and more. On a production device, a full walk might reveal network interface details, routing tables, or software versions that an attacker could use to plan further attacks.

    Step 7: Interpret the Results

    Review the data you collected from each SNMP query and consider what it reveals about the target.

    • sysDescr disclosed the device type, firmware version, and a descriptive label. An attacker could use version information to search for known vulnerabilities affecting that specific firmware
    • sysLocation revealed the physical location of the device. Physical location data helps an attacker map out the facility and identify high-value areas on the factory floor
    • sysContact exposed administrator contact details. Contact information can feed social engineering attacks; an attacker could impersonate IT staff or reference specific personnel names to build credibility

    Karl assumed SNMP was harmless because the gateway sits on an internal network. The data you extracted demonstrates that even "monitoring-only" protocols can leak operationally sensitive information when protected by default community strings.

    Flag Format

    Assemble the flag using the tokens in the order you discovered them:

    OCR{________}

    Where sysDescr is the token from the sysDescr query (Step 3), sysLocation is the token from the sysLocation query (Step 4), and sysContact is the token from the sysContact query (Step 5).

    Step 8: Submit the Flag

    Combine all three tokens into the flag format. The flag follows the pattern OCR{...} where the three token values are joined with underscores. Paste the assembled flag into the Submit Flag form on the platform and click Submit.

    Analysis Questions

    Consider the following questions based on what you observed during the lab. Each question is followed by an answer you can use to check your reasoning.

    1. Why did a standard Nmap scan (without the -sU flag) fail to detect SNMP on the target?

    Reveal Answer

    SNMP runs on UDP port 161, not TCP. A default Nmap scan sends TCP SYN packets, which only detect TCP-based services. UDP services require the -sU flag because UDP has no handshake; Nmap must send a UDP probe and wait for either a response or a timeout. Without -sU, SNMP is invisible to the scan.

    2. The community string "public" gave you read access to the entire MIB tree. What could an attacker do if the community string provided write access?

    Reveal Answer

    Write access through a community string like private would allow an attacker to modify device configuration remotely; changing the system location, disabling interfaces, altering routing tables, or even loading new firmware. On an OT gateway, write access could disrupt manufacturing processes or disable safety monitoring systems.

    3. Karl argued that SNMP is safe because the gateway is on an internal network. What is the flaw in that reasoning?

    Reveal Answer

    Internal networks are not inherently safe. An attacker who gains access through phishing, a compromised workstation, or a misconfigured firewall rule can pivot into the internal network and query SNMP services. Defense in depth requires securing services regardless of network location; change default community strings, restrict SNMP access to specific management stations, and upgrade to SNMPv3 with authentication and encryption.

    Key Takeaways

    • UDP scanning requires the -sU flag in Nmap; standard TCP scans will miss protocols like SNMP, DNS, and TFTP that run exclusively over UDP
    • SNMP community strings function as plain-text passwords, and the default value public is left unchanged on a large number of production devices
    • MIB trees organize device data into a hierarchical structure addressable by OIDs, exposing system descriptions, locations, contact details, network interfaces, and more
    • Default configurations are a recurring vulnerability; the security of a protocol depends on how it is configured, not on the protocol's intended purpose
    • Week 4 builds on these enumeration skills by introducing new protocols and deeper service interrogation techniques
