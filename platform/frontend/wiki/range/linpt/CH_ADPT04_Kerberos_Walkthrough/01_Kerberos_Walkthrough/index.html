    Exercise 1.4: Kerberos Walkthrough

    Before You Begin

    Kerberos is the protocol behind nearly every offensive Active Directory attack worth knowing. ASREPRoast attacks the AS-REP message. Kerberoast attacks the TGS-REP message. Golden ticket forges a TGT inside an AS-REP. Silver ticket forges a TGS-REP. None of these attacks make sense until you can name the four messages of the Kerberos exchange and point at which fields they manipulate.

    Exercise 1.4 puts the protocol in front of you on the wire. You will run tshark while triggering authentications, decode the AS-REQ, AS-REP, TGS-REQ, and TGS-REP messages, and pull a flag fragment out of three different message fields.

    Tools required: tshark, wireshark, smbclient, kinit. All are pre-installed on Kali.

    Scenario

    Marcus Bell: "Every Kerberos attack worth knowing exploits one specific message in the exchange. You cannot abuse what you do not understand. Capture the protocol, read it, name the parts. Three fragments of the flag are split across three Kerberos message fields. Find them all, concatenate them in the order AS-REQ + AS-REP + TGS-REQ, and submit."

    Credentials:

    Username Password
    j.chen Welcome2026#

    Domain: corp.nordport.local Domain controller: corp-dc01

    Your Objectives

    • Capture Kerberos AS-REQ and AS-REP exchanges between your Kali and the DC
    • Capture a TGS-REQ and TGS-REP triggered by an SMB connection to a member service
    • Identify the encrypted-timestamp field in the AS-REQ
    • Locate the TGT inside the AS-REP
    • Read the sname field in a TGS-REQ to identify the service requested
    • Concatenate three fragments and submit the assembled flag

    Background: The Four Messages of Kerberos

    Kerberos answers two questions: "who are you?" and "what may you talk to?" It separates the two by issuing two different kinds of tickets.

    Ticket Lifecycle at a Glance

    The diagram below collapses an entire authentication-to-service-access flow into one picture. Hold this in your head for the rest of the track; every Kerberos attack twists exactly one arrow on this diagram.

    sequenceDiagram
    autonumber
    participant C as Client (Kali / j.chen)
    participant K as KDC (corp-dc01)
    participant S as Service (cifs/file01)

    Note over C,K: Step 1 -- Authentication (AS exchange)
    C->>K: AS-REQ<br/>cname=j.chen, padata=ENC-TIMESTAMP(user_key)
    K-->>C: AS-REP<br/>TGT enc with krbtgt_key + session_key enc with user_key

    Note over C,K: Step 2 -- Authorization (TGS exchange)
    C->>K: TGS-REQ<br/>TGT in padata, sname=cifs/file01
    K-->>C: TGS-REP<br/>service ticket enc with service_key

    Note over C,S: Step 3 -- Service access (AP exchange)
    C->>S: AP-REQ<br/>service ticket presented over SMB
    S-->>C: AP-REP / SMB session established

    AS-REQ / AS-REP: identity

    The Authentication Service exchange proves who you are and gives you a Ticket Granting Ticket (TGT).

    Client                                                    KDC (DC)
  |                                                          |
  |  AS-REQ  (cname=j.chen, realm=CORP.NORDPORT.LOCAL,       |
  |          padata: pA-ENC-TIMESTAMP encrypted with         |
  |          the user's password-derived key)                |
  |--------------------------------------------------------->|
  |                                                          |
  |                                          [KDC verifies   |
  |                                           timestamp can  |
  |                                           be decrypted   |
  |                                           with user key] |
  |                                                          |
  |  AS-REP  (TGT encrypted with krbtgt's key,               |
  |          enc-part with session key encrypted to user)    |
  |<---------------------------------------------------------|

    The pre-authentication padata is the security boundary that ASREPRoast attacks. If pre-auth is disabled (DONT_REQ_PREAUTH flag), the KDC sends an AS-REP without checking the timestamp first. The encrypted enc-part is then crackable offline because it is encrypted with a derivation of the user's password.

    TGS-REQ / TGS-REP: authorization

    Once you have a TGT you ask the KDC for service tickets, one per service you want to talk to.

    Client                                                    KDC
  |                                                          |
  |  TGS-REQ (TGT in padata, sname=cifs/file01, ...)         |
  |--------------------------------------------------------->|
  |                                                          |
  |                                          [KDC validates  |
  |                                           TGT, checks    |
  |                                           that user can  |
  |                                           access target] |
  |                                                          |
  |  TGS-REP (service ticket encrypted with the              |
  |          target service account's key)                   |
  |<---------------------------------------------------------|
  |                                                          |
  |                                                       Service
  |  AP-REQ  (service ticket presented to the service)       |
  |--------------------------------------------------------->|

    The service ticket is encrypted with the service account's password-derived key, not the user's. That is the boundary Kerberoast attacks. If the service account password is weak, the encrypted blob can be cracked offline. The TGS-REQ itself is observable on the wire to anyone watching the KDC; that is how SOC tools detect mass enumeration.

    The four-message map

    Message Purpose Encrypted with
    AS-REQ Request a TGT, prove identity User's key (in pA-ENC-TIMESTAMP)
    AS-REP TGT issued TGT body: krbtgt key. Enc-part: user key.
    TGS-REQ Request a service ticket TGT presented as proof
    TGS-REP Service ticket issued Ticket body: service account key. Enc-part: TGT session key.

    Memorize this table. It is the framework every Kerberos attack maps to.

    Which Attack Touches Which Message

    Each major Kerberos attack hijacks exactly one of the four messages. The map below tells you where on the wire each technique lives. Refer back here when you reach Levels 3 through 5 of the track.

    flowchart TD
    AS_REQ["AS-REQ<br/>(client to KDC)"]
    AS_REP["AS-REP<br/>(KDC to client)"]
    TGS_REQ["TGS-REQ<br/>(client to KDC)"]
    TGS_REP["TGS-REP<br/>(KDC to client)"]

    AS_REP -- "no preauth -> crackable" --> ASREP["ASREPRoast<br/>(Hashcat 18200)"]
    TGS_REP -- "weak service pw -> crackable" --> KROAST["Kerberoast<br/>(Hashcat 13100)"]
    AS_REP -- "forge TGT body w/ krbtgt key" --> GOLD["Golden Ticket"]
    TGS_REP -- "forge service ticket w/ service key" --> SILV["Silver Ticket"]
    TGS_REQ -- "S4U2self + S4U2proxy" --> DEL["Delegation abuse<br/>(constrained / RBCD)"]

    Tool Primer

    tshark

    The CLI version of Wireshark. Lighter than the GUI, scriptable, and handles all the same dissectors.

    sudo tshark -i any -f "host <dc_ip> and port 88" -w kerb.pcap
    Flag Effect
    -i any capture on any interface
    -f "..." BPF filter to keep the capture small (port 88 is Kerberos)
    -w kerb.pcap write to a file you can open in Wireshark later

    To analyze a capture file from the CLI:

    tshark -r kerb.pcap -V -Y "kerberos.msg_type == 10"   # AS-REQ
tshark -r kerb.pcap -V -Y "kerberos.msg_type == 11"   # AS-REP
tshark -r kerb.pcap -V -Y "kerberos.msg_type == 12"   # TGS-REQ
tshark -r kerb.pcap -V -Y "kerberos.msg_type == 13"   # TGS-REP

    Kerberos message types are integers; remember 10/11/12/13.

    Wireshark Kerberos display filters

    Filter Matches
    kerberos All Kerberos packets
    kerberos.msg_type == 10 AS-REQ
    kerberos.msg_type == 11 AS-REP
    kerberos.msg_type == 12 TGS-REQ
    kerberos.msg_type == 13 TGS-REP
    kerberos.CNameString == "j.chen" Packets where the cname is j.chen
    kerberos.SNameString == "cifs" Service tickets for cifs

    kinit (manual TGT request)

    kinit j.chen@CORP.NORDPORT.LOCAL

    kinit performs a clean AS-REQ/AS-REP cycle and stores the resulting TGT in your local credential cache (klist to view). Useful for triggering an isolated AS exchange without the side effects of a full SMB connect.

    smbclient (TGS triggering)

    Once you have a TGT in cache, an SMB connect to a domain-joined host triggers a TGS-REQ for cifs/<host>.

    smbclient //corp-dc01/Public -k

    The -k flag tells smbclient to use the cached Kerberos credential rather than prompting for a password.

    Walkthrough

    Step 1: Launch the Exercise

    Launch Kerberos Walkthrough from the AD Penetration Track. Note the DC IP from the Active Lab View.

    Step 2: Configure Your Kerberos Realm

    Linux Kerberos clients (kinit, klist, kdestroy, anything that speaks GSSAPI) read /etc/krb5.conf to find out which KDC serves which realm and how to talk to it. Without this file every Kerberos call defaults to either no realm at all or whatever Kerberos picks up from DNS SRV records, which is fragile.

    Kali - Configure /etc/krb5.conf

    sudo tee /etc/krb5.conf >/dev/null <<EOF
[libdefaults]
    default_realm = CORP.NORDPORT.LOCAL
    dns_lookup_kdc = true
    dns_lookup_realm = false

[realms]
    CORP.NORDPORT.LOCAL = {
        kdc = <dc_ip>
        admin_server = <dc_ip>
    }

[domain_realm]
    .corp.nordport.local = CORP.NORDPORT.LOCAL
    corp.nordport.local = CORP.NORDPORT.LOCAL
EOF

    What each piece does:

    • sudo tee /etc/krb5.conf >/dev/null write standard input to the file as root, redirecting tee's stdout to /dev/null so the heredoc doesn't echo back.
    • <<EOF ... EOF heredoc; the lines between are sent to tee as input.
    • [libdefaults] default_realm = CORP.NORDPORT.LOCAL the realm to assume when one is not specified. Kerberos realm names are conventionally the uppercase form of the domain FQDN.
    • dns_lookup_kdc = true if a realm is not in the [realms] block, ask DNS for _kerberos._tcp.<realm> SRV records. AD publishes these by default.
    • dns_lookup_realm = false do NOT trust DNS to map a hostname to a realm; use the explicit [domain_realm] mapping below. Disabling this avoids spoofing risk in untrusted networks.
    • [realms] block: maps each realm name to a list of KDCs. kdc = <dc_ip> says "this IP is a KDC for CORP.NORDPORT.LOCAL". admin_server is the host that handles password changes via kpasswd (port 464); same IP for AD.
    • [domain_realm] maps DNS-style hostnames to Kerberos realms. The leading dot form (.corp.nordport.local) matches all subdomains; the bare form matches the realm itself.

    Replace <dc_ip> with the IP shown in the lab dashboard. Verify with cat /etc/krb5.conf after writing.

    Step 3: Start the Capture

    Open two terminals: one for tshark to capture packets, one to drive the auth flow. Capturing is read-only; nothing depends on the order between the two terminals other than starting tshark BEFORE the auth so you do not miss the first packets.

    Kali - Start tshark capturing all Kerberos traffic

    sudo tshark -i any -f "host <dc_ip> and (port 88 or port 445)" \
  -w /tmp/kerb.pcap

    What each option does:

    Flag Effect
    sudo Required: only root can put an interface in promiscuous mode and read raw packets.
    -i any Capture on every available interface. tshark merges packets from all NICs into one stream. Use -i eth0 to limit to one interface.
    -f "host <dc_ip> and (port 88 or port 445)" BPF (Berkeley Packet Filter) capture filter. Applied at kernel level, drops non-matching packets before tshark sees them. Drastically reduces capture file size.
    -w /tmp/kerb.pcap Write captured packets to a file in pcap format. Without -w, tshark prints to stdout (one line per packet).

    The BPF filter explained:

    • host <dc_ip> packets where source OR destination matches the DC IP.
    • port 88 or port 445 Kerberos (88) OR SMB (445). Kerberos rides over both UDP and TCP/88; SMB carries the AP-REQ tickets we want to inspect.
    • The combination: capture every packet to or from the DC on those two ports.

    Leave tshark running in this terminal. The pcap grows until you Ctrl-C the process. Open a SECOND terminal for the next steps.

    Step 4: Trigger the AS Exchange

    kinit performs a clean AS-REQ/AS-REP cycle and stores the resulting TGT in the local credential cache. Useful for triggering an isolated AS exchange without the side effects of a full SMB connect.

    Kali - Request a TGT for j.chen

    echo 'Welcome2026#' | kinit j.chen@CORP.NORDPORT.LOCAL
klist

    What each piece does:

    • echo 'Welcome2026#' | kinit ... pipe the password into kinit's stdin. By default kinit prompts interactively; piping skips the prompt.
    • kinit j.chen@CORP.NORDPORT.LOCAL request a TGT for the principal j.chen in the realm CORP.NORDPORT.LOCAL. The realm form is user@REALM (always uppercase realm).
    • klist list cached tickets. After a successful kinit you see one TGT (krbtgt/CORP.NORDPORT.LOCAL@CORP.NORDPORT.LOCAL) with a 10-hour default lifetime.

    Common errors:

    • kinit: Clock skew too great while getting initial credentials: your Kali clock differs from the DC's by more than 5 minutes. Fix: sudo ntpdate -u <dc_ip> (uses the DC's clock as the reference) or sudo timedatectl set-ntp true if your network has working NTP.
    • kinit: Pre-authentication failed while getting initial credentials: wrong password.
    • kinit: Cannot find KDC for realm: /etc/krb5.conf is missing or the realm name is wrong.

    Step 5: Trigger the TGS Exchange

    Once you have a TGT cached, the next step in normal Kerberos flow is requesting a service ticket (TGS) for some service. Connecting to SMB on the DC triggers a TGS-REQ for cifs/<host>.

    Kali - Trigger a TGS-REQ for cifs/corp-dc01

    smbclient //corp-dc01/Public -k -c "ls"

    What each option does:

    • //corp-dc01/Public UNC path: SMB connect to the Public share on corp-dc01. Use the FQDN or short name; smbclient resolves it via /etc/hosts, then DNS, then NetBIOS.
    • -k use Kerberos authentication: present the cached TGT to the KDC and exchange it for a TGS for cifs/<host>. WITHOUT -k, smbclient falls back to NTLM and uses the password from -U (no Kerberos exchange happens at all).
    • -c "ls" non-interactive: run ls then exit.

    What happens on the wire (visible in the pcap):

    1. Client sends TGS-REQ to KDC, padata contains the TGT-wrapped AP-REQ.
    2. KDC returns TGS-REP with a service ticket encrypted with corp-dc01$'s machine key.
    3. Client opens TCP/445 to corp-dc01 and presents the service ticket inside an AP-REQ.
    4. corp-dc01 decrypts and accepts; SMB session established; share lists.

    Once the share lists, stop the capture in the first terminal with Ctrl-C.

    Step 6: Analyze AS-REQ for Fragment 1

    Open the captured pcap and filter to the AS-REQ packets only. tshark in read mode (no -i, just -r) is the same dissector as Wireshark with no GUI overhead.

    Kali - Read the AS-REQ packet

    tshark -r /tmp/kerb.pcap -V -Y "kerberos.msg_type == 10" | less

    What each option does:

    Flag Effect
    -r /tmp/kerb.pcap Read mode: parse this pcap file instead of capturing live.
    -V Verbose: print the FULL dissector tree (every protocol layer, every field). Without -V, tshark prints a one-line summary per packet.
    -Y "kerberos.msg_type == 10" Display filter (different from BPF capture filter). Applied AFTER dissection; can reference parsed fields like kerberos.msg_type. The integer 10 is the AS-REQ Kerberos message type.
    \| less Page the output (verbose dissector trees are tens of lines per packet). Use space/b for next/previous page, q to quit.

    Kerberos message types worth memorizing: AS-REQ=10, AS-REP=11, TGS-REQ=12, TGS-REP=13. Every Kerberos attack maps to one of these.

    Inside the AS-REQ you will see:

    Kerberos
    Pvno: 5
    MSG Type: AS-REQ (10)
    padata: 1 item
        PA-DATA pA-ENC-TIMESTAMP
            padata-type: pA-ENC-TIMESTAMP (2)
            padata-value: <encrypted bytes>
    req-body
        cname: j.chen
        realm: CORP.NORDPORT.LOCAL
        sname: krbtgt/CORP.NORDPORT.LOCAL

    The pA-ENC-TIMESTAMP value is the encrypted-timestamp field. Its presence is the proof of pre-authentication; an account with DONT_REQ_PREAUTH would have no such field. Fragment 1 is the literal string kdc; the answer to the question "what acronym is the KDC role?". The hint that this is the right fragment lives in priya.ramanathan's description attribute (your config script seeded it there).

    Confirm the hint:

    Kali - Confirm Fragment 1 from priya.ramanathan's description

    ldapsearch -x -LLL -H ldap://<dc_ip> \
  -D "CORP\j.chen" -w 'Welcome2026#' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(sAMAccountName=priya.ramanathan)" description

    The description ends with Kerberos protocol fragment hint: kdc. Fragment 1 = kdc.

    Step 7: Analyze AS-REP for Fragment 2

    Kali - Read the AS-REP packet

    tshark -r /tmp/kerb.pcap -V -Y "kerberos.msg_type == 11" | less

    Inside the AS-REP:

    Kerberos
    Pvno: 5
    MSG Type: AS-REP (11)
    crealm: CORP.NORDPORT.LOCAL
    cname: j.chen
    ticket
        tkt-vno: 5
        realm: CORP.NORDPORT.LOCAL
        sname: krbtgt/CORP.NORDPORT.LOCAL
        enc-part: <encrypted with krbtgt key>
    enc-part: <encrypted with user key, contains session key>

    The TGT body lives in the ticket field. The service name (sname) of a TGT is always krbtgt/<REALM>. Fragment 2 is the literal string speaks; the verb that describes what the KDC is doing in the AS-REP (it speaks the TGT into existence).

    Step 8: Analyze TGS-REQ for Fragment 3

    Kali - Read the TGS-REQ packet

    tshark -r /tmp/kerb.pcap -V -Y "kerberos.msg_type == 12" | less

    Inside the TGS-REQ:

    Kerberos
    Pvno: 5
    MSG Type: TGS-REQ (12)
    padata: 1 item
        PA-DATA pA-TGS-REQ
            <AP-REQ wrapping the TGT>
    req-body
        sname:
            name-type: kRB5-NT-SRV-INST (2)
            sname-string: cifs
            sname-string: corp-dc01.corp.nordport.local

    The sname.name-string array tells the KDC which service the client is requesting. The first element is the service class (cifs). The second is the host. Fragment 3 is the literal string 4_messages; the count that completes the workbook's main lesson, "the KDC speaks 4 messages."

    Step 9: Assemble and Submit

    Concatenate Fragment 1 + Fragment 2 + Fragment 3, wrap in OCR{...} joined with underscores per the protocol field naming.

    Kali - Assemble the flag

    F1='kdc'
F2='speaks'
F3='4_messages'
echo "OCR{${F1}_${F2}_${F3}}"

    The output is your assembled flag in the form OCR{<F1>_<F2>_<F3>}. Submit it on the platform.

    Blue Team Perspective

    Every Kerberos exchange leaves a security event on the DC. The four events below cover almost every detection a SOC writes for the protocol; learn what they look like clean so you recognize the abuse cases in later exercises.

    Activity Event ID Where it fires
    AS-REQ -> AS-REP success 4768 (TGT issued) DC Security log
    AS-REQ pre-auth failure 4771 (Pre-authentication failed) DC Security log
    TGS-REQ -> TGS-REP success 4769 (Service ticket requested) DC Security log
    TGS-REQ failure 4773 DC Security log

    What attacks look like in 4768/4769

    A normal user's daily activity produces one or two 4768 events (one TGT in the morning, maybe one after a renewal) and a steady trickle of 4769 events (one per distinct service contacted). ASREPRoast looks like a 4768 with Pre-Authentication Type: 0; the giveaway. Kerberoast shows up as a burst of 4769 events from a single user requesting many SPNs in seconds, often with Ticket Encryption Type: 0x17 (RC4) when the attacker forces a downgrade to make cracking faster.

    Hardening Note

    Kerberos is fundamentally trust-on-key. You harden it by raising the cost of forging or cracking those keys.

    Practical Kerberos hardening

    • Rotate the krbtgt account password twice every 6-12 months. The double rotation invalidates lingering golden tickets without breaking active sessions.
    • Disable RC4 Kerberos encryption forest-wide. Force AES-128/256 via msDS-SupportedEncryptionTypes so kerberoast cracking takes orders of magnitude longer.
    • Move all service accounts to gMSAs (Group Managed Service Accounts). The KDC manages and rotates the password automatically; the resulting hash is far too long to crack offline.
    • Audit and clear the DONT_REQ_PREAUTH UAC bit on every account quarterly.
    • Forward 4768/4769/4771 to a SIEM with detection rules for: pre-auth = 0, encryption type = 0x17 on a service ticket, multiple SPNs requested by the same user inside one minute.

    Analysis Questions

    1. ASREPRoast targets the AS-REP message. What specifically about pre-authentication makes the AS-REP attackable, and why is DONT_REQ_PREAUTH so rare in modern environments?

    Reveal Answer

    Pre-authentication means the AS-REQ includes a timestamp encrypted with the user's password-derived key. The KDC verifies that timestamp before issuing an AS-REP. If verification fails the KDC returns an error rather than an encrypted blob, so an attacker cannot get a crackable ciphertext from a guess. With DONT_REQ_PREAUTH set on a user, the KDC skips the timestamp check and returns an AS-REP whose enc-part is encrypted with the user's key. That blob is then crackable offline. DONT_REQ_PREAUTH is rare today because Microsoft turns pre-auth on by default, modern provisioning rarely disables it, and detection tools flag the AUC bit. It typically survives only on legacy service accounts where pre-auth was disabled to support an old protocol that did not implement it (often early 2000s integrations) and was never re-enabled.

    2. Kerberoast targets the TGS-REP. Which key encrypts the service ticket, and why is the strength of that key the entire game?

    Reveal Answer

    The service ticket inside a TGS-REP is encrypted with the service account's password-derived key (not the user's, not the KDC's). When you request a TGS-REP for an SPN that resolves to a domain user account (typical for service accounts that auto-register an SPN like MSSQLSvc/...), the encrypted blob you get back is essentially a hash of the service account's password under your chosen ticket. If the service account's password is weak, you can crack the blob offline with hashcat mode 13100. The TGS-REP looks like normal traffic: any authenticated user is allowed to request a TGS for any SPN, and the KDC has no way to know whether the requester intends to actually use the ticket. The defense is strong service account passwords (managed service accounts, gMSAs); not blocking the request itself.

    3. The TGS-REQ presents the TGT as proof of identity inside its padata. If you forge a TGT (golden ticket), every TGS-REQ you make will be accepted. Why does a forged TGT survive password rotation of normal users but not rotation of a special account?

    Reveal Answer

    A golden ticket is a TGT forged with the krbtgt account's NTLM hash. The KDC validates incoming TGTs by decrypting them with krbtgt's key. Since you encrypted the forged TGT with the same key, the KDC accepts it as authentic. Rotating the password of any normal user does not change krbtgt and therefore does not invalidate the forged TGT. Only rotating krbtgt (twice, since the previous and current passwords are both honored briefly) invalidates the forgery. Most organizations have never rotated krbtgt. The "rotate twice" recommendation exists because rotating once leaves a window where forged tickets encrypted with the old key are still accepted; the second rotation discards the old key entirely. Treat krbtgt as a Tier-0 secret on par with the Domain Admin password.

    Key Takeaways

    • Kerberos has four messages: AS-REQ (10), AS-REP (11), TGS-REQ (12), TGS-REP (13). Memorize the numbers; tshark filters them by integer.
    • AS-REP is encrypted with the user's key (target of ASREPRoast).
    • TGS-REP service ticket is encrypted with the service account's key (target of Kerberoast).
    • TGT is encrypted with krbtgt's key (target of golden ticket forgery).
    • Pre-authentication is the timestamp encrypted in the AS-REQ; its absence makes the AS-REP attackable.
    • kinit produces a clean AS exchange; the first SMB connect after kinit produces a clean TGS exchange.

    Spaced Repetition

    Card 1: Four Kerberos Message Types

    Q: Name the four core Kerberos message types and their integer codes.

    Answer

    AS-REQ (10); client requests a TGT. AS-REP (11); KDC issues a TGT. TGS-REQ (12); client requests a service ticket using the TGT as proof. TGS-REP (13); KDC issues a service ticket. Memorize 10/11/12/13 because tshark and Wireshark display filters use the integers.

    Card 2: Which Key Encrypts What

    Q: For each of AS-REP enc-part, AS-REP TGT body, TGS-REP enc-part, and TGS-REP service ticket body, name the key that encrypts it.

    Answer

    AS-REP enc-part: the user's password-derived key (target of ASREPRoast). AS-REP TGT body: the krbtgt account's key (target of golden ticket forgery). TGS-REP enc-part: the TGT session key (held by the user and the KDC). TGS-REP service ticket body: the service account's password-derived key (target of Kerberoast).

    Card 3: tshark Display Filter for Each Message

    Q: Write the tshark -Y filter expression for each of AS-REQ, AS-REP, TGS-REQ, and TGS-REP.

    Answer

    kerberos.msg_type == 10 (AS-REQ), kerberos.msg_type == 11 (AS-REP), kerberos.msg_type == 12 (TGS-REQ), kerberos.msg_type == 13 (TGS-REP). Combine with && and kerberos.CNameString == "user" to filter to a specific principal.

    Card 4: Triggering a Clean TGS-REQ from Linux

    Q: With kinit already cached, write the smbclient command that produces exactly one TGS-REQ for the cifs service of srv01.corp.local.

    Answer 
    smbclient //srv01.corp.local/Share -k -c "ls"

    -k tells smbclient to use the cached Kerberos credential. The first connect triggers a TGS-REQ for cifs/srv01.corp.local@CORP.LOCAL. Subsequent connects within the ticket lifetime reuse the cached TGS.

    Card 5: pA-ENC-TIMESTAMP and ASREPRoast

    Q: What field in the AS-REQ proves pre-authentication, and what user account control flag disables it?

    Answer

    The padata array contains a pA-ENC-TIMESTAMP element whose value is a timestamp encrypted with the user's password-derived key. Its presence proves the user knows the password. The DONT_REQ_PREAUTH UAC flag (0x400000, decimal 4194304) disables the requirement; the KDC then issues an AS-REP without the check, exposing the encrypted enc-part to offline cracking via Hashcat mode 18200. Find ASREPRoastable accounts with the LDAP filter (userAccountControl:1.2.840.113556.1.4.803:=4194304).
