    Exercise WS-1.1: Domain Controller Port Discovery

    Before You Begin

    Exercise WS-1.1 is the first exercise in the Windows Server track. No prior exercise results are needed, but you should confirm that your VPN connection to the Open Cyber Range is active and that your Kali Linux attack box can reach the target host dc01.

    Prerequisites:

    • Active VPN connection to the lab environment
    • Terminal access on your Kali Linux attack box
    • The nmap and dig commands available in your PATH

    Scenario

    You are a junior penetration tester at CyberShield Consulting. Your team has been engaged to assess a corporate Active Directory (AD) environment. Your first task is to perform initial reconnaissance against a suspected Domain Controller (DC) at hostname dc01. You need to identify the services running on the host and confirm whether the machine is functioning as a DC.

    Your Objectives

    1. Perform a targeted TCP port scan against dc01 to identify AD-related services
    2. Identify AD-specific ports: 88 (Kerberos), 389 (LDAP), 636 (LDAPS), 3268 (Global Catalog)
    3. Run DNS queries to confirm the DC role
    4. Retrieve the flag from a DNS TXT record

    Background: Domain Controller Port Signatures

    A Domain Controller is the most service-dense host in any Windows domain. Because the DC must handle authentication, name resolution, directory queries, file replication, and group policy distribution, the server listens on a predictable set of TCP ports. Recognizing the pattern of open ports is often the fastest way to confirm that a host is a DC.

    The signature that distinguishes a Domain Controller from a regular Windows server is the combination of Kerberos (port 88), LDAP (port 389), and Global Catalog (port 3268). A member server might run DNS or SMB (Server Message Block), but only a DC exposes Kerberos and the Global Catalog service. When you see ports 88, 389, 636, and 3268 open alongside DNS (53) and SMB (445), you can be confident the target is a Domain Controller.

    Tool Primer: nmap

    Nmap is the standard network scanner for discovering hosts and services on a network. The command syntax for a targeted service-version scan is shown below.

    nmap -sV -p <port-list> <target>

    The flags break down as follows:

    Flag Purpose
    -sV Probe open ports to determine service name and version
    -p Specify a comma-separated list of ports to scan

    Nmap outputs a table with four columns for each scanned port: the port number, its state (open, closed, or filtered), the service name, and the detected version. A sample output line looks like the following:

    88/tcp   open  kerberos-sec  Microsoft Windows Kerberos

    When scanning a known target with a specific port list, the scan completes in seconds. Scanning all 65,535 ports is unnecessary when you already know which services to look for on a DC.

    Tool Primer: dig

    The dig command (Domain Information Groper) queries DNS servers directly. You will use dig to query specific record types against the target DC.

    dig <record-type> <name> @<server>
    Parameter Purpose
    <record-type> The DNS record type: A, AAAA, TXT, MX, AXFR, PTR, etc.
    <name> The fully qualified domain name to query
    @<server> The DNS server to query (the DC in these exercises)

    A TXT record query returns arbitrary text strings stored in DNS. Administrators sometimes use TXT records for SPF (Sender Policy Framework) entries, domain verification tokens, and other metadata.

    Walkthrough

    Step 1: Run a Targeted Port Scan

    Scan the DC for AD service ports

    Open a terminal on your Kali attack box and run the following Nmap command. The port list covers the standard AD services plus RDP and WinRM (Windows Remote Management).

    nmap -sV -p 53,88,135,139,389,445,636,3268,3389,5985 dc01

    Nmap will take a few seconds to probe each port and attempt service-version detection. Watch the output for the STATE column; you are looking for ports reported as open.

    Step 2: Read the Scan Results

    Review the Nmap output carefully. You should see a results table similar to the following (version strings may vary):

    PORT     STATE SERVICE       VERSION
53/tcp   open  domain        Simple DNS Plus
88/tcp   open  kerberos-sec  Microsoft Windows Kerberos
389/tcp  open  ldap          Microsoft Windows Active Directory LDAP
...
(additional ports omitted; check your own output)

    Focus on the AD-critical ports. Port 88 (Kerberos), port 389 (LDAP), port 636 (LDAPS; LDAP over TLS), and port 3268 (Global Catalog) together confirm that dc01 is a Domain Controller, not a regular member server.

    Step 3: Confirm the DC Role with a DNS Query

    Query the Kerberos SRV record

    A Domain Controller that also runs a DNS server registers special SRV (Service Locator) records in the domain's DNS zone. Query for the Kerberos SRV record to confirm the DC role.

    dig SRV _kerberos._tcp.corp.ocr-range.lab @dc01

    The response should include a record pointing to dc01.corp.ocr-range.lab on port 88. The presence of the Kerberos SRV record is definitive proof that the DNS server knows about an AD domain named corp.ocr-range.lab and that dc01 is registered as a Kerberos Key Distribution Center (KDC) for that domain.

    Step 4: Query for DNS TXT Records

    Query the flag TXT record

    DNS TXT records can hold arbitrary text. Query for a TXT record at _flag.corp.ocr-range.lab to check for useful information.

    dig TXT _flag.corp.ocr-range.lab @dc01

    Examine the ANSWER SECTION of the dig output. TXT record values are enclosed in double quotes in the response.

    Step 5: Interpret the Results

    Review your findings table and answer the following questions for yourself before moving on:

    • Which ports confirmed that dc01 is a Domain Controller rather than a standard Windows server?
    • What domain name did the SRV record reveal?
    • Why would a penetration tester scan a specific port list rather than scanning all 65,535 ports during initial AD reconnaissance?

    Port 88 (Kerberos) and port 3268 (Global Catalog) are the two most distinctive indicators of a Domain Controller. Member servers do not run Kerberos KDC services or host the Global Catalog. The combination of these ports with LDAP (389) and DNS (53) forms a fingerprint that is unique to a DC.

    Step 6: Find and Submit the Flag

    The DNS TXT record query in Step 4 returned the flag for this exercise. The flag value is stored in the TXT record at _flag.corp.ocr-range.lab. Enter the flag value in the format OCR{...} on the submission page.

    The flag follows the standard OCR{...} format. Submit it on the platform to complete the exercise.

    Analysis Questions

    1. Why does a Domain Controller expose more services than a typical Windows member server?

    Reveal Answer

    A Domain Controller must handle authentication (Kerberos on port 88), directory queries (LDAP on port 389 and LDAPS on port 636), forest-wide lookups (Global Catalog on port 3268), name resolution (DNS on port 53), and file-based policy distribution (SMB on port 445). A member server only needs to consume these services; not host them; so the member server does not open the corresponding listener ports.

    2. If you saw ports 53, 135, 139, and 445 open but ports 88, 389, and 3268 closed, what could you conclude about the target host?

    Reveal Answer

    The host is likely a Windows member server or workstation, not a Domain Controller. DNS (53) can run on any server configured as a DNS server, and SMB (445), RPC (135), and NetBIOS (139) are standard on all Windows machines. The absence of Kerberos, LDAP, and Global Catalog rules out the DC role.

    3. What is the advantage of using the -sV flag in Nmap rather than performing a basic port scan without version detection?

    Reveal Answer

    The -sV flag instructs Nmap to send protocol-specific probes to each open port and match the response against its signature database. The version information helps you distinguish between services that share the same port number on different platforms. For example, port 389 could host OpenLDAP on a Linux server or Microsoft Active Directory LDAP on a Windows DC; version detection tells you which one you are dealing with.

    4. Why would a penetration tester query DNS SRV records early in the reconnaissance phase?

    Reveal Answer

    SRV records published by Active Directory reveal the domain name, the hostnames of all Domain Controllers, and the services each DC provides (Kerberos KDC, LDAP, Global Catalog). A single SRV query can map the entire DC infrastructure of a domain without triggering authentication events or account lockouts.

    Key Takeaways

    • Domain Controllers expose a distinctive set of ports: 53 (DNS), 88 (Kerberos), 389 (LDAP), 636 (LDAPS), and 3268 (Global Catalog). Recognizing the pattern lets you confirm a DC in seconds.
    • Nmap with -sV provides service-version details that help you distinguish AD-specific services from generic listeners on the same port numbers.
    • DNS SRV records (_kerberos._tcp, _ldap._tcp) are registered automatically by AD and confirm both the domain name and the DC hostname.
    • TXT records in DNS can hold arbitrary data. Penetration testers routinely check for TXT records because administrators and applications store metadata there that may be useful during an engagement.
    • The open ports you discovered in this exercise; especially DNS (53), SMB (445), and LDAP (389); are the entry points for the remaining exercises in this chapter. Exercise WS-1.2 will target the DNS service you confirmed here.
