    Exercise WS-5.1: AD Reconnaissance Assessment

    Before You Begin

    The previous four chapters each focused on a single reconnaissance discipline; DNS (Domain Name System) queries, LDAP (Lightweight Directory Access Protocol) enumeration, SMB (Server Message Block) share analysis, and GPO (Group Policy Object) review. Exercise WS-5.1 is the capstone assessment for the Windows Server track. You will apply all four disciplines against a live Active Directory (AD) domain to locate three flag parts hidden in different data sources.

    Read the scenario and objectives carefully before you begin. The assessment is designed to be completed independently using the methodology checklist from the chapter introduction.

    Scenario

    Meridian Technologies has contracted your security team to perform a thorough AD reconnaissance assessment against their primary domain controller. The engagement scope covers DNS infrastructure, directory services, file shares, and group policy configurations. Your point of contact, Aisha Patel, has provided a low-privilege domain account for authenticated testing. The domain runs on a Windows Server environment with standard AD services.

    Your mission is to demonstrate full reconnaissance capability by recovering three assessment markers (flag parts) that the Meridian IT team has placed across different AD data sources. Each marker is stored in a different protocol layer; DNS, LDAP, and SMB; and requires a different reconnaissance technique to retrieve. Recovering all three markers and assembling the complete flag proves that your team can extract intelligence from every layer of the AD infrastructure.

    Your Objectives

    The assessment requires you to demonstrate proficiency across all four reconnaissance disciplines covered in the Windows Server track.

    • Perform thorough DNS reconnaissance including forward lookups, reverse lookups, SRV record queries, and TXT record discovery
    • Enumerate AD objects via LDAP including users, groups, Organizational Units (OUs), and computer objects
    • Access and analyze SMB shares using both anonymous and authenticated connections
    • Review GPO configurations and SYSVOL contents for policy and security information
    • Locate all three flag parts across the different data sources
    • Assemble the complete flag from the three parts and submit the result

    Suggested Approach

    The guidance below provides a general methodology for approaching the assessment. Specific commands and exact syntax are not included; the assessment tests your ability to select the right tool and construct the right query based on what you learned in Chapters WS01 through WS04.

    Phase 1: DNS Reconnaissance

    Start with DNS because the results inform every subsequent phase. DNS records reveal hostnames, IP addresses, and service locations that you will need when querying LDAP and connecting to SMB shares.

    Begin by performing forward lookups for the domain controller hostname and the domain itself. Check whether the DNS server responds to queries for the corp.ocr-range.lab zone. Query SRV records to confirm domain controller locations and identify any additional services registered in DNS.

    Look beyond standard records. TXT records are often used for SPF (Sender Policy Framework) configurations, domain verification tokens, and sometimes custom metadata. Administrators may have created TXT records on specific subdomains; consider what subdomain names might be relevant to an assessment scenario. The dig tool supports querying specific record types on specific hostnames.

    Record every DNS finding in your worksheet. Pay attention to any records that contain strings or codes that look like flag fragments.

    Phase 2: LDAP Enumeration

    LDAP enumeration reveals the directory structure and the attributes attached to every AD object. Start by confirming the base Distinguished Name (DN) for the domain, then work your way through the directory tree.

    Enumerate OUs first; they organize the directory and may contain assessment-specific containers. Search for user objects within each OU, paying close attention to attributes beyond the common ones. Standard attributes like sAMAccountName and displayName contain expected values, but attributes like info, description, and comment sometimes hold data that administrators did not intend to be widely visible.

    Look for user accounts with names related to the assessment scenario. The ldapsearch tool supports filters that match specific attribute values or patterns. Once you find a relevant user object, dump all of its attributes to see the complete picture.

    Record every LDAP finding; OUs, users, groups, and any unusual attribute values; in your worksheet.

    Phase 3: SMB Share Analysis

    SMB analysis provides access to files stored on the domain controller. Test both anonymous and authenticated access to discover all available shares and their permission levels.

    Start with anonymous enumeration to establish a baseline. Then connect using the provided credentials to see which additional shares become available. Authenticated access typically reveals more shares and higher permission levels than anonymous connections.

    Once you identify accessible shares, list their contents and examine any files that relate to the assessment. Look for text files, notes, configuration files, and any documents that might contain flag data. The smbclient tool supports inline commands for listing directory contents and retrieving files without entering an interactive session.

    Record every share name, permission level, and file listing in your worksheet.

    Phase 4: GPO and SYSVOL Review

    GPO review provides insight into the domain's security configuration and policy enforcement. The SYSVOL share on every domain controller contains GPO templates, logon scripts, and policy definitions that are readable by any authenticated domain user.

    Access the SYSVOL share using authenticated credentials and browse the policy directories. Look for GPO names, script files, and configuration templates. While the GPO review may not contain a flag part directly, the information supports the assessment report and demonstrates thorough methodology.

    Document the GPO names, any scripts you find, and notable policy settings in your worksheet.

    Phase 5: Flag Assembly

    After completing all four phases, review your worksheet for the three flag parts. Each part is a string fragment found in a different data source. Concatenate the parts in order (Part 1 from DNS, Part 2 from LDAP, Part 3 from SMB) and wrap them in the OCR{...} format.

    Verify that the assembled flag looks syntactically correct before submitting. The complete flag should be a single continuous string inside the braces with no spaces.

    Detailed Walkthrough

    The walkthrough below provides the exact commands and expected output for each phase of the assessment. Use the walkthrough only after attempting the assessment independently; the learning value comes from figuring out the approach on your own.

    Launch the Lab

    Open the platform and start the assessment environment.

    • Navigate to Exercises then Windows Server then Level 5
    • Click Launch on "AD Reconnaissance Assessment"
    • Wait for the status to change to Running
    • Note the target information displayed in the Active Lab View

    Step 1: DNS Forward Lookups

    Resolve the domain controller hostname

    Begin by resolving the domain controller hostname to confirm connectivity and identify the target IP address.

    dig A dc01.corp.ocr-range.lab @dc01

    The dig command queries the DNS server at dc01 for the A record (IPv4 address) of the domain controller hostname. The response should contain a single A record with the IP address of dc01. Record the IP address; you will need it for reverse lookups and as a fallback if hostname resolution fails during later steps.

    Resolve the domain name

    Next, resolve the domain name itself to check for any additional addresses.

    dig A corp.ocr-range.lab @dc01

    The domain name may resolve to the same IP as the domain controller, or it may return multiple addresses if there are additional DCs (Domain Controllers) in the environment.

    Step 2: DNS Reverse Lookup

    Reverse-lookup the domain controller IP

    Perform a reverse lookup on the IP address you discovered in Step 1 to verify that forward and reverse DNS are consistent. Replace <dc01_ip> with the address from Step 1.

    dig -x <dc01_ip> @dc01

    The -x flag tells dig to perform a PTR (Pointer) record lookup, which maps an IP address back to a hostname. Consistent forward and reverse records confirm that the DNS infrastructure is properly maintained. Inconsistencies can indicate stale records or split-horizon DNS configurations.

    Step 3: SRV Record Queries

    Query SRV records for domain services

    Query SRV records to discover domain services registered in DNS. SRV records identify the hostname and port for specific services within the domain. Run each query in turn.

    dig SRV _ldap._tcp.corp.ocr-range.lab @dc01

    dig SRV _kerberos._tcp.corp.ocr-range.lab @dc01

    dig SRV _gc._tcp.corp.ocr-range.lab @dc01

    Each SRV query returns the hostname, port, priority, and weight for the specified service. The _ldap._tcp record identifies LDAP servers (domain controllers). The _kerberos._tcp record identifies Kerberos Key Distribution Center (KDC) servers. The _gc._tcp record identifies Global Catalog servers. All three are standard AD DNS records.

    Step 4: DNS TXT Record Discovery (Flag Part 1)

    Discover the TXT record flag part

    Query TXT records for assessment-related subdomains. The assessment scenario indicates that a flag part is stored in a DNS TXT record on a specific subdomain.

    dig TXT _assess1.corp.ocr-range.lab @dc01

    The response should contain a TXT record with a string value. The value is the first part of the assessment flag. Expected output fragment:

    _assess1.corp.ocr-range.lab.  IN  TXT  "<flag_part_1>"

    Record the value returned by the TXT query as Flag Part 1 in your worksheet.

    Step 5: LDAP Base DN Discovery

    Discover the LDAP base DN

    Query the LDAP root DSE (Directory System Agent Entry) to discover the base DN for the domain.

    ldapsearch -x -H ldap://dc01 -s base namingContexts

    The output reveals the base DN, typically DC=corp,DC=ocr-range,DC=lab for the corp.ocr-range.lab domain. Record the base DN; every subsequent LDAP query needs it.

    Flag Purpose
    -x Use simple authentication instead of SASL (Simple Authentication and Security Layer)
    -H ldap://dc01 Connect to the LDAP server on dc01
    -s base Search only the root entry (base scope)
    namingContexts Request the naming context attributes

    Step 6: LDAP OU Enumeration

    Enumerate all OUs

    Enumerate all OUs in the domain to find assessment-related containers.

    ldapsearch -x -H ldap://dc01 -b "DC=corp,DC=ocr-range,DC=lab" "(objectClass=organizationalUnit)" dn

    The filter (objectClass=organizationalUnit) returns only OU objects. The dn at the end limits the output to Distinguished Names, making the results easier to scan. Look for OUs with names related to the assessment; an OU named "Flags" or "Assessment" is a strong indicator of where flag data is stored.

    Step 7: LDAP User Search (Flag Part 2)

    Search for user objects in the Flags OU

    Search for user objects within the Flags OU and examine their attributes.

    ldapsearch -x -H ldap://dc01 -b "OU=Flags,DC=corp,DC=ocr-range,DC=lab" "(objectClass=user)"

    The query returns all user objects within the Flags OU along with their readable attributes. Look for a user account named assess.flag or similar. Once you identify the relevant user, examine the info attribute; AD stores freeform text in the info field, and administrators sometimes use the field for notes or metadata.

    Dump all attributes for the flag user

    To search specifically for the assessment flag user and retrieve all attributes, target it by sAMAccountName and request every attribute with *.

    ldapsearch -x -H ldap://dc01 -b "OU=Flags,DC=corp,DC=ocr-range,DC=lab" "(sAMAccountName=assess.flag)" "*"

    The info attribute holds Flag Part 2. Expected output fragment:

    dn: CN=assess.flag,OU=Flags,DC=corp,DC=ocr-range,DC=lab
sAMAccountName: assess.flag
info: <flag_part_2>

    Record the info attribute value as Flag Part 2 in your worksheet.

    Step 8: LDAP Group and Computer Enumeration

    Enumerate groups and computers

    Perform additional LDAP enumeration to demonstrate full coverage. Query group objects and then computer objects within the domain.

    ldapsearch -x -H ldap://dc01 -b "DC=corp,DC=ocr-range,DC=lab" "(objectClass=group)" cn description

    ldapsearch -x -H ldap://dc01 -b "DC=corp,DC=ocr-range,DC=lab" "(objectClass=computer)" cn operatingSystem

    The group query returns group names and descriptions. The computer query returns computer names and their operating system versions. Record the results in your worksheet; full enumeration demonstrates thoroughness even when specific objects do not contain flag data.

    Step 9: Anonymous SMB Enumeration

    List shares with a null session

    Test anonymous access to SMB shares on the domain controller.

    smbclient -L //dc01 -N

    The -N flag suppresses the password prompt, sending a null session. The output lists all shares visible to anonymous users, along with their type (Disk, IPC, or Printer). Record every share name and type.

    Map anonymous share permissions

    Next, map permissions for anonymous access.

    smbmap -H dc01

    The smbmap output shows READ, WRITE, or NO ACCESS for each share. Any share granting anonymous read or write access is a significant finding. Document the results even if anonymous access is limited; the contrast between anonymous and authenticated access levels is itself a useful finding.

    Step 10: Authenticated SMB Access (Flag Part 3)

    List shares with authenticated credentials

    Connect to shares using the provided credentials to discover additional accessible resources.

    smbclient -L //dc01 -U 'guest.user%Guest2024#'

    Compare the authenticated share list with the anonymous results from Step 9. Authenticated access typically reveals additional shares or higher permission levels on existing shares.

    Retrieve the assessment notes file

    Access the IT-Tools share and retrieve the assessment notes file.

    smbclient //dc01/IT-Tools -U 'guest.user%Guest2024#' -c 'get assessment-notes.txt -'

    The file contents include the third flag part. Record the value from the file as Flag Part 3 in your worksheet.

    Flag Purpose
    //dc01/IT-Tools Connect to the IT-Tools share on dc01
    -U 'guest.user%Guest2024#' Authenticate with the provided credentials
    -c 'get assessment-notes.txt -' Execute the get command to retrieve the file, printing to stdout (-)

    Step 11: Authenticated SMB Permission Mapping

    Map authenticated share permissions

    Map share permissions with authenticated credentials to complete the SMB analysis.

    smbmap -H dc01 -u guest.user -p 'Guest2024#'

    Compare the authenticated permission map with the anonymous results. Document which shares are accessible only with credentials and what permission level each share grants. The difference between anonymous and authenticated access demonstrates the value of credential-based testing.

    Step 12: SYSVOL and GPO Review

    Recursively list SYSVOL

    Access the SYSVOL share to review GPO configurations and scripts.

    smbclient //dc01/SYSVOL -U 'guest.user%Guest2024#' -c 'recurse ON; ls'

    The recurse ON; ls command sequence enables recursive directory listing and then lists all files and directories within the SYSVOL share. The output includes GPO template directories, logon scripts, and policy definition files. Each GPO is stored in a directory named with its GUID (Globally Unique Identifier).

    Browse the GPO policy directories

    Browse the GPO directories to find policy files.

    smbclient //dc01/SYSVOL -U 'guest.user%Guest2024#' -c 'cd corp.ocr-range.lab\Policies; ls'

    Record the GPO GUIDs and any scripts or configuration files you discover. While the GPO data may not contain a flag part, the review demonstrates thorough assessment methodology.

    Step 13: Assemble the Complete Flag

    Gather the three flag parts from your worksheet and concatenate them in order.

    Part Source Value
    Part 1 DNS TXT record on _assess1.corp.ocr-range.lab (your Part 1)
    Part 2 LDAP info attribute on user assess.flag (your Part 2)
    Part 3 SMB file assessment-notes.txt on IT-Tools share (your Part 3)

    Concatenate the three parts to form the complete flag:

    Complete flag: OCR{<part1><part2><part3>}

    Submit the complete flag on the platform to confirm your assessment is successful.

    Analysis Questions

    The questions below go beyond individual techniques and ask you to evaluate the assessment as a whole. Consider the relationships between the four reconnaissance disciplines and the real-world implications of the findings.

    1. Why is combining multiple reconnaissance techniques more effective than relying on a single protocol?

    Reveal Answer

    Each protocol exposes a different layer of the AD infrastructure. DNS reveals naming and service locations but not user details. LDAP exposes directory objects and attributes but not file contents. SMB provides file access but not directory structure. GPO shows security policies but not individual user data. An attacker who queries only one protocol sees a partial picture; combining all four produces a full map of the environment that reveals relationships and misconfigurations invisible from any single vantage point.

    2. What does the presence of sensitive data in the LDAP info attribute suggest about the organization's directory hygiene?

    Reveal Answer

    The info attribute is readable by any authenticated domain user by default. Storing sensitive data in the info field means that every user in the domain can retrieve the information with a basic LDAP query. The finding suggests that the organization does not audit non-standard LDAP attributes for sensitive content and has not applied restrictive ACLs (Access Control Lists) to limit attribute visibility. In a real environment, password hints, internal notes, and configuration details stored in readable attributes represent a significant information disclosure risk.

    3. How would you prioritize the remediation of findings from this assessment for a real client?

    Reveal Answer

    The highest priority is restricting anonymous and low-privilege access to sensitive data. The TXT record containing assessment data should be removed or restricted. The LDAP info attribute should be cleared and ACLs tightened to prevent low-privilege users from reading sensitive attributes. The SMB share should enforce least-privilege access so that general-purpose accounts cannot retrieve internal files. GPO configurations should be reviewed to ensure SYSVOL permissions follow the principle of least privilege. Each finding should be documented with business impact and a specific remediation action.

    4. An attacker has compromised a low-privilege domain account. Based on this assessment, what information could they extract without escalating privileges?

    Reveal Answer

    With a low-privilege account, an attacker could query DNS for all registered services and hostnames, enumerate the full directory tree via LDAP including user accounts and group memberships, access authenticated SMB shares to retrieve files, and browse SYSVOL for GPO scripts and policy configurations. The assessment demonstrates that low-privilege access is sufficient to map the entire AD infrastructure, identify high-value targets, and extract data from misconfigured shares and attributes. Privilege escalation is not required to cause significant damage when basic access controls are weak.

    5. How would the methodology change if you had no credentials at all?

    Reveal Answer

    Without credentials, LDAP enumeration would be limited to anonymous bind capabilities; some domains allow anonymous base DN queries but restrict object enumeration. SMB access would be limited to null sessions and guest access, which typically expose fewer shares. DNS reconnaissance would be unaffected because DNS queries do not require domain authentication. GPO review would be unavailable because SYSVOL requires authentication. The overall coverage would be significantly reduced. Even low-privilege credentials are valuable for thorough reconnaissance.

    Key Takeaways: Windows Server Track Summary

    The five chapters of the Windows Server track built a complete AD reconnaissance methodology from the ground up. Each takeaway below connects a technique to the broader assessment discipline.

    • DNS is the foundation of AD reconnaissance. Forward lookups, reverse lookups, SRV records, and TXT records reveal the naming infrastructure, service locations, and sometimes hidden metadata. Every assessment should start with thorough DNS queries because the results inform every subsequent phase.

    • LDAP exposes the directory tree to any authenticated user. OUs, users, groups, computers, and their attributes are all queryable with basic credentials. Non-standard attributes like info, description, and comment frequently contain data that administrators did not intend to expose. Always enumerate beyond the obvious fields.

    • SMB share access depends on both the share permissions and the NTFS (New Technology File System) permissions. Anonymous access reveals misconfigurations at the share level, while authenticated access tests NTFS-level controls. The difference between the two access levels is itself a finding worth documenting.

    • GPO configurations and SYSVOL contents are readable by every authenticated domain user. Policy settings, logon scripts, and configuration templates stored in SYSVOL provide insight into the domain's security posture. Reviewing GPO data completes the picture that DNS, LDAP, and SMB began.

    • Multi-source intelligence is more valuable than any single finding. The split-flag design in the assessment mirrors real-world scenarios where important information is scattered across protocols. A thorough methodology that covers all four disciplines produces findings that no single-protocol approach could achieve.

    • Low-privilege access is sufficient for thorough reconnaissance. The entire assessment was completed with a guest-level domain account. Organizations that focus exclusively on preventing privilege escalation while neglecting basic access controls leave their AD infrastructure exposed to thorough enumeration by any authenticated user.
