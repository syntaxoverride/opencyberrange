    Exercise OTSOC-5.4: The Notification

    Scenario

    The Pecan Creek Creamery freezer incident is contained and the root cause is known: an unauthorized engineering write moved the freezer barrel setpoint from minus 5 C to plus 2.5 C, a warm drift that spoiled product while staying under the coarse alarm limits. The attacker reached the controller through the IT/OT boundary using a stolen contractor credential, mapped to MITRE ATT&CK for ICS T0836, Modify Parameter. Containment, forensics, and root cause are done. What is left is the part many responders skip and regulators do not: the notification.

    You are the incident lead writing the mandated report. You write a CIP-008 style incident notification and an internal executive brief, then submit them to the deliverable grader, which checks for every required element and releases a flag only when the report is complete. You read the required elements and submit the report with curl, jq, and python3 on your Kali-based RangeBox.

    Host Role
    rubric.pcc.local (HTTP 80) The incident-report deliverable grader

    Why this matters

    A technically perfect incident response that produces no report is an incomplete response. NERC CIP-008 governs cyber security incident reporting and response for the bulk electric system, and the same structure is the de facto standard for OT incident notification across critical-infrastructure sectors. The point of a mandated report is not paperwork; it is that the next defender, the regulator, and the information-sharing community all get a complete, comparable picture of what happened. A report that omits the safety impact, or the severity justification, or the remediation, leaves the reader unable to judge whether the response was adequate or whether the same attack is hitting them right now.

    The seven elements the grader checks are the irreducible minimum of an OT incident notification: what happened, affected systems, safety impact, containment, root cause, remediation, and severity classification. Writing them in plain language a regulator and an executive can both read is a skill, and the discipline of severity classification is the part responders get wrong most often. A warm-drift product-spoilage event with a contained safety impact and no loss of life is not the same severity as an ammonia release, and your report has to say why. The flag is released only when every element is present, so a complete report is the deliverable.

    Before You Begin

    Every command runs on your Kali-based RangeBox. Read the grader host IP from the Exercise Network panel and capture it into a variable, because every student gets a different /24.

    Kali - capture the grader host IP from the panel

    # Replace the example octet with the rubric IP from the Exercise Network panel.
RUBRIC=10.100.42.22
echo "rubric=$RUBRIC"

    Confirm the grader answers with a health check.

    Kali - prove the grader is reachable

    curl -s "http://$RUBRIC/health"

    A JSON status of ok means the grader is up. An empty reply or a hang means the lab is not Running yet.

    Learning Objectives

    • List the required elements of the CIP-008 style report from the grader
    • Write the regulator notification and the internal executive brief
    • Cover what happened, affected systems, safety impact, containment, root cause, and remediation
    • Decide and justify the severity classification
    • Submit the report and pass at threshold 1.0, then recover the flag

    Background: CIP-008 Style Incident Reporting

    CIP-008 structures an incident notification so that any reader can reconstruct the event and judge the response. The grader encodes the seven required elements; every one must be present to pass.

    Element What it answers What it must literally state
    What happened The narrative A summary of events
    Affected systems The scope The affected or impacted assets
    Safety impact The consequence The food-safety consequence assessment
    Containment The response How it was contained, the Safe Cyber Position
    Root cause The cause The one-sentence root cause
    Remediation The recovery Corrective action and recovery steps
    Severity classification The judgment The severity or priority and its justification

    Severity is a judgment you justify, not a label you pick

    A severity classification with no justification fails the purpose of the element. State the severity and then say why: a contained warm-drift spoilage event with no safety-system trip and no loss of life sits below a release event in any OT severity scale. The justification is what lets a regulator agree or push back.

    Walkthrough

    Step 1: List the required elements from the grader

    Read the required elements before you write, so your report covers every one. The grader returns the element names, weights, and the pass threshold.

    Kali - list the required elements

    curl -s "http://$RUBRIC/rubric?deliverable=incident-report" | jq '.'

    Required elements returned

    {
  "deliverable": "incident-report",
  "threshold": 1.0,
  "required": [
    {"name": "what happened"},
    {"name": "affected systems"},
    {"name": "safety impact assessment"},
    {"name": "containment actions"},
    {"name": "root cause"},
    {"name": "remediation steps"},
    {"name": "severity classification"}
  ]
}

    The threshold is 1.0, so all seven elements must be present. The grader matches on keywords, which means your report has to literally name each element: a summary of events, the affected systems, the safety impact, the containment and Safe Cyber Position, the root cause, the remediation, and the severity classification.

    Step 2: Draft the report covering every element

    Write the report in plain language a regulator and an executive can both read, and make sure each of the seven elements appears explicitly. Compose it into a shell variable so you can submit it without quoting headaches. Build it element by element so nothing is missed.

    Kali - draft the CIP-008 style report

    REPORT="Pecan Creek Creamery incident notification, PCC-IR-2026-014.

What happened: summary of events. An unauthorized engineering write changed the
continuous freezer barrel setpoint, producing a slow warm drift that spoiled
product while staying under coarse alarm limits.

Affected systems: the affected assets are the continuous freezer PLC and the
freezer production line. Ammonia refrigeration, the pasteurizer, and cold storage
were not impacted.

Safety impact: the food safety consequence was a quantity of product warmed below
the cold-chain threshold. The independent ammonia safety function did not trip and
there was no release and no loss of life.

Containment: the incident was contained with a Safe Cyber Position that blocked the
rogue source path and froze further engineering writes while holding the process in
a known-safe state, without pulling the PLC or wiping the HMI.

Root cause: an unauthorized parameter write moved the freezer barrel setpoint from
minus 5 C to plus 2.5 C, warming product below the alarm threshold.

Remediation: corrective action restored the baseline setpoint, revoked the abused
contractor credential, and added a detection for out-of-band setpoint writes;
recovery of the line is complete.

Severity classification: moderate priority. Justification: a contained product
spoilage event with no safety-system trip, no release, and no loss of life ranks
below an ammonia release event on the plant severity scale."
echo "$REPORT" | head -c 160; echo " ..."

    Each paragraph names one required element with the keyword the grader looks for. Drafting element by element is how you guarantee threshold 1.0; skipping any one paragraph drops you below passing.

    Step 3: Submit the report and read the score

    POST the report to the grader. The response reports passed, the score against the total, per-element feedback, and the flag when you pass.

    Kali - submit the report to the grader

    curl -s -X POST "http://$RUBRIC/check" \
  -H 'Content-Type: application/json' \
  -d "$(jq -nc --arg s "$REPORT" '{deliverable:"incident-report", submission:$s}')" \
  | jq '.'

    A passing response

    {
  "deliverable": "incident-report",
  "passed": true,
  "score": 7,
  "total": 7,
  "threshold": 1.0,
  "flag": "OCR{pcc_cip008_<masked>}"
}

    A passed of true with score equal to total means all seven elements registered. The flag field carries your submission.

    Step 4: Fix any missing element

    If passed is false, the feedback array names exactly which element did not register. Filter for the gaps, add the missing wording, and resubmit.

    Kali - show only the elements the grader did not find

    curl -s -X POST "http://$RUBRIC/check" \
  -H 'Content-Type: application/json' \
  -d "$(jq -nc --arg s "$REPORT" '{deliverable:"incident-report", submission:$s}')" \
  | jq '[.feedback[] | select(.found==false)]'

    An empty array means nothing is missing. Any entry names an element whose keyword your report lacks; add a sentence that states it plainly and resubmit. A common miss is the severity justification, where the word severity appears but the reason it is moderate rather than critical does not.

    Output Interpretation

    • The grader is a keyword check, so the report has to literally state each element; a report that implies the safety impact without naming it fails the safety element even if a human reader would infer it
    • Threshold 1.0 means there is no partial credit; six of seven elements is a fail, which mirrors a real regulator returning an incomplete notification
    • The severity element is the one most often missed, because responders state a severity without justifying it; the justification is what the element actually grades
    • A passing score is the deliverable, but the value to the plant is the report itself, a record the regulator, the insurer, and the next defender can all read

    Analysis Questions

    1. Why is severity classified as moderate here rather than critical, and how do you justify it?

    Reveal answer

    The incident was a contained product-spoilage event: the independent ammonia safety function never tripped, there was no release, and there was no loss of life. Severity in OT is driven by consequence, and a quality impact that was caught and contained ranks below a safety-system event such as an ammonia release. The justification names the absence of a safety trip, a release, and casualties as the reasons the classification is moderate and not critical.

    2. The grader matches keywords. Why is that a reasonable model for an incident-report exercise?

    Reveal answer

    A CIP-008 style notification is judged on whether it contains the mandated elements, and a keyword check is a fair proxy for completeness: it confirms the report names what happened, the affected systems, the safety impact, the containment, the root cause, the remediation, and the severity. It does not grade prose quality, which a human reviewer would, but for the completeness gate that a regulator applies first, presence of every element is exactly the right check.

    3. Which element would a technically strong responder most likely omit, and why does omitting it fail the report?

    Reveal answer

    The severity justification. A responder who solved the technical incident often states a severity label and moves on, treating the justification as obvious. The report fails because severity drives the regulator's and the insurer's response, and an unjustified severity gives them nothing to agree with or challenge. The element grades the reasoning, not the label.

    Capture the Flag

    The flag is released by the incident-report grader only when your report contains all seven required elements at threshold 1.0: what happened, affected systems, safety impact, containment, root cause, remediation, and severity classification with its justification. Submit the report from Step 3; the grader returns the flag in the flag field. The flag names the completed CIP-008 style report.

    Flag format: OCR{pcc_cip008_<masked>}
