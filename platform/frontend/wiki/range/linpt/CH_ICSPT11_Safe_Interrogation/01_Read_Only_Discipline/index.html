    Exercise ICSPT-2.3: Safe Read-Only Interrogation

    Engagement Status

    Client Masa Foods, Inc. (fictional)
    Role OT Security Engineer, Plant 1
    Phase Discovery Enumeration Exploitation Reporting

    What you know so far: You have crossed the enterprise-to-OT boundary (Exercise 2.1) and audited a contractor's after-hours activity (Exercise 2.2). You have never issued a dangerous Modbus function code against a Plant 1 PLC. Exercise 2.3 makes that discipline explicit: learn the safe function codes, use them deliberately, and leave the PLCs in exactly the state you found them.

    Scenario

    Reyna Alvarado has booked a one-hour read-only assessment window on the Plant 1 tortilla line. During the window, she wants proof that you can interrogate both the MC-7200 tortilla PLC and the MC-3100 mixer PLC without issuing any dangerous Modbus function code. Reyna is sensitive because the mixer is known to crash on malformed packets, and she wants the new OT security engineer to demonstrate safe technique in front of operations.

    Why this matters

    Real OT engagements are contractually bounded by scope. Most of them say "read-only" in the statement of work, and some of them say it more than once, in bold, with the client's legal team copied. The reasons are not theoretical:

    • Insurance carriers. Cyber-insurance policies for manufacturing plants commonly require that any third-party testing be certified read-only. An engineer who issues a write during a read-only engagement violates the policy, and the carrier may decline to pay on any incident that occurs during the test window regardless of whether the engineer's write was the cause. One careless function code can cost seven figures.
    • Regulatory scope. NERC CIP and similar regimes require change control on any action that modifies a Critical Cyber Asset. A pen tester who writes to a register without a change ticket creates a regulatory incident for the client, even if nothing bad happens operationally.
    • Reputation and repeat business. The first engagement with a new OT client is always on probation. If the shift supervisor sees a single tag jitter that cannot be explained, the pen test firm does not get called back. Clean read-only discipline is how you earn the second engagement, and the second engagement is where the real work happens.

    Knowing which function codes are safe is not an academic classification. It is the line between a professional who gets hired again and one who gets a legal letter. Exercise 2.3 forces you to internalize the function-code table by using it under conditions that match a real engagement: an operator watching, a fragile PLC on the other end, and zero tolerance for an errant write.

    In this exercise you learn the distinction between safe Modbus function codes (reads, diagnostic queries, device identification) and dangerous function codes (writes, diagnostic resets, mask writes). You read the mixer serial string from the MC-3100, read the plc1 commissioning certificate from the MC-7200, and compose a composite flag that proves both reads succeeded. Every read is one mbpoll Function Code 3 query, and you decode the ASCII by hand.

    Credentials in scope Username Password Where it is used
    Operator HMI plant_op masa_op_2025 Reference only; not used here

    The flag is a composite that proves you read two specific fields without writing anything: the mixer PLC serial string and the plc1 commissioning certificate. The format is:

    OCR{<serial>_<cert>}

    where <serial> is the mixer serial lowercased with hyphens removed, and <cert> is the decoded commissioning certificate text with the OCR{ and } wrapper stripped off. You read and decode each piece yourself; neither component is printed in this workbook.

    Background: Safe vs Dangerous Modbus Function Codes

    The Modbus specification defines about 20 function codes. In an OT engagement, you must know by heart which ones are safe to issue against a production PLC and which ones are not. The consequences of guessing wrong range from "the PLC ignores your packet" to "the PLC reboots and stops a live process." Older PLCs (pre-2010 firmware) are especially fragile; newer PLCs tolerate more but still expose process state to any write.

    Safe function codes

    The "safe" list is the read family plus diagnostic queries that do not modify PLC state.

    FC Name What it does
    1 Read Coils Returns N bits of coil state
    2 Read Discrete Inputs Returns N bits of discrete input state
    3 Read Holding Registers Returns N 16-bit holding register values
    4 Read Input Registers Returns N 16-bit input register values
    7 Read Exception Status Returns 8 bits of exception state
    11 Get Comm Event Counter Returns a 16-bit communication event counter
    12 Get Comm Event Log Returns a communication event log
    17 Report Server ID Returns a vendor-specific server identification
    20 Read File Record Returns N records from a file
    24 Read FIFO Queue Returns the contents of a FIFO queue
    43 Encapsulated Interface Transport (subfunction 14) Returns device identification (vendor, product, version)

    All of these are reads. None of them cause state changes on the PLC. FC 7, 11, 12, 17, 20, and 24 are historical and less common on modern PLCs but are still safe on the wire.

    Dangerous function codes

    Anything that modifies PLC state, resets counters, or exercises the diagnostic subsystem is dangerous. Treat this list as off-limits for reconnaissance:

    FC Name What it does
    5 Write Single Coil Sets one coil to ON or OFF
    6 Write Single Register Sets one holding register to a new value
    8 Diagnostics Multiple subfunctions including Restart Communications Option (reboots the PLC)
    15 Write Multiple Coils Sets a contiguous block of coils
    16 Write Multiple Registers Sets a contiguous block of holding registers
    21 Write File Record Modifies file records
    22 Mask Write Register Applies an AND/OR mask to a holding register
    23 Read/Write Multiple Registers Reads a block and writes a different block in one transaction

    FC 8 deserves a special mention. The diagnostic subfunction numbers include Restart Communications Option (subfunction 1), Clear Counters (subfunction 10), and Clear Overrun (subfunction 20). Every one of them mutates PLC state and several have been used in the field to crash controllers.

    The mixer crashes on function codes it does not recognize

    The MC-3100 Mixer Controller running on the Masa Plant 1 dough line is a 2012-era PLC. Reyna's note "reboots if you look at it funny" is not an exaggeration. Stick to FC 3 (Read Holding Registers) on the mixer for this entire exercise. FC 43 would also be safe in theory, but the MC-3100 does not implement it cleanly, so convention at Masa is "mixer is FC 3 only."

    Methodology

    You build the answer with tools, not scripts. Checkpoint 1 rereads the register map so you know where the safe read targets live. Checkpoint 2 reads the mixer serial with one mbpoll command and decodes it by hand. Checkpoint 3 reads the plc1 certificate the same way. Checkpoint 4 captures one of the reads in Wireshark and confirms on the wire that you issued only Function Code 3. Checkpoint 5 records the decoded tokens and composes the flag.

    Checkpoint 2: Read the Mixer Serial with mbpoll

    Where the register numbers come from. The MC-3100 mixer stores its serial number in holding registers 40110 through 40117 as ASCII text, two characters per register. That is eight registers, sixteen characters of capacity. The docs portal publishes the layout; you are not guessing addresses.

    The documented register, the wire address, and what mbpoll wants. Holding registers are documented in the 4xxxx range. On the wire the address is zero-based and drops the leading 4, so documented register 40110 is wire address 109. The mbpoll tool hides that arithmetic for you: its -r option takes the register number without the leading 4, so -r 110 reads documented register 40110. Reading the eight-register block 40110 through 40117 is therefore -r 110 -c 8.

    Documented register Holds mbpoll -r
    40110 through 40117 mixer serial (2 ASCII chars per register, big-endian) 110, count 8

    Read the block with one command. There is no client to write. mbpoll is the standard Modbus/TCP CLI, and a single read covers the whole block. Function Code 3 (read holding registers) is the one code the fragile MC-3100 is guaranteed to accept.

    Kali

    mbpoll -1 -a 1 -t 4 -r 110 -c 8 mixer.masa.local
    -1 polls once and exits, -a 1 is the Modbus unit id, -t 4 selects holding registers (Function Code 3), -r 110 starts at documented register 40110, and -c 8 reads the eight-register serial block. Port 502 is the default. mbpoll labels each value with its register number, so you read the layout straight off the output.

    The eight values on your screen are the serial, one register at a time, as decimal integers. They are not human-readable yet because each register is two packed ASCII bytes. You convert them to text by hand below.

    Decode one register so the method is clear. Each holding register is 16 bits, which is two bytes, which is two ASCII characters with the high byte first (the Modbus big-endian convention). Convert each register's decimal value to hex, then read the two bytes as characters. A register reading 19777 is 0x4D41 in hex: the high byte 0x4D is the ASCII character M, and the low byte 0x41 is A, so that register carries MA. The 0x4D41 -> MA example is deliberately not part of the mixer serial, so you still have to run the read and do the decode yourself.

    Apply the same split to every register in your output, in register order, and concatenate the characters. Drop any trailing null padding (0x0000). The remaining characters spell the mixer serial, which is a Maxon part-number string with a hyphen in it. For the flag you need the lowercased version with the hyphen removed; record both forms in the Checkpoint 5 table.

    Checkpoint 3: Read the plc1 Commissioning Certificate with mbpoll

    The commissioning certificate lives at 40500 through 40515 on plc1, packed as sixteen registers of ASCII, two characters per register, big-endian. The wire address for documented register 40500 is 499, and mbpoll's -r option takes the register number without the leading 4, so -r 500 -c 16 reads the whole block.

    Documented register Holds mbpoll -r
    40500 through 40515 commissioning certificate (2 ASCII chars per register, big-endian) 500, count 16

    Kali

    mbpoll -1 -a 1 -t 4 -r 500 -c 16 plc1.masa.local
    Same options as Checkpoint 2, except the target is plc1.masa.local, -r 500 starts at documented register 40500, and -c 16 reads the sixteen-register certificate block.

    Decode the same way. Convert each of the sixteen register values to hex, split into two ASCII bytes high byte first, and concatenate in register order. Drop the trailing null registers. The decoded string is an OCR{...} certificate. For the flag you need the inner token only, which is the certificate with the OCR{ prefix and the } suffix stripped off. Record both the full certificate and the inner token in the Checkpoint 5 table.

    Checkpoint 4: Confirm on the Wire That You Used Only Safe Function Codes

    mbpoll is the fast path; Wireshark is how you prove to Reyna and the operator that every packet you sent was a read. Capture TCP port 502 while you re-run one of the reads, then confirm the dissected function code is 3 (Read Holding Registers) and not a write code like 6 or 16.

    Capture the query while you run it. Start a capture on TCP port 502, re-run a Checkpoint 2 or 3 read, then stop the capture and set the display filter to modbus.

    Kali (shell one)

    sudo tshark -i any -f 'tcp port 502' -w /tmp/modbus_safe.pcap &
echo $! > /tmp/tshark.pid

    Kali (shell two)

    mbpoll -1 -a 1 -t 4 -r 110 -c 8 mixer.masa.local

    Kali (shell one, after the read completes)

    sudo pkill -F /tmp/tshark.pid 2>/dev/null || sudo pkill tshark
tshark -r /tmp/modbus_safe.pcap -Y 'modbus' \
  -T fields -e frame.number -e ip.src \
  -e modbus.func_code -e modbus.reference_num -e modbus.word_cnt
    The modbus.func_code column reads 3 on the query. A write would read 6, 16, or 5. Seeing only 3 is your wire-level proof of read-only discipline.

    Now open the capture in the Wireshark GUI. The terminal fields prove the data is there; the GUI is where you point at the function code and recognize a read on sight. Walk these steps exactly:

    1. Open the capture. From a terminal run wireshark /tmp/modbus_safe.pcap &, or inside Wireshark choose File > Open and pick the file. To capture live instead, double-click your network interface on the Wireshark welcome screen to start, run the mbpoll read, then click the red square Stop button in the toolbar.
    2. Filter to Modbus. In the display filter bar (the wide bar directly under the toolbar), type modbus and press Enter. The packet list narrows to just the query and its response.
    3. Select the query. In the Packet List (top pane), click the row whose Info column reads Query: ... Func: 3: Read Holding Registers. The word Query and Func: 3 together tell you this is a read going to the PLC.
    4. Expand the MBAP header. In the Packet Details (middle pane), click the arrow to the left of Modbus/TCP. The four MBAP fields drop down: Transaction Identifier, Protocol Identifier, Length, and Unit Identifier.
    5. Expand the PDU and read the Function Code. Click the arrow next to the Modbus node just below it. The first field is Function Code: 3 (Read Holding Registers), followed by the Reference Number and Word Count. That 3 is the field that proves you stayed read-only; a 6 or 16 here would be a write.
    6. Tie the field to the bytes. Click the Function Code field name and watch the matching byte highlight in the Packet Bytes pane at the bottom. The single byte 03 is the function code on the wire. That is how you connect a decoded field to its exact position in the frame.

    Checkpoint 5: Record Your Findings and Compose the Flag

    You now hold two decoded tokens: the normalized mixer serial and the inner certificate token. Turn each into the form the flag template OCR{<serial>_<cert>} expects, then submit the result in the OCR platform flag box. The platform tells you immediately whether the composite is correct, so the finished string is not printed here.

    Read-only audit:

    Target Register block mbpoll command Decoded value Token for flag
    Mixer 40110-40117 -r 110 -c 8 _____ _____ (lowercase, no hyphen)
    plc1 40500-40515 -r 500 -c 16 _____ _____ (inner token, no OCR{})

    Function code observed in Wireshark: _____ (should read 3, Read Holding Registers)

    Flag: OCR{<serial>_<cert>}

    Substitute the two tokens you decoded into the template and submit. Do not write the components or the assembled flag anywhere in this workbook; the platform is the only place you confirm the answer.

    Output Interpretation

    • A clean read of the mixer serial tells you that plc1.masa.local and mixer.masa.local are both on the operations VLAN and both accept FC 3 from your Kali
    • The commissioning certificate is stored as plaintext ASCII. That is a training convention; real plants hide serial numbers behind vendor-specific encapsulated device identification responses (FC 43 subfunction 14)
    • The Wireshark function-code column is your engagement evidence. A capture that shows only Func: 3 across every packet is the artifact you hand Reyna to prove read-only discipline, far stronger than a verbal assurance
    • The composite flag format is deliberately fussy: it requires you to normalize the serial (lowercase, no hyphens) and strip the OCR wrapper off the certificate. Real engagements produce reports that require the same kind of careful text handling

    Analysis Questions

    1. Why is FC 8 (Diagnostics) considered dangerous even though the name sounds read-only?

    Reveal answer

    FC 8 is a family of diagnostic sub-functions. Subfunctions 0, 2, 11, 12, 13, 14, 15, 16, 17, 18, and 19 are queries and are safe; subfunctions 1 (Restart Communications Option), 10 (Clear Counters), and 20 (Clear Overrun) modify PLC state and can cause a PLC to drop its TCP connections or reset its error counters. Treat FC 8 as dangerous by default because distinguishing the sub-functions on the wire is error-prone and real PLCs have silently misimplemented the sub-function mapping for years.

    2. The mixer supports FC 43 (Encapsulated Interface Transport) in theory but the convention at Masa is to avoid it. Why?

    Reveal answer

    FC 43 sub-function 14 (Read Device Identification) is a multi-packet transport. Older MC-3100 firmware versions had a known bug where a mid-sequence disconnect would leave the PLC's socket in a half-open state, and the next incoming connection would get rejected until the PLC was power-cycled. Maxon Controls issued a firmware update in 2016 but Masa never deployed it because the plant has been running the old image for a decade. Convention beats correctness: stick to FC 3.

    3. Suppose you wanted to identify the PLC vendor on an unknown Modbus device. What is the first safe command you would try?

    Reveal answer

    Try FC 3 against register block 40100 first. Most vendors put a device identification block in that range, and FC 3 is universally supported. With mbpoll that is one command, -r 100 -c 7. If nothing is there, try FC 43 sub-function 14, which is the standard encapsulated interface transport for device identification. If both fail, check banner grabs on common ports (502, 102, 2222, 20000) and cross-reference against the plcscan database of known vendor fingerprints.

    4. Why does the flag format strip the OCR wrapper off the certificate?

    Reveal answer

    Because the flag itself is already wrapped in OCR{}. Nesting the wrapper would produce a doubly wrapped string that is unreadable and would fail the OCR platform flag validator. Stripping wrappers when composing composite flags is the normalization discipline that every real engagement report needs when combining artifacts from multiple sources.

    Defensive Recommendations to Masa

    Finding Risk Mitigation
    MC-3100 mixer running a 2012 firmware image with known FC 43 bug Medium Schedule a maintenance window and apply the Maxon 2016 firmware update
    Modbus write function codes accepted from any host on the operations VLAN Critical Deploy a Modbus-aware firewall with write-function-code allowlisting (see Exercise 3.4 Snort rule)
    Commissioning certificate stored as plaintext ASCII on the PLC Low Accept as a training convention; real plants would store the certificate off-PLC
    No enforced separation between "read-only" and "read-write" Modbus clients Medium Use Modbus/TCP Security (RFC 8502) where supported, or enforce source-IP allowlisting at the segmentation boundary

    Key Takeaways

    • Safe Modbus function codes are 1, 2, 3, 4, 7, 11, 12, 17, 20, 24, and 43. Dangerous ones are 5, 6, 8, 15, 16, 21, 22, 23
    • One mbpoll -t 4 command reads a whole register block with Function Code 3 and no code to write
    • A Wireshark capture showing only Func: 3 is the wire-level proof of read-only discipline you hand the client
    • Old PLCs crash on unexpected function codes. Never experiment on a production mixer; use an isolated test bench
    • Composite flags force you to normalize tokens (lowercase, strip wrappers, remove punctuation) the same way a real report does
