    Exercise OTSOC-5.2: Preserve the Evidence

    Scenario

    The freezer incident at Pecan Creek Creamery is being worked, and the plant engineer wants to reboot the affected freezer PLC to clear the warm drift and get production back. A reboot is reasonable from an operations point of view and a disaster from a forensics point of view: it wipes the volatile controller state, the running parameter export, and any in-memory write history. You have fifteen minutes of scenario time before that reboot to preserve the evidence that proves what the attacker did.

    You are the OT incident responder. Everything has been staged in a read-only evidence package so you can practice the prioritization and the evidentiary reasoning without touching production. You pull each artifact with curl and inspect it with jq on your Kali-based RangeBox.

    Host Role
    evidence.pcc.local (HTTP 80) The IR evidence package

    The package holds the controller running export, the known-good baseline, the corporate web access log, the jump-host auth log and shell history, the historian time series, and an incident summary. One of those artifacts is destroyed by the reboot. Your job is to collect in the right order and to recover the attacker's last logic change before the controller state is gone.

    Why this matters

    Order of volatility is an IT forensics idea that matters even more in OT, because the most valuable OT artifact is also the most fragile. In an IT breach you race to capture RAM before the host is powered off. In an OT breach you race to capture the controller's running parameters before an engineer reboots the PLC to restore production, and the operational pressure to reboot is enormous: every minute the line is down costs product. The running parameter export holds the attacker's last write, the register, the value, and the source, and a reboot clears it from controller memory with no copy anywhere else. The logs on the engineering workstation and the jump host are written to disk and survive a controller reboot, so they are lower in the collection order. Getting the order wrong means you reboot, restore production, and then discover the one artifact that proved the attack is gone.

    The reasoning you practice here is what separates an OT responder from an IT responder dropped into a plant. The IT responder pulls the logs first because that is the IT habit. The OT responder grabs the volatile controller state first, because the controller is about to be rebooted and the disk-based logs are not going anywhere. The flag is encoded in the controller artifact, so recovering it proves you preserved the right thing first.

    Before You Begin

    Every command runs on your Kali-based RangeBox. After the lab transitions to Running, read the evidence host IP from the Exercise Network panel and capture it into a shell variable, because every student gets a different /24.

    Kali - capture the evidence host IP from the panel

    # Replace the example octet with the evidence IP from the Exercise Network panel.
EVID=10.100.42.21
echo "evidence=$EVID"

    Confirm the package answers by reading its index.

    Kali - prove the evidence package is reachable

    curl -s "http://$EVID/" | head -20

    A directory index listing JSON and log files means the package is up. An empty reply or a hang means the lab is not Running yet.

    Learning Objectives

    • Prioritize OT forensic evidence by order of volatility under a reboot deadline
    • Identify the controller running export as the highest-priority, reboot-volatile artifact
    • Collect each artifact from the package and state its evidentiary value
    • Recover the attacker's last logic change from the controller export
    • Assemble the flag from the last write register and value

    Background: Order of Volatility in OT

    Order of volatility ranks evidence by how quickly it disappears, so you collect the most perishable first. The ranking for this incident, most volatile at the top:

    Rank Artifact Why it ranks here Survives a PLC reboot?
    1 Controller running parameter export Lives in controller memory; cleared by the reboot No
    2 Engineering workstation / jump-host auth log Written to disk on the jump host Yes
    3 Jump-host shell history On-disk file on the jump host Yes
    4 Corporate web access log On-disk Apache log on the IT/OT boundary Yes
    5 Historian time series Persisted on the historian database Yes

    The single artifact that the reboot destroys is the controller running export, so it is collected first regardless of how easy the disk-based logs are to grab. Everything below it can wait until after the line is restored.

    The OT inversion of the IT habit

    An IT responder grabs the logs first. In OT the controller running state is more volatile than any disk log and carries the proof of the manipulation, so it leads the collection order. Train the habit: in a plant, the controller memory is your RAM capture, and a pending reboot is your power-off clock.

    Walkthrough

    Step 1: Inventory the package

    List every staged artifact so you can plan the collection order before the clock runs out. Read the index, then note which file is the controller running state.

    Kali - list the staged artifacts

    curl -s "http://$EVID/" | grep -oE 'href="[^"]+"' | sed 's/href="//; s/"//'

    Artifacts in the package

    freezer_plc_running.json
freezer_plc_baseline.json
corpweb_access.log
jumphost_auth.log
jumphost_shell_history.txt
historian_timeseries.json
incident_summary.json

    The file named freezer_plc_running.json is the controller running export. It is the only artifact a PLC reboot would destroy, so it is first in the collection order.

    Step 2: Collect the highest-priority artifact first

    Collect the controller running export before anything else. Saving a local copy is your preservation step: once it is on your workstation, the reboot can no longer take it.

    Kali - preserve the controller running export

    curl -s "http://$EVID/freezer_plc_running.json" -o running.json
jq '.' running.json

    The running export

    {
  "controller": "freeze.pcc.local",
  "label": "running parameters at time of incident",
  "parameters": {
    "barrel_temp_pv_c": 1.8,
    "barrel_temp_sp_c": 2.5,
    "run_state": 1,
    "last_write_register": 11,
    "last_write_value_raw": 25,
    "last_write_source_ip": "10.100.4.66"
  }
}

    The parameters object carries the live state at the time of impact: a barrel process value of 1.8 C against a setpoint of 2.5 C, far above the normal minus 5 C. The three last_write_* fields are the attacker's last logic change, the register written, the raw value, and the source. None of that survives the reboot, which is why you grabbed it first.

    Step 3: Collect the surviving artifacts and note what each proves

    With the volatile artifact safe, collect the disk-based evidence. Each one corroborates a different stage of the intrusion. Read the jump-host auth log and shell history to establish the access path.

    Kali - collect the jump-host evidence

    curl -s "http://$EVID/jumphost_auth.log"
echo "----"
curl -s "http://$EVID/jumphost_shell_history.txt"

    What the jump-host evidence shows

    jump01 sshd[4811]: Accepted password for ot_contractor from 10.100.4.66 ...
...
nmap -n -p 502,102,44818,20000,4840 10.100.4.6 ...
python3 -c "...c.write_register(11, 25, slave=1)..."
history -c

    The auth log proves the ot_contractor account logged in from the same source IP the controller recorded, and the shell history shows the register enumeration, the write_register(11, 25) that set the warm drift, and the history -c the attacker ran to cover the tracks. The history -c cleared the in-memory history, but the on-disk copy you just collected survived.

    Now collect the boundary log and the historian trend to round out the timeline.

    Kali - collect the boundary log and the historian trend

    curl -s "http://$EVID/corpweb_access.log" | grep -i 'portal.php?page=../'
echo "----"
curl -s "http://$EVID/historian_timeseries.json" | jq '.[-4:]'

    The corporate access log shows the LFI requests that pulled the remote-access profile from the IT/OT boundary, the attacker's initial access. The historian trend shows the freezer barrel temperature climbing across the anomaly window, the physical effect of the write. Together they bracket the intrusion from initial access to physical impact.

    Step 4: Recover the attacker's last logic change

    The flag is built from the controller's last logic change: the register that was written and the raw value. Read both fields out of the running export you preserved.

    Kali - extract the last write register and value

    jq '{register: .parameters.last_write_register, value: .parameters.last_write_value_raw, source: .parameters.last_write_source_ip}' running.json

    The last logic change

    {
  "register": 11,
  "value": 25,
  "source": "10.100.4.66"
}

    The attacker wrote register 11 with a raw value of 25. On the CIP setpoint scale, a raw 25 corresponds to a barrel setpoint of plus 2.5 C, the warm drift that spoils product while staying under the coarse alarm limit. The register and value are the two tokens the flag encodes. The source IP is a finding you record in the timeline; it is read from the artifact, not a host you connect to.

    Output Interpretation

    • The controller running export was the only artifact at risk from the reboot, so collecting it first was the whole point of the exercise; the disk-based logs were never going to disappear
    • last_write_register and last_write_value_raw are the controller's own record of the manipulation, which is stronger evidence than the shell history because it lives on the device that was changed
    • The history -c in the shell history is an anti-forensics step, but the on-disk history file the responder collected predates the in-memory clear, so the attacker's commands survived
    • A raw register value of 25 is not 25 degrees; it is the raw integer on the controller's setpoint scale, which decodes to plus 2.5 C. Reading raw values without decoding them is a common analyst error

    Analysis Questions

    1. The engineer wants to reboot the PLC immediately. What do you collect before you let that happen, and why only that?

    Reveal answer

    Collect the controller running parameter export, freezer_plc_running.json, because it is the only artifact the reboot destroys. The auth log, shell history, web access log, and historian trend are all written to disk on hosts that are not being rebooted, so they can be collected after production is restored. Order of volatility says you spend your fifteen minutes on the one thing that is about to vanish, not on the logs that will still be there in an hour.

    2. The shell history ends with history -c. Does that mean the attacker's commands are gone?

    Reveal answer

    No. history -c clears the current shell's in-memory history list, but the responder collected the on-disk history file that was written before the clear ran, so the enumeration and the write_register(11, 25) are still recoverable. Anti-forensics that targets in-memory state often misses the on-disk copy, which is why preserving the file early matters.

    3. Why is the controller's last_write_register field stronger evidence than the jump-host shell history showing the same write?

    Reveal answer

    The shell history shows what the attacker typed on the jump host; the controller's running export shows what the controller actually received and applied. The shell history could be incomplete or tampered, but the controller recording its own last write is the device's first-party record of the change. Corroborating the two together, the typed command and the applied change, is the strongest evidentiary position.

    Capture the Flag

    The flag is built from the attacker's last logic change recorded in freezer_plc_running.json: the register that was written and the raw value. From Step 4, the register is the last_write_register field and the value is the last_write_value_raw field. Assemble them into the flag format below using the two integers you recovered. The flag names the engineering-workstation artifact and the last write it preserved.

    Flag format: OCR{ews_last_write_<masked>}

    The masked tokens are the register and value you read out of the controller running export. Assemble the flag and submit it in the OCR platform.
