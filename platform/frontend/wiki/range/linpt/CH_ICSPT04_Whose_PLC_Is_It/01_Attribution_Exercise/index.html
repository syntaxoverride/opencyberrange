    Exercise ICSPT-1.4: Whose PLC Is It Anyway?

    Engagement Status

    Client Masa Foods, Inc. (fictional)
    Role OT Security Engineer, Plant 1
    Phase Discovery Enumeration Exploitation Reporting

    What you know so far: You can read and decode Modbus/TCP at the byte level. Ben Ortiz, the Masa controls technician, has handed you an unlabeled PCAP from a forgotten USB stick and asked you for attribution.

    Environment Checklist

    Every ICSPT exercise assumes you read the Before-You-Begin section in Exercise 1.1 (Touring Masa Foods) first. If you have not, open that page now: it explains the two attacker-host options (your own Kali over VPN, or the browser-mounted RangeBox), how to read target IPs from the Exercise Network panel, and how to export them into shell variables.

    Exercise 1.4 uses the pcaphost.masa.local entry. If you already ran Exercise 1.3 this session, your /etc/hosts still has it. Otherwise add it now with the IP from the Exercise Network panel (label pcaphost):

    Kali (one-time per session)

    sudo tee -a /etc/hosts <<'HOSTS'
10.100.42.7   pcaphost.masa.local
HOSTS

    Then confirm name resolution and reachability:

    Kali

    getent hosts pcaphost.masa.local
ping -c 2 pcaphost.masa.local
curl -s -o /dev/null -w 'HTTP %{http_code}\n' http://pcaphost.masa.local/

    Expected: one name-to-IP line, two successful pings, and HTTP 200 from curl. If any step fails, fix connectivity before continuing.

    Scenario

    Ben found a USB stick in a desk drawer labeled mystery_capture.pcap. He dropped it off with a shrug: "I caught this off a plant switch last spring. I cannot remember which plant, and I do not want to plug a production switch back in to find out." The file is hosted at http://pcaphost.masa.local/mystery_capture.pcap. Your job is attribution.

    Why this matters

    Real incidents arrive with incomplete evidence. A USB stick from a retired engineer. A PCAP forwarded by a vendor after a support call. A log file from a SIEM that does not tag source plant. An email attachment with "I think this was from the water plant?" in the body. Before you can decide what to do with the evidence, you have to answer the prior question: where did it come from and what was it looking at?

    Attribution from traffic alone is a core OT incident response skill for three reasons. First, it lets you triage: a PCAP from the packaging line is a different conversation than a PCAP from the water treatment plant because the regulatory impact is different. Second, it lets you verify the chain of custody when a third party hands you evidence: if Ben's PCAP looks like Plant 2 but he swears he captured it at Plant 1, something is wrong and you need to know before you act. Third, it lets you produce a defensible report: a findings document that cannot name the source plant, the vendor, and the polling cadence is not a findings document, it is speculation. Every OT engagement eventually forces this exact question on the engineer, and the answer is always "read the traffic carefully until it tells you."

    You must answer four questions from traffic alone:

    1. Which Masa plant was captured (plant1, plant2, or plant3)?
    2. Which PLC vendor family do the controllers belong to?
    3. How many distinct PLCs appear?
    4. What is the HMI polling interval in whole seconds?

    Compose the answers into the flag format:

    OCR{<plant>_<vendor>_<count>plc_<interval>sec}

    No live PLC interaction is permitted. You have no walkthrough for this exercise. Use what you learned in Exercises 1.1 through 2.1 to read the capture methodically, and treat the mystery capture like real evidence: do not open it on a production host, use a clean scratch directory, and document every step.

    Suggested Methodology

    The flow below is one approach. Adapt it as you learn the capture.

    Stage 1: Triage

    • Download the file to a clean scratch directory on your attacker host
    • Run capinfos to get total duration, packet count, and start timestamp
    • Run tshark -z io,phs to confirm the protocol mix is Modbus-only

    Stage 2: Subnet and Host Listing

    • Run tshark -z conv,tcp -q to list TCP conversations and their byte counts
    • Note the source subnet of the HMI and the destination subnets of the PLCs
    • Cross-reference against the Plant 1 network diagram on docs.masa.local

    Stage 3: Vendor Fingerprinting

    • Filter to modbus and look at the registers being polled. Maxon PLCs use 40001-range for process variables and 40100-range for device identification
    • Check the byte patterns in responses for ASCII vendor codes if any FC43 or identification block reads appear
    • Compare your findings against the Plant 1 register map on the docs portal

    Stage 4: PLC Count

    • Use tshark -T fields -e ip.dst -Y 'modbus' | sort -u | wc -l for a quick count, or
    • Use Wireshark Statistics -> Conversations -> IPv4 for a graphical view
    • Confirm the count aligns with what the Plant 1 diagram shows

    Stage 5: Polling Interval

    • Pick one HMI-to-PLC destination pair
    • Filter modbus.func_code == 3 && ip.dst == <plc_ip> and examine the frame timestamps
    • Use tshark -T fields -e frame.time_relative to compute deltas in seconds
    • Round the interval to the nearest whole second for the flag

    Stage 6: Compose the Flag

    Once the four answers are known, substitute them into the template. Submit in the OCR platform.

    Worked Example of Methodology (Generic Values)

    If you were to use tshark end to end, your shell history for the exercise might look like:

    Kali

    mkdir -p ~/mystery && cd ~/mystery
curl -O http://pcaphost.masa.local/mystery_capture.pcap
capinfos mystery_capture.pcap
tshark -r mystery_capture.pcap -q -z io,phs
tshark -r mystery_capture.pcap -q -z conv,ip
tshark -r mystery_capture.pcap -Y modbus -T fields -e ip.src -e ip.dst | sort -u
tshark -r mystery_capture.pcap -Y 'modbus.func_code == 3 && ip.dst == <one_plc_ip>' \
  -T fields -e frame.time_relative

    The last command filters to the queries the HMI sends to a single PLC, so the timestamps it prints are one poll cycle apart. The gap between them is the polling interval. Do not measure the tens-of-milliseconds gap between a query and its response, or the fraction-of-a-second gap between the reads to the two different PLCs; neither is the polling interval.

    The same four answers come straight out of the Wireshark GUI if you prefer it to the terminal. The pcap you downloaded with curl is owned by you, so open it without sudo:

    Kali

    wireshark mystery_capture.pcap &
    1. Confirm the protocol, then read the subnet. Open Statistics > Protocol Hierarchy to confirm the traffic is Modbus/TCP. Then open Statistics > Conversations and select the IPv4 tab: one host (the HMI) talks to all the others, and every address sits in a single subnet, which is the plant signature you match against the network diagram on docs.masa.local.
    2. Count the PLCs. Stay in Conversations and switch to the TCP tab: the distinct hosts answering on port 502 are the PLCs. Count the unique server addresses, or type modbus in the display filter and read the distinct source addresses of the response packets.
    3. Fingerprint the vendor. Type modbus in the display filter and press Enter. Click a packet whose Info column reads Query ... Func: 3: Read Holding Registers, and in the Packet Details pane expand the Modbus node. Wireshark labels the field Reference Number, and it shows the zero-based wire address, not the documented register number: a Reference Number: 0 is documented holding register 40001 (the documented register is the reference number plus 40001, so wire 0 is 40001 and wire 99 would be 40100). The queries here sit at Reference Number: 0, the start of the holding-register block, which is the 40001 process-variable range and the Maxon register convention. Cross-check the layout against the register map on the docs portal.
    4. Measure the polling interval. Two short gaps will try to distract you, and neither is the polling interval: the PLC answers each query within tens of milliseconds (the request-response round-trip), and the HMI reads the second PLC a fraction of a second after the first (both happen inside one poll cycle). The polling interval is the gap between the HMI's reads to the same PLC across cycles. Isolate those: set the display filter to modbus.func_code == 3 && ip.dst == <one_plc_ip>, which leaves only the queries the HMI sends to that one PLC. Choose View > Time Display Format > Seconds Since Beginning of Capture and read the Time column: the gap from one timestamp to the next is the polling interval. Round it to whole seconds.

    Analysis Questions

    1. Why is the source IP subnet a stronger attribution signal than hostname resolution?

    Reveal answer

    Hostnames are a naming convention that can be retyped, reassigned, or not present at all in a network capture. Source IP subnets are assigned at the switch and router layer and reflect the physical cabling. On a plant network, subnets tend to be stable over years and map directly to cell, line, or plant boundaries. If the mystery capture shows a Plant 1 subnet, you can be highly confident the capture was taken on Plant 1 cabling.

    2. The vendor family is visible from the register map alone. How?

    Reveal answer

    Vendors publish register map conventions that become fingerprints. Maxon Controls uses 40001-range for process variables, 40100-range for device identification, and specific integer scalings (tenths of a degree Fahrenheit for the oven temperature). If the traffic shows those exact patterns, the PLC is almost certainly Maxon. Siemens, Allen-Bradley, and Schneider each have their own conventions you will learn in later phases.

    3. Could the attacker fake the MBAP transaction identifier pattern to throw off attribution?

    Reveal answer

    A sophisticated attacker could. Transaction IDs are chosen by the client with no validation. However, register addresses, byte scalings, and polling cadences are harder to fake because they depend on the actual PLC configuration. Attribution from a single field is weak. Attribution from four or five fields (subnet, register map, polling cadence, vendor code, function code mix) is strong.

    4. Why does the exercise require a round-number polling interval rather than an exact second?

    Reveal answer

    Real HMI poll loops drift by milliseconds due to scheduler jitter, TCP retransmits, and load on the HMI host. A capture that averages 5.02 seconds between polls is still a "5 second" poll. The flag format uses whole seconds because that is the precision most plant documentation uses. If a capture averaged 4.6 seconds, the same convention would round to 5.

    Defensive Recommendations to Masa

    Finding Risk Mitigation
    Unlabeled PCAP found on plant equipment Low Adopt an evidence handling standard and require captures to carry capture-time metadata
    Capture contains full unauthenticated Modbus traffic Critical Segment the plant VLAN and block unmonitored access to TCP/502
    Polling cadence visible to anyone on the operations subnet Low Baseline and alert on changes to polling cadence, which can indicate a rogue client

    Key Takeaways

    • Attribution is cheap when you combine subnet, register map, PLC count, and polling interval
    • Vendor fingerprints are baked into register map conventions, not just banners
    • Treat unlabeled captures like real evidence: scratch directory, documented steps, and metadata preserved
    • Whole-second polling intervals are the plant documentation convention
