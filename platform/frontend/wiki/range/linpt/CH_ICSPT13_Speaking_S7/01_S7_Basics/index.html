    Scenario

    Why this matters

    Speaking a new ICS protocol on the wire is a skill, not a library call. The first time you connect to a Siemens S7 PLC you will meet concepts that have no Modbus equivalent: PDUs, racks and slots, datablocks, and the TPKT/COTP transport stack that wraps every S7 message. Reyna does not care whether you read the right number on the first try. Reyna cares that the next time you touch Plant 2, you know what rack, slot, and db_read mean and you can explain to the plant engineer why the connection succeeded or failed. Exercise 4.1 exists to build that muscle.

    The commissioning certificate in DB10 is a deliberately safe read. The Masa Foods Plant 2 engineering team plants an ASCII certificate in DB10 on every commissioned PLC so that operations staff can confirm the controller identity without opening TIA Portal. Your job is to read 32 bytes from DB10 starting at offset 0 and decode them as ASCII. The decoded value is the flag.

    Background: What S7comm Is

    S7comm is the proprietary protocol Siemens uses for all of its S7-300, S7-400, and S7-1200/1500 controllers. On the wire it is layered on top of two older standards:

    Layer Purpose
    TCP/102 Transport
    TPKT (RFC 1006) Packetizes ISO messages over TCP
    COTP Connection-Oriented Transport Protocol (ISO 8073 class 0)
    S7comm Application layer (function codes, item addressing, datablocks)

    The TPKT and COTP layers come from the OSI era and are why every S7 connection starts with a short handshake. python-snap7 handles both layers for you, so the only call you need is Client.connect(address, rack, slot, tcpport=102).

    Rack and slot

    Siemens addresses a PLC by rack and slot. For S7-1200 controllers, the CPU sits at rack 0, slot 1. That is the combination every Exercise 4.x uses. Older S7-300 controllers sometimes live at rack 0, slot 2, but you will not meet one in this track.

    Datablocks (DBs)

    Where Modbus has "holding registers", S7comm has "datablocks". A datablock is a named region of memory inside the PLC that you address by number. DB1 is process data. DB10 is a commissioning certificate. DB100 is the device identification string. The Plant 2 PLC uses DB999 for an incident marker and DB200 for an assessment flag. You address a datablock read as db_read(db_number, offset, length).

    Walkthrough

    Stage 1: Verify the Stack

    Kali

    python3 -c "from snap7.client import Client; print('snap7 ok')"
getent hosts plc-water.masa.local
nc -zv plc-water.masa.local 102

    All three must succeed before you continue.

    Stage 2: Connect and Read DB10

    Open a Python script that builds an S7 connection step by step. The pattern is:

    1. Create a Client() object (the snap7 session handle).
    2. Call connect(host, rack, slot, tcpport=102). For S7-1200 CPUs, rack is always 0 and slot is always 1.
    3. Call db_read(db_number, start_offset, length) to pull raw bytes from a datablock.
    4. Wrap the result in bytes() because db_read returns a bytearray that does not support .decode() directly.
    5. Strip trailing null bytes with .rstrip(b"\x00") because Siemens datablocks are null-padded to their declared size.
    6. Decode the remaining bytes as ASCII.

    Kali

    python3 - <<'PYEOF'
from snap7.client import Client
c = Client()
c.connect("plc-water.masa.local", 0, 1, tcpport=102)
raw = bytes(c.db_read(10, 0, 32))
text = raw.rstrip(b"\x00").decode("ascii")
print("DB10:", repr(text))
c.disconnect()
c.destroy()
PYEOF
    Expected output 
    DB10: 'OCR{...}'

    The six-step pattern (create, connect, db_read, bytes, rstrip, decode) is the S7comm equivalent of the Modbus read_holding_registers workflow you used on Plant 1. Every Exercise 4.x reuses it. Commit the sequence to memory now.

    Decode and submit in the OCR platform.

    Stage 3: Spot the Device ID

    DB100 holds the device identification string. The first 32 bytes are the vendor line, and the next 32 bytes are the order code. Read all 64 bytes, then slice the buffer into two halves and decode each one separately. The slicing is necessary because the null-padding between the two fields would otherwise appear as garbage in the middle of a single decoded string.

    Kali

    python3 - <<'PYEOF'
from snap7.client import Client
c = Client()
c.connect("plc-water.masa.local", 0, 1, tcpport=102)
raw = bytes(c.db_read(100, 0, 64))
vendor = raw[0:32].rstrip(b"\x00").decode("ascii")
order = raw[32:64].rstrip(b"\x00").decode("ascii")
print("vendor:", vendor)
print("order: ", order)
c.disconnect()
c.destroy()
PYEOF

    Output Interpretation

    • A successful connect() call returns with no exception. If you get Snap7Exception, check that rack=0, slot=1 and that TCP/102 is reachable
    • db_read returns a bytearray that must be wrapped in bytes() before you slice or decode it
    • The certificate block is null-padded to 32 bytes. Strip trailing null bytes before decoding
    • A device ID that does not start with Siemens means you are talking to the wrong host. Disconnect and verify the target IP

    Analysis Questions

    1. Why does S7comm require rack and slot numbers where Modbus does not?

    Reveal answer

    Siemens S7 hardware is modular. A real plant rack holds a power supply, a CPU card, and optional communication processors, each in a numbered slot. The rack and slot numbers let a client address the correct CPU card when a rack holds more than one. Modbus has no concept of hardware modularity at the protocol layer, so it does not need an equivalent.

    2. What happens if you pass tcpport=102 without the keyword argument?

    Reveal answer

    python-snap7's connect() takes positional args (address, rack, slot) only. Passing a fourth positional argument raises TypeError. You must always use the tcpport= keyword. The keyword requirement catches most students on their first S7 connection because the Modbus equivalent is positional.

    3. DB10 in the Plant 2 simulator is a plain ASCII string. Is that how a real PLC would store commissioning data?

    Reveal answer

    Real Siemens projects store commissioning metadata as structured datatypes (STRUCTs with typed fields for plant code, commissioning date, firmware hash, and so on), not as freeform ASCII. The simulator uses flat ASCII because it is the cleanest way to teach db_read and .decode('ascii') without also teaching S7 structured data. Treat the ASCII certificate pattern as a teaching aid, not a production model.

    4. Wireshark shows a TPKT and COTP layer on every S7comm packet. Could a Modbus IDS signature catch an S7 write attempt?

    Reveal answer

    No. Modbus signatures look for the Modbus function code byte at a fixed offset in a TCP payload that has no TPKT or COTP header. S7comm payloads have those headers, so a Modbus signature will not match. Protecting Plant 2 requires an S7-aware IDS ruleset, and the two plants cannot share a single detection signature set.

    Key Takeaways

    • S7comm rides on TPKT and COTP over TCP/102. python-snap7 hides that plumbing, but you should still know it is there
    • Siemens S7-1200 CPUs always live at rack 0, slot 1. S7-300 controllers sometimes use slot 2
    • Datablocks are the S7 equivalent of Modbus holding registers, addressed by number and offset
    • Modbus and S7comm do not share an IDS signature. Plant 2 needs its own detection ruleset
    • Strip trailing null bytes before decoding ASCII datablock reads, or your decoded string will carry garbage
