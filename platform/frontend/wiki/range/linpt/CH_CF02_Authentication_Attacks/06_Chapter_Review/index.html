    CapitalFlow Markets Authentication Attacks: Chapter Review

    What You Learned

    The five exercises in this chapter covered the most common categories of web application authentication and access control vulnerabilities. Each exercise targeted a different CapitalFlow Markets service, demonstrating that a single organization can have multiple independent security flaws across its infrastructure.

    Exercise CF2.1 demonstrated credential stuffing against a login endpoint without rate limiting. The attack succeeded because the server accepted unlimited authentication attempts, allowing hydra to test hundreds of username/password combinations per minute. The defense is straightforward: rate limiting, account lockout, and CAPTCHA challenges.

    Exercise CF2.2 revealed how custom session management using MD5 hashes of predictable inputs (timestamp and user ID) allows token forgery. The server exposed the generation parameters in response headers, giving you everything needed to compute a valid admin token. The lesson: always use cryptographically secure random number generators for session tokens.

    Exercise CF2.3 exploited SQL injection in a transaction search feature. The application concatenated user input directly into SQL queries, allowing UNION-based extraction of data from the admin_secrets table. Parameterized queries would have prevented the attack entirely.

    Exercise CF2.4 demonstrated IDOR in a portfolio management system where changing the user ID in the URL granted access to other users' data. The application checked authentication but not authorization. Server-side ownership validation is the only reliable fix.

    Exercise CF2.5 used stored XSS to steal the admin's session cookie through a feedback form that did not sanitize HTML or JavaScript input. The admin's cookie lacked the HttpOnly flag, allowing the injected script to read and exfiltrate it.

    Connect the Dots

    Real-world penetration tests rarely use a single technique. The five attack categories from this chapter frequently chain together in multi-stage compromises.

    Consider a scenario where the reconnaissance from Chapter 1 reveals a login endpoint and the technology stack. A brute-force attack (CF2.1) discovers valid credentials. Those credentials grant access to the application, where a SQL injection vulnerability (CF2.3) exposes the database schema, including a user table with password hashes. Cracking the admin hash (or forging a session token as in CF2.2) grants admin access. From the admin dashboard, an IDOR vulnerability (CF2.4) exposes all user portfolios. A stored XSS payload (CF2.5) planted in the admin panel captures the cookies of every staff member who logs in, extending the compromise beyond a single account.

    Each exercise in isolation demonstrates a single vulnerability class. Combined, they illustrate how attackers escalate from initial access to full organizational compromise through systematic exploitation of multiple flaws.

    Self-Assessment Answer Key

    1. Rate limiting restricts the number of login attempts per IP or account per time window. Account lockout disables the account after a threshold of failures. CAPTCHA challenges require human interaction, blocking automated tools. Implementing all three provides defense in depth.

    2. MD5 is deterministic and fast, meaning the same input always produces the same output and millions of candidates can be tested per second. When the inputs (timestamp and user ID) are predictable, an attacker can compute valid tokens for any user. Secure session tokens require cryptographically secure random number generators (CSPRNGs) that produce outputs no attacker can predict.

    3. A parameterized query separates SQL code from user data using placeholders. The database engine compiles the query structure first, then inserts user input as literal data values. Because the input is never interpreted as SQL code, injection syntax is treated as a search term rather than query logic.

    4. Authentication verifies who the user is (identity). Authorization determines what the user is allowed to do (permissions). IDOR exploits missing authorization checks: the user is authenticated, but the server does not verify they are authorized to access the specific resource they requested.

    5. Stored XSS persists on the server and executes in every victim's browser that views the affected page. Reflected XSS requires the victim to click a crafted link. Stored XSS affects multiple victims simultaneously without additional attacker interaction.

    6. The HttpOnly flag tells the browser to block JavaScript from accessing the cookie via document.cookie. Session cookies marked HttpOnly cannot be stolen through XSS, because injected scripts cannot read them. All session and authentication cookies should use HttpOnly because client-side JavaScript has no legitimate need to access session tokens directly.

    7. The attacker sends UNION SELECT queries with increasing numbers of NULL columns (1, 2, 3, ...) until the database stops returning an error. The number of NULLs that produces a valid response matches the column count of the original query.

    8. Sequential integers allow an attacker to enumerate all resources by simply incrementing a counter. UUIDs are harder to guess, which slows enumeration, but do not fix the vulnerability. If the server skips the authorization check, an attacker who obtains a valid UUID (from API responses, error messages, or URL leakage) can still access unauthorized resources. Server-side authorization is the only reliable fix.
