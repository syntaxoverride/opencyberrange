    Exercise 5.1: Pass-the-Hash

    Before You Begin

    NTLM authentication is challenge-response over the user's NT hash. Anywhere NTLM is accepted, the NT hash alone is sufficient; you never need the plaintext. The technique is "pass-the-hash" (PtH). Modern AD environments still accept NTLM on SMB, WMI, WinRM (kind of), MSSQL, and any other protocol that runs the NTLMSSP exchange. Plaintext is convenience; the NT hash is the actual currency.

    Exercise 5.1 gives you the local Administrator NT hash for a per-student member server and asks you to authenticate, run commands, and read the per-token flag.

    Tools required: netexec, psexec.py, wmiexec.py, smbexec.py, evil-winrm. Pre-installed on Kali.

    Scenario

    Marcus Bell: "Plaintext passwords are nice. Hashes are enough."

    The hash for Administrator on ws-mem-<token> is shown in your lab dashboard. The flag file is C:\flags\pth_flag_<token>.txt.

    Credentials:

    Username Hash Source
    Administrator (local) (per-token NT hash) Lab dashboard

    Target: ws-mem-<token>

    Your Objectives

    • Verify SMB authentication with the hash
    • Choose between psexec.py, wmiexec.py, smbexec.py, and evil-winrm for command execution
    • Read the per-token flag

    NTLM Authentication With a Hash

    The diagram below shows the canonical three-message NTLMSSP exchange. The attacker has the NT hash; the server has its stored copy. The plaintext password never appears anywhere.

    sequenceDiagram
    autonumber
    participant C as Client (Kali)
    participant S as Server (ws-mem-token)

    C->>S: NEGOTIATE_MESSAGE<br/>"I want NTLMv2"
    S-->>C: CHALLENGE_MESSAGE<br/>random 8-byte challenge
    Note over C: Compute HMAC-MD5(NT_HASH, challenge + client_blob)
    C->>S: AUTHENTICATE_MESSAGE<br/>username + computed HMAC

    Tool Picker: Noise vs Capability

    Four common execution paths exist on top of PtH. The table below ranks them so you pick the right tool for the job.

    Tool Privilege Noise Best for
    evil-winrm Administrator low (WinRM looks like normal admin traffic) interactive PowerShell
    wmiexec.py Administrator medium (WMI process create) one-shot commands
    smbexec.py SYSTEM medium-high (SMB service install) when you need SYSTEM and WinRM is off
    psexec.py SYSTEM high (event 7045 service install) classic, but loud

    Background: How Pass-the-Hash Works

    NTLM authentication is a three-message exchange:

    1. NEGOTIATE: client tells server "I want to do NTLM"
    2. CHALLENGE: server returns a random 8-byte challenge
    3. AUTHENTICATE: client computes HMAC-MD5(NT_HASH, challenge) and sends the result

    The server (or KDC) verifies by computing the same HMAC against its stored NT hash for the user. If they match, authentication succeeds. Note what the protocol requires: the NT hash, not the plaintext. The plaintext is only ever needed when the NT hash itself is missing (i.e., when computing the NT hash from the password the user typed). Once the hash exists in any form; in SAM, in LSASS, in cached credentials, in the wire dump from a previous capture; it is interchangeable with the plaintext for any NTLM-accepting protocol.

    Where the hash comes from

    Source How
    secretsdump.py DCSync rights pull every domain user's NT hash from the DC
    mimikatz lsadump::sam Local SAM extraction on a compromised host
    mimikatz sekurlsa::logonpasswords LSASS memory dump on a compromised host
    lsassy Network-side LSASS dump (gives hashes for cached creds)
    pypykatz Cross-platform LSASS parsing (Linux-friendly)
    dpapi-ng Windows credential vault decryption
    LAPS read Plaintext local admin from ms-Mcs-AdmPwd (then NTLM-hash it locally)
    Captured Net-NTLM cracked Cracking Net-NTLMv2 yields plaintext, then compute NT hash

    What works with PtH and what doesn't

    Protocol / Service PtH works?
    SMB (psexec, wmi, smbclient, etc.) Yes
    WinRM with NTLM auth Yes
    MSSQL with Windows auth Yes
    RDP Only with Restricted Admin mode + registry tweak
    Web SSO via NTLM (intranet sites) Yes
    Web SSO via Kerberos / SAML No (need plaintext or a TGT)
    Workgroup local logon at console No (need plaintext)

    The exception list is short. Most operationally interesting access works PtH-direct.

    Tool Primer

    netexec PtH validation

    netexec smb <target> -u Administrator -H '<NT hash>' --local-auth

    -H accepts an NT hash (32 hex chars) instead of a password. --local-auth says "this is a local account, not a domain account." Drop --local-auth for domain accounts.

    psexec.py

    psexec.py Administrator@<target> -hashes :<NT hash>

    Format: LM_HASH:NT_HASH. LM is usually empty for modern hashes; just use :NT_HASH. Drops you to a SYSTEM shell on the target.

    wmiexec.py

    wmiexec.py Administrator@<target> -hashes :<NT hash>

    Quieter than psexec (no service install). Runs commands as Administrator (not SYSTEM). No interactive shell semantics; each command is a separate WMI invocation.

    smbexec.py

    smbexec.py Administrator@<target> -hashes :<NT hash>

    Drops to a SYSTEM shell via SMB-only protocol. Less detection than psexec.

    evil-winrm with hash

    evil-winrm -i <target> -u Administrator -H <NT hash>

    Native PowerShell shell over WinRM. The cleanest interactive experience.

    Walkthrough

    Step 1: Validate the Hash

    Before chaining any execution tool, confirm the hash actually authenticates. netexec smb does the cheapest possible NTLM exchange (NEGOTIATE / CHALLENGE / AUTHENTICATE then session disconnect) and prints whether the hash worked. The probe catches hash typos and stale credentials before you spend time on a noisier execution attempt.

    Kali - Confirm hash works

    netexec smb ws-mem-${OCR_SCOPE_TOKEN} \
  -u Administrator -H '<NT hash>' --local-auth
    Flag Effect
    smb Use the SMB protocol module.
    -u Administrator Username (local).
    -H '<hash>' NT hash (32 hex chars). Replaces -p.
    --local-auth Authenticate as a local account, not domain. Drop this for domain accounts.

    [+] indicates success. The output also shows the target OS string, signed/unsigned SMB, and (with --shares) the available shares.

    Step 2: Pick Your Execution Method

    The four common methods compared:

    Method Privilege Detection Interactive
    psexec.py SYSTEM Service install (loud) Yes
    smbexec.py SYSTEM Service install via SMB only (quieter than psexec) Yes
    wmiexec.py Administrator WMI process create (medium) Pseudo
    evil-winrm Administrator WinRM session (often allowlisted for admins) Yes

    For this exercise, any of them works. Use evil-winrm for the cleanest interactive PowerShell.

    Step 3: Read the Flag (evil-winrm)

    evil-winrm wraps the WinRM protocol (HTTP on TCP 5985 by default, HTTPS on 5986). With -H it sends NTLM with the NT hash directly. The remote PowerShell session runs as Administrator (not SYSTEM); for this exercise, Administrator can read the file.

    Kali - Connect via evil-winrm

    evil-winrm -i ws-mem-${OCR_SCOPE_TOKEN} \
  -u Administrator -H '<NT hash>'
    Flag Effect
    -i <host> Target hostname or IP.
    -u <user> Username.
    -H <hash> NT hash (no quoting required by evil-winrm but quote to be safe).

    At the PowerShell prompt:

    PS C:\> type C:\flags\pth_flag_${OCR_SCOPE_TOKEN}.txt

    Submit the OCR{...} value.

    Step 4: Compare Methods

    For practice, run the same operation through psexec, wmiexec, and smbexec, noting the differences in shell semantics and what the SOC would see for each.

    Kali - psexec.py

    psexec.py Administrator@ws-mem-${OCR_SCOPE_TOKEN} -hashes :<NT hash>
    Token Effect
    <user>@<host> impacket auth string.
    -hashes :<NT> LM:NT hash format; LM is empty so the colon is leading.

    Drops to C:\Windows\system32 as NT AUTHORITY\SYSTEM. Generates event 7045 (service install) on the target.

    Kali - wmiexec.py

    wmiexec.py Administrator@ws-mem-${OCR_SCOPE_TOKEN} -hashes :<NT hash>

    Each command is a one-shot WMI process invocation; no persistent shell. Quieter than psexec because no service is installed.

    Common gotchas

    • Hash format mismatch: impacket scripts want LM:NT (LM half is usually empty so use :NT). netexec wants just NT for -H. evil-winrm wants just NT for -H. Mixing the two formats produces STATUS_LOGON_FAILURE.
    • Wrong account scope: --local-auth validates against the target's local SAM. Without it, netexec authenticates against AD. The same hash may exist in both stores with different values for accounts that share a name; check the source.
    • WinRM disabled: evil-winrm fails with Connection refused if WinRM is not running. Fall back to psexec or wmiexec, both of which use SMB.
    • Account lockout: even though PtH does not "fail" in the traditional sense, multiple wrong-hash attempts increment badPwdCount on the account. Two stale-hash attempts plus a real user typo can lock the local Administrator. Be deliberate.

    Blue Team Perspective

    Pass-the-Hash itself produces no unique signal at the protocol level; defenders detect on the lateral pattern that follows.

    Activity Event ID Where it fires
    Lateral logon as local Administrator 4624 logon type 3 Target Security log
    psexec service install 7045 Target System log
    Suspicious authentication (NTLM type) 4624 with Authentication Package = NTLM from non-DC source Target Security log
    Defender for Identity "Suspected identity theft (pass-the-hash)" MDI

    What detection is realistic

    PtH-specific detection is hard because the wire bytes are identical to legitimate NTLM auth. The detection that works is on the identity reuse pattern: the same local Administrator account authenticating to many machines from one source IP within a short window. Microsoft Defender for Identity ships this detection as "Lateral movement using local admin credentials." SIEM rule: alert when a local Administrator account succeeds at NTLM auth on more than 3 distinct hosts within 5 minutes.

    Hardening Note

    PtH disappears as an attack class when you disable NTLM and rotate local admin passwords per host. The list below is the realistic order of operations.

    PtH hardening

    • Deploy LAPS (legacy or Windows LAPS) to give every host a unique random local admin password.
    • Audit and reduce NTLM usage with event 8001 logging; migrate consumers to Kerberos.
    • Disable NTLM outbound on Tier-0 servers and inbound on DCs first.
    • Restrict local admin lateral logon via Deny access to this computer from the network for Domain Users and Local accounts GPOs.
    • Enforce Credential Guard on managed workstations to make LSASS dumps useless on modern Windows.
    • Build SIEM detection on cross-host local-admin NTLM auth bursts.

    Analysis Questions

    1. PtH works because NTLM authentication uses the NT hash directly. Why does Microsoft not just stop accepting NTLM?

    Reveal Answer

    Backwards compatibility. NTLM is the fallback when Kerberos is not available: workgroup hosts, machines that cannot reach a DC, downlevel clients, certain monitoring tools, third-party identity bridges, applications that hardcoded NTLM endpoints during their development. Disabling NTLM domain-wide in a typical enterprise breaks something on the order of dozens of integrations (sometimes hundreds), most of which are owned by teams that no longer exist or that regard NTLM as a deep dependency. Microsoft is moving toward NTLM disablement: Windows 11 and Server 2022 introduced "NTLM auditing" (event 8001) so administrators can quantify who actually uses NTLM, with the long-term plan to disable it. The migration path is years long for any enterprise that did not start in the late 2010s. Mid-migration environments often disable NTLM only on specific server classes (DCs, Tier-0 servers) while leaving it on workstations.

    2. The exercise says PtH works on RDP only with Restricted Admin mode plus a registry tweak. What does Restricted Admin do, and why is it less convenient than regular RDP?

    Reveal Answer

    Restricted Admin mode (RDP) avoids sending the user's plaintext credential to the remote host. Instead, it uses Network Level Authentication (NLA) via NTLM with the NT hash. The remote host accepts the NTLM authentication and authorizes the user, but the user's credentials are not loaded into the remote LSASS. The implications: (a) the user can RDP with PtH (no plaintext required); (b) the user cannot reach further hosts from the RDP'd host using the same credentials, because the credentials are not present in memory to be re-used or stolen via Mimikatz. The trade-off is the second point: legitimate operators who RDP-then-RDP (jump host workflows) lose the credential-cache convenience. The registry tweak HKLM\System\CurrentControlSet\Control\Lsa\DisableRestrictedAdmin = 0 enables it; many organizations leave it disabled because the support cost of "I cannot RDP through the jump host" exceeds the security benefit.

    3. The four execution tools (psexec, smbexec, wmiexec, evil-winrm) trade noise for capability. Rank them by likely SOC detection signal and explain why.

    Reveal Answer

    Loudest to quietest, roughly: psexec > smbexec > wmiexec > evil-winrm (in many environments). psexec installs a Windows service, fires event 7045 (service install) plus the service's own start events; SOCs commonly rule on 7045 from non-management origins. smbexec uses an SMB-only service install path that historically left less log evidence (no 7045 in some configs) but newer Windows versions log it similarly. wmiexec uses WMI process creation; event 4688 fires on the target with the parent process being WmiPrvSE.exe, which is detectable but blends with legitimate management traffic. evil-winrm uses WinRM (HTTP/5985 or HTTPS/5986); WinRM is often allow-listed for admin tools (Ansible, PowerShell Remoting, Configuration Manager), so the connection itself looks like normal admin traffic. The actual ranking depends on the environment: a SOC with strict WinRM monitoring sees evil-winrm immediately; a SOC drowning in WMI noise from SCCM may miss wmiexec entirely. Operators try the quietest tool that gets the job done first.

    Key Takeaways

    • NTLM accepts the NT hash directly; PtH = use the hash where you would use the plaintext.
    • netexec smb -H <hash> is the smallest validation step.
    • Four common execution paths (psexec, smbexec, wmiexec, evil-winrm) trade noise for capability.
    • RDP requires Restricted Admin mode for PtH, and that mode is often disabled.
    • Microsoft's long-term plan is NTLM disablement; the migration is years long for most enterprises.

    Cheat Sheet Recap

    The four operations below cover the entire PtH workflow. Pick the execution tool to match the noise budget you have on the engagement.

    Goal Command
    Validate hash via SMB netexec smb <host> -u Administrator -H '<NT hash>' --local-auth
    Interactive PowerShell shell evil-winrm -i <host> -u Administrator -H <NT hash>
    One-shot SYSTEM cmd psexec.py Administrator@<host> -hashes :<NT hash>
    Quieter Administrator one-shot wmiexec.py Administrator@<host> -hashes :<NT hash>

    Spaced Repetition

    Card 1: netexec PtH One-Liner

    Q: Validate local Administrator PtH against 10.10.10.20 with hash aad3b....

    Answer 
    netexec smb 10.10.10.20 -u Administrator -H 'aad3b...' --local-auth

    --local-auth for local accounts. Drop it for domain accounts. -H takes the NT hash; the LM half is optional and usually empty.

    Card 2: psexec.py Hash Format

    Q: Write the psexec.py command for local Administrator on 10.10.10.20 with NT hash e5d3....

    Answer 
    psexec.py Administrator@10.10.10.20 -hashes :e5d3...

    Format: LM:NT. LM is usually empty (:NT). Drops to a SYSTEM cmd shell. For domain auth: psexec.py CORP/Administrator@10.10.10.20 -hashes :NT.

    Card 3: Where PtH Does NOT Work

    Q: Name three contexts where you have an NT hash but PtH does not give you access.

    Answer
    1. RDP without Restricted Admin mode + registry tweak (RDP normally requires plaintext at the workstation logon prompt). 2. Web SSO via Kerberos or SAML (those flows require a TGT or SAML assertion, not an NTLM hash). 3. Console / interactive logon at a workgroup machine (no NTLMSSP exchange involved; the SAM stores the hash but Windows logon UI does not accept the hash form). For each of these you need either the plaintext, a forged TGT, or a Silver/Golden ticket.

    Card 4: evil-winrm with Hash

    Q: Write the evil-winrm command to PowerShell-shell into srv01 as Administrator with NT hash 7777....

    Answer 
    evil-winrm -i srv01 -u Administrator -H 7777...

    Drops to a PowerShell prompt as Administrator. Works against any Windows host with WinRM enabled (port 5985 default). Useful built-ins at the prompt: upload localfile remotefile, download remotefile localfile, Invoke-Command.

    Card 5: NTLM Disablement Trajectory

    Q: Why is Microsoft's plan to disable NTLM taking so long?

    Answer

    Backwards compatibility. NTLM is the fallback when Kerberos is unavailable, used by workgroup hosts, downlevel clients, third-party tools that hardcoded NTLM endpoints, and many monitoring/management tools whose vendors have not migrated. Disabling NTLM in a typical enterprise breaks dozens or hundreds of integrations whose owners are unknown or unresponsive. Microsoft is shipping NTLM auditing (event 8001) so administrators can quantify usage before disabling. Mature environments are doing partial disablement (Tier-0 first, then DCs, then sensitive servers); full domain-wide disablement is years out for most enterprises.
