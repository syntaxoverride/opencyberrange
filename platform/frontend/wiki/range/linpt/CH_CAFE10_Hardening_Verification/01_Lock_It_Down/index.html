    Exercise 5B: Lock It Down

    Engagement Status

    Client: Bean & Byte Cafe Role: Security Auditor Phase: Reconnaissance Service Enumeration Exploitation Detection Hardening Verification

    What you know so far:

    • You mapped the entire cafe network (9 devices, flat subnet, zero segmentation)
    • You exploited default SNMP community strings, DVR default passwords, POS debug endpoints, thermostat command injection, NAS default credentials, printer JetDirect, barista workstation cron escalation, and more
    • You captured traffic, performed credential pivots, wrote IDS rules, and delivered a full audit report
    • The cafe owner hired an IT consultant to remediate the findings

    Your task: The consultant claims the worst vulnerabilities are fixed. Verify the remediation independently. Find what's actually been secured, what hasn't, and collect the flag parts from the remaining vulnerable services. Flag tokens in service responses are prefixed with OCR-SN:: use only the value after the prefix when assembling the flag.

    Objective

    Re-test the partially hardened Bean & Byte Cafe environment. Systematically verify each previously exploited attack path. Determine which vulnerabilities have been remediated and which remain. Extract flag parts from the services that are still exploitable.

    Difficulty: Advanced Estimated time: 75 minutes

    Background: Why Verification Matters

    Remediation without verification is theater. An IT consultant says "I fixed SNMP" -- what does that actually mean? Did they change the community string? Disable the service entirely? Restrict it to a management VLAN? You don't know until you test.

    Partial hardening is arguably worse than no hardening at all. It creates a false sense of security. The cafe owner thinks the problems are solved. Meanwhile, half the attack surface is exactly where you left it.

    Your job is to produce a verification matrix -- a device-by-device, vulnerability-by-vulnerability accounting of what changed and what didn't.

    The Verification Methodology

    flowchart TD
    A[Previous Finding] --> B{Re-test Exploit}
    B -->|Fails| C[Remediated]
    B -->|Succeeds| D[Still Vulnerable]
    C --> E[Document Fix Method]
    D --> F[Document Remaining Risk]
    E --> G[Verification Report]
    F --> G

    What the Consultant Claims to Have Fixed

    According to the remediation report you received:

    1. Gateway SNMP -- Community string changed from public to a non-default value
    2. DVR default password -- Admin password changed from 123456 to a strong password
    3. POS debug endpoint -- /debug route removed from the application

    Your first task is to verify these three claims. Then re-test everything else.

    Phase 1: Verify Claimed Remediations

    Start by confirming the three fixes the consultant reported.

    SNMP Community String

    Test the gateway SNMP community string

    Test whether the gateway still responds to public. Replace <gateway_ip> with the gateway address from your prior recon.

    timeout 5 snmpget -v2c -c public <gateway_ip> 1.3.6.1.2.1.1.1.0

    A real fix causes the command to timeout or return "No Response." A successful data response means the community string was never changed.

    DVR Default Password

    Re-test the DVR login with the old password

    Send the previously working credentials to the DVR login endpoint. Replace <dvr_ip> with the DVR address.

    curl -s -X POST http://<dvr_ip>/login -d 'user=admin&pass=123456'

    A real fix returns an authentication failure. Check the HTTP response code and body.

    Browse to the DVR login

    Open http://<dvr_ip>/ to see the login form you are testing. The web console is still exposed to the whole subnet, so even if the password changed, the form remains a brute-force target you note in the verification matrix.

    POS Debug Endpoint

    Probe the POS debug route

    Request the debug route and read only the HTTP status code. Replace <pos_ip> with the POS terminal address.

    curl -s -o /dev/null -w '%{http_code}' http://<pos_ip>:8080/debug

    A real fix returns 404.

    Phase 2: Re-test Remaining Attack Surface

    Now test everything else. The consultant's report only mentioned three fixes. What about the rest?

    Smart Thermostat: Command Injection

    Re-test thermostat command injection

    The /diagnostics endpoint was vulnerable to command injection. Inject id after a benign host value to verify whether the vulnerability persists. Replace <thermo_ip> with the thermostat address.

    curl -s http://<thermo_ip>:8080/diagnostics -d 'host=127.0.0.1;id'

    If the output includes uid=0(root), the vulnerability is still live. Go deeper.

    Browse to the thermostat console

    Open http://<thermo_ip>:8080/ to see the operator UI and the "Network Diagnostics" link at the bottom. That link reaches the /diagnostics endpoint you just abused, confirming the injectable feature is still wired into the live interface.

    NAS Backup: Default SSH Credentials

    Re-test NAS default SSH credentials

    The NAS accepted admin:password via SSH. Attempt the same login and run whoami on it. Replace <nas_ip> with the NAS address.

    sshpass -p 'password' ssh -o StrictHostKeyChecking=no admin@<nas_ip> 'whoami'

    If you get admin back, nothing has changed.

    Browse to the NAS File Station

    Open https://<nas_ip>:8443/ (accept the self-signed certificate). The console lands straight on File Station with the default account, exposing the /backups share of POS database dumps, WiFi logs, and employee records. Default credentials over SSH and the same default exposure through the web UI are the same unfixed finding.

    Printer: JetDirect

    Query the printer over JetDirect

    Send a PJL information request to the raw print port and read the response. Replace <printer_ip> with the printer address.

    echo '@PJL INFO ID' | nc -w 5 <printer_ip> 9100

    Still responding without authentication? Note it.

    Barista Workstation: Cron Escalation

    Re-check the barista maintenance directory

    Log in as the barista user and list the maintenance directory permissions. Replace <barista_ip> with the workstation address.

    sshpass -p 'C0ff33_Br3w#' ssh -o StrictHostKeyChecking=no barista@<barista_ip> 'ls -la /opt/maintenance/'

    If /opt/maintenance/ is still world-writable, the cron escalation path is still open.

    Phase 3: Extract the Flag

    The remaining vulnerable services contain flag parts. You already know how to get them.

    Flag Part 1: Thermostat

    Read the thermostat flag part via command injection

    Reuse the command injection to read the flag file on the thermostat. Replace <thermo_ip> with the thermostat address.

    curl -s http://<thermo_ip>:8080/diagnostics -d 'host=127.0.0.1;cat /etc/flag_part.txt'

    Flag Part 2: NAS

    Read the NAS flag part over SSH

    Use the default SSH credentials to read the flag file on the NAS. Replace <nas_ip> with the NAS address.

    sshpass -p 'password' ssh -o StrictHostKeyChecking=no admin@<nas_ip> 'cat /srv/flag_part.txt'

    Combine both parts: OCR{________}

    Phase 4: Suricata Rule Development

    A hardened environment needs monitoring. Write Suricata rules to detect exploitation attempts against both the fixed and unfixed vulnerabilities.

    Provided Example Rules

    These two rules are provided as a starting point:

    alert udp any any -> $HOME_NET 161 (msg:"SNMP Community String Brute Force"; content:"public"; sid:1000001; rev:1;)
alert tcp any any -> $HOME_NET 9100 (msg:"Unauthenticated PJL Access"; content:"@PJL"; sid:1000002; rev:1;)

    Your Rules

    Write Suricata rules for the following detection scenarios. Consider what network traffic each attack generates.

    Rule 1: Thermostat Command Injection Detection

    The /diagnostics endpoint receives POST data with a host parameter. Command injection payloads typically contain shell metacharacters (;, |, `, $() after the hostname.

    # Write your rule here
# Hint: alert on POST requests to port 8080 containing both "diagnostics" and shell metacharacters

    Rule 2: NAS Default Credential SSH Login

    Detecting default credential use over SSH is harder at the network level because SSH is encrypted. Think about what you can detect: repeated SSH connection attempts to the NAS from non-management IPs, or successful SSH sessions from unexpected sources.

    # Write your rule here
# Hint: alert on SSH connections to the NAS IP from any source outside the management range

    Rule 3: DVR Brute Force Detection

    Even though the password was changed, the login form is still exposed. Detect brute force attempts.

    # Write your rule here
# Hint: alert on repeated POST requests to /login on port 80 within a short time window

    Defensive Recommendations: Complete Hardening

    The consultant fixed three things. Here is what complete hardening looks like:

    Category Remediation Priority
    Network Architecture Implement VLANs: POS, IoT, Staff, Guest, Management Critical
    SNMP Disable SNMP or restrict to SNMPv3 with authentication; bind to management VLAN only High
    SSH Disable password authentication; use key-based auth only; restrict to management VLAN High
    IoT Devices Isolate thermostat, cameras, menu display on dedicated IoT VLAN with no internet egress High
    Web Applications Input validation on all endpoints; parameterized queries; remove debug interfaces Critical
    Default Credentials Audit and change ALL default passwords across every device Critical
    Printer Require authentication for PJL/management; restrict JetDirect to print VLAN Medium
    Cron Jobs Audit file permissions on all scheduled task directories; principle of least privilege Medium
    Monitoring Deploy IDS/IPS (Suricata) with rules for all known attack patterns High
    Certificate Management Replace self-signed certificates with CA-signed; enforce HTTPS everywhere Medium
    Firmware Update all device firmware; establish patch management schedule High

    Common Mistakes

    Assuming fixed means secure

    The SNMP community string was changed, but SNMP still runs on the gateway and remains accessible from the entire subnet. Changing the string is a band-aid, not a fix. The real fix is network segmentation plus SNMPv3.

    Testing only what was reported

    The consultant fixed three things. If you only tested those three, you missed six other vulnerabilities that are still wide open. Always re-test the full attack surface.

    Forgetting the cron escalation

    The barista workstation cron job is subtle. The world-writable maintenance directory means any user with SSH access can escalate to root. The consultant never addressed it.

    Key Takeaways

    What You Learned

    1. Verification is a separate discipline from remediation. The person who fixes a vulnerability should not be the person who verifies the fix. Independent verification catches gaps.

    2. Partial hardening creates false confidence. Three fixes out of eleven vulnerabilities is a 27% remediation rate. The cafe owner believes the network is secure. It is not.

    3. Defense in depth requires completeness. Changing a password doesn't help if the service is still exposed to the entire network. Removing a debug endpoint doesn't help if the admin login is still injectable. Each fix must be evaluated in context.

    4. Monitoring fills the gap. While remediation catches up, detection rules (Suricata, log analysis) provide visibility into exploitation attempts. You can't fix everything overnight, but you can watch for attacks.

    5. Documentation drives accountability. The verification matrix is a professional deliverable. It tells the client exactly what was fixed, what wasn't, and what the remaining risk is. No ambiguity.
