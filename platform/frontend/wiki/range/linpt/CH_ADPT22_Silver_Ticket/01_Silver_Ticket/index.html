    Exercise 5.3: Silver Ticket

    Before You Begin

    A silver ticket is a forged TGS. You craft a service ticket from scratch, encrypt it with the target service's NT hash (or AES key), and present it to the service. The service decrypts the ticket, sees a valid PAC, and authenticates you as whoever you put in the ticket. The KDC is never involved; there is no AS-REQ, no TGS-REQ, no event 4769 on the DC. The signal lives entirely on the target service.

    The single-service scope makes silver tickets attractive when you need persistence on a specific service: the ticket works as long as the service account password does not rotate, and rotation is the only invalidation mechanism. Silver tickets are quieter than golden tickets (golden = forged TGT = used everywhere; silver = forged TGS = used on one service). Narrower scope; quieter footprint.

    Exercise 5.3 gives you the NT hash for svc-app01_<token>$ (a machine account) plus the domain SID. Forge a silver ticket for cifs/svc-app01_<token> as Administrator, mount the Admin$ share, read the flag.

    Tools required: impacket-ticketer. Pre-installed on Kali.

    Scenario

    Background: Silver vs Golden

    Property Silver Ticket Golden Ticket
    What is forged TGS-REP (service ticket) AS-REP TGT
    Signing key Service account NT hash / AES krbtgt NT hash / AES
    Scope One service Every service in the domain
    KDC interaction None (presented directly to service) None (TGT used to mint TGSes locally; no AS exchange)
    Detection signal Service-side PAC validation failures (rare); no KDC events Anomalous TGT lifetimes (often default 10 years in forgeries vs 10 hours real); KDC events 4769 with mismatched parents
    Invalidation Rotate the service account password Rotate krbtgt twice
    Persistence value Per-service, weeks-to-years Domain-wide, until krbtgt rotates

    The silver ticket's narrower scope is the trade-off: quieter, but only useful for the one service whose key you have. Operators use silver tickets when they have a specific target (a backup share, a database server, a file server holding sensitive data) and want to access it persistently without DC contact.

    Why the service accepts a forged ticket

    Service tickets are decrypted by the service using its own password-derived key. The decrypted ticket includes: - Authentication time - Authorization data (the PAC, with user SID and group memberships) - Various flags

    The service does not call back to the KDC to validate the ticket. The PAC has its own signatures (server signature + KDC signature), but on default Microsoft installations the KDC signature is not validated by the service; only the server signature, which is created with the service's own key. Since the attacker has that key, both signatures are forge-able.

    Microsoft introduced PAC validation modes that require services to call the KDC for the KDC-signature check, but the default for most services is "do not validate." The default-off behavior is why silver tickets work in practice.

    What goes in the ticket

    ticketer.py populates: - User SID (e.g., Administrator's: <DomainSID>-500) - User name (Administrator) - Domain SID - Group SIDs (default: 513, 512, 520, 518, 519 = Domain Users, Domain Admins, Group Policy Creator Owners, Schema Admins, Enterprise Admins) - Auth time, ticket lifetime - Flags (forwardable, renewable, etc.)

    The default group set is "all the famous groups" including Domain Admins. The service does not check whether the user is actually in those groups; the PAC says they are, the service trusts the PAC.

    Tool Primer

    ticketer.py for silver ticket

    ticketer.py \
  -nthash <NT_HASH> \
  -domain-sid <DOMAIN_SID> \
  -domain corp.nordport.local \
  -spn cifs/svc-app01_<token>.corp.nordport.local \
  Administrator
    Flag Effect
    -nthash the service account's NT hash (the forging key)
    -domain-sid the domain SID (so the ticket's Administrator SID is constructed correctly)
    -domain realm name
    -spn the service principal name in the ticket
    - positional argument: the impersonated user

    Output: Administrator.ccache written to current directory.

    Using the forged ticket

    export KRB5CCNAME=Administrator.ccache
klist
smbclient //svc-app01_<token>.corp.nordport.local/Admin$ -k -c "ls"

    -k tells smbclient to use the cached Kerberos ticket. The service receives the AP-REQ wrapping the ticket and authenticates the session as Administrator.

    Walkthrough

    Step 1: Gather the Inputs

    Silver-ticket forgery needs four inputs: the service account's NT hash (the forging key), the domain SID (so the impersonated user's SID is constructed correctly), the realm name, and the SPN of the target service. The lab dashboard supplies the first two; the realm and SPN you derive from the scenario.

    From the lab dashboard, note:

    Service account:   svc-app01_<token>$
NT hash:           <32 hex chars>
Domain SID:        S-1-5-21-XXXX-YYYY-ZZZZ
Service host FQDN: svc-app01_<token>.corp.nordport.local

    If you do not have the domain SID, derive it from any object's SID by stripping the trailing RID: S-1-5-21-1234-5678-9012-500 (Administrator) drops the -500 to give S-1-5-21-1234-5678-9012. secretsdump.py -just-dc-user krbtgt also prints the domain SID in its output.

    Step 2: Forge the Silver Ticket

    ticketer.py builds a TGS structure from scratch: it fills in the user/group SIDs, server signature with the supplied NT hash, and writes a Kerberos credential cache file. No DC contact occurs; the entire forgery is local.

    Kali - ticketer.py

    cd ~/work && mkdir -p adpt-5-03 && cd adpt-5-03
ticketer.py \
  -nthash '<NT hash>' \
  -domain-sid 'S-1-5-21-XXXX-YYYY-ZZZZ' \
  -domain corp.nordport.local \
  -spn "cifs/svc-app01_${OCR_SCOPE_TOKEN}.corp.nordport.local" \
  Administrator
ls -la Administrator.ccache
    Flag Effect
    -nthash <hash> NT hash of the service account; the forging key. Use -aesKey for AES-only environments.
    -domain-sid <SID> Domain SID prefix (without trailing RID).
    -domain <realm> Realm name. Lowercase or uppercase both work; ticketer normalizes.
    -spn '<svc>/<host>' SPN this ticket is good for. Must match how the client will request the service.
    <user> Positional: the user identity the ticket impersonates.

    The output is <user>.ccache (here Administrator.ccache) ready to use. ticketer prints [+] Saving ticket in Administrator.ccache on success.

    Step 3: Use the Ticket

    The ccache is loaded by setting KRB5CCNAME. SMB-aware tools with -k use cached Kerberos credentials transparently. The target service receives an AP-REQ wrapping the forged TGS; it decrypts with its own key (matches), validates the server signature (matches because we used its key), and serves the request as Administrator.

    Kali - smbclient with the forged ticket

    export KRB5CCNAME=$(pwd)/Administrator.ccache
klist
smbclient "//svc-app01_${OCR_SCOPE_TOKEN}.corp.nordport.local/Admin$" -k \
  -c "ls; get silver_flag_${OCR_SCOPE_TOKEN}.txt"
cat silver_flag_${OCR_SCOPE_TOKEN}.txt
    Token Effect
    KRB5CCNAME=$(pwd)/... Absolute path required (relative paths confuse some GSSAPI versions).
    klist Display the ccache contents; verifies the right principal/SPN is loaded.
    -k Use cached Kerberos credentials for SMB.

    Submit the OCR{...} value.

    Step 4: Confirm No DC Events

    For learning, confirm the KDC saw nothing. From the DC's event log, search 4769 events around the time of your operation. There should be none from your source IP for the silver-ticketed SPN. The TGS was forged locally; the KDC never received a request. Compare to the GenericAll exercise (4.1) where 4724 fires immediately on the DC; the silence here is the silver ticket's defining advantage.

    Common gotchas

    • SPN mismatch: the SPN in the ticket must exactly match the SPN derived from how the client connects. //host/share derives cifs/host; //host.fqdn/share derives cifs/host.fqdn. Pick one and be consistent.
    • Wrong RID for impersonation: Administrator always has RID 500. ticketer hardcodes the right value when given the user name; if you supply -user-id 500 explicitly, double-check.
    • Stale credential cache: KRB5CCNAME may already point at a previous TGT. Clear with kdestroy -A (all caches) or set KRB5CCNAME to the new file's full path to override.
    • AES-only KDC: if the domain disables RC4, the service's stored key is AES, not NT hash. Use -aesKey <key> instead of -nthash. The AES256 key from secretsdump output works directly.
    • PAC validation enabled: rare but possible; if the target enforces KDC PAC signature validation, the silver ticket fails because you cannot forge the krbtgt-signed portion. Switch to a different target service.

    Blue Team Perspective

    Silver tickets are the quietest forgery in AD. The detection has to live on the target service or rely on cross-referenced logs.

    Activity Event ID Where it fires
    Auth as Administrator on target 4624 logon type 3 Target Security log
    Missing 4769 for the same auth 4769 absence DC Security log (cross-reference)
    KDC PAC validation failure 4673 (failure) DC + target log (only if validation on)
    Defender for Identity "Suspected Golden Ticket usage (encryption downgrade)" MDI (catches ticket anomalies)

    Why detection is hard

    The KDC never sees the silver ticket. The target service accepts it as a normal AP-REQ because the server signature is valid. The cross-reference signal; "auth happened on the service but no 4769 was issued by the KDC for that user/service pair"; exists only if you correlate target and DC logs by user, service name, and timestamp. Microsoft Defender for Identity does some of this; bespoke SIEM rules can do more.

    Hardening Note

    The vulnerability is the cached service-account password. Rotate it and the forgery dies; rotate it forever (gMSA) and forgery is impractical.

    Silver-ticket hardening

    • Migrate every service account to a gMSA. 240-byte auto-rotated passwords make captured hashes uncrackable and obsolete every 30 days.
    • Enable KDC PAC signature validation on Tier-0 services (registry / GPO setting). Costs a round-trip per auth; defeats silver-ticket forgery.
    • Audit machine-account hash exposure: any compromise of a host = silver ticket for every service on that host.
    • Monitor target Security logs for 4624 logon type 3 events that have no corresponding 4769 on the DC within a 5-minute window.
    • Disable RC4 forest-wide so silver tickets must use AES (still feasible but increases attacker complexity).

    Analysis Questions

    1. Silver tickets work because services do not validate the KDC signature on the PAC. Why does Microsoft default to no validation, and what changes when validation is on?

    Reveal Answer

    Default no-validation is a performance and reliability optimization: every service operation becomes a KDC round-trip if validation is on, doubling the load on DCs and adding a network dependency to every authenticated call. The Microsoft setting Validate KDC PAC Signature (registry / GPO) enables it. When on, the service computes the KDC signature using its trust relationship with the KDC and sends a validation call to the DC; if the signature does not match, the service rejects the ticket. With validation on, silver tickets fail because the attacker does not have the krbtgt key needed to forge the KDC signature. Most environments leave validation off for the performance cost. Tier-0 services (DCs themselves, certain backup software) sometimes have it on; the rest typically do not.

    2. The default group SID list in ticketer.py includes 512 (Domain Admins). The service trusts that claim without verification. What is the implication for non-DA services that should restrict access to actual DA members?

    Reveal Answer

    Non-DA services that gate access on group membership read the membership from the PAC, which the attacker has populated with whatever groups they want. So a "Domain Admins only" share, a "Backup Operators only" backup target, or any service that checks IsInRole("Domain Admins") will accept the forged ticket as a valid DA. Silver tickets are dangerous against well-secured services for exactly that reason: the gating logic on the service trusts the ticket, not the directory. The defender controls are: (a) enforce KDC PAC signature validation as above; (b) authorize requests by querying AD directly rather than reading the PAC (slower, but accurate); (c) rotate service account passwords frequently, which invalidates outstanding silver tickets (typically gMSA's 30-day rotation does this automatically). Most environments do none of these; silver tickets remain effective.

    3. Silver tickets are scoped to one service, but the same NT hash forges tickets for any SPN registered to that account. How does the practical scope of a silver ticket compare to the theoretical "one service"?

    Reveal Answer

    Practically: every SPN registered to the account is a forge-able service. A SQL service account with SPNs MSSQLSvc/db01:1433, MSSQLSvc/db02:1433, and MSSQLSvc/db-cluster:1433 can be silver-ticketed for any of those three. A machine account ALSO has SPNs by default: cifs/<host>, host/<host>, RestrictedKrbHost/<host>, RPCSS/<host>, WSMAN/<host>, TERMSRV/<host>. So a captured machine NT hash forges tickets for every Windows service running on that host: SMB, CIFS, WinRM, RDP, RPC. The "one service" framing is misleading; the practical scope is "everything the account can speak Kerberos for." For a machine account that is the entire Windows service surface of that host.

    Key Takeaways

    • Silver ticket = forged TGS; signed with the service account's NT hash; presented directly to the service; KDC never involved.
    • ticketer.py -nthash <hash> -spn <service> <impersonated_user> forges in one command.
    • Default Windows services do not validate the KDC PAC signature; the forgery is accepted.
    • Practical scope is every SPN registered to the account, not "one service."
    • Defender controls: KDC PAC validation (rarely enabled), gMSA rotation, query AD directly for authz.

    Card 2: Silver vs Golden Comparison

    Q: Three differences between silver and golden tickets.

    Answer
    1. Forging key: silver uses the service account's hash; golden uses krbtgt's hash. 2. Ticket type: silver is a TGS for one service; golden is a TGT usable everywhere. 3. Invalidation: silver invalidates when the service account password rotates; golden invalidates only after rotating krbtgt twice. Trade-off: silver is quieter and per-service; golden is louder and domain-wide.

    Card 3: Why Forgery Works Against Default Services

    Q: Default Windows services skip which PAC signature check, and what would change if it were enforced?

    Answer

    Services skip the KDC signature validation on the PAC by default; they only validate the server signature which they themselves can verify with their own key. Enabling KDC PAC signature validation forces the service to call the DC to verify; with validation on, silver tickets fail because the attacker has the service key but not krbtgt's. The validation costs a round-trip per authentication and is therefore disabled for performance.

    Card 4: Practical Scope of a Compromised Machine Hash

    Q: A captured machine account NT hash silver-tickets which services on that host?

    Answer

    All of them: cifs/<host> (SMB / Admin$), host/<host> (general host services), RestrictedKrbHost/<host> (constrained variant), RPCSS/<host> (RPC), WSMAN/<host> (WinRM), TERMSRV/<host> (RDP), LDAP/<host> (if the host runs LDAP). Every Windows service registers an SPN against the machine account by default; possessing the machine hash makes all of them forge-able. From silver tickets to those SPNs, local SYSTEM on the host is one S4U2self away.

    Card 5: Detection of Silver Tickets

    Q: Why are silver tickets so hard to detect, and what is the most practical defender control?

    Answer

    The KDC sees nothing (no 4769 event for a forged TGS). The service sees an inbound AP-REQ with a valid PAC; from the service's perspective the auth looks normal. The only KDC-side anomaly is the absence of a corresponding 4769 for the service ticket the service is using; detectable only with cross-referenced logs. The most practical defender control is gMSA migration: gMSA passwords rotate every 30 days and are 240 random bytes, so even a captured hash becomes useless quickly and is uncrackable in the meantime. KDC PAC validation is the strongest control but rarely enabled.
