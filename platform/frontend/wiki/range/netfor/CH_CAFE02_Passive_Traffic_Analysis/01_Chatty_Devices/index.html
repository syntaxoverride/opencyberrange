    Exercise 1B: Chatty Devices

    Engagement Status

    Client: Bean & Byte Cafe Role: Security Auditor Phase: Reconnaissance Passive Analysis Service Enumeration Exploitation Detection

    What you know so far:

    • You mapped the network in Exercise 1 and found 9 devices on a flat subnet
    • All devices are reachable from any position on the network
    • The cafe WiFi has no encryption: it is an open network

    Your task: Capture live network traffic and discover cleartext credentials, DNS queries, and mDNS service advertisements being broadcast by devices on the cafe WiFi.

    Objective

    Use passive traffic capture tools to observe network communications on the Bean & Byte Cafe WiFi. The customer laptop and other devices are constantly sending traffic, HTTP requests, DNS queries, and mDNS service announcements, all in cleartext. Capture the three flag tokens hidden in this traffic. Flag tokens in service responses are prefixed with OCR-SN: to help you identify them.

    Difficulty: Beginner Estimated time: 45 minutes

    Background: Why Open WiFi Is Dangerous

    An open WiFi network transmits all data without encryption. Every device on the network can see every packet sent by every other device. The risk is not theoretical: unencrypted wireless networks behave exactly this way by default.

    When a customer connects to the cafe's open WiFi and logs into a website over HTTP, their username and password travel across the air in plaintext. Any other device on the same network can capture and read those credentials.

    What Passive Analysis Reveals

    flowchart LR
    A[Open WiFi] -->|No Encryption| B[All Traffic Visible]
    B --> C[HTTP Credentials]
    B --> D[DNS Queries]
    B --> E[mDNS Services]
    C --> F[Passwords in Cleartext]
    D --> F2[Browsing History]
    E --> F3[Device Identities]

    Three categories of information leak on open networks:

    1. HTTP traffic: Login forms, search queries, and page content sent over port 80 are completely readable. Passwords submitted to HTTP sites appear as plaintext form data.

    2. DNS queries: Every website a user visits generates a DNS lookup. Even if the site itself uses HTTPS, the DNS query reveals which domain the user is trying to reach.

    3. mDNS/service discovery: Devices announce themselves on the local network using mDNS (multicast DNS, port 5353). These announcements reveal device names, types, and available services.

    Why This Matters for Security Auditing

    Passive traffic analysis requires no exploitation: the auditor only listens to what devices voluntarily broadcast. Passive capture is:

    • Legal in most contexts: You are observing traffic on a network you are authorized to audit
    • Undetectable: No packets are sent, so no intrusion detection system will flag your activity
    • Highly revealing: Credentials, browsing patterns, and device inventories all appear without any active probing

    Tools You'll Need

    Tool Purpose Example
    tcpdump Capture and display network packets tcpdump -i lab0 -A 'port 80'
    tshark Terminal-based Wireshark (alternative to tcpdump) tshark -i any -f 'port 53'
    strings Extract printable text from binary data tcpdump ... \| strings

    Both tcpdump and tshark are available in most penetration testing distributions (Kali, Parrot, etc.). You only need one of them: tcpdump is simpler for beginners.

    Key tcpdump Flags

    Flag Meaning
    -i lab0 Capture on the lab network interface (see note below)
    -A Print packet payload in ASCII (readable text)
    -c N Stop after capturing N packets
    -w file.pcap Write raw packets to a file for later analysis
    'port 80' BPF filter: only capture traffic on port 80

    RangeBox users: interface name

    The commands in this walkthrough use lab0 as the network interface. If you are using the RangeBox (browser-based terminal), your lab network interface will appear as eth1 instead. Run ip addr show to confirm your interfaces, then substitute eth1 wherever you see lab0 in the commands below.

    Flag Progress

    The flag has 3 parts. Collect all three from captured network traffic:

    Part Protocol What to Look For Token Found?
    1 HTTP (port 80) Cleartext password in POST data ________
    2 DNS (port 53) Suspicious hostname in query ________
    3 mDNS (port 5353) Service name in announcement ________

    Assembled flag format: OCR{________}

    Solution Walkthrough

    Independent Mode

    Want to try this on your own? You have everything you need above: the objective, the tools, and the flag progress table. Skip the walkthrough and come back if you get stuck. Hints are available in the platform after 5, 12, and 18 minutes.

    Step 1: Verify Your Position on the Network

    Confirm you are connected to the cafe network and can see traffic:

    ip addr show

    Note your VPN interface and IP address. You are on the same flat subnet as all cafe devices: including the customer laptop that is actively generating traffic.

    Step 2: Capture HTTP Traffic (Flag Part 1)

    The customer laptop is repeatedly submitting login credentials to the gateway over HTTP. Since the connection is unencrypted, the password appears in plaintext.

    Filter the tap stream for HTTP traffic:

    sudo tcpdump -i lab0 -A 'port 80'

    Watch the output for a few seconds. You will see HTTP POST requests containing form data.

    What to look for 

    POST /login HTTP/1.1
Host: 10.x.x.1
Content-Type: application/x-www-form-urlencoded

username=cafe_customer&password=XXXXXX_secret_pass
    The password field contains form data. Look for a value prefixed with OCR-SN:: the token is the part after the prefix.

    Filtering the noise

    If there is too much HTTP traffic, narrow your capture to only POST requests: 

    sudo tcpdump -i lab0 -A 'port 80' | grep -i 'password'

    Press Ctrl+C to stop the capture once you have found the token.

    Flag Part 1

    Look for a value prefixed with OCR-SN: in the POST data. The token is the part after the prefix. Write it down as Part 1.

    See the page those credentials log into

    The cleartext password you just captured is being POSTed to the gateway's web login. Browse to http://<gateway_ip>/ to see that exact admin page. The capture shows you the password travelling in the open; the browser shows you the door it opens.

    Step 3: Capture DNS Queries (Flag Part 2)

    DNS queries reveal every hostname a device tries to resolve. Even when browsing is done over HTTPS, the DNS lookup itself is usually unencrypted.

    Filter the tap stream for DNS traffic:

    sudo tcpdump -i lab0 'port 53'

    Watch the output. You will see normal DNS queries for sites like google.com and facebook.com, but mixed in among them is a query for an unusual internal hostname.

    What to look for

    Among the normal queries, look for one targeting a .beanandbyte.internal domain. The subdomain contains the second token, prefixed with OCR-SN:.

    Speeding up the search

    Pipe the output through grep to find the token faster: 

    sudo tcpdump -i lab0 'port 53' 2>/dev/null | strings | grep 'beanandbyte'

    Flag Part 2

    Look for the DNS query targeting a .beanandbyte.internal domain. The subdomain contains a value prefixed with OCR-SN:: the token is the part after the prefix. Write it down as Part 2.

    Step 4: Capture mDNS Announcements (Flag Part 3)

    Multicast DNS (mDNS) runs on port 5353 and is used by devices to announce their services on the local network. Devices broadcast their names and service types to the multicast address 224.0.0.251.

    Filter the tap stream for mDNS traffic:

    sudo tcpdump -i lab0 -A 'port 5353'

    Watch for mDNS announcement packets. One of the service names advertised on the network contains the third token.

    What to look for

    Look for a service advertisement containing a value prefixed with OCR-SN:. The token appears in the service type or instance name within the mDNS packet.

    Alternative approach

    sudo tcpdump -i lab0 -A 'port 5353' 2>/dev/null | strings | grep '_.*_tcp'
    Flag Part 3

    Look for a value prefixed with OCR-SN: in the mDNS advertisements. The token is the part after the prefix. Write it down as Part 3.

    Put a face on the chatty device

    The menu display is one of the devices announcing itself over mDNS and exchanging traffic with the gateway. Browse to http://<menu_ip>/ to see what that device actually serves: the cafe's digital menu board. A sign on the wall is still a networked computer broadcasting its identity to everyone on the open WiFi.

    Step 5: Assemble and Submit the Flag

    Combine the three tokens you captured:

    OCR{________}

    Submit this as your flag in the platform.

    Step 6: Save a Full Capture (Optional)

    A real security auditor would save the captured traffic for their report. Capture all three types of traffic to a PCAP file:

    sudo tcpdump -i lab0 -w /tmp/cafe_capture.pcap

    Press Ctrl+C after 60 seconds. The resulting file can be opened in Wireshark for detailed analysis.

    Common Mistakes

    Not waiting long enough

    The customer laptop sends traffic in a loop with random delays. If you don't see anything immediately, wait 10-15 seconds. The traffic will appear.

    Missing the POST data

    If you use tcpdump without the -A flag, you only see packet headers, not the payload content. Always use -A when looking for cleartext data.

    Confusing mDNS with regular DNS

    Regular DNS runs on port 53. mDNS runs on port 5353. They are different protocols on different ports. Make sure you capture on the correct port.

    Flag format

    The flag is OCR{________} with underscores separating the tokens. Do not add spaces or change the case.

    Key Takeaways

    What You Learned

    1. Open WiFi is a packet capture playground. Without encryption, every device on the network can read every other device's traffic. Packet visibility is not a vulnerability to exploit: it is the normal, expected behavior of unencrypted networks.

    2. HTTP is not secure. Any credentials submitted over HTTP (port 80) travel in cleartext. Cleartext transport is why HTTPS exists, but many IoT devices and older systems still use plain HTTP.

    3. DNS queries reveal browsing patterns. Even when a user connects to a site over HTTPS, the DNS query that resolves the hostname is typically unencrypted. An attacker can build a complete browsing history from DNS captures alone.

    4. mDNS announces device identities. Devices that use mDNS (Apple Bonjour, Linux Avahi) broadcast their names and services to the entire local network. The constant broadcasts make device enumeration trivial on flat networks.

    5. Passive analysis is undetectable. Unlike active scanning (nmap), passive capture generates no traffic and triggers no alerts. A real attacker on the cafe WiFi could sit quietly and collect credentials all day.

    Defensive Recommendations

    If you were writing this up for the cafe owner, here is what you would recommend:

    Finding Risk Recommendation
    Open WiFi (no encryption) All traffic visible to any connected device Enable WPA3 encryption with a posted passphrase at minimum; consider 802.1X for staff
    HTTP login on gateway Admin credentials transmitted in cleartext Enforce HTTPS-only access for all admin interfaces
    Cleartext DNS Browsing patterns exposed to all local devices Deploy encrypted DNS (DoH/DoT) on the gateway
    mDNS service announcements Device types and names broadcast to all Isolate IoT devices on a separate VLAN; disable mDNS on devices that do not need it
    No client isolation Connected clients can see each other's traffic Enable AP/client isolation on the wireless access point
