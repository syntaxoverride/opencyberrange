    Exercise CF1.2: Technology Fingerprinting

    Before You Begin

    You should have completed Exercise CF1.1 (Basic Web Enumeration), where you mapped the CapitalFlow Markets website, documented its pages and forms, and discovered hidden directories. The skills from CF1.1 carry forward here, as you will build on the attack surface map by identifying the exact technologies powering the application. Your VPN must be connected and your terminal open before continuing.

    Scenario

    Sarah Chen (CTO of CapitalFlow Markets) reviewed your initial reconnaissance findings and wants a deeper analysis. She asked: "You found the pages and forms. Now tell me exactly what software stack we are running, down to the version numbers. If any component has a known vulnerability, I want to know before we go live."

    Phase 2 of the assessment focuses on technology fingerprinting: identifying the web server, backend framework, frontend libraries, and any other software components from their signatures in HTTP headers, HTML markup, and JavaScript files.

    Target: capitalflow.lab (port 80)

    No credentials are provided. All fingerprinting is performed as an unauthenticated visitor.

    Your Objectives

    • Extract web server identification from HTTP response headers
    • Identify the backend framework from X-Powered-By and other custom headers
    • Analyze HTML source for frontend framework signatures and meta tags
    • Inspect JavaScript files for library names and version strings
    • Run an automated fingerprinting scan with whatweb
    • Find and submit the flag in OCR{...} format

    Background: Technology Fingerprinting

    Why Technology Identification Matters

    Every piece of software has a history of vulnerabilities. Knowing that a server runs nginx 1.24.0 narrows the search to CVEs (Common Vulnerabilities and Exposures) affecting that exact version. Knowing the frontend uses jQuery 3.6.0 reveals whether the application is susceptible to known prototype pollution or XSS (Cross-Site Scripting) vectors in that library. Technology fingerprinting transforms a generic target into a specific list of software components, each with its own vulnerability profile.

    Where Technology Signatures Hide

    Web applications leak technology information through multiple channels:

    Source What It Reveals Example
    Server header Web server name and version nginx/1.24.0
    X-Powered-By header Backend framework Express, PHP/8.2
    HTML <meta> tags CMS or generator <meta name="generator" content="WordPress 6.4">
    JavaScript <script> tags Frontend libraries jquery-3.6.0.min.js
    CSS class naming CSS framework class="btn btn-primary" (Bootstrap)
    Cookie names Session framework PHPSESSID (PHP), connect.sid (Express)
    Error pages Server/framework defaults Default nginx 404 or Express error handler

    Automated Fingerprinting

    Manual inspection catches obvious signatures, but automated tools combine hundreds of detection rules to identify technologies that leave subtle traces. Tools like whatweb, Wappalyzer, and BuiltWith test for specific patterns across headers, HTML, cookies, and JavaScript.

    Tool Primer: curl -I and whatweb

    curl -I for Header Inspection

    The -I flag sends an HTTP HEAD request and displays only the response headers. Headers contain server identification, caching policy, security controls, and session management details.

    curl -I http://<target>/

    Sample output:

    HTTP/1.1 200 OK
Server: nginx/1.24.0
X-Powered-By: Express
Content-Type: text/html; charset=utf-8
Set-Cookie: connect.sid=abc123; Path=/; HttpOnly

    Each header line provides a data point for the technology profile.

    whatweb for Automated Fingerprinting

    WhatWeb identifies web technologies by testing for known signatures across headers, HTML content, cookies, and JavaScript. The tool comes pre-installed on Kali Linux.

    whatweb http://<target>/

    Verbosity levels:

    Flag Level Output Detail
    (default) Brief One-line summary of detected technologies
    -v Verbose Detailed breakdown of each detection
    -a 3 Aggressive Sends additional requests to confirm detections

    Sample output:

    http://example.com [200 OK] Bootstrap, Country[US], HTML5, HTTPServer[nginx/1.24.0],
JQuery[3.6.0], Script, Title[Example Site], X-Powered-By[Express]

    WhatWeb lists every technology it detects along with version numbers where available.

    Walkthrough

    Step 1: Launch the Exercise

    Open the platform in your browser and start the exercise environment.

    • Navigate to Exercises and locate the CapitalFlow Markets track
    • Find Technology Fingerprinting and click Launch
    • Wait for the status to change to Running
    • Note the target IP displayed in the Active Lab View

    Step 2: Fetch HTTP Response Headers

    Start by requesting the response headers from the main page. The headers are the fastest source of technology information.

    Kali - Fetch response headers from the homepage

    curl -I http://capitalflow.lab/

    Examine each header line in the response. Look for:

    • Server: The web server software and version (e.g., nginx/1.24.0)
    • X-Powered-By: The backend framework (e.g., Express, PHP/8.2)
    • Set-Cookie: The cookie name reveals the session framework (connect.sid means Express/Node.js, PHPSESSID means PHP, JSESSIONID means Java)
    • X-Content-Type-Options, X-Frame-Options, Strict-Transport-Security: Security headers (or their absence)

    Record every header and its value. Missing security headers are findings too; they indicate gaps in the server's defensive configuration.

    Step 3: Inspect Headers on Additional Endpoints

    Different pages may return different headers. The login endpoint, API paths, and error pages can reveal additional technology details.

    Kali - Fetch headers from the login endpoint

    curl -I http://capitalflow.lab/login

    Kali - Fetch headers from an API endpoint

    curl -I http://capitalflow.lab/api/

    Kali - Trigger a 404 error page and examine its headers

    curl -I http://capitalflow.lab/nonexistent-page-12345

    Compare the headers across all three responses. Error pages sometimes reveal framework-specific default error handlers. API endpoints may return different Content-Type headers or additional custom headers that the main page does not include.

    Step 4: Analyze HTML Source for Framework Signatures

    Frontend frameworks leave distinctive patterns in the HTML markup. Bootstrap uses specific CSS class names, React injects a data-reactroot attribute, and content management systems embed generator meta tags.

    Kali - Search for meta generator tags

    curl -s http://capitalflow.lab/ | grep -i "meta.*generator\|meta.*version"

    Kali - Search for CSS framework signatures

    curl -s http://capitalflow.lab/ | grep -i "bootstrap\|tailwind\|bulma\|foundation"

    Kali - Search for frontend framework markers

    curl -s http://capitalflow.lab/ | grep -i "react\|angular\|vue\|data-reactroot\|ng-app\|v-app"

    Each match narrows down the technology stack. A class="navbar navbar-expand-lg" pattern indicates Bootstrap. A <div id="app"> with v-cloak attributes indicates Vue.js. Record every framework indicator you find.

    Step 5: Inspect JavaScript Files for Library Versions

    JavaScript files loaded by the page often contain version strings in their filenames or within the file content itself.

    Kali - List all JavaScript files loaded by the homepage

    curl -s http://capitalflow.lab/ | grep -oi 'src="[^"]*\.js[^"]*"'

    Look at the filenames in the output. A reference to jquery-3.6.0.min.js immediately identifies jQuery 3.6.0. Framework bundles like app.bundle.js or vendor.js may contain version strings inside the file.

    Kali - Fetch a JavaScript file and search for version strings

    curl -s http://capitalflow.lab/js/app.js | grep -i "version\|@license\|jQuery v\|React v\|Vue v"

    Library files typically include a license header at the top with the exact version number. These headers survive minification in many build configurations.

    Step 6: Run whatweb for Automated Detection

    Manual inspection catches the obvious signatures, but whatweb combines hundreds of detection rules to find technologies you might miss.

    Kali - Run whatweb in verbose mode

    whatweb -v http://capitalflow.lab/

    Review the output section by section. WhatWeb reports each detected technology with a confidence level and the evidence that triggered the detection. Pay attention to:

    • Technologies you already identified manually (confirmation)
    • Technologies you missed (new findings)
    • Version numbers you could not determine from headers alone

    Kali - Run whatweb in aggressive mode for deeper detection

    whatweb -a 3 http://capitalflow.lab/

    Aggressive mode sends additional requests to probe for technologies that require specific pages or paths to detect. Compare the aggressive results with the verbose results to see if additional components appear.

    Combine all findings from headers, HTML source, JavaScript files, and whatweb into a single technology profile. The profile should list every identified component with its version number (where known).

    Analysis Questions

    1. A web server returns the header Server: nginx without a version number. Does the absence of a version number mean the server is secure? What should a tester do next?

    Reveal Answer

    The absence of a version number means the administrator configured nginx to suppress version information (using server_tokens off). The server may still run a vulnerable version. A tester should look for other fingerprinting vectors: error page formatting, specific response behaviors, timing differences, and tools like nmap's HTTP fingerprinting scripts (http-server-header, http-headers) that can sometimes infer the version from behavioral patterns rather than explicit headers.

    2. Why is identifying JavaScript library versions important for a security assessment, even when the libraries run in the browser rather than on the server?

    Reveal Answer

    Client-side JavaScript libraries with known vulnerabilities can be exploited through XSS attacks. For example, older jQuery versions are vulnerable to selector-based XSS, and outdated Angular versions have template injection flaws. An attacker who identifies a vulnerable library version can craft payloads tailored to that library's specific weaknesses. Additionally, library versions sometimes correlate with the overall application age and maintenance level; a site running jQuery 2.x is likely to have other outdated components as well.

    3. An application sets a cookie named connect.sid. What does the cookie name tell you about the backend technology, and how does that knowledge help an attacker?

    Reveal Answer

    The connect.sid cookie name is the default for the express-session middleware in Node.js/Express applications. Knowing the backend framework helps an attacker in several ways: searching for Express-specific vulnerabilities, understanding the session management implementation (e.g., how tokens are generated and stored), and crafting payloads that target Node.js behaviors (such as prototype pollution or type coercion). Framework identification narrows the attack surface from "all possible technologies" to a specific set of known issues.

    Key Takeaways

    • HTTP response headers are the fastest source of technology information, often revealing the web server, backend framework, and session management approach in a single request
    • HTML source code contains framework signatures through CSS class naming conventions, meta tags, and data attributes that identify frontend libraries
    • JavaScript files include version strings in filenames and license headers that survive minification, revealing exact library versions for CVE research
    • Automated tools like whatweb combine hundreds of detection rules to catch subtle technology indicators that manual inspection would miss
    • Technology profiles feed directly into vulnerability research; every identified component with a version number becomes a search query against CVE databases and exploit repositories
