    CapitalFlow Markets Reconnaissance: Chapter Review

    What You Learned

    The two exercises in this chapter covered the complete web reconnaissance workflow against the CapitalFlow Markets trading platform. Exercise CF1.1 focused on manual exploration: browsing pages, reading HTML source code, identifying forms and input fields, checking robots.txt, and running gobuster to discover hidden directories. Exercise CF1.2 shifted to technology fingerprinting: extracting server versions from HTTP headers, identifying frontend frameworks from HTML signatures, inspecting JavaScript files for library versions, and running whatweb for automated detection.

    Together, these exercises produced a comprehensive attack surface map and technology profile for the CapitalFlow Markets application. Every finding from this chapter feeds directly into the authentication attack exercises in Chapter 2.

    Connecting to Chapter 2

    The reconnaissance data you gathered here is not just documentation; it is the operational input for every attack in Chapter 2. The login endpoint URL and form field names from CF1.1 tell you exactly where to send brute-force attempts (CF2.1). The session management details from CF1.2 inform your session hijacking approach (CF2.2). The technology stack identification helps you choose SQL injection payloads appropriate for the backend database (CF2.3). Directory enumeration results may have revealed API endpoints where IDOR (Insecure Direct Object Reference) vulnerabilities live (CF2.4). And understanding the frontend framework tells you how user input is handled, which shapes your XSS (Cross-Site Scripting) payloads (CF2.5).

    Professional penetration testers spend more time on reconnaissance than on exploitation. Thorough reconnaissance means fewer dead ends, more targeted attacks, and a clearer picture of the most impactful vulnerabilities.

    Self-Assessment Answer Key

    1. HTML comments can contain developer notes, internal API paths, TODO items about unfinished security features, hardcoded credentials, and version strings. Developers should strip all comments during the build process because every visitor receives the complete source code, including comments, when the page loads.

    2. Gobuster sends HTTP requests for thousands of common directory and file names from a wordlist. Each request tests whether a specific path exists on the server by examining the response status code. Paths that return 200, 301, or 302 exist on the server, even if no visible page links to them.

    3. The Server header identifies the web server software (e.g., nginx, Apache) and optionally its version. The X-Powered-By header identifies the backend application framework (e.g., Express, PHP). Together, they reveal both the infrastructure layer and the application layer of the technology stack.

    4. A 403 response confirms the path exists and contains something the server is actively protecting. A 200 response on a different path means open access. The 403 path is a higher-value target because the server administrator considered it important enough to restrict, which suggests sensitive content worth pursuing through other access methods.

    5. Known JavaScript library versions can be cross-referenced against CVE databases and exploit repositories. An attacker who identifies jQuery 3.6.0 can search for XSS vulnerabilities specific to that version and craft payloads that exploit the exact parsing behavior of that library, rather than guessing which payloads might work against an unknown target.
