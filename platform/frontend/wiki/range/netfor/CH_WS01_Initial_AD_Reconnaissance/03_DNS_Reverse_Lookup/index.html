    Exercise WS-1.3: DNS Reverse Lookup Mapping

    Before You Begin

    Exercise WS-1.2 revealed the forward lookup zone contents through a zone transfer. The zone data referenced a reverse lookup zone for the 10.100.0.0/16 network. Exercise WS-1.3 uses reverse DNS queries to map IP addresses to hostnames across a specific subnet within that range.

    Prerequisites:

    • Exercises WS-1.1 and WS-1.2 completed (you know dc01 hosts DNS and have seen the forward zone)
    • Active VPN connection to the Open Cyber Range
    • The dig command available on your Kali Linux attack box
    • Basic familiarity with shell scripting (for loops in Bash)

    Scenario

    Your zone enumeration in Exercise WS-1.2 revealed that a reverse lookup zone exists for the 10.100.0.0/16 network. Your team lead asks you to scan the DHCP (Dynamic Host Configuration Protocol) scope subnet; 10.100.250.0/24; for PTR (Pointer) records. Reverse lookups map IP addresses back to hostnames, and sweeping an entire subnet reveals which addresses are in use and what the associated hosts are named.

    Your Objectives

    1. Understand how PTR records work in reverse DNS zones
    2. Perform reverse lookups across the 10.100.250.0/24 subnet to discover active hosts
    3. Map discovered IP addresses to their hostnames
    4. Locate and retrieve the flag hidden in a reverse DNS entry

    Background: Reverse DNS and PTR Records

    Forward DNS maps names to addresses: you ask "What is the IP for dc01.corp.ocr-range.lab?" and get back an A record with the IP address. Reverse DNS works in the opposite direction: you provide an IP address and ask "What hostname is associated with 10.100.250.10?" The answer comes back as a PTR record.

    Reverse DNS zones are structured using the special in-addr.arpa domain. The octets of the IP address are reversed and appended to in-addr.arpa. For example, the reverse lookup for 10.100.250.10 queries the name 10.250.100.10.in-addr.arpa. Active Directory environments typically maintain reverse lookup zones so that PTR records are created automatically when hosts register their A records.

    Penetration testers use reverse DNS sweeps when they know a network range but do not have a complete list of hostnames. Sweeping a /24 subnet (256 addresses) takes only a few seconds and reveals every host that has a PTR record. Hosts without PTR records will return an empty response, so the sweep also shows which IP addresses are unused or unregistered in DNS.

    Tool Primer: dig for Reverse Lookups

    The dig command supports reverse lookups with the -x flag. The -x flag automatically converts the IP address into the in-addr.arpa format and queries for a PTR record.

    dig +short -x <ip-address> @<dns-server>
    Flag Purpose
    +short Print only the answer (hostname), not the full DNS response
    -x Perform a reverse lookup (PTR query) for the given IP
    @<dns-server> The DNS server to query

    When a PTR record exists, dig +short -x returns the hostname. When no PTR record exists, the command returns nothing (empty output). The +short flag is valuable when scripting because the output is a single line; the hostname; with no headers or extra sections.

    Wrap reverse lookups in a sweep loop

    To sweep a range of addresses, you can wrap the dig command in a Bash for loop:

    for i in $(seq 1 254); do
    result=$(dig +short -x 10.100.250.$i @dc01)
    if [ -n "$result" ]; then
        echo "10.100.250.$i -> $result"
    fi
done

    The loop iterates through addresses 10.100.250.1 to 10.100.250.254, performs a reverse lookup for each one, and prints only the addresses that have PTR records. The if [ -n "$result" ] test filters out empty responses so the output contains only live entries.

    Walkthrough

    Step 1: Test a Single Reverse Lookup

    Test a single reverse lookup

    Before sweeping the entire subnet, confirm that reverse DNS is working by querying a known address. The DC itself should have a PTR record.

    dig +short -x 10.100.250.10 @dc01

    Replace 10.100.250.10 with the IP address of dc01 if you recorded a different address in Exercise WS-1.1. A successful response returns the fully qualified domain name (FQDN) of the host, such as dc01.corp.ocr-range.lab. (note the trailing dot, which is standard in DNS responses).

    If the query returns nothing, verify that you are using the correct IP address and that your VPN connection is active.

    Step 2: Sweep the Subnet

    Sweep the subnet for PTR records

    Run the following loop to perform reverse lookups across the entire 10.100.250.0/24 subnet. The loop scans addresses 1 through 100 in the DHCP scope range.

    for i in $(seq 1 100); do
    result=$(dig +short -x 10.100.250.$i @dc01)
    if [ -n "$result" ]; then
        echo "10.100.250.$i -> $result"
    fi
done

    The sweep takes approximately 30-60 seconds depending on network latency. Each address with a PTR record will produce a line of output showing the IP-to-hostname mapping. Addresses without PTR records are silently skipped.

    Watch the output as the loop runs. Record every IP-to-hostname mapping you see; the complete list gives you a network map of the subnet.

    Step 3: Review the Sweep Results

    After the loop completes, review the list of discovered hosts. Look for patterns in the hostnames that suggest specific server roles or naming conventions. Note any hostnames that seem unusual or do not follow the standard naming pattern.

    Look through your results for any entry whose hostname suggests it might be significant or related to a flag.

    If you missed the entry during the live sweep, re-examine your sweep output carefully. You can also re-run the sweep and watch for hostnames that stand out from the standard naming pattern.

    Step 4: Query the Flag Hostname for a TXT Record

    Query the flag hostname for a TXT record

    The reverse lookup revealed a hostname that looks like a flag marker. Query that hostname for a TXT record to retrieve the actual flag value.

    dig +short TXT flag-r3v3rs3.corp.ocr-range.lab @dc01

    The TXT record associated with the flag hostname contains the lab flag. The value appears in double quotes in the dig output.

    Step 5: Interpret the Results

    The reverse DNS sweep turned IP addresses into a readable network map. Consider the following as you review your findings:

    • How many hosts are active in the 10.100.250.0/24 subnet?
    • Do the hostnames follow a consistent naming convention?
    • Which hosts appear to be servers versus workstations based on their names?
    • Why might the flag have been placed at a PTR record pointing to IP address 10.100.250.53 specifically? (Port 53 is the well-known port for DNS.)

    Reverse DNS sweeps are a reliable technique even when forward zone transfers are blocked. Administrators often forget to lock down reverse zones because the information disclosure risk is less obvious; but a complete IP-to-hostname map is valuable for an attacker planning lateral movement.

    Step 6: Find and Submit the Flag

    The TXT record query in Step 4 returned the flag for this exercise. The flag was found by following the chain: reverse lookup of 10.100.250.53 yielded the hostname flag-r3v3rs3.corp.ocr-range.lab, and a TXT query against that hostname returned the flag.     Analysis Questions

    1. Why do penetration testers perform reverse DNS sweeps even when they already have forward zone data from a zone transfer?

    Reveal Answer

    Forward zone transfers and reverse DNS sweeps can reveal different sets of hosts. Some hosts may have A records without corresponding PTR records, and vice versa. Running both techniques provides a more complete picture. Reverse sweeps also confirm which IP addresses are actively registered in DNS, helping the tester identify live hosts in a specific subnet.

    2. What does the in-addr.arpa domain do, and why are the IP octets reversed?

    Reveal Answer

    The in-addr.arpa domain is the DNS namespace designated for reverse lookups. The octets are reversed so that the DNS delegation hierarchy matches the IP address hierarchy. IP addresses are allocated from left to right (the leftmost octets identify the network), but DNS delegates from right to left (the rightmost labels are the top-level domain). Reversing the octets aligns the two hierarchies, allowing reverse DNS zones to be delegated along network boundaries.

    3. How could an administrator prevent the reverse DNS sweep performed in this exercise?

    Reveal Answer

    The administrator could restrict reverse zone queries by configuring DNS access control lists (ACLs) to limit which clients can query the reverse zone, or by removing the reverse lookup zone entirely if reverse DNS is not needed. In Active Directory environments, limiting DNS query access is more complex because domain-joined machines rely on DNS for service discovery. A more practical mitigation is to monitor DNS query logs for sweep patterns; hundreds of sequential PTR queries from a single source in a short time period.

    4. Why might some IP addresses in the subnet have no PTR record?

    Reveal Answer

    Hosts that are powered off, that use static IPs without DNS registration, or that were recently decommissioned may lack PTR records. DHCP-assigned addresses only have PTR records if the DHCP server or the client is configured to register reverse DNS entries. Devices outside the Windows domain (printers, network appliances, Linux hosts) may not register PTR records automatically.

    Key Takeaways

    • PTR records map IP addresses to hostnames and are stored in reverse lookup zones under the in-addr.arpa domain.
    • Reverse DNS sweeps across a subnet reveal which IP addresses are in use and what the associated hosts are named, even when forward zone transfers are blocked.
    • The dig -x flag automates the conversion of an IP address into in-addr.arpa format for reverse lookups.
    • Bash for loops combined with dig +short allow you to sweep an entire /24 subnet in under a minute from the command line.
