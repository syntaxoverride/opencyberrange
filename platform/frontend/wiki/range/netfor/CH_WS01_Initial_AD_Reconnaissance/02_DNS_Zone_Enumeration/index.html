    Exercise WS-1.2: DNS Zone Enumeration

    Before You Begin

    Exercise WS-1.1 confirmed that dc01 is a Domain Controller running DNS on port 53. Exercise WS-1.2 builds directly on that finding by querying the DNS service for a full inventory of records in the corp.ocr-range.lab zone.

    Prerequisites:

    • Exercise WS-1.1 completed (you know dc01 is a DC with DNS on port 53)
    • Active VPN connection to the Open Cyber Range
    • The dig command available on your Kali Linux attack box

    Scenario

    Having confirmed that dc01 is a Domain Controller running DNS, your next step as a penetration tester at CyberShield Consulting is to enumerate the DNS zone. A misconfigured DNS server may allow zone transfers, which would reveal every record in the domain's forward lookup zone; hostnames, IP addresses, mail servers, service locators, and text records; in a single query.

    Your Objectives

    1. Attempt an AXFR (full zone transfer) against corp.ocr-range.lab
    2. Enumerate DNS records returned in the zone transfer
    3. Identify TXT records that may contain useful information
    4. Retrieve the flag from a DNS TXT record

    Background: DNS Zones and Zone Transfers

    DNS organizes records into zones. A forward lookup zone maps hostnames to IP addresses (A and AAAA records), while a reverse lookup zone maps IP addresses back to hostnames (PTR records). Active Directory Integrated DNS zones also contain SRV records that advertise domain services, TXT records for various metadata, and other record types that support AD operations.

    A zone transfer (AXFR) is a mechanism designed to let secondary DNS servers replicate the full contents of a zone from a primary server. When a secondary server requests an AXFR, the primary server sends every record in the zone. The problem arises when the DNS server does not restrict which hosts can request a transfer. An unrestricted AXFR allows any client; including an attacker; to download the complete zone file.

    In a properly hardened environment, zone transfers are restricted to specific IP addresses (the secondary DNS servers). In lab and poorly configured production environments, zone transfers are sometimes left open to all clients. Penetration testers always check for unrestricted AXFR because the payoff; a complete map of the domain's DNS records; is enormous for minimal effort.

    Tool Primer: dig for Zone Transfers

    The dig command supports zone transfers with the AXFR query type. The syntax is as follows:

    dig AXFR <zone-name> @<dns-server>
    Parameter Purpose
    AXFR Request a full zone transfer (all records in the zone)
    <zone-name> The DNS zone to transfer, e.g., corp.ocr-range.lab
    @<dns-server> The DNS server to query

    When a zone transfer succeeds, dig prints every record in the zone. The output begins and ends with an SOA (Start of Authority) record, and all other records appear between those two SOA entries. A failed transfer returns a Transfer failed message or a REFUSED status code.

    You can also query for specific record types within a zone without a full transfer:

    dig TXT <name> @<dns-server>

    The TXT query returns only the text records associated with the specified name.

    Walkthrough

    Step 1: Attempt a Zone Transfer

    Attempt a full zone transfer

    Run the following command to request a full zone transfer of the corp.ocr-range.lab zone from dc01.

    dig AXFR corp.ocr-range.lab @dc01

    The output will be long if the transfer succeeds. Scroll through the results and look for the following record types:

    • SOA: Start of Authority, marks the beginning and end of the zone data
    • A: Hostname-to-IP mappings
    • SRV: Service locator records (AD uses these heavily)
    • TXT: Text records that may contain metadata, flags, or configuration data
    • NS: Name server records identifying the authoritative DNS servers

    If the transfer fails with Transfer failed or ;; connection timed out, the server is configured to deny AXFR requests from unauthorized clients.

    Step 2: Analyze the Zone Transfer Output

    A successful zone transfer reveals the full structure of the domain's DNS namespace. Review the output and look for patterns that help you understand the environment.

    Pay attention to the hostnames in A records; each one represents a host registered in DNS. Count the number of unique hostnames to estimate the size of the environment. Note any hostnames that suggest specific roles, such as dc01, web01, sql01, or file01.

    SRV records in the zone follow a naming convention that reveals AD services. Records under _tcp.corp.ocr-range.lab advertise Kerberos, LDAP, and Global Catalog (GC) endpoints. These records confirm the DC infrastructure you identified in Exercise WS-1.1.

    Step 3: Identify TXT Records in the Zone

    Scan the zone transfer output for lines containing TXT. TXT records stand out because their data is enclosed in double quotes. Some TXT records are standard (SPF records for email validation, for example), while others may contain custom data placed by administrators or applications.

    Filter the zone transfer for TXT records

    If you want to isolate TXT records from the zone transfer output, you can pipe the results through grep:

    dig AXFR corp.ocr-range.lab @dc01 | grep TXT

    The grep filter reduces the output to only lines containing the string "TXT," making flag-related records easier to spot among hundreds of zone entries.

    Step 4: Query the Flag TXT Record Directly

    Query the flag TXT record directly

    Based on the TXT records you found in the zone transfer, query the specific record that contains the flag.

    dig TXT _zone-flag.corp.ocr-range.lab @dc01

    Examine the ANSWER SECTION of the response. The TXT record value appears in double quotes and contains the flag for this exercise.

    Step 5: Interpret the Results

    The zone transfer gave you a complete view of the domain's DNS structure. Consider what the results tell you about the target environment:

    • How many hosts are registered in the forward zone?
    • Are there any hostnames that suggest high-value targets (database servers, web applications, file servers)?
    • Did the zone transfer reveal any reverse lookup zones? The presence of reverse zones means PTR (Pointer) records exist, which you will explore in Exercise WS-1.3.
    • What does a successful zone transfer tell you about the DNS server's security configuration?

    A successful AXFR against a production DNS server is a significant finding. The administrator has failed to restrict zone transfers to authorized secondary DNS servers. In a real engagement, you would document the unrestricted zone transfer as a vulnerability in your report and recommend configuring transfer restrictions.

    Step 6: Find and Submit the Flag

    The TXT record query in Step 4 returned the flag for this exercise. The flag is stored in the DNS TXT record at _zone-flag.corp.ocr-range.lab. Enter the flag value in the format OCR{...} on the submission page.

    Analysis Questions

    1. Why are unrestricted zone transfers considered a security vulnerability?

    Reveal Answer

    An unrestricted zone transfer exposes every DNS record in the zone to any client that requests one. The attacker gains a complete map of hostnames, IP addresses, service locations, and metadata; information that would otherwise require many individual queries or brute-force enumeration to collect. Restricting AXFR to authorized secondary DNS server addresses prevents unauthenticated information disclosure.

    2. What is the difference between a forward lookup zone and a reverse lookup zone?

    Reveal Answer

    A forward lookup zone maps hostnames to IP addresses using A records (IPv4) and AAAA records (IPv6). A reverse lookup zone maps IP addresses back to hostnames using PTR records. Both zone types can be stored in Active Directory Integrated DNS. Forward zones are organized by domain name (corp.ocr-range.lab), while reverse zones are organized by IP network in reverse notation (e.g., 250.100.10.in-addr.arpa for the 10.100.250.0/24 subnet).

    3. If the zone transfer had failed, what alternative techniques could you use to enumerate DNS records?

    Reveal Answer

    When AXFR is blocked, you can enumerate DNS records through brute-force subdomain enumeration using wordlists (tools like dnsrecon, dnsenum, or fierce automate the process). You can also query for known AD SRV record patterns (_ldap._tcp, _kerberos._tcp, _gc._tcp) to discover DCs and services. Reverse DNS sweeps across known IP ranges (covered in Exercise WS-1.3) provide another path to hostname discovery without relying on zone transfers.

    4. Why do Active Directory environments rely heavily on DNS SRV records?

    Reveal Answer

    Active Directory uses DNS SRV records to advertise the location of domain services to clients. When a workstation needs to find a Kerberos KDC, an LDAP server, or a Global Catalog server, the workstation queries DNS for the appropriate SRV record rather than relying on a hardcoded server list. SRV records enable automatic DC discovery, site-aware authentication, and failover when a DC goes offline.

    Key Takeaways

    • Zone transfers (AXFR) dump the entire contents of a DNS zone in a single query. When unrestricted, AXFR gives an attacker a complete map of the domain's DNS namespace.
    • Active Directory Integrated DNS stores zone data within the AD database itself, and zone transfers follow the same permissioning model as standard DNS; if not locked down, anyone can request a copy.
    • TXT records in DNS can hold arbitrary strings. Penetration testers check TXT records because administrators and applications store metadata, verification tokens, and configuration data there.
    • SRV records reveal the service infrastructure of the domain: which hosts serve as Kerberos KDCs, LDAP servers, and Global Catalog servers.
    • The zone transfer may have revealed a reverse lookup zone for the network. Exercise WS-1.3 will use reverse DNS lookups to map IP addresses to hostnames across an entire subnet.
