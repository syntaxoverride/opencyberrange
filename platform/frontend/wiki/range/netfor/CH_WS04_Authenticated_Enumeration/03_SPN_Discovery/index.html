    Exercise WS-4.3: Service Principal Name Discovery

    Before You Begin

    Exercises WS-4.1 and WS-4.2 demonstrated that authenticated domain users can read SMB shares and GPO templates that are invisible to anonymous connections. Service Principal Name (SPN) discovery takes authenticated enumeration in a different direction; querying Active Directory (AD) directly for accounts that run services. SPN-registered accounts are high-value targets because any authenticated user can request a Kerberos service ticket for them, and that ticket can be cracked offline to recover the account's password.

    Scenario

    You continue your assessment of the corp.ocr-range.lab domain using the guest.user credentials. The engagement lead wants you to identify all accounts with registered SPNs, document the services they provide, and assess the Kerberoasting attack surface. Service accounts frequently run with elevated privileges and use passwords that are weaker than expected because administrators set them once and rarely rotate them. Your task is to query Lightweight Directory Access Protocol (LDAP) for all SPN-bearing user accounts and analyze what you find.

    Your Objectives

    • Query the AD directory for all user accounts that have a servicePrincipalName attribute
    • Identify what services each account provides based on its SPN values
    • Understand how SPN discovery enables the Kerberoasting attack
    • Document the Kerberoasting attack surface for the domain
    • Locate and submit the flag from a service account description

    Background: Service Principal Names and Kerberoasting

    A Service Principal Name is a unique identifier that associates a service instance with a logon account in Active Directory. When a client application needs to authenticate to a service (such as a SQL Server database or a web application), Kerberos uses the SPN to locate the correct service account and issue a service ticket. SPNs follow a structured format that encodes the service type, hostname, and optional port number.

    SPN format:

    serviceclass/hostname:port

    Common SPN examples:

    SPN Service Typical Account
    MSSQLSvc/sql01.corp.ocr-range.lab:1433 Microsoft SQL Server svc-sql
    HTTP/web01.corp.ocr-range.lab Web application (IIS/HTTP) svc-web
    CIFS/fileserver.corp.ocr-range.lab SMB file sharing Machine account
    exchangeMDB/mail01.corp.ocr-range.lab Exchange mailbox service svc-exchange
    ldap/dc01.corp.ocr-range.lab LDAP directory service Machine account

    SPNs registered to machine accounts (accounts ending with $) are not useful for Kerberoasting because machine account passwords are 120+ character random strings that cannot be cracked. SPNs registered to user accounts (standard sAMAccountName entries) are the targets, because human-set passwords are typically much weaker and susceptible to offline cracking.

    The Kerberoasting Attack

    Kerberoasting exploits a fundamental design feature of Kerberos authentication. When any authenticated user requests a service ticket (TGS) for an SPN, the Key Distribution Center (KDC) encrypts part of that ticket using the service account's password hash. The user receives the ticket regardless of whether they actually have permission to access the service.

    The attack proceeds in four steps:

    graph LR
    A["Enumerate SPNs<br/>via LDAP"] --> B["Request TGS<br/>Tickets"]
    B --> C["Extract Encrypted<br/>Ticket Data"]
    C --> D["Crack Password<br/>Offline"]

    style A fill:#4a90d9,color:#fff
    style B fill:#6aaa64,color:#fff
    style C fill:#e8a735,color:#fff
    style D fill:#d9534f,color:#fff
    1. Enumerate SPNs: Query LDAP for user accounts with servicePrincipalName attributes (the focus of this exercise)
    2. Request service tickets: Ask the KDC for a TGS ticket for each SPN
    3. Extract ticket data: Pull the encrypted portion from the ticket
    4. Crack offline: Use a tool like Hashcat or John the Ripper to brute-force the service account password

    The critical security implication is that steps 2 and 3 require no special privileges; any authenticated domain user can perform them. The KDC does not check whether the requesting user has access to the service. SPN discovery (step 1) is therefore the reconnaissance phase that identifies which accounts to target.

    Why Service Accounts Are Vulnerable

    Service accounts often have characteristics that make their passwords easier to crack than regular user passwords:

    Factor Risk
    Passwords set once, rarely changed Old passwords may predate current complexity requirements
    Created by administrators, not users May use predictable patterns (e.g., ServiceName2020!)
    Password never expires flag Often set to prevent service outages from password rotation
    Elevated privileges Service accounts frequently hold admin rights on multiple servers

    A cracked service account password provides the attacker with that account's full set of permissions, which often includes local administrator access on the servers running the service.

    Tool Primer: ldapsearch for SPN Enumeration

    The ldapsearch tool can query AD for all user accounts that have an SPN registered. The key is combining an LDAP filter that matches user objects with a presence test for the servicePrincipalName attribute.

    Enumerate user accounts with SPNs

    Combine an objectClass=user filter with a presence test for servicePrincipalName to return only user accounts that have an SPN registered.

    ldapsearch -D "guest.user@corp.ocr-range.lab" -w "Guest2024#" \
  -H ldap://dc01 \
  -b "DC=corp,DC=ocr-range,DC=lab" \
  "(&(objectClass=user)(servicePrincipalName=*))" \
  sAMAccountName servicePrincipalName description

    Each result block is one Kerberoasting candidate; record the sAMAccountName, every servicePrincipalName, and any description text.

    The filter components work together to narrow the results:

    Filter Component Purpose
    (objectClass=user) Match user account objects (not groups, OUs, or containers)
    (servicePrincipalName=*) Match entries that have at least one SPN attribute
    & Boolean AND; both conditions must be true

    The requested attributes provide the information needed for attack planning:

    Attribute Purpose
    sAMAccountName The account's logon name (used in Kerberoasting tools)
    servicePrincipalName The registered SPN values (identifies which services the account runs)
    description Administrator-written notes (may reveal account purpose or credentials)

    Expected output (approximate):

    # svc-sql, Users, corp.ocr-range.lab
dn: CN=svc-sql,CN=Users,DC=corp,DC=ocr-range,DC=lab
sAMAccountName: svc-sql
servicePrincipalName: MSSQLSvc/sql01.corp.ocr-range.lab:1433
description: SQL Server service account

    Each result block shows one account that could be targeted for Kerberoasting. Multiple servicePrincipalName lines on a single entry indicate the account serves multiple hosts or ports.

    Walkthrough

    Step 1: Launch the Lab

    Open the Open Cyber Range platform in your browser and start the lab environment.

    • Navigate to Exercises, then Windows Server, then Level 4
    • Click Launch on "Service Principal Name Discovery"
    • Wait for the status to change to Running
    • Note the target IP displayed in the Active Lab View

    Step 2: Query for All SPN-Bearing User Accounts

    Query for all SPN-bearing user accounts

    Run the LDAP query that searches the entire domain for user accounts with registered SPNs.

    ldapsearch -D "guest.user@corp.ocr-range.lab" -w "Guest2024#" \
  -H ldap://dc01 \
  -b "DC=corp,DC=ocr-range,DC=lab" \
  "(&(objectClass=user)(servicePrincipalName=*))" \
  sAMAccountName servicePrincipalName description

    Examine the output carefully. Each result block represents one account that the Kerberos KDC will issue service tickets for. Note the sAMAccountName, all servicePrincipalName values, and any description text.

    Step 3: Analyze the SPN Values

    For each account returned in Step 2, break down the SPN values to understand what services are running and where. Parse the SPN format to extract the service class, hostname, and port.

    Example analysis:

    SPN Value Service Class Hostname Port
    MSSQLSvc/sql01.corp.ocr-range.lab:1433 MSSQLSvc sql01 1433
    HTTP/web01.corp.ocr-range.lab HTTP web01 (default)

    The service class tells you what application the account supports. The hostname reveals which server runs the service. The port confirms the listening port, which is useful for direct service enumeration.

    Step 4: Filter Out Machine Accounts

    Compare against machine accounts

    Machine accounts (computer objects) also have SPNs, but they are not useful for Kerberoasting. Verify that your filter targets user objects by running an unfiltered presence query and comparing the results.

    ldapsearch -D "guest.user@corp.ocr-range.lab" -w "Guest2024#" \
  -H ldap://dc01 \
  -b "DC=corp,DC=ocr-range,DC=lab" \
  "(servicePrincipalName=*)" \
  sAMAccountName servicePrincipalName objectClass

    The unfiltered query returns both user and computer accounts with SPNs. Machine accounts have objectClass: computer and their sAMAccountName ends with a $ character. Comparing the two result sets confirms that the filtered query from Step 2 correctly targets only user accounts; the ones vulnerable to Kerberoasting.

    Step 5: Check Account Descriptions

    Check account descriptions

    Service account descriptions frequently contain useful information that administrators leave as internal documentation. Query for all user accounts with SPNs and pay close attention to the description attribute.

    ldapsearch -D "guest.user@corp.ocr-range.lab" -w "Guest2024#" \
  -H ldap://dc01 \
  -b "DC=corp,DC=ocr-range,DC=lab" \
  "(&(objectClass=user)(servicePrincipalName=*))" \
  sAMAccountName description

    Administrators sometimes store password hints, creation dates, responsible teams, or operational notes in the description field. Any of this information helps profile the account for targeted password guessing or social engineering.

    Step 6: Assess the Kerberoasting Attack Surface

    Document the complete Kerberoasting attack surface based on your findings. For each SPN-bearing user account, record the account name, the services it provides, and any notes from the description field. An account running with elevated privileges or a critical service warrants higher priority in an actual Kerberoasting attack.

    Consider the following questions for each account:

    • What service does the account run? (SQL, web, file services)
    • Does the account likely have elevated privileges?
    • How old might the password be based on description or naming patterns?
    • Are multiple services registered to a single account (broader blast radius if compromised)?

    Analysis Questions

    1. Why can any authenticated domain user request a Kerberos service ticket for any SPN?

    Reveal Answer

    Kerberos was designed so that authentication happens before authorization. When a client requests a service ticket, the KDC verifies the client's identity (authentication) and issues the ticket without checking whether the client has permission to use the service (authorization). Authorization is the service's responsibility; the service checks the ticket and decides whether to grant access. The KDC's willingness to issue tickets to any authenticated user is what makes Kerberoasting possible.

    2. Why are SPNs registered to user accounts vulnerable but SPNs registered to machine accounts are not?

    Reveal Answer

    Machine account passwords are automatically generated by Windows as 120+ character random strings that change every 30 days by default. Cracking a password of that length and complexity is computationally infeasible with current hardware. User account passwords, by contrast, are set by humans (typically administrators) and are subject to human password-selection habits; shorter, less random, and often unchanged for years. The difference in password strength makes user-account SPNs practical targets for offline cracking.

    3. How does SPN discovery fit into a broader attack chain against Active Directory?

    Reveal Answer

    SPN discovery is a reconnaissance step that identifies Kerberoasting targets. If the attacker cracks a service account password, they gain that account's permissions; often local administrator access on one or more servers. From there, the attacker can move laterally to other systems, extract additional credentials from memory, and work toward domain administrator access. SPN discovery turns a low-privilege domain account into a path toward high-privilege compromise without exploiting any software vulnerability.

    4. What defenses can an organization implement to reduce Kerberoasting risk?

    Reveal Answer

    Organizations can defend against Kerberoasting through several measures: use long (25+ character) random passwords for all service accounts, use Group Managed Service Accounts (gMSAs) that rotate passwords automatically, monitor for anomalous TGS ticket requests (a spike in SPN ticket requests from a single user is suspicious), implement the "Protected Users" group for sensitive accounts, and audit SPN registrations to remove unnecessary entries. Reducing the number of user accounts with SPNs directly shrinks the attack surface.

    Key Takeaways

    • Any authenticated domain user can query LDAP for all accounts with registered SPNs
    • SPNs registered to user accounts (not machine accounts) are targets for Kerberoasting
    • Kerberoasting allows offline password cracking of service account credentials without triggering account lockout
    • Service account descriptions may contain operational details that help profile the account
    • The LDAP filter (&(objectClass=user)(servicePrincipalName=*)) isolates user accounts with SPNs
    • SPN discovery requires no special tools or privileges; standard ldapsearch is sufficient
    • Exercise WS-4.4 examines another category of AD information accessible to authenticated users: object permissions and DACLs
