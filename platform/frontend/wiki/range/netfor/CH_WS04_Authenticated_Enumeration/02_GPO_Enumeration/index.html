    Exercise WS-4.2: Group Policy Object Enumeration

    Before You Begin

    Exercise WS-4.1 demonstrated that authenticated domain users can access shares hidden from anonymous connections. One of those shares; SYSVOL; is especially valuable because it stores Group Policy Object (GPO) templates that define security settings, software deployment rules, and logon scripts for the entire domain. Any authenticated user can read SYSVOL by design, making GPO enumeration a standard post-compromise reconnaissance technique.

    Scenario

    You have authenticated SMB access to dc01 using the guest.user account. The engagement lead has asked you to examine the domain's Group Policy infrastructure for sensitive information. GPOs may contain password policies, drive mapping configurations, scheduled task definitions, startup scripts, and occasionally hardcoded credentials. Your task is to navigate the SYSVOL share, identify GPO folders, and use Lightweight Directory Access Protocol (LDAP) queries to extract GPO metadata including names and descriptions.

    Your Objectives

    • Access the SYSVOL share on dc01 using authenticated credentials
    • Navigate the GPO folder structure within SYSVOL
    • Identify individual GPO folders by their Globally Unique Identifier (GUID) names
    • Read GPO settings files and scripts stored in the GPO template directories
    • Use LDAP to query GPO metadata (display names, descriptions) from Active Directory (AD)
    • Locate and submit the flag hidden in a GPO description

    Background: Group Policy Objects and SYSVOL

    Group Policy is the primary configuration management system in Windows Active Directory environments. Administrators create GPOs that define settings for users and computers; password complexity requirements, firewall rules, software installation packages, logon scripts, drive mappings, and hundreds of other configuration options. GPOs are linked to Organizational Units (OUs), sites, or the domain itself, and they apply automatically to all objects within their scope.

    Every GPO consists of two parts stored in different locations:

    Component Location Contains
    Group Policy Container (GPC) Active Directory (LDAP) GPO metadata: name, description, version, link information
    Group Policy Template (GPT) SYSVOL share on domain controllers GPO files: scripts, settings, registry policies, software packages

    The SYSVOL share is replicated across all domain controllers to ensure every DC has an identical copy of the policy templates. The share path follows a standard structure:

    \\dc01\SYSVOL\corp.ocr-range.lab\Policies\{GPO-GUID}\

    Each GPO folder is named with the GPO's GUID; a long hexadecimal identifier enclosed in curly braces. Inside each GPO folder, you find a Machine directory (computer settings) and a User directory (user settings), along with a GPT.INI file that tracks the GPO version number.

    The security-sensitive files within GPO templates include:

    Path Contains
    Machine\Scripts\Startup\ Scripts that run when computers boot
    User\Scripts\Logon\ Scripts that run when users log on
    Machine\Preferences\Groups\Groups.xml Local group membership changes (may contain passwords)
    Machine\Preferences\ScheduledTasks\ Scheduled task definitions
    Machine\Preferences\Services\ Service configuration changes
    Machine\Preferences\DataSources\ ODBC data source configurations (may contain credentials)

    Historically, Microsoft's Group Policy Preferences (GPP) stored encrypted passwords in XML files within SYSVOL. The encryption key was published by Microsoft, making those passwords trivially recoverable. Microsoft patched the ability to set new GPP passwords in MS14-025, but legacy passwords from before the patch may still exist in SYSVOL.

    Tool Primer: smbclient for SYSVOL Navigation and ldapsearch for GPO Metadata

    Two tools work together for thorough GPO enumeration. The smbclient tool provides file-level access to the SYSVOL share, while ldapsearch queries Active Directory for GPO metadata that maps GUID folder names to human-readable policy names.

    List the SYSVOL share root

    Authenticate to SYSVOL with the guest.user credentials and list the top-level contents in one non-interactive command.

    smbclient //dc01/SYSVOL -U 'guest.user%Guest2024#' -c 'ls'

    A successful listing confirms your account can read SYSVOL and shows the domain-named folder at the root.

    Navigate into subdirectories

    Chain cd and ls inside the -c argument to drill into the Policies directory without opening an interactive session.

    smbclient //dc01/SYSVOL -U 'guest.user%Guest2024#' \
  -c 'cd corp.ocr-range.lab\Policies; ls'

    The result lists one folder per GPO, each named with a GUID.

    Read a file from SYSVOL

    Use the get command with - as the destination to print a file directly to your terminal instead of saving it to disk.

    smbclient //dc01/SYSVOL -U 'guest.user%Guest2024#' \
  -c 'cd corp.ocr-range.lab\Policies\{GPO-GUID}; get GPT.INI -'

    The file contents stream to stdout so you can inspect scripts and settings inline.

    Query GPO metadata via LDAP

    Run an LDAP query against the Policies container to map each GPO GUID to its human-readable display name and description.

    ldapsearch -D "guest.user@corp.ocr-range.lab" -w "Guest2024#" \
  -H ldap://dc01 \
  -b "CN=Policies,CN=System,DC=corp,DC=ocr-range,DC=lab" \
  "(objectClass=groupPolicyContainer)" \
  displayName description

    Each returned entry pairs a GUID with a display name, letting you prioritize which GPO folders to inspect.

    The LDAP query targets the CN=Policies,CN=System container, which holds all Group Policy Container objects. The filter (objectClass=groupPolicyContainer) matches GPO entries. The attributes displayName and description provide the human-readable name and any description the administrator set for each GPO.

    Parameter Purpose
    -D "guest.user@corp.ocr-range.lab" Bind DN; authenticate as guest.user using UPN format
    -w "Guest2024#" Password for the bind account
    -H ldap://dc01 LDAP server URI
    -b "CN=Policies,CN=System,..." Search base; the Policies container in AD
    "(objectClass=groupPolicyContainer)" Filter for GPO objects only
    displayName description Return only these attributes

    Walkthrough

    Step 1: Launch the Lab

    Open the Open Cyber Range platform in your browser and start the lab environment.

    • Navigate to Exercises, then Windows Server, then Level 4
    • Click Launch on "Group Policy Object Enumeration"
    • Wait for the status to change to Running
    • Note the target IP displayed in the Active Lab View

    Step 2: Access the SYSVOL Share

    Connect to the SYSVOL share

    Connect to the SYSVOL share on dc01 and list its top-level contents.

    smbclient //dc01/SYSVOL -U 'guest.user%Guest2024#' -c 'ls'

    The top-level directory should contain a folder named after the domain (corp.ocr-range.lab). SYSVOL follows a rigid structure that is consistent across all Windows AD environments.

    Step 3: Navigate to the Policies Directory

    Navigate to the Policies directory

    Drill into the domain folder and then into the Policies subdirectory.

    smbclient //dc01/SYSVOL -U 'guest.user%Guest2024#' \
  -c 'cd corp.ocr-range.lab\Policies; ls'

    The Policies directory contains one subdirectory for each GPO in the domain. Each subdirectory is named with a GUID in curly braces (e.g., {31B2F340-016D-11D2-945F-00C04FB984F9}). Two GUIDs are present on every domain by default:

    GUID GPO Name
    {31B2F340-016D-11D2-945F-00C04FB984F9} Default Domain Policy
    {6AC1786C-016F-11D2-945F-00C04FB984F9} Default Domain Controllers Policy

    Any additional GUIDs represent custom GPOs created by the domain administrators. Record all GUIDs you find.

    Step 4: Explore a GPO Template Directory

    Explore a GPO template directory

    Pick one of the GPO GUIDs from the listing and examine its internal structure.

    smbclient //dc01/SYSVOL -U 'guest.user%Guest2024#' \
  -c 'cd corp.ocr-range.lab\Policies\{31B2F340-016D-11D2-945F-00C04FB984F9}; ls'

    The standard GPO template structure contains Machine and User directories along with a GPT.INI file. Explore both the Machine and User directories to look for scripts, preferences, and configuration files.

    Step 5: Read GPT.INI Files

    Read GPT.INI files

    The GPT.INI file inside each GPO folder tracks the GPO version. Reading it confirms the GPO is active and tells you how many times the policy has been modified.

    smbclient //dc01/SYSVOL -U 'guest.user%Guest2024#' \
  -c 'cd corp.ocr-range.lab\Policies\{31B2F340-016D-11D2-945F-00C04FB984F9}; get GPT.INI -'

    A GPT.INI file with a version number greater than zero indicates the GPO has been configured with custom settings. A version of zero means the GPO exists but has no custom configuration applied.

    Step 6: Search for Scripts and Preferences

    Search for scripts and preferences

    Check the Machine and User script directories within each GPO for startup, shutdown, logon, and logoff scripts. Run the Machine listing first, then the User listing.

    smbclient //dc01/SYSVOL -U 'guest.user%Guest2024#' \
  -c 'cd corp.ocr-range.lab\Policies\{31B2F340-016D-11D2-945F-00C04FB984F9}\Machine\Scripts; ls'

    smbclient //dc01/SYSVOL -U 'guest.user%Guest2024#' \
  -c 'cd corp.ocr-range.lab\Policies\{31B2F340-016D-11D2-945F-00C04FB984F9}\User\Scripts; ls'

    Look for .bat, .ps1, .vbs, or .cmd files in the script directories. Read any scripts you find; they may contain server names, file paths, credentials, or other operationally sensitive information.

    Step 7: Map GUIDs to GPO Names via LDAP

    Map GUIDs to GPO names via LDAP

    The GUID folder names in SYSVOL are not human-readable. Use an LDAP query to retrieve the display names and descriptions of all GPOs in the domain.

    ldapsearch -D "guest.user@corp.ocr-range.lab" -w "Guest2024#" \
  -H ldap://dc01 \
  -b "CN=Policies,CN=System,DC=corp,DC=ocr-range,DC=lab" \
  "(objectClass=groupPolicyContainer)" \
  displayName description

    The output maps each GPO's Distinguished Name (DN); which contains the GUID; to its displayName attribute. Cross-reference the GUIDs from your SYSVOL listing with the display names from the LDAP query to identify which policy is stored in which folder. Expected output (approximate):

    # {31B2F340-016D-11D2-945F-00C04FB984F9}, Policies, System, corp.ocr-range.lab
dn: CN={31B2F340-016D-11D2-945F-00C04FB984F9},CN=Policies,CN=System,DC=corp,DC=ocr-range,DC=lab
displayName: Default Domain Policy

# {6AC1786C-016F-11D2-945F-00C04FB984F9}, Policies, System, corp.ocr-range.lab
dn: CN={6AC1786C-016F-11D2-945F-00C04FB984F9},CN=Policies,CN=System,DC=corp,DC=ocr-range,DC=lab
displayName: Default Domain Controllers Policy

    Review the description field on each GPO entry. Administrators sometimes store notes, configuration details, or other metadata in the description attribute.

    The flag for this exercise is embedded in the description attribute of a GPO object in Active Directory. Run the LDAP query from Step 7 and examine the description field on each GPO entry.     Analysis Questions

    1. Why is SYSVOL readable by all authenticated domain users?

    Reveal Answer

    Domain-joined computers must read GPO templates from SYSVOL to apply Group Policy settings during startup and logon. If SYSVOL were restricted, machines could not apply security policies, software deployment rules, or logon scripts. Microsoft designed SYSVOL with broad read access as a functional requirement. Attackers benefit from the same access that machines need for normal operations.

    2. What types of sensitive information might a penetration tester find inside GPO template directories?

    Reveal Answer

    GPO templates can contain logon/startup scripts with hardcoded credentials, Group Policy Preferences XML files with encrypted passwords (decryptable using the published Microsoft key), scheduled task definitions revealing service accounts, registry policy files showing security configurations, and drive mapping settings exposing internal file server names and share paths. Any of these can provide footholds for deeper compromise.

    3. Why is mapping GUIDs to display names an important step in GPO enumeration?

    Reveal Answer

    SYSVOL stores GPO templates in folders named by GUIDs, which are meaningless without context. Mapping GUIDs to display names lets you prioritize which GPOs to examine. A GPO named "Deploy SQL Credentials" warrants immediate inspection, while "Desktop Wallpaper Policy" is low priority. The LDAP query provides this mapping and may also reveal sensitive information in the description field, as demonstrated by the flag in this exercise.

    4. What was the MS14-025 vulnerability, and why might it still be relevant today?

    Reveal Answer

    MS14-025 addressed a design flaw in Group Policy Preferences where administrators could set local account passwords through GPP. The passwords were stored in XML files in SYSVOL, encrypted with a symmetric AES key that Microsoft published in MSDN documentation. Any authenticated user could read these files and decrypt the passwords. Microsoft's patch prevented creation of new GPP passwords but did not remove existing ones. Organizations that used GPP passwords before the patch may still have decryptable credentials sitting in their SYSVOL share, accessible to any domain user.

    Key Takeaways

    • SYSVOL is a domain controller share readable by all authenticated domain users by design
    • GPO templates stored in SYSVOL may contain scripts, credentials, and configuration details
    • GPO folders are named by GUIDs that require an LDAP query to map to human-readable names
    • The groupPolicyContainer LDAP object class stores GPO metadata including names and descriptions
    • Combining SMB file access with LDAP metadata queries provides a complete picture of domain Group Policy
    • GPO enumeration feeds directly into later attack stages: credential harvesting, privilege escalation, and lateral movement
    • Exercise WS-4.3 shifts focus to Service Principal Names, another category of AD information accessible to any authenticated user
