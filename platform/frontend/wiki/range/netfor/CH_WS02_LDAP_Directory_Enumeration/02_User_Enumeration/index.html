    Exercise WS-2.2: Domain User Enumeration

    Before You Begin

    Exercise WS-2.1 mapped the Organizational Unit structure of the corp.ocr-range.lab domain, revealing which departments and divisions exist in the directory. Exercise WS-2.2 builds on that map by enumerating the user accounts that populate those OUs. You will need the same ldapsearch setup; a Kali Linux machine with VPN access and anonymous LDAP connectivity to dc01.

    Prerequisites

    • Exercise WS-2.1 completed (OU structure mapped)
    • VPN active and dc01 reachable
    • ldapsearch available (ldap-utils package)
    • Your OU hierarchy notes from Exercise WS-2.1

    Scenario

    With the OU structure mapped, your next objective is to enumerate user accounts across the domain. Active Directory (AD) stores detailed information about every user; display names, descriptions, group memberships, and freeform info fields. Enumerating these accounts reveals who works in which department, which accounts have administrative roles, and whether any accounts carry sensitive notes that administrators left in public-facing attributes.

    Your Objectives

    • List all user accounts in the domain using an LDAP search filter
    • Identify key attributes for each account: sAMAccountName, displayName, description, info, and memberOf
    • Distinguish between regular user accounts, service accounts, and administrative accounts based on naming conventions and group membership
    • Locate the lab flag hidden in a user's info attribute field

    Background: User Objects in Active Directory

    Every person, service, or application that authenticates to an AD domain has a user object stored in the directory. User objects belong to the user objectClass and carry dozens of attributes that describe the account. Some attributes; like sAMAccountName (the pre-Windows 2000 logon name) and userPrincipalName: are required for authentication. Others; like displayName, description, title, and info: are optional metadata fields that administrators and HR provisioning systems populate during account creation.

    From a reconnaissance perspective, user objects are among the most valuable targets in the directory. The sAMAccountName gives you a valid logon name you can test against authentication services. The memberOf attribute lists every group the user belongs to, immediately flagging accounts with elevated privileges. The description and info fields are freeform text that administrators sometimes use to store temporary passwords, account purpose notes, or system references that were never meant for external eyes.

    Service accounts deserve special attention during enumeration. Organizations often create dedicated user objects for applications and automated tasks; names like svc_backup, sql_service, or app_monitor are common patterns. Service accounts frequently hold elevated privileges and may have weaker password policies or passwords that rarely change, making them prime targets in later attack phases.

    Tool Primer: ldapsearch for User Enumeration

    The command below queries every user object in the domain and returns the five most informative attributes for reconnaissance.

    ldapsearch -x -H ldap://dc01 -b "DC=corp,DC=ocr-range,DC=lab" "(objectClass=user)" sAMAccountName displayName description info memberOf

    The filter (objectClass=user) matches all user objects. Note that in AD, computer accounts also inherit from the user class, but they are more specifically classified under computer. The query may return a small number of built-in system accounts (like krbtgt) alongside the regular user accounts.

    A typical user entry in the output looks like the following.

    # jsmith, Users, corp.ocr-range.lab
dn: CN=John Smith,OU=HR,DC=corp,DC=ocr-range,DC=lab
sAMAccountName: jsmith
displayName: John Smith
description: HR department analyst
memberOf: CN=HR-Staff,OU=Groups,DC=corp,DC=ocr-range,DC=lab

    Attributes that have no value; for example, an empty info field; are omitted from the output. When you spot an attribute that most users lack but one user has, pay close attention to its contents.

    Attribute What It Reveals
    sAMAccountName Logon username; usable for authentication attempts
    displayName Full name; helps identify the person behind the account
    description Admin-written notes; may contain passwords or sensitive info
    info Freeform text field; rarely audited, sometimes misused for notes
    memberOf Group memberships; reveals privilege level at a glance

    Walkthrough

    Step 1: Run the User Enumeration Query

    Enumerate all domain user accounts

    Execute the full user enumeration command against dc01. The output will contain one block per user object, separated by blank lines.

    ldapsearch -x -H ldap://dc01 -b "DC=corp,DC=ocr-range,DC=lab" "(objectClass=user)" sAMAccountName displayName description info memberOf

    The result set may be large. Pipe the output to a file so you can search and sort it without losing data to terminal scrollback limits.

    ldapsearch -x -H ldap://dc01 -b "DC=corp,DC=ocr-range,DC=lab" "(objectClass=user)" sAMAccountName displayName description info memberOf > /tmp/users.ldif

    Step 2: Count the User Accounts

    Count the user accounts

    Check the summary line at the end of the output to see how many user entries the query returned. You can also count entries in the saved file.

    grep -c "^dn:" /tmp/users.ldif

    Record the total number of user accounts. Compare this number against what you would expect for an organization with the OU structure you mapped in Exercise WS-2.1.

    Step 3: Identify Account Types

    Review the saved output and categorize each account into one of three types based on naming conventions and attributes.

    Regular user accounts typically have names that follow a firstname.lastname or flastname pattern, carry a displayName matching a person's real name, and belong to departmental groups.

    Service accounts often start with a prefix like svc_, svc-, app_, or sql_. Their description fields usually state the service or application they support. Service accounts may belong to privileged groups that grant access to specific resources.

    Administrative accounts may follow patterns like admin_jsmith or belong to groups such as Domain Admins, Administrators, or custom admin groups. The memberOf attribute is the fastest way to spot these.

    Create a table in your notes with columns for username, account type, and notable attributes.

    Step 4: Examine the memberOf Attribute

    The memberOf attribute lists the Distinguished Names of every group the user belongs to. Scan the output for users who are members of high-privilege groups. Look for group names containing keywords like "Admin", "Domain Admins", "Enterprise Admins", "Administrators", or custom elevated groups discovered during OU enumeration.

    Find users in administrative groups

    The next filter pulls every user whose memberOf value references an Admin group.

    grep -B5 "memberOf.*Admin" /tmp/users.ldif

    The -B5 flag shows the five lines before each match, which should include the user's sAMAccountName and displayName. Record every user that appears in an administrative group.

    Step 5: Search the description and info Fields

    Search description and info fields

    The description and info attributes are freeform text fields that warrant careful inspection. Search the saved output for any description or info lines that contain interesting data.

    grep -i "^description:\|^info:" /tmp/users.ldif

    Most entries will have brief, routine descriptions. Focus on entries that stand out; passwords, flags, internal references, or anything that looks like it was not intended for public consumption. The flag for this exercise is stored in the info attribute of a user account in the IT department.

    Step 6: Narrow the Search to IT Department Users

    Narrow the search to IT department users

    Using the OU structure from Exercise WS-2.1, you know which OU holds IT department accounts. Run a targeted query with a narrower search base to isolate IT users and their info fields.

    ldapsearch -x -H ldap://dc01 -b "OU=IT,DC=corp,DC=ocr-range,DC=lab" "(objectClass=user)" sAMAccountName displayName info

    Review the output for any user whose info attribute contains the flag. The info field is rarely populated, so any entry that has a value is worth examining.

    Step 7: Extract a Complete User List

    Extract a complete username list

    For reference in later exercises, generate a clean list of all sAMAccountName values in the domain. The following command extracts usernames and sorts them alphabetically.

    grep "^sAMAccountName:" /tmp/users.ldif | awk '{print $2}' | sort

    Save the sorted list to a file for future use.

    grep "^sAMAccountName:" /tmp/users.ldif | awk '{print $2}' | sort > /tmp/usernames.txt

    The username list will be valuable for credential-testing and password-spraying exercises in later chapters.

    Users in administrative groups:

    Username Field Value

    Step 8: Interpret the Results

    Review your account classification table and group membership findings. Consider what the user inventory reveals about the organization. A large number of users in administrative groups may indicate poor privilege separation. Service accounts with broad group memberships may represent overly permissive configurations. Users with notes in description or info fields highlight a pattern of storing sensitive data in publicly readable attributes.

    Cross-reference the user locations (the OU portion of each DN) with the OU hierarchy from Exercise WS-2.1. Confirm that users appear in the OUs you would expect based on their department and role.

    Step 9: Find and Submit the Flag

    The flag for this exercise is stored in the info attribute of a user account located in the IT department OU. If you followed Steps 5 and 6, you should have already identified the entry. The flag follows the standard OCR{...} format. Copy it exactly as it appears in the LDAP output.

    Analysis Questions

    1. Why is the info attribute particularly risky from a security standpoint?

    Reveal Answer

    The info attribute is a freeform text field with no enforced structure or validation. Administrators and help-desk staff sometimes use it to store temporary notes, including passwords or sensitive references. Because the field is rarely audited and is readable by anyone with LDAP access, sensitive data stored there can persist indefinitely without detection.

    2. What distinguishes a service account from a regular user account in Active Directory, and why do attackers target service accounts?

    Reveal Answer

    Service accounts are user objects created to run applications or automated tasks rather than to represent a person. They are often identifiable by naming conventions (prefixes like svc_) and by their group memberships. Attackers target service accounts because they frequently hold elevated privileges, may have passwords that rarely rotate, and are less likely to trigger suspicious-logon alerts than interactive user accounts.

    3. How could an administrator reduce the information exposed by anonymous LDAP user enumeration?

    Reveal Answer

    The most effective measure is to disable anonymous LDAP binds entirely, requiring authentication before any query can return results. Administrators can also apply granular access-control entries to sensitive attributes (like description and info) so that only authorized principals can read them. Removing unnecessary data from user attributes during provisioning further limits exposure.

    4. You saved the user list to /tmp/usernames.txt. How might an attacker use that list in a later phase?

    Reveal Answer

    A list of valid usernames enables password-spraying attacks, where the attacker tries a small number of common passwords against every account. Valid usernames also support Kerberos-based attacks like AS-REP roasting (targeting accounts that do not require pre-authentication). Having confirmed usernames eliminates guesswork and reduces the number of failed authentication attempts, helping the attacker stay below lockout thresholds.

    Key Takeaways

    • User objects are the richest source of reconnaissance data in Active Directory; every account carries a logon name, group memberships, and optional freeform fields.
    • The sAMAccountName attribute provides valid logon names that can be used in authentication attacks during later phases.
    • Freeform attributes like description and info are frequently overlooked during security audits but are fully readable through LDAP, making them a common hiding place for sensitive data.
    • Categorizing accounts into regular, service, and administrative types helps prioritize targets and understand the organization's privilege model.
    • With users enumerated, Exercise WS-2.3 will map group memberships in detail to build a complete picture of who has access to what.
