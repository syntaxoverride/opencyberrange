    Chapter WS02: LDAP Directory Enumeration

    Why Directory Enumeration Matters

    Active Directory (AD) is the backbone of most enterprise Windows networks. Every user account, computer, group, and organizational boundary lives inside the AD directory, and the Lightweight Directory Access Protocol (LDAP) is the primary protocol applications and administrators use to query that directory. When an attacker gains even limited read access to LDAP, the directory becomes an open book; revealing the organization's structure, its privileged accounts, and the policies that govern credential security.

    In Chapter WS01 you confirmed that anonymous LDAP binds are allowed against the domain controller. That single finding unlocked the door to a wealth of reconnaissance data. Chapter WS02 walks through that door systematically, querying LDAP to extract Organizational Units (OUs), user accounts, group memberships, computer objects, and password policies. Each query builds on the last, steadily assembling a picture of the target domain that will inform every later attack path.

    Understanding directory enumeration also matters on the defensive side. Blue-team analysts who know exactly what LDAP exposes can audit permissions, restrict anonymous access, and monitor for the telltale query patterns that signal reconnaissance in progress. Whether you sit on offense or defense, mastering LDAP enumeration is a foundational skill for Windows-domain security work.

    What You Will Learn

    The five exercises in Chapter WS02 follow a deliberate progression: start with the containers that organize the directory (OUs), then enumerate the objects inside those containers (users, groups, computers), and finish by extracting the domain-wide password policy that governs credential strength. Each exercise introduces new LDAP search filters and attributes while reinforcing the core ldapsearch workflow you will use throughout the Windows Server track.

    By the end of this chapter you will be able to:

    • Query LDAP for every Organizational Unit and interpret OU attributes such as description
    • Enumerate all domain user accounts and distinguish regular users from service and administrative accounts
    • Map security-group memberships to identify users with elevated privileges
    • Discover every domain-joined computer and extract operating-system metadata
    • Retrieve the domain password policy, including minimum length, complexity, and lockout thresholds
    • Combine the results of multiple LDAP queries to build a coherent map of the target domain

    Understanding LDAP and Active Directory Structure

    LDAP is a client-server protocol designed for reading and writing directory data. In an AD environment the domain controller hosts the LDAP service (TCP port 389 for plaintext, 636 for LDAPS). Clients send search requests that specify a base DN (the starting point in the directory tree), a scope (how deep to search), a filter (which objects to match), and a list of attributes to return.

    Active Directory organizes objects in a hierarchical tree rooted at the domain's Distinguished Name (DN). For the lab domain corp.ocr-range.lab, the root DN is DC=corp,DC=ocr-range,DC=lab. Below the root sit Organizational Units: container objects that group related accounts and computers much like folders group files. Inside OUs you find leaf objects: users, groups, computers, and other directory entries. Every object has a set of attributes; key-value pairs such as sAMAccountName, description, memberOf, and operatingSystem: that store the object's metadata.

    A critical concept is the objectClass attribute. Every directory object carries one or more object classes that define which attributes the object may (or must) have. Filtering on objectClass is the primary way to select a specific type of object. For example, (objectClass=organizationalUnit) returns only OUs, while (objectClass=user) returns user accounts. Mastering these filters lets you slice the directory precisely and extract only the data you need.

    How LDAP Search Scopes Work

    Every LDAP search operates within a defined scope that controls how far below the base DN the server looks for matching objects. Three scope levels exist, and choosing the right one determines whether your query returns a single object, a shallow list, or a deep recursive result.

    The subtree scope (the default when no -s flag is specified) searches the base DN and every object beneath it at any depth. The one-level scope (-s one) returns only the immediate children of the base DN, ignoring grandchildren and deeper objects. The base scope (-s base) returns only the single object at the base DN itself, which is how Exercise WS-2.5 extracts password policy attributes stored directly on the domain object. Understanding these scopes lets you control query breadth; broad searches for discovery, narrow searches for targeted extraction.

    Key Terminology Reference

    The following terms appear throughout the chapter. Refer back to this list whenever you encounter an unfamiliar abbreviation or concept.

    Term Definition
    LDAP Lightweight Directory Access Protocol; the protocol used to query and modify directory data
    AD Active Directory; Microsoft's directory service for Windows domain networks
    DN Distinguished Name; the full path to an object in the directory tree
    RDN Relative Distinguished Name; the leftmost component of a DN, identifying the object within its parent container
    OU Organizational Unit; a container object used to group and organize directory objects
    objectClass An attribute that defines the type of a directory object and which attributes it may carry
    Base DN The starting point in the directory tree for an LDAP search
    Scope The depth of an LDAP search: base (single object), one-level (immediate children), or subtree (all descendants)
    Anonymous bind An LDAP connection that provides no credentials, relying on the server to permit unauthenticated reads
    sAMAccountName The pre-Windows 2000 logon name; the short username used for authentication
