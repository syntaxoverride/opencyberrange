    Exercise 15D: Final Exam Practice (Atlas Distribution)

    Before You Begin

    The course has covered fifteen weeks of offensive techniques. Atlas Distribution is your final exam practice. If you can clear this lab without assistance from the workbook then you are ready for the final exam. The final exam exercise will be closed book/notes.

    Your VPN must be connected and your Kali terminal open before you proceed. The lab gives you 180 minutes. Hints unlock at 60, 90, and 120 minutes; treat them as a backstop, not a shortcut. The assembled flag from this practice doubles as your engagement code for the actual final exam, so make sure you record it cleanly in your notes.

    Scenario

    Atlas Distribution is a regional logistics firm with twelve branches along the Gulf Coast and the southwest United States. Three years ago Atlas acquired a smaller competitor and inherited the Corpus Christi branch office. The branch was supposed to be folded into corporate IT but never was. The branch IT admin departed in 2025 and was never replaced. Headquarters wants a pentest to quantify the residual risk before they decommission the site.

    Briefing from Karen Vogel, Director of Corporate Security: "The Corpus Christi branch ran on its own for years. We do not have an inventory of what is on that subnet, what services are exposed, or who has credentials. Two systems are reachable from the corporate VPN: a Linux file server that the branch used for shared documents, and an internal portal that the branch IT admin built to manage tickets. Find what is exposed, demonstrate access, and document anything that would let an outsider reach our data."

    Three tokens are planted across the engagement. One is recovered through reconnaissance, one through SMB enumeration with a credential pivot, and one through web exploitation against a hidden staff portal. Each token is a short string in the form token=<value>. After collecting all three, you assemble the values into a single flag of the form OCR{________} and submit that flag to the platform.

    Your Objectives

    The list below maps to the three token locations.

    • Discover both in-scope hosts on the branch subnet and identify their services with nmap
    • Recover token 1 from an SNMP system field on the file server
    • Enumerate SMB shares anonymously, harvest credentials from a leaked handover document, and use those credentials to recover token 2 from a restricted share
    • Discover the hidden staff portal on the intranet server, exploit a SQL injection authentication bypass, and recover token 3 from the staff dashboard
    • Assemble the three tokens in order into the flag format OCR{________} and submit a single flag within the 180 minute window

    Background: The Three-Phase Pentest Pattern

    A real pentest engagement follows a predictable shape: you start by enumerating what is reachable, then look for exposed services that leak information, and finally exploit any application vulnerabilities you find. The Atlas engagement walks you through that exact pattern in three phases.

    The diagram below shows the host layout and the order you will work through the three tokens.

    graph LR
    ATK["Attacker (Kali)"] -->|"Phase 1: nmap, snmpwalk"| FS["Branch File Server<br/>SMB :445, SNMP :161"]
    ATK -->|"Phase 3: gobuster, browser"| PORTAL["Branch Intranet Portal<br/>HTTP :80"]
    FS -.->|"Phase 2: SMB enumeration"| ATK
    FS -->|"Anon share leaks creds"| LOOT["Backup share unlocked"]
    LOOT -->|"Token 2 retrieved"| ATK

    style ATK fill:#4a90d9,color:#fff
    style FS fill:#e8a735,color:#fff
    style LOOT fill:#e8a735,color:#fff
    style PORTAL fill:#d9534f,color:#fff

    Phase 1 establishes ground truth: which IPs are alive, what ports are open, and what services are running. Phase 2 walks the SMB share tree, recovers credentials from the public share, and uses those credentials to reach the restricted share. Phase 3 enumerates the web application, finds the hidden login path, and bypasses authentication with a SQL injection payload.

    The order matters. SMB enumeration depends on nmap confirming SMB is open. The credential-protected SMB share depends on reading the leaked password from the anonymous share. The staff portal exploitation depends on discovering the hidden path through directory enumeration with gobuster. Each step unlocks the next, and each phase yields exactly one token.

    Tool Primer: Five Tools You Already Know

    Every tool used in this lab has appeared in a previous week. The primer below is a quick reference rather than an introduction.

    Tool Phase Purpose
    nmap Recon TCP/UDP port discovery and service version detection across the subnet
    snmpwalk Recon Read system MIB fields from the file server using the default public community string
    smbclient SMB List shares, read files anonymously, and authenticate to restricted shares
    gobuster Web Brute-force directory and file names against the portal to discover the hidden staff login path
    Browser Web Submit the SQL injection payload through the staff portal login form and read the recovered token directly from the rendered dashboard

    nmap (subnet sweep):

    nmap -sV -p- <subnet>/24

    The -sV flag enables service version detection. The -p- flag scans all 65,535 TCP ports rather than the default 1,000.

    snmpwalk (default community string):

    snmpwalk -v2c -c public <target_ip> system

    The -v2c flag selects SNMP version 2c. The -c public flag passes the community string. Walking the system subtree returns sysDescr, sysContact, sysName, and sysLocation; one of these holds token 1.

    smbclient (list and access):

    smbclient -L //<target_ip> -N
smbclient //<target_ip>/<share_name> -N
smbclient //<target_ip>/<share_name> -U <username>%<password>

    -L lists shares without connecting to one. -N sends a null (no password) authentication. -U user%pass provides credentials inline.

    Browser (form submission):

    Open the staff portal URL gobuster discovers in a browser tab. The login form accepts standard SQL injection payloads in the username or password field. The browser handles the POST, the 302 redirect, and the session cookie automatically; once authenticated, the dashboard renders and the recovered token is visible inside the page.

    Walkthrough

    Phase 1: Recon

    Recon establishes the ground truth for everything that follows. Skipping this phase leaves you guessing. Spending too long here also costs you on a timed exam, so move with intent.

    Step 1: Launch the Exercise and Note Both Target IPs

    Open the platform in your browser and start the exercise environment. The Atlas lab deploys two hosts; the Active Lab View shows both target IPs.

    • Navigate to Exercises and locate Exercise 15D; Final Exam Practice (Atlas Distribution)
    • Click Launch and wait for the status to change to Running
    • Note both target IPs displayed in the Active Lab View:
    • Branch File Server: SMB on TCP 139/445, SNMP on UDP 161
    • Branch Intranet Portal: HTTP on TCP 80
    • Record both IPs before proceeding; you will need each one in different phases

    Step 2: Sweep the Subnet With nmap

    Service-scan both target hosts with nmap

    The first move on any unfamiliar subnet is a TCP service scan. Even though the Active Lab View tells you which IPs are in scope, a service scan confirms the port and version data you need to plan the rest of the engagement.

    nmap -sV -p- <fs_ip> <portal_ip>

    Replace <fs_ip> and <portal_ip> with the IPs from the Active Lab View. The scan will take a couple of minutes because -p- covers all TCP ports. While it runs, you can move to the SNMP step.

    Expected ports:

    • File server: 139/tcp open netbios-ssn, 445/tcp open microsoft-ds (Samba)
    • Portal: 80/tcp open http (Werkzeug or Python httpd)

    The TCP scan will not reveal SNMP, because SNMP runs on UDP. UDP scanning takes much longer. For this lab you can skip the UDP scan because the briefing tells you SNMP is enabled; in a real engagement you would run nmap -sU -p 161 on the file server to confirm.

    Step 3: Walk SNMP to Recover Token 1

    Walk the SNMP system tree to recover token 1

    The previous IT admin enabled SNMP on the file server with the default public community string. Walking the system MIB tree reveals administrative metadata that the previous admin set during deployment, including the asset token planted in the sysContact field.

    snmpwalk -v2c -c public <fs_ip> system

    The output is a series of lines like iso.3.6.1.2.1.1.X.0 = STRING: "...". Each line corresponds to one system MIB variable. Read each STRING value in order; one of them contains a string of the form token=<value>.

    Narrow the SNMP walk to the sysContact OID

    If the system tree is too noisy, narrow your scan to a single OID.

    snmpwalk -v2c -c public <fs_ip> 1.3.6.1.2.1.1.4.0

    OID 1.3.6.1.2.1.1.4.0 is the sysContact field; token 1 is stored there as the value after token=.

    Record token 1 in your notes. You will assemble all three tokens into the final flag at the end.

    Phase 2: SMB Enumeration and Credential Pivot

    SMB enumeration is the most realistic part of this engagement. Real branch offices regularly leave file shares with anonymous read access, and real IT handover documents regularly leak credentials. Your job is to walk the share tree, read the public files, and pivot from anonymous access to credentialed access on the restricted share.

    Step 4: List SMB Shares Anonymously

    List SMB shares anonymously

    The first SMB action against any unfamiliar server is to list the shares. The list itself is administrative metadata; reading it does not require any credentials when guest access is enabled.

    smbclient -L //<fs_ip> -N

    The -L flag asks the server for its share list. The -N flag sends a null authentication. The output includes a Sharename column showing each available share.

    Expected shares:

    • branch-shared (Disk; guest accessible)
    • dispatch-backups (Disk; access restricted)
    • IPC$ (interprocess communication; ignore for this lab)

    The dispatch-backups share appears in the list, but you cannot read its contents without credentials. The credentials you need are stored on the public share.

    Step 5: Read the IT Handover Document From the Public Share

    Connect to the public share anonymously

    Connect to the branch-shared share with anonymous access and download the files inside. The previous IT admin left a handover document explaining what they were responsible for, including the password for the backup service account.

    smbclient //<fs_ip>/branch-shared -N

    Once connected you will see an smb: \> prompt.

    Download the handover files from inside the smbclient prompt

    Use SMB commands at the smb: \> prompt to list and download files.

    ls
get IT_Handover_Notes.txt
get welcome.txt
get phone_directory.txt
exit

    The get command downloads each file to your current working directory on Kali.

    Read the IT handover document on Kali

    After exiting the smbclient prompt, read the handover document on your Kali host.

    cat IT_Handover_Notes.txt

    The handover document describes both the file server and the portal. Look for a section titled FILE SERVER and read the credentials for the dispatch_svc account. The password is in plain text. The same document also describes the INTRANET PORTAL and references the hidden /staff-portal/ path; record both pieces of information now because you will need them in Phase 3.

    Expected finding: username dispatch_svc, password B4ckup_Atl4s_2024#. Record both values.

    Step 6: Use the Credentials to Recover Token 2

    Authenticate to the restricted share with the recovered credentials

    Authenticate to the dispatch-backups share using the credentials you just recovered. The share contains a quarterly status report; the document control line near the top of that report contains token 2.

    smbclient //<fs_ip>/dispatch-backups -U dispatch_svc%B4ckup_Atl4s_2024#

    The -U flag passes the username and password inline using the username%password syntax. The connection should open without prompting for a password, dropping you at the smb: \> prompt.

    Download the status report from the restricted share

    Download the status report at the smb: \> prompt.

    ls
get branch_status_report.txt
exit

    Read the status report to recover token 2

    Read the downloaded report on your Kali host.

    cat branch_status_report.txt

    Look for a line beginning Document control token=. The value after token= is token 2. Record it.

    The pivot pattern you just executed is one of the most common findings in real pentest engagements. Anonymous access on one share leaks credentials for a restricted share. The fix is not just tightening the restricted share; it is removing the credential leak from the public share or eliminating anonymous access entirely.

    Phase 3: Web Exploitation

    The branch intranet portal looks like a public-facing marketing site. The homepage, navigation, news articles, and careers page all render normally. The actual login form is hidden from the navigation; reaching it requires discovering the path through directory enumeration. Once you find the login form, the application is vulnerable to a classic SQL injection authentication bypass.

    Step 7: Discover Hidden Paths With gobuster

    Brute-force hidden portal paths with gobuster

    The portal homepage links to legitimate marketing pages but not to the staff login. To find paths the developer chose not to advertise, run a directory brute-force against the portal using a wordlist of common path names.

    gobuster dir -u http://<portal_ip>/ -w /usr/share/wordlists/dirb/common.txt

    The dir mode tells gobuster to enumerate paths (it also has DNS and vhost modes that do not apply here). The -u flag sets the target URL. The -w flag points to the wordlist; /usr/share/wordlists/dirb/common.txt ships with Kali and contains roughly 4,600 common path names. The scan takes about a minute against a small application like this one.

    Expected output (abridged):

    /admin                (Status: 302) [Size: 217]
/api                  (Status: 401) [Size: 86]
/careers              (Status: 200) [Size: ...]
/contact              (Status: 200) [Size: ...]
/login                (Status: 200) [Size: ...]
/news                 (Status: 200) [Size: ...]
/robots.txt           (Status: 200) [Size: 76]
/services             (Status: 200) [Size: ...]
/staff-portal         (Status: 308) [Size: ...]

    Read each row by its status code. 200 means the path returned content. 308 is a permanent redirect (gobuster has discovered a path that the application then redirects to a trailing-slash version). 401 means the path requires credentials. 302 is a temporary redirect, often used to send unauthenticated visitors to a login page.

    The path of interest is /staff-portal/. The 308 you see for /staff-portal indicates the application redirected gobuster to the trailing-slash version, which is where the login form lives. The handover document from Phase 2 referenced this same path, so finding it through both gobuster and the leaked notes confirms the target.

    Step 8: Browse to the Staff Portal Login Form

    Open the staff portal in a browser tab using the URL gobuster found:

    http://<portal_ip>/staff-portal/

    The page renders a username and password form that POSTs to /staff-portal/login. The form does not appear in the site navigation; the only way to reach it is by visiting the path you discovered with gobuster (or by following the reference in the handover document).

    Step 9: Bypass Authentication With SQL Injection

    The login form passes the username and password into a SQL query that uses string formatting rather than parameterized queries. Any payload that breaks out of the password string literal and adds an always-true clause causes the query to return the first row in the staff table, which the application treats as a successful login.

    Work this step in your browser:

    1. Type a username into the Username field. admin is a safe choice and any other value also works because the bypass overrides the username check.
    2. Type one of the SQL injection payloads below into the Password field.
    3. Click Sign In.

    A successful injection redirects you to /staff-portal/dashboard and the staff dashboard renders. A failed injection returns you to the login form with an error message.

    Any of the following payloads produces a successful login. Try several so you build comfort with the variants you are likely to see on real engagements.

    Payload Why it works
    ' OR '1'='1 Closes the password literal, adds an always-true OR clause
    ' OR 1=1-- Same as above with the rest of the query commented out using ANSI --
    ' OR 1=1# Same idea using the MySQL-style # comment marker
    ' OR ''=' Closes the literal, compares two empty strings (always true)
    admin'-- (in the Username field with anything in Password) Closes the username literal, comments out the rest of the WHERE clause

    Why the payloads work: the application builds the SQL query as SELECT id, username, role FROM staff WHERE username='<u>' AND password='<p>'. With ' OR '1'='1 injected as the password, the query becomes ... WHERE username='admin' AND password='' OR '1'='1'. The trailing OR '1'='1' is always true, so the query returns the first row of the staff table. The application checks only whether the query returned any row, not which row, so it considers the login successful and sets a session cookie. The other payload variations all reach the same outcome through different syntax.

    Step 10: Recover Token 3 From the Dashboard

    After a successful injection, the browser lands on the staff dashboard. Read the System Status table near the top of the page and find the row labeled Asset Token. The right-hand cell contains a value formatted as token=<value>.

    Record the value as token 3. There is no command-line step here; the dashboard renders the token directly in the page so you can copy it from the browser into your notes.

    Assemble and Submit the Flag

    You have collected three tokens. The platform expects one composite flag built from those three values, in order, separated by underscores.

    The format is:

    OCR{________}

    Substitute the values you recovered. For example, if token 1 is aaaa, token 2 is bbbb, and token 3 is cccc, the assembled flag would be OCR{aaaa_bbbb_cccc}.

    • Open the Active Lab View for Exercise 15D
    • Locate the Submit Flag input
    • Paste the assembled OCR{...} string into the input
    • Click Submit

    The platform will record completion and award course credit. Save the assembled flag value in your notes; it is also your engagement code for the actual final exam in the next session.

    Flag Format

    The flag is OCR{________}. The platform validates the exact string. If submission fails, double-check that you assembled the tokens in the correct order (recon, SMB, web), used underscores between values, and wrapped the whole thing in OCR{...}. No spaces, no dashes, no quotes.

    Analysis Questions

    Work through each question before revealing the answer. The questions reinforce the methodology you just executed.

    1. Token 1 was stored in an SNMP MIB field. Why is leaving the default public community string enabled a meaningful finding even though SNMP is read-only?

    Reveal Answer

    The default public community string allows anyone with network reachability to read every SNMP MIB variable on the device. Even when read-only, the data exposed includes hostname, system location, system contact, OS version, running processes (depending on the agent configuration), network interfaces, and routing tables. Attackers use this to fingerprint the host, identify high-value targets, and discover the names and roles of administrators (whose contact information is usually in the sysContact field). The fact that an asset token (token 1 in this lab) was stored in the sysContact field demonstrates how administrators frequently use SNMP fields to record sensitive metadata, which is then exposed to anyone who can reach UDP port 161 with the default community string.

    2. The SMB chain depended on credentials being readable from an anonymous share. If the IT handover document had been stored in the restricted dispatch-backups share instead, would the engagement have stalled? Why or why not?

    Reveal Answer

    The engagement would have stalled at the SMB phase, because there would be no path from anonymous access to credentialed access. The structural lesson is that the security boundary on a file server is the share with the lowest access requirement, not the share with the most sensitive data. Putting credentials on a public share creates a path-of-least-resistance pivot. In a real environment, the appropriate fix is to remove credentials from anonymous shares entirely (rotate the password and store it only in a secrets manager), not to merely tighten the permissions on the share that holds the sensitive content.

    3. The SQL injection payload anything' OR '1'='1 worked because the application concatenated user input into the SQL string. Name two specific defenses that would have prevented the bypass and explain how each one works.

    Reveal Answer

    Two defenses, each addressing a different layer:

    1. Parameterized queries (prepared statements). The application would pass the username and password as bound parameters rather than embedding them in the SQL string. The database treats parameters as literal values, so ' OR '1'='1 becomes part of the password string the application is checking, not part of the SQL syntax. The query returns no rows because no user has that literal password. Parameterization is the structural fix; it eliminates the vulnerability at the database driver layer.

    2. Server-side validation of authentication results. Even if the SQL query is vulnerable, the application should not consider login successful merely because a row was returned. A correct implementation would compare the returned password hash to a hashed version of the user-supplied password, rather than checking whether the WHERE clause matched at least one row. Result validation is a defense-in-depth measure; it limits the impact of a bug in the SQL query construction.

    A third common defense, input filtering (escaping or rejecting quotes), is not a strong fix on its own. Filters can be bypassed with encoding, alternate quote characters, or comment syntax, and they do not address the structural problem of mixing data and code in the query string.

    4. The lab uses three tokens assembled into one flag rather than three separate flag submissions. From an operator perspective, why does the assembly step matter?

    Reveal Answer

    Assembly enforces that you keep notes on every phase of the engagement and present a single deliverable at the end. In a real pentest, the deliverable is a written report that ties findings together, not a series of unrelated tokens. The assembly step here is a small simulation of that workflow; you must write down what you found at each stage, in order, and combine them into a coherent submission. A student who treats each phase in isolation and forgets to record an intermediate token cannot produce the final flag, even if they technically completed all three phases. The discipline of writing down each finding as you go is the same discipline that produces good pentest reports.
