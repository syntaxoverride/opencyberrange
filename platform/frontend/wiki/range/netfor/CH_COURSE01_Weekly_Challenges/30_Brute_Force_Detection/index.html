    Challenge 14B: Brute Force Detection and Response

    Before You Begin

    Challenge 14 taught you how to write Suricata rules against two classic web attacks (SQL injection and command injection) where each attack fires on a single packet. Challenge 14B widens the lens to a credential-stuffing campaign: the same attacker, sending hundreds of login attempts in a row, mostly failures with one success buried in the flood. Your detection task is to catch the bulk pattern, catch the successful one, and extract the IOCs (Indicators of Compromise) the attacker tool left behind.

    Your VPN must be connected and your terminal ready. You should be comfortable with SSH, basic Linux navigation, and the Suricata rule-writing workflow from Challenge 14. If you have not completed Challenge 14 yet, do that first; the syntax background is assumed here.

    Scenario

    Aegis Security Corp, a managed security services provider headquartered in Denver, Colorado, has observed a sustained brute-force attack against their client-facing authentication portal. The Security Operations Center detected a high volume of HTTP POST requests to the login endpoint originating from a single source, with hundreds of different username and password combinations attempted over a short period. Worse, their access logs show one entry where the POST got a 200 OK back; the attacker appears to have guessed a valid credential.

    You are an analyst on the incident response team. Your team lead, Sarah Nguyen (Principal Threat Analyst), sent you this message:

    "We have an active credential stuffing campaign hitting our auth gateway. The IDS sensor is deployed inline but has no custom rules, so it's not catching anything. I need you to write Suricata detection rules for the brute-force POST traffic, find the campaign identifier the attacker is using (they embed tracking tags in their payloads), and check the web portal logs. I suspect the same actor is hitting that too with a custom tool. Pull every IOC you can find. Brief me by end of shift."

    Your toolkit includes SSH access to the Aegis IDS sensor (Suricata and tcpdump) and the corporate web portal (nginx). The brute-force attack is ongoing; new login attempts arrive every few seconds.

    Credentials

    • IDS Sensor SSH: analyst / A3g1s_S0C_2024#
    • Web Portal SSH: webadmin / A3g1s_Adm1n#

    Why this matters

    Credential stuffing is the single most common attack against public-facing auth endpoints today, and the attacker's economics are in their favor: password reuse means a list of millions of stolen credentials from one breach yields thousands of valid logins somewhere else. Detecting the volume signature early is what separates a contained incident from a breach disclosure call to Aegis's entire client base.

    • Aegis's clients include financial and healthcare firms. Every valid credential the attacker finds risks a downstream incident at a customer, escalating contractually to breach notification under SLAs and regulatory scope (GLBA, HIPAA).
    • Sarah has to brief the CEO in the morning on whether the SOC caught the attack or whether customers saw it first. Rule evidence with timestamps is the artifact she needs; a vague "we saw something" is not enough.
    • The rate limiting on the auth gateway is an application-layer control; the IDS is your layer-7 visibility for traffic that never reaches the application. Without the rule, the attacker can iterate for hours before anyone notices.
    • Campaign identifiers embedded by the attacker tool are forensic gold: they let the SOC pivot across time to find every prior attempt from the same campaign, and they support threat-intel sharing with peer SOCs.

    Background: Brute Force and Credential Stuffing

    A brute-force login attack tries many username and password combinations against an authentication endpoint until one succeeds. A credential-stuffing attack is a narrower form: instead of guessing passwords, the attacker reuses known-valid (username, password) pairs stolen from other breaches, relying on password reuse across sites. The network signature is similar; the defender's detection task is the same.

    Three properties of brute-force traffic make it detectable even when each individual request looks valid:

    1. Volume: hundreds of POST requests to the same endpoint in a short window
    2. Shape: each request carries a password (or similar) field in the body
    3. Repetition: the attacker's tool uses the same User-Agent, the same Content-Type, and often the same request structure across every attempt

    Detection can hit any of these properties. A threshold rule counts requests per source; a content rule matches the shape of the POST; a User-Agent rule flags the attacker's tool directly. For Challenge 14B you will write two content rules that fire on every POST body carrying a password field, and a tighter one that fires on the one POST body carrying a specific campaign tracking tag the attacker embedded.

    Tool Primer: Suricata Rule Options for POST Traffic

    Suricata's rule syntax was covered in Challenge 14; this primer extends it to the POST-specific options you need for brute-force detection.

    Matching HTTP methods

    The content:"POST"; http_method; pair tells Suricata to match the literal string POST against the parsed HTTP method field, not against the raw packet bytes. Using the parsed field avoids a false positive on any random request whose body happens to contain the characters POST (for example a POST request describing a blog post).

    Matching POST bodies

    The http_client_body modifier, applied to a content: keyword, tells Suricata to match only inside the client-sent request body. For a login POST the body looks like:

    username=alice&password=Winter2024&campaign=brut3&exfil=d3t3ct

    A rule with content:"password"; http_client_body; fires when the word password appears in that body. It does not fire when password appears in a response body from the server, or in an HTTP header, or in the URL.

    Flow direction

    The flow:to_server,established; keyword pair restricts matching to packets traveling from the client toward the server on an already-established TCP connection. For brute-force detection you never want to match server-to-client traffic (responses), so always include the flow keyword on POST-inspection rules. It also cuts processing cost by skipping packets that cannot be attacks.

    The full rule shape

    Putting the pieces together:

    alert http any any -> any any (
    msg:"Brute Force Login Attempt";
    flow:to_server,established;
    content:"POST"; http_method;
    content:"password"; http_client_body;
    sid:1000001; rev:1;
)

    In plain English: alert on HTTP traffic in either direction (address-wise), arriving on an established connection in the client-to-server direction, where the method is POST and the word password appears in the client body. That one rule catches every brute-force attempt even when the username and password values themselves are unique.

    Parsing eve.json alerts

    When the rules above match, Suricata writes an alert record to /var/log/suricata/eve.json. The payload_printable field holds the raw request body (the place where the campaign and exfil tokens live). The jq filter pattern you need is:

    jq -r 'select(.alert != null) | select(.alert.signature_id == 1000001) | .payload_printable' /var/log/suricata/eve.json

    Use head -1 to stop after the first match once you have confirmed the extraction works.

    Step 2: SSH to the IDS Sensor

    All of the detection work runs on the sensor.

    SSH to the IDS sensor

    Open a terminal on your Kali and connect with the analyst credentials.

    ssh analyst@<ids_sensor_ip>

    When prompted for the password, enter:

    A3g1s_S0C_2024#

    Confirm the shell prompt and the hostname; you should be on the Aegis sensor.

    Step 3: Confirm Suricata Is Running

    Writing rules against a dead engine wastes your shift.

    Confirm Suricata is running

    Check that Suricata is running on the sensor before touching the rules file.

    pidof suricata

    A numeric process ID in the output means the engine is up. An empty response means Suricata is not running; re-check that the lab finished launching.

    Note that pgrep -x suricata does not reliably detect Suricata in daemon mode; the main thread renames itself to Suricata-Main, so the exact-match flag misses it. Use pidof suricata or pgrep -f suricata.

    Step 4: Observe Live Brute-Force Traffic

    Before writing rules, you need to see what the attacker is sending.

    Capture live brute-force traffic with tcpdump

    Run tcpdump on port 80 on the sensor and filter for POST to focus on the login requests.

    sudo tcpdump -i eth0 -A port 80 | grep -A 5 "POST /login" | head -40

    Let the capture run for fifteen to twenty seconds, then stop it with Ctrl+C. Look for three details in the output:

    Field What to look for Why it matters
    Request method and URL POST /login HTTP/1.1 Confirms the brute-force target
    Request body username=<varied>&password=<varied>&exfil=d3t3ct The exfil= parameter is the same on every attempt; that is a content signature
    Successful request body username=<valid>&password=<valid>&campaign=brut3 The campaign=brut3 parameter only appears on the successful login; that is a second content signature worth catching separately

    Two patterns jump out: every brute-force POST body contains the literal word password, and one specific POST body contains campaign=brut3. Each becomes its own Suricata rule.

    Step 5: Write Two Suricata Rules

    Custom signatures live in /etc/suricata/rules/local.rules on the sensor. The image is a stripped-down Ubuntu build with no interactive editor installed (production IDS appliances are minimal for the same reason), so write the file with a heredoc through sudo tee. The single-quoted 'EOF' marker tells bash to pass every character through verbatim, which preserves the double quotes inside the rule bodies.

    Rule 1: Brute-force POST detection. The rule fires on every POST carrying a password field, which covers the entire flood. The flow:to_server,established; limit keeps the rule from inspecting server responses.

    Write the brute-force detection rule

    Write the first rule on the sensor, overwriting any existing contents of the file.

    sudo tee /etc/suricata/rules/local.rules > /dev/null <<'EOF'
alert http any any -> any any (msg:"Brute Force Login Attempt"; flow:to_server,established; content:"POST"; http_method; content:"password"; http_client_body; sid:1000001; rev:1;)
EOF

    The redirect to /dev/null discards the echoed rule text so the terminal stays clean.

    Rule 2: Campaign marker detection. The rule fires only on the single POST that carries the attacker's tracking tag campaign=brut3. Pairing a high-noise rule with a narrow rule is a standard SOC pattern: the narrow rule tells you when the "interesting" event happened inside the volume pattern.

    Append the campaign marker rule

    Append the second rule. The -a flag tells tee to append rather than overwrite, which keeps Rule 1 in place.

    sudo tee -a /etc/suricata/rules/local.rules > /dev/null <<'EOF'
alert http any any -> any any (msg:"Campaign Marker Detected"; flow:to_server,established; content:"POST"; http_method; content:"campaign=brut3"; http_client_body; sid:1000002; rev:1;)
EOF

    The narrow rule fires only on the single POST carrying the attacker's tracking tag.

    Confirm both rules landed in the file

    Confirm both rules landed in the file before reloading; a missing newline or stray quote at this stage is the most common reason the reload in Step 6 reports zero loaded rules.

    cat /etc/suricata/rules/local.rules

    Expected output: two alert http any any lines, one ending in sid:1000001; rev:1;) and the other in sid:1000002; rev:1;).

    Step 6: Reload Suricata Without Restarting

    Suricata does not watch the rules file for changes.

    Reload Suricata with the USR2 signal

    Send Suricata the USR2 signal to re-read every configured rule file without dropping monitored traffic.

    sudo kill -USR2 $(pidof suricata)

    No output from the command means the signal was delivered. Suricata takes a few seconds to parse the new rules. If you instead see the kill usage help print, the $(...) expansion returned nothing; re-check Step 3.

    Confirm the reload actually loaded your rules

    The most common failure in this exercise is that the USR2 was delivered but Suricata ended up with zero rules loaded (bad path, bad syntax, stale process). A silent reload looks identical to a bad reload, so always verify.

    Verify the ruleset loaded

    Query Suricata's command socket for ruleset statistics to confirm both rules are active.

    sudo suricatasc -c ruleset-stats /var/run/suricata/suricata-command.socket

    Read rules_loaded and rules_failed from the JSON; you want rules_loaded to be 2 and rules_failed to be 0.

    Expected output:

    {"message": [{"id": 0, "rules_loaded": 2, "rules_failed": 0}], "return": "OK"}

    Interpret the result:

    rules_loaded rules_failed Meaning What to do
    2 0 Both rules active Move on to Step 7
    0 0 Rules file empty, unreadable, or reload never reached Suricata Re-check Step 5, re-run the USR2
    1 with rules_failed > 0 nonzero One rule has a syntax error and was skipped Tail /var/log/suricata/suricata.log for an Error parsing signature line, fix the broken rule, re-run the USR2

    Do not move on to Step 7 until rules_loaded is 2. Alerts will not fire and you will waste time looking for IOCs that do not exist yet.

    Step 7: Verify Alerts Are Firing

    With both rules loaded and the attack traffic still flowing, Suricata should begin writing alert records within fifteen to twenty seconds (one attack cycle).

    List the firing alert signatures

    Check the eve.json log on the sensor for the distinct alert signatures that have fired.

    jq 'select(.alert != null) | .alert.signature' /var/log/suricata/eve.json | sort -u

    Expected output:

    "Brute Force Login Attempt"
"Campaign Marker Detected"

    If only one signature shows, one of your rules is not matching. Re-open local.rules and double-check syntax, then re-run Step 6. If both signatures show, you have working detection and can move on to IOC extraction.

    Count alerts per signature

    To get a feel for the rate, count how many alerts have fired so far per signature.

    jq -r 'select(.alert != null) | .alert.signature' /var/log/suricata/eve.json | sort | uniq -c

    In a typical five-minute window you will see dozens of Brute Force alerts (one per attack cycle) and a much smaller count of Campaign Marker alerts (one per full attack loop).

    Step 8: Extract Token 1 from the Campaign Marker Alert

    The campaign=brut3 parameter is the attacker's tracking tag for the successful-login POST. Suricata captured the full POST body in the alert's payload_printable field.

    Extract the campaign token

    Pull the campaign value from the Campaign Marker alert with jq and grep.

    jq -r 'select(.alert != null) | select(.alert.signature_id == 1000002) | .payload_printable' /var/log/suricata/eve.json | grep -oP 'campaign=\K[^& \r\n]+' | head -1

    Record the value returned as flag part 1.

    What the filter does, step by step:

    Fragment Purpose
    select(.alert != null) Keep only alert records, not HTTP metadata events
    select(.alert.signature_id == 1000002) Keep only Campaign Marker alerts (sid of Rule 2)
    .payload_printable Emit the raw POST body as a string
    grep -oP 'campaign=\K[^& \r\n]+' Match campaign=... and emit only the value
    head -1 Stop after the first match

    Record the value returned as flag part 1.

    Step 9: Extract Token 2 from the Brute-Force Alerts

    The exfil=d3t3ct parameter rides on every failed-login POST body. It is the attacker's outbound-data tag: every credential the tool tests gets shipped back with this label.

    Extract the exfil token

    Pull the exfil value from a Brute Force alert the same way you pulled the campaign token.

    jq -r 'select(.alert != null) | select(.alert.signature_id == 1000001) | .payload_printable' /var/log/suricata/eve.json | grep -oP 'exfil=\K[^& \r\n]+' | head -1

    The only difference from Step 8 is the signature_id filter (1000001 is your Brute Force rule) and the parameter name (exfil instead of campaign). Record the value returned as flag part 2.

    Record the value returned as flag part 2.

    Step 11: Interpret the Results

    Review the three IOCs and what they say about the attacker's operation.

    The campaign marker campaign=brut3 rode on the single successful-login POST. Attackers use campaign markers to link a successful hit back to the specific wordlist, target list, or customer job that produced it. In a credential-stuffing-as-a-service operation the marker tells the operator which customer to bill; in an independent attack the marker tells the attacker which campaign's tooling was most efficient. For you, the marker is a pivot point: every prior alert carrying campaign=brut3 is part of the same operation.

    The exfil tag exfil=d3t3ct appeared on every failed-login POST. The tag labels the outbound-data channel; the attacker ships every tested credential back to themselves under this label, regardless of whether the login succeeded. The tag is therefore a volume indicator: a spike of traffic carrying exfil=d3t3ct is a spike of this attacker's activity, and it decouples "attacker tool" from "attacker identity" (the same tool can run several concurrent exfil channels).

    The AegisCracker User-Agent on the portal ties the recon probing to the same adversary (or the same tool) that ran the brute-force against the sensor. Custom User-Agent strings are lazy OpSec but strong IOCs: they link attack streams across hosts, support WAF blocking, and travel with the tool even when the source IP rotates.

    Assemble the three values with underscores between them: OCR{________}.

    Flag Format

    Use the tokens in the order you discovered them:

    OCR{<campaigntoken>_<exfiltoken>_<useragenttoken>}

    Where campaigntoken is from the Campaign Marker alert payload, exfiltoken is from the Brute Force alert payload, and useragenttoken is from the nginx access log User-Agent string.

    Analysis Questions

    The questions below ask you to generalize beyond the mechanics of the exercise. Consider each one before reading the answer.

    1. Your brute-force rule fires on every POST that contains the word password. In a real production auth gateway, why would a rule written that loosely generate too much noise, and what would you add to tighten it?

    Reveal Answer

    Every legitimate login request also contains the word password in the POST body, so in production the rule would fire on real users as well as attackers. Real credential-stuffing detection rules add one or more of the following constraints to tighten the match: (a) a threshold keyword that only fires after N matches from the same src_ip within a time window (for example, threshold: type threshold, track by_src, count 20, seconds 60); (b) a dsize constraint on request size; (c) a content filter on the specific User-Agent string of the attacker tool; (d) an anomaly detector that compares request rate per source against a baseline. For lab work the loose rule is pedagogically useful because it reliably fires every three seconds and lets you focus on the extraction workflow, but it would be unshippable to a live SOC.

    2. The attacker embedded campaign=brut3 and exfil=d3t3ct in the POST body, both in cleartext. Why would a real attacker leave identifiers like that inline, and what risk does it create for them?

    Reveal Answer

    Attackers embed campaign and exfil tags for the same reasons any software operator adds tracking identifiers: they need to reconcile billing in credential-stuffing-as-a-service, A/B-test different wordlists or targets against each other, or correlate successful hits back to specific jobs. The OpSec risk is that any defender who captures the traffic can use those tags to cluster otherwise-unrelated attack streams, build a timeline of the same operator's activity, pivot across victims, and supply a high-quality IOC to threat-intel sharing groups. A sophisticated attacker would encode or encrypt the tags, rotate them between campaigns, or embed them in a header the IDS is less likely to log. Seeing them inline in cleartext is either a sign of a lower-skill operator or a sign that the tooling is mature enough that the operator accepts the exposure as the cost of easier internal reconciliation.

    3. The campaign-marker rule (sid 1000002) is a subset of the brute-force rule (sid 1000001); every packet that matches the campaign rule also matches the brute-force rule. Why write both instead of just the tighter one, and how does a SOC analyst benefit from the pair?

    Reveal Answer

    The two rules serve different operational purposes. The wide rule (sid 1000001) measures the volume and shape of the attack: how long the flood lasted, how many attempts per minute, which source IPs participated, when it started and stopped. The narrow rule (sid 1000002) measures the outcome: the single moment the attacker found a valid credential, including the exact payload that succeeded. Writing only the tighter rule means the SOC misses the flood entirely and sees only the success; writing only the wider rule means the SOC buries the success in the noise of the flood. Paired, the two rules let an analyst answer two distinct questions in one query: "how big is the attack" and "did the attacker win". In real deployments this layering is standard: one rule per pattern of interest, regardless of whether one is a subset of another.

    Key Takeaways

    • Flow and body modifiers together turn a generic content: match into a tight HTTP rule that only fires on client-to-server POST bodies. Always include flow:to_server,established; on POST-inspection rules to cut noise and processing cost.
    • Pair a wide rule with a narrow rule when you care about both the shape of an attack and a specific outcome inside it. The wide rule measures volume; the narrow rule measures success. A SOC that runs only one of the pair has half the picture.
    • Always verify the rule reload with suricatasc -c ruleset-stats .... A silent failed reload looks identical to a successful reload in the terminal, and debugging "why am I not seeing alerts" wastes far more time than the verification takes.
    • Payload tokens in cleartext are IOC gold. Campaign tags, exfil tags, and custom User-Agent strings travel with the attacker tool across targets and over time. Extracting them from a single alert lets the SOC pivot across the rest of the attack surface.
    • Cross-source correlation is more defensible than single-source evidence. IDS payloads plus nginx logs together tell Sarah a story she can brief to the CEO; either alone is a fragment. Week 15 builds on detection and correlation in the capstone CTF.
