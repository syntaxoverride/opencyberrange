    Exercise 15: Capstone CTF

    Before You Begin

    Over the past fourteen weeks, you have progressed from running your first port scan to chaining exploits across multi-server environments. Every technique you practiced; enumeration, web exploitation, credential discovery, lateral movement, privilege escalation, and database extraction; appears somewhere in the attack path ahead. Exercise 15 is the final assessment for the course, and it requires you to identify which skill applies at each stage without being told.

    Your VPN must be connected and your terminal open before you proceed. Review your notes from Exercises 1 through 14, because the engagement draws on concepts from every prior week. One important difference from previous labs: hints are locked for the first 30 minutes. The platform will not display any hint text until that delay has passed. Use those 30 minutes to work independently and demonstrate the methodology you have built over the semester.

    Scenario

    Zenith Global Corp is a multinational logistics company headquartered in Chicago. The company has engaged your elite red team for a full-scope penetration test as part of their annual security program. Everything you have learned across the entire course comes together in the engagement ahead.

    Your briefing comes from Diane Holloway, CISO (Chief Information Security Officer): "We have three tiers of infrastructure. The web frontend handles customer tracking and order management. Behind that, our application server runs the business logic. And at the core, our database server holds everything; customer data, financial records, shipping manifests. I want you to demonstrate whether an external attacker can reach our data. Our architecture team says it's impossible without insider access."

    Prove them wrong. Three target servers make up the engagement scope: a web frontend running an HTTP (Hypertext Transfer Protocol) API on port 80, an application server running SSH (Secure Shell) on port 22, and a database server running MySQL on port 3306. Assessment markers are distributed across all three tiers. Your job is to chain vulnerabilities across the full infrastructure, moving from the externally facing web frontend all the way to the backend database. The difficulty level is Advanced, the time limit is 120 minutes, and hints remain locked for the first 30 minutes.

    Your Objectives

    The following list outlines what you need to accomplish during the engagement. Each objective maps to one or more walkthrough phases below.

    • Perform thorough reconnaissance across all three target systems
    • Exploit an IDOR (Insecure Direct Object Reference) vulnerability in the web frontend API to discover internal credentials
    • Identify broken access control on an administrative API endpoint to extract a marker token
    • Use discovered credentials to pivot laterally to the application server via SSH
    • Escalate privileges on the application server by exploiting a SUID (Set User ID) binary
    • Extract database credentials from the compromised application server
    • Connect to the backend MySQL database and query for the final assessment marker
    • Assemble and submit the flag in OCR{...} format

    Background: Red Team Engagement Methodology

    A red team engagement differs from a standard penetration test in scope and approach. A penetration test typically focuses on finding as many vulnerabilities as possible within a defined target set. A red team engagement, by contrast, simulates a real adversary attempting to achieve a specific objective; usually proving that an attacker can reach sensitive data or critical systems. The red team operates with a defined goal and chains together whatever vulnerabilities are necessary to reach it.

    Full-scope assessments like the Zenith Global engagement test the entire defensive posture of an organization, not individual components in isolation. The web frontend may have its own vulnerabilities, the application server may have misconfigurations, and the database may have weak access controls; but the real finding is whether an attacker can chain all three weaknesses together to move from external access to complete data compromise. Defenders often test each tier independently and miss the compounding risk that emerges when flaws exist across multiple layers.

    Multi-tier architecture attacks follow a predictable pattern: gain a foothold on the outermost tier, discover credentials or pivot paths to the next tier, and repeat until you reach the core data. The Zenith Global infrastructure follows a classic three-tier model where the web frontend is publicly accessible, the application server sits behind it, and the database server holds the sensitive records at the core.

    Tool Primer: Combining Everything

    The capstone engagement uses four core tools, each mapped to a specific phase of the attack. You have practiced each of these tools in previous labs, so the primer below focuses on how they connect rather than introducing them from scratch.

    Tool Phase Purpose
    curl Web Reconnaissance + API Exploitation Send HTTP requests to the web frontend, enumerate API endpoints, and extract JSON responses containing credentials and tokens
    ssh Lateral Movement Connect to the application server using credentials discovered during the web exploitation phase
    python3 Privilege Escalation Exploit the SUID bit on the python3 binary to escalate from a standard user to root on the application server
    mysql Database Extraction Connect to the MySQL database server and query tables for the final assessment marker

    The chaining pattern works as a pipeline. Curl discovers credentials in the web API, which feeds into an SSH connection to the application server. Privilege escalation on the application server reveals database credentials stored in a configuration file. Those database credentials feed into a MySQL connection that retrieves the final marker. Each tool's output becomes the input for the next stage.

    curl; HTTP request syntax:

    curl -s http://<target>/api/endpoint

    The -s flag silences the progress bar, producing clean JSON output that you can read or pipe into other tools.

    ssh; Remote connection syntax:

    ssh <username>@<target>

    You will be prompted for a password. Use the credentials discovered during the web exploitation phase.

    python3; SUID escalation technique:

    When python3 has the SUID bit set and is owned by root, calling os.setuid(0) switches the effective user to root. The os.system() function then spawns a shell or executes a command with root privileges.

    python3 -c "import os; os.setuid(0); os.system('/bin/sh')"

    mysql; Database query syntax:

    mysql --skip-ssl -h <db_host> -u <username> -p'<password>' <database_name> -e "SELECT * FROM <table>"

    The -h flag specifies the remote host, -u sets the username, -p provides the password (with no space between -p and the password), and -e executes a query without entering the interactive MySQL shell.

    Walkthrough

    Phase 1: Web Reconnaissance

    The engagement begins with the externally facing web frontend. Before you can exploit anything, you need to understand what is running and how the API is structured.

    Step 1: Launch the Exercise and Note All Three Target IPs

    Open the platform in your browser and start the exercise environment. The Zenith Global lab deploys three servers, so you will see three IP addresses in the Active Lab View rather than the one or two IPs from previous labs.

    • Navigate to Exercises and locate Exercise 15; Capstone CTF
    • Click Launch and wait for the status to change to Running
    • Note all three target IPs displayed in the Active Lab View:
    • Web Frontend: serves the customer-facing API on port 80
    • App Server: runs SSH on port 22
    • Database: runs MySQL on port 3306
    • Record all three IPs before proceeding; you will need each one at different phases of the engagement

    The web frontend is the only externally facing service described in Diane Holloway's briefing. Your attack path starts there and works inward toward the database.

    Step 2: Enumerate the Web Frontend

    Confirm that the web frontend is responding and explore its API surface.

    Request the web frontend root

    Send a basic HTTP request to the root URL of the web frontend.

    curl -s http://<webfront_ip>/

    Replace <webfront_ip> with the web frontend IP from the Active Lab View. You should receive a response confirming the application is running; look for JSON output or an HTML page that references the Zenith Global order management system.

    Probe for an API endpoint

    Now probe for API endpoints. Web applications built with Flask (a Python web framework) commonly expose their functionality through /api/ routes. Test whether an API exists by requesting a known path pattern.

    curl -s http://<webfront_ip>/api/orders/1

    A successful response containing order data confirms that the API endpoint exists and is returning records. The response format will be JSON (JavaScript Object Notation); a structured data format using key-value pairs enclosed in curly braces.

    Step 3: Discover the IDOR Vulnerability

    An IDOR vulnerability occurs when an application exposes internal object references (like order IDs) in the URL and does not verify that the requesting user is authorized to view the requested record. If the API returns order data for /api/orders/1, test whether it returns data for other order IDs as well; even those that would belong to different users.

    Enumerate order IDs to confirm IDOR

    Enumerate orders 1 through 10 by changing the ID number in the URL.

    curl -s http://<webfront_ip>/api/orders/1
curl -s http://<webfront_ip>/api/orders/2
curl -s http://<webfront_ip>/api/orders/3

    Continue through /api/orders/10. A different response per ID confirms the API serves any order without an authorization check.

    Automate the order enumeration with a loop

    You can also use a bash loop to automate the enumeration across all ten IDs in one command.

    for i in $(seq 1 10); do
  echo "=== Order $i ==="
  curl -s http://<webfront_ip>/api/orders/$i
  echo ""
done

    The loop prints each order in turn so you can scan them together.

    Read each response carefully. Most orders will contain standard logistics data; tracking numbers, addresses, shipment details. One order contains something different: internal notes with system credentials. Look for fields labeled notes, internal_notes, comments, or similar keys that contain usernames and passwords rather than shipping information.

    Expected finding: Order #7 contains internal notes that include SSH credentials for the application server. Record the username and password; you will need them in Phase 3.

    Phase 2: API Exploitation

    With the IDOR vulnerability confirmed and credentials extracted, there is still more to gather from the web frontend before moving on. Broken access control vulnerabilities often expose administrative endpoints that should be restricted.

    Step 4: Record the SSH Credentials from Order #7

    Examine the full JSON response from order #7. The response contains a field with credentials for the application server. The format will resemble:

    {
  "order_id": 7,
  "notes": "Internal: appserver credentials; appuser / <password>"
}

    The exact field names may vary, but the critical information is a username and password pair intended for SSH access to the application server. Write down or copy both values; you will use them during the lateral movement phase.

    Step 5: Access the Config Endpoint and Extract the First Marker

    Many web applications have configuration or status endpoints that developers create during development and forget to restrict in production.

    Access the unprotected config endpoint

    Test whether the Zenith Global frontend exposes a configuration endpoint that should be restricted.

    curl -s http://<webfront_ip>/api/config

    A successful response indicates broken access control; the /api/config endpoint should require authentication but does not. The response contains internal application configuration data, including a marker token that proves you accessed the administrative configuration.

    Expected output: The JSON response includes a field like "marker" with a value that forms part of your final flag assembly. Record the marker value from the config endpoint.

    The combination of IDOR on the orders API and broken access control on the config endpoint demonstrates two distinct vulnerability classes on the web frontend. Both stem from missing authorization checks; the application serves data to anyone who requests it, regardless of whether they should have access.

    Phase 3: Lateral Movement

    With credentials in hand from the web frontend, pivot to the application server. Lateral movement is the process of using access on one system to reach another system in the environment.

    Step 6: SSH to the Application Server

    SSH to the application server

    Use the username and password discovered in order #7 to connect to the application server via SSH.

    ssh appuser@<appserver_ip>

    Replace <appserver_ip> with the application server IP from the Active Lab View. When prompted, enter the password you extracted from the API response. A successful login places you on the application server with a standard user shell.

    Confirm your identity on the application server

    Confirm your identity and orientation on the new system now that you have a shell on the target.

    whoami
hostname
pwd

    The whoami command should return appuser, confirming you are logged in as the account whose credentials were exposed through the IDOR vulnerability. You now have a foothold on the second tier of the infrastructure; the application server that Diane Holloway's architecture team said was "impossible to reach without insider access."

    Phase 4: Privilege Escalation

    Standard user access on the application server is not sufficient to reach all files and configurations. Root-level access is needed to read sensitive configuration files that may contain database credentials. A common privilege escalation vector on Linux systems is the SUID bit; a file permission that allows a program to run with the privileges of its owner rather than the user who executed it.

    Step 7: Discover the SUID python3 Binary

    Search the filesystem for binaries with the SUID bit set.

    Search for SUID binaries

    The find command with the -perm flag locates files that have specific permission bits enabled. Run it on the application server where you now have a shell.

    find / -perm -4000 -type f 2>/dev/null

    The -perm -4000 flag matches files where the SUID bit is set. The 2>/dev/null portion redirects error messages (from directories you cannot access) to /dev/null so they do not clutter your output. The output includes /usr/bin/python3 (or a similar path) in the list of SUID binaries. Python3 with the SUID bit set is a critical misconfiguration; the Python interpreter can execute arbitrary system calls, and the SUID bit means those calls run as root.

    Confirm the SUID bit on python3

    Confirm the finding by checking the permissions on the python3 binary.

    ls -la $(which python3)

    Look for the s character in the permission string (e.g., -rwsr-xr-x). The s in the owner's execute position confirms the SUID bit is active.

    Step 8: Exploit SUID python3 to Escalate to Root

    Python3 with SUID can escalate privileges because the os.setuid(0) call switches the effective user ID to 0 (root), and that call succeeds when the binary has the SUID bit set and is owned by root.

    Spawn a root shell via SUID python3

    Execute the following command on the application server to spawn a root shell.

    python3 -c "import os; os.setuid(0); os.system('/bin/sh')"

    Breaking down the command:

    • import os: loads the Python operating system module
    • os.setuid(0): sets the effective user ID to 0 (root); succeeds because of SUID
    • os.system('/bin/sh'): spawns an interactive shell, which inherits the root privilege

    Confirm root on the application server

    After execution, you should have a root shell. Confirm your effective user.

    whoami

    The output should read root. You now have full administrative access to the application server.

    Read the privilege escalation marker

    With root access, check for a marker file in the root home directory.

    cat /root/marker.txt

    Record the marker value. The content of the marker file proves you achieved privilege escalation on the application server.

    Phase 5: Database Extraction

    Root access on the application server opens the path to the final tier: the database. Application servers commonly store database connection credentials in configuration files, because the application needs those credentials to communicate with the backend.

    Step 9: Read Database Credentials from the Configuration File

    Read the database configuration file

    Search for database configuration files on the application server. The Zenith Global application stores its configuration under /opt/zenith/.

    cat /opt/zenith/db.conf

    The configuration file contains database connection parameters; a hostname or IP, a username, a password, and a database name. The format will resemble:

    DB_HOST=<datastore_ip>
DB_USER=zenith_app
DB_PASS=<password>
DB_NAME=zenith

    Record the database hostname (or IP), username, password, and database name. You will need all four values to connect to the MySQL server in the next step.

    Step 10: Connect to MySQL and Query for the Final Flag

    Query the MySQL database for the final flag

    Use the MySQL command-line client from the compromised application server to connect to the database server and query for the assessment marker. Replace the placeholders with the values from db.conf.

    mysql --skip-ssl -h <datastore_ip> -u zenith_app -p'<password>' zenith -e "SELECT * FROM flags"

    The query returns one or more rows from the flags table. Look for a row with a name column of assessment and a value column containing the final marker.

    Breaking down the command:

    • -h <datastore_ip>: the database server's IP address (from the Active Lab View or from db.conf)
    • -u zenith_app: the database username from the configuration file
    • -p'<password>': the database password, with no space between -p and the password string
    • zenith: the database name
    • -e "SELECT * FROM flags": executes the SQL query and returns the results without entering the interactive MySQL prompt

    Expected output: The query returns one or more rows from the flags table. Look for a row with a name column of assessment and a value column containing the final marker.

    Record the value from the flags table. Combined with the markers from the web frontend config endpoint and the root marker on the application server, you now have all the pieces needed to assemble the final flag.

    Analysis Questions

    The following questions ask you to reflect on the strategy and methodology behind the engagement, not the specific commands you typed. Think through each one before reading the answer.

    1. Why is the IDOR vulnerability on the orders API more dangerous than it might appear at first glance? What makes the exposure of order #7 different from a typical data leak?

    Reveal Answer

    A standard IDOR vulnerability exposes data belonging to other users; order details, personal information, or financial records. The Zenith Global IDOR goes further because order #7 contains internal system credentials. The leaked data is not customer information but an authentication secret that grants access to a different tier of the infrastructure. A single missing authorization check on the web frontend created a pivot path to the application server, which means the IDOR is not an isolated finding; it is the entry point for a full infrastructure compromise.

    2. The /api/config endpoint had no authentication requirement. How does broken access control differ from an IDOR, and why do both matter in the same application?

    Reveal Answer

    An IDOR vulnerability exposes data by manipulating object references (like order IDs) within an endpoint that does perform some level of access control; the endpoint exists for legitimate users, but it fails to verify that the requesting user owns the specific record. Broken access control on the config endpoint is a different class: the entire endpoint should be restricted to administrators, but no access control exists at all. Finding both in the same application indicates a systemic authorization weakness; the development team likely did not implement a consistent access control framework, which means other endpoints may have similar gaps.

    3. Python3 had the SUID bit set on the application server. Why is SUID on an interpreter (like python3, perl, or bash) more dangerous than SUID on a purpose-built utility?

    Reveal Answer

    A purpose-built SUID utility (like passwd or ping) performs a narrow, well-defined function and then exits. An interpreter with SUID can execute any code the user provides, which means the entire programming language runs with root privileges. Python3 with SUID allows the attacker to call os.setuid(0) and spawn a root shell; turning arbitrary code execution into full privilege escalation. System administrators should never set the SUID bit on interpreters, because doing so grants unrestricted root access to anyone who can execute the binary.

    4. Trace the full attack chain from the first curl command to the final MySQL query. At which single point could Zenith Global have broken the chain most effectively?

    Reveal Answer

    Removing the IDOR vulnerability on the orders API would have been the most effective single fix. Without the credentials leaked through order #7, the attacker has no path from the web frontend to the application server. The config endpoint leak and the SUID python3 misconfiguration are both serious findings, but neither one is reachable without the initial credential exposure. Fixing the earliest link in the chain denies the attacker every subsequent step; the SUID binary and the database credentials become irrelevant if the attacker never reaches the application server.

    Key Takeaways

    The capstone engagement brings together every technique from the fourteen weeks that preceded it. The following points summarize the core lessons from the full course journey.

    • Attack chains are greater than the sum of their parts. Individual vulnerabilities that seem moderate in isolation; an IDOR, a missing access control check, a SUID misconfiguration; combine into a complete infrastructure compromise when they exist across connected systems. Defenders must evaluate risk across tiers, not within them.

    • Reconnaissance determines everything that follows. The entire engagement depended on methodical enumeration of the web frontend API. Skipping orders or failing to test the config endpoint would have left critical credentials and markers undiscovered. Thorough reconnaissance is the foundation of every successful assessment.

    • Credentials are the most valuable discovery in any engagement. Passwords, API keys, and database connection strings found during one phase unlock access to the next phase. The SSH password in order #7 and the database password in db.conf were the two pivots that moved the attack from tier to tier.

    • SUID binaries on interpreters are a critical misconfiguration. Setting the SUID bit on python3, perl, bash, or any general-purpose interpreter grants unrestricted root access to any user who can run the binary. Regular SUID audits using find / -perm -4000 should be part of every system hardening checklist.

    • Broken access control is a systemic problem, not an isolated bug. The Zenith Global web frontend had both IDOR and unauthenticated admin endpoints, indicating a missing authorization framework. Organizations that find one access control flaw should audit every endpoint for the same pattern.

    • Post-exploitation proves business impact. Reaching the database and extracting records from the flags table demonstrates that an external attacker can access Zenith Global's core data; the exact scenario Diane Holloway's architecture team said was impossible. The technical chain matters, but the finding that resonates with executives is the data at the end of it.
