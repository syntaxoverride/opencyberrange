    Exercise OTSOC-6.3: Design the IT/OT Boundary

    Scenario

    Pecan Creek Creamery has a corporate web portal sitting on the same flat network as the plant. The portal carries a Local File Inclusion bug, and through it an attacker reaches an OT VPN profile that hands out a working control-network credential. The boundary that should stop that pivot does not exist, so a web bug on a marketing portal becomes a path to the ammonia controllers.

    Your job in this exercise is to design the Level 3.5 industrial DMZ that closes the gap. You reproduce the LFI first so the exposure is concrete, then you design the iDMZ: which services move into it, what the brokered jump host enforces, and the replicated-historian pattern that keeps IT consumers out of the control zones. You write the deny-by-default boundary firewall rule set, mapping each control to its Foundational Requirement, and you prove that no direct IT-to-OT path survives. The boundary design goes to the boundary-design rubric, which releases the flag once every direct path is eliminated and the rule set is deny-by-default with justifications.

    Why this matters

    The IT/OT boundary is the single most scrutinized control in any OT insurance questionnaire, because it is where the overwhelming majority of real intrusions cross from the enterprise into the plant. A Level 3.5 industrial DMZ is the 62443 answer: a buffer segment between IT (Level 4) and OT (Levels 0 to 3) where the only assets are brokers and replicas. IT consumers talk to the DMZ; OT devices talk to the DMZ; nothing talks straight through.

    The corpweb LFI you reproduce is the textbook failure mode. A vulnerability on an IT-reachable asset leaks a credential, and on a flat network that credential reaches a PLC with nothing in the way. The fix is not to patch the LFI alone, because the next bug will leak the next credential. The fix is architectural: a brokered jump host that demands MFA and records sessions, a replicated historian so IT reads a copy instead of reaching into the control zone, and a deny-by-default firewall where every allow is explicit, minimal, and justified. Each control maps to a Foundational Requirement, which is how the underwriter ties your design back to the SL-T vectors from Exercise 6.2.

    Credentials in scope Username Password Where it is used
    Leaked OT contractor account ot_contractor PecanCreek#2026 Leaked by the corpweb LFI; the credential your design must neutralize
    Operator HMI kiosk operator PecanCreek#2026 Read-only cross-reference (optional)

    Walkthrough

    Step 1: Reproduce the LFI and confirm the exposure

    Before you design the fix, see the exposure for yourself. The corporate portal includes a page parameter that reads a file off disk with no path validation, the classic Local File Inclusion. Point it at the OT VPN profile and the remote-access document and read what leaks. Confirming the bug yourself is read-only against an IT asset; you touch no plant device.

    Kali - reach the OT VPN profile through the LFI

    curl -s "http://$CORP/portal.php?page=config/ot_vpn_profile.ovpn"

    Expected output (abridged)

    # Pecan Creek Creamery OT remote access profile
remote jump01.pcc.local 1194
# contractor login
auth-user-pass
# username ot_contractor
# password PecanCreek#2026
...

    The profile leaks the credential ot_contractor / PecanCreek#2026 and points at the jump host jump01.pcc.local. Pull the remote-access document too, since it names the assets the contractor was expected to reach.

    Kali - read the remote-access document through the same bug

    curl -s "http://$CORP/portal.php?page=config/remote_access.pdf" | strings | head -20

    The document confirms the contractor account is meant to reach control-network devices. On the current flat network nothing stops that credential from reaching the PLCs directly, so a web bug on the portal is a straight line to the ammonia controllers. That line is what your design eliminates.

    Step 2: Enumerate every direct IT-to-OT path

    List the paths that exist today. Each one is a finding the boundary design must close. The LFI pivot is the headline, but it is not the only path.

    Direct IT-to-OT path today Why it is dangerous
    corpweb LFI to OT VPN profile to PLCs A web bug leaks a credential that reaches control devices
    Flat segment: any IT host can ARP the control zone No segmentation between Level 4 and Level 1
    IT consumers read the historian inside the control area A read path into OT is also a potential write path
    Contractor VPN lands directly on the OT subnet No brokered hop, no MFA, no session recording

    Every row resolves to the same root cause: there is no boundary. The design in the next steps replaces all four with conduits through a single DMZ.

    Step 3: Design the Level 3.5 industrial DMZ

    The target architecture puts a buffer segment between IT and OT. IT talks to the DMZ, OT talks to the DMZ, and the firewall denies everything else. The diagram below is the target boundary.

    flowchart LR
    subgraph IT["IT Zone (Level 4)"]
        CORP["corpweb portal"]
        ITUSER["IT consumers"]
    end
    subgraph IDMZ["Industrial DMZ (Level 3.5)"]
        JUMP["jump01: brokered jump host<br/>MFA, session recording"]
        HISTREP["replicated historian<br/>read-only copy"]
    end
    subgraph OT["OT Zones (Levels 1 to 3)"]
        HIST["historian.pcc.local"]
        CTRL["control + supervisory devices"]
        SIS["ammonia SIS (safety zone)"]
    end
    ITUSER -->|"MFA, brokered"| JUMP
    JUMP -->|"explicit allow only"| CTRL
    HIST -->|"one-way replication"| HISTREP
    ITUSER -->|"read the replica"| HISTREP
    CORP -.->|"DENY: no path to OT"| OT

    The DMZ holds two assets. The brokered jump host, jump01, is the only way an IT identity reaches OT: it demands MFA, it brokers the connection rather than passing the credential through, and it records every session. The replicated historian is a read-only copy of the plant historian; IT consumers read the replica in the DMZ and never reach into the control zone for live data. The corpweb portal stays in IT with no path into OT at all, so even if the LFI is exploited again, the leaked credential lands on a segment that cannot reach a PLC.

    Step 4: Write the deny-by-default firewall rule set

    The boundary firewall denies everything by default. Every allow is a single explicit rule naming a source, a destination, a protocol or port, and a justification. The implicit final rule is deny-all-log. Write the rules as a table the grader and an auditor can both read.

    # Source Destination Proto/Port Action Justification
    1 IT consumers jump01 (DMZ) TCP 443 + MFA ALLOW Sole brokered entry into OT; MFA enforced
    2 jump01 (DMZ) control zone named mgmt ports ALLOW Engineering access, brokered and recorded only
    3 plant historian replicated historian (DMZ) one-way replication ALLOW Historian copy; replication is push-only
    4 IT consumers replicated historian (DMZ) TCP 3000 read ALLOW IT reads the replica, never the live plant
    5 corpweb / any IT any OT zone any DENY (log) No direct IT-to-OT path survives
    6 any ammonia safety zone any except status DENY (log) SIS isolated; status conduit only
    7 any any any DENY (log) Default deny, everything else dropped and logged

    Rules 5 through 7 are the ones the grader checks hardest: rule 5 kills the LFI pivot, rule 6 protects the safety zone, and rule 7 is the deny-by-default backstop. Every allow above it is minimal and justified.

    Step 5: Map each control to its Foundational Requirement

    Tie the design back to the SL-T vectors from Exercise 6.2 by mapping each control to the requirement it satisfies. The mapping is how the underwriter traces the fix to the gap.

    Control Foundational Requirement
    MFA on the jump host FR1 Identification and Authentication Control
    Brokered access, no pass-through credential FR2 Use Control
    Integrity monitoring on the conduit FR3 System Integrity
    Segmentation, no direct IT-to-OT path FR5 Restricted Data Flow
    Session recording and conduit logging FR6 Timely Response to Events

    Output Interpretation

    • The LFI is the motivation, not the fix; a submission that only patches the portal and leaves the flat network fails, because the grader checks that no direct IT-to-OT path survives
    • Deny-by-default is a specific structure: the grader looks for an explicit default-deny plus minimal justified allows, not a list of blocks
    • The replicated historian is the element students forget; without it, IT still reads into the control zone and a direct path remains
    • The FR mapping is what ties this design to the SL-T gap from Exercise 6.2; an unmapped control reads as a recommendation, not a closed requirement

    Analysis Questions

    1. Why is patching the corpweb LFI not a sufficient fix for the IT/OT boundary?

    Reveal answer

    The LFI is one instance of a class. The next web bug, misconfiguration, or stolen laptop will leak the next credential, and on a flat network that credential reaches a PLC just as easily. The durable fix is architectural: an industrial DMZ where no IT asset has a direct path to OT, so a leaked credential lands on a segment that cannot reach the control zone regardless of how it leaked.

    2. What does a brokered jump host give you that a plain VPN into the OT subnet does not?

    Reveal answer

    A plain VPN drops the user directly onto the control network with whatever credential they hold. A brokered jump host terminates the IT session in the DMZ, demands MFA, opens a separate controlled connection to OT, and records the whole session. The IT credential never reaches the plant, the access is logged, and a single broker is far easier to monitor and revoke than a flat VPN landing zone.

    3. Why does the design replicate the historian into the DMZ instead of letting IT read the plant historian directly?

    Reveal answer

    Any read path from IT into the control zone is also a potential write path and a reconnaissance channel, and it keeps an IT-to-OT conduit open. A one-way push of historian data to a read-only replica in the DMZ lets IT consumers get the trends they need while the live plant historian stays unreachable from IT. The replication is push-only, so the control zone initiates the flow and IT never reaches in.
