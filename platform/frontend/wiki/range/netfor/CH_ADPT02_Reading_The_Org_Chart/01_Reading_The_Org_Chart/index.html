    Exercise 1.2: Reading the Org Chart

    Before You Begin

    Exercise 1.1 introduced raw LDAP queries. They scale poorly. Five queries are fine; five hundred is a chore. BloodHound turns the same data into a graph and lets you ask "who has a path to Domain Admins?" in one Cypher query rather than thirty manual joins.

    In this exercise you will collect data with SharpHound, ingest it into BloodHound CE, and answer four targeted questions about Nordport's privileged group structure. Submit the SHA-1 of the four answers concatenated to retrieve the flag.

    Tools required: bloodhound-python (collector), BloodHound CE GUI, neo4j, a working Cypher console. All are pre-installed on your Kali workstation. Neo4j and BloodHound start automatically when you open the BloodHound shortcut.

    Scenario

    Marcus Bell, your senior consultant, hands you a four-question pop quiz. Each question is something a senior pentester answers from a BloodHound collection in under a minute. He wants to see you do the same.

    The questions:

    1. How many users have a path to Domain Admins (any path, any length, transitive)?
    2. Who is the manager of the manager of the manager of the user priya.ramanathan?
    3. Which user is a member of the most groups (counted transitively)?
    4. Which non-DA user is in the most groups that have local administrator on at least one computer?

    Concatenate the four answers in order. Take the SHA-1 of the resulting string. Submit the hash to the scoring API on this exercise's network. The scorer returns the flag if all four answers are correct.

    Credentials:

    Username Password
    j.chen Welcome2026#

    Your Objectives

    • Run SharpHound (bloodhound-python) against corp.nordport.local
    • Ingest the JSON collection into BloodHound CE
    • Use the GUI and Cypher console to answer the four questions
    • Compute the SHA-1 of the concatenation
    • Submit the hash to the scoring API and retrieve the flag

    Background: What BloodHound Actually Is

    BloodHound is a graph-database visualization of Active Directory. The collector (SharpHound, or bloodhound-python for the Linux version) reads AD over the same LDAP and SMB interfaces you used in Exercise 1.1. The collected data is loaded into a Neo4j graph database, then a web UI lets you query the graph visually or with Cypher (Neo4j's query language).

    Nodes

    Each AD object is a node in the graph. Common types:

    Node type What it is
    User A domain user account
    Group A security or distribution group
    Computer A domain-joined computer
    OU An organizational unit
    GPO A Group Policy Object
    Domain A domain or trust target

    Edges

    Each relationship between objects is an edge. Common edges relevant to attack paths:

    Edge Meaning
    MemberOf The source is a member of the target group
    AdminTo The source has local admin on the target computer
    CanRDP The source can RDP to the target computer
    GenericAll The source has full control on the target
    GenericWrite The source can write any property on the target
    WriteDACL The source can change the target's permissions
    WriteOwner The source can take ownership of the target
    ForceChangePassword The source can reset the target's password without knowing it
    AddMember The source can add members to the target group
    AllowedToDelegate The source is configured to delegate to the target
    AllowedToAct The source is in the target's RBCD list
    HasSession The source user has an active session on the target computer

    The power of the graph is composition: an attacker walks edges from a starting node (j.chen) to a goal node (Domain Admins) regardless of how many hops are required. BloodHound does the path search; you read off the answer.

    A Path is a Chain of Edges

    The diagram below shows what a typical attack path looks like inside the graph. Reading left to right, each arrow is a single privilege you abuse to take the next hop.

    flowchart LR
    JC["User: j.chen<br/>(your foothold)"]
    G1["Group: HelpDesk-Admins"]
    SVC["User: svc-sql<br/>(Kerberoastable)"]
    SQL["Computer: sql01<br/>(local admin)"]
    DA["Group: Domain Admins"]
    JC -->|MemberOf| G1
    G1 -->|ForceChangePassword| SVC
    SVC -->|AdminTo| SQL
    SQL -->|HasSession| DA

    A few seconds of Cypher gives you the same answer as an hour of LDAP filtering plus mental graph composition. That speed multiplier is why every modern AD assessment starts with BloodHound.

    BloodHound CE GUI

    Launch with the desktop shortcut BloodHound CE on your Kali. The first run wizard creates an admin account on the embedded Neo4j; remember the password. The web interface opens at http://localhost:8080.

    To ingest your collection, click Upload Files and select the zip from bloodhound-python. The dashboard updates within seconds.

    Cypher

    The Neo4j query language. Examples (run from the Cypher tab in the BloodHound UI):

    // All users in the domain
MATCH (u:User) RETURN u.name LIMIT 25

    // All users transitively in Domain Admins (canonical BloodHound CE form)
MATCH (u:User)-[:MemberOf*1..]->(m:Group) WHERE m.name = 'DOMAIN ADMINS@CORP.NORDPORT.LOCAL' RETURN u

    // Path from j.chen to Domain Admins (canonical form)
MATCH p=shortestPath((n:User)-[*1..]->(m:Group)) WHERE n.name = 'J.CHEN@CORP.NORDPORT.LOCAL' AND m.name = 'DOMAIN ADMINS@CORP.NORDPORT.LOCAL' RETURN p

    A note on case: BloodHound stores names UPPERCASE with the domain in UPN form. j.chen becomes J.CHEN@CORP.NORDPORT.LOCAL and Domain Admins becomes DOMAIN ADMINS@CORP.NORDPORT.LOCAL in the graph. The official BloodHound CE Cypher form (mirrored above and in every Privilege Zones rule) uses WHERE <var>.name = '...' rather than embedding the name in the node pattern.

    Walkthrough

    Step 1: Launch the Exercise

    Launch Reading the Org Chart in the platform. Note the DC IP and the scorer URL displayed in the Active Lab View. The scorer is a small HTTP service running on the same lab network.

    Step 2: Pre-flight DNS Sanity Check

    bloodhound-python reads the DC's dnsHostName attribute and then attempts to resolve that name to an IP. If resolution fails the collector aborts with AttributeError: 'NoneType' object has no attribute 'extend'. A 30-second sanity check now saves a confused traceback later.

    Get the DC IP from your Active Lab View (typically shown as corp-dc01: 10.100.X.10 where X varies per spawn). Substitute it into DC_IP= below. Auto-derivation from Kali's interfaces is unreliable because Kali may sit on a routed lab-management subnet rather than directly on the lab subnet itself.

    Kali - Confirm the DC's FQDN resolves

    DC_IP=10.100.2.10   # <-- REPLACE with your DC IP from Active Lab View

DC_FQDN=$(ldapsearch -x -LLL -H "ldap://$DC_IP" -s base "(objectClass=*)" dnsHostName 2>/dev/null | awk '/dnsHostName:/{print $2; exit}')
echo "DC reports FQDN: $DC_FQDN"
getent hosts "$DC_FQDN" >/dev/null && echo "Resolves OK" || { echo "Resolution failed; adding /etc/hosts entry as fallback"; echo "$DC_IP $DC_FQDN ${DC_FQDN%%.*}" | sudo tee -a /etc/hosts; }
    Token Effect
    DC_IP=10.100.2.10 The DC IP from the Active Lab View. Edit this value before pasting.
    ldapsearch ... -s base "(objectClass=*)" dnsHostName Read the rootDSE attribute that names the DC's FQDN.
    awk '/dnsHostName:/{print $2; exit}' Extract the value from LDIF output.
    getent hosts "$DC_FQDN" Check whether the system resolver knows the name.
    Conditional sudo tee -a /etc/hosts Add a fallback mapping when the DC's own DNS does not have an A record for itself.

    On a properly built lab the DC's DNS already has the matching A record and the script reports Resolves OK. If the lab was built before the DNS-fix patch (2026-04-26), you will see the /etc/hosts fallback fire once.

    Step 3: Run the Collector

    The SharpHound family of collectors enumerates AD objects, ACLs, sessions, and trusts via LDAP and SMB, packages the result as a set of JSON files, and zips them for ingestion. We use the Linux-native variant (bloodhound-python) because we are operating from Kali; the Windows variant (SharpHound.exe) is only useful when you have a Windows foothold.

    Kali - Run bloodhound-python

    mkdir -p ~/work/adpt-1-02 && cd ~/work/adpt-1-02
bloodhound-python -u j.chen -p 'Welcome2026#' \
  -d corp.nordport.local -ns <dc_ip> \
  -c All --zip

    What each option does:

    • -u j.chen username for the LDAP/SMB binds. The collector authenticates once and reuses the session for every object.
    • -p 'Welcome2026#' password. Quote it so shell special characters do not break it.
    • -d corp.nordport.local domain (and Kerberos realm).
    • -ns <dc_ip> nameserver. The collector resolves hostnames during enumeration; pointing at the DC ensures every internal name resolves correctly.
    • -c All collection methods. Equivalent to -c Group,LocalAdmin,Session,Trusts,ACL,Container,RDP,ObjectProps,LoggedOn,DCOM,PSRemote. Each method exercises a different AD primitive: Group reads memberships, ACL reads object DACLs, Session and LoggedOn enumerate active user sessions on remote hosts, Trusts reads domain trust objects, etc.
    • --zip bundle the resulting JSON files into a single timestamped .zip. The zip is what BloodHound CE wants to ingest.

    What the output looks like (per object class):

    INFO: Found AD domain: corp.nordport.local
INFO: Connecting to LDAP server: corp-dc01.corp.nordport.local
INFO: Found 1 domains
INFO: Found 1 domains in the forest
INFO: Found 87 users
INFO: Found 42 groups
INFO: Found 4 computers
INFO: Connecting to GC LDAP server...
INFO: Done in 00M 28S

    Common gotchas:

    • If Connecting to LDAP server hangs, the -ns value is wrong (DNS resolution is failing). Try the DC's IP literally instead of corp-dc01.
    • -c LoggedOn is the noisiest collection method (it queries every reachable host's session list) and triggers ITDR products like Microsoft Defender for Identity. For stealth, use -c Group,LocalAdmin,Session,Trusts,ACL,Container,RDP,ObjectProps (drop LoggedOn and DCOM).

    Kali - Start BloodHound CE

    sudo bloodhound cli start

    What this does:

    • Starts the embedded Postgres (BloodHound metadata store), Neo4j (graph database holding the AD model), and the BloodHound API + UI containers via docker-compose under the hood.
    • The first startup creates the local user and admin password; copy these from the terminal output (you will not see them again unless you sudo bloodhound cli reset-admin-password).
    • sudo is required because BloodHound CE manages docker containers in the system docker socket.

    Wait for the line BloodHound CE is ready at http://localhost:8080. Open that URL in Firefox.

    Step 5: Answer Question 1 (Paths to Domain Admins)

    BloodHound CE ships a curated library of attack-path detection rules under Privilege Zones -> All Rules -> Default Routes. Each rule is a pre-saved Cypher query that runs against the loaded graph and returns matching paths. Browse the rules to see what BloodHound's authors consider high-value attack patterns; run any of them to populate the graph view.

    For an exact COUNT (rather than the visual graph), paste a custom query into the Cypher box on the Explore page.

    Confirm ingest before querying

    Both the curated rules AND any custom Cypher return "No results match your criteria" when the graph is empty. After uploading the zip, check the four dashboard tiles at the top of the Explore page (Users / Computers / Groups / OUs). If they all show 0, the ingest has not completed: gear icon -> File Ingest -> UPLOAD FILE(S) -> select the zip -> wait for Ready -> Running -> Complete (60-90s).

    First, confirm the Domain Admins group node exists in the graph by SID. Domain Admins always has a Relative Identifier (RID) of 512, regardless of domain name or BloodHound version. The query below finds it without depending on case-sensitive name matching:

    BloodHound CE Cypher - paths from any user to Domain Admins

    MATCH p=shortestPath((n:User)-[*1..]->(m:Group)) WHERE m.name = 'DOMAIN ADMINS@CORP.NORDPORT.LOCAL' RETURN p

    This is the canonical form from the official BloodHound CE docs (https://bloodhound.specterops.io/analyze-data/bloodhound-gui/cypher-search). It returns every shortest path from any User to the Domain Admins group, regardless of edge type, with no depth cap.

    What each piece of the query does:

    • MATCH p=shortestPath(...) one MATCH that binds the path to variable p and uses Cypher's built-in shortestPath() function. BHCE renders the path in the graph view.
    • (n:User)-[*1..]->(m:Group) the path pattern. (n:User) is any User; (m:Group) is any Group; [*1..] means "1 or more hops via any edge type, no upper bound" (BHCE's planner handles the unbounded case efficiently for this idiom).
    • WHERE m.name = 'DOMAIN ADMINS@CORP.NORDPORT.LOCAL' restricts m to the Domain Admins group by exact name. BloodHound stores group names as <UPPERCASE NAME>@<UPPERCASE DOMAIN>; this string must match exactly.
    • RETURN p returns the path. The graph view renders the result; the result count above the canvas is the integer answer to Question 1.

    Look at the result indicator above the graph (typically "X paths" or "X results"). That number is your Question 1 answer. Save it for the SHA-1 calculation in Step 9.

    BloodHound CE Cypher quirks

    BHCE 5.x+'s Cypher parser is stricter than Neo4j Browser, AND its result panel does not render scalar columns. Two rules cover almost every failure mode:

    • Always return paths or nodes, never scalars. RETURN p, RETURN u, or UNWIND ... RETURN path draws on the canvas. RETURN COUNT(...) or RETURN u.name, COUNT(g) returns numbers and strings the canvas cannot draw, and the GUI shows "No results match your criteria" with no visible result panel. Aggregate inside a WITH clause and return the resulting NODE or PATH.
    • shortestPath() on a single line, one MATCH per query. Line breaks inside shortestPath(), or chaining a second MATCH without an intervening WITH, produce no viable alternative at input errors. Paste each query as a single logical line.

    Step 6: Answer Question 2 (Manager-of-the-manager-of-the-manager)

    The Manager attribute lives on each user object in AD as the LDAP manager attribute (a DN pointing at the next user up the chain). BloodHound CE 5.x represents this as a HasManager edge ONLY when collected by SharpHound CE (Windows-only). The Linux bloodhound-python collector that Kali ships does NOT surface manager as a graph edge, so a [:HasManager] Cypher query returns nothing on this lab.

    The data is on the DC regardless of what BloodHound captured. Walk the chain via LDAP directly.

    PASTE THIS IN YOUR KALI TERMINAL, NOT BLOODHOUND

    The script below is bash (#!/bin/bash-style), not Cypher. Open your Kali shell terminal, not the BloodHound web UI's Cypher box. If you paste bash into BloodHound you will see errors like mismatched input 'DC_IP', token recognition error at: '\j', etc.

    Kali shell (NOT BloodHound) - walk Priya's manager chain via LDAP

    Set DC_IP to the value shown in your Active Lab View. Each statement is one short line with ; separators - no \ continuations to break on paste:

    DC_IP=10.100.2.10   # <-- REPLACE with your DC IP from Active Lab View
CRED='CORP\j.chen'; PASS='Welcome2026#'; BASE='DC=corp,DC=nordport,DC=local'

walk_manager() { ldapsearch -x -LLL -o ldif-wrap=no -H "ldap://$DC_IP" -D "$CRED" -w "$PASS" -b "$1" -s base manager 2>/dev/null | awk '/^manager: /{sub(/^manager: /,""); print; exit}'; }

PRIYA_DN=$(ldapsearch -x -LLL -o ldif-wrap=no -H "ldap://$DC_IP" -D "$CRED" -w "$PASS" -b "$BASE" "(sAMAccountName=priya.ramanathan)" dn 2>/dev/null | awk '/^dn: /{sub(/^dn: /,""); print; exit}')
echo "Priya DN: $PRIYA_DN"

M1=$(walk_manager "$PRIYA_DN"); echo "Priya -> $M1"
M2=$(walk_manager "$M1");        echo "       -> $M2"
M3=$(walk_manager "$M2");        echo "       -> $M3"

ldapsearch -x -LLL -o ldif-wrap=no -H "ldap://$DC_IP" -D "$CRED" -w "$PASS" -b "$M3" -s base sAMAccountName 2>/dev/null | awk '/^sAMAccountName: /{sub(/^sAMAccountName: /,""); print "Q2 answer: "$0; exit}'
    Token Effect
    DC_IP=10.100.2.10 The DC IP from the Active Lab View. Edit before pasting; auto-derivation is unreliable because Kali may sit on a routed lab-management subnet rather than the lab subnet itself.
    -o ldif-wrap=no Tell ldapsearch not to wrap long DN values across lines. Without this, AD users with long full names get DNs split mid-string and the awk truncates.
    walk_manager() Helper that takes a DN and returns the value of its manager attribute.
    ldapsearch -b "$1" -s base manager Read the manager attribute on the object whose DN is $1.
    awk '/^manager: /{sub(/^manager: /,""); print; exit}' Strip the manager: prefix and print the rest of the line. The naive print $2 form takes only the first whitespace-separated field, which truncates DNs that contain spaces (e.g., CN=Priya Ramanathan,... becomes CN=Priya).

    The script prints each intermediate DN as it walks up Priya's manager chain, then resolves the third-hop DN to its sAMAccountName. The Q2 answer: line is what you submit (lowercased, before @). Expect: r.kowalski.

    If Derived DC IP is empty or wrong

    Hardcode it from the Active Lab View. Replace the first line with:

    DC_IP=<the value you see in the Active Lab View>; CRED='CORP\j.chen'; PASS='Welcome2026#'; BASE='DC=corp,DC=nordport,DC=local'

    Other failure modes:

    • Can't contact LDAP server (-1) - DC IP is wrong (use Active Lab View) or LDAP/389 is firewalled.
    • Bind succeeds but Priya DN empty - the user account priya.ramanathan may have a different SAM in your seed; run ldapsearch -x -LLL -H "ldap://$DC_IP" -D "$CRED" -w "$PASS" -b "$BASE" "(sAMAccountName=priya*)" sAMAccountName dn to find the actual SAM.
    • Output shows command not found on filter strings - the \ continuations from a hand-edited copy got partially preserved. Paste the verbatim version above; every command sits on one logical line.
    Why not BloodHound for this question?

    SharpHound CE (the new Windows-only collector for BHCE 5.x) emits HasManager edges via the ObjectProps collection method. The Linux bloodhound-python Kali ships does not. To see manager edges in BHCE you would need to run SharpHound from a Windows host; LDAP is faster and works on the credential you already have.

    Step 7: Answer Question 3 (User with the Most Groups, Transitive)

    Group nesting (a group that contains other groups as members) is what makes counting "transitive" memberships interesting. A user might be DIRECTLY in 3 groups but TRANSITIVELY in 30 because of nesting. Cypher's *1.. syntax does the chain traversal natively.

    In BHCE 5.x+, scalar Cypher returns (RETURN u.name, COUNT(g)) do not render in the graph canvas. The query below uses the canonical "find the winner, then return its membership paths as a graph" pattern: aggregate to find who has the most groups, then UNWIND the collected paths so the canvas draws the user node and all its group connections. Read the answer off the single User node label.

    BloodHound Cypher - top user by transitive group memberships, rendered as a graph

    Paste as one logical line in the Cypher search box.

    MATCH (u:User)-[:MemberOf*1..]->(g:Group) WHERE u.enabled = true WITH u, COUNT(DISTINCT g) AS gc ORDER BY gc DESC LIMIT 1 MATCH p=(u)-[:MemberOf*1..]->(:Group) RETURN p

    What each piece does:

    • MATCH (u:User)-[:MemberOf*1..]->(g:Group) walk every user-to-group membership chain. *1.. traverses the full nesting chain.
    • WITH u, COUNT(DISTINCT g) AS gc ORDER BY gc DESC LIMIT 1 aggregate to find the user with the highest distinct-group count, then narrow the working set to just that one user.
    • MATCH p=(u)-[:MemberOf*1..]->(:Group) RETURN p re-walk the paths from the winning user and return them as graph data so the canvas draws them.

    The canvas draws ONE central User node fanning out into the group hierarchy. The user's sAMAccountName (lowercased, no @DOMAIN suffix) is your Question 3 answer.

    Why two MATCH clauses? BHCE's Cypher REST serialization will not return RETURN p correctly when p was collected and unwound through an aggregation. Aggregating to find the winner with WITH ... LIMIT 1, then re-matching the paths from that single bound user, is the idiom that draws on the canvas reliably.

    Step 8: Answer Question 4 (Non-DA user with the most ACL-based control over other principals)

    In modern AD, the most dangerous unprivileged accounts are usually NOT the ones with AdminTo edges to workstations. They're the ones who, via group membership, hold rewritable ACLs (GenericAll, WriteOwner, WriteDacl, ForceChangePassword, GenericWrite, AddSelf) over other users, groups, or computers. Those edges let an attacker pivot ownership of a target object without needing local admin on any host. BloodHound surfaces them as colored edges between principals.

    Question 4 finds the non-Domain-Admin user whose group memberships transitively grant control over the most distinct target principals.

    BloodHound Cypher - non-DA user with the most ACL reach, rendered as a graph

    Paste as one logical line.

    MATCH (u:User)-[:MemberOf*1..]->(g:Group)-[:GenericAll|WriteDacl|WriteOwner|ForceChangePassword|GenericWrite|AddSelf|AllowedToDelegate]->(target) WHERE u.enabled = true AND NOT (u)-[:MemberOf*1..]->(:Group {name:'DOMAIN ADMINS@CORP.NORDPORT.LOCAL'}) WITH u, COUNT(DISTINCT target) AS reach ORDER BY reach DESC LIMIT 1 MATCH p=(u)-[:MemberOf*1..]->(:Group)-[:GenericAll|WriteDacl|WriteOwner|ForceChangePassword|GenericWrite|AddSelf|AllowedToDelegate]->() RETURN p

    What this query does:

    • First MATCH walks every user-to-group-to-target ACL chain.
    • WHERE u.enabled = true AND NOT (u)-[:MemberOf*1..]->(:Group {name:'DOMAIN ADMINS@...'}) excludes disabled accounts and anyone transitively in Domain Admins.
    • WITH u, COUNT(DISTINCT target) AS reach ORDER BY reach DESC LIMIT 1 aggregates to find the single user with the largest ACL reach.
    • Second MATCH re-walks the paths from that one user and returns them as graph data so the canvas draws everything.

    The canvas draws ONE central User node, the group(s) they're in, and the targets those groups can take over. The user's sAMAccountName is your Question 4 answer.

    Why this matters operationally: a single mis-scoped helpdesk group with WriteOwner on three sensitive accounts gives every member of that group a path to compromise those accounts. Find the user with the largest such fan-out and you've found the most leveraged unprivileged identity in the domain.

    Step 9: Compute the SHA-1 Hash

    The scoring API expects the SHA-1 of your four answers concatenated in Q1+Q2+Q3+Q4 order. Producing a hash (rather than four free-text answers) means the API can validate without revealing the right answers in error messages.

    Kali - Compute the SHA-1

    Q1='27'                    # replace with your number
Q2='domain admins'         # replace
Q3='j.chen'                # replace
Q4='j.chen'                # replace
echo -n "${Q1}${Q2}${Q3}${Q4}" | sha1sum | awk '{print $1}'

    What each piece does:

    • Q1='27' etc.: shell variables holding your answers as strings. Variable assignments must have no spaces around =.
    • echo -n "..." print the concatenation WITHOUT a trailing newline. The -n matters: SHA-1 of the same string with vs. without a newline produces totally different hashes; the scoring API computes its hash without the newline, so you must too.
    • ${Q1}${Q2}${Q3}${Q4} parameter expansion concatenated with no separator. The order matters; the scorer assumes Q1, Q2, Q3, Q4 in that exact order.
    • | sha1sum pipe to the SHA-1 hasher. Output looks like <40-hex-chars> - (the trailing dash means "stdin").
    • | awk '{print $1}' keep only the first whitespace-separated field (the hash), drop the dash.

    Final output is a 40-character hex string. Copy it for Step 9.

    Step 10: Submit to the Scorer

    The scorer is a small HTTP service running on the same lab network as your Kali. Its IP is shown in the Active Lab View. The /submit endpoint validates your four answers and returns the flag if all match.

    Kali - Submit answers to the scorer

    curl -s -X POST http://<scorer_ip>:8080/submit \
  -d "q1=${Q1}" -d "q2=${Q2}" -d "q3=${Q3}" -d "q4=${Q4}"

    What each option does:

    • -s silent. Suppresses curl's progress meter so the response prints cleanly. Useful when piping the output to jq or saving to a file.
    • -X POST use the HTTP POST method (curl defaults to GET). The scorer expects POST.
    • http://<scorer_ip>:8080/submit the scoring endpoint. Replace <scorer_ip> with the IP from the Active Lab View.
    • -d "q1=${Q1}" form data field. Each -d adds one URL-encoded form field. Multiple -d flags concatenate with & automatically. Equivalent: -d "q1=...&q2=...&q3=...&q4=..." as one big string.

    On success the response JSON includes a flag key holding the OCR{...} value to submit to the platform. On failure the JSON lists which answer numbers were wrong (e.g. {"correct":[true,true,false,true]}).

    Blue Team Perspective

    Microsoft Defender for Identity (MDI) treats SharpHound-style collection as a top-priority signal. Once a single account starts pulling object properties, ACLs, sessions, and group membership across the entire forest in a few seconds, MDI fires the canonical "Reconnaissance using directory services queries" alert. The detection pivots are listed below.

    Activity Signal
    Bulk LDAP property reads MDI alert: "Reconnaissance using directory services queries"
    Session enumeration via SAMR/NetSessionEnum MDI alert: "User and IP address reconnaissance (SMB)"
    Cross-DC kerberoast of every SPN Event 4769 spike on each DC
    Wide LDAP queries Diagnostic event 1644 with high searchSize

    What collectors look like to a SOC

    SharpHound finishes a small domain in under a minute and emits a recognizable burst pattern: a few hundred 4624 logon events, thousands of 4662 directory-access events, and a tail of 5145 (network share access) on every DC. Splitting the collection into multiple sessions across hours can reduce the burst signature, but defenders running MDI on the DC catch the pattern even when the collection is paced.

    Hardening Note

    You cannot kill BloodHound without breaking AD itself; defenders settle for raising the cost of the collection and shrinking the resulting graph. The list below is the hardening menu most blue teams reach for.

    Mitigations that change BloodHound output

    • Deploy Microsoft Defender for Identity on every DC. Detection accuracy is high and the SOC sees the collector immediately.
    • Disable anonymous SAMR (Network access: Restrict clients allowed to make remote calls to SAM GPO). Forces collectors to authenticate to enumerate sessions.
    • Remove Authenticated Users read on Tier 0 OUs so privileged accounts do not appear in the graph at all.
    • Audit and prune nested group membership; the longer the path, the more rope BloodHound finds for an attacker.
    • Set dsHeuristics bit 0 to 1 to disable anonymous LDAP bind.
    • Ship DC Security and Directory Services logs to a SIEM with high-cardinality query alerts on event 1644.

    Analysis Questions

    1. The collection methods passed to SharpHound differ in noise level. Session collects active user sessions, which requires admin SMB access to remote hosts. Why does collecting Session matter for offensive planning, and what is the noisier alternative?

    Reveal Answer

    Session populates HasSession edges between users and computers. Knowing where a Domain Admin currently has an active session is the difference between a clean attack path (kerberoast a service account that DA logs into) and a broken one (the DA never logs into anything reachable). The noisier alternative is LoggedOn, which queries each remote host for its session list via SAMR/NetSessionEnum. LoggedOn finds users who do not currently have an active session but have logged on recently, but it makes a connection to every computer in the collection set, which is loud. Operators usually run Session on the first pass and only escalate to LoggedOn when the path search needs more data.

    2. Why does BloodHound store object names UPPERCASE in the graph, and what gotcha does that introduce when writing Cypher queries?

    Reveal Answer

    BloodHound normalizes names to UPPERCASE with the domain in UPN form for case-insensitive matching: AD itself treats j.chen and J.CHEN as the same identity, but Neo4j is case-sensitive by default. By forcing UPPERCASE during ingest, BloodHound side-steps this. The gotcha: when you copy a username from another tool (rpcclient, ldapsearch) and paste it into a Cypher query, you must uppercase it and append @DOMAIN or your query returns no results. A common mistake is searching for 'j.chen' instead of 'J.CHEN@CORP.NORDPORT.LOCAL' and concluding the user does not exist. Use the BloodHound search bar to find the canonical name first, then copy it into Cypher.

    3. The official BloodHound CE docs use [*1..] (unbounded depth) in shortestPath(). Why is that safe in BHCE when unbounded path searches are notorious memory hogs?

    Reveal Answer

    Cypher's shortestPath() function is special-cased in the planner: it terminates as soon as the first matching path is found, even with unbounded depth. The unbounded [*1..] does NOT mean "search every possible path"; it means "find the shortest one, however many hops it takes". Because shortestPath() is bounded by the actual minimum, BHCE's planner explores at most the diameter of the reachable graph rather than every possible path. That makes [*1..] perfectly safe for shortestPath(). Bounded depth ([*1..15]) is only useful for allShortestPaths() or unbounded path enumeration, not for finding a single shortest path. The BHCE Privilege Zones rules all use [*1..] for this reason.

    Key Takeaways

    • BloodHound turns LDAP enumeration into a graph. The collector reads the same data ldapsearch reads; the visualization is the difference.
    • Names in the BloodHound graph are stored UPPERCASE with @DOMAIN.TLD; raw lowercase usernames will not match in Cypher.
    • BloodHound CE's curated rule library lives under Privilege Zones -> All Rules -> Default Routes; each rule is a pre-saved Cypher query.
    • Canonical BHCE Cypher pattern (per the official docs): MATCH p=shortestPath((n:User)-[*1..]->(m:Group)) WHERE m.name = '<NAME>@<DOMAIN>' RETURN p is the workhorse for any attack-path question.
    • [*1..] (unbounded) is safe inside shortestPath(); the planner returns at the first match. Avoid chaining MATCH clauses without WITH; keep shortestPath() on a single line; scalar RETURN values only show in the Table view tab.

    Spaced Repetition

    Card 1: SharpHound Linux Collection

    Q: Write the bloodhound-python command to collect every method against corp.local at DC 10.10.10.10 as j.smith / Pass#.

    Answer 
    bloodhound-python -u j.smith -p 'Pass#' \
  -d corp.local -ns 10.10.10.10 \
  -c All --zip

    -c All enables Group, LocalAdmin, Session, Trusts, ACL, Container, RDP, ObjectProps, LoggedOn, DCOM, PSRemote. --zip bundles the JSON outputs.

    Card 2: BloodHound Path Cypher

    Q: Write the Cypher query to find the shortest path from user j.smith@corp.local to the Domain Admins group at corp.local.

    Answer 
    MATCH p=shortestPath((n:User)-[*1..]->(m:Group)) WHERE n.name = 'J.SMITH@CORP.LOCAL' AND m.name = 'DOMAIN ADMINS@CORP.LOCAL' RETURN p

    Canonical BloodHound CE form (matches the official docs at bloodhound.specterops.io/analyze-data/bloodhound-gui/cypher-search). Single MATCH, single WHERE with AND, RETURN p so the graph view renders it. Names are UPPERCASE with @DOMAIN.TLD suffix. Keep the entire query on one logical line; pasted line wraps inside the WHERE string literal break the comparison.

    Card 3: BloodHound Edges to Memorize

    Q: Name five BloodHound edge types that represent direct privilege grants and explain what each enables.

    Answer

    GenericAll; full control over the target (you can do anything to it). GenericWrite; write any property (set SPNs, change membership). WriteDACL; modify the target's ACL (add your own grant). WriteOwner; take ownership, then grant yourself further rights. ForceChangePassword; reset the target user's password without knowing the old one. Honorable mention: AddMember (add yourself to a group) and AllowedToAct (RBCD trust).

    Card 4: Why Sessions Matter

    Q: A BloodHound collection without Session data is missing what attack signal, and how does that change planning?

    Answer

    Session populates HasSession edges showing which users currently have an active session on which computer. Without it, you cannot tell where a Domain Admin currently is, which means kerberoast / overpass-the-hash plans cannot prioritize accounts whose tickets are sitting in memory on reachable hosts. Operators who skip Session end up with attack paths that look great on paper but require waiting for the right user to log on to the right host before they execute.
