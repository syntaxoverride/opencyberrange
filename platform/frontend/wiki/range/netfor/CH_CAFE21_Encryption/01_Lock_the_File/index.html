    Objective

    Learn and practice file encryption using OpenSSL. You will encrypt files using both symmetric (AES) and asymmetric (RSA) encryption, understand the strengths and limitations of each approach, and learn why real-world systems use both together (the hybrid approach that powers TLS/HTTPS).

    Difficulty: Beginner Estimated time: 60 minutes

    Section 1: What Is Encryption?

    The Lockbox Analogy

    Encryption is like putting a letter in a lockbox. Anyone can see the lockbox exists: they can hold it, weigh it, even shake it. But only someone with the key can open it and read what's inside.

    When you visited the Bean & Byte Cafe's network in Phase 2, you captured traffic from the POS terminal. The transaction data, customer names, card numbers, purchase totals, was all in plaintext. That means anyone who intercepted the traffic could read it, just like reading a postcard as it passes through the mail system.

    Encryption solves this. It transforms readable data (plaintext) into unreadable gibberish (ciphertext). Only someone with the correct key can reverse the transformation and recover the original data.

    Why This Matters for the Cafe

    Think back to the POS transaction log you captured in Phase 2:

    TXN-001  2026-03-10 07:12  Latte (Large)  $5.75  VISA ****4821

    The POS terminal transmitted that data in cleartext. An attacker running a MITM attack (like the ARP spoofing from Phase 7) could read every transaction. If the data had been encrypted, the attacker would see something like:

    U2FsdGVkX1+J7QKm3v8h2xR9dZxF0P3qTk5LmNwA6Bc=

    Completely unreadable without the key.

    Two Types of Encryption

    There are two fundamental approaches to encryption, each with different strengths:

    Symmetric Encryption: One Key Does Both

    Analogy: Imagine a padlock where the same key both locks and unlocks it. You lock your diary with the key, and anyone who has a copy of that same key can unlock it.

    • How it works: One secret key encrypts the data. The same key decrypts it.
    • Strengths: Very fast. Can encrypt files of any size.
    • Weakness: How do you safely share the key? If you send the key over the network, an attacker could intercept it, and then they can decrypt everything. Cryptographers call this the key distribution problem.
    • Common algorithms: AES-128, AES-256, DES (old, insecure), 3DES

    Asymmetric Encryption: Two Keys Work Together

    Analogy: Imagine a mailbox on the street. Anyone can drop a letter in through the slot (that's the public key, it only locks/encrypts). But only the mailbox owner has the key to open the door and retrieve the letters (that's the private key, it unlocks/decrypts).

    • How it works: Two mathematically linked keys are generated together. The public key encrypts data. Only the corresponding private key can decrypt it.
    • Strengths: Solves the key distribution problem. You can share your public key with the whole world: it can only encrypt, not decrypt.
    • Weakness: Much slower than symmetric encryption. Can only encrypt data smaller than the key size.
    • Common algorithms: RSA, ECC (Elliptic Curve)

    Step 4: Generate a Random AES Key

    Before you can encrypt, you need a key. AES-128 uses a 128-bit key, which is 16 bytes:

    openssl rand -out my_aes_key 16

    What this does:

    Part Meaning
    openssl rand Generate cryptographically random bytes
    -out my_aes_key Save the random bytes to a file called my_aes_key
    16 Generate 16 bytes (128 bits): the key size for AES-128

    Why 16 bytes?

    AES comes in three flavors: AES-128 (16-byte key), AES-192 (24-byte key), and AES-256 (32-byte key). The number refers to the key length in bits. Longer keys are harder to brute-force. AES-128 is considered secure for most purposes: brute-forcing it would take longer than the age of the universe with current technology.

    You can verify the key file exists:

    ls -la my_aes_key
    Expected Output 
    -rw------- 1 crypto crypto 16 Mar 19 12:00 my_aes_key

    The file is exactly 16 bytes: your AES-128 encryption key. The key file contains raw binary data, so cat would show garbled characters.

    Step 5: Encrypt the File

    Now encrypt the customer data using AES-128-CBC:

    openssl enc -aes-128-cbc -base64 -e -kfile my_aes_key -in /data/customer_data.txt -out customer_encrypted.enc

    What every flag means:

    Flag Meaning
    openssl enc Use OpenSSL's symmetric encryption tool
    -aes-128-cbc Algorithm: AES with 128-bit key in CBC (Cipher Block Chaining) mode
    -base64 Encode the output as Base64 text (readable characters instead of raw binary)
    -e Encrypt (as opposed to -d for decrypt)
    -kfile my_aes_key Read the encryption key from the file my_aes_key
    -in /data/customer_data.txt Input file: the plaintext to encrypt
    -out customer_encrypted.enc Output file: where to write the ciphertext

    What is CBC mode?

    CBC (Cipher Block Chaining) is a mode of operation for block ciphers. AES encrypts data in 16-byte blocks. In CBC mode, each block of plaintext is XORed with the previous block's ciphertext before being encrypted. The chaining means identical plaintext blocks produce different ciphertext blocks, making pattern analysis much harder for an attacker.

    Step 6: Try to Read the Encrypted File

    Now look at what an attacker would see if they captured this file:

    cat customer_encrypted.enc
    Expected Output 
    U2FsdGVkX19kYmR3bHpwZ3J4dGtscnF2...
aW5nIHRoZSBCZWFuICYgQnl0ZSBDYWZl...
MjAyNi0wMy0xMCAwNzoxMiAgTGF0dGUg...
...
(several lines of Base64-encoded ciphertext)

    Encrypted data looks like random gibberish. The original transaction records, card numbers, amounts, everything, are now completely unreadable. An attacker running a MITM attack would capture this gibberish and have no way to recover the original data without your key.

    Step 7: Decrypt the File

    Now prove you can recover the original data:

    openssl enc -aes-128-cbc -base64 -d -kfile my_aes_key -in customer_encrypted.enc -out customer_decrypted.txt

    Notice the only change from the encrypt command: -d (decrypt) instead of -e (encrypt). Everything else stays the same: same algorithm, same key, same base64 encoding.

    Step 8: Verify the Decryption

    Compare the decrypted file to the original:

    diff /data/customer_data.txt customer_decrypted.txt
    Expected Output 
    (no output)

    No output from diff means the files are identical. Your decryption perfectly recovered the original plaintext.

    You can also view the decrypted file to confirm:

    cat customer_decrypted.txt

    You should see the exact same POS transaction log you started with.

    The Key Distribution Problem

    You encrypted a file and decrypted it with the same key. But consider the following scenario:

    The cafe owner wants to send the encrypted POS backup to the NAS for safe storage. The NAS needs the AES key to decrypt it. How do you send the key?

    • Option 1: Send the key over the network. But if an attacker is watching (like your MITM from Phase 7), they capture the key, and now they can decrypt everything.
    • Option 2: Walk the key over on a USB drive. Secure, but impractical for automated systems.
    • Option 3: Use asymmetric encryption to securely transmit the key. Asymmetric encryption is the solution.

    The key distribution problem is exactly why cryptographers developed asymmetric encryption.

    Section 3: Asymmetric Encryption with OpenSSL

    Asymmetric encryption uses two keys: a public key that anyone can have, and a private key that must be kept secret. What one key encrypts, only the other can decrypt.

    The Mailbox Analogy

    Think of a mailbox on the street:

    • The mail slot is the public key: anyone can drop a letter in
    • The mailbox door key is the private key: only the owner can open it and read the letters
    • You can tell the whole world where your mailbox is (share your public key) without worrying: all they can do is put letters in, not take them out

    Step 1: Generate an RSA Keypair

    Generate a 4096-bit RSA private key:

    openssl genrsa -out private_key.pem 4096

    What this does:

    Part Meaning
    openssl genrsa Generate an RSA private key
    -out private_key.pem Save the private key to this file
    4096 Key size in bits: 4096 is very secure
    Expected Output 
    Generating RSA private key, 4096 bit long modulus (2 primes)
.......++++
.........................................++++
e is 65537 (0x010001)

    What does 4096 bits mean?

    The key size determines how hard it is to break the encryption. A 4096-bit RSA key means the mathematical problem an attacker would need to solve involves a number with over 1,200 digits. With current technology, brute-forcing a 4096-bit RSA key would take billions of years. For comparison, a 512-bit RSA key was broken in 1999.

    Step 2: Extract the Public Key

    The private key file actually contains both keys. Extract only the public key:

    openssl rsa -in private_key.pem -pubout -out public_key.pem
    Part Meaning
    openssl rsa RSA key management tool
    -in private_key.pem Read from the private key file
    -pubout Output only the public key
    -out public_key.pem Save the public key to this file
    Expected Output 
    writing RSA key

    Step 3: Examine Both Keys

    Look at the public key:

    cat public_key.pem
    Expected Output 
    -----BEGIN PUBLIC KEY-----
MIICIjANBgkqhkiG9w0BAQEFAAOCAg8AMIICCgKCAgEA...
(several lines of Base64-encoded data)
...
-----END PUBLIC KEY-----

    Now look at the private key:

    cat private_key.pem
    Expected Output 
    -----BEGIN PRIVATE KEY-----
MIIJQwIBADANBgkqhkiG9w0BAQEFAASCCS0wggkpAgEA...
(many more lines -- the private key is much longer)
...
-----END PRIVATE KEY-----

    Notice that the private key is much larger than the public key. The private key contains the mathematical components needed for both encryption and decryption, while the public key only contains what's needed for encryption.

    Critical Security Rule

    The public key can be shared with anyone: post it on a website, email it, print it on a business card. It can only encrypt, never decrypt.

    The private key must NEVER be shared. Anyone with the private key can decrypt everything encrypted with the corresponding public key. Treat it like a password.

    Step 4: Encrypt a File with the Public Key

    Encrypt the employee schedule using the public key:

    openssl pkeyutl -encrypt -inkey public_key.pem -pubin -in /data/employee_schedule.txt -out schedule_encrypted.enc
    Flag Meaning
    openssl pkeyutl Public key utility: RSA encrypt/decrypt operations
    -encrypt Perform encryption
    -inkey public_key.pem Use this key for the operation
    -pubin The key file is a public key (not a private key)
    -in /data/employee_schedule.txt Input file to encrypt
    -out schedule_encrypted.enc Output encrypted file

    Note about pkeyutl vs rsautl

    Older tutorials may show openssl rsautl. The rsautl command is deprecated in newer versions of OpenSSL. The modern replacement is openssl pkeyutl, which works with RSA and other key types. Both do the same thing for RSA operations.

    Step 5: Decrypt with the Private Key

    Now decrypt using the private key: the only key that can reverse this:

    openssl pkeyutl -decrypt -inkey private_key.pem -in schedule_encrypted.enc -out schedule_decrypted.txt

    Notice: no -pubin flag this time, because we're using the private key.

    Step 6: Verify

    diff /data/employee_schedule.txt schedule_decrypted.txt
    Expected Output 
    (no output -- files are identical)

    The decryption perfectly recovered the original schedule.

    RSA's Size Limitation

    Try encrypting the larger customer data file with RSA:

    openssl pkeyutl -encrypt -inkey public_key.pem -pubin -in /data/customer_data.txt -out customer_rsa_encrypted.enc
    Expected Output 
    Public Key operation error
...
pkeyutl: Error in encrypt operation

    The command fails because RSA can only encrypt data smaller than the key size. A 4096-bit key can encrypt at most ~470 bytes of data. The customer data file is much larger than that.

    A fundamental limitation of asymmetric encryption: it works great for small pieces of data (like keys), but cannot handle large files.

    Section 4: Why We Use Both: The Hybrid Approach

    You've now seen both types of encryption:

    Type Speed Size Limit Key Distribution
    Symmetric (AES) Very fast No limit Problematic: how to share the key?
    Asymmetric (RSA) Slow ~470 bytes for RSA-4096 Solved: public key can be shared openly

    Each has a critical weakness. But together, they cover each other's gaps.

    The Real-World Solution: Hybrid Encryption

    Here's how real systems combine both:

    1. Generate a random AES key (only 16 or 32 bytes: tiny)
    2. Encrypt the DATA with AES (fast, no size limit)
    3. Encrypt the AES KEY with RSA (the key is tiny enough for RSA)
    4. Send both the encrypted data and the encrypted key

    The recipient uses their RSA private key to decrypt the AES key, then uses the AES key to decrypt the data.

    Walk Through It

    Walk through it step by step:

    Step 1: Generate a fresh AES key:

    openssl rand -out hybrid_aes_key 16

    Step 2: Encrypt the large customer data file with AES:

    openssl enc -aes-128-cbc -base64 -e -kfile hybrid_aes_key -in /data/customer_data.txt -out hybrid_data.enc

    Step 3: Encrypt the tiny AES key with RSA:

    openssl pkeyutl -encrypt -inkey public_key.pem -pubin -in hybrid_aes_key -out hybrid_key.enc

    The AES key is only 16 bytes: well within RSA's size limit.

    Step 4: Now you could safely send hybrid_data.enc and hybrid_key.enc over the network. An attacker who captures both files has:

    • hybrid_data.enc: AES-encrypted data, unreadable without the AES key
    • hybrid_key.enc: the AES key, RSA-encrypted, unreadable without the private key

    Without the RSA private key, the attacker is stuck.

    Step 5: The recipient decrypts the chain:

    openssl pkeyutl -decrypt -inkey private_key.pem -in hybrid_key.enc -out recovered_aes_key

    openssl enc -aes-128-cbc -base64 -d -kfile recovered_aes_key -in hybrid_data.enc -out recovered_data.txt

    Step 6: Verify:

    diff /data/customer_data.txt recovered_data.txt

    No output means perfect recovery through the entire hybrid chain.

    This Is How TLS/HTTPS Works

    Every time you visit a website with https://, your browser performs this exact hybrid approach:

    1. Your browser gets the server's public key (from the TLS certificate)
    2. Your browser generates a random session key (like an AES key)
    3. Your browser encrypts the session key with the server's public key and sends it
    4. Both sides now have the session key and use it for fast symmetric encryption of all data

    The entire process happens in milliseconds, every time, for every HTTPS connection. The concepts you practiced by hand are running billions of times per second across the internet.

    Section 6: Analysis Questions

    Answer these questions in your lab report. Each one connects what you practiced to real-world security concepts.

    Question 1: The MITM Scenario

    You encrypted customer_data.txt with AES-128. Imagine an attacker running the same MITM attack from Phase 7: they're ARP spoofing the crypto-station and capturing all its traffic. They intercept the encrypted file customer_encrypted.enc as it's being sent to the NAS.

    • Can the attacker read the transaction data? Why or why not?
    • What specific piece of information would the attacker need to decrypt it?
    • If the AES key were also sent over the network in plaintext, would the encryption still protect the data?

    Question 2: RSA Key Strength

    You generated a 4096-bit RSA key. RSA security depends on the difficulty of factoring large numbers: specifically, the product of two large prime numbers.

    • Why is a 4096-bit RSA key considered secure today?
    • The largest RSA key ever publicly factored was 829 bits (RSA-250) in 2020, using a cluster of computers over several years. How many bits is your key, and roughly how much harder is it to factor?
    • Quantum computers threaten RSA encryption. Research: what key size would be needed to resist quantum attacks? (Hint: the answer might surprise you.)

    Question 3: The Trade-offs

    The cafe owner asks: "If encryption is so good, why isn't everything encrypted? Why don't we encrypt every file on every computer?"

    Write a response addressing:

    • Performance cost: Encryption requires CPU time. What impact would encrypting everything have on the cafe's POS system during a rush?
    • Key management: If every file is encrypted, where do you store all the keys? What happens if a key is lost?
    • Usability: How would employees access encrypted files? What training would they need?
    • The practical answer: What files SHOULD the cafe encrypt, and what can remain in plaintext?
