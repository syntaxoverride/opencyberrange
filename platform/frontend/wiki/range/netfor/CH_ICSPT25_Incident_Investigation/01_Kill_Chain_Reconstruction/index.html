    Why this matters

    Incident investigation in OT environments is harder than in IT because the evidence spans two domains: traditional IT logs (web server access logs, SSH authentication, bash history) and OT artifacts (PCAPs with ICS protocol traffic, historian time-series data). An effective OT incident responder must correlate timestamps across both domains to reconstruct how an attacker moved from IT initial access to OT impact. Exercise 6.3 builds exactly that skill.

    The professional habit Exercise 6.3 develops is independent analysis before reading the official report. In a real incident, the official timeline is written by the responder, not handed to them. Reconstructing the kill chain from raw evidence and then comparing your findings to the summary teaches you to trust evidence over narrative.

    Background: OT Incident Kill Chain

    ICS-targeted attacks follow a recognizable kill chain that spans IT and OT domains. The MITRE ATT&CK for ICS framework documents the common stages:

    Stage IT/OT Domain Masa Foods Incident
    Initial Access IT LFI on corporate web server
    Credential Access IT OT credentials stolen from server config files
    Lateral Movement IT to OT SSH pivot through jump server
    Discovery OT Protocol enumeration on plant networks
    Impact OT Process variable manipulation on all three plants

    Evidence correlation methodology

    The key to reconstructing a cross-domain kill chain is timestamp correlation. Each evidence artifact covers a different part of the attack:

    1. Web access logs reveal the initial access vector and the exact time the attacker first touched the corporate perimeter
    2. SSH auth logs reveal when the attacker pivoted from IT to OT and which credentials were used
    3. Bash history reveals the commands the attacker ran on the jump server (protocol tools, network scans, attack scripts)
    4. PCAPs reveal the exact protocol commands sent to each plant's PLCs
    5. Historian time-series reveals the process impact (temperature exceedances, dosing anomalies, phantom counts)

    Read the artifacts in that order. Each artifact builds context for the next.

    Suggested Methodology

    Exercise 6.3 is an independent exercise. No step-by-step walkthrough is provided. Instead, here are the stages a methodical incident responder would follow.

    Stage 1: Collect All Evidence

    Download every artifact from both servers into a working directory. Verify file sizes to confirm complete downloads. Do not read the incident_summary.json yet. Save it for Stage 5.

    Stage 2: Analyze IT-Side Evidence

    Start with the corporate web server access log. Search for requests from the attacker IP (10.100.1.99) and identify the LFI pattern. LFI requests typically contain path traversal sequences (../) in URL parameters. Note the timestamp of the first malicious request.

    Move to the jump server authentication log. Search for successful SSH logins from 10.100.1.99 or from the corporate web server's IP. Note the timestamp and the username used. Compare the credentials to the ones stolen via LFI.

    Review the bash history from the jump server session. The commands reveal what the attacker did after gaining OT network access: scanning, protocol tool usage, and attack execution.

    Stage 3: Analyze OT-Side Evidence

    Examine the attack PCAPs (reuse the Plant 1, 2, and 3 captures from Exercise 6.1). For each PCAP, identify the exact protocol command that caused the process impact:

    • Plant 1: Look for Modbus FC 6 writing an oven setpoint value of 500
    • Plant 2: Look for S7comm Write Var setting a caustic dosing rate to 200
    • Plant 3: Look for CIP Write Tag setting PalletCount to 9999

    Cross-reference the PCAP timestamps with the historian time-series data to confirm when each plant's process variables deviated from normal.

    Stage 4: Build the Kill Chain Timeline

    Assemble a chronological timeline that links every artifact to a kill chain stage. A complete timeline should include at minimum:

    1. First LFI request on the corporate web server (timestamp, URL, source IP)
    2. Credential theft (which file was read via LFI, what credentials were extracted)
    3. SSH login to the jump server (timestamp, username, source IP)
    4. OT network reconnaissance (commands from bash history)
    5. Plant 1 attack (Modbus write, timestamp, setpoint value)
    6. Plant 2 attack (S7 write, timestamp, dosing rate)
    7. Plant 3 attack (CIP write, timestamp, pallet count)
    8. Process impact detection (SIS trip on Plant 2, temperature alarm on Plant 1, phantom pallets on Plant 3)

    Stage 5: Validate Against the Official Summary

    Now read incident_summary.json. Compare the official timeline, attacker IP, initial access vector, and per-plant impact against your reconstruction. Note any discrepancies. In a real incident, discrepancies mean either your analysis missed evidence or the official summary is incomplete.

    Stage 6: Assemble and Submit the Flag

    The flag encodes the three plant impacts: the oven setpoint (500), the SIS trip, and the phantom pallet count (9999). Combine them into the flag format and submit.

    Output Interpretation

    • The web access log should show LFI attempts with path traversal sequences targeting configuration files that contain OT credentials
    • The SSH auth log should show a successful login using the plant_op account from an unexpected source (the corporate web server or the attacker's IP)
    • The bash history should reveal ICS protocol tools (Python scripts, nmap scans targeting OT ports) that match the attack PCAPs
    • Historian time-series data should show sharp deviations at timestamps matching the PCAP attack packets: oven temperature spiking, caustic dosing rate jumping, pallet count leaping to 9999
    • If timestamps between logs and PCAPs do not align, check for timezone differences. The exercise uses UTC throughout, but verify the log format headers

    Analysis Questions

    1. The attacker used LFI on the corporate web server as initial access. What single control would have prevented the pivot from IT to OT?

    Reveal answer

    An IT/OT DMZ (Purdue Level 3.5) with a jump server that requires multi-factor authentication would have blocked the pivot. The attacker stole a username and password via LFI, but MFA on the jump server would have rendered the stolen credentials insufficient for SSH access. Even without MFA, network segmentation that blocks direct SSH from the corporate web server to the OT jump server would have forced the attacker to find another pivot path.

    2. The attacker hit all three plants within a 20-minute window. What does that speed suggest about the attacker's preparation?

    Reveal answer

    A 20-minute window across three different ICS protocols (Modbus, S7comm, CIP) suggests the attacker had pre-written attack scripts for each protocol and had already performed reconnaissance on the plant network topology. An unprepared attacker would need hours to learn each protocol, identify the target PLCs, and craft the correct write commands. The speed indicates prior access (possibly from an earlier undetected intrusion) or detailed knowledge of Masa Foods' OT environment from insider information or public disclosures.

    3. Plant 2's SIS tripped and shut down the caustic dosing process. From an incident response perspective, is the SIS trip a success or a failure?

    Reveal answer

    The SIS trip is a safety success and a security failure. The Safety Instrumented System performed exactly as designed: it detected an out-of-range process variable (200 ml/min exceeds the 120 ml/min threshold) and shut down the process to prevent physical harm. The security failure is that the attacker reached the SIS trip point at all. A properly segmented network with authenticated S7comm access would have prevented the unauthorized write before the SIS needed to act. In the ideal defense-in-depth model, the SIS should never be the first line of defense against a cyber attack.

    4. You reconstructed the kill chain before reading the official incident summary. Why is that order important in real incident response?

    Reveal answer

    Reading the summary first introduces confirmation bias. An investigator who reads the conclusion before examining the evidence will unconsciously seek evidence that confirms the narrative and dismiss evidence that contradicts it. Independent reconstruction forces the investigator to follow the evidence wherever it leads, which may reveal attack stages or secondary compromises that the original summary missed. In a real incident, the first summary is always incomplete. The investigator's job is to find what the summary missed, not to confirm what it already says.

    Defensive Recommendations to Masa

    Finding Risk Mitigation
    Corporate web server vulnerable to LFI, providing access to OT credentials Critical Patch the LFI vulnerability immediately; move OT credentials out of web-accessible configuration files; rotate all OT passwords
    Single-factor SSH authentication on the OT jump server Critical Enforce multi-factor authentication for all jump server access; restrict SSH source IPs to authorized management stations
    Attacker pivoted from IT to OT with no detection until process impact occurred High Deploy network monitoring at the IT/OT boundary that alerts on new SSH sessions from unexpected sources
    All three plants attacked within 20 minutes, suggesting pre-staged scripts High Implement rate limiting and anomaly detection on OT protocol writes; alert on multiple write commands from a single source within a short window

    Key Takeaways

    • OT incident investigation requires correlating evidence across IT logs (web access, SSH auth, bash history) and OT artifacts (PCAPs, historian data)
    • Timestamp correlation is the primary technique for linking kill chain stages across domains
    • Independent analysis before reading the official summary prevents confirmation bias and reveals gaps in the existing narrative
    • The SIS is a safety system, not a security control. Defense-in-depth should prevent attackers from reaching the SIS trip threshold
    • A 20-minute multi-plant attack window indicates pre-staged scripts and prior reconnaissance, pointing to a sophisticated or insider-informed adversary
