    Exercise 6A: Mapping the Wire

    Before You Begin

    You will perform Layer 2 reconnaissance using the Address Resolution Protocol (ARP). You will map MAC addresses to IP addresses, observe ARP broadcast behavior, and build a baseline of the cafe network's Layer 2 identity bindings. The baseline you create here is essential for detecting ARP spoofing attacks in later exercises.

    Make sure you have:

    • VPN connected and verified
    • Access to the lab network (attacker machine)
    • Familiarity with basic networking concepts (IP, MAC, broadcast)

    Scenario

    You've already mapped the Bean & Byte Cafe network at Layers 3 and 4: IP addresses, open ports, running services. But there's a layer beneath all of that: Layer 2, where MAC addresses live. ARP is the protocol that translates between IP addresses and MAC addresses, and it operates on blind trust. Any device can claim any MAC-to-IP binding, and the network will believe it.

    Before you can detect ARP-based attacks, you need to know what "normal" looks like. Your task is to build a complete ARP baseline of the cafe network: every device's MAC address, its IP binding, and its ARP broadcast behavior.

    Your Objectives

    • Discover all 5 devices and their MAC addresses using arp-scan
    • Verify individual MAC-to-IP bindings with arping
    • Capture live ARP traffic with tcpdump and identify broadcast patterns
    • Build a baseline ARP table documenting MAC, IP, and vendor OUI for every device
    • Identify which devices send gratuitous ARPs and explain why

    Background: The Address Resolution Protocol

    What is ARP?

    ARP (Address Resolution Protocol) operates at Layer 2 of the OSI model. When a device needs to communicate with another device on the same subnet, it knows the destination IP address but needs the destination MAC address to construct an Ethernet frame. ARP solves this by broadcasting a question to the entire network: "Who has IP x.x.x.x? Tell me your MAC address."

    How ARP Works

    Step Action Packet Type
    1 Source broadcasts "Who has 10.100.2.42?" ARP Request (broadcast)
    2 Target responds "10.100.2.42 is at AA:BB:CC:DD:EE:FF" ARP Reply (unicast)
    3 Source caches the binding in its ARP table (no packet)

    ARP Request vs. ARP Reply

    • ARP Request: Broadcast to all devices on the subnet (destination MAC = ff:ff:ff:ff:ff:ff). Contains the sender's MAC and IP, and the target IP being queried.
    • ARP Reply: Unicast response from the target device. Contains the target's MAC address, confirming the binding.

    Gratuitous ARP

    A gratuitous ARP is an ARP reply sent without a preceding request. A device sends a gratuitous ARP to announce its own MAC-to-IP binding, typically after booting up, changing IP addresses, or for redundancy failover. While legitimate, gratuitous ARPs are also the mechanism exploited in ARP spoofing attacks.

    Why ARP is Insecure

    ARP has no authentication. Any device can send an ARP reply claiming any MAC-to-IP binding, and other devices will accept it without verification. The lack of authentication is the fundamental vulnerability that enables ARP spoofing and man-in-the-middle attacks.

    OUI: Organizationally Unique Identifier

    The first three octets (24 bits) of a MAC address identify the manufacturer. The first three octets form the OUI. For example:

    OUI Vendor
    00:1A:2B Cisco Systems
    DC:A6:32 Raspberry Pi Foundation
    B8:27:EB Raspberry Pi Foundation (older)

    Tools like arp-scan automatically look up OUI vendor strings, which helps identify device types on the network.

    Tools You'll Need

    Tool Purpose
    arp-scan Discover devices by sending ARP requests to every IP on the subnet
    arping Send ARP requests to a specific IP and observe the reply
    tcpdump Capture and display raw network traffic, including ARP packets
    arp View and manage the local ARP cache table
    ip neigh Modern alternative to arp for viewing neighbor (ARP) table

    Step 1: Discover All Devices with arp-scan

    Discover all devices with arp-scan

    arp-scan sends ARP requests to every IP address on the local subnet and reports which ones reply. Unlike nmap -sn (which uses ICMP and TCP), arp-scan operates purely at Layer 2 and will find devices that block ping. The -l flag tells arp-scan to scan the local network, auto-detecting the subnet from the interface configuration.

    arp-scan -I eth0 -l

    Step 2: Verify MAC-to-IP Bindings with arping

    Verify the gateway binding with arping

    arping sends ARP requests to a specific host and reports each reply. The response confirms whether a specific IP address maps to the expected MAC address. The -c 3 flag sends exactly 3 ARP requests. Replace <gateway_ip> with the gateway IP from your arp-scan results.

    arping -I eth0 -c 3 <gateway_ip>

    Expected output:

    ARPING 10.100.2.1 from 10.100.2.250 eth0
Unicast reply from 10.100.2.1 [00:18:f8:10:01:01]  0.847ms
Unicast reply from 10.100.2.1 [00:18:f8:10:01:01]  0.652ms
Unicast reply from 10.100.2.1 [00:18:f8:10:01:01]  0.714ms
Sent 3 probes (1 broadcast(s))
Received 3 response(s)

    Key observations:

    • The MAC address in each reply should be identical: if it changes between replies, something is wrong (possible ARP spoofing).
    • The response time gives you a rough latency baseline.

    Verify every other device

    Repeat the targeted verification for each remaining device, substituting its IP from your arp-scan results.

    arping -I eth0 -c 3 <pos_terminal_ip>
arping -I eth0 -c 3 <barista_ip>
arping -I eth0 -c 3 <printer_ip>
arping -I eth0 -c 3 <thermostat_ip>

    Compare the MAC address returned by arping against what arp-scan reported. They should match exactly. If they don't, the ARP cache may have been poisoned.

    Step 3: View the ARP Cache

    Inspect the local ARP cache

    After scanning and pinging, the tap has built an ARP cache: a local table of known MAC-to-IP bindings. ip neigh reads that neighbor table for the chosen interface.

    ip neigh show dev eth0

    Expected output:

    10.100.2.1 dev eth0 lladdr 00:18:f8:10:01:01 REACHABLE
10.100.2.17 dev eth0 lladdr 00:17:c5:10:11:17 REACHABLE
10.100.2.23 dev eth0 lladdr d4:be:d9:10:17:23 STALE
10.100.2.42 dev eth0 lladdr 3c:2a:f4:10:2a:42 REACHABLE
10.100.2.51 dev eth0 lladdr b4:75:0e:10:33:51 REACHABLE

    The state field tells you how fresh each entry is, as summarized below.

    State Meaning
    REACHABLE Recently confirmed: binding is trusted
    STALE Not recently confirmed: will be re-verified on next use
    DELAY Re-verification in progress
    FAILED ARP request sent but no reply received

    Step 4: Capture ARP Traffic with tcpdump

    Capture live ARP traffic with tcpdump

    Observe ARP traffic flowing across the network in real time. The -e flag shows Ethernet (Layer 2) headers including MAC addresses, and -nn disables hostname and port-name resolution so you see raw IPs and numbers. Let this run for 30-60 seconds to observe the patterns.

    tcpdump -i eth0 -enn arp

    Expected output:

    12:34:56.789 00:18:f8:10:01:01 > ff:ff:ff:ff:ff:ff, ARP, Request who-has 10.100.2.17 tell 10.100.2.1, length 28
12:34:56.790 00:17:c5:10:11:17 > 00:18:f8:10:01:01, ARP, Reply 10.100.2.17 is-at 00:17:c5:10:11:17, length 28
12:34:57.123 b4:75:0e:10:33:51 > ff:ff:ff:ff:ff:ff, ARP, Reply 10.100.2.51 is-at b4:75:0e:10:33:51, length 28

    The third packet above is a gratuitous ARP: an ARP Reply sent to the broadcast address (ff:ff:ff:ff:ff:ff) without a preceding Request. The thermostat is announcing its own binding. Press Ctrl+C to stop the capture.

    Step 5: Isolate Gratuitous ARPs

    Filter for ARP replies only

    Filter the capture to ARP replies to surface gratuitous ARPs. The filter arp[6:2] = 2 matches ARP operation code 2 (Reply). Gratuitous ARPs are replies sent to ff:ff:ff:ff:ff:ff, the broadcast address.

    tcpdump -i eth0 -enn 'arp and arp[6:2] = 2'

    Each line is a reply. Watch for replies sent to the broadcast MAC, which are the gratuitous announcements.

    Capture a bounded set of gratuitous ARPs

    Capture a fixed number of reply packets so the command exits on its own. The -c 10 flag captures exactly 10 matching packets, then stops.

    tcpdump -i eth0 -enn -c 10 'arp and arp[6:2] = 2'

    Review the 10 captured replies and note which devices announce their own binding unprompted.

    Analysis Questions

    1. Why does the thermostat send gratuitous ARPs, and how could an attacker exploit this?

    Reveal Answer The thermostat sends gratuitous ARPs to announce or refresh its MAC-to-IP binding on the network. IoT devices commonly do this after waking from sleep mode or reconnecting to the network. An attacker could exploit this by sending their own gratuitous ARPs with the thermostat's IP but the attacker's MAC address: all other devices would update their ARP caches to point the thermostat's IP to the attacker. Since gratuitous ARPs are accepted without verification, this is trivial to execute.

    2. What is the difference between the ARP cache states REACHABLE and STALE? Why does it matter for security?

    Reveal Answer REACHABLE means the binding was recently confirmed via a successful ARP exchange and is trusted by the kernel. STALE means the entry exists but hasn't been reconfirmed recently: the kernel will re-verify it (send a new ARP request) the next time it's needed. For security, STALE entries are vulnerable: if an attacker sends a spoofed ARP reply before the legitimate device responds to the re-verification, the attacker's binding will be cached as REACHABLE. Monitoring for unexpected state transitions can indicate ARP spoofing.

    3. You used arp-scan (broadcast) and arping (targeted). When would you use one versus the other?

    Reveal Answer `arp-scan -I eth0 -l` is a discovery tool, use it when you need to find all devices on a subnet. It sends ARP requests to every possible IP and reports all responders. `arping` is a verification tool, use it when you already know a specific IP and want to confirm its MAC binding, measure response time, or detect if multiple devices claim the same IP (which would indicate ARP spoofing). In an incident response scenario, you'd use `arp-scan` first for situational awareness, then `arping` to verify suspicious bindings.

    4. How could you detect ARP spoofing using only the tools from this exercise?

    Reveal Answer Compare your baseline against live observations. Run `arp-scan -I eth0 -l` periodically and compare MAC-to-IP bindings against your documented baseline. If a MAC address changes for a given IP, spoofing may be occurring. Use `arping` to send targeted ARP requests: if you get replies from two different MAC addresses for the same IP, one of them is an attacker. Monitor `tcpdump -i eth0 -enn arp` for an unusual volume of gratuitous ARPs or ARP replies for IPs that weren't queried. The baseline you built today is the reference point for all of these checks.

    5. Why does arp-scan find devices that nmap -sn sometimes misses?

    Reveal Answer `nmap -sn` uses a combination of ICMP echo requests, TCP SYN packets, and ARP requests (when scanning the local subnet). Some devices have firewalls that block ICMP and TCP probes but cannot block ARP, because ARP is required for basic network communication. A device that drops all ICMP pings will still respond to ARP requests, because without ARP it cannot communicate on the Ethernet network at all. `arp-scan` operates exclusively at Layer 2, bypassing any Layer 3/4 firewall rules.

    Defensive Recommendations

    Based on your ARP reconnaissance findings:

    1. Enable Dynamic ARP Inspection (DAI) on managed switches to validate ARP packets against a trusted DHCP snooping database
    2. Configure static ARP entries for critical infrastructure (gateway, POS terminal) to prevent their bindings from being spoofed
    3. Deploy ARP monitoring (e.g., arpwatch) to alert on MAC-to-IP binding changes
    4. Segment the network: IoT devices (thermostat) should not share a broadcast domain with payment systems (POS terminal)
    5. Disable gratuitous ARP acceptance on critical servers where possible (/proc/sys/net/ipv4/conf/*/arp_accept)

    Key Takeaways

    • ARP operates on trust: There is no authentication mechanism in ARP: any device can claim any MAC-to-IP binding
    • A baseline is your first defense: Without documenting normal MAC-to-IP bindings, you cannot detect when they change
    • Gratuitous ARPs are both useful and dangerous: Legitimate devices use them for announcements, but attackers use the same mechanism for spoofing
    • Layer 2 reconnaissance precedes Layer 2 attacks: The mapping you did today is exactly what an attacker does before launching ARP spoofing
    • arp-scan, arping, and tcpdump are complementary: Discovery, verification, and live monitoring form a complete ARP reconnaissance toolkit
    • OUI lookup reveals device identity: The vendor portion of a MAC address helps classify unknown devices on the network
