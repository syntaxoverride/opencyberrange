    Exercise 1.3: Incident Investigation

    Before You Begin

    Exercise 1.3 is the capstone lab of Chapter F1 and the longest exercise in this chapter. You will connect to the Windows target via RDP and conduct a hands-on forensic investigation of a simulated breach. Unlike Exercises 1.1 and 1.2 where you worked from your Kali machine, this exercise requires you to work directly on the Windows desktop using native Windows tools: Event Viewer, the command prompt, and PowerShell.

    The flag for this exercise is split into three parts hidden across different forensic artifacts. You must investigate the system thoroughly to find all three parts and assemble the complete flag.

    Username LabUser
    Password Password123#

    Estimated time: 60-90 minutes. this exercise involves significant investigation. Keep a text file open on the Windows desktop to organize your notes as you work through each step.

    Make sure you have:

    • Completed Exercises 1.1 and 1.2
    • xfreerdp installed on your Kali machine (xfreerdp --version)
    • Target IP noted from the Active Lab panel; replace <target-ip> below
    • Credentials ready: LabUser / Password123#

    Scenario

    Meridian Technologies' SOC has detected suspicious activity on the workstation you assessed in Exercises 1.1 and 1.2. Their SIEM flagged a series of failed login attempts from IP address 10.150.0.99: an address that does not belong to any known Meridian system; followed by a successful authentication. Shortly after, an unauthorized user account appeared in the local Administrators group, and anomalous scheduled tasks were registered on the system.

    The SOC has preserved the machine in its current state and granted your team RDP access for investigation. Your task is to determine what the attacker did, how they maintained persistence, and what indicators of compromise (IOCs) they left behind. The engagement is no longer an assessment; it is incident response.

    Your Objectives

    • Connect to the target via RDP and orient yourself on the Windows desktop
    • Examine Windows Event Logs to identify the brute-force attack pattern
    • Identify unauthorized user accounts and group membership changes
    • Investigate suspicious scheduled tasks and decode encoded payloads
    • Check registry persistence mechanisms (Run keys)
    • Explore file system artifacts left by the attacker
    • Review PowerShell command history for attacker activity
    • Assemble the three-part flag from evidence found across the system
    • Construct a complete attack timeline

    Background: Windows Forensic Artifacts

    Windows maintains an extensive collection of artifacts that record system activity. During an incident investigation, these artifacts tell the story of what happened, when it happened, and often who did it. Understanding where to look is half the battle.

    Windows Event Logs

    Windows Event Logs are the primary source of security telemetry on a Windows system. They are stored in .evtx files under C:\Windows\System32\winevt\Logs\ and are accessed through Event Viewer (eventvwr.msc) or PowerShell (Get-WinEvent). The three most important logs for incident response are:

    • Security Log: Authentication events, privilege use, policy changes
    • System Log: Service starts/stops, driver loading, system errors
    • Application Log: Application-specific events, including custom logging

    The following Event IDs are critical for detecting unauthorized access and persistence:

    Event ID Log What It Records
    4624 Security Successful logon. Includes logon type, source IP, and account name.
    4625 Security Failed logon. Same fields as 4624; critical for detecting brute force.
    4720 Security User account created. Records the new account name and who created it.
    4732 Security Member added to a security-enabled local group. Key for detecting privilege escalation.
    1102 Security Audit log was cleared. Strong indicator of anti-forensic activity.
    4688 Security A new process was created. When enabled, records every command executed.
    7045 System A new service was installed. Used to detect persistence via service creation.

    Persistence Mechanisms

    Attackers who gain access to a system want to maintain that access even if the machine reboots or the user logs out. Common Windows persistence mechanisms include:

    • Scheduled Tasks: Windows Task Scheduler can execute programs on a schedule or at system events (logon, startup). Attackers create scheduled tasks that run their malware automatically. Investigate with schtasks /query /fo LIST /v.

    • Registry Run Keys: The registry keys HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run and the corresponding HKCU key execute programs every time a user logs on. These are among the oldest and most common persistence mechanisms. Check with reg query.

    • Services: Windows services run in the background with SYSTEM privileges. Attackers create malicious services that start automatically. Event ID 7045 records new service installations.

    PowerShell Artifacts

    PowerShell is the attacker's tool of choice on Windows. It provides full access to the .NET framework, Windows APIs, and system management functions; all from a command line that can be scripted and obfuscated.

    Key PowerShell artifacts:

    • ConsoleHost_history.txt: PowerShell records every command typed in an interactive session to C:\Users\<username>\AppData\Roaming\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt. This file persists across sessions and is rarely cleaned by attackers.

    • Script Block Logging: When enabled, records the full text of every PowerShell script that executes, including decoded versions of obfuscated scripts. Stored in the Microsoft-Windows-PowerShell/Operational event log.

    • Base64 Encoding: Attackers frequently encode PowerShell commands in Base64 using the -EncodedCommand parameter. The encoding evades simple string-based detection but is trivially decoded with [System.Text.Encoding]::Unicode.GetString([Convert]::FromBase64String('...')).

    Tool Primer

    Tool / Command What It Does
    eventvwr.msc Opens Event Viewer GUI. Navigate to Windows Logs > Security/System/Application.
    net user Lists all local user accounts.
    net user <username> Shows detailed information about a specific account (creation date, group membership, last logon).
    net localgroup Administrators Lists members of the local Administrators group.
    schtasks /query /fo LIST /v Lists all scheduled tasks with full details (trigger, command, author).
    reg query "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run" Shows programs that auto-run at user logon (machine-wide).
    reg query "HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run" Shows programs that auto-run at logon (current user only).
    powershell -c "[System.Text.Encoding]::Unicode.GetString([Convert]::FromBase64String('...'))" Decodes a Base64-encoded Unicode string.

    Walkthrough

    Step 1: Connect via RDP

    Open an RDP session to the target

    From your Kali terminal, initiate an RDP session to the Windows target. The /cert:ignore flag bypasses the self-signed certificate warning.

    xfreerdp /v:<target-ip> /u:LabUser /p:Password123# /cert:ignore

    Once connected, you should see the Windows 10 desktop. Open a Command Prompt (cmd.exe); you will use it extensively throughout this investigation.

    Take a moment to orient yourself. Note the computer name in the system properties, the current date/time, and any unusual icons or files on the desktop. Investigators always document the initial state of the system before making any changes.

    Step 2: Examine Event Viewer

    Open Event Viewer by typing eventvwr.msc in the Start menu search or Run dialog.

    Navigate to Windows Logs > Application. In the Application log, look for events from a source called SecuritySimulation. These events record the simulated attack activity. To filter for them:

    1. In Event Viewer, click Filter Current Log in the right panel
    2. In the Event sources dropdown, type or select SecuritySimulation
    3. Click OK to apply the filter

    Review the filtered events chronologically (oldest first). You will see a pattern that tells the story of the attack:

    • Eight failed login attempts from IP 10.150.0.99: the attacker tried multiple passwords against the local accounts
    • One successful login: the attacker found valid credentials
    • Account creation and privilege escalation events: the attacker established persistence

    Look carefully at the description field of the event that records the successful brute force completion. It contains Flag Part 1:

    Flag Part 1: 1nc1d3nt

    Write this down. You will need all three parts to assemble the complete flag at the end of the investigation.

    • Timestamp of the first failed attempt: ___
    • Timestamp of the successful login: ___

    List local user accounts on the target

    In the Command Prompt on the Windows desktop, list all local user accounts.

    Compare this list to the accounts you discovered remotely in Exercise 1.2. Look for any account that was not present before or that seems out of place.

    Check the Administrators group

    Still on the Windows host, check who belongs to the local Administrators group.

    net localgroup Administrators

    You should find that the svc_updater account is a member of the local Administrators group. In Exercise 1.2, you enumerated this account, but now you need to determine whether it is legitimate. The name suggests a Windows Update service account, but legitimate Windows Update does not use a local user account; it runs as the built-in SYSTEM account.

    Step 4: Examine the Backdoor Account

    Inspect the suspicious account

    On the Windows host, get detailed information about the suspicious account.

    net user svc_updater

    Review the output carefully:

    • Full Name: May be blank or contain a misleading name
    • Comment/Description: Look for Windows Update Service or similar. A label like that is a social engineering tactic; the attacker named the account to look legitimate at a glance
    • Account active: Should show Yes
    • Last logon: When was this account last used?
    • Password last set: When was it created?
    • Local Group Memberships: Confirms Administrators group membership

    The description field saying "Windows Update Service" is a red flag. Real Windows services run under built-in accounts (SYSTEM, LOCAL SERVICE, NETWORK SERVICE), not under custom local accounts. An attacker created this account to blend in with legitimate services; a common persistence technique.

    Step 5: Investigate Scheduled Tasks

    Query scheduled tasks for persistence

    Attackers use scheduled tasks to maintain persistence and execute commands automatically. On the Windows host, query all scheduled tasks and filter for the task name, the command, and the author.

    schtasks /query /fo LIST /v | findstr /i "task\|command\|author"

    Scroll through the output and look for tasks that:

    • Have unusual names that mimic legitimate Windows tasks
    • Execute PowerShell with encoded commands
    • Were authored by an unexpected user account
    • Trigger at logon or system startup

    You should find a task named WindowsUpdateCheck that stands out. Note its properties:

    • Task Name: \WindowsUpdateCheck
    • Trigger: At logon (runs every time any user logs in)
    • Action: Executes powershell.exe with a -EncodedCommand parameter
    • Author: The compromised or attacker-created account

    A legitimate Windows Update task would be authored by Microsoft and would not use encoded PowerShell commands. The task is attacker-created persistence.

    Record Your Findings

    • Suspicious task name: ___
    • Trigger type: ___
    • Command executed: ___
    • Author: ___
    • Base64-encoded payload: ___

    Step 6: Decode the Base64 Payload

    The scheduled task from Step 5 runs a Base64-encoded PowerShell command. Decode it to reveal the attacker's payload.

    Decode the Base64 PowerShell payload

    Open PowerShell on the Windows host (type powershell in the Command Prompt) and run the decoder. The one-liner converts the Base64 string from Unicode bytes back to readable text.

    powershell -c "[System.Text.Encoding]::Unicode.GetString([Convert]::FromBase64String('UABpAG4AZwAgADEAMAAuADEANQAwAC4AMAAuADkAOQA='))"

    The decoded output is:

    Ping 10.150.0.99

    The ping is a callback to the attacker's IP address (10.150.0.99). Every time a user logs in, the scheduled task pings the attacker's machine; a basic heartbeat mechanism that tells the attacker the compromised system is online. In a real attack, this would be replaced with a reverse shell or C2 beacon, but the principle is identical: the persistence mechanism phones home automatically.

    Now examine the full encoded command from the scheduled task. The complete payload contains a comment with Flag Part 2. Decode the full Base64 string found in the task definition:

    Flag Part 2: r3sp0ns3

    Step 7: Check Registry Persistence

    Check the machine-wide Run key

    Attackers frequently add entries to the Windows Run registry keys so their tools execute automatically at logon. On the Windows host, check the machine-wide Run key.

    reg query "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run"

    A non-standard entry here runs for every user on the machine, which makes the HKLM key a high-value persistence location.

    Check the current-user Run key

    Now check the current user Run key for entries scoped to the logged-in account.

    reg query "HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run"

    In the HKLM Run key, you should find an entry named WindowsUpdateHelper that points to a PowerShell script:

    WindowsUpdateHelper    REG_SZ    powershell.exe -WindowStyle Hidden -ExecutionPolicy Bypass -File C:\Windows\Temp\svc_tools\update_helper.ps1

    Analyze this entry:

    • -WindowStyle Hidden: The PowerShell window is invisible to the user
    • -ExecutionPolicy Bypass: Script execution restrictions are overridden
    • -File C:\Windows\Temp\svc_tools\update_helper.ps1: The script runs from a temporary directory, not a legitimate Program Files location

    Every element of this command is a red flag. Legitimate software installs to C:\Program Files, does not bypass execution policies, and does not hide its windows. The registry key ensures the attacker's script runs silently every time the system starts.

    Record Your Findings

    • Registry key path: ___
    • Entry name: ___
    • Command value: ___
    • Script location: ___
    • Why is this suspicious? ___

    Step 8: Explore File System Artifacts

    List the attacker's tool directory

    Based on the registry entry from Step 7, the attacker stored tools in C:\Windows\Temp\svc_tools\. On the Windows host, list this directory.

    dir C:\Windows\Temp\svc_tools\

    You should find several attacker files:

    File Contents
    dump.txt Credential hashes dumped from the local SAM database
    recon.txt Network reconnaissance output; IP ranges, hostnames, open ports
    update_helper.ps1 The PowerShell script from the registry Run key; contains a reverse shell or callback mechanism

    Read the attacker's dropped files

    Display the contents of each file the attacker left behind.

    type C:\Windows\Temp\svc_tools\dump.txt
type C:\Windows\Temp\svc_tools\recon.txt
type C:\Windows\Temp\svc_tools\update_helper.ps1

    The dump.txt file contains NTLM hashes; evidence that the attacker ran a credential dumping tool (like Mimikatz or secretsdump) to harvest passwords from the local Security Account Manager. The recon.txt file shows the attacker was mapping the internal network for lateral movement targets. The update_helper.ps1 script contains the persistence payload.

    Read the PowerShell command history

    Next, check the PowerShell command history. The history file records every command the attacker typed in an interactive PowerShell session.

    type C:\Users\LabUser\AppData\Roaming\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt

    Review the history for commands that reveal the attacker's methodology; account creation, scheduled task registration, credential dumping, and network reconnaissance. The history file is often the most revealing artifact in a Windows investigation because it captures the attacker's exact sequence of actions in chronological order.

    Step 10: Assemble the Complete Flag

    You have collected all three flag parts from different forensic artifacts across the system. Combine them to form the complete flag:

    Part Source Value
    Part 1 Event Viewer (Application log, SecuritySimulation) <part1>
    Part 2 Scheduled Task (Base64-decoded payload comment) <part2>
    Part 3 File system (C:\forensic_evidence\flag.txt) <part3>

    Complete flag:

    OCR{<part1>_<part2>_<part3>}

    The flag parts were deliberately scattered across different artifact categories to reinforce the principle that a thorough investigation examines all available evidence sources; logs, accounts, tasks, registry, file system, and command history. Checking only one category misses parts of the story.

    Analysis Questions

    1. The attacker created a scheduled task and a registry Run key for persistence. Why use two different mechanisms?

    Redundancy. If a defender discovers and removes the scheduled task, the registry Run key still executes the attacker's payload at next logon. If they find and clean the registry key, the scheduled task still fires. Sophisticated attackers install multiple persistence mechanisms so that removing one does not evict them from the system. During remediation, incident responders must identify and remove ALL persistence mechanisms; missing even one means the attacker retains access.

    2. What indicators of compromise (IOCs) would you extract from this investigation for your threat intelligence team?

    IP address: 10.150.0.99 (attacker source). Account name: svc_updater (backdoor account). Scheduled task name: WindowsUpdateCheck. Registry value: WindowsUpdateHelper. File paths: C:\Windows\Temp\svc_tools\*. PowerShell command patterns: Base64-encoded commands with -WindowStyle Hidden and -ExecutionPolicy Bypass. These IOCs should be searched across all systems in the environment to determine if the attacker compromised other machines using the same tools and techniques.

    3. The attacker used the account name svc_updater with the description "Windows Update Service." How does this demonstrate social engineering at the system level?

    The attacker chose an account name and description that mimic a legitimate Windows service to avoid detection during casual review. An administrator running net user or viewing the account in Computer Management might glance at "svc_updater" and assume it belongs to a legitimate update service. The deception is social engineering applied to system artifacts rather than humans. Defenders should maintain an authoritative list of approved service accounts and alert on any new account creation, especially accounts added to the Administrators group.

    4. Why is the PowerShell ConsoleHost_history.txt file so valuable for forensic investigation?

    ConsoleHost_history.txt records every command typed in an interactive PowerShell session, in chronological order, across all sessions. Unlike event logs which may be cleared (Event ID 1102), many attackers forget that this file exists. It provides a complete record of the attacker's manual activity; account creation commands, tool execution, credential dumping, reconnaissance; in the exact order they were performed. The file is often the single most informative artifact on a compromised Windows system.

    5. The scheduled task payload decoded to Ping 10.150.0.99. In a real attack, what would this likely be replaced with?

    A real attacker would replace the simple ping with a reverse shell (connecting back to their command-and-control server), a PowerShell download cradle (fetching and executing a remote payload), or a C2 beacon (such as Cobalt Strike, Sliver, or Metasploit). The ping serves the same conceptual purpose; it contacts the attacker's infrastructure; but a real payload would establish an interactive command channel. The Base64 encoding technique is identical in both cases, making this exercise exercise directly applicable to real-world investigations.

    Key Takeaways

    • Windows Event Logs are the first place to look in any incident investigation ; Event IDs 4624/4625 (logon success/failure), 4720 (account creation), and 4732 (group membership change) tell the authentication story
    • Attackers create accounts that mimic legitimate services to blend in; always verify new accounts against an approved service account list
    • Scheduled tasks and registry Run keys are the two most common persistence mechanisms on Windows; check both during every investigation
    • Base64-encoded PowerShell commands are trivially decoded; the encoding evades casual inspection but not forensic analysis
    • The PowerShell ConsoleHost_history.txt file is an often-overlooked artifact that records the attacker's exact command sequence
    • Attacker tools and outputs (credential dumps, recon data) are frequently left on disk in temporary directories; always check C:\Windows\Temp\ and user profile temp directories
    • A complete investigation examines all artifact categories (logs, accounts, tasks, registry, file system, command history); checking only one category misses critical evidence
