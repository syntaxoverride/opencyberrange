    Exercise WS-2.1: Organizational Unit Discovery

    Before You Begin

    Chapter WS01 confirmed that the domain controller dc01 accepts anonymous LDAP binds on port 389. Exercise WS-2.1 puts that access to work by querying for the directory containers that organize every other object in the domain. You should have ldapsearch installed on your Kali machine and a working VPN connection to the lab environment.

    Prerequisites

    • Chapter WS01 completed (anonymous LDAP access confirmed)
    • VPN active and dc01 reachable
    • ldapsearch available (ldap-utils package)

    Scenario

    With anonymous LDAP access confirmed, your next task is to map the organization's Organizational Unit (OU) structure. OUs often mirror an organization's departmental layout; Human Resources, Finance, IT, and so on. Enumerating OUs early in reconnaissance reveals how the directory is partitioned, which guides where to look for high-value accounts and sensitive resources in later queries.

    Your Objectives

    • Enumerate all OUs in the domain using an LDAP search filter
    • Understand the hierarchical directory structure by reading OU Distinguished Names (DNs)
    • Examine OU attributes; especially description: for hidden or overlooked information
    • Locate a hidden OU whose description attribute contains the lab flag

    Background: Organizational Units in Active Directory

    An Organizational Unit is a container object inside Active Directory that groups related objects such as users, computers, and groups. Administrators create OUs to reflect organizational structure, delegate administrative control, and apply Group Policy Objects (GPOs) to specific subsets of the directory. A company with offices in multiple cities might create OUs named OU=NewYork, OU=London, and OU=Tokyo, each containing the user and computer accounts for that location.

    Every OU has a Distinguished Name that encodes its position in the directory tree. The DN OU=IT,DC=corp,DC=ocr-range,DC=lab tells you the OU named "IT" sits directly under the domain root. Nested OUs work the same way: OU=Servers,OU=IT,DC=corp,DC=ocr-range,DC=lab describes a "Servers" OU inside the "IT" OU. Reading DNs from right to left reveals the path from the root down to the object.

    OUs also carry optional attributes. The description attribute is a free-text field that administrators sometimes use for internal notes; and occasionally for information they assume no one outside the admin team will ever read. During enumeration, always request the description attribute because careless notes, temporary passwords, or references to sensitive systems sometimes appear there.

    Tool Primer: ldapsearch

    The ldapsearch command-line tool sends LDAP search requests and prints the results to standard output. Below is the anatomy of the command you will run in this exercise.

    ldapsearch -x -H ldap://dc01 -b "DC=corp,DC=ocr-range,DC=lab" "(objectClass=organizationalUnit)" dn description

    Each flag and argument serves a specific purpose.

    Component Meaning
    -x Use simple authentication (anonymous bind; no credentials)
    -H ldap://dc01 Connect to the LDAP server at hostname dc01 on port 389
    -b "DC=corp,DC=ocr-range,DC=lab" Set the search base to the domain root
    "(objectClass=organizationalUnit)" Filter: return only objects whose class is organizationalUnit
    dn description Request only the DN and description attributes

    When ldapsearch returns results, each matching object is printed as a block of attribute-value pairs separated by a blank line. A typical entry looks like the following.

    # IT, corp.ocr-range.lab
dn: OU=IT,DC=corp,DC=ocr-range,DC=lab
description: Information Technology department

    The first line (starting with #) is a comment showing the object's Relative Distinguished Name (RDN) and domain. The dn: line gives the full path. Any requested attributes that have values follow on subsequent lines. If an attribute has no value set, the line is omitted entirely.

    Walkthrough

    Step 1: Verify LDAP Connectivity

    Verify anonymous LDAP connectivity

    Before running a targeted query, confirm that ldapsearch can reach dc01 and that anonymous access still works. Run a minimal query that returns the root DSE (Directory Service Agent-Specific Entry), which every LDAP server exposes without authentication.

    ldapsearch -x -H ldap://dc01 -b "" -s base "(objectClass=*)" namingContexts

    The output should include a namingContexts attribute listing the directory partitions. Look for DC=corp,DC=ocr-range,DC=lab in the results. If the command times out or returns an error, verify your VPN connection and confirm that port 389 is open on dc01.

    Step 2: Enumerate All Organizational Units

    Enumerate all Organizational Units

    Run the primary OU enumeration command. The filter (objectClass=organizationalUnit) matches every OU in the directory, and requesting dn and description keeps the output concise.

    ldapsearch -x -H ldap://dc01 -b "DC=corp,DC=ocr-range,DC=lab" "(objectClass=organizationalUnit)" dn description

    Scroll through the output and note every OU that appears. Pay attention to the DN of each entry; the OU names and their nesting reveal the directory's organizational layout. Some OUs sit directly under the domain root while others are nested inside parent OUs.

    Step 3: Count the Results

    The final line of ldapsearch output reports how many entries matched the filter. Look for a line like the following.

    # numEntries: X

    Record the total count. Knowing how many OUs exist helps you confirm that you have captured the full list and gives you a baseline for comparison if you run the query again later.

    Step 4: Map the OU Hierarchy

    Using the DN values from Step 2, sketch the OU hierarchy on paper or in a text file. Start with the domain root at the top and draw each OU as a branch. Nested OUs should appear as children of their parent OU. The hierarchy will resemble a directory tree.

    DC=corp,DC=ocr-range,DC=lab
├── OU=IT
├── OU=HR
├── OU=Finance
├── OU=...
│   └── OU=NestedExample
└── OU=...

    Replace the placeholder names with the actual OUs you discovered. The goal is a visual map you can reference throughout the rest of this chapter.

    Step 5: Inspect OU Descriptions

    Review each OU entry in the output and look for the description attribute. Some OUs will have a description value; others will not (the line will be absent). Read every description carefully. Administrators sometimes leave internal notes, temporary references, or metadata in description fields that they expect only fellow admins to see.

    Page OU descriptions through less

    If the output from Step 2 scrolled past your terminal buffer, re-run the command and pipe it through less for easier navigation.

    ldapsearch -x -H ldap://dc01 -b "DC=corp,DC=ocr-range,DC=lab" "(objectClass=organizationalUnit)" dn description | less

    Use the / key inside less to search for specific strings. Try searching for "hidden", "secret", "flag", or "OCR" to locate noteworthy descriptions quickly.

    Step 6: Look for Unusual or Hidden OUs

    Not every OU will have an obvious departmental name. Some organizations create OUs for staging, testing, decommissioned accounts, or security-sensitive purposes and give them nondescript or misleading names. Compare your OU list against what you would expect from a typical corporate directory. Any OU whose name does not match a standard department warrants closer inspection.

    When you find an OU with an unexpected name, examine its description attribute carefully. The flag for this exercise is stored in the description attribute of a hidden OU.

    Step 7: Interpret the Results

    Review the hierarchy you mapped and the descriptions you collected. Consider what the OU structure tells you about the organization. Departments like IT and Finance suggest where to look for privileged accounts and sensitive data in later exercises. Nested OUs may indicate sub-teams or role-based separation. Hidden or unusually named OUs may contain objects the administrators wanted to keep out of casual view.

    Step 8: Find and Submit the Flag

    One of the OUs you discovered has a description attribute containing the flag. The flag follows the format OCR{...} and is located on a hidden OU; one whose name does not correspond to a standard corporate department. Copy the flag exactly as it appears in the LDAP output and submit it.

    Analysis Questions

    1. Why do administrators create Organizational Units rather than placing all objects directly under the domain root?

    Reveal Answer

    OUs allow administrators to delegate control over subsets of the directory, apply Group Policy Objects to specific groups of objects, and maintain a logical structure that mirrors the organization. Placing all objects at the root would make delegation and policy targeting far more difficult.

    2. An OU's description field contained sensitive information in this exercise. What defensive step would prevent that exposure?

    Reveal Answer

    Disabling anonymous LDAP binds would prevent unauthenticated users from reading any directory attributes. Administrators should also audit description fields across all OUs and objects to remove sensitive notes, and apply access-control entries that restrict read access to the description attribute where needed.

    3. How does the -b (search base) flag affect the scope of your query, and when might you change it?

    Reveal Answer

    The -b flag sets the starting point in the directory tree. Searching from the domain root returns objects across the entire domain. Narrowing the base to a specific OU; for example, -b "OU=IT,DC=corp,DC=ocr-range,DC=lab": limits results to that OU and its children, which is useful when you want to focus on a particular department.

    4. What LDAP scope option would you use if you only wanted OUs directly under the domain root, not nested OUs?

    Reveal Answer

    The -s one (one-level) scope restricts results to objects that are immediate children of the search base. Combined with the domain root as the base, the query ldapsearch -x -H ldap://dc01 -b "DC=corp,DC=ocr-range,DC=lab" -s one "(objectClass=organizationalUnit)" dn returns only top-level OUs.

    Key Takeaways

    • Organizational Units are the directory's structural framework; enumerating them first gives you a roadmap for every subsequent query.
    • The description attribute on any object type can contain notes, references, or data that administrators did not intend to be publicly visible.
    • Anonymous LDAP access exposes the entire directory tree unless the administrator has explicitly restricted it, making OU enumeration trivial when it is allowed.
    • Reading Distinguished Names from right to left reveals the hierarchical path from the domain root down to the object.
    • With the OU map in hand, Exercise WS-2.2 will enumerate the user accounts that live inside these containers, expanding your understanding of the domain's population.
