    Exercise WS-4.4: AD ACL Weak Permission Discovery

    Before You Begin

    Exercises WS-4.1 through WS-4.3 focused on reading data that Active Directory (AD) exposes to authenticated users: SMB shares, Group Policy Object (GPO) templates, and Service Principal Names (SPNs). AD Access Control List (ACL) analysis takes a fundamentally different approach; instead of reading data, you examine who has permission to modify data. Weak ACLs on AD objects create privilege escalation paths that let low-privilege users perform high-privilege actions like resetting passwords, modifying group memberships, or writing attributes on sensitive accounts.

    Scenario

    You continue your assessment of the corp.ocr-range.lab domain with the guest.user credentials. The engagement lead suspects that AD object permissions have not been properly audited and that some objects may have overly permissive Discretionary Access Control Lists (DACLs). Your task is to enumerate Organizational Units (OUs) and user accounts in the domain, identify objects where guest.user has unexpected write access, and document the privilege escalation paths that weak permissions create.

    Your Objectives

    • Understand how AD DACLs control access to directory objects
    • Enumerate OUs and objects in the domain using authenticated Lightweight Directory Access Protocol (LDAP) queries
    • Discover the Flags OU and analyze its contents
    • Identify objects where guest.user has been granted excessive permissions
    • Locate and submit the flag from a misconfigured object's description

    Background: Active Directory Access Control

    Every object in Active Directory; users, groups, OUs, computers, GPOs; has a security descriptor that controls who can read, modify, or delete the object. The security descriptor contains a DACL, which is a list of Access Control Entries (ACEs). Each ACE grants or denies a specific permission to a specific security principal (user, group, or computer).

    AD permissions are more granular than file system permissions. Instead of basic read/write/execute, AD supports object-specific permissions that control access at the attribute level.

    Common AD permissions and their attack value:

    Permission What It Allows Attack Potential
    GenericAll Full control over the object Reset passwords, modify group membership, write any attribute
    GenericWrite Write any attribute on the object Modify descriptions, write SPNs, change logon scripts
    WriteDacl Modify the object's ACL Grant yourself additional permissions
    WriteOwner Change the object's owner Take ownership, then modify the ACL
    ForceChangePassword Reset the target's password Take over the target account without knowing the current password
    AddMember Add members to a group Add yourself to privileged groups
    WriteProperty (specific) Write to a specific attribute Depends on the target attribute

    How Weak ACLs Create Attack Paths

    In a properly secured environment, low-privilege users can read most AD objects but cannot modify them. Misconfigurations occur when administrators grant excessive permissions; often during troubleshooting, delegation, or automated provisioning; and forget to remove them. A low-privilege user with GenericAll on a high-privilege group can add themselves to that group, instantly escalating to administrative access.

    ACL-based attack paths are among the most common findings in AD security assessments. Tools like BloodHound map these paths across an entire domain, but the underlying technique starts with the same LDAP queries you will use in this exercise.

    Permission Inheritance

    AD permissions can be inherited from parent objects. An OU with a misconfigured ACL passes those permissions down to every object inside it. Granting guest.user GenericAll on the Flags OU means guest.user has full control over every user, group, and computer object within that OU; including the ability to read and write any attribute on those objects.

    Tool Primer: ldapsearch for ACL-Related Object Discovery

    Directly reading DACLs via ldapsearch requires parsing binary security descriptor data, which is complex. In a full engagement, tools like BloodHound, PowerView, or dacledit.py from Impacket handle DACL parsing. For this exercise, you will use ldapsearch to discover objects that your account has access to and read their attributes; the readable attributes themselves reveal what permissions you hold.

    Enumerate OUs in the domain

    Filter on objectClass=organizationalUnit to map every OU container in the directory tree.

    ldapsearch -D "guest.user@corp.ocr-range.lab" -w "Guest2024#" \
  -H ldap://dc01 \
  -b "DC=corp,DC=ocr-range,DC=lab" \
  "(objectClass=organizationalUnit)" \
  dn description

    The returned DNs reveal the organizational structure; watch for any OU with an unusual name or description.

    List objects in a specific OU

    Set the search base to a single OU and match all object types to see what accounts and resources it contains.

    ldapsearch -D "guest.user@corp.ocr-range.lab" -w "Guest2024#" \
  -H ldap://dc01 \
  -b "OU=Flags,DC=corp,DC=ocr-range,DC=lab" \
  "(objectClass=*)" \
  dn description

    Results are limited to objects inside the named OU, so the listing stays focused.

    Query a specific account

    Match a single account by its sAMAccountName to read its attributes directly.

    ldapsearch -D "guest.user@corp.ocr-range.lab" -w "Guest2024#" \
  -H ldap://dc01 \
  -b "DC=corp,DC=ocr-range,DC=lab" \
  "(sAMAccountName=flag.account)" \
  description

    The fact that your low-privilege account can read these attributes is itself evidence of the permission delegation.

    The search base (-b) parameter controls where in the directory tree the search begins. Setting the base to a specific OU limits results to objects within that OU. The filter (objectClass=*) matches all object types, while (objectClass=organizationalUnit) matches only OUs.

    Parameter Purpose
    -b "OU=Flags,DC=corp,DC=ocr-range,DC=lab" Search only within the Flags OU
    "(objectClass=*)" Match all objects regardless of type
    "(sAMAccountName=flag.account)" Match a specific account by logon name
    dn description Return the Distinguished Name and description attribute

    Walkthrough

    Step 1: Launch the Lab

    Open the Open Cyber Range platform in your browser and start the lab environment.

    • Navigate to Exercises, then Windows Server, then Level 4
    • Click Launch on "AD ACL Weak Permission Discovery"
    • Wait for the status to change to Running
    • Note the target IP displayed in the Active Lab View

    Step 2: Enumerate All Organizational Units

    Enumerate all Organizational Units

    Begin by mapping the OU structure of the domain. OUs are the organizational containers that hold users, groups, and computers, and each OU can have its own set of delegated permissions.

    ldapsearch -D "guest.user@corp.ocr-range.lab" -w "Guest2024#" \
  -H ldap://dc01 \
  -b "DC=corp,DC=ocr-range,DC=lab" \
  "(objectClass=organizationalUnit)" \
  dn description

    Review the list of OUs in the output. Standard AD deployments include OUs like Domain Controllers, but custom OUs created by administrators reveal organizational structure. Look for any OU with an unusual name or an interesting description.

    Step 3: Discover the Flags OU

    Discover the Flags OU

    The OU listing from Step 2 should reveal an OU named Flags. Enumerate all objects within the Flags OU to see what accounts and resources it contains.

    ldapsearch -D "guest.user@corp.ocr-range.lab" -w "Guest2024#" \
  -H ldap://dc01 \
  -b "OU=Flags,DC=corp,DC=ocr-range,DC=lab" \
  "(objectClass=*)" \
  dn description

    The search base is set to the Flags OU, so results are limited to objects within that container. Record the Distinguished Names (DNs) of all objects returned. The DN tells you the object's name, type, and location in the directory tree.

    Step 4: Examine Objects in the Flags OU

    Examine objects in the Flags OU

    For each object found in Step 3, query its full set of attributes to understand what information is stored on it.

    ldapsearch -D "guest.user@corp.ocr-range.lab" -w "Guest2024#" \
  -H ldap://dc01 \
  -b "OU=Flags,DC=corp,DC=ocr-range,DC=lab" \
  "(objectClass=*)" \
  dn objectClass sAMAccountName description memberOf

    The additional attributes reveal each object's type (objectClass), account name (sAMAccountName), description, and group memberships (memberOf). Pay attention to the description field; administrators and lab designers store metadata there.

    Step 5: Query Objects Discovered in the Flags OU

    Query objects discovered in the Flags OU

    Based on the results from Steps 3 and 4, query the user objects you discovered in the Flags OU directly to read their attributes. Use the sAMAccountName values returned in the previous steps to confirm the targets.

    ldapsearch -D "guest.user@corp.ocr-range.lab" -w "Guest2024#" \
  -H ldap://dc01 \
  -b "OU=Flags,DC=corp,DC=ocr-range,DC=lab" \
  "(objectClass=user)" \
  sAMAccountName description

    Examine the description attribute on each account returned. The fact that guest.user can read these attributes is itself evidence of the permission delegation; in this case, guest.user has GenericAll on the Flags OU, which grants full control (including read and write) over every object inside it.

    Step 6: Understand the Permission Implication

    The guest.user account has GenericAll permissions on the Flags OU. GenericAll is the most powerful AD permission; equivalent to full control. In a real environment, GenericAll on an OU grants the following capabilities over every object within that OU:

    • Read all attributes on any object in the OU
    • Write all attributes on any object in the OU (modify descriptions, phone numbers, logon scripts)
    • Reset passwords for any user account in the OU (without knowing the current password)
    • Modify group membership for any group in the OU
    • Delete objects from the OU
    • Create new objects in the OU

    A penetration tester who discovers GenericAll on an OU containing privileged accounts could reset an administrator's password, log in as that administrator, and gain full domain control; all from a low-privilege starting point.

    Analysis Questions

    1. Why are ACL misconfigurations considered one of the most dangerous AD security issues?

    Reveal Answer

    ACL misconfigurations create invisible privilege escalation paths. Unlike a missing patch or a weak password, a misconfigured ACL does not generate alerts, does not appear in vulnerability scans, and persists until someone explicitly audits and corrects the permissions. An attacker who discovers a GenericAll permission on a privileged group can escalate to Domain Admin in seconds. Organizations with complex delegation models; where permissions are granted for helpdesk operations, provisioning workflows, or third-party integrations; are especially prone to ACL drift over time.

    2. How does permission inheritance amplify the risk of a single misconfigured ACL?

    Reveal Answer

    Permissions set on a parent OU propagate to every child object within it unless inheritance is explicitly blocked. A single GenericAll ACE on a top-level OU grants full control over potentially hundreds of user accounts, groups, and computer objects. The attacker does not need separate permissions on each object; the inherited permission covers them all. Auditing individual object ACLs without considering inheritance misses these cascading grants entirely.

    3. What tools do professional penetration testers use to map AD ACL attack paths at scale?

    Reveal Answer

    BloodHound is the primary tool for mapping AD ACL attack paths. BloodHound uses an ingestor (SharpHound or BloodHound.py) to collect ACL data, group memberships, session data, and trust relationships from AD. The collected data is loaded into a Neo4j graph database, and BloodHound's query engine identifies shortest paths from any compromised account to high-value targets like Domain Admins. PowerView (part of PowerSploit) and Impacket's dacledit.py provide command-line alternatives for querying and modifying AD ACLs.

    4. The guest.user account has GenericAll on the Flags OU. In a real engagement, what would your next steps be?

    Reveal Answer

    The next steps follow the attack chain: first, enumerate all objects in the Flags OU and identify which accounts have elevated privileges or interesting group memberships. For any user account in the OU, you could reset the password (using GenericAll's ForceChangePassword capability) and log in as that user. You would check whether the compromised account has access to additional systems, is a member of privileged groups, or has its own ACL-based permissions on other objects. Each compromised account becomes a new starting point for further enumeration and escalation.

    Key Takeaways

    • Every AD object has a DACL that controls who can read, modify, or delete the object
    • GenericAll grants full control, including the ability to reset passwords and modify group membership
    • Permission inheritance means a misconfigured OU ACL affects every object inside that OU
    • Low-privilege users with unexpected write access represent the most common AD attack paths
    • LDAP queries can discover objects and read attributes, revealing what permissions your account holds
    • Professional tools like BloodHound automate ACL analysis at domain-wide scale
    • ACL-based attacks do not exploit software vulnerabilities; they abuse legitimate AD features that have been misconfigured
    • Authenticated enumeration across all four labs in this chapter demonstrates the massive information gap between anonymous and authenticated access in Active Directory
