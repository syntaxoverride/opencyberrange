    Scenario

    The Plant 1 network tap recorded an hour of HMI polling traffic during a window when shift supervisors noted that the oven ran hot. The capture file is plant1_mixed_protocols.pcap, hosted at http://pcaphost.masa.local/. Download it to your Kali, open it in Wireshark, and decode the Modbus Read Holding Registers response that contains the anomalous oven setpoint.

    Why this matters

    Most real plant incident response runs on PCAPs that nobody knew would be important when they were captured. A shift supervisor notices oven temperature drift at 02:30, files a ticket, and goes home. The network tap has been rolling the whole time. Three weeks later, quality control pulls a batch of burnt tortillas off the line and asks "what happened that night?" The only honest answer is "open the PCAP and decode it."

    The skill this exercise teaches is protocol literacy on captured evidence. Without it you cannot reconstruct a historical incident, debunk a false positive from an IDS, or answer a regulator's question about whether a specific write ever hit a specific register during a specific window. With it you can walk into any plant, any vendor, any historical tape and pull the answer out of raw bytes. Protocol literacy is the single most portable OT forensic skill because every vendor eventually reuses Modbus/TCP somewhere in their stack.

    Background: Modbus/TCP on the Wire

    Modbus is one of the oldest still-deployed fieldbus protocols. The 1979 Modicon release targeted PLCs on a serial bus. Modbus/TCP is the 1999 wrapping that carries the same Application Data Unit (ADU) over TCP port 502. The ADU breaks into two parts:

    The MBAP Header (7 bytes)

    Offset Size Field Purpose
    0 2 Transaction Identifier Matches request to response, chosen freely by the client
    2 2 Protocol Identifier Always 0x0000 for Modbus
    4 2 Length Number of bytes that follow in this ADU
    6 1 Unit Identifier Slave address, usually 1 on Modbus/TCP

    The PDU (Function Code + Data)

    The first byte after the MBAP header is the function code. Function code 3 is Read Holding Registers. The next bytes depend on whether the frame is a request or a response.

    Direction PDU layout
    Request FC (1) | start_addr (2) | count (2)
    Response FC (1) | byte_count (1) | values (2 bytes per register)

    A single-register Read Holding Registers response therefore has a total wire length of 7 (MBAP) + 1 (FC) + 1 (byte_count) + 2 (value) = 11 bytes. You will confirm this byte count when you inspect the capture.

    No authentication, no integrity

    Everything above is on the wire in plaintext. The MBAP header has no signature, no nonce, and no encryption. Anyone on the operations VLAN who can read port 502 can decode every Modbus transaction. Anyone who can write port 502 can forge function codes and values. The security model is "the cable is trusted," and the cable is rarely trusted.

    Walkthrough

    Step 1: Download the PCAP

    Kali

    mkdir -p ~/plant1_forensics
cd ~/plant1_forensics
curl -O http://pcaphost.masa.local/plant1_mixed_protocols.pcap
ls -la plant1_mixed_protocols.pcap
    Expected output 
    -rw-r--r-- 1 kali kali 5583 Apr  1 14:00 plant1_mixed_protocols.pcap

    Step 2: Initial Triage with tshark

    Before opening Wireshark, get a feel for the capture with the command-line equivalent. The -z io,phs option prints a protocol hierarchy.

    Kali

    tshark -r plant1_mixed_protocols.pcap -q -z io,phs
    Expected output 

    ===================================================================
Protocol Hierarchy Statistics
Filter:

eth                                      frames:66 bytes:...
  ip                                     frames:66 bytes:...
    tcp                                  frames:66 bytes:...
      mbtcp                              frames:66 bytes:...
        modbus                           frames:66 bytes:...
===================================================================
    Every packet is Modbus. Sixty-six frames add up to thirty-three request/response pairs, which matches a roughly 60-second capture at a two-second polling cadence.

    Step 3: Open in Wireshark and Apply the Modbus Filter

    Open the PCAP in Wireshark:

    Kali

    wireshark plant1_mixed_protocols.pcap &

    Apply the display filter modbus in the filter bar. You will see alternating request and response frames. Modbus function code 3 (Read Holding Registers) covers every frame in this capture.

    Faster filter

    modbus.func_code == 3 && modbus.byte_cnt == 2 narrows the view to responses that return exactly one register (two bytes of payload). The anomalous setpoint response is a single-register response, so it lives in that filtered set.

    Step 4: Find the Anomalous Response

    A typical Plant 1 oven setpoint is around 3500 (tenths of a degree Fahrenheit, so 350.0 deg F). The anomalous response returns a value well above that baseline. Sort the filtered list by response value or simply scroll until you spot the outlier.

    Kali

    Using tshark from the command line: 

    tshark -r plant1_mixed_protocols.pcap \
  -Y 'modbus.func_code == 3 && modbus.byte_cnt == 2' \
  -T fields -e mbtcp.trans_id -e modbus.regval_uint16

    Expected output 

    265     3500
275     3500
277     4250
    Three single-register responses. The first two return the normal baseline setpoint. The third response returns 4250, which decodes to 425.0 degrees Fahrenheit, well into the range that Reyna flagged as anomalous.

    Step 5: Confirm the Decode by Hand

    Kali

    tshark -r plant1_mixed_protocols.pcap \
  -Y 'mbtcp.trans_id == 277' \
  -T fields -e frame.number -e ip.src -e ip.dst -e mbtcp.trans_id -e modbus.regval_uint16
    Expected output 

    44   172.30.1.13   172.30.1.10   277
45   172.30.1.10   172.30.1.13   277    4250
    Frame 44 is the HMI request. Frame 45 is the PLC response carrying the register value 4250. Transaction identifier 277 links the two frames.

    Step 6: Read the Raw Bytes

    Confirm the parser got it right by looking at the response frame in hex.

    Kali

    tshark -r plant1_mixed_protocols.pcap -Y 'frame.number == 45' -x | head -20
    Expected output (partial) 

    0030  ...  01 15 00 00 00 05 01 03 02 10 9a
    The last eleven bytes are the full Modbus ADU. Decoding by field:

    Bytes Field Value
    01 15 Transaction Identifier 277
    00 00 Protocol Identifier 0 (Modbus)
    00 05 Length 5 bytes follow
    01 Unit Identifier 1
    03 Function Code 3 (Read Holding Registers response)
    02 Byte Count 2 (one register)
    10 9a Register Value 4250

    The register value 4250 matches the tenths-of-a-degree scaling in the register map, so the decoded setpoint is 425.0 degrees Fahrenheit.

    Output Interpretation

    • A single-register Read Holding Registers response is exactly 11 bytes on the wire. Any deviation from 11 bytes on an FC3 response with byte count 0x02 is a protocol anomaly and worth investigating
    • MBAP transaction identifiers are chosen by the client. A real capture of a well-behaved HMI will show monotonically increasing identifiers with small gaps
    • Register values returned in tenths of a degree are a Maxon Controls convention. Other vendors use different scalings; always confirm the scaling from the vendor's register map before interpreting the number
    • Wireshark's modbus.regval_uint16 is the parsed integer value, not a hex dump. Use -x to cross-check against the raw bytes when you are new to a protocol

    Analysis Questions

    1. Why does the MBAP header include a Transaction Identifier instead of relying on TCP sequence numbers to pair requests and responses?

    Reveal answer

    Modbus was designed to carry multiple logical transactions over a single TCP connection, and a client can pipeline requests without waiting for the previous response. The transaction identifier gives the client a cheap way to match responses back to the originating request regardless of TCP-level ordering or any intermediate gateway that might reorder frames. Because the identifier is chosen by the client and never validated, it is also a handy fingerprint for traffic analysis (see Exercise 1.4).

    2. How would you detect the anomalous setpoint read in near real time rather than hours later from a PCAP?

    Reveal answer

    Deploy a Modbus-aware monitoring tool (Zeek with the Modbus parser, a passive Modbus probe, or a commercial tool like Dragos or Claroty) that baselines the normal value range for each polled register. Alert when the returned value steps outside the baseline. A simple Zeek script can do the read-side baseline in under fifty lines.

    3. Wireshark shows the protocol as mbtcp in some places and modbus in others. What is the difference?

    Reveal answer

    Wireshark's mbtcp dissector handles the MBAP header (transaction ID, protocol ID, length, unit ID). The modbus dissector handles the PDU (function code and data). You use mbtcp.trans_id for header fields and modbus.func_code or modbus.regval_uint16 for PDU fields. The separation is historical: the same Modbus PDU rides over both serial Modbus (RTU and ASCII) and TCP, and each transport has a distinct dissector.

    4. Could you run pymodbus against the captured traffic to decode it instead of Wireshark?

    Reveal answer

    Not directly. pymodbus is a live client and does not parse PCAP files. You would either use Wireshark or tshark for dissection, or write a small Python parser using scapy (which has a Modbus contrib layer) or raw byte slicing against the MBAP header layout. For training, Wireshark remains the gold standard because it shows both the parsed fields and the hex bytes side by side.

    Key Takeaways

    • MBAP header is seven bytes: transaction ID, protocol ID, length, unit ID
    • Function code 3 response wire format is FC | byte_count | values
    • Transaction ID is the pairing fingerprint for matching requests to responses
    • Wireshark -x hex dump is the fastest way to sanity-check a parser
    • Decoding scaled register values (tenths of a degree) requires a copy of the vendor's register map
