    Exercise WS-3.3: DHCP Scope Reconnaissance

    Before You Begin

    Exercises WS-3.1 and WS-3.2 focused on DNS; querying SRV records and detecting conditional forwarders. Exercise WS-3.3 shifts to a different protocol: Dynamic Host Configuration Protocol (DHCP). While DNS tells you what services exist and where they live, DHCP reveals how the network itself is structured; address ranges, gateways, DNS servers, and custom options that administrators configure for client machines. Combining DHCP data with DNS findings produces a much richer picture of the environment.

    • Confirm your VPN connection is active and you can reach dc01.
    • No credentials are needed; DHCP discovery uses broadcast packets that any client on the network can send.
    • You should be comfortable running Nmap from a Linux terminal.

    Scenario

    Your team has mapped the DNS infrastructure of corp.ocr-range.lab across Exercises WS-3.1 and WS-3.2. The next task is to understand the network addressing layer. The Domain Controller dc01 also runs the DHCP server role; a common configuration in Windows Server environments. DHCP scopes define which IP ranges are assigned to clients, which gateways and DNS servers clients receive, and what custom options are pushed. Your objective is to enumerate the DHCP scope on dc01, identify its configuration, and examine custom DHCP options; particularly option 252, the Web Proxy Auto-Discovery (WPAD) URL, which has a well-documented history of abuse in man-in-the-middle (MITM) attacks.

    Your Objectives

    • Discover DHCP services running on dc01
    • Enumerate DHCP scope details including address range, subnet mask, gateway, and DNS servers
    • Identify custom DHCP options, particularly option 252 (WPAD)
    • Understand the security implications of WPAD in enterprise environments
    • Extract the flag from DHCP response data

    Background: DHCP in Active Directory Environments

    DHCP assigns IP addresses and network configuration to clients automatically. When a client connects to a network, it sends a DHCP Discover broadcast. A DHCP server responds with an Offer containing an available IP address, subnet mask, default gateway, DNS servers, and any custom options the administrator has configured. The client then requests the offered configuration, and the server acknowledges the assignment.

    In many AD environments, the Domain Controller runs the DHCP server role alongside DNS and AD Directory Services (AD DS). Hosting DHCP on the DC centralizes management but also means that the DC responds to DHCP queries from any client on the network segment. A penetration tester can send a DHCP Discover packet and receive the full scope configuration without authentication.

    DHCP options extend the base configuration with additional parameters. Each option has a numeric code and a value. Some common options include:

    Option Name Purpose
    1 Subnet Mask Defines the network mask for the assigned IP
    3 Router Default gateway address
    6 DNS Servers DNS server addresses for name resolution
    15 Domain Name DNS domain suffix for the client
    252 WPAD URL URL for proxy auto-configuration script

    Option 252 deserves special attention. WPAD allows clients to automatically discover a web proxy by fetching a configuration file from a URL pushed by DHCP. Attackers who can inject a malicious WPAD URL; through DHCP spoofing or DNS poisoning; can redirect all HTTP traffic through a proxy they control. Even when configured legitimately, the WPAD option reveals internal proxy infrastructure that may be vulnerable to attack.

    The discovery process does not require the client to be domain-joined or authenticated. Any device on the network segment can send a DHCP Discover and receive the full scope configuration.

    Tool Primer: Nmap DHCP Discovery Scripts

    Nmap includes Nmap Scripting Engine (NSE) scripts specifically designed for DHCP enumeration. Two scripts are relevant for this exercise.

    dhcp-discover script:

    The dhcp-discover script sends a DHCP Discover packet to a specific host and displays the response, including all DHCP options.

    nmap --script dhcp-discover -sU -p 67 <target>

    broadcast-dhcp-discover script:

    The broadcast-dhcp-discover script sends a broadcast DHCP Discover packet. Any DHCP server on the network segment will respond, making this useful for discovering unknown DHCP servers.

    nmap --script broadcast-dhcp-discover

    Key flags:

    Flag Purpose
    --script dhcp-discover Targeted DHCP query to a specific server
    --script broadcast-dhcp-discover Broadcast DHCP discovery on the local segment
    -sU UDP scan (DHCP uses UDP)
    -p 67 Target DHCP server port (67/UDP)

    Sample output:

    PORT   STATE SERVICE
67/udp open  dhcps
| dhcp-discover:
|   DHCP Message Type: DHCPACK
|   Server Identifier: <dc01_ip>
|   IP Address Lease Time: 8d00h00m00s
|   Subnet Mask: 255.255.255.0
|   Router: <gateway_ip>
|   Domain Name Server: <dc01_ip>
|   Domain Name: corp.ocr-range.lab
|   WPAD: http://wpad.corp.ocr-range.lab/wpad.dat

    The output reveals the full DHCP configuration in a readable format. Each line corresponds to a DHCP option and its value. The WPAD entry shows the proxy auto-configuration URL pushed to all clients.

    Walkthrough

    Step 1: Launch the Lab and Verify Connectivity

    Navigate to Exercises, then Windows Server, then Level 3, and launch Exercise WS-3.3. Wait for the environment status to show Running.

    Verify connectivity to dc01

    Verify you can reach dc01 with a short ping. The -c 3 flag sends three packets and then exits.

    ping -c 3 dc01

    You should see replies confirming network connectivity. If the ping times out, check your VPN connection.

    Step 2: Confirm DHCP Service on dc01

    Before enumerating DHCP options, confirm that dc01 is running a DHCP server. DHCP servers listen on UDP port 67. A targeted UDP scan reveals whether the port is open.

    Scan for the DHCP port on dc01

    Run a UDP scan against port 67 to confirm dc01 is listening for DHCP. The -sU flag selects a UDP scan and -p 67 limits it to the DHCP server port.

    nmap -sU -p 67 dc01

    The output should show port 67/udp as open. UDP scanning is inherently less reliable than TCP scanning because UDP does not use a three-way handshake; an open port may appear as open|filtered if no response is received. The DHCP discovery scripts in the next steps will confirm the service definitively by eliciting an actual DHCP response.

    Step 3: Run DHCP Discovery Against dc01

    With the DHCP port confirmed, run the dhcp-discover NSE script to retrieve the full scope configuration from dc01.

    Run targeted DHCP discovery against dc01

    Execute the targeted DHCP discovery. The dhcp-discover NSE script sends a DHCP Discover packet to dc01 and prints every option the server returns.

    nmap --script dhcp-discover -sU -p 67 dc01

    Examine the output carefully. The script sends a DHCP Discover packet directly to dc01 and displays the server's response. Look for the following fields in the output:

    • Server Identifier: The IP address of the DHCP server (should match dc01)
    • Subnet Mask: Defines the size of the network (e.g., 255.255.255.0 for a /24)
    • Router: The default gateway clients will use
    • Domain Name Server: The DNS server(s) pushed to clients
    • Domain Name: The DNS suffix for the domain
    • WPAD: The Web Proxy Auto-Discovery URL (option 252)

    Record each value. Together, these fields describe the network architecture that every client on the subnet receives automatically.

    Step 4: Run Broadcast DHCP Discovery

    The broadcast method discovers all DHCP servers on the network segment, not a single target. Running both targeted and broadcast discovery ensures you do not miss rogue DHCP servers.

    Run broadcast DHCP discovery

    Execute the broadcast discovery. The broadcast-dhcp-discover script sends its DHCP Discover to the whole segment, so any DHCP server present replies.

    nmap --script broadcast-dhcp-discover

    Compare the results with the targeted discovery from Step 3. The responding server should be dc01. If additional DHCP servers respond, note their IP addresses; rogue DHCP servers are a serious security concern in any network.

    The broadcast script does not require a target IP because the DHCP Discover packet is sent to the broadcast address (255.255.255.255). Every DHCP server on the local segment will respond.

    Step 5: Analyze the WPAD Option

    Option 252 (WPAD) pushes a URL to clients that points to a Proxy Auto-Configuration (PAC) file. When a client receives the WPAD URL through DHCP, the operating system's proxy settings automatically fetch the PAC file and configure web traffic routing.

    Review the WPAD value from your DHCP discovery output. The URL typically follows the format:

    http://wpad.corp.ocr-range.lab/wpad.dat

Clients that trust the DHCP response will route their HTTP traffic through the attacker's proxy, enabling credential interception and content manipulation. Tools like Responder exploit WPAD poisoning as a primary attack vector in Windows networks.

    Analysis Questions

    1. Why is hosting DHCP on the Domain Controller a common but risky configuration?

    Reveal Answer

    Hosting DHCP on the DC centralizes network management and reduces the number of servers to maintain. The risk is that a compromise of the DC also compromises DHCP, allowing the attacker to push malicious configurations; rogue DNS servers, WPAD URLs, or incorrect gateways; to every client on the network. Separating roles limits the blast radius of a single server compromise.

    2. How can an attacker abuse the WPAD option in a DHCP response?

    Reveal Answer

    An attacker who controls DHCP responses (through a rogue server or spoofing) can push a WPAD URL pointing to a malicious PAC file. Clients that auto-configure proxy settings will route HTTP traffic through the attacker's proxy. The attacker can then intercept credentials transmitted over HTTP, inject content into web pages, or redirect users to phishing sites. Tools like Responder automate WPAD poisoning in Windows environments.

    3. What defenses can an organization deploy against DHCP-based attacks?

    Reveal Answer

    DHCP snooping on network switches restricts DHCP responses to trusted ports, preventing rogue servers from responding. Disabling WPAD through Group Policy removes the auto-configuration vector. 802.1X port-based authentication ensures only authorized devices receive network access. Monitoring DHCP logs for unexpected scope changes or option modifications provides detection capability.

    Key Takeaways

    • DHCP scopes reveal network architecture: address ranges, gateways, DNS servers, and domain suffixes are all visible without authentication
    • Nmap NSE scripts for DHCP discovery (dhcp-discover and broadcast-dhcp-discover) extract the full scope configuration from a DHCP server
    • Option 252 (WPAD) pushes proxy auto-configuration URLs to clients and is a well-known vector for MITM attacks
    • Broadcast DHCP discovery detects rogue DHCP servers that targeted scans would miss
    • DHCP data complements DNS findings: combining scope information with SRV records and conditional forwarders builds a complete network map
