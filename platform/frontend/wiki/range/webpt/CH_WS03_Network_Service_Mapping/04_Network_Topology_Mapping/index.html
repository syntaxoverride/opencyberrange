    Exercise WS-3.4: Network Topology Mapping

    Before You Begin

    Exercises WS-3.1 through WS-3.3 each focused on a single protocol; DNS SRV records, conditional forwarders, and DHCP scopes. Exercise WS-3.4 brings these data sources together. Network topology mapping is the practice of correlating findings from multiple protocols to build a complete picture of an environment. A DNS record alone tells you a hostname exists. A DHCP scope alone tells you an address range is in use. Combined with Lightweight Directory Access Protocol (LDAP) computer objects, these fragments form a map that reveals the full network architecture.

    • Confirm your VPN connection is active and you can reach dc01.
    • LDAP anonymous bind must be available on dc01 for the user attribute query in the second half of this exercise.
    • You should be comfortable with dig, nmap, and ldapsearch from previous exercises.

    Scenario

    Your assessment of corp.ocr-range.lab is nearing completion. You have enumerated DNS SRV records, discovered a conditional forwarder to partner.local, and extracted DHCP scope data. Your team lead wants a consolidated network topology that correlates all findings. The final deliverable requires combining DNS hostnames, DHCP addressing, and LDAP computer objects into a single view. A two-part flag validates your work: the first part comes from a DNS TXT record, and the second part comes from an LDAP user attribute. Assembling the complete flag demonstrates your ability to correlate data across protocols.

    Your Objectives

    • Correlate DNS records with LDAP computer objects to identify all hosts in the domain
    • Map the DHCP scope to the discovered hosts
    • Build a network topology diagram from combined data sources
    • Retrieve Part 1 of the flag from a DNS TXT record
    • Retrieve Part 2 of the flag from an LDAP user attribute
    • Assemble the complete multi-part flag

    Background: Cross-Protocol Correlation

    No single protocol provides a complete view of an Active Directory (AD) environment. DNS contains SRV records and hostname-to-IP mappings, but DNS does not know which machines are domain-joined or what roles they serve. LDAP stores computer objects with attributes like operating system, organizational unit (OU) placement, and service principal names (SPNs), but LDAP does not reveal network addressing. DHCP defines address ranges and network parameters, but DHCP does not know hostnames or domain roles.

    Effective network mapping requires layering these data sources. Start with DNS to build a list of hostnames and their IP addresses. Add LDAP computer objects to confirm which machines are domain-joined and what operating systems they run. Overlay the DHCP scope to understand which addresses are dynamically assigned versus statically configured. The result is a topology that shows what exists and how the network is organized.

    In penetration testing, cross-protocol correlation reveals inconsistencies that attackers exploit. A computer object in LDAP with no corresponding DNS record may be a decommissioned machine that was never removed from the directory. A DHCP reservation for a hostname not found in DNS may indicate a device that bypasses normal name resolution. A DNS A record pointing to an address outside the DHCP scope may be a server with a static IP that the DHCP scope does not manage. Each inconsistency is a potential finding worth investigating.

    Tool Primer: ldapsearch for Computer and User Queries

    The ldapsearch command queries LDAP directories from the command line. For topology mapping, you will query both computer objects and user objects. Computer objects live in the default CN=Computers container or in custom OUs. User objects used for flag storage may reside in a dedicated Flags OU.

    Syntax for computer enumeration:

    ldapsearch -x -H ldap://dc01 -b "DC=corp,DC=ocr-range,DC=lab" \
  "(objectClass=computer)" cn operatingSystem dNSHostName

    Syntax for user attribute query:

    ldapsearch -x -H ldap://dc01 -b "OU=Flags,DC=corp,DC=ocr-range,DC=lab" \
  "(cn=topo.flag)" info

    Key flags:

    Flag Purpose
    -x Use simple authentication (anonymous bind)
    -H Specify the LDAP server URI
    -b Set the search base Distinguished Name (DN)
    (filter) LDAP search filter to match specific objects

    Sample computer object output:

    dn: CN=DC01,OU=Domain Controllers,DC=corp,DC=ocr-range,DC=lab
cn: DC01
operatingSystem: Windows Server 2022 Standard
dNSHostName: dc01.corp.ocr-range.lab

    Each computer object contains the hostname (cn), operating system, and DNS hostname. Cross-referencing dNSHostName with DNS A records confirms the machine's IP address.

    Sample user attribute output:

    dn: CN=topo.flag,OU=Flags,DC=corp,DC=ocr-range,DC=lab
cn: topo.flag
info: <flag_part>

    The info attribute on user objects stores a freeform string. In this exercise, the Flags OU contains a user object whose info attribute holds the second part of the flag.

    Walkthrough

    Step 1: Launch the Lab and Verify Access

    Navigate to Exercises, then Windows Server, then Level 3, and launch Exercise WS-3.4. Wait for the environment status to show Running.

    Verify DNS, LDAP, and network access

    Verify all three data sources respond before you start mapping. The three commands confirm DNS resolution, anonymous LDAP bind, and basic reachability in turn.

    dig +short A dc01.corp.ocr-range.lab @dc01
ldapsearch -x -H ldap://dc01 -b "" -s base namingContexts
ping -c 2 dc01

    The dig query should return dc01's IP address. The ldapsearch query should return the naming contexts, confirming anonymous LDAP access. The ping confirms basic connectivity. If any of these fail, check your VPN connection before continuing.

    Step 2: Enumerate DNS A Records

    DNS A records map hostnames to IP addresses. Querying for A records across the corp.ocr-range.lab zone builds the hostname layer of your topology.

    Attempt a zone transfer for all A records

    Attempt a zone transfer to get all records at once. The AXFR query type returns the entire zone when the server permits it.

    dig AXFR corp.ocr-range.lab @dc01

    If the zone transfer succeeds, extract all A records from the output.

    Query individual A records if the transfer is denied

    If the transfer is denied, query for known hostnames individually and repeat for each name you suspect exists.

    dig +short A dc01.corp.ocr-range.lab @dc01

    Record every hostname-to-IP mapping you discover. These become the nodes in your topology diagram.

    Step 3: Enumerate LDAP Computer Objects

    LDAP computer objects represent domain-joined machines. Querying for all computer objects reveals machines that DNS may not list; such as workstations that were joined to the domain but never received a DNS A record.

    Enumerate LDAP computer objects

    Run the computer object query. The -x flag uses an anonymous bind, and the (objectClass=computer) filter returns only machine accounts.

    ldapsearch -x -H ldap://dc01 -b "DC=corp,DC=ocr-range,DC=lab" \
  "(objectClass=computer)" cn operatingSystem dNSHostName

    The output lists every computer object in the domain. For each entry, note the cn (common name), operatingSystem, and dNSHostName attributes. Compare the dNSHostName values with the DNS A records from Step 2.

    Machines that appear in LDAP but not in DNS may have been removed from DNS but not from the directory. Machines in DNS but not in LDAP may be non-domain-joined devices with static DNS entries.

    Step 4: Review DHCP Scope Data

    Retrieve the DHCP scope data

    If you completed Exercise WS-3.3, you already have the DHCP scope data. Retrieve it again if needed with the same dhcp-discover NSE script.

    nmap --script dhcp-discover -sU -p 67 dc01

    From the DHCP response, record:

    • Subnet and mask: defines the address range for the network segment
    • Gateway: the default route for all clients
    • DNS server: should match dc01's IP address
    • Domain name: should match corp.ocr-range.lab

    Compare the DHCP address range with the IP addresses you found in DNS A records. Addresses within the DHCP scope are likely dynamically assigned to workstations. Addresses outside the scope (but within the same subnet) are likely statically assigned to servers.

    Step 5: Build the Correlated Topology

    Combine your findings from DNS, LDAP, and DHCP into a single topology view. The goal is a map that shows every discovered host, its IP address, its role, and whether it uses static or dynamic addressing.

    Use the following template to organize your data:

    Hostname IP Address Source(s) OS / Role Addressing
    dc01.corp.ocr-range.lab ____ DNS, LDAP, DHCP Windows Server 2022 DC Static
    (additional hosts) ____ _____ _____ ____

    Hosts that appear in all three sources are well-documented infrastructure. Hosts that appear in only one source are anomalies worth investigating.

    Step 6: Retrieve Flag Part 1 from DNS

    Query the topology TXT record

    The first part of the flag is stored in a DNS TXT record. TXT records often contain metadata, verification strings, or documentation notes. Search for topology-related TXT records by reviewing the zone transfer output from Step 2 for TXT entries, or probe common naming patterns related to topology (e.g., prefixes like _topo, _map, or _net). Replace <record_name> with each candidate.

    dig TXT <record_name>.corp.ocr-range.lab @dc01

    The ANSWER SECTION contains a quoted string. Record the value; the string is the first half of the flag.

    Confirm the TXT value with short output

    You can also use the short format for a cleaner view of the same record.

    dig +short TXT _topo1.corp.ocr-range.lab @dc01

    The response should return a quoted string value. Note the exact value including any special characters.

    Step 7: Retrieve Flag Part 2 from LDAP

    The second part of the flag is stored in an LDAP user object's info attribute. The user topo.flag exists in the Flags OU within the domain directory. Querying this user object requires an LDAP search with the correct base DN and filter.

    Enumerate the Flags OU for user objects

    Enumerate the Flags OU in the domain directory and look for user objects with interesting attributes. Start by listing all user objects in the Flags OU, requesting the cn and info attributes.

    ldapsearch -x -H ldap://dc01 -b "OU=Flags,DC=corp,DC=ocr-range,DC=lab" \
  "(objectClass=user)" cn info

    Review the results for user objects whose names relate to topology or mapping. Once you identify the relevant user object, examine its info attribute; the second half of the flag lives there.

    Broaden the search to the whole domain

    If the query returns no results, broaden the search base to the entire domain rather than a single OU.

    ldapsearch -x -H ldap://dc01 -b "DC=corp,DC=ocr-range,DC=lab" \
  "(objectClass=user)" cn info

    The broader search base looks across the entire domain rather than a specific OU. The info attribute should return the second part of the flag.

    Step 8: Assemble the Complete Flag

    The full flag combines Part 1 (from DNS) and Part 2 (from LDAP). Concatenate the two values inside the OCR{...} wrapper.

    • Part 1 (DNS TXT): The value from the TXT record query in Step 6
    • Part 2 (LDAP info): The value from the LDAP query in Step 7
    • Complete flag: OCR{<part1><part2>}

    The multi-part flag structure demonstrates the core principle of this exercise: no single protocol provides the complete answer. Correlating DNS and LDAP data produces information that neither source contains alone.

    Analysis Questions

    1. Why is cross-protocol correlation more valuable than querying a single data source?

    Reveal Answer

    Each protocol reveals different aspects of the environment. DNS provides hostname-to-IP mappings and service locations. LDAP provides computer object details, OS versions, and organizational structure. DHCP provides network addressing and configuration. Correlating all three produces a topology that no single source can provide alone. Inconsistencies between sources; such as a computer in LDAP with no DNS record; often point to misconfigurations or decommissioned systems that were not fully cleaned up.

    2. What does a computer object in LDAP without a corresponding DNS A record suggest?

    Reveal Answer

    The computer account may belong to a machine that was decommissioned but never removed from the directory. Stale computer accounts retain their passwords and SPNs in AD. An attacker who can reset or impersonate a stale computer account may gain access to the domain with that machine's identity. AD hygiene policies should regularly audit and remove inactive computer accounts.

    3. How would you extend this methodology to a multi-site AD environment?

    Reveal Answer

    Multi-site AD environments contain site-specific SRV records under _tcp.<site-name>._sites. subdomains. Querying these reveals which DCs serve each site. DHCP scopes differ per subnet, so each site has its own address range and gateway. LDAP site objects under CN=Sites,CN=Configuration describe the site topology and subnet-to-site mappings. Correlating all of these across sites produces a complete enterprise topology.

    4. What LDAP attributes on computer objects are most useful for topology mapping?

    Reveal Answer

    The dNSHostName attribute links the LDAP object to its DNS name. The operatingSystem and operatingSystemVersion attributes identify the OS. The servicePrincipalName (SPN) attribute reveals what services the machine hosts (e.g., HTTP, MSSQL, Exchange). The whenCreated and lastLogonTimestamp attributes indicate whether the machine is active. The managedBy attribute may link the machine to a responsible user or group.

    Key Takeaways

    • Cross-protocol correlation combines DNS, LDAP, and DHCP data into a topology that no single source can provide
    • Inconsistencies between sources reveal decommissioned systems, misconfigurations, and shadow IT that attackers exploit
    • DNS provides hostnames and service locations, LDAP provides computer objects and organizational context, and DHCP provides network addressing
    • Multi-part flags mirror real-world assessments where complete findings require data from multiple sources
    • Topology mapping is a deliverable: clients expect penetration test reports to include network diagrams built from correlated evidence, not assumptions
