    Exercise OTSOC-3.1: Mapping the Intrusion

    Engagement Status

    Client Pecan Creek Creamery (fictional)
    Role OT SOC Analyst, Plant Floor
    Phase Reconstruction Detection Engineering Threat Hunting

    What you know so far: Last shift, a rogue host on the OT segment reached the blend tank, swept its Modbus holding registers, then wrote new setpoints. The attack is already over. Your job is not to attack anything; it is to reconstruct what happened and translate it into a shared vocabulary the whole team can defend against.

    Scenario

    Pecan Creek Creamery ran an unauthorized intrusion against the blend tank and freezer lines last shift. A rogue host at 172.31.4.66 swept the Modbus holding registers on the blend tank, then issued function code 6 writes that flipped the recipe and the agitator setpoint. The plant sensor and the pcap host preserved the evidence. The blend tank PLC is mix.pcc.local, a Pecan Creek Controls PCCK-300 on Modbus/TCP port 502.

    Your role is the SOC analyst on the day-after. The adversary already acted. You walk the capture and the Zeek logs, list each action in order, and translate raw packets into MITRE ATT&CK for ICS technique IDs. The deliverable is a coverage table you submit to the plant rubric grader at rubric.pcc.local, which scores your mapping against a canonical checklist and releases the flag once your coverage clears the pass threshold.

    Why this matters

    A pile of packets is not an incident report. Until you can name what the adversary did in a vocabulary your detection engineers, your management, and your peers at other plants all recognize, the capture is just noise on a disk. MITRE ATT&CK for ICS is that vocabulary. Mapping a real intrusion to technique IDs is the bridge between "something weird happened" and "here is the detection we are building so it never happens silently again."

    Mapping also forces honesty about coverage. When you write down that the rogue host ran a register sweep (T0846 Remote System Discovery) and you realize no sensor rule would have caught it, you have just found a detection gap before the next adversary does. The coverage table you hand the grader is the same artifact a real OT SOC hands its detection-engineering backlog: each row is a technique observed, the data source that revealed it, and the rule you owe.

    Before You Begin: Read the Network Panel

    After the lab shows Running, the Exercise Network panel on the track page lists every target with its IP. Two hosts matter here: the PCAP evidence host and the rubric grader. Copy their IPs into shell variables so the walkthrough commands work without hardcoding any subnet octets.

    Kali - set target variables from the Exercise Network panel

    # Replace each value with the IP shown in the Exercise Network panel.
PCAP=<pcaphost-ip-from-panel>     # pcaphost.pcc.local, HTTP/80
RUBRIC=<rubric-ip-from-panel>     # rubric.pcc.local, HTTP/80
echo "pcap=$PCAP rubric=$RUBRIC"

    A quick reachability check confirms both hosts answer before you invest time in analysis. A succeeded! on each line means you are wired into the plant network.

    Kali - confirm both evidence hosts are reachable

    nc -zv "$PCAP" 80
nc -zv "$RUBRIC" 80

    If either probe hangs or reports No route to host, the lab is not fully Running yet, or your VPN tunnel dropped. Fix connectivity before continuing.

    Walkthrough

    Step 1: Pull the Capture Index

    The pcap host serves a small library of curated captures over plain HTTP. List them first so you know which file holds the blend tank intrusion. The index is a simple directory page.

    Kali - list the available captures

    curl -s "http://$PCAP/" | grep -oE '[a-z-]+\.pcap'

    You should see four captures: baseline.pcap, attack-mix.pcap, pasteurizer-divert.pcap, and ammonia-trip.pcap. The blend tank intrusion lives in attack-mix.pcap. The baseline.pcap is your benign reference: the HMI polling the freezer with read-only function code 3 every couple of seconds, nothing writing.

    Step 2: Download the Attack Capture

    Pull attack-mix.pcap to your Kali so you can analyze it offline with Zeek and Wireshark. Saving to /tmp keeps it as scratch you can re-parse.

    Kali - download the blend tank attack capture

    curl -s "http://$PCAP/attack-mix.pcap" -o /tmp/attack-mix.pcap
ls -l /tmp/attack-mix.pcap

    A non-zero file size confirms the download. If the file is empty, re-check that attack-mix.pcap appeared in the Step 1 listing and that $PCAP holds the right IP.

    Step 3: Run Zeek to Extract the Modbus Conversation

    Wireshark is fine for a visual pass, but Zeek with the ICSNPP Modbus analyzer turns the capture into a flat modbus.log you can grep and reason about. Run Zeek against the pcap in a scratch directory so the log files land somewhere tidy.

    Kali - parse the capture with Zeek

    mkdir -p /tmp/zeek-mix && cd /tmp/zeek-mix
zeek -C -r /tmp/attack-mix.pcap
ls

    Zeek writes conn.log, modbus.log, and possibly modbus_detailed.log. The -C flag tells Zeek to ignore TCP checksum errors that are common in curated captures. If zeek is not on your Kali, the same analysis works in Wireshark by filtering on modbus.

    Step 4: Identify the Read Sweep

    Open modbus.log and look at the function codes the rogue host issued. The attack always starts with reconnaissance: a sweep of read requests across the holding-register bands to learn the tank's layout before touching anything. In Modbus, that is function code 3 (read holding registers).

    Kali - list every Modbus request with its source and function

    zeek-cut -d ts id.orig_h id.resp_h func < modbus.log | head -40

    Watch the id.orig_h column. The legitimate poller appears repeatedly with READ_HOLDING_REGISTERS, but the rogue source 172.31.4.66 issues a burst of reads walking across different register offsets in a short window. A single host reading every register band in sequence is not normal operator polling; it is enumeration. Map that pattern to T0846 Remote System Discovery: the adversary is mapping the control device before acting on it.

    Step 5: Identify the Unauthorized Write

    After the sweep, the rogue host stops reading and starts writing. In Modbus, a setpoint change uses function code 6 (write single register). Legitimate HMIs almost never write; they poll. A write from an unexpected host is the action that actually changed the process.

    Kali - isolate the write operations

    zeek-cut -d ts id.orig_h func < modbus.log | grep -i write

    Every write line should trace back to 172.31.4.66. The captured writes hit register 40002 (the agitator setpoint) and 40030 (the recipe id), flipping the blend recipe and the agitator speed. Two ATT&CK techniques apply to this one observation. The act of sending a command the adversary was never authorized to send is T0855 Unauthorized Command Message. The effect of that command, changing a control parameter that alters the physical process, is T0836 Modify Parameter. A clean coverage table records both, because a detection that catches the command on the wire (T0855) is a different rule from a detection that catches the parameter changing on the PLC (T0836).

    Step 6: Pin the Rogue Host

    Confirm that the malicious reads and writes share one source and that the source is not a known plant asset. The Pecan Creek OT segment is a 10.100.x.0/24 per-student subnet; a 172.31.4.66 source is plainly foreign.

    Kali - confirm the rogue source owns the malicious traffic

    zeek-cut id.orig_h func < modbus.log | sort | uniq -c | sort -rn

    The output groups every source by how many of each function it sent. The legitimate poller shows many reads and zero writes. The host 172.31.4.66 shows the enumeration burst plus the writes. One foreign host performing both the discovery and the parameter change is your attacker, and naming it is part of the deliverable.

    Step 7: Check the Required Elements, Then Submit

    The grader publishes the exact elements your coverage table must cover before you write it. Always read the rubric first so you do not submit a table that misses a required column.

    Kali - read the required elements for this deliverable

    curl -s "http://$RUBRIC/rubric?deliverable=detection-mapping"

    The response lists what the grader scores: the technique IDs, the unauthorized write, the read sweep, the rogue host, and a proposed detection signature. Assemble your coverage table as free text addressing each element, then POST it. The grader compares your submission against its canonical checklist and returns the flag when you clear the 0.8 threshold.

    Coverage table shape (fill in from your own analysis)

    T0846 Remote System Discovery -- rogue host 172.31.4.66 ran an FC3 read
  sweep across the blend tank holding-register bands. Data source: Zeek
  modbus.log func=READ_HOLDING_REGISTERS from a non-engineering host.
  Detection: alert on a single source reading many register offsets in a
  short window.
T0855 Unauthorized Command Message -- the FC6 write itself, sent from a
  host that is not the engineering workstation. Data source: modbus.log
  func write_single_register. Detection: alert on any FC6 from a
  non-allowlisted source.
T0836 Modify Parameter -- the FC6 writes changed agitator setpoint (40002)
  and recipe id (40030), altering the blend. Detection: alert when a
  protected setpoint register changes outside a maintenance window.

    Kali - submit your coverage table to the grader

    curl -s -X POST "http://$RUBRIC/check" \
  -H 'Content-Type: application/json' \
  -d '{"deliverable":"detection-mapping","submission":"<your coverage table here>"}'

    A passing submission returns a JSON body containing your flag. If the score comes back below threshold, re-read the rubric output and add the element you missed, most commonly the rogue host source or the explicit detection signature, then POST again.

    Output Interpretation

    • A burst of function code 3 reads from one host walking sequential register offsets is enumeration, not polling. Operator HMIs poll the same small set of registers on a fixed cadence; an attacker reads everything once.
    • Any function code 6 (or 16) write on this network is suspicious by default. The legitimate HMI is read-only, so a write is either a sanctioned maintenance change inside a window or an attack.
    • A source IP outside the plant /24 is the single loudest signal in the whole capture. Asset inventory plus a foreign source equals an intrusion you can prove.
    • One technique ID is rarely enough. The same FC6 write maps to both T0855 (the message) and T0836 (the effect), and your detection engineers will build two different rules from those two rows.

    Analysis Questions

    1. Why does the read sweep matter if the damage was done by the write?

    Reveal answer

    The sweep is the earliest detectable moment of the intrusion. The write changed the process, but the enumeration that preceded it is your earliest warning and your best early-detection opportunity. A rule that alerts on a single host reading every register band would have fired before any parameter was touched, giving operations time to isolate the rogue host. Mapping T0846 documents that early-detection opportunity even though it caused no direct harm.

    2. The same FC6 write maps to both T0855 and T0836. Why record both instead of picking one?

    Reveal answer

    The two technique IDs drive two different detections. T0855 Unauthorized Command Message is a network signal: alert on the command on the wire from an unexpected source. T0836 Modify Parameter is a process signal: alert when the setpoint value on the PLC changes. A network rule can be evaded (encrypted tunnel, spoofed source) while the process rule still catches the effect, and vice versa. Defenders want both rows so they build defense in depth.

    3. The rogue source is 172.31.4.66, which is not on the plant subnet. What does that tell you about the intrusion path?

    Reveal answer

    A foreign source on the OT segment means the boundary between IT and OT failed somewhere: a flat network, a misconfigured firewall rule, a compromised jump host, or a rogue device plugged into the plant. The Modbus capture proves the OT-layer action, but the foreign source IP is a pointer to a separate investigation into how that host reached the control network at all. Record it as both a rogue actor and a segmentation finding.

    Key Takeaways

    • ATT&CK for ICS is the shared vocabulary that turns a packet capture into a defensible incident narrative and a detection backlog.
    • Reconstruction is read-only. You parse evidence the adversary already created; you never replay the attack against the live PLC.
    • A coverage table pairs each observed technique with the data source that revealed it and the rule you owe, which is exactly how a real OT SOC tracks detection gaps.
    • Read the grader rubric before you write your submission. Missing one required element (usually the rogue host or the detection signature) is the most common reason a table scores below threshold.
