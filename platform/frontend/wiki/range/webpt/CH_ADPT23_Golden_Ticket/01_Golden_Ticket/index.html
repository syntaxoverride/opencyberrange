    Exercise 5.4: Golden Ticket

    Before You Begin

    A golden ticket is a forged TGT. The attacker possesses krbtgt's NT hash (or AES key) and uses it to encrypt a TGT for any user, with any group memberships, with any lifetime. Every DC in the domain accepts the forged TGT as authentic because krbtgt's hash is what every DC uses to validate TGTs. The forgery is undetectable in the ticket itself: cryptographically, the TGT is valid.

    The only invalidation is rotating krbtgt twice (twice because the previous and current passwords are both honored briefly). Most organizations have never rotated krbtgt. So a golden ticket forged today is often usable years later.

    Exercise 5.4 gives you krbtgt's NT hash. Forge a TGT for a non-existent user named GhostAdmin with Domain Admins membership. Use it to read a flag in a share that legitimate accounts cannot reach.

    Tools required: impacket-ticketer. Pre-installed on Kali.

    Scenario

    Marcus Bell: "The krbtgt account encrypts every TGT in the domain. Possess its hash and you write your own laminated all-access pass. The only fix is to rotate krbtgt twice. Most companies have never done it once."

    The flag lives at \\corp-dc01\GoldenFlags\golden_flag_<token>.txt, accessible only to Domain Admins.

    Credentials:

    Item Value
    krbtgt NT hash (per-token, dashboard; or recover via Exercise 5.2 DCSync)
    Domain SID (per-token, dashboard; S-1-5-21-...)

    Domain: corp.nordport.local

    Group RIDs to Claim

    ticketer.py accepts a comma-separated list of group RIDs to put in the PAC. The defaults cover the standard domain-wide admin set; the table below tells you when to add more.

    RID Group When to include
    512 Domain Admins Always
    513 Domain Users Always
    518 Schema Admins Schema modifications
    519 Enterprise Admins Forest-level admin (multi-domain forests)
    520 Group Policy Creator Owners GPO modifications
    544 BUILTIN\Administrators Local admin on DC's filesystem
    551 Backup Operators Bypass file ACLs via backup right

    Background: Why Golden Tickets Work

    The KDC validates incoming TGTs by decrypting them with krbtgt's key. If the decryption succeeds and the contents are well-formed, the KDC accepts the TGT and issues TGSes for whatever services the (claimed) user requests. There is no callback to verify that the user actually exists in AD; the PAC inside the ticket is the source of truth for identity and group membership.

    The attacker forges a ticket with: - A made-up username (GhostAdmin); AD never sees the name; the KDC trusts the PAC - The Administrator user ID (RID 500) for SID construction - Group SIDs for Domain Admins (RID 512), Enterprise Admins (519), Schema Admins (518), Group Policy Creator Owners (520), Domain Users (513) - A long lifetime (default ticketer.py produces 10 years; tune for stealth)

    The KDC issues TGSes against the forged TGT. Every service accepts those TGSes because they are normal TGSes signed with the right service key (which the KDC has). The chain is invisible to the targeted services; only the DC's KDC sees a TGT it cannot link to a real authentication event.

    Detection signals

    Signal Why it fires
    TGT lifetime anomaly ticketer.py defaults to 10-year lifetime; real TGTs are 10 hours
    Encryption-type mismatch If you forge with NT hash (RC4), services expecting AES log the etype mismatch
    4769 with no preceding 4768 TGS request without a corresponding TGT issuance
    RID 500 from non-Administrator name GhostAdmin claims RID 500 (Administrator), but the original Administrator's history shows different login times

    The most reliable defender control is the lifetime check: a TGT with a 10-year lifetime is impossible in normal operation. ticketer.py's -duration flag tunes it; a 10-hour TGT looks like every other ticket but expires fast.

    Why "rotate krbtgt twice"

    Microsoft's krbtgt rotation cmdlet (New-KrbtgtKeys.ps1 from the krbtgt rotation script) honors the previous password for backwards compatibility; DCs accept tickets encrypted with the previous OR current key briefly to handle in-flight authentication. So one rotation invalidates tickets encrypted with the older-old key but not the previous-old key. Two rotations, separated by a wait period (default 24 hours) for the first rotation to propagate, fully retire all old keys.

    A note on AES

    Modern domains use AES for krbtgt by default. Forging with the NT hash (-nthash) produces an RC4-encrypted TGT, which works but stands out in logs. Forging with the AES key (-aesKey) produces an AES-encrypted TGT that blends in. Use the AES key when available.

    Walkthrough

    Step 1: Gather Inputs

    Three inputs forge the ticket: krbtgt's NT hash (the forging key), the domain SID (so the impersonated user's SID has the correct prefix), and the realm name. The username string can be anything since AD is never consulted to validate it.

    From the dashboard:

    KRBTGT NT hash:   <32 hex chars>
Domain SID:       S-1-5-21-XXXX-YYYY-ZZZZ

    If the dashboard does not have the krbtgt hash, recover it via Exercise 5.2 (DCSync). The same domain SID is in the secretsdump output line for any user (strip the trailing -RID).

    Step 2: Forge the Golden Ticket

    ticketer.py builds a TGT structure: PAC with the impersonated user's SID and group SIDs, server signature with krbtgt's hash, KDC signature with the same key, and a long lifetime. The result is a credential cache file ready to use.

    Kali - ticketer.py golden ticket

    cd ~/work && mkdir -p adpt-5-04 && cd adpt-5-04
ticketer.py \
  -nthash '<KRBTGT_NT_HASH>' \
  -domain-sid 'S-1-5-21-XXXX-YYYY-ZZZZ' \
  -domain corp.nordport.local \
  -user-id 500 \
  -groups 513,512,520,518,519 \
  GhostAdmin
ls -la GhostAdmin.ccache
    Flag Effect
    -nthash <hash> krbtgt's NT hash. Use -aesKey for AES-only environments (stealthier).
    -domain-sid <SID> Domain SID prefix (no trailing RID).
    -domain <realm> Realm name.
    -user-id 500 RID for the impersonated user. 500 = Administrator.
    -groups 513,512,520,518,519 Group RIDs to claim in the PAC. Default covers Domain Users + the four admin groups.
    GhostAdmin Positional: the username string in the ticket. Any value; AD is not consulted.

    Step 3: Inject and Use

    The ccache loads with KRB5CCNAME. The forged TGT is now your "TGT": when smbclient needs a TGS for a service, it sends a TGS-REQ to the KDC with the forged TGT in the padata. The KDC decrypts the TGT with krbtgt's key (matches), reads the PAC (says you are Administrator with Domain Admins), and issues a fresh TGS for whatever service you ask for.

    Kali - Use the forged TGT

    export KRB5CCNAME=$(pwd)/GhostAdmin.ccache
klist

    klist shows Default principal: GhostAdmin@CORP.NORDPORT.LOCAL and the krbtgt service ticket. The TGT lifetime line shows the (long) validity period; if you used the default, this reads ~10 years.

    Kali - Read the protected share

    smbclient "//corp-dc01.corp.nordport.local/GoldenFlags" -k \
  -c "get golden_flag_${OCR_SCOPE_TOKEN}.txt"
cat golden_flag_${OCR_SCOPE_TOKEN}.txt

    Step 4: Confirm Persistence Property

    For learning, note that:

    1. The user GhostAdmin does not exist in AD. Get-ADUser GhostAdmin returns nothing.
    2. If the legitimate Administrator's password were rotated right now, your ticket would still work tomorrow, next week, and ten years from now; until krbtgt is rotated twice.
    3. There is no event 4768 (AS request) for GhostAdmin on any DC, because no AS exchange happened.

    Independence from any user-account password rotation is the persistence property that makes golden tickets the gold standard for long-term access.

    Common gotchas

    • Default lifetime triggers detection: ticketer.py defaults to 10-year tickets; that is impossible in normal AD operation. Add -duration 10 (hours) to mimic a real TGT.
    • RC4 vs AES: -nthash produces an RC4-encrypted TGT. Modern domains often log "Kerberos encryption type downgrade" alerts on RC4. Use -aesKey with the krbtgt AES256 key (also dumped by secretsdump) for blending in.
    • Domain SID format: must be S-1-5-21-X-Y-Z (4 segments after S-1-5-21). A 3-segment value is the BUILTIN SID and produces a ticket no service trusts.
    • Cross-realm tickets: golden tickets only forge tickets within the krbtgt's domain. To forge a child-domain or trust-relationship ticket, see inter-realm golden tickets and forest-trust forgery (a separate technique).
    • Time skew: Kerberos rejects tickets more than 5 minutes off. chronyc tracking should show your Kali within seconds of the DC.
    • DC accepts but service rejects: if a target service has KDC PAC validation enabled (rare), it will detect the forgery. Switch services or accept the noise.

    Blue Team Perspective

    A golden ticket is cryptographically valid; the detection signal lives in metadata anomalies and missing precursor events.

    Activity Event ID Field giveaway
    TGS-REQ from forged TGT 4769 no preceding 4768 for the same user/source
    Excessive ticket lifetime 4769 TGT lifetime > policy max (default ticketer.py = 10 years)
    Encryption-type downgrade 4769 RC4 etype on a domain that requires AES
    Defender for Identity "Suspected Golden Ticket usage" MDI alert

    Where SOCs win against golden tickets

    The cleanest detection is on TGT lifetime: any 4769 referencing a parent TGT with Ticket Lifetime > 10 hours is a forgery. SIEM rule with near-zero false positives. Defender for Identity ships this detection. The metadata anomalies (RC4 etype, no preceding 4768, mismatched name vs SID) are weaker individually but compound when correlated.

    Hardening Note

    The golden ticket vulnerability is the cached krbtgt hash. Rotate it; monitor for use; harden detection at the KDC.

    Golden ticket hardening

    • Rotate krbtgt twice every 6-12 months. Use Microsoft's published rotation script with the 24-hour wait between rotations.
    • Apply Microsoft's May 2022 PKINIT hardening (KrbtgtFullPacSignature = 2) to harden the PAC sigs.
    • Enforce AES-only Kerberos forest-wide; RC4-encrypted TGTs become anomalies.
    • Configure SIEM rule on 4769 events with abnormal TGT lifetime.
    • Treat any compromised DC as a krbtgt exposure; rotate krbtgt twice on the next maintenance window after recovery.
    • Enable Microsoft Defender for Identity for built-in golden ticket detections.

    Analysis Questions

    1. The forged TGT claims Administrator's RID (500) but a fictional username. Why does the KDC accept the mismatch?

    Reveal Answer

    The KDC does not verify the username against AD when validating an incoming TGT. The TGT's PAC contains the user SID (<DomainSID>-500), which the KDC trusts as the identity claim. The username string is informational metadata; it is not cross-referenced. Services downstream (CIFS, LDAP, etc.) authorize based on the SID, not the name string. So a TGT with name=GhostAdmin, SID=S-1-5-21-...-500 is treated as Administrator wherever the SID is the gating field. The defender's response is to enforce Privileged Attribute Certificate (PAC) validation with the KDC for sensitive services; but as discussed in the Silver Ticket exercise, default Windows services skip this check.

    2. ticketer.py defaults to a 10-year ticket lifetime. What is the operational reason for that, and why is it also the easiest detection signal?

    Reveal Answer

    The 10-year default is a stealth-versus-persistence trade-off impacket made by accident: long-lived tickets are convenient for operators who want a single ticket they can use whenever, without having to re-mint. The cost is that real TGTs in modern AD environments default to 10 hours; a 10-year TGT in the wild is impossible by accident and immediately distinctive. SIEM rules that check "TGT lifetime exceeds policy maximum" catch every default ticketer.py forgery. The operational counter is -duration <hours> to set a sane lifetime: 10 hours mimics a normal ticket. Operators who want stealth use realistic lifetimes; operators who want zero-effort persistence use the default and accept the detection risk.

    3. Rotating krbtgt twice is the standard mitigation. What breaks during the rotation, and why is it operationally hard for many organizations?

    Reveal Answer

    Operationally, the rotation requires: (a) running the krbtgt rotation script on every DC; (b) waiting 24 hours between the first and second rotation for replication and ticket lifetime expiration; (c) accepting that during the wait, any in-flight tickets encrypted with the soon-to-be-discarded key may fail and require re-authentication. The pain points are: (1) cross-domain trusts (forest with multiple domains, or external trusts with parent organizations) need coordinated rotation; (2) some legacy applications hardcoded long Kerberos ticket lifetimes and break when older keys expire faster; (3) Azure AD Connect / Entra Connect replication uses the krbtgt account, and rotation can disrupt sync; (4) the rotation script is unsigned and many security teams refuse to run unsigned scripts on Tier-0 systems without elaborate review. Most organizations skip the rotation indefinitely, accepting the persistent-golden-ticket risk as the cost of operational stability. The reality is that most production AD environments have a krbtgt key that is years old, which means any past compromise of krbtgt yields tickets that are still valid today.

    Key Takeaways

    • Golden ticket = forged TGT signed with krbtgt's hash; accepted by every DC.
    • ticketer.py -nthash <krbtgt> -user-id 500 -groups 513,512,520,518,519 <name> forges in one command.
    • The ticket persists until krbtgt rotates twice; most environments have never rotated krbtgt.
    • Detection: 10-year ticket lifetime (default) and TGS without preceding TGT issuance.
    • Use -duration 10 (hours) and -aesKey (instead of -nthash) for stealth.

    Card 2: Golden vs Silver

    Q: Two reasons golden tickets are operationally more valuable than silver tickets, and one reason silver is sometimes preferred.

    Answer

    Golden advantages: (1) usable against every Kerberos-aware service in the domain (silver is per-service); (2) survives service account password rotations (silver invalidates at rotation). Silver preferred when: (1) you do not have krbtgt and only the service account hash; (2) you want quieter persistence on a specific high-value service without the broad detection surface of using golden tickets domain-wide; (3) the service account password rotates rarely while you do not want to risk tipping off detection by minting golden tickets.

    Card 3: krbtgt Rotation

    Q: Why "twice" and how long between?

    Answer

    The first rotation puts a new password in place but keeps the old one valid briefly to handle in-flight tickets. The second rotation discards the previous (now-old) password entirely, invalidating any ticket encrypted with the original key. Microsoft's published guidance: 24 hours between rotations to allow replication to complete and outstanding tickets to expire. Skipping the wait can cause widespread authentication failures.

    Card 4: TGT Lifetime Detection

    Q: Why is a 10-year TGT the easiest golden-ticket detection signal, and what is the operator's stealth counter?

    Answer

    Real TGTs default to 10 hours per AD policy. A 10-year TGT in the wild is impossible by accident; SIEM rules that check ticket lifetime against policy maximum catch every ticketer.py forgery using defaults. Operator stealth counter: -duration 10 (hours) on the ticketer.py command, producing a normal-looking ticket. Re-mint as needed. Long lifetimes are convenience, not requirement.

    Card 5: Why GhostAdmin Works

    Q: A golden ticket can claim a username that does not exist in AD. Why?

    Answer

    The KDC validates incoming TGTs cryptographically (krbtgt key) and trusts the PAC for identity and group claims; it does NOT cross-check the username against AD. Services downstream authorize based on the SID in the PAC, not the name string. So GhostAdmin@corp.local with SID <DomainSID>-500 is treated as Administrator wherever Administrator's SID is the gating field. The mismatch is invisible to default services; only the most paranoid SIEM rules cross-reference TGT name strings against AD.
