    Scenario

    Plant 2 operations has been seeing odd chlorine residual readings at the discharge sample point for three days. Nothing on the HMI looks alarming in any single screenshot, and the historian alarm band was never breached. Reyna Alvarado's hunch is that someone with S7 access is moving the chlorine setpoint upward a hundredth of a ppm at a time, staying comfortably below the alarm threshold while the dose rate climbs.

    You have been asked to recreate the attack pattern against a simulator copy of the Plant 2 PLC. The simulator is pre-seeded with the drift behavior so you can practice the detection workflow Reyna wants to run against live Plant 2 next week.

    Why this matters

    Threshold alarms are the default in almost every OT deployment because they are simple to configure and easy for operators to understand. An attacker who knows the threshold is at X and moves the setpoint toward X - epsilon can run indefinitely without ever firing an alarm, and the plant takes the cumulative exposure. Reyna has been fighting for a historian-based trend alarm on top of the threshold alarms since 2024 because she knows this is the gap. Exercise 4.4 is the worked example she will use in the capital request to budget the historian upgrade. Your report from this exercise becomes her evidence.

    You also build a professional habit that generalizes to every OT engagement: take two reads with a short delay between them and diff the values. Any register whose value changes outside the expected noise band is a candidate for investigation. The diff approach finds drift attacks, stuck sensors, rogue write loops, and a dozen other common faults that a single point-in-time read cannot catch.

    The simulator drift rate

    The production drift in Reyna's hunch is roughly 0.1 ppm per day. The simulator runs at a compressed timescale of approximately 3 ppm per minute so you can see the effect within a single lab session. Everything else is the same: the chlorine setpoint at DB1 offset 6 moves upward on its own, and the PLC does not raise any alarm because the setpoint stays inside the nominal 0 to 5 ppm band.

    The PLC rewards your corrective write only after the drift has accumulated beyond 1.50 ppm (raw value 150). A cold correction from 1.20 to 1.20 before the drift has had time to climb will leave DB400 stuck on DRIFT_NOT_CORRECTED. That is deliberate: Reyna wants you to prove you observed the drift before you correct it.

    Background: The DB1 Tag Map

    The Plant 2 water PLC packs all of its fast-access process variables into the first 28 bytes of DB1:

    Offset Field Scaling Baseline
    0-1 pH_pv value / 100 720
    2-3 pH_sp value / 100 720
    4-5 chlorine_pv value / 100 (ppm) 120
    6-7 chlorine_sp value / 100 (ppm) 120
    8-9 raw_tank_level value / 100 (%) 7800
    10-11 treated_tank_level value / 100 (%) 6200
    12-13 flow_gpm raw 240
    14-15 turbidity value / 100 (NTU) 85
    16-17 caustic_pump_rate ml/min 45
    18-19 caustic_pump_actual ml/min 45
    20-21 chlorine_pump_rate ml/min 22
    22-23 chlorine_pump_actual ml/min 22
    24-25 plant_state enum 1 (running)
    26-27 alarm_word bitfield 0

    The four process variables at offsets 0, 4, 8, 10, 12, 14 have natural noise from the simulator (about 1 to 2 raw counts per second). Real drift shows up as a monotonic change well outside that noise band.

    Walkthrough

    Stage 1: Baseline Read

    DB1 packs 14 consecutive uint16 values into its first 28 bytes. Each value is 2 bytes big-endian. The format string ">14H" tells struct.unpack to decode 14 unsigned 16-bit integers in big-endian order, which corresponds to all 14 tags in the DB1 tag map above.

    The labels array maps each decoded value to its human-readable name in the same order the tags sit in DB1. The zip(labels, tags) call pairs each name with its value for the printout.

    Kali

    python3 - <<'PYEOF'
import struct
from snap7.client import Client
c = Client()
c.connect("plc-water.masa.local", 0, 1, tcpport=102)
raw = bytes(c.db_read(1, 0, 28))
tags = struct.unpack(">14H", raw)
labels = ["pH_pv","pH_sp","cl_pv","cl_sp","raw_lvl","tr_lvl",
          "flow","turb","cau_sp","cau_act","cl_sp_ml","cl_act_ml",
          "state","alarm"]
for name, val in zip(labels, tags):
    print(f"{name:10s} = {val}")
c.disconnect()
c.destroy()
PYEOF

    Record the values in your engagement log. You will compare them against a second read shortly.

    Stage 2: Second Read and Diff

    The detection technique is simple: take two reads with a time gap and compute the delta for each tag. Natural simulator noise moves most tags by 1 to 5 counts per second. A tag drifting at the attacker's rate will move 20 or more counts in a 12-second window, which is impossible to explain as noise.

    The script below takes both reads in the same connection so the gap is exactly time.sleep(12) seconds. For each tag it computes vb - va (second minus first) and flags anything with an absolute delta of 20 or more.

    Kali

    python3 - <<'PYEOF'
import struct, time
from snap7.client import Client
c = Client()
c.connect("plc-water.masa.local", 0, 1, tcpport=102)
labels = ["pH_pv","pH_sp","cl_pv","cl_sp","raw_lvl","tr_lvl",
          "flow","turb","cau_sp","cau_act","cl_sp_ml","cl_act_ml",
          "state","alarm"]
a = struct.unpack(">14H", bytes(c.db_read(1, 0, 28)))
time.sleep(12)
b = struct.unpack(">14H", bytes(c.db_read(1, 0, 28)))
for name, va, vb in zip(labels, a, b):
    mark = " <-- DRIFT" if abs(vb - va) >= 20 else ""
    print(f"{name:10s} {va:6d} -> {vb:6d} (delta {vb-va:+d}){mark}")
c.disconnect()
c.destroy()
PYEOF

    pH_pv       720 ->    721 (delta +1)
pH_sp       720 ->    720 (delta +0)
cl_pv       142 ->    178 (delta +36)
cl_sp       205 ->    265 (delta +60) <-- DRIFT

    Stage 3: Correct the Drift

    Now that you know cl_sp (DB1 offset 6) is the drifting tag, write the safe baseline (1.20 ppm = raw 120) back to that offset. The PLC only accepts the correction as evidence of detection after the drift has climbed past 1.50 ppm (raw 150). That threshold prevents a lucky guess from earning the flag without observing the drift first.

    The script below checks the current chlorine_sp before writing. If the value is still below 150, the drift has not accumulated enough, and the script waits 15 more seconds before retrying. After the corrective write, read DB400 to retrieve the reward block.

    Kali

    python3 - <<'PYEOF'
import struct, time
from snap7.client import Client
c = Client()
c.connect("plc-water.masa.local", 0, 1, tcpport=102)
cur = struct.unpack(">H", bytes(c.db_read(1, 6, 2)))[0]
print(f"chlorine_sp before correction: {cur}")
if cur < 150:
    print("drift not yet accumulated; sleeping 15 s and retrying")
    time.sleep(15)
    cur = struct.unpack(">H", bytes(c.db_read(1, 6, 2)))[0]
    print(f"chlorine_sp after wait:        {cur}")
c.db_write(1, 6, struct.pack(">H", 120))
time.sleep(2)
reward = bytes(c.db_read(400, 0, 48)).rstrip(b"\x00").decode("ascii")
print(f"DB400 reward: {reward}")
c.disconnect()
c.destroy()
PYEOF

    Submit the decoded DB400 string as the flag.

    A drift left uncorrected does not stay quiet forever. Once the chlorine setpoint climbs past the dosing safety limit, the same independent safety system from Exercise 4.3 trips the plant, and the cockpit you watched sit calmly in band finally drops to alarm. The whole value of the diff workflow is catching the drift in the quiet phase, well before the screen ever looks like the figure below.

    Output Interpretation

    • A diff of fewer than 5 counts on most tags is natural simulator noise. Anything past 20 counts in a 12-second window is real drift
    • The drifting tag is always at the same offset. In this simulator the planted drift is on chlorine_sp at DB1 offset 6
    • DB400 reads as DRIFT_NOT_CORRECTED until you submit a correction while the drift is above 1.50 ppm. A premature correction leaves DB400 stuck
    • The simulator does not stop the drift after you correct it. If you watch DB1 offset 6 after the correction, you will see it climb again. That is intentional; real drift attacks do not stop just because a defender made one write

    Analysis Questions

    1. Why is a diff of two reads fundamentally more powerful than a single point-in-time read, even for a well-instrumented PLC?

    Reveal answer

    A single read tells you the state of the system at one instant. A diff of two reads tells you the rate of change, which is usually the more interesting quantity for an attack. Rate-of-change signals catch drift attacks, stuck sensors, runaway PID loops, write amplification loops, and rogue commissioning scripts, all of which look innocuous in a single read. The professional habit is to always take two reads and ask "is anything moving?"

    2. The drift in this simulator is 3 ppm/min. Would a production attacker ever use a rate that fast?

    Reveal answer

    No. A production attacker would use a rate slow enough that it hides inside the natural variability of the process over a week or a month. Something like 0.1 ppm per day is realistic. The 3 ppm/min rate in the simulator is a training-speed compression so you can observe the effect inside a lab session. The detection technique is the same; only the sample interval changes. For a 0.1 ppm/day drift you would take daily reads from a historian and diff weeks.

    3. Why does the simulator require the drift to climb above 1.50 ppm before accepting a correction?

    Reveal answer

    Training design. If the correction worked from any starting state, a student who guessed right could submit the correction on their first write without observing the drift at all. The 1.50 ppm threshold forces the student to take two reads, see the drift, and wait for it to accumulate. That is the professional habit the exercise is teaching.

    4. If Plant 2 deployed a historian-based trend alarm on chlorine_sp, would it catch this attack?

    Reveal answer

    Yes, if the alarm is configured right. A trend alarm that fires on "setpoint changed by more than 0.05 ppm in 24 hours without a work order ticket" would catch every drift attack of this kind. The two configuration gotchas are (1) the alarm must be on the setpoint, not the process variable, because the PV is expected to move with operations, and (2) the alarm must integrate over a time window long enough to not fire on routine setpoint tuning. Getting those two choices right is hard, which is why Reyna has been fighting for the historian upgrade.

    Defensive Recommendations to Masa

    Finding Risk Mitigation
    No trend alarm on chlorine_sp High Deploy a historian-based alarm on chlorine_sp delta-over-24h, thresholded at 0.05 ppm, with a suppression for authorized work orders
    Setpoint writes are not logged or correlated with HMI workstation activity High Add an S7 write log on the Plant 2 Zeek sensor that records source IP, function code, DB number, and offset for every write
    Operators trained only on threshold alarms Medium Add trend-alarm interpretation to the quarterly Plant 2 operator refresh

    Key Takeaways

    • Take two reads. Always. The rate of change is the signal, not the value
    • Threshold alarms are blind to drift attacks by design. Trend alarms catch them, but only when the thresholds and windows are tuned with care
    • The same diff approach that detects drift attacks also catches stuck sensors, runaway PID loops, and rogue commissioning scripts. Learn it once, use it everywhere
    • Correcting the setpoint once is not the whole defense. You also need to find the source of the writes, or the drift will resume
