    Challenge 6B: Filtered Injection

    Before You Begin

    Challenge 6B is an unguided reinforcement exercise that builds on Challenge 6 (Command Injection). Complete that exercise first. Your VPN must be connected and your terminal ready.

    Scenario

    TrueNorth Hosting, a managed DNS provider in Toronto, Ontario, offers a web-based DNS lookup tool. After a previous security audit flagged command injection, the development team added input filtering to strip dangerous characters. They are confident the fix is sufficient.

    Your firm has been engaged to verify the remediation. Alex Tran (VP of Engineering) is direct: "We strip semicolons, pipes, and ampersands from all input. Our pen test last quarter said we were clean. Prove us wrong; or prove us right."

    Two assessment tokens are placed on the server. Reaching them requires bypassing the input filter to execute arbitrary commands. The filter blocks common injection characters but has a gap that allows an alternative injection technique.

    Your Objectives

    • Test the DNS lookup tool with normal input to understand its behavior
    • Attempt standard command injection techniques and observe the filtering
    • Identify which characters are filtered and which are not
    • Discover a bypass technique that the filter does not catch
    • Use the bypass to execute commands and extract assessment tokens
    • Assemble and submit the flag

    Analysis Questions

    1. Why is input filtering (blocklist approach) generally less secure than input validation (allowlist approach) for preventing command injection?

     

     

    2. What alternative to shell=True could the developer use to eliminate command injection entirely, regardless of filtering?

     

     

    Key Takeaways

    • Blocklist-based filtering (stripping specific characters) is inherently incomplete; attackers will find characters or encodings the developer did not anticipate.
    • Newline injection (%0a) is a frequently overlooked bypass because newlines are not traditionally considered "dangerous" characters, yet the shell interprets them as command separators.
    • Defense in depth requires using parameterized command execution (e.g., subprocess.run(["nslookup", user_input]) without shell=True) rather than relying on input sanitization alone.
