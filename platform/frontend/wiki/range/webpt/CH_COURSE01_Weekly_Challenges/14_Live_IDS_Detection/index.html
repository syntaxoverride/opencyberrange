    Exercise 14: Live IDS Detection

    Before You Begin

    Week 13 introduced offline traffic analysis using PCAP (Packet Capture) files; you examined pre-recorded network data for signs of malicious activity. Week 14 shifts from post-incident analysis to real-time detection. The attack is happening now, and your job is to write rules that catch it as packets cross the wire.

    Your VPN must be connected and your terminal open. You should be comfortable with basic Linux command-line navigation and have a working understanding of HTTP request structure from previous labs.

    Scenario

    Sentinel Defense Corp, a boutique cybersecurity consulting firm based in Arlington, Virginia, has detected anomalous network traffic on their DMZ (Demilitarized Zone) segment. The Network Operations Center flagged repeated connections from an unidentified source targeting multiple hosts in the 10.100.x.0/24 range. Initial triage suggests automated reconnaissance and exploitation attempts.

    You are a junior SOC (Security Operations Center) analyst pulling the night shift. Your supervisor, Marcus Chen (Senior Threat Hunter), left you a voicemail before signing off:

    "We've got active probing hitting the DMZ. The IDS sensor is online but we never deployed custom detection rules; it's running blind. I need you to analyze the traffic, write Suricata rules that catch the specific attack signatures, and pull the IOCs from the captured payloads. Also check the web portal; I think the attacker got some hits there. Extract everything you can. I'll review your findings in the morning."

    Your toolkit includes SSH access to the IDS sensor (running Suricata and tcpdump) and the corporate web portal (running nginx). The attack is ongoing; new malicious requests arrive every few seconds. The clock is ticking.

    Your Objectives

    The following list outlines what you need to accomplish in the lab environment. Each objective maps to one or more walkthrough steps below.

    • Observe live attack traffic on the IDS sensor using packet capture tools
    • Identify distinct attack signatures in the traffic (SQL injection, command injection)
    • Write custom Suricata IDS rules to detect each attack vector
    • Extract indicators of compromise (IOCs) from Suricata alert payloads
    • Investigate the target web server's logs for additional forensic evidence
    • Assemble the flag parts and submit the completed flag

    Background: Intrusion Detection Systems and Suricata

    An IDS (Intrusion Detection System) is a network security tool that monitors traffic for suspicious patterns and generates alerts when it finds a match. An IDS differs from an IPS (Intrusion Prevention System) in one critical way: an IDS observes and alerts, while an IPS can actively block or drop malicious packets. Think of an IDS as a security camera and an IPS as a security guard; one watches, the other intervenes.

    Most IDS engines rely on signature-based detection, where the system compares each packet against a database of known attack patterns. Each pattern is expressed as a rule that describes what to look for; a specific string in the URL, a byte sequence in the payload, or a combination of header values. When a packet matches a rule, the engine writes an alert to its log file with details about the match.

    Suricata is an open-source, high-performance IDS/IPS engine maintained by the Open Information Security Foundation (OISF). Suricata inspects network traffic in real time, applies rules against each packet or reassembled stream, and logs alerts in a structured JSON format called Eve (Extensible eVent Engine) JSON. Security analysts use Eve JSON logs to investigate alerts, correlate events, and extract IOCs.

    The distinction between IDS and IPS matters for your work tonight. The Sentinel Defense Corp sensor is configured in IDS mode; it will detect and log, but it will not block. Your rules need to be precise enough to flag the real attacks without generating noise from normal traffic.

    Tool Primer: Writing Suricata Rules

    Suricata rules follow a structured syntax that tells the engine what traffic to inspect and what conditions trigger an alert. Understanding the rule format is essential before you write your own detection signatures.

    Rule Structure

    Every Suricata rule has two parts: a header and an options section. The header specifies the action, protocol, source, destination, and direction. The options section (in parentheses) contains the detection logic and metadata.

    alert http <src_ip> <src_port> -> <dst_ip> <dst_port> (options;)

    Here is a concrete example that detects the string "UNION SELECT" in an HTTP URI:

    alert http any any -> any any (msg:"SQLi Detected"; content:"UNION SELECT"; nocase; http_uri; sid:1000001; rev:1;)

    Breaking down each component:

    Component Value Meaning
    Action alert Generate an alert when matched
    Protocol http Inspect HTTP traffic only
    Source any any Any source IP and port
    Direction -> Traffic flowing to the destination
    Destination any any Any destination IP and port
    msg "SQLi Detected" Human-readable alert message
    content "UNION SELECT" Byte string to match
    nocase ; Case-insensitive matching
    http_uri ; Match only within the HTTP URI
    sid 1000001 Signature ID (unique per rule)
    rev 1 Rule revision number

    Key Content Modifiers

    Suricata provides several modifiers that control where content matching occurs within a packet or stream:

    • http_uri: match within the request URI (the path and query string)
    • http_client_body: match within the POST body sent by the client
    • http_header: match within HTTP headers
    • nocase: ignore capitalization when matching the content string

    Eve JSON Log Format

    When a rule fires, Suricata writes a JSON record to /var/log/suricata/eve.json. Each alert record contains the signature name, signature ID, source and destination IPs, and protocol-specific fields like the HTTP URL and payload.

    A typical alert entry looks like the following (simplified for readability):

    {
  "timestamp": "2024-11-15T03:22:41.123456+0000",
  "event_type": "alert",
  "src_ip": "10.100.5.31",
  "dest_ip": "10.100.5.47",
  "alert": {
    "signature": "SQLi Detected",
    "signature_id": 1000001
  },
  "http": {
    "url": "/search?q=1'+UNION+SELECT+...&campaign=REDACTED"
  }
}

    Parsing Eve JSON with jq

    The jq command-line tool filters and formats JSON data. You will use it to extract alert records from the Eve log and pull specific fields from matching entries.

    Filter only alert events from the log:

    jq 'select(.alert != null)' /var/log/suricata/eve.json

    Extract only the alert signature and HTTP URL from alert events:

    jq 'select(.alert != null) | {sig: .alert.signature, url: .http.url}' /var/log/suricata/eve.json

    Filter alerts by a specific signature ID:

    jq 'select(.alert != null) | select(.alert.signature_id == 1000001)' /var/log/suricata/eve.json

    These jq patterns will be essential for extracting IOCs from your Suricata alerts during the walkthrough.

    Walkthrough

    Step 1: Launch the Exercise

    The lab environment provisions two servers: an IDS sensor running Suricata and a web portal running nginx. Both machines must be running before you begin your investigation.

    • Navigate to Exercises and locate the Week 14 lab: Sentinel Defense Corp; Live IDS Detection
    • Click Launch and wait for the status to change to Running
    • Note the IP addresses for both the IDS Sensor and the Web Portal displayed in the Active Lab View

    The IDS sensor sits between the attacker and the web portal on the DMZ network. Automated attack traffic is already flowing; your containers begin receiving malicious requests as soon as the lab starts.

    Step 2: SSH to the IDS Sensor

    You will perform most of your work on the IDS sensor, where Suricata is running. Connect using the analyst credentials provided for the engagement.

    SSH into the IDS sensor

    Open an SSH session to the Suricata IDS sensor as the analyst user. Replace <ids_sensor_ip> with the IDS Sensor IP shown in the Active Lab View.

    ssh analyst@<ids_sensor_ip>

    When prompted for the password, enter:

    S3nt1n3l_S0C#

    After logging in, you should see a standard Linux shell prompt. Confirm you are on the correct machine by checking the hostname; it should indicate the IDS sensor role.

    Step 3: Verify Suricata Is Running

    Before writing detection rules, confirm that the Suricata process is active and listening on the network interface. A stopped engine cannot detect anything, and writing rules for a dead process wastes time.

    Confirm Suricata is running

    On the IDS sensor, ask for the Suricata process ID. A numeric result means the engine is active.

    pidof suricata

    A numeric process ID in the output confirms Suricata is running. If the command returns nothing, the engine is not active; contact your lab platform support before proceeding.

    Note that pgrep -x suricata does not reliably detect a running Suricata. When Suricata runs in daemon mode, its main thread renames itself (for example, to Suricata-Main), so the exact-match flag (-x) misses it. Use pidof suricata or pgrep -f suricata instead.

    You can also check the Suricata service status for more detail:

    Inspect the Suricata process line

    Print the full process listing and filter for suricata to see which interface and config file it loaded.

    ps aux | grep suricata

    Look for a process line showing suricata with flags indicating which interface and configuration file it is using. The presence of the process means the engine is ready to accept rules and begin generating alerts.

    Step 4: Observe Live Attack Traffic

    Before writing rules, you need to understand what the attack looks like on the wire. Watching raw traffic with tcpdump reveals the attack patterns, which you will then translate into Suricata signatures.

    Run the following command to capture HTTP traffic on port 80 and display the ASCII content of each packet:

    Watch live HTTP traffic with tcpdump

    On the IDS sensor, sniff port 80 on eth0. The -A flag prints payloads in ASCII so you can read the request lines.

    sudo tcpdump -i eth0 -A port 80 | head -100

    Watch the output for 15-20 seconds. You should see HTTP requests arriving at regular intervals. Pay close attention to two distinct patterns:

    Pattern 1; SQL Injection (SQLi) via GET requests:

    Look for GET requests where the URL query string contains SQL syntax. The attacker is injecting UNION SELECT statements into search parameters. A typical request URI looks something like:

    GET /search?q=1'+UNION+SELECT+username,password+FROM+users--&campaign=SOMETHING

    The UNION SELECT keyword combination is a hallmark of SQL injection; the attacker is attempting to append their own database query to a legitimate search.

    Pattern 2; Command Injection (CMDi) via POST requests:

    Look for POST requests where the body contains operating system commands. The attacker is injecting system commands like cat /etc/passwd into form fields. A typical POST body looks something like:

    cmd=;cat /etc/passwd&exfil=SOMETHING

    The cat /etc pattern reveals command injection; the attacker is attempting to execute arbitrary commands on the server and read sensitive system files.

    Note both patterns carefully. Each one will require its own Suricata rule.

    Step 5: Write Suricata Rules for SQLi and CMDi Detection

    Now that you have identified the two attack vectors, write Suricata rules that detect each pattern. The rules file for custom signatures on the IDS sensor is located at /etc/suricata/rules/local.rules.

    Open the file in a text editor:

    Open the local rules file

    On the IDS sensor, open the custom rules file with nano under sudo so you can save it.

    sudo nano /etc/suricata/rules/local.rules

    Add the two rules shown below to the file.

    Add the following two rules to the file:

    Rule 1; SQL Injection Detection:

    alert http any any -> any any (msg:"SQLi Attack Detected"; content:"UNION SELECT"; nocase; http_uri; sid:1000001; rev:1;)

    The first rule matches any HTTP traffic containing the string UNION SELECT (case-insensitive) in the request URI. The http_uri modifier restricts the match to the URL path and query string, avoiding false positives from response bodies.

    Rule 2; Command Injection Detection:

    alert http any any -> any any (msg:"Command Injection Detected"; content:"cat /etc"; nocase; http_client_body; sid:1000002; rev:1;)

    The second rule matches HTTP traffic containing cat /etc in the POST body. The http_client_body modifier limits the search to data sent by the client (the attacker), ensuring the rule fires on inbound exploitation attempts.

    Save the file and exit the editor (in nano: Ctrl+O to write, Enter to confirm, Ctrl+X to exit).

    Step 6: Reload Suricata Rules

    Suricata does not automatically pick up changes to rule files. You must signal the running process to reload its rule set. The USR2 signal tells Suricata to re-read all configured rule files without restarting the engine or dropping monitored traffic.

    Signal Suricata to reload rules

    On the IDS sensor, send the USR2 signal to the Suricata process so it re-reads the rule files without restarting.

    sudo kill -USR2 $(pidof suricata)

    No output from the command means the signal was delivered successfully. Suricata will parse the updated rule files in the background. Wait approximately 5 seconds for the reload to complete before proceeding.

    If you instead see kill print its usage help (kill [options] <pid> [...]), that means the command inside $(...) returned no PID and kill had nothing to signal. The empty result comes from the same daemon-mode issue from Step 3; pgrep suricata misses the renamed main thread. Use pidof suricata (shown above), or read the PID directly from Suricata's PID file:

    Reload using the PID file

    If pidof returned nothing, read the PID straight from Suricata's PID file and signal that instead.

    sudo kill -USR2 $(sudo cat /var/run/suricata/suricata.pid)

    Step 7: Verify Alerts Are Firing in Eve JSON

    With rules loaded and attack traffic still flowing, Suricata should begin generating alerts within 15-20 seconds (the interval between attack cycles). Check the Eve JSON log for alert records.

    Read alert records from the Eve log

    On the IDS sensor, filter the Eve JSON log for records that contain an alert object.

    jq 'select(.alert != null)' /var/log/suricata/eve.json

    You should see JSON objects containing your alert signatures. If the output is empty, wait another 15 seconds and try again; the next wave of attack traffic has not yet arrived. If no alerts appear after 30 seconds, revisit Step 5 and verify your rule syntax.

    To see only the signature names from your alerts:

    List unique alert signatures

    Extract just the signature names and deduplicate them so you can confirm both rules fired.

    jq -r 'select(.alert != null) | .alert.signature' /var/log/suricata/eve.json | sort -u

    Successful output shows both SQLi Attack Detected and Command Injection Detected in the list. Seeing both signatures confirms your rules are working against the live traffic.

    Step 8: Extract the SQLi Indicator (Campaign Tag)

    The attacker's SQL injection requests contain a campaign parameter in the query string. Suricata captured the full URL in the Eve JSON alert record, and you can extract the campaign value using jq and grep.

    Extract the SQLi campaign tag

    On the IDS sensor, pull the captured URL from the SQLi alerts (signature ID 1000001) and grep out the campaign parameter value.

    jq -r 'select(.alert != null) | select(.alert.signature_id == 1000001) | .http.url' /var/log/suricata/eve.json | grep -oP 'campaign=\K[^&]+' | head -1

    Record the value returned; the campaign tag is the first part of the flag. Write it down before moving on.

    Step 9: Extract the CMDi Indicator (Exfil Tag)

    The attacker's command injection POST requests contain an exfil parameter in the request body. Suricata captured the printable payload content, and you can extract the exfil value from the alert records.

    Extract the CMDi exfil tag

    On the IDS sensor, pull the printable payload from the CMDi alerts (signature ID 1000002) and grep out the exfil parameter value.

    jq -r 'select(.alert != null) | select(.alert.signature_id == 1000002) | .payload_printable' /var/log/suricata/eve.json | grep -oP 'exfil=\K[^& \r\n]+' | head -1

    Record the value returned; the exfil tag is the second part of the flag.

    Step 10: Investigate the Web Portal Access Logs

    Marcus mentioned the attacker may have hit the web portal too. SSH to the web portal server to examine the nginx access logs for additional forensic evidence.

    Open a new terminal window (or exit the IDS sensor session) and connect to the web portal:

    SSH into the web portal

    From a fresh terminal, open an SSH session to the nginx web portal as webadmin. Replace <web_portal_ip> with the Web Portal IP shown in the Active Lab View.

    ssh webadmin@<web_portal_ip>

    When prompted for the password, enter:

    Dmz_Adm1n_2024#

    Read the nginx access log

    On the web portal, print the access log and scan the User-Agent strings. Normal browsers report Mozilla/5.0 ...; the attacker's tool stands out.

    cat /var/log/nginx/access.log

    Look for a User-Agent containing SentinelBreaker/ followed by a value.

    Extract the attacker User-Agent value

    Grep the access log for the custom User-Agent and print only the value that follows SentinelBreaker/.

    grep -oP 'SentinelBreaker/\K[^ "]+' /var/log/nginx/access.log | head -1

    Record the value returned; the User-Agent tag is the third and final part of the flag.

    Step 11: Interpret the Results

    Review the three IOCs you extracted and consider what they reveal about the attacker's operation.

    The campaign tag embedded in the SQL injection requests is a label the attacker uses to track which exploitation campaign generated the data. Attackers often tag their payloads with internal identifiers so they can correlate stolen data back to specific targets or timeframes. Finding the tag confirms the attack is organized, not random.

    The exfil tag in the command injection POST requests serves a similar purpose; it labels the data exfiltration channel. The presence of both a campaign tag and an exfil tag suggests the attacker is running multiple concurrent operations and uses tagging to keep them organized.

    The custom User-Agent on the web portal confirms that the same attacker (or the same tool) targeted both the IDS sensor and the web portal. Automated attack tools frequently use distinctive User-Agent strings, either by accident or by design. Correlating the User-Agent across both servers links the two attack streams to a single source.

    Assemble the three values into the flag format: OCR{________}, where each part is separated by an underscore.

    Flag Format

    Assemble the flag using the tokens in the order you discovered them:

    OCR{<sqlitoken>_<cmditoken>_<useragenttoken>}

    Where sqlitoken is from the Suricata SQLi alert campaign payload, cmditoken is from the Suricata CMDi alert exfil payload, and useragenttoken is from the Nginx access log User-Agent string.

    Navigate back to the lab platform in your browser. Paste the assembled flag in OCR{...} format into the Submit Flag field and click Submit. The platform will confirm whether your flag is correct. If the submission is rejected, double-check each extracted value and ensure the parts are joined with underscores in the correct order.

    Analysis Questions

    The following questions ask you to think beyond the mechanics of writing rules. Consider each one before reading the answer.

    1. Why does the http_uri modifier matter in the SQLi rule? What would happen if you omitted it and matched content:"UNION SELECT" against all traffic?

    Reveal Answer

    Without http_uri, Suricata matches the string against the entire packet payload, including response bodies. A web page that discusses SQL injection (such as a security tutorial) could contain the words "UNION SELECT" in its HTML content, triggering a false positive. The modifier constrains matching to the request URI, where the string indicates an actual injection attempt rather than benign content.

    2. The attacker embedded campaign and exfil tags directly in the HTTP requests. Why would a real-world attacker include metadata in their payloads, and what risk does it create for them?

    Reveal Answer

    Attackers tag payloads to organize multi-target campaigns; the metadata helps them sort incoming stolen data by victim, timeframe, or method. However, embedding identifiers in cleartext HTTP creates a significant operational security risk. Defenders who capture the traffic (as you did) can use those tags to link different attack streams, attribute activity to a specific campaign, and potentially track the attacker across multiple targets or incidents.

    3. The IDS sensor was running in detection mode, not prevention mode. If the sensor had been configured as an IPS, how would the outcome differ?

    Reveal Answer

    In IPS mode, Suricata can drop or reject packets that match a rule instead of only logging them. The SQL injection and command injection requests would have been blocked before reaching the target application, preventing exploitation entirely. However, IPS mode carries risk; a poorly written rule can block legitimate traffic. Organizations often start with IDS mode to validate rules before switching to inline prevention.

    Key Takeaways

    • Signature-based IDS detection works by matching traffic against predefined rules; the rules are only as good as the analyst who writes them, and an IDS with no custom rules is effectively blind to targeted attacks.
    • Suricata rules follow a structured format with an action, protocol, addressing, and options section; content modifiers like http_uri and http_client_body control exactly where matching occurs to reduce false positives.
    • Eve JSON logs provide structured, machine-readable alert data that analysts can parse with tools like jq to extract specific fields, filter by signature ID, and correlate events across time.
    • IOC extraction from captured payloads turns raw alerts into actionable intelligence; campaign tags, exfiltration labels, and custom User-Agents all serve as forensic evidence linking attack activity.
    • Correlating evidence across multiple servers (the IDS sensor and the web portal) provides a fuller picture of an attacker's operation than any single data source alone.
