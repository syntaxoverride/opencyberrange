    Exercise 9A: Data Breach Assessment

    Before You Begin

    Exercise 9A combines web application enumeration with backend database analysis to investigate a potential data breach. You should have completed Exercises 1 through 8 before attempting this lab. The skills from Exercise 4 (directory traversal) and Exercise 10's preview of database interaction are both relevant here. Your VPN must be connected and your terminal ready.

    Scenario

    Meridian Financial Group is a mid-size investment advisory firm headquartered in Raleigh, North Carolina. The firm has engaged your team at Ironwood Security Consulting for a data protection assessment. The engagement was triggered by an internal audit that flagged "potential data exposure," but the scope and severity are unknown.

    Your point of contact is James Park, IT Director: "We migrated our internal systems last quarter and stood up a new employee intranet. The development team assures me everything is locked down, but our compliance officer noticed some anomalies in the access logs. I need your team to investigate the intranet and our backend database to determine if any sensitive data was exposed during the migration."

    James shares that the intranet runs on one server and the company database runs on a separate host. He believes the database is only accessible to authenticated application users. Your task is to assess both systems, identify any data protection failures, and locate the compliance finding that documents the breach.

    Your Objectives

    • Enumerate the corporate intranet to discover all available pages and directories
    • Identify exposed backup files containing sensitive data
    • Extract database credentials from backup artifacts
    • Connect to the backend database and enumerate schemas and tables
    • Locate the compliance finding that documents the data breach
    • Capture the flag

    Background: Data Breach Investigation Methodology

    Data breach assessments follow a structured investigation process. Unlike a penetration test where the goal is to break in, a breach assessment asks "what was already exposed, and how bad is the damage?" The methodology involves four stages: asset discovery, exposure mapping, data classification, and impact assessment.

    Asset Discovery

    The first step is identifying what systems and data stores exist. In a corporate environment, web servers, databases, file shares, and backup archives form the data landscape. Each asset may store, process, or transmit sensitive information, and each one needs to be examined for misconfiguration.

    Exposure Mapping

    Once assets are identified, you determine which ones are accessible without proper authorization. Common exposures include world-readable backup directories, unprotected database ports, and configuration files left in web-accessible locations. The gap between "what should be accessible" and "what actually is accessible" defines the breach surface.

    Data Classification

    Not all exposed data carries the same risk. Data classification assigns sensitivity levels, public, internal, confidential, and PII (Personally Identifiable Information), to each piece of exposed data. A marketing brochure left in an open directory is low-impact; a SQL dump containing customer records is critical.

    Impact Assessment

    The final stage documents the findings in terms of regulatory and business impact. Compliance frameworks like SOC 2, HIPAA, and PCI DSS define specific requirements for data protection. A breach assessment maps each finding to the relevant compliance requirement and assigns a severity level.

    Tool Primer: curl and mysql

    Two tools drive this exercise. You have used curl since Week 1 for HTTP requests; here you will use it for web enumeration and file retrieval. The mysql command-line client is new; it connects directly to a MySQL database server and lets you run SQL queries interactively.

    curl for directory probing:

    curl -s -o /dev/null -w '%{http_code}' http://<target>/path/

    The flags work together: -s suppresses progress output, -o /dev/null discards the response body, and -w '%{http_code}' prints only the HTTP status code. A 200 means the path exists and is accessible. A 403 means the path exists but access is denied. A 404 means the path does not exist. Probing with the status code alone lets you map directories quickly without reading their full content.

    mysql client for database interaction:

    mysql --skip-ssl -h <db_host> -u <username> -p'<password>'

    The --skip-ssl flag prevents Kali's MariaDB client from rejecting MySQL 8.0's self-signed SSL certificate. The -h flag specifies the database server's IP address. The -u flag provides the username, and -p provides the password (with no space between -p and the password value).

    The -p flag has no space

    Write -p'MyPassword': not -p 'MyPassword'. If you put a space after -p, MySQL interprets the next word as a database name instead of a password, and the connection will fail with an "Access denied" error.

    Once connected, your terminal prompt changes to MariaDB [(none)]>: this means you are inside the MySQL client and the server is waiting for SQL commands. Everything you type from this point forward is SQL, not bash. Here are the essential commands:

    Command Purpose
    SHOW DATABASES; List all databases the user can see
    USE <database>; Switch to a specific database (prompt changes to show the database name)
    SHOW TABLES; List all tables in the current database
    DESCRIBE <table>; Show the column names and data types of a table
    SELECT * FROM <table>; Display all rows from a table
    SELECT * FROM <table> WHERE <column> = '<value>'; Filter rows by a condition
    EXIT; or quit Leave the MySQL client and return to your bash shell

    Important SQL syntax rules:

    • Every SQL command must end with a semicolon (;). If you press Enter without a semicolon, MySQL shows a -> continuation prompt: it is waiting for you to finish the command. Type ; and press Enter to execute it.
    • SQL keywords like SELECT, FROM, WHERE, and SHOW are case-insensitive: show databases; works the same as SHOW DATABASES;. However, database names, table names, and column values are case-sensitive on Linux systems.
    • If a table returns too many columns and the output wraps awkwardly, you can select specific columns instead of using *: SELECT column1, column2 FROM table_name;

    Walkthrough

    Step 1: Launch the Exercise and Note Both Target IPs

    Exercise 9A deploys two servers: a web server hosting the corporate intranet and a database server running MySQL. Both IP addresses appear in the Active Lab View.

    • Navigate to Exercises and locate Exercise 9A; Data Breach Assessment
    • Click Launch and wait for the status to change to Running
    • Note both target IPs: one for the intranet web server and one for the database server

    Step 2: Enumerate the Corporate Intranet

    Retrieve the intranet homepage

    Start by retrieving the intranet homepage and examining its content for navigation links, references to internal pages, or clues about the site structure.

    curl http://<webserver_ip>/

    The homepage should contain links to internal pages. Follow each link to understand what the intranet offers. Common corporate intranet sections include staff directories, internal notices, policies, and contact pages.

    Follow the internal page links

    Retrieve the staff and notices pages to understand the intranet structure.

    curl http://<webserver_ip>/staff/
curl http://<webserver_ip>/notices/

    Read the content of each page carefully. The IT notices page is particularly important; look for any references to system migrations, backup procedures, or infrastructure changes. A notice mentioning a "backup migration" is a strong indicator that backup files may still be accessible on the web server.

    Step 3: Probe for Backup Directories

    Corporate web servers sometimes host backup directories that should have been removed or access-restricted after a migration.

    Probe for a backups directory by status code

    Test whether a /backups/ directory exists on the web server by reading the HTTP status code alone.

    curl -s -o /dev/null -w '%{http_code}' http://<webserver_ip>/backups/

    A 403 Forbidden response means the directory exists but the root path is access-restricted. However, subdirectories within a restricted parent may have different permissions.

    Test backup subdirectory names

    Common backup subdirectory names include legacy, old, archive, and temp. Test variations against the restricted parent.

    curl http://<webserver_ip>/backups/legacy/

    If the legacy subdirectory is accessible, it will return a directory listing showing the files inside. Look for SQL dump files, configuration backups, and migration notes; any of these could contain sensitive information.

    Step 4: Extract Credentials from the SQL Dump

    Download the SQL dump file

    Download and examine the SQL dump file found in the backup directory. SQL dump files are database exports that contain table definitions, data, and sometimes user credentials embedded in GRANT statements or INSERT commands.

    curl http://<webserver_ip>/backups/legacy/meridian_dump.sql

    The dump may be large; the next command narrows it to the lines that matter.

    Grep the dump for credentials

    Search the output for credential-related keywords so you do not have to read the whole dump.

    curl -s http://<webserver_ip>/backups/legacy/meridian_dump.sql | grep -i -E "grant|password|identified"

    The dump file should contain a MySQL GRANT statement that reveals a database username and password. Record these credentials; they provide access to the backend database server.

    Step 5: Connect to the Backend Database

    Connect to the backend database

    Use the credentials extracted from the SQL dump to connect to the MySQL database server. The database server listens on port 3306, which is the default MySQL port.

    mysql --skip-ssl -h <dbserver_ip> \
  -u meridian_app -p'M3r1d14n_App_2024#'

    Replace <dbserver_ip> with the second target IP from the Active Lab View.

    If the connection succeeds, your terminal prompt will change from the normal Kali prompt to something like:

    MariaDB [(none)]>

    The (none) means you are connected to the MySQL server but have not selected a database yet. If you see an "Access denied" error instead, double-check that you copied the username and password exactly as they appeared in the SQL dump: including special characters like #, !, and @.

    Stuck at the -> prompt?

    If you accidentally pressed Enter without a semicolon, MySQL shows a -> continuation prompt. It is waiting for you to finish the command. Simply type ; and press Enter to execute whatever you have typed so far. If you want to cancel the current command entirely, type \c and press Enter.

    Step 6: Explore the Available Databases

    List the visible databases

    Now that you are inside the MySQL client, start by listing all databases your account can see.

    SHOW DATABASES;

    The output will show a table of database names. You should see several databases listed. Not all of them will be accessible.

    Test access to a restricted database

    Try switching to the HR database to see whether your account can reach it.

    USE meridian_hr;

    If the account does not have permission, MySQL will return an error like ERROR 1044 (42000): Access denied for user 'meridian_app'@'%' to database 'meridian_hr'. The denial is expected and demonstrates the principle of least privilege: the application service account was granted access only to the databases it needs, not to all data in the system.

    Switch to the compliance database

    Try switching to the compliance database, which the service account should be able to reach.

    USE meridian_compliance;

    If this succeeds, the prompt will change to MariaDB [meridian_compliance]>, confirming you are now working inside that database.

    Step 7: Enumerate Tables and Understand the Schema

    List tables in the compliance database

    With a database selected, list its tables.

    SHOW TABLES;

    The SHOW TABLES statement returns a list of table names.

    Inspect the data_classifications schema

    Before querying a table, it helps to understand its structure: what columns it has and what type of data each column holds. Use DESCRIBE to inspect a table's schema.

    DESCRIBE data_classifications;

    The output shows each column name, its data type (VARCHAR, INT, TEXT, etc.), and whether it allows NULL values. The schema tells you what columns are available to query before you run any SELECT statements.

    Query all data classifications

    Now query the data classifications to understand the scope of the breach.

    SELECT * FROM data_classifications;

    The SELECT * query returns all rows and all columns.

    Filter for PII records

    If the output is too wide for your terminal, you can select specific columns and filter for the most sensitive category instead.

    SELECT classification, record_name
FROM data_classifications
WHERE classification = 'PII';

    The WHERE clause filters the results to show only PII (Personally Identifiable Information) records: the most sensitive category. Any exposure of PII data triggers regulatory notification requirements under frameworks like GDPR, CCPA, and HIPAA.

    Step 8: Locate the Critical Finding and Capture the Flag

    Inspect the compliance_findings schema

    Now examine the compliance findings table. Start by checking its structure.

    DESCRIBE compliance_findings;

    The schema shows which column holds the severity and which holds the finding detail.

    Query for the critical finding

    Then query for critical-severity entries to locate the documented breach.

    SELECT finding_id, severity, finding_detail
FROM compliance_findings
WHERE severity = 'CRITICAL';

    The critical finding contains the flag in OCR{...} format. Record the flag.

    Exit the MySQL client

    When you are finished exploring, exit the MySQL client and return to your bash shell.

    EXIT;

    Your prompt returns to the normal Kali shell.

    Flag Format

    The flag is a single token retrieved from the database:

    OCR{token}

    Return to the platform in your browser and submit the flag.

    Analysis Questions

    1. The /backups/ directory returned a 403 Forbidden status, but /backups/legacy/ was accessible. Why does restricting access to a parent directory not automatically protect its subdirectories?

    Reveal Answer

    Web server access controls are configured per-directory. A Deny or Require directive on /backups/ applies only to that specific path unless the configuration explicitly includes subdirectories. If /backups/legacy/ has its own configuration block (or no configuration at all), it inherits the server's default permissions, which may allow directory listing. Inherited defaults are a common misconfiguration: administrators assume that blocking the parent path protects everything beneath it, but web servers evaluate each directory independently unless configured otherwise with recursive rules.

    2. The meridian_app database account could access meridian_compliance but not meridian_hr or meridian_finance. How does this demonstrate the principle of least privilege, and why is it still insufficient to prevent the breach?

    Reveal Answer

    Least privilege means granting each account only the minimum permissions required for its function. The meridian_app account was correctly restricted to the compliance database because the application only needs compliance data. However, least privilege at the database layer does not compensate for failures at other layers. The breach occurred because the web server exposed backup files containing the credentials in the first place. Even with perfect database permissions, an attacker who obtains any valid credential can query whatever that credential allows. Defense in depth requires security controls at every layer: web server access controls, encrypted backups, credential rotation, and network segmentation, not just database permissions.

    3. The SQL dump file contained credentials in plaintext. What steps should the migration team have taken before placing the dump file on the web server?

    Reveal Answer

    The migration team should have: (1) stripped all credential-related statements (GRANT, CREATE USER, SET PASSWORD) from the dump before transferring it; (2) stored the dump in a location outside the web server's document root so it could never be served over HTTP; (3) encrypted the dump file at rest using a tool like gpg or openssl so that even if the file were accessed, its contents would be unreadable without the decryption key; (4) deleted the dump file from the web server after the migration was complete. Leaving credentials in a web-accessible backup file is one of the most common and preventable data exposure findings in security assessments.

    Key Takeaways

    • Backup files on web servers are a frequent source of data breaches; SQL dumps, configuration backups, and archive files often contain credentials, schema details, and sensitive data that developers assume are protected by obscurity
    • HTTP status codes reveal directory structure even when access is denied; a 403 confirms the path exists, which guides further enumeration of subdirectories
    • Database least privilege limits the blast radius of a credential compromise but does not prevent the compromise itself; defense in depth requires securing every layer independently
    • Data classification helps prioritize investigation findings; PII exposure carries regulatory consequences that internal-only data exposure does not
    • Breach assessments follow a structured methodology: discover assets, map exposures, classify data, and assess impact; each stage informs the next and builds the evidence needed for compliance reporting
