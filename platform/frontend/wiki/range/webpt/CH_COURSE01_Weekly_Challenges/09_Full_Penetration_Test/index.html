    Exercise 9: Full Penetration Test

    Before You Begin

    Weeks 1 through 8 introduced individual penetration testing skills in isolation; port scanning, service enumeration, web exploitation, credential discovery, lateral movement, and privilege escalation. Exercise 9 requires you to chain every one of those skills together against a multi-server environment. You will not receive step-by-step guidance at the same level of detail as previous labs; the walkthrough provides direction, but you are expected to recognize which tool and technique to apply at each stage.

    Your VPN must be connected and your terminal open before continuing. Review your notes from Exercises 1 through 8, because every major concept from those weeks appears somewhere in the attack chain.

    Scenario

    Nexus Dynamics is a growing SaaS (Software as a Service) company based in Atlanta, Georgia. The company has hired your firm for a full-scope penetration test before their Series B funding round. The board of directors wants assurance that the company's infrastructure is secure before investors commit.

    Your point of contact is Andrea Walsh, VP of Security: "We have a perimeter web server that runs our marketing site and customer API. Behind that is our core application server that handles the heavy lifting. The web server is the only thing exposed to the internet; the core server should be completely unreachable from outside."

    Two target servers make up the engagement scope: a perimeter web server exposed on port 80, and a core application server running SSH (Secure Shell) on port 22. Three assessment markers are distributed across the infrastructure. Your job is to retrieve all three markers and assemble them into the final flag, proving complete compromise of the environment.

    A few important notes about the lab structure: the difficulty level is Advanced, and the time limit is 90 minutes. Hints are locked for the first 20 minutes; the platform will not display any hint text until that delay has passed. Use the first 20 minutes to work independently and apply your skills from the course so far.

    Your Objectives

    The following list outlines what you need to accomplish during the assessment. Each objective maps to one or more walkthrough phases below.

    • Enumerate services across both target systems using port scanning
    • Identify and exploit a web application vulnerability for initial access to the perimeter server
    • Discover credentials stored in application configuration files on the perimeter server
    • Pivot laterally to the core server using discovered credentials
    • Escalate privileges on the core server to achieve root access
    • Collect all three assessment markers and assemble the final flag
    • Submit the flag in OCR{...} format

    Background: Attack Chaining Methodology

    Real-world penetration tests rarely involve a single exploit that grants immediate access to the target. Most engagements follow a kill chain: a sequence of stages where each successful step provides the foothold needed for the next. Understanding the kill chain helps you approach complex environments methodically rather than attempting random attacks.

    The five phases of the attack chain you will execute in this exercise map directly to skills you learned in previous weeks:

    1. Reconnaissance (Week 1); Scan the target environment to discover hosts, open ports, and running services. Port scanning reveals the attack surface and tells you where to focus.
    2. Initial Access (Weeks 5-6); Exploit a vulnerability in an exposed service to gain a foothold. In web applications, command injection and other input validation flaws often provide the first way in.
    3. Credential Discovery (Weeks 2-3); Search the compromised system for credentials, configuration files, and secrets that grant access to additional systems. Developers frequently store passwords in plaintext configuration files.
    4. Lateral Movement (Week 4); Use discovered credentials to move from the initial foothold to other systems in the environment. SSH connections between servers are a common lateral movement path.
    5. Privilege Escalation (Week 7); Elevate from a standard user account to root on the target system. Misconfigured permissions, SUID (Set User ID) binaries, and weak sudo rules are the most common escalation vectors on Linux.

    Each phase builds on the one before it. You cannot pivot to the core server without credentials, and you cannot find credentials without command execution on the perimeter server. Skipping a phase or attempting them out of order will not work; the attack chain must be followed sequentially.

    Tool Primer: Combining Your Arsenal

    Previous labs introduced each tool in isolation. Exercise 9 requires you to use multiple tools in sequence, where the output of one tool feeds directly into the next. The table below summarizes the core tools and how they connect across phases.

    Tool Purpose Phase
    nmap Discover open ports and services on both servers Reconnaissance
    curl Interact with web applications and send POST requests with injection payloads Initial Access, Credential Discovery
    ssh Connect to remote servers using discovered credentials Lateral Movement
    find Search for files, enumerate SUID binaries, and exploit SUID misconfigurations Privilege Escalation
    cat Read file contents; flags, configuration files, markers All Phases

    The chaining pattern works like a pipeline. Nmap output tells you which ports are open, which tells you to investigate the web application on port 80. Curl lets you interact with the web application, discover injectable endpoints, and execute commands on the perimeter server. Command execution lets you read configuration files containing SSH credentials. SSH gets you onto the core server. The find command on the core server reveals SUID binaries, and exploiting a SUID binary gives you root. Each tool's output is the input for the next decision.

    A key difference from earlier labs: nobody will tell you which tool to use at each step. The scenario provides the context, and you must recognize which tool fits the situation. When you reach a new server or discover a new service, pause and ask yourself: "What did I learn in previous weeks that applies here?"

    Walkthrough

    Phase 1: Reconnaissance

    The engagement begins with reconnaissance. Before you can exploit anything, you need to know what is running and where.

    Step 1: Launch the Exercise and Note Both Target IPs

    Open the platform in your browser and start the exercise environment. The Nexus Dynamics lab deploys two servers, so you will see two IP addresses in the Active Lab View rather than the single IP you are used to from previous labs.

    • Navigate to Exercises and locate Nexus Dynamics: Full Penetration Test
    • Click Launch and wait for the status to change to Running
    • Note both target IPs displayed in the Active Lab View; one for the perimeter server and one for the core server
    • Record both IPs before proceeding; you will need both throughout the assessment

    The perimeter server is the externally facing system that Andrea Walsh described. The core server is the internal system that "should be completely unreachable from outside." Your attack path starts at the perimeter and works inward.

    Step 2: Scan the Perimeter Server

    Begin with a port scan of the perimeter server to identify exposed services. The perimeter server handles web traffic, so you should expect to find HTTP (Hypertext Transfer Protocol) services.

    Scan the perimeter server

    Replace <perimeter_ip> with the first target IP from the Active Lab View. Nmap reports the open ports and services that define the perimeter attack surface.

    nmap <perimeter_ip>

    Review the output and identify every open port and service. You should see port 80 open with an HTTP service; the web application that Andrea Walsh mentioned.

    Scan the core server

    Replace <core_ip> with the second target IP from the Active Lab View. Scan the internal host to learn which services it exposes.

    nmap <core_ip>

    The core server should show port 22 open with an SSH service. Record both scan results, because they define your attack surface for the rest of the assessment.

    Comparing the two scans tells you the engagement layout: the perimeter server has a web application you can reach over HTTP, and the core server has SSH that you will need credentials to access. The attack path is clear; start with the web application, find credentials, then move to SSH.

    Phase 2: Initial Access

    With reconnaissance complete, you know the perimeter server runs a web application on port 80. Your next task is to explore the application, identify injectable inputs, and achieve command execution.

    Step 3: Identify the Web Application on the Perimeter Server

    Load the perimeter web application in your browser or use curl to examine it from the command line. Start by requesting the root page to see what the application offers.

    Request the perimeter root page

    Fetch the root page of the perimeter web application to see what it exposes.

    curl http://<perimeter_ip>/

    Examine the response for clues about the application's functionality. Look for links, endpoints, API routes, or references to diagnostic features. Nexus Dynamics runs a marketing site and customer API; the application may expose administrative or operational endpoints beyond the public-facing pages.

    Step 4: Discover the /healthcheck Endpoint

    Web applications often include health-check or diagnostic endpoints that system administrators use for monitoring. These endpoints sometimes accept user input to perform network tests like ping or DNS lookups, making them potential targets for command injection.

    Probe the /healthcheck endpoint to see how it responds.

    Probe the healthcheck endpoint

    Send a plain GET request to learn what the diagnostic endpoint returns.

    curl http://<perimeter_ip>/healthcheck

    A GET request to /healthcheck may return usage information or a status page. The important detail is how the endpoint behaves when it receives POST data; diagnostic features typically accept a hostname or IP address as input to test connectivity.

    Send a baseline healthcheck POST

    Post a host value to exercise the diagnostic feature with legitimate input.

    curl -X POST http://<perimeter_ip>/healthcheck -d 'host=127.0.0.1'

    The response should contain network diagnostic output (such as ping results) for the IP address you provided. The application accepted your input and passed it to a system command; the same pattern you saw in Exercise 6 with the CloudPing diagnostic tool.

    Step 5: Exploit Command Injection on the /healthcheck Endpoint

    The /healthcheck endpoint accepts a host parameter and passes it to a system command. Test whether the application sanitizes the input by appending a shell metacharacter and a second command. The semicolon (;) tells the shell to execute an additional command after the first one completes.

    Start with a basic injection test using the id command.

    Inject the id command

    Append ;id to the host value so the shell runs id after the diagnostic command.

    curl -X POST http://<perimeter_ip>/healthcheck -d 'host=127.0.0.1;id'

    If the application is vulnerable, the response will contain the normal diagnostic output followed by the output of the id command; a line showing uid=, gid=, and groups=. The presence of the id output confirms that the server executes your injected commands without filtering.

    With command injection confirmed, you can run any command the web server process has permission to execute. Test reading a file to verify filesystem access.

    Verify filesystem access

    Inject a cat of /etc/hostname to confirm you can read files on the perimeter server.

    curl -X POST http://<perimeter_ip>/healthcheck -d 'host=127.0.0.1;cat /etc/hostname'

    The response should include the server's hostname, confirming that you have arbitrary command execution on the perimeter server.

    The first assessment marker is located on the perimeter server. Use your command injection access to read it.

    Read the first marker

    Inject a cat command that prints the marker file from the assessment directory.

    curl -X POST http://<perimeter_ip>/healthcheck -d 'host=127.0.0.1;cat /opt/nexus/assessment/marker1.txt'

    Record the marker value; you will need it to assemble the final flag.

    Phase 3: Credential Discovery

    You now have command execution on the perimeter server. The next objective is to find credentials that grant access to the core server. Developers frequently store database passwords, API keys, and SSH credentials in environment files and configuration files within the application directory.

    Step 6: Extract SSH Credentials from the Application Configuration

    The Nexus Dynamics web application lives in /var/www/nexus-app/. Environment files (commonly named .env) are a standard location for storing application secrets such as database connection strings, API tokens, and service credentials. Use your command injection to read the .env file.

    Read the application .env file

    Inject a cat of the application's environment file to harvest any stored secrets.

    curl -X POST http://<perimeter_ip>/healthcheck -d 'host=127.0.0.1;cat /var/www/nexus-app/.env'

    Examine the output for variables containing SSH credentials. You should find entries that specify a username and password for the core server, formatted as environment variables:

    CORE_SSH_USER=deploy
CORE_SSH_PASS=N3xus_D3pl0y#

    These credentials belong to the deploy account on the core application server. Record both values; the username and the password; because you will use them in the next phase to establish an SSH connection. Credential storage in plaintext .env files is a common finding in web application penetration tests, and it represents a significant security risk when an attacker gains filesystem access through any vulnerability.

    Phase 4: Lateral Movement

    With valid SSH credentials for the core server, you can now move laterally from the perimeter to the internal infrastructure. Lateral movement is the point where a perimeter breach becomes a full internal compromise.

    Step 7: SSH to the Core Server

    Use the credentials discovered in Step 6 to connect to the core server over SSH. The core server exposes port 22, which your Nmap scan confirmed in Step 2.

    SSH to the core server

    Replace <core_ip> with the second target IP from the Active Lab View. When prompted for a password, enter the credential you extracted from the .env file.

    ssh deploy@<core_ip>

    A successful login drops you into a shell on the core server as the deploy user.

    After logging in, confirm your identity and assess your current privilege level.

    Confirm your foothold on the core server

    Check your account and privileges on the core server shell.

    whoami
id

    The whoami command should return deploy, and the id output should show a standard user account with no special group memberships. You are now on the core server, but you do not yet have root access.

    Read the second assessment marker, which is accessible to the deploy user.

    Read the second marker

    Print the marker file from the deploy user's home directory.

    cat /home/deploy/marker2.txt

    Record the marker value alongside the first one from the perimeter server.

    Phase 5: Privilege Escalation

    You have user-level access on the core server, but the final assessment marker is in /root/, which requires root privileges to read. Apply the privilege escalation techniques you learned in Week 7 to elevate from the deploy user to root.

    Step 8: Enumerate SUID Binaries on the Core Server

    SUID enumeration is one of the first checks in any Linux privilege escalation methodology. Search the filesystem for binaries with the SUID bit set.

    Enumerate SUID binaries on the core server

    Run the SUID search on the core server. The 2>/dev/null suppresses permission-denied noise so only the file paths print.

    find / -perm -4000 -type f 2>/dev/null

    Review the output and compare it against the standard set of SUID binaries you learned about in Exercise 7. Expected SUID binaries include passwd, su, mount, umount, chfn, chsh, and newgrp. Any binary outside that expected set is a potential escalation vector. Look for /usr/bin/find in the results; its -exec flag allows execution of arbitrary commands, so when it carries the SUID bit and is owned by root, every command run through -exec runs as root.

    Verify the permissions on the suspicious binary.

    Verify the find binary permissions

    Inspect the binary to confirm the SUID bit and owner.

    ls -la /usr/bin/find

    The output should show -rwsr-xr-x with root as the owner; the s in the owner's execute position confirms the SUID bit is active.

    Step 9: Exploit SUID find to Escalate to Root

    Use the same technique from Exercise 7 to spawn a root shell through the SUID find binary. The -exec flag runs a command for each matched file, and the -p flag on /bin/sh preserves the elevated effective UID (User ID) instead of dropping it.

    Spawn a root shell through SUID find

    Run this on the core server. Because find is SUID root, the /bin/sh -p it launches keeps root's effective UID.

    find . -exec /bin/sh -p \; -quit

    Breaking down the command:

    • find .: search the current directory (the search target does not matter; you need find to execute, not to find files)
    • -exec /bin/sh -p \;: for each matched file, execute /bin/sh with the -p flag to preserve root privileges
    • -quit: stop after the first match so only one shell is spawned

    Verify that the escalation succeeded.

    Confirm root on the core server

    Check your effective identity in the new shell.

    whoami
id

    The whoami command should return root, and the id output should show euid=0(root). You now have full root-level access on the core server.

    Step 10: Read the Final Assessment Marker

    With root privileges, you can access the /root/ directory. Read the third and final assessment marker.

    Read the final marker

    Print the last marker file from the root home directory, now readable thanks to your root shell.

    cat /root/marker3.txt

    Record the marker value. You now have all three assessment markers from across the infrastructure:

    • Marker 1: from /opt/nexus/assessment/marker1.txt on the perimeter server
    • Marker 2: from /home/deploy/marker2.txt on the core server
    • Marker 3: from /root/marker3.txt on the core server

    Assemble the three markers into the final flag using the OCR{...} format as indicated by the lab instructions.

    Analysis Questions

    The following questions ask you to reflect on the methodology you applied across the full assessment. Each answer appears directly below the question.

    1. The Nexus Dynamics engagement required five distinct phases to achieve full compromise. Why is it important to follow the kill chain sequentially rather than attempting random exploits against each server?

    Reveal Answer

    Each phase produces information required by the next phase. Without reconnaissance, you would not know which ports are open or which services to target. Without initial access on the perimeter server, you could not read the .env file containing SSH credentials. Without those credentials, you could not log into the core server. Random exploitation skips the information-gathering steps that make each subsequent attack possible, wasting time on attacks that lack the necessary context to succeed.

    2. Andrea Walsh stated that the core server "should be completely unreachable from outside." Your Nmap scan showed port 22 open on the core server. Does the fact that you could scan port 22 contradict her statement, and what does it tell you about the network architecture?

    Reveal Answer

    The network architecture in the lab environment allows direct connectivity to both servers for practical purposes. In a production environment, the core server would sit behind a firewall that blocks external access to port 22. Andrea's statement reflects the intended architecture, but network segmentation must be enforced through firewall rules and access control lists; not assumed. The engagement proved that even if the core server were properly segmented, an attacker who compromises the perimeter server can pivot internally, bypassing perimeter-only defenses.

    3. The SSH credentials were stored in plaintext in a .env file on the perimeter server. Name two alternative approaches that would prevent an attacker with filesystem access from extracting usable credentials.

    Reveal Answer

    The application could retrieve credentials at runtime from a secrets management system such as HashiCorp Vault, AWS Secrets Manager, or Azure Key Vault. Secrets managers store credentials in an encrypted backend and provide them to the application through authenticated API calls; even if an attacker reads the .env file, it would contain only a reference to the secret, not the secret itself. The second approach is to eliminate shared credentials entirely by using SSH key-based authentication with keys stored in a hardware security module (HSM) or a secrets manager, removing passwords from the filesystem altogether.

    4. You exploited the same SUID find binary technique from Exercise 7 to escalate privileges on the core server. If an administrator removed the SUID bit from find but left the deploy user's SSH credentials unchanged, would the system be secure? Explain your reasoning.

    Reveal Answer

    Removing the SUID bit from find eliminates one escalation path but does not address the root cause. The deploy account still has valid SSH access to the core server, and the credentials are still stored in plaintext on the perimeter server. An attacker could still pivot to the core server and then search for alternative escalation vectors; writable cron jobs, sudo misconfigurations, kernel vulnerabilities, or other SUID binaries. Thorough remediation requires fixing every link in the chain: sanitizing the web application input, removing plaintext credentials, rotating the compromised password, auditing all SUID binaries, and implementing network segmentation.

    Key Takeaways

    • Attack chaining is the core methodology of penetration testing; real engagements require linking multiple vulnerabilities across different systems to achieve full compromise, not relying on a single exploit
    • Reconnaissance drives every decision in the kill chain; without accurate enumeration of services and ports, you cannot identify which attack techniques to apply at each stage
    • Credential storage in plaintext configuration files (.env, config.ini, settings.py) remains one of the most common findings in web application assessments, and it frequently enables lateral movement to internal systems
    • Lateral movement transforms a perimeter-only breach into a full internal compromise; network segmentation and credential isolation are the primary defenses against pivoting
    • Privilege escalation through SUID misconfigurations demonstrates that a single misconfigured permission can undermine an otherwise well-secured system; regular auditing of SUID binaries is essential
    • Week 10 builds on this exercise by introducing reporting and remediation planning, where you will learn to translate technical findings into actionable recommendations for stakeholders like Andrea Walsh and the Nexus Dynamics board
