    Exercise 11: Credential Pivot Attack

    Before You Begin

    Week 10 focused on web application exploitation, where you probed a target through its exposed HTTP services. The skills you built there; reading source code, understanding application logic, and connecting to remote services; carry forward into a new domain: lateral movement. Your VPN must be connected and your terminal ready before continuing.

    Scenario

    Crestline Financial Services, a regional investment firm based in Charlotte, North Carolina, engaged your team at Apex Red Team for an internal network penetration test. Phase 1 is complete; your team gained initial access to the company's front-end web server through a vulnerability in their customer portal.

    You now have SSH (Secure Shell) access to the web server as the "webdev" service account. Your objective for Phase 2 is lateral movement: find a way to reach other systems on the internal network. Crestline's IT manager, Nathan Cole, mentioned during the scoping call that the web application connects to an internal database server that "only the app can reach." He is confident the database credentials are properly secured.

    Prove him wrong. Find the database credentials, pivot to the internal server, and extract the assessment marker to demonstrate the risk. Document the full attack chain for the final report.

    Your Objectives

    The engagement scope covers two internal servers. Your goals for Phase 2 are well-defined and mirror a real-world penetration test report structure.

    • Enumerate the compromised web server for stored credentials and configuration files
    • Identify hardcoded database credentials in application configuration
    • Use discovered credentials to pivot laterally to an internal server
    • Extract evidence from the database server to complete the assessment
    • Capture the flag

    Background: Lateral Movement Through Credential Reuse

    Lateral movement is the process of moving from one compromised system to another within a network. Attackers who gain access to a single machine rarely stop there; they search the filesystem for credentials, tokens, and connection strings that let them reach additional systems. A single set of reused credentials can turn a minor foothold into full network compromise.

    Web applications frequently store database connection details in plaintext configuration files. Developers need the application to connect to backend databases automatically, so they place hostnames, usernames, and passwords in files such as .env, config.php, database.yml, or files within a config/ directory. These files often live alongside the application code under /var/www/ or similar web root directories. The credentials stored in these files are rarely rotated and often grant broad access to the database server.

    The danger is compounded when administrators reuse the same credentials for SSH access, database logins, or other services. An attacker who finds a database password in a .env file can try that same password against SSH on the database host; and succeed far more often than organizations expect.

    Tool Primer: Searching for Credentials

    Credential hunting on a Linux system relies on a small set of commands you already know: find, grep, and cat. The key is knowing where to look and what patterns to search for. The following commands are the most useful for locating credentials in application directories.

    Locating configuration files with find:

    find /var/www/ -name "*.env" -o -name "*.conf" -o -name "*.cfg" -o -name "*.ini"

    The find command searches a directory tree for files matching the given name patterns. The -o flag means "or," so the command above looks for any file ending in .env, .conf, .cfg, or .ini under the /var/www/ directory.

    Searching file contents with grep:

    grep -ri "password\|pass\|secret\|key\|token" /var/www/

    The -r flag tells grep to search recursively through all files in the directory. The -i flag makes the search case-insensitive. The \| syntax separates multiple search terms so grep matches any of them. Sensitive keywords like "password," "secret," and "token" frequently appear near hardcoded credentials.

    Reading a specific file with cat:

    cat /var/www/crestline-portal/.env

    Once you identify a promising file, cat prints its full contents to the terminal. Environment files (.env) follow a KEY=VALUE format, making credentials visible at a glance.

    Step 2: Connect to the Web Server

    Your team obtained SSH credentials for the web server during Phase 1. Use them now to establish your initial foothold on the Crestline network.

    SSH into the web server

    Open an SSH session to the compromised web server using the webdev service account recovered in Phase 1. Replace <web_server_ip> with the IP address shown in the Active Lab View.

    ssh webdev@<web_server_ip>

    When prompted for the password, enter:

    Cr3st_W3b_2024#

    After a successful login, your prompt should change to reflect the webdev user on the web server.

    Step 3: Explore the Web Application Directory

    Web applications store their files under a web root directory, typically /var/www/. The Crestline customer portal lives in a subdirectory there. Start by listing the contents of the application directory.

    List the web application directory

    Run this on the web server you just logged into. The -a flag reveals hidden dotfiles, and -l shows ownership and permissions.

    ls -la /var/www/crestline-portal/

    Look for configuration files and directories in the output. Files named .env are hidden by default (the leading dot hides them from a plain ls), which is why the -a flag is important. You should also look for a config/ directory, which applications commonly use to store connection parameters.

    Step 4: Read Configuration Files and Discover Database Credentials

    The application directory should contain both a .env file and a config/ directory. Read them both to build a complete picture of the application's backend connections.

    Read the .env file

    Print the environment file on the web server. Environment files follow a KEY=VALUE format, so credentials are visible at a glance.

    cat /var/www/crestline-portal/.env

    Look for lines starting with DB_HOST, DB_USER, and DB_PASS. These values tell you where the database server lives, what account the application uses, and the password for that account.

    List the config directory

    Configuration backups and API key files sometimes hold additional credentials or assessment tokens. List the directory contents first.

    ls -la /var/www/crestline-portal/config/

    Read any files you find there.

    Read a config file

    Replace <filename> with each file you found in the previous listing and print its contents.

    cat /var/www/crestline-portal/config/<filename>

    From the .env file, you should find the following connection details:

    • DB_HOST: the hostname of the database server (dbserver)
    • DB_USER: the database account username (dbadmin)
    • DB_PASS: the database account password

    Record all of these values. You will use them in Step 6 to pivot to the database server.

    Step 5: Find the Assessment Token on the Web Server

    The config directory may contain a file with an assessment token. Look for files with names that suggest backup or key storage, and search for lines containing "assessment_token" or similar markers.

    Search config files for the assessment token

    Recursively grep the config directory on the web server for the marker string so you do not have to open every file by hand.

    grep -r "assessment_token" /var/www/crestline-portal/config/

    Record the token value you find. The complete flag is assembled from pieces found on both servers, so you will need to combine the values from the web server and the database server.

    Step 6: Pivot to the Database Server

    Using the credentials you discovered in Step 4, connect to the database server via SSH. The lateral movement happens here; you are using credentials harvested from the web server to access a completely separate system.

    Pivot to the database server over SSH

    From the web server shell, SSH onward to the internal database host using the harvested dbadmin credentials. The hostname dbserver resolves on the internal network.

    ssh dbadmin@dbserver

    When prompted for the password, enter the DB_PASS value you found in the .env file:

    F1n4nc3_DB_Pr0d#

    A successful login confirms the core finding of the engagement: credentials stored in plaintext application configuration files can be used to access other systems on the network.

    Step 7: Find the Flag Token on the Database Server

    The database server contains the second piece of the assessment marker. Check the dbadmin home directory and any subdirectories for files related to the assessment.

    List the dbadmin home directory

    Now on the database server, list the home directory to spot maintenance folders or token files.

    ls -la /home/dbadmin/

    Look for a maintenance/ directory or similar location.

    Read the assessment token file

    Print the token file from the maintenance directory on the database server.

    cat /home/dbadmin/maintenance/assessment_token.txt

    Record the value you find. Combine the token from Step 5 with the token from the database server to assemble the complete flag in OCR{...} format.

    Step 8: Interpret the Results

    Review the attack chain you documented. The engagement followed a clear sequence that penetration testers encounter regularly in corporate environments.

    You started with a low-privilege service account on the web server. That account had read access to application configuration files; a normal requirement for the web application to function. Inside those configuration files, you found plaintext database credentials. Because the database server accepted SSH connections with the same credentials, you were able to move laterally from one system to another without exploiting any software vulnerability. The entire pivot relied on credential reuse and plaintext credential storage.

    Nathan Cole believed the database was protected because "only the app can reach" it. The database server's PostgreSQL port (5432) may indeed be firewalled from external access, but SSH (port 22) was not restricted in the same way. Layered security; restricting both the credentials and the network access; would have made the pivot significantly harder.

    Flag Format

    Assemble the flag using the tokens in the order you discovered them:

    OCR{<webserver_token>_<pivottarget_token>}

    Where <webserver_token> is the value from the web config API keys backup, and <pivottarget_token> is from the pivot target assessment token on the database server.

    Analysis Questions

    The following questions ask you to think beyond the steps you performed and consider the broader security implications. Take a moment to reason through each one before reading the answer.

    1. Why do developers store database credentials in plaintext configuration files, and what alternatives exist?

    Reveal Answer

    Applications need credentials at runtime to connect to backend databases. Developers store them in .env files or config directories because the approach is fast and compatible with most frameworks. Safer alternatives include environment variable injection at deploy time (so credentials never touch disk), secrets management tools like HashiCorp Vault, and cloud provider secret stores such as AWS Secrets Manager. Each approach removes the plaintext file from the server's filesystem.

    2. The database server accepted SSH connections with the same credentials used for the database. What security principle does credential reuse violate, and how would you fix it?

    Reveal Answer

    Credential reuse violates the principle of least privilege: each service should have its own unique credentials scoped to the minimum access required. The SSH account and the database account should use separate passwords. Better yet, SSH access to the database server should require key-based authentication with no password login allowed, and database access should be restricted to connections from the web server's IP address only.

    3. If the web server had been configured so the webdev account could not read the .env file, would the attack still succeed? Why or why not?

    Reveal Answer

    Restricting file permissions on .env so that only the application process (running as a different user) can read it would block the credential discovery step entirely. The webdev account would see the file in a directory listing but could not read its contents. Proper file ownership and permissions (e.g., chmod 600 owned by the application user) are a low-cost defense that many organizations overlook.

    Key Takeaways

    • Lateral movement is the process of moving from one compromised system to another within a network, and credential reuse in configuration files is one of the most common paths attackers exploit
    • Plaintext credentials in .env files and config directories are a top finding in penetration test reports; applications need database access, but storing passwords in readable files creates unnecessary risk
    • Credential reuse across services (using the same password for SSH and database access) multiplies the impact of a single credential leak
    • File permissions on configuration files are a critical but frequently neglected control; the application user should be the only account that can read sensitive configs
    • Defense in depth requires securing both the credentials (unique passwords, secrets management) and the network path (firewall rules, IP allowlists); Week 12 will explore how defenders detect and respond to lateral movement attempts
