    Exercise: Block a Port

    Before You Begin

    You will enable a firewall on a remote Linux server and block a single insecure service. The entire exercise takes place across two machines: your Kali terminal for scanning and your target server where you configure the firewall over SSH. Your VPN must be connected and your terminal open.

    Scenario

    Greenleaf Accounting is a three-person firm in Dallas, Texas. They run a single Ubuntu server for file storage. Two services are running on the server:

    Port Service Purpose
    21 vsftpd (FTP) Legacy file sharing, no longer used
    22 OpenSSH Remote administration

    A former employee set up the FTP server years ago. Nobody uses it anymore, but it is still running and accepting anonymous connections. The firm's accountant, Maria Chen, asked you to "turn on the firewall and shut down that FTP thing." SSH must stay open so the IT consultant can manage the server remotely.

    Credentials for the Greenleaf server:

    Username Password Access
    sysadmin GreenFW2026# SSH, sudo (no password required)

    Background: Firewalls in 60 Seconds

    A firewall controls which network traffic is allowed to reach a machine. Without a firewall, every running service is reachable by anyone on the network. With one, you decide exactly which ports stay open and which get blocked.

    UFW (Uncomplicated Firewall) is the standard firewall tool on Ubuntu. It works by applying a default policy to all traffic and then layering exceptions on top. The two policies that matter today:

    Policy Effect
    default deny incoming Block all inbound traffic unless a rule explicitly allows it
    default allow outgoing Let the server reach the internet freely (for updates, DNS, etc.)

    When you combine default deny incoming with an allow rule for SSH, the result is simple: SSH works, everything else is blocked.

    Walkthrough

    Step 1: Launch the Exercise

    • Navigate to your Course view and locate the Week 12 assignment
    • Click Launch on "Block a Port"
    • Wait for the status to change to Running
    • Note the target IP displayed in the Active Lab View

    Step 2: Baseline Scan

    Scan the target from Kali to see what is exposed before any firewall rules exist.

    Kali - Baseline port scan

    nmap -sV <target_ip>

    You should see two open ports:

    Port State Service
    21/tcp open vsftpd
    22/tcp open OpenSSH

    Both services are reachable from the network. Anyone could connect to the FTP server and browse the old files anonymously.

    What did you observe? Two ports are open. One of them (FTP) should not be accessible. Your goal is to block it while keeping SSH alive.

    Step 3: SSH into the Target

    Connect to the Greenleaf server using the credentials from the scenario.

    Kali - SSH into the target

    ssh sysadmin@<target_ip>

    Accept the host key fingerprint when prompted (yes), then enter the password GreenFW2026#.

    Once logged in, check UFW status:

    Target - Check UFW status

    sudo ufw status

    The output reads Status: inactive. The firewall is installed but not running.

    Step 4: Allow SSH

    Before enabling the firewall, add a rule to allow SSH. If you skip this step, the firewall will block your own connection the moment it activates.

    Target - Allow SSH

    sudo ufw allow 22/tcp

    The output confirms: Rules updated.

    Why SSH first? You are connected to the server over SSH right now. Enabling a default-deny firewall without an SSH rule will immediately drop your connection. The terminal will freeze, and you will have no remote way to fix it. Always allow SSH before enabling.

    Step 5: Enable UFW

    Set the default policy to deny all inbound traffic and activate the firewall:

    Target - Set default policy and enable

    sudo ufw default deny incoming
sudo ufw enable

    Type y when prompted. Your SSH session will survive because of the rule you added in Step 4.

    Verify the firewall is active:

    Target - Confirm active status

    sudo ufw status

    Expected output:

    Status: active

To                         Action      From
--                         ------      ----
22/tcp                     ALLOW       Anywhere
22/tcp (v6)                ALLOW       Anywhere (v6)

    One rule: SSH is allowed. Everything else (including FTP on port 21) is denied by the default policy. You did not need to write a "deny FTP" rule because the default-deny policy handles it automatically.

    Step 6: Verify from Kali

    Switch back to your Kali terminal and scan again:

    Kali - Scan after enabling UFW

    nmap -sV <target_ip>

    Compare the results to your baseline:

    Port Before After
    21/tcp open filtered
    22/tcp open open

    Port 21 now shows as filtered. Nmap sent packets to port 21 but received no response; the firewall silently dropped them. Port 22 is still open because your allow rule permits SSH traffic.

    What did you observe? FTP went from "open" to "filtered." The service is still running on the server, but the firewall prevents anyone on the network from reaching it.

    Analysis Questions

    1. You only created one allow rule (for SSH), yet FTP was blocked. How?

    Reveal Answer

    The default deny incoming policy blocks all inbound traffic that does not match an explicit allow rule. Since there is no allow 21/tcp rule, FTP traffic hits the default policy and gets dropped. You do not need individual deny rules for each service; the default policy covers everything you did not explicitly allow.

    2. The FTP service is still running on the server even though the firewall blocks it. Is the problem fully solved?

    Reveal Answer

    The firewall prevents remote access, but the service still consumes system resources and could be exploited if an attacker gains local access through another vector. Best practice is to also stop and disable the service itself: sudo systemctl stop vsftpd && sudo systemctl disable vsftpd. The firewall is one layer of defense; disabling unused services is another.

    3. What would happen if you had run sudo ufw enable before sudo ufw allow 22/tcp?

    Reveal Answer

    The firewall would activate with a default-deny policy and no allow rules. Your SSH session would freeze immediately because the firewall would start dropping SSH packets. Recovery would require physical console access or an out-of-band management interface. On a cloud server with no console, you might need to attach the disk to another instance to fix the configuration.

    Key Takeaways

    • Default-deny blocks everything you did not explicitly allow; you do not need individual deny rules for each port
    • Always allow SSH before enabling a remote firewall, or you will lock yourself out
    • A filtered port in Nmap means the firewall is silently dropping packets
    • Firewalls and service management are complementary: block the port with the firewall and disable the service if it is no longer needed
    • UFW rules take effect immediately with no restart required

    Spaced Repetition

    Card 1 - Enable UFW safely

    Q: You are SSH'd into a remote server. Write the commands to enable UFW without losing your connection.

    Answer 
    sudo ufw allow 22/tcp
sudo ufw default deny incoming
sudo ufw enable

    Allow SSH first, then set the default policy, then enable. Order matters.

    Card 2 - Default deny vs explicit deny

    Q: Do you need to write sudo ufw deny 21/tcp to block FTP when using a default-deny policy?

    Answer

    No. The default-deny policy blocks all traffic that does not match an allow rule. An explicit deny rule is only needed when the default policy is allow or when you want to block a specific port that another rule might otherwise permit.

    Card 3 - Filtered vs closed

    Q: After enabling UFW, Nmap reports port 21 as "filtered" instead of "closed." What is the difference?

    Answer

    Filtered means no response at all; the packet was silently dropped by a firewall. Closed means the host sent back a TCP RST, confirming no service is listening. Filtered reveals less information to an attacker because they cannot tell whether a service exists behind the firewall.
