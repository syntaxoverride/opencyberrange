    Exercise OTSOC-5.3: PLC Logic Root-Cause

    Scenario

    The freezer incident at Pecan Creek Creamery is contained and the volatile evidence is preserved. Now you have to prove the root cause. The plant kept a known-good baseline parameter export from seven days before the incident, and the incident response team captured the running parameters at the time of impact. Diff the two exports, find the single changed setpoint, reconstruct what the attacker did, and build a timeline mapped to MITRE ATT&CK for ICS.

    You are the OT incident responder writing the root-cause section of the report. Both exports are staged in the read-only evidence package. You pull them with curl, diff them with jq and python3 on your Kali-based RangeBox, and cross-reference the auth log and the historian trend to fix the access path and the change time.

    Host Role
    evidence.pcc.local (HTTP 80) The IR evidence package

    The two controller exports you need:

    File What it is
    freezer_plc_baseline.json Known-good baseline, captured seven days before the incident
    freezer_plc_running.json Running parameters at the time of impact

    Why this matters

    Containment stops the bleeding; root cause stops it from happening again. An OT incident report that says the freezer got warm is useless to a plant manager who has to decide whether to change a credential, a firewall rule, or a controller protection setting. A root cause that names the exact parameter that changed, the value it changed from and to, and the access path that delivered the change tells the manager precisely what to fix. The cleanest way to prove root cause on a controller is a baseline diff: compare the running parameters against a known-good export and let the single difference fall out. Every other parameter matching the baseline is itself evidence, because it rules out a broad reconfiguration and pins the incident to one deliberate write.

    Mapping the reconstructed change to ATT&CK for ICS turns a one-off finding into a defensible narrative. T0836, Modify Parameter, is the technique an unauthorized setpoint write falls under, and naming it lets a SOC compare this incident against known adversary behavior and build a detection that catches the next one. The flag is derived from the changed setpoint, so reconstructing the diff correctly is what earns it.

    Background: Baseline Diff as Root-Cause Proof

    A baseline diff compares a known-good controller configuration against the configuration at the time of impact. In OT it is the most reliable root-cause method for a parameter attack, because controllers hold a small, stable set of setpoints, and a single changed value stands out against an otherwise identical baseline.

    Concept Meaning here
    Baseline The export captured seven days before, labeled known-good
    Running The export captured at the time of impact
    Single-difference principle If only one parameter differs, the incident is one deliberate change, not a broad reconfiguration
    ATT&CK for ICS T0836 Modify Parameter: an adversary alters a control setpoint or parameter to affect the process

    Why the unchanged parameters matter too

    A diff that shows only one changed parameter is a strong finding. It rules out a sweeping reconfiguration, a firmware swap, or a logic download, and pins the incident to a single setpoint write. The parameters that match the baseline are not noise; they are the control that proves the change was surgical.

    Walkthrough

    Step 1: Pull both controller exports

    Collect the baseline and the running export so you can compare their parameter sets. Save local copies so the diff is repeatable.

    Kali - pull the baseline and the running export

    curl -s "http://$EVID/freezer_plc_baseline.json" -o baseline.json
curl -s "http://$EVID/freezer_plc_running.json"  -o running.json
jq '{label: .label, params: .parameters}' baseline.json
jq '{label: .label, params: .parameters}' running.json

    The baseline is labeled known-good and the running export is labeled as the parameters at the time of the incident. The running export carries a few extra fields the baseline lacks, the last_write_* metadata, which you will use to pin the access path.

    Step 2: Diff the parameter sets

    Compare the two parameters objects key by key. A small Python diff lists every key whose value changed between the baseline and the running export, so you do not have to eyeball two JSON blobs.

    Kali - diff the parameter sets

    python3 - <<'PY'
import json
base = json.load(open("baseline.json"))["parameters"]
run  = json.load(open("running.json"))["parameters"]
for k in sorted(set(base) & set(run)):
    if base[k] != run[k]:
        print(f"CHANGED  {k}: {base[k]}  ->  {run[k]}")
PY

    The diff output

    CHANGED  barrel_temp_pv_c: -5.0  ->  1.8
CHANGED  barrel_temp_sp_c: -5.0  ->  2.5

    Two values differ, but only one is a commanded change. The barrel_temp_pv_c is the process value, the measured temperature, and it moved because the setpoint moved. The barrel_temp_sp_c is the setpoint, the commanded target, and it is the parameter the attacker actually wrote. The setpoint changed from minus 5.0 C to plus 2.5 C; the process value followed. Every other parameter matched the baseline, which confirms a single surgical change.

    Step 3: Correlate the change with the access path

    A changed setpoint is the what. The last_write_* metadata in the running export plus the auth log give you the who and the how. Read the metadata, then confirm it against the jump-host auth log.

    Kali - read the last-write metadata

    jq '.parameters | {last_write_register, last_write_value_raw, last_write_source_ip}' running.json

    The write metadata

    {
  "last_write_register": 11,
  "last_write_value_raw": 25,
  "last_write_source_ip": "10.100.4.66"
}

    The controller recorded that register 11 was written with a raw value of 25, the integer that decodes to plus 2.5 C on the setpoint scale, from a single source. Now confirm that source reached the OT network through the jump host.

    Kali - confirm the access path in the auth log

    curl -s "http://$EVID/jumphost_auth.log" | grep -i 'Accepted'

    The auth log shows the ot_contractor account accepted from the same source IP the controller recorded. The access path is now fixed: a stolen contractor credential, a jump-host login, and a single Modbus-style write to the freezer setpoint register.

    Step 4: Build the timeline mapped to ATT&CK for ICS

    Assemble the corroborated facts into an ordered timeline and tag each step with its ATT&CK for ICS technique. The historian trend and the corporate access log give you the bracketing events; the controller export gives you the impact.

    Kali - confirm the physical effect in the historian trend

    curl -s "http://$EVID/historian_timeseries.json" \
  | jq '[.[] | select(.tag=="freezer_barrel_temp_c")] | .[-3:]'

    The trend shows the barrel temperature climbing across the anomaly window, the physical confirmation that the setpoint write took effect. With that, build the timeline:

    Incident timeline (PCC-IR-2026-014):

    Order Event Evidence source ATT&CK for ICS
    1 LFI on the IT/OT boundary portal pulled the remote-access profile corpweb_access.log Initial access via IT/OT boundary
    2 Contractor credential used to log into the jump host jumphost_auth.log Valid Accounts
    3 Freezer registers enumerated, then setpoint register written jumphost_shell_history.txt T0836 Modify Parameter
    4 Barrel setpoint changed from minus 5.0 C to plus 2.5 C freezer_plc_running.json diff T0836 Modify Parameter
    5 Barrel temperature drifted warm across the window historian_timeseries.json Impact: product spoilage

    Step 5: State the root cause

    Write the root cause in one sentence a manager can act on. Name the parameter, the before and after values, and the consequence.

    Root cause: An unauthorized engineering write moved the freezer barrel setpoint from minus 5 C to plus 2.5 C, warming product below the alarm threshold while the process kept running.

    That sentence tells the plant exactly what to fix: control who can write to the freezer setpoint register, and add a detection for an out-of-band setpoint change.

    Output Interpretation

    • Two values changed in the diff, but only the setpoint is a commanded change; the process value moved because the setpoint moved, so report the setpoint as the attack and the process value as the effect
    • Every unchanged parameter is evidence that the attack was a single surgical write, not a broad reconfiguration, which narrows the remediation to one register and one access path
    • A raw register value of 25 decodes to plus 2.5 C on the controller scale; reporting the raw integer without decoding it would understate the impact to a reader who reads it as 25 degrees
    • The historian trend is the independent confirmation that the setpoint write reached the physical process; a setpoint change with no corresponding temperature drift would suggest the write was blocked or rolled back

    Analysis Questions

    1. The diff shows two changed values. Why do you report only one of them as the root cause?

    Reveal answer

    Only barrel_temp_sp_c, the setpoint, is a commanded change. barrel_temp_pv_c, the process value, is the measured temperature, and it moved because the controller drove the barrel toward the new setpoint. Reporting both as separate attacks would misrepresent a single write as two events. The setpoint is the cause; the process value is the effect.

    2. Why does it matter that every other parameter matched the baseline?

    Reveal answer

    Matching parameters rule out a sweeping reconfiguration, a firmware change, or a logic download, and pin the incident to one deliberate setpoint write. That narrows remediation to controlling write access to a single register and confirms the attacker's goal was a quiet quality attack, not a destructive one. The unchanged parameters are the control that gives the diff its evidentiary weight.

    3. Which ATT&CK for ICS technique covers the setpoint write, and why is naming it useful?

    Reveal answer

    T0836, Modify Parameter, covers an adversary altering a control setpoint or parameter to affect the process. Naming the technique lets the SOC map this incident against known adversary behavior, write a detection that generalizes beyond this one register, and communicate the incident in a vocabulary that other defenders and regulators already share.

    Capture the Flag

    The flag is derived from the changed setpoint you found in the diff: the baseline value and the running value. From Step 2, the baseline barrel_temp_sp_c is minus 5.0 C and the running value is plus 2.5 C. To stay ASCII-safe the flag spells a minus sign as the word minus and a decimal point as an underscore, so the baseline value minus 5.0 becomes the token minus5 and the running value plus 2.5 becomes the token 2_5. Join your two tokens with the literal _to_ (underscore, the word to, underscore) to form OCR{barrel_sp_changed_<baseline-token>_to_<running-token>}. Worked example with different numbers: a baseline of minus 8.0 and a running of plus 1.5 would read OCR{barrel_sp_changed_minus8_to_1_5}. The flag names the parameter that changed and the values it changed between.

    Flag format: OCR{barrel_sp_changed_<masked>}

    The masked part encodes the baseline setpoint and the running setpoint you read out of the diff. Assemble the flag and submit it in the OCR platform.
