    Exercise 5A: What Just Happened?

    Before You Begin

    Previous exercises placed you in the attacker's role: scanning, enumerating, exploiting, escalating. The perspective flips here. A security incident has already occurred at the Bean & Byte Cafe. Your job is to figure out what happened by analyzing a packet capture.

    Make sure you have:

    • VPN connected and verified
    • SSH client available
    • Familiarity with strings, grep, base64 commands

    Scenario

    A Bean & Byte Cafe customer reported unauthorized transactions on their bank account shortly after using the cafe WiFi. Management retained your firm to investigate. A network tap captured traffic during the suspected incident window.

    The packet capture resides on an analyst workstation. SSH in, examine the evidence, and reconstruct the attack chain. Determine what the attacker did, what they stole, and how they did it.

    Your Objectives

    • Access the analyst workstation
    • Analyze the PCAP file for attack evidence
    • Identify the attack method (ARP spoofing, DNS hijacking)
    • Extract stolen credentials from HTTP traffic
    • Decode exfiltrated data to find the flag

    Background: Network Forensics

    Network forensics examines captured traffic to reconstruct events, identify attackers, and determine the scope of a compromise. The primary evidence format is the PCAP (packet capture) file.

    Common Attack Indicators in PCAP Data

    Attack What to Look For
    ARP Spoofing Multiple ARP replies for the same IP from different MACs
    DNS Hijacking DNS responses resolving legitimate domains to unexpected IPs
    Credential Theft HTTP POST requests containing usernames and passwords in cleartext
    Data Exfiltration Outbound connections to unfamiliar hosts carrying encoded payloads

    Forensic Tools

    Tool Use Case
    strings Extract readable text from binary files: fast first pass
    tcpdump -r Parse and display PCAP packets with protocol detail
    grep Filter output for specific patterns (IPs, keywords, credentials)
    base64 -d Decode base64-encoded data found in packet payloads
    xxd Hex dump for examining raw packet bytes

    Step 2: Examine Available Evidence

    List the evidence and read the brief

    Run these on the analyst workstation. The directory listing shows the available files, and the incident brief explains what management already knows.

    ls -la ~/
cat ~/INCIDENT_BRIEF.txt

    Read the incident brief. Note the PCAP file at /home/analyst/incident.pcap.

    Step 3: Initial Triage with strings

    Triage the PCAP with strings

    Run a broad extraction of readable strings from the PCAP on the analyst workstation. strings pulls printable text out of the binary capture for a fast first look.

    strings /home/analyst/incident.pcap

    Scan the output. You should see HTTP headers, hostnames, and other protocol data embedded in the packets. The result provides a fast overview of what the capture contains without needing a full protocol parser.

    Step 4: Identify the Attacker

    Filter for attacker indicators

    Look for MAC addresses and suspicious network indicators. Piping strings into grep -i narrows the output to host and server references.

    strings /home/analyst/incident.pcap | grep -i 'host\|server\|evil'

    Note any references to external or suspicious hostnames. The MAC address AA:BB:CC:DD:EE:FF appears repeatedly: that address belongs to the attacker's interface.

    Step 5: Find Stolen Credentials

    Search for stolen credentials

    Search for HTTP authentication data. The grep filter surfaces the cleartext login fields captured in the traffic.

    strings /home/analyst/incident.pcap | grep -i 'password\|username\|login'

    You should find an HTTP POST containing form-encoded credentials. The victim submitted their banking login through a hijacked connection. Record the username and password.

    Step 6: Identify DNS Hijacking

    Spot the DNS hijack

    Look for DNS-related anomalies. The grep terms pull the forged banking domain and the attacker-controlled IP out of the capture.

    strings /home/analyst/incident.pcap | grep -i 'banking\|HIJACK\|192.168.99'

    The attacker redirected banking.example.com to 192.168.99.1: an IP under their control. Combined with the ARP spoofing evidence, the data confirms a man-in-the-middle attack chain.

    Step 7: Decode Exfiltrated Data

    Find the exfiltration payload

    Search for the outbound upload that carries the encoded data. The attacker POSTed the stolen records to an external server in a data= form field, so the base64 blob sits behind a data= prefix rather than alone on its own line.

    strings /home/analyst/incident.pcap | grep 'data='

    The matching line is the exfiltration payload: a long base64 string immediately after data=. A whole-line anchored regex would miss it because the data= prefix sits on the same line, so target the data= field directly.

    Extract and decode the payload

    Pull out the data= field, strip the data= prefix, and decode the remaining base64. grep -oE prints only the matched data=... portion, sed removes the prefix, and base64 -d reverses the encoding.

    strings /home/analyst/incident.pcap | grep -oE 'data=[A-Za-z0-9+/=]+' | head -1 | sed 's/^data=//' | base64 -d

    The decoded output reveals the exfiltrated data, including the flag in the form OCR{...}. Record the full flag exactly as it appears.

    Step 8: Record the Flag

    The flag appears in the decoded exfiltration payload.

    Step 9: Exit

    Close the analyst session

    Leave the analyst workstation once you have recorded the flag and findings.

    exit

    The session returns you to your Kali terminal.

    Analysis Questions

    1. The attacker used ARP spoofing before DNS hijacking. Why was that sequence necessary?

    Reveal Answer

    ARP spoofing redirects the victim's traffic through the attacker's machine at Layer 2. Without this, the attacker cannot intercept or modify the victim's DNS queries. The ARP spoof positions the attacker as a man-in-the-middle, which then enables the DNS hijack (returning a forged DNS response pointing banking.example.com to an attacker-controlled IP). The sequence is: ARP spoof to become the gateway, then DNS hijack to redirect specific domains, then serve a fake login page to harvest credentials.

    2. The credentials were transmitted in cleartext HTTP. What would have prevented this?

    Reveal Answer

    HTTPS with proper certificate validation would have prevented credential theft. If the banking site enforced HTTPS and the victim's browser validated the TLS certificate, the attacker's fake site would have triggered a certificate warning (the attacker cannot produce a valid certificate for banking.example.com). HSTS (HTTP Strict Transport Security) preload lists provide additional protection by preventing the browser from ever making an HTTP connection to known HTTPS-only domains.

    3. How could the cafe network have detected or prevented the ARP spoofing attack?

    Reveal Answer

    Prevention: 802.1X port-based authentication, Dynamic ARP Inspection (DAI) on managed switches, static ARP entries for critical infrastructure like the gateway. Detection: ARP monitoring tools (arpwatch, XArp) that alert on MAC-IP binding changes, IDS rules that flag gratuitous ARP replies, and network segmentation that isolates customer WiFi from internal systems. The cafe's flat network with no monitoring made the attack trivial.

    Key Takeaways

    • The attacks you learned to execute are visible in traffic captures: ARP spoofing, DNS hijacking, and credential theft all leave forensic evidence
    • strings is the fastest first-pass forensic tool: extracting readable text from binary captures reveals hostnames, credentials, and payloads without protocol parsing
    • Base64 encoding is not encryption: exfiltrated data encoded in base64 is trivially decoded by any analyst
    • Attack chains follow a logical sequence: ARP spoof enables man-in-the-middle, which enables DNS hijack, which enables credential theft, which enables data exfiltration
    • Defenders analyze what attackers create: every technique from Exercises 1-8 produces artifacts that forensic analysis can uncover
    • Cleartext protocols are forensic goldmines: HTTP, DNS, and ARP operate without encryption: everything is visible in the capture
