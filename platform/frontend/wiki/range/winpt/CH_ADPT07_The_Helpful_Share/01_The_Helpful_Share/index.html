    Exercise 2.3: The Helpful Share

    Before You Begin

    Helpdesk teams write to themselves. They drop notes onto shares to coordinate handoffs, pasted screenshots when a ticket is escalating, runbooks they wrote at 2 AM and never edited again. SOC tooling rarely scans these files. Defenders rarely audit them. Pentesters find a credential in one of them on most engagements.

    Exercise 2.3 gives you a low-privileged credential, points you at a directory full of helpdesk archive notes, and asks you to find the one note that contains a working password. The recovered account stores your flag in extensionAttribute1.

    Tools required: netexec, smbclient, manspider, ldapsearch. All are pre-installed on Kali.

    Scenario

    Marcus Bell: "Engineering put a file called vendor_setup_notes.txt on a read-everyone share three years ago. Marketing put a screenshot of an email on the IT share when their VPN was broken. Helpdesk put a notes file in their archive folder when they were rotating a contractor password over the weekend and never came back to clean it up. Hunt."

    The contractor's account is t.archer_<token>. The flag is in their extensionAttribute1.

    Credentials:

    Username Password
    j.chen Welcome2026#

    Domain: corp.nordport.local

    Your Objectives

    • Enumerate the IT-Tools share on corp-dc01
    • Spider the helpdesk-archive directory and identify your per-token note
    • Recover the credential for t.archer_<token>
    • Authenticate as that account and read its extensionAttribute1
    • Submit the flag

    Hunt Decision Tree

    The flowchart below is the order of operations on every share-credential hunt. Filename match is faster but only works when you already know what you are looking for; content scanning catches the rest.

    flowchart TD
    Start["IT-Tools share<br/>read access confirmed"]
    A{"Do you know<br/>filename pattern?"}
    B["smbclient ls *<token>*<br/>then get the match"]
    C["manspider --content<br/>against credential regex"]
    D["File found"]
    E["Extract username + password<br/>(read the file)"]
    F["Validate via netexec smb"]
    G{"Auth succeeds?"}
    H["Use account, read flag attribute"]
    I["Try other matches /<br/>broaden regex"]

    Start --> A
    A -- "yes" --> B --> D
    A -- "no" --> C --> D
    D --> E --> F --> G
    G -- "yes" --> H
    G -- "no" --> I

    Common Credential Regex Patterns

    The patterns below catch the formats you will find on shared drives in the wild. Combine them with | in the manspider --content argument for a single sweep.

    Regex Catches
    password\s*[:=]\s*\S+ password: Foo# or password=Foo#
    pwd\s*[:=]\s*\S+ pwd: Foo#
    cpassword="[^"]+" GPP cpassword leftover
    connectionString= ODBC / ADO strings (often plaintext)
    BEGIN OPENSSH PRIVATE KEY SSH private keys
    aws_secret_access_key\s*= AWS programmatic keys
    client_secret"?\s*[:=] OAuth client secrets
    Authorization:\s*Basic\s+[A-Za-z0-9+/=]+ Cached HTTP Basic-auth tokens

    Background: Where Helpdesk Credentials Leak

    The pattern is consistent across organizations. Helpdesk staff need a place to coordinate work that is more durable than chat (chats roll off, are not retroactively searchable, and do not survive across teams) and lower-friction than a ticketing system (ticket fields are rigid, comments hide easily). The pragmatic answer is a shared drive: \\corp-dc01\IT-Tools\, \\srv-helpdesk\Notes\, \\dc01\Helpdesk$\. Each note is a small text file with a date, a title, and a few lines of content. Most are harmless: runbooks, contact lists, patch windows. Some contain credentials.

    The credential leak shapes:

    1. Inline plaintext -- "Username: contractor1 / Password: TempVPN2024#"
    2. Email forwarded for context; the original email had a temporary password the user is supposed to change
    3. Embedded in a script -- net use \\srv\share /user:contractor1 TempVPN2024#
    4. Connection string in an INI -- Data Source=...;User Id=svc_app;Password=...
    5. Pasted from a password manager -- "Vault export 2024-08, do not delete" with the export below

    The defender's countermeasure is content scanning the share with the same tools attackers use. manspider against your own shares quarterly, with a regex covering the patterns above, catches most of these leaks before an attacker does.

    Tool Primer

    manspider for content scanning

    manspider <host> -u <user> -p <pass> -d <domain> --content "<regex>" -e <extensions>

    Useful patterns:

    Pattern Catches
    password\s*[:=] Plaintext "password: ..." or "password=..."
    cpassword GPP cpassword leftover
    connectionString= ODBC / ADO connection strings
    BEGIN OPENSSH PRIVATE KEY SSH keys
    client_secret OAuth client secrets
    aws_secret_access_key AWS credentials

    Multiple patterns with |: --content "password\s*=|cpassword|client_secret".

    smbclient targeted listing

    smbclient //corp-dc01/IT-Tools -U "CORP\j.chen%Welcome2026#" \
  -c "cd helpdesk-archive; ls"

    Lists one specific directory without a full mirror download.

    ldapsearch for extensionAttribute reads

    ldapsearch -x -LLL -H ldap://corp-dc01 \
  -D "CORP\t.archer_<token>" -w '<password>' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(sAMAccountName=t.archer_<token>)" extensionAttribute1

    extensionAttribute1 through extensionAttribute15 are free-form attributes Microsoft reserves for HRIS sync, custom apps, and operator notes. They are readable by Authenticated Users by default. They show up nowhere in the GUI, which is exactly why operators use them to hide things.

    Walkthrough

    Step 1: Confirm Token

    Every Kali user in this lab gets a 4-character scope token injected at session start as the environment variable OCR_SCOPE_TOKEN. The seeded helpdesk note, the contractor account, and the flag attribute are all suffixed with that token. Reading it once at the start of a chapter prevents the most common per-token mistake: typing your neighbor's token by accident.

    Kali - Confirm scope token

    echo "$OCR_SCOPE_TOKEN"

    Output is a 4-character alphanumeric string (for example j001 or m4tk). Save it visually; every command in this chapter will substitute it for <token>.

    Step 2: Enumerate Shares on corp-dc01

    Before content-scanning anything you need a list of shares the credential can touch. netexec --shares enumerates every share on the host, attempts an authenticated tree connect against each, and prints the access level it observed.

    Kali - Share inventory

    netexec smb corp-dc01 -u j.chen -p 'Welcome2026#' -d corp.nordport.local --shares
    Flag Effect
    smb Targets the SMB protocol.
    corp-dc01 Hostname of the file server (resolves through the DC).
    -u, -p, -d Username, password, domain.
    --shares After auth, walks every share and prints READ, WRITE, or no access.

    Look for IT-Tools in the listing with READ access. Any share j.chen has only NO ACCESS to is irrelevant; do not waste time on it. The other shares with READ are not part of this exercise but are worth noting for your own report.

    Step 3: Browse the Helpdesk Archive

    The full share has hundreds of files; you only care about one folder. smbclient -c runs a single semicolon-separated command list against the server, which is faster than the interactive shell when you already know where to look.

    Kali - List helpdesk-archive

    smbclient //corp-dc01/IT-Tools -U "CORP\j.chen%Welcome2026#" \
  -c "cd helpdesk-archive; ls"
    Flag Effect
    //corp-dc01/IT-Tools UNC path with forward slashes (Linux convention).
    -U "DOMAIN\user%password" Inline credential. The % separator avoids a prompt.
    -c "cd ...; ls" Run two commands in one connection then exit.

    The listing shows ~25 per-token note files plus ~25 decoys. Your note follows the pattern vpn_helpdesk_handoff_<token>.txt. Other students' notes are visible but not readable (DACL'd to deny Authenticated Users).

    Step 4: Filter to Your Token

    Listing 50 files when only one matters wastes time. SMB's ls accepts glob patterns just like a shell, so a wildcard around your token narrows the result instantly.

    Kali - List only your token's notes

    smbclient //corp-dc01/IT-Tools -U "CORP\j.chen%Welcome2026#" \
  -c "cd helpdesk-archive; ls *${OCR_SCOPE_TOKEN}*"

    Exactly one file matches. Pull it next.

    Kali - Download your note

    mkdir -p ~/work/adpt-2-03 && cd ~/work/adpt-2-03
smbclient //corp-dc01/IT-Tools -U "CORP\j.chen%Welcome2026#" \
  -c "cd helpdesk-archive; get vpn_helpdesk_handoff_${OCR_SCOPE_TOKEN}.txt"
cat vpn_helpdesk_handoff_${OCR_SCOPE_TOKEN}.txt
    Flag Effect
    mkdir -p ... && cd ... Create a per-exercise working directory so artifacts do not pollute your home.
    get <remote_file> Pull the file into the current local directory.
    cat ... Display the contents locally.

    The file shows the username t.archer_<token> and a plaintext password. Real-world equivalents include "vendor turnover notes," "vpn temp creds," "contractor runbooks." All look mundane; all leak secrets.

    Step 5: Validate the Credential

    Before chaining any further commands on the recovered account, confirm the credential actually works. netexec smb against the DC is the cheapest probe: a single SMB Negotiate + SessionSetup and you know whether the password is right.

    Kali - Validate t.archer_

    netexec smb corp-dc01 -u "t.archer_${OCR_SCOPE_TOKEN}" \
  -p '<password from the note>' -d corp.nordport.local

    Look for [+] (auth success) at the end of the line. [-] with STATUS_LOGON_FAILURE means the password in the note is wrong; reread the note (line breaks, trailing characters, copy-paste artifacts).

    Step 6: Read extensionAttribute1

    Once you have a working credential, query LDAP for the contractor user object and request the single attribute that holds the flag. Selecting attributes by name (rather than *) keeps the response small and the action narrow.

    Kali - Read extensionAttribute1 over LDAP

    ldapsearch -x -LLL -H ldap://corp-dc01 \
  -D "CORP\t.archer_${OCR_SCOPE_TOKEN}" -w '<password>' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(sAMAccountName=t.archer_${OCR_SCOPE_TOKEN})" extensionAttribute1
    Flag Effect
    -x Simple bind (no SASL). Required for username+password auth.
    -LLL LDIF output without comments or version line. Cleaner to grep.
    -H ldap://corp-dc01 LDAP URI; ldap:// is plaintext on 389.
    -D "CORP\user" Bind DN (down-level format works for AD).
    -w '<pw>' Password inline. Use -W to be prompted instead.
    -b "<base_dn>" Search base; the domain root for a domain-wide hunt.
    (sAMAccountName=...) Filter selecting only the contractor object.
    extensionAttribute1 Trailing attribute list; only this attribute is returned.

    The flag appears as the value of extensionAttribute1. Submit it to the platform.

    Step 7: Bonus - Find the File via Content Scan

    In a real engagement you would not know the contractor's username up front. The realistic discovery path is to content-scan every readable share for credential-shaped strings and triage the hits. The bonus step below practices that workflow against your own per-token note.

    Kali - Content scan for your token

    manspider corp-dc01 -u j.chen -p 'Welcome2026#' -d corp.nordport.local \
  --content "t.archer_${OCR_SCOPE_TOKEN}" -e txt,csv,docx,ini
    Flag Effect
    <host> Target SMB server.
    --content "<regex>" Server-side fetch then local regex scan; multiple patterns join with |.
    -e txt,csv,docx,ini Restrict to the listed extensions; no point reading binaries.

    Manspider returns the same path Step 4 found. In a real engagement, swap the regex for a generic credential pattern (password\s*[:=]|cpassword|client_secret) and triage the hits.

    Common gotchas

    • Unquoted token expansion: shells will expand *${OCR_SCOPE_TOKEN}* if the variable is empty. Always echo $OCR_SCOPE_TOKEN first.
    • Backslash escaping in -U: bash interprets \ so quote the credential string. "CORP\user%pass" works; CORP\user%pass does not.
    • manspider verbose output: by default it prints every file it considered. Add -q to suppress non-matching entries.
    • DACL'd notes: trying to read another student's note will fail silently with NT_STATUS_ACCESS_DENIED; that is the lab's per-token isolation, not a tool bug.

    Blue Team Perspective

    The first detectable signal is not the read but the use. A contractor account that suddenly authenticates from a workstation IP it has never touched before is the easiest catch in this attack chain.

    Activity Event ID Where it fires
    File read on IT-Tools share 5145 (detailed share access) File server Security log
    Credential write to share 4663 + file integrity monitor File server Security log
    New auth from contractor account 4624 logon type 3 from new IP DC Security log
    LDAP read of extensionAttribute1 4662 with attribute access audit DC Security log

    What a tuned SOC catches

    Most environments do not catch the file read; baseline noise on IT-Tools is too high. They do catch the unusual 4624 logon type 3 for t.archer_* from a non-helpdesk subnet, especially when paired with no recent 4768 (TGT issuance) for that user. Identity-driven detection beats file-content monitoring on this attack class.

    Hardening Note

    You cannot stop helpdesk teams from sharing notes; you can stop them from sharing credentials in those notes. The list below is the realistic checklist.

    Helpful-share hardening

    • Rotate every credential found by an internal manspider sweep; do not just delete the file.
    • Replace shared text-file workflows with a wiki that has search and revision history.
    • Require credentials to be stored in a password manager and only referenced by entry name in shared notes.
    • Run manspider --content "password\s*[:=]|cpassword|client_secret" quarterly against every read-everyone share; route hits to a triage queue.
    • DACL extensionAttribute1 through extensionAttribute15 to deny Authenticated Users read where they are not used.
    • Build a SIEM detection: contractor-class accounts logging in from a host outside the helpdesk subnet.

    Analysis Questions

    1. Helpdesk staff frequently use SMB shares for notes because the alternatives are worse. From a defender's perspective, what is the right trade-off between auditability and friction?

    Reveal Answer

    The realistic alternatives are: a properly indexed wiki (high auditability, moderate friction), a ticketing system (high auditability, high friction for short notes), or chat (low auditability, low friction, but searchable history is per-tool). A read/write SMB share is the lowest friction tool helpdesk staff can use, which is precisely why credentials end up there. The right defender response is not to ban the share but to combine: (a) make the wiki frictionless enough to compete with the share, (b) auto-scan all writeable shares weekly with manspider against a credential regex, (c) require credentials to be stored in a password manager and only referenced by ID in any document. Banning the share without giving staff a competitive alternative produces the same notes in WhatsApp and personal Google Drives, which is worse.

    2. extensionAttribute1 through extensionAttribute15 are free-form fields. Why were they introduced, and what defensive controls limit their abuse as covert storage?

    Reveal Answer

    Microsoft introduced extensionAttribute1 through 15 (and mailNickname, proxyAddresses) for Exchange to extend user objects with mailbox-related metadata without each Exchange version needing schema modifications. They became general-purpose because no schema authority restricted them; HRIS sync products, custom HR apps, asset trackers, and ad-hoc admin scripts all use them. Defensive controls: (a) DACL the attributes to deny Authenticated Users read for the attributes you do not want broadly visible; AD ACLs are per-attribute; (b) flag attribute writes in audit policy (event 4738 with the right attributes) and treat any write outside business hours as suspicious; (c) periodic audits looking for non-empty values on accounts that should not have them. The attributes were not designed for sensitive data and any operator using them as covert storage is making the defender's job easier rather than harder.

    3. The credential leak in this exercise is plaintext, but the same finding pattern with hashes (NTDS dumps, LSA secret dumps in scripts) is common. What is the practical difference for an attacker between finding a plaintext password and finding a hash?

    Reveal Answer

    A plaintext password is immediately reusable everywhere: SMB, LDAP, RDP, web SSO, third-party SaaS that federates against AD, password reuse on personal services. A hash is only directly reusable in protocols that accept the hash form: pass-the-hash works against SMB, WMI, WinRM, MSSQL with NTLM. Pass-the-ticket works after exchanging the hash for a Kerberos ticket. RDP requires Restricted Admin mode (and a registry tweak on the target). Web SSO usually requires the plaintext to compute the auth flow. So a hash is more constrained but still extremely valuable; an attacker often cracks the hash offline in parallel and uses pass-the-hash for the lateral movement, treating the cracked plaintext as a bonus.

    Key Takeaways

    • Helpdesk archive shares are the single highest-yield credential leak surface in a typical AD environment.
    • manspider --content "<regex>" content-scans shares at scale; defenders should run the same scan periodically.
    • extensionAttribute1 through extensionAttribute15 are readable by any authenticated user by default.
    • A plaintext credential beats a hash in flexibility but the credential leak pattern is the same in either form.
    • Per-token scoping in this exercise teaches you the workflow on your file; in a real engagement no scope token bounds the search.

    Cheat Sheet Recap

    The four operations below are the share-credential hunt loop. Use the credential-regex patterns from the table at the top of this chapter.

    Goal Command
    Inventory shares netexec smb <host> -u <user> -p '<pw>' -d <domain> --shares
    Filename match smbclient //<host>/<share> -U "..." -c "cd <dir>; ls *<token>*"
    Content scan at scale manspider <host> -u <user> -p '<pw>' -d <domain> --content "password\\s*[:=]\|cpassword" -e txt,ini,xml,csv,docx,xlsx,config
    Read extensionAttribute1 ldapsearch -x -LLL -H ldap://<dc> -D "<DOMAIN>\<user>" -w '<pw>' -b "<DN>" "(sAMAccountName=<target>)" extensionAttribute1

    Spaced Repetition

    Card 1: manspider Credential Hunt

    Q: One command to scan every share on corp-dc01.corp.local for files containing the substring password= or cpassword, restricted to text-like extensions, as j.smith / Pass#.

    Answer 
    manspider corp-dc01.corp.local -u j.smith -p 'Pass#' -d corp.local \
  --content "password=|cpassword" -e txt,ini,xml,config,csv

    Add patterns with |. Add file extensions with -e. The output prints every hit with the file path and the matching line.

    Card 2: extensionAttribute Read via LDAP

    Q: Write the ldapsearch command that reads extensionAttribute1 from the user t.archer on corp.local at 10.10.10.10, authenticating as the same user with password Pass#.

    Answer 
    ldapsearch -x -LLL -H ldap://10.10.10.10 \
  -D "CORP\t.archer" -w 'Pass#' \
  -b "DC=corp,DC=local" \
  "(sAMAccountName=t.archer)" extensionAttribute1

    Any authenticated user can usually read these attributes on any user (default ACL grants Authenticated Users read).

    Card 3: smbclient One-Shot Read

    Q: Write the smbclient command to print the contents of \\corp-dc01\IT-Tools\helpdesk-archive\vpn_handoff.txt to stdout in one invocation, using j.smith / Pass#.

    Answer 
    smbclient //corp-dc01/IT-Tools -U "CORP\j.smith%Pass#" \
  -c "cd helpdesk-archive; get vpn_handoff.txt -" \
  | cat

    The - filename to get means "stdout". Pipe to cat (or omit it; smbclient writes directly).

    Card 4: Why Helpdesk Shares Leak

    Q: Name three reasons helpdesk staff write credentials to shares despite ticketing systems and password managers being available.

    Answer
    1. Speed: a one-line text file is faster than logging into the password vault and naming a new entry. 2. Coordination: a shared file is visible to the whole team without permissions juggling. 3. Continuity: notes survive across shifts and outlast chat history. The defender's job is to make the password vault and wiki fast enough that helpdesk staff actually prefer them.
