    Exercise ICSPT-2.4: The Nervous Operator

    Engagement Status

    Client Masa Foods, Inc. (fictional)
    Role OT Security Engineer, Plant 1
    Phase Discovery Enumeration (independent) Exploitation Reporting

    What you know so far: You learned the safe Modbus function codes in Exercise 2.3 and practiced a clean read-only assessment on the mixer and the tortilla PLC. Exercise 2.4 raises the pressure: operations is watching, the PLC is instrumented to detect any write on the wire, and a single FC 5, 6, 15, 16, 22, or 23 anywhere in your session replaces the flag with a dirty marker.

    Environment Checklist

    Every ICSPT exercise assumes you read the Before-You-Begin section in Exercise 1.1 (Touring Masa Foods) first. If you have not, open that page now: it explains the two attacker-host options and walks you through the one-time /etc/hosts setup that lets you call every Plant 1 target by its friendly name.

    Exercise 2.4 reaches plc1.masa.local, historian.masa.local, and hmi.masa.local. All three names are already in your /etc/hosts from the Exercise 1.1 block. Confirm resolution and reachability:

    Kali

    getent hosts plc1.masa.local historian.masa.local hmi.masa.local
ping -c 2 plc1.masa.local
nc -zv plc1.masa.local 502
curl -s -o /dev/null -w 'HTTP %{http_code}\n' http://historian.masa.local:3000/

    Expected: three name-to-IP lines, two successful pings, succeeded! on TCP/502, and HTTP 200 from the historian. If any step fails, fix connectivity before continuing.

    Start this exercise from a brand new shell

    If you still have shell history from Exercise 3.3 (Overcooked Tortilla) or Exercise 3.4 (Silent Conveyor) in the current terminal, do NOT reuse any write command from those sessions. Those exercises send write function codes (the mbpoll -t 4 ... <value> write form, or a write client), and running any of them against the current plc1 container will trip the clean-mode tracker and replace the Exercise 2.4 token with a dirty marker. Every command in this exercise is a read: mbpoll -t 4 with no trailing value writes nothing. Open a fresh terminal tab and start with a blank history. If in doubt, run history -c after you confirm reachability.

    Scenario

    Operations has agreed to a one-hour read-only assessment window on the Plant 1 tortilla line. The shift supervisor will watch you on the operator HMI for the entire window. Reyna Alvarado was clear: if any tag jitters unexpectedly, the supervisor pulls the plug and the assessment is over.

    Why this matters

    The first assessment with a new OT client is always on probation, and the probation is enforced by the shift supervisor, not by Reyna. Reyna wants you there; the supervisor does not care about cybersecurity and has every incentive to pull the plug at the first sign of trouble because if production stops on his shift, he is the one who gets the call from plant leadership. A clean read-only assessment is how you keep the supervisor quiet, and keeping the supervisor quiet is how you get invited back.

    Exercise 2.4 trains three things that you cannot learn by reading:

    • The muscle memory of pure-read operation. Your hands have to reach for the read form (mbpoll -t 4 with no trailing value) by reflex, even when you are tired, under time pressure, or half-certain a write would be faster. Muscle memory is the only defense against a three-AM mistake.
    • The discipline of cross-reference. Reading a register in isolation is a data point. Reading a register and confirming it against the live HMI tile is an observation. Observations are what go in a report. The exercise forces you to cross-reference because that is the professional habit you need to build.
    • The self-audit of shell history. A clean engagement ends with a shell history file that contains no write calls. Making that the final check on the exercise is how you learn to self-audit before the supervisor audits you.

    Concretely, the MC-7200 has an in-PLC tripwire specifically designed to make this exercise unforgiving. There is no safety net. If your shell history touches a write function code even once, the PLC records the event and the flag reads as DIRTY_WRITES_DETECTED for the rest of the container lifetime. The only recovery is stopping the exercise and restarting it from the OCR platform, which in a real plant maps to "stopping the assessment window and rescheduling with operations," which is the career-damaging outcome this exercise is teaching you to avoid.

    The MC-7200 firmware has a simple internal check. The PLC populates holding registers 40800 through 40815 with an assessment token. While the PLC has received no dangerous write function codes from the wire, the token reads as the clean flag. On the first FC 5, FC 6, FC 15, FC 16, FC 22, or FC 23 the PLC receives from any client on the network, the token flips to DIRTY_WRITES_DETECTED and stays that way until the PLC is restarted.

    The PLC does not know which client issued the write. If you write, the whole assessment is ruined. If any other client on the lab network writes, the assessment is also ruined, but on your per-user lab network there are no other clients. The only way to trip the flag is your own commands.

    Your job is to produce a clean read-only assessment of the Plant 1 tortilla PLC, cross-reference two register values against the HMI dashboard, read the assessment flag at register 40800, and submit it.

    Background: How the Clean-Mode Tracker Works

    The MC-7200 firmware wraps its Modbus slave context in a subclass that overrides setValues. Every time the pymodbus server dispatches a wire-level write to the slave context (function codes 5, 6, 15, 16, 22, or 23), the override sets a module-level CLEAN_MODE["value"] flag to False. The simulation loop reads that flag on every tick and chooses which string to pack into the assessment flag block.

    While CLEAN_MODE is True, the block holds the clean assessment token as ASCII, two bytes per register, big-endian (high byte first). After any dangerous write, the block holds DIRTY_WRITES_DETECTED followed by null padding. The flag is always readable (it is still a holding register block and FC 3 still works), but its contents depend entirely on whether any client on the network has ever issued a dangerous function code since the container booted. You read the block and decode it yourself; the workbook does not print the clean token.

    Internal process-variable updates from the simulator itself (oven temperature drift, mixer speed feedback, batch counter increment) go directly to the datablock and bypass the slave context, so they do not trip the tracker. Only network writes count.

    Why the tracker cannot distinguish clients

    Modbus/TCP is stateless at the protocol layer. The PLC sees TCP connections from Kali clients, HMIs, historians, and engineering workstations with no authentication and no client identifier. All of them look the same to the slave context. The tracker's only defense is "any write from anyone marks the PLC dirty," which is exactly the assumption that makes read-only discipline valuable in production.

    Suggested Methodology

    Exercise 2.4 is independent, so the stages below are a reminder of the shape of a clean assessment, not a click-by-click script. You build every read with mbpoll, never a write client, and you confirm with Wireshark that only Function Code 3 ever left your host. The clean-mode tracker punishes any FC 5, 6, 15, 16, 22, or 23, so the tool choice is the discipline: mbpoll -t 4 sends Function Code 3 and nothing else.

    The documented register, the wire address, and what mbpoll wants. Holding registers are documented in the 4xxxx range. On the wire the address is zero-based and drops the leading 4, so documented register 40800 is wire address 799. The mbpoll tool hides that arithmetic for you: its -r option takes the register number without the leading 4, so -r 800 reads documented register 40800. Reading the sixteen-register assessment block 40800 through 40815 is therefore -r 800 -c 16.

    Documented register Holds mbpoll -r
    40800 through 40815 assessment token (2 ASCII chars per register, big-endian) 800, count 16

    Stage 1: Confirm You Are Clean

    Read the assessment block first, before touching anything else, with a single read-only mbpoll command. Function Code 3 (-t 4) is the only code that ever touches the wire, so this read cannot trip the tracker.

    Kali

    mbpoll -1 -a 1 -t 4 -r 800 -c 16 plc1.masa.local
    -1 polls once and exits, -a 1 is the Modbus unit id, -t 4 selects holding registers (Function Code 3), -r 800 starts at documented register 40800, and -c 16 reads the sixteen-register assessment block. Port 502 is the default.

    mbpoll labels each value with its register number, so you read the layout straight off the output: sixteen decimal integers, one per register from 40800 through 40815. They are not human-readable yet because each register is two packed ASCII bytes; you decode them in Stage 5. Decode the block now to check the marker. If it spells DIRTY_WRITES_DETECTED, the container was pre-dirty (stale session, or a writeable exercise ran before you), so stop the exercise from the OCR platform and relaunch before continuing. If it spells an OCR{...} string, you are clean and may continue.

    Stage 2: Confirm Only Function Code 3 Left Your Host

    mbpoll is the fast path; Wireshark is how you prove to yourself (and to the supervisor) that nothing you ran was a write. Capture TCP port 502 while you run the Stage 1 read, then confirm every packet you originated decodes to Function Code 3.

    Kali (shell one)

    sudo tshark -i any -f 'tcp port 502' -w /tmp/clean_assessment.pcap &
echo $! > /tmp/tshark.pid

    Kali (shell two)

    mbpoll -1 -a 1 -t 4 -r 800 -c 16 plc1.masa.local

    Kali (shell one, after the read completes)

    sudo pkill -F /tmp/tshark.pid 2>/dev/null || sudo pkill tshark
tshark -r /tmp/clean_assessment.pcap -Y 'modbus' \
  -T fields -e frame.number -e ip.src -e modbus.func_code
    Every row whose ip.src is your host must read func code 3. Any 5, 6, 15, 16, 22, or 23 from your address means a write left your host and the assessment is compromised.

    Now open the capture in the Wireshark GUI. The terminal fields prove the data is there; the GUI is where you learn to recognize a read on sight and audit a session at a glance. Walk these steps exactly:

    1. Open the capture. From a terminal run wireshark /tmp/clean_assessment.pcap &, or inside Wireshark choose File > Open and pick the file. To capture live instead, double-click your network interface on the Wireshark welcome screen to start, run the mbpoll read, then click the red square Stop button in the toolbar.
    2. Filter to Modbus. In the display filter bar (the wide bar directly under the toolbar), type modbus and press Enter. The packet list narrows to just your query and the PLC's response.
    3. Select the query. In the Packet List (top pane), click the row whose Info column reads Query: ... Func: 3: Read Holding Registers. A read-only assessment should show only Func: 3 queries from your host and nothing else.
    4. Expand the Modbus tree. In the Packet Details (middle pane), click the arrow to the left of Modbus/TCP to see the MBAP header, then the arrow next to the Modbus node below it to reveal the Function Code, Reference Number (799, the zero-based wire form of documented register 40800), and Word Count (16).
    5. Tie a field to the bytes. Click the Function Code field name and watch the matching byte highlight in the Packet Bytes pane at the bottom. The single byte 0x03 is the whole reason this read is safe, and seeing it on the wire is how you confirm it.

    Stage 3: Read the Process Variables

    Read a small block of process-variable registers that you can match against the HMI dashboard. Documented register 40001 is -r 1, so the block 40001 through 40055 is -r 1 -c 55.

    Kali

    mbpoll -1 -a 1 -t 4 -r 1 -c 55 plc1.masa.local
    Same options as Stage 1, except -r 1 starts at documented register 40001 and -c 55 reads the process-variable block. The oven PV is at 40001 (in tenths of a degree), the oven setpoint at 40010, mixer PV/SP at 40020/40021, conveyor at 40030, batch count at 40040, and line state at 40050.

    Record the values in your engagement log.

    Stage 4: Cross-Reference the HMI

    Open http://hmi.masa.local/ in a browser (HMI IP from the Exercise Network panel, port 80) and read the operator cockpit: the live process values, line state, interlocks, and alarm banner give you the clean baseline before you touch anything.

    Capture the same baseline state as JSON from the command line so you have a machine-readable record next to the visual one. The api/state endpoint returns the exact values the cockpit renders, which makes it an explicit cross-check against what you just read in the browser.

    Kali

    curl -s http://hmi.masa.local/api/state | jq .

    Compare the HMI state values against the register reads from Stage 3. Oven setpoint and conveyor speed are the easiest to match exactly; the process variables carry small amounts of drift that show as floating-point values on the HMI and scaled integers in the registers.

    Stage 5: Decode the Assessment Token by Hand and Record It

    The assessment block is sixteen registers of two ASCII bytes each, high byte first, which is the Modbus big-endian convention. Convert each register's decimal value to hex, then read the two bytes as characters.

    Walk one register so the method is clear. A register reading 19777 is 0x4D41 in hex. The high byte is 0x4D, which is the ASCII character M. The low byte is 0x41, which is A. So that register carries MA. Apply the same split to every register in your Stage 1 output, in register order, and concatenate the characters. The last few registers of a clean block are null padding (0x0000); drop the trailing nulls. The remaining characters spell the assessment token, OCR{...} wrapper included, and that is your flag.

    The worked 0x4D41 -> MA example is deliberately not part of the real token, so you still have to run the Stage 1 read and do the decode yourself. Re-run the Stage 1 mbpoll read one last time before you submit, decode it, and confirm it still spells the clean OCR{...} token rather than DIRTY_WRITES_DETECTED. If the two decodes diverge, something on the network issued a write between your reads and you have lost the exercise. Submit the decoded string in the OCR platform.

    Clean assessment log:

    Step Read target mbpoll -r -c Function code HMI cross-reference
    1 40800-40815 -r 800 -c 16 3 n/a
    2 40001-40055 -r 1 -c 55 3 oven_sp, conveyor
    3 40800-40815 (confirm) -r 800 -c 16 3 n/a

    Output Interpretation

    • The first and last reads of the assessment block should decode to the same clean string. If they diverge, something on the network issued a write between your two reads and you have lost the exercise
    • Cross-referencing oven setpoint against the HMI proves the PLC and the HMI agree on state, which is the operational definition of a healthy Plant 1 session
    • A clean block decodes to an OCR{...} token the firmware packs as big-endian ASCII; the dirty block decodes to DIRTY_WRITES_DETECTED padded with nulls. The two are easy to tell apart once you run the hand decode, which is exactly why the decode is the by-hand skill and not a printed answer
    • Your shell history after this exercise should contain only mbpoll -t 4 reads against plc1, the tshark/wireshark capture commands, and a single curl to the HMI. No mbpoll -t 4 ... <value> write form, no write client of any kind. Audit it as a final discipline check

    Analysis Questions

    1. What is the operational value of instrumenting a PLC to track and report dirty-write state?

    Reveal answer

    A real plant that deploys this pattern gets a cheap, protocol-level tripwire on any unauthorized write. It does not replace a Modbus-aware IDS (the IDS sees the actual source IP, the function code, and the address), but it is a last-line signal that an operator or a supervisor can verify on the HMI without a SIEM. The drawback is that the tracker cannot distinguish authorized writes from unauthorized ones, so it is only useful during explicit read-only assessment windows.

    2. Why does the simulator flip the tracker on FC 22 (Mask Write Register) and FC 23 (Read/Write Multiple Registers) even though FC 23 performs a read?

    Reveal answer

    FC 23 is a combined read-and-write transaction. The write half mutates PLC state just as surely as FC 6 or FC 16, so from a dirty-tracker perspective it is indistinguishable from a pure write. FC 22 applies an AND/OR mask to a holding register, which is also a state mutation. A tracker that ignored FC 22 or FC 23 would miss real writes dressed up in less common function codes.

    3. Could you legitimately argue that reading the assessment flag itself counts as a write, since your TCP connection causes state change inside the PLC?

    Reveal answer

    No. A TCP connection and an FC 3 request change internal PLC counters (connection count, last-seen timestamp, exception counter), but those are not state that Modbus clients can observe via function codes. The clean-mode tracker is specifically about whether any client issued a function code that the Modbus protocol defines as a write. Everything else (connection setup, packet headers, ACKs) is transport-layer and not in scope.

    4. How would the assessment change if the plant had a Modbus-aware IDS instead of an in-PLC tripwire?

    Reveal answer

    A Modbus-aware IDS would catch writes in real time and alert on source IP, function code, and address. That is strictly better than the in-PLC tripwire because it identifies the offender, records the payload, and fires even when the PLC does not report dirty state. The in-PLC tripwire is a complementary control: it works even when the IDS is offline or misconfigured, and it can be read directly by operators without a SIEM. Defense in depth means both exist.

    Defensive Recommendations to Masa

    Finding Risk Mitigation
    No real-time alert when any client writes to plc1 during a declared read-only window Medium Pair the in-PLC dirty tracker with a Modbus-aware IDS rule (from Exercise 3.4) that fires on any write from a non-HMI source
    Read-only assessment windows are not coordinated on a shared calendar Medium Add read-only windows to the plant maintenance calendar and require ticketed sign-off before the window opens
    Dirty state on plc1 is sticky until restart Low Add an operator-only "clear dirty" button on the HMI that pages the shift supervisor before clearing
    No automated audit of shell history after a read-only assessment Low Require engineers to submit their shell history file as part of the assessment writeup

    Key Takeaways

    • Read-only discipline is a muscle, not a rule. If your shell history contains any write function code against plc1 during a declared read-only window, you failed the exercise, full stop. mbpoll -t 4 with no trailing value is the read form, and Wireshark filtered to modbus is how you prove only Function Code 3 left your host
    • The clean-mode tracker is a simple pattern that any plant can deploy: subclass the Modbus slave context, flip a flag on dangerous function codes, and surface the flag through a reserved register block
    • Internal simulator state updates must bypass the slave context (direct datablock writes) so they do not trip the tracker. Real plants would implement the same distinction between "PLC updates its own state" and "a client writes over the wire"
    • Cross-referencing PLC reads against the HMI is the fastest way to confirm you and the plant agree on reality. Always do it
    • Dirty state is sticky. If you lose the clean run, relaunch the exercise from the OCR platform and start over
