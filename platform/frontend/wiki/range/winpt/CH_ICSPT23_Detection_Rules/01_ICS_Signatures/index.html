    Exercise ICSPT-6.1: Writing ICS Detection Rules

    Engagement Status

    Client Masa Foods, Inc. (fictional)
    Role OT Security Engineer, All Plants
    Phase Discovery Exploitation Defense (detection rules) Capstone

    What you know so far: Levels 1 through 5 gave you protocol fluency across Modbus, S7comm, CIP, and DNP3. You have attacked all three Masa Foods plants and seen exactly what malicious ICS traffic looks like on the wire. Exercise 6.1 flips your perspective from attacker to defender. You will write Snort rules that detect the same attack patterns you used, then validate them against real PCAPs.

    Environment Checklist

    Exercise 6.1 introduces one new host: the PCAP evidence server at pcap-evidence.masa.local (HTTP, port 8080), which was not in your /etc/hosts from earlier levels. Add it now using the pcap-evidence IP shown in the Exercise Network panel on the OCR track page:

    Kali

curl -s http://pcap-evidence.masa.local:8080/ | head -20

    The server should return an index listing four PCAP files.

    Scenario

    After five levels of penetration testing across all three Masa Foods plants, Reyna Alvarado has a clear picture of what attacks look like on each protocol. The SOC team has asked for detection signatures they can deploy on the plant-floor Snort sensors. Four PCAPs are available on the evidence server: one benign baseline and one attack capture per plant. Your job is to write three Snort rules (one per plant attack pattern), validate them against the attack PCAPs to confirm true positives, and validate them against the benign baseline to confirm zero false positives.

    The four PCAPs available at pcap-evidence.masa.local:8080:

    File Contents
    benign_baseline.pcap Normal HMI-to-PLC traffic across all three plants, no attacks
    plant1_modbus_attack.pcap Modbus Function Code 6 (Write Single Register) from a non-HMI source (10.x.x.99)
    plant2_s7_attack.pcap S7comm Write PDU on port 102 from a non-HMI source
    plant3_cip_attack.pcap CIP Write Tag service (0x4D) on port 44818 from a non-HMI source

    Why this matters

    Detection engineering is where offensive skills become defensive value. Every attack you executed in Levels 1 through 5 left a network signature. A Modbus FC 6 from an unexpected source IP, an S7 write from outside the HMI subnet, a CIP Write Tag from an unauthorized host: each of these is a pattern a Snort rule can match. Writing those rules is the single most impactful defensive action Reyna can take before the next budget cycle, because it turns the existing Snort sensors (already deployed, already licensed) into ICS-aware monitors at zero additional cost.

    The professional skill Exercise 6.1 builds is translating attack knowledge into detection logic. Penetration testers who can write the detection rules for their own findings are worth more to the client than testers who only write findings.

    Background: Snort Rule Syntax for ICS Protocols

    Snort rules follow a consistent structure. Every rule has a header (action, protocol, source, destination) and an options block (content matches, metadata, SID).

    action protocol src_ip src_port -> dst_ip dst_port (options)

    A concrete example for generic TCP traffic:

    alert tcp any any -> any 502 (msg:"Modbus write from any source"; sid:999999; rev:1;)

    Key options for ICS detection

    Option Purpose Example
    msg Human-readable alert description msg:"Modbus FC6 from non-HMI";
    content Byte pattern match in payload content:"\|00 06\|";
    offset Start matching at byte N offset:7;
    depth Match within N bytes from offset depth:1;
    sid Unique signature ID sid:1000001;
    rev Rule revision number rev:1;

    Modbus over TCP frame structure

    Modbus TCP wraps the function code at byte offset 7 of the TCP payload (after the 7-byte MBAP header). Function Code 6 (Write Single Register) is the byte \x06 at offset 7. The legitimate HMI address ends in .5; any write from another source (such as .99) is suspicious.

    S7comm frame structure

    S7comm runs inside TPKT/COTP on TCP port 102. A Write PDU contains the S7 function byte \x05 (Write Var) in the S7 header. The exact offset varies by COTP negotiation, but the content match on \x05 combined with port 102 and a non-HMI source IP is sufficient for a first-pass rule.

    CIP frame structure

    CIP runs on TCP port 44818. The Write Tag service uses service code \x4D. Matching that byte in the CIP payload, combined with port 44818 and a non-HMI source IP, produces a targeted detection rule.

    Walkthrough

    Stage 1: Download All PCAPs

    The evidence server hosts four files. Download all of them into a working directory so you can inspect them locally.

    Kali

    mkdir -p ~/icspt-detection && cd ~/icspt-detection
curl -O http://pcap-evidence.masa.local:8080/benign_baseline.pcap
curl -O http://pcap-evidence.masa.local:8080/plant1_modbus_attack.pcap
curl -O http://pcap-evidence.masa.local:8080/plant2_s7_attack.pcap
curl -O http://pcap-evidence.masa.local:8080/plant3_cip_attack.pcap
ls -lh *.pcap
    Expected output 
    -rw-r--r-- 1 kali kali  ...  benign_baseline.pcap
-rw-r--r-- 1 kali kali  ...  plant1_modbus_attack.pcap
-rw-r--r-- 1 kali kali  ...  plant2_s7_attack.pcap
-rw-r--r-- 1 kali kali  ...  plant3_cip_attack.pcap

    All four files should be present and non-empty.

    Stage 2: Analyze the Plant 1 Attack PCAP (Modbus)

    Before writing any rule, examine the attack traffic to confirm the detection-worthy pattern. The Plant 1 attack uses Modbus Function Code 6 (Write Single Register) from a source IP ending in .99 rather than the legitimate HMI at .5.

    Kali

    cd ~/icspt-detection
tcpdump -r plant1_modbus_attack.pcap -nn 'tcp port 502' | head -20

    Look for packets from a .99 source address destined for port 502. Each Modbus TCP frame carries the function code at byte 7 of the payload. You can use tshark to extract the function code field directly.

    Kali

    tshark -r plant1_modbus_attack.pcap -Y "modbus.func_code == 6" -T fields -e ip.src -e ip.dst -e modbus.func_code
    Expected output 
    10.x.x.99    10.x.x.10    6

    The source address .99 is not the authorized HMI (.5). Function code 6 means Write Single Register. Both facts together form the detection signature.

    Stage 3: Analyze the Plant 2 Attack PCAP (S7comm)

    The Plant 2 attack sends an S7comm Write PDU on port 102 from a non-HMI source. Examine the capture to confirm.

    Kali

    tshark -r plant2_s7_attack.pcap -Y "s7comm" -T fields -e ip.src -e ip.dst -e s7comm.param.func
    Expected output 
    10.x.x.99    10.x.x.10    0x05

    The S7 function 0x05 is Write Var. Any S7 write from a non-HMI source on port 102 is the detection pattern.

    Stage 4: Analyze the Plant 3 Attack PCAP (CIP)

    The Plant 3 attack sends a CIP Write Tag (service code 0x4D) on port 44818 from a non-HMI source.

    Kali

    tshark -r plant3_cip_attack.pcap -Y "cip" -T fields -e ip.src -e ip.dst -e cip.service
    Expected output 
    10.x.x.99    10.x.x.10    0x4d

    Service code 0x4D is CIP Write Tag. Combined with port 44818 and a non-HMI source, the pattern is clear.

    Stage 5: Write the Snort Rules

    Now that you have confirmed all three attack patterns, write a rules file with three signatures. Each rule matches the protocol, the target port, and a content byte that identifies the write operation. The source IP is set to any rather than hardcoding .99 because the next attacker will use a different address. The key detection logic is "write operation from anything other than the HMI."

    Create the rules file with the following three rules.

    Kali

    cat > ~/icspt-detection/masa_ics.rules << 'EOF'
# Plant 1: Modbus FC 6 (Write Single Register) from any source to port 502
# Byte \x06 at offset 7 in TCP payload (after 7-byte MBAP header)
alert tcp any any -> any 502 (msg:"MASA Modbus FC6 Write Single Register from non-HMI"; content:"|06|"; offset:7; depth:1; sid:1000001; rev:1;)

# Plant 2: S7comm Write Var (function 0x05) on port 102 from any source
alert tcp any any -> any 102 (msg:"MASA S7comm Write Var from non-HMI"; content:"|05|"; sid:1000002; rev:1;)

# Plant 3: CIP Write Tag (service 0x4D) on port 44818 from any source
alert tcp any any -> any 44818 (msg:"MASA CIP Write Tag from non-HMI"; content:"|4d|"; sid:1000003; rev:1;)
EOF
cat ~/icspt-detection/masa_ics.rules

    Each rule targets the destination port for its protocol (502, 102, 44818) and matches the single byte that identifies the write operation. The msg field describes what the rule detects in plain language.

    Stage 6: Validate Against Attack PCAPs (True Positives)

    Run Snort in packet-logging mode against each attack PCAP to confirm the corresponding rule fires. Each command below should produce at least one alert.

    Kali

    cd ~/icspt-detection
snort -r plant1_modbus_attack.pcap -c /dev/null -R masa_ics.rules -A console -q 2>&1 | grep "1000001"
    Expected output 
    ... [1:1000001:1] MASA Modbus FC6 Write Single Register from non-HMI ...

    Repeat for Plant 2 and Plant 3 to verify SIDs 1000002 and 1000003 fire on their respective PCAPs.

    Kali

    snort -r plant2_s7_attack.pcap -c /dev/null -R masa_ics.rules -A console -q 2>&1 | grep "1000002"
snort -r plant3_cip_attack.pcap -c /dev/null -R masa_ics.rules -A console -q 2>&1 | grep "1000003"

    Both commands should return alert lines containing their respective SIDs.

    Stage 7: Validate Against Benign Baseline (False Positives)

    Run all three rules against the benign baseline PCAP. No alerts should fire because the benign capture contains only legitimate HMI traffic with no write operations from unauthorized sources.

    Kali

    snort -r benign_baseline.pcap -c /dev/null -R masa_ics.rules -A console -q 2>&1 | grep -c "Priority"
    Expected output 
    0

    A count of zero confirms no false positives. If you see alerts, review the benign PCAP to determine whether legitimate traffic is matching your content patterns and tighten the rule (add offset and depth constraints, or narrow the source IP range).

    All three SIDs validated. The flag encodes the three SIDs in order.

    Output Interpretation

    • An alert line from Snort includes the SID, the message, the source IP, and the destination IP. Confirm the SID matches the rule you expect and the source IP is the attacker (.99), not the HMI (.5)
    • A false positive on the benign baseline means your content match is too broad. Adding offset and depth constraints narrows the match to the exact byte position of the function code rather than matching anywhere in the payload
    • If Snort exits with a parse error, check the rules file for missing semicolons inside the options block. Every option must end with a semicolon, and the options block must be enclosed in parentheses
    • If Snort produces zero alerts on an attack PCAP, verify the content byte is correct by re-examining the PCAP with tshark and checking the exact hex value at the expected offset

    Analysis Questions

    1. The three rules use any as the source IP instead of hardcoding the attacker address 10.x.x.99. Why is that the better detection strategy?

    Reveal answer

    Hardcoding the attacker's IP creates a signature that only catches one specific attacker. The next attacker will use a different source address. The detection-worthy event is "a write operation from any host that is not the authorized HMI," not "a write operation from 10.x.x.99 specifically." Using any as the source catches all unauthorized writes regardless of the attacker's IP. In a production deployment, you would further refine the rule with a ! negation on the HMI IP (e.g., !10.x.x.5) to allow legitimate HMI writes through while alerting on everything else.

    2. The Plant 2 rule (SID 1000002) matches the byte \x05 without an offset constraint. What is the risk of that approach?

    Reveal answer

    Without offset and depth, Snort will match the byte \x05 anywhere in the TCP payload, not just in the S7 function code field. A benign packet that happens to contain \x05 in its data payload (a setpoint value, a string character, a length field) could trigger a false positive. A production-quality rule would constrain the match to the exact byte position of the S7 function field within the TPKT/COTP/S7 header stack. The exercise uses the simpler form to demonstrate the concept, but a SOC deployment must add positional constraints.

    3. Snort is a signature-based IDS. What category of ICS attacks would these three rules completely miss?

    Reveal answer

    Signature-based rules match known byte patterns. Attacks that use legitimate function codes with legitimate-looking values from legitimate-looking sources will not trigger any of these rules. For example, an attacker who compromises the actual HMI and sends writes from the HMI's IP address using the correct function code will bypass all three rules. Process-anomaly detection (monitoring for out-of-range setpoint values rather than unauthorized sources) requires a different detection approach, typically a behavioral or model-based IDS that understands normal operating ranges.

    4. Reyna asks you to reduce false positives on the Modbus rule without reducing true positives. What single change would you make?

    Reveal answer

    Replace any any on the source side with !10.x.x.5 any (negating the legitimate HMI address). Legitimate Modbus writes from the HMI are expected and should not alert. Writes from any other source are suspicious. The negation preserves full detection coverage for unauthorized writes while eliminating alerts on normal HMI operations. In a plant with multiple authorized HMI stations, use a variable like $HMI_HOSTS and negate the entire group.

    Defensive Recommendations to Masa

    Finding Risk Mitigation
    No ICS-specific Snort rules deployed on plant-floor sensors Critical Deploy the three rules from Exercise 6.1 (SIDs 1000001 through 1000003) on all plant-floor Snort sensors immediately
    Rules use any source, which will alert on legitimate HMI writes Medium Refine each rule with !$HMI_HOSTS source negation after documenting all authorized HMI addresses per plant
    Signature-based detection cannot catch compromised-HMI attacks High Supplement Snort with a process-anomaly IDS that monitors setpoint values against safe operating ranges
    No rule management process exists for OT Snort sensors Medium Establish a quarterly rule review cycle where the OT security team updates SIDs based on new threat intelligence and plant topology changes

    Key Takeaways

    • Detection engineering translates offensive findings into defensive value. Every attack you executed in Levels 1 through 5 has a network signature that Snort can match
    • Snort rules follow the pattern: action, protocol, source, destination, then options with content matches, offsets, and a unique SID
    • Validation requires both true-positive testing (rule fires on attack traffic) and false-positive testing (rule does not fire on benign traffic)
    • Positional constraints (offset and depth) reduce false positives by matching bytes at the exact protocol field rather than anywhere in the payload
    • Signature-based detection is a starting point, not an endpoint. Process-anomaly and behavioral detection are necessary complements for ICS environments
