    Exercise 4.3: LAPS in the Wild

    Before You Begin

    LAPS (Local Administrator Password Solution) is Microsoft's mitigation for local admin password reuse across an estate. Each domain-joined machine gets a randomized local admin password, rotated on a schedule, stored on the machine's AD computer object in the ms-Mcs-AdmPwd attribute (legacy LAPS) or msLAPS-Password (Windows LAPS). The whole approach depends on read delegations being scoped tightly: only specific helpdesk groups should be able to read the LAPS attribute on specific OUs. When the delegation is too wide, any member of that group becomes effective local admin on every covered machine.

    Exercise 4.3 puts you on the wrong side of an over-scoped delegation. WS_Admins_<token> can read ms-Mcs-AdmPwd on WS-ENG-<token>. j.chen is a member via IT_HelpDesk nesting. Read the password.

    Tools required: netexec, pyLAPS, ldapsearch, bloodhound-python. Pre-installed on Kali.

    Scenario

    Marcus Bell: "LAPS is the right answer to local admin password reuse. Read access to the LAPS attribute is the wrong answer to delegation."

    The LAPS-stored password for WS-ENG-<token> contains your flag literally; you do not need to authenticate to the workstation, you need to read the attribute and submit the value.

    Credentials:

    Username Password
    j.chen Welcome2026#

    Domain: corp.nordport.local

    Your Objectives

    • Identify the LAPS-protected attribute (ms-Mcs-AdmPwd or msLAPS-Password)
    • Confirm that j.chen (via inherited group) can read the attribute on WS-ENG-<token>
    • Read the value
    • Submit it as the flag

    LAPS Architecture at a Glance

    LAPS is a small ecosystem: a CSE on each managed host writes the password into AD; reads are gated by delegations on the computer object. The diagram below maps the pieces together.

    flowchart LR
    GPO["GPO settings:<br/>policy + interval"]
    CSE["LAPS CSE<br/>(on every workstation)"]
    AD["AD computer object<br/>ms-Mcs-AdmPwd<br/>(or msLAPS-Password)"]
    HD["Helpdesk delegate group<br/>(read on attribute)"]
    Atk["Attacker (j.chen)<br/>via nested group"]

    GPO --> CSE
    CSE -- "rotate + write" --> AD
    HD -- "read" --> AD
    Atk -- "transitive memberOf" --> HD

    Legacy vs Windows LAPS

    The two flavors look similar in the directory but differ on the trust boundary that protects the secret. The table below summarises which attack works against which.

    Property Legacy LAPS Windows LAPS
    Schema ms-Mcs-AdmPwd msLAPS-Password (plain) or msLAPS-EncryptedPassword (DPAPI-NG)
    Storage Plaintext, ACL-gated Plaintext OR DPAPI-NG ciphertext to a named principal
    Read attack LDAP read with delegated group LDAP read PLUS DPAPI-NG decrypt as principal
    Defender's lever Tighten ACL Tighten ACL + scope decryption principal
    netexec --laps outcome Plaintext if you have read Plaintext if you can decrypt; ciphertext otherwise

    Background: Two Kinds of LAPS

    Variant Schema attribute Encryption at rest Read API
    Legacy LAPS (AdmPwd.PS) ms-Mcs-AdmPwd Plaintext (relies on AD ACLs) LDAP read
    Windows LAPS (Server 2019+) msLAPS-Password, msLAPS-EncryptedPassword Optional DPAPI-NG encryption to a designated principal LDAP read + decrypt

    Legacy LAPS is more common in environments older than ~2022. Windows LAPS is the modern default. The attack model is the same: find who can read the attribute and abuse the over-scoped delegation. The difference: Windows LAPS with encryption requires you to also be the encryption principal (or someone authorized to decrypt for them) to recover the plaintext.

    Why over-scoped delegations happen

    Helpdesk teams need to recover local admin passwords for break-fix work. The administrator delegating the read permission has two choices:

    1. Per-OU scoped: grant Engineering_Helpdesk read on ms-Mcs-AdmPwd for the Engineering OU only. Repeat per OU. Tedious but correct.
    2. Domain-wide: grant IT_HelpDesk read on ms-Mcs-AdmPwd for the whole domain. One click. Wrong.

    Option 2 is the path of least resistance and exists in many production environments. The result: any compromise of any IT_HelpDesk member yields local admin on every domain-joined machine.

    The defender's audit query

    # Find every principal that can read ms-Mcs-AdmPwd somewhere
Find-AdmPwdExtendedRights -Identity "OU=Workstations,DC=corp,DC=nordport,DC=local"

    The output should show only the per-OU helpdesk groups. If you see Domain Users or any unexpected principal, the delegation is wrong.

    Tool Primer

    netexec --laps

    netexec ldap corp-dc01 -u j.chen -p 'Welcome2026#' -d corp.nordport.local --laps

    Outputs every machine the caller can read LAPS for, with the plaintext password (and decrypts Windows LAPS if the attacker is authorized).

    Direct LDAP

    ldapsearch -x -LLL -H ldap://corp-dc01 \
  -D "CORP\j.chen" -w 'Welcome2026#' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(name=WS-ENG-<TOKEN>)" \
  ms-Mcs-AdmPwd ms-Mcs-AdmPwdExpirationTime

    If you can read the attribute, the value comes back; if not, the attribute is omitted from the response.

    pyLAPS

    pyLAPS --action get -d corp.nordport.local -u j.chen -p 'Welcome2026#' --dc-ip <dc>

    A purpose-built tool that handles both legacy and Windows LAPS, including DPAPI-NG decryption when you have the right keys.

    Walkthrough

    Step 1: Confirm Membership Path

    Group nesting is the trap LAPS delegations fall into. j.chen is a direct member of IT_HelpDesk, which is itself nested into WS_Admins_<token>. The standard memberof= filter does not follow nesting; you need the LDAP chain matching extended OID 1.2.840.113556.1.4.1941 to return transitive memberships.

    Kali - Verify j.chen reaches WS_Admins_

    ldapsearch -x -LLL -H ldap://corp-dc01 \
  -D "CORP\j.chen" -w 'Welcome2026#' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(&(memberof:1.2.840.113556.1.4.1941:=CN=WS_Admins_${OCR_SCOPE_TOKEN},OU=IT,DC=corp,DC=nordport,DC=local)(sAMAccountName=j.chen))" \
  sAMAccountName
    Token Effect
    memberof:1.2.840.113556.1.4.1941:= LDAP_MATCHING_RULE_IN_CHAIN; matches transitive group membership.
    CN=WS_Admins_<token>,OU=IT,DC=... Full distinguished name of the target group.
    (sAMAccountName=j.chen) And-clause to verify j.chen specifically.

    If j.chen's name appears in the output, the transitive path is alive. Empty output means a nesting break (common after group reorgs); without the path, Step 2 returns no LAPS hits.

    Step 2: Read LAPS via netexec

    netexec ldap --laps walks every computer object the caller can see, attempts to read the LAPS attribute on each, and prints whichever are readable. It tries both legacy (ms-Mcs-AdmPwd) and Windows LAPS (msLAPS-Password, msLAPS-EncryptedPassword) and decrypts the latter when the caller is authorized.

    Kali - Pull every readable LAPS password

    netexec ldap corp-dc01 -u j.chen -p 'Welcome2026#' \
  -d corp.nordport.local --laps
    Token Effect
    ldap LDAP protocol module (vs smb, winrm, etc.).
    --laps Enable the LAPS-reader sub-feature.

    Output format: one line per readable computer with the plaintext after LAPS Password:. Look for WS-ENG-<token> (the token is uppercased in the computer name; netexec prints it as stored). Other students' machines that you can also see (because IT_HelpDesk is over-scoped on the lab too) appear in the same listing.

    Step 3: Read LAPS via Direct LDAP

    For surgical extraction (one machine, one attribute) and to demonstrate the underlying primitive without netexec's wrapper, use ldapsearch directly. The tr command upper-cases the token because computer object names use upper-case in this lab.

    Kali - LDAP read of ms-Mcs-AdmPwd on your computer

    TOK=$(echo "${OCR_SCOPE_TOKEN}" | tr 'a-z' 'A-Z')
ldapsearch -x -LLL -H ldap://corp-dc01 \
  -D "CORP\j.chen" -w 'Welcome2026#' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(name=WS-ENG-${TOK})" ms-Mcs-AdmPwd
    Token Effect
    tr 'a-z' 'A-Z' Translate lower to upper case (token may be lowercase in env var).
    (name=WS-ENG-XXXX) Filter by computer name attribute.
    ms-Mcs-AdmPwd Trailing attribute; only this attribute returned.

    The ms-Mcs-AdmPwd value is the flag. If the attribute does not appear in the response (no error, just absent), the read permission is denied; recheck Step 1.

    Step 4: Submit

    The plaintext IS the flag. Submit on the platform.

    Common gotchas

    • Wrong token case: lab computer names are WS-ENG-J001 (uppercase) but OCR_SCOPE_TOKEN is j001 (lowercase). Always upper-case the token for computer-object lookups.
    • Windows LAPS instead of legacy: if the lab were Windows LAPS, ms-Mcs-AdmPwd would be empty and msLAPS-Password would hold the plaintext (or msLAPS-EncryptedPassword if encrypted). Re-query with the right attribute.
    • No transitive path: AD groups are not always transitive. Domain Local groups with Global group members work; some cross-forest scenarios do not. Step 1's chain-match query is the diagnostic.
    • netexec verbose mode: add -v if --laps returns no hits to see whether netexec saw the computer at all (scope filter problem) or saw it and could not read (ACL problem).

    Blue Team Perspective

    Reads of the LAPS attribute generate event 4662 with a specific access mask only when the relevant SACL is configured. Most environments are missing this, which is exactly why the attack persists.

    Activity Event ID Where it fires
    LAPS attribute read 4662 (with SACL) DC Security log
    Bulk LAPS enumeration 4662 burst DC Security log
    Workstation local-admin login 4624 logon type 3 / 10 Workstation Security log
    Defender for Identity "Suspicious LDAP query (LAPS)" MDI

    What real defenders look for

    Set a SACL on the ms-Mcs-AdmPwd (or msLAPS-Password) attribute auditing successful reads by non-Tier-0 principals. Forward the resulting 4662 events to the SIEM. Alert on any read by a principal not on the helpdesk allow-list. The detection has very low cardinality and high signal.

    Hardening Note

    LAPS is the right control; ACL hygiene around it is what makes or breaks the deployment. The list below is the practical menu.

    LAPS hardening

    • Migrate to Windows LAPS with DPAPI-NG encryption tied to a tightly scoped principal.
    • Scope read delegations per OU using Set-AdmPwdReadPasswordPermission. Never delegate at the domain root.
    • Run Find-AdmPwdExtendedRights quarterly against each managed OU; alert on changes.
    • Add a SACL auditing reads of the LAPS attribute and forward 4662 events with allow-list of legitimate readers.
    • Disable legacy LAPS attributes once Windows LAPS is fully deployed; confirm ms-Mcs-AdmPwd is empty everywhere.
    • Build a SIEM detection on netexec ldap --laps-shaped traffic: many distinct computer-attribute reads from one source in seconds.

    Analysis Questions

    1. Legacy LAPS stores the password in plaintext under ms-Mcs-AdmPwd. Why does that work, and what is Microsoft's improvement in Windows LAPS?

    Reveal Answer

    Legacy LAPS works because the attribute's read permission is restricted by AD ACLs to the delegated helpdesk groups. The plaintext is "encrypted" by access control rather than cryptographic encryption: only authorized principals can read it. The improvement in Windows LAPS is the introduction of DPAPI-NG-based encryption tied to a specific principal (a user, group, or computer), so even an attacker who reads the attribute as Domain Admin cannot recover the plaintext without being able to decrypt via the principal's key. The encryption narrows the trust boundary from "anyone with read on the attribute" to "the specific principal authorized to decrypt." Operationally, Windows LAPS encryption also makes it possible to grant read across a wider scope (for inventory tooling) while keeping plaintext recovery scoped tighter.

    2. The defender control is to scope the read delegation tightly per OU. What stops a defender from doing this in practice?

    Reveal Answer

    The barriers are organizational, not technical: (a) helpdesk teams want one-click access to any machine across the estate so per-OU delegation feels obstructive; (b) executive turnover reorganizes OUs faster than delegations get re-evaluated, so old wide delegations accumulate; (c) AD ACL audits are tedious manual work; few teams do them quarterly; (d) Microsoft's installation tooling defaults to wide ("apply to OU=Computers") rather than narrow. The fix is automation: scripts that periodically audit Find-AdmPwdExtendedRights against a baseline and alert on changes, plus a service-catalog-style helpdesk request flow where the operator clicks a button per host that grants ephemeral access for a short window.

    3. Once you read the LAPS password, you are local admin on the workstation. What does that get you that the AD compromise alone does not?

    Reveal Answer

    Local admin on a domain-joined workstation gets you: (a) every credential cached on the machine via LSASS / DPAPI dumping (mimikatz sekurlsa::logonpasswords, lsassy, pypykatz), (b) every browser session cookie (DPAPI-protected, but trivially decrypted as the user), (c) every saved Wi-Fi key, every saved RDP credential, every personal certificate enrolled to the user, (d) every running process's memory, including in-memory credentials for SaaS tools, and (e) the ability to install a persistence mechanism. If the workstation belongs to a higher-privileged user (an admin doing helpdesk work, or a developer with cloud credentials), the lateral pivot to higher AD privilege via that user's stored secrets is often immediate.

    Key Takeaways

    • LAPS attribute is ms-Mcs-AdmPwd (legacy) or msLAPS-Password (Windows LAPS).
    • Read delegations are AD ACLs; widely-scoped delegations leak local admin on every covered machine.
    • netexec ldap --laps enumerates every readable LAPS password in one call.
    • Windows LAPS adds DPAPI-NG encryption tied to specific decryption principals.
    • Defender control: per-OU scoped delegations, periodic ACL audits, service-catalog-style ephemeral access.

    Cheat Sheet Recap

    The four operations below cover discovery and abuse for both LAPS variants. Run them in this order on any engagement.

    Goal Command
    Bulk LAPS enumeration netexec ldap <dc> -u <user> -p '<pw>' -d <domain> --laps
    Targeted LDAP read (legacy) ldapsearch -x -LLL -H ldap://<dc> -D "<DOMAIN>\<user>" -w '<pw>' -b "<DN>" "(name=<HOST>)" ms-Mcs-AdmPwd
    Targeted LDAP read (Windows LAPS) ldapsearch ... "(name=<HOST>)" msLAPS-Password msLAPS-EncryptedPassword
    pyLAPS (handles DPAPI-NG decrypt) pyLAPS --action get -d <domain> -u <user> -p '<pw>' --dc-ip <dc>

    Spaced Repetition

    Card 1: LAPS Attribute Names

    Q: What attributes hold the LAPS password in legacy LAPS vs Windows LAPS?

    Answer

    Legacy LAPS: ms-Mcs-AdmPwd (plaintext, ACL-protected). Windows LAPS: msLAPS-Password (plaintext when not encrypted) and msLAPS-EncryptedPassword (DPAPI-NG encrypted blob, requires the authorized decryption principal). The expiration time is ms-Mcs-AdmPwdExpirationTime for legacy, msLAPS-PasswordExpirationTime for Windows LAPS.

    Card 2: netexec --laps Discovery

    Q: One command to enumerate every LAPS password readable by j.smith / Pass# on corp.local against DC dc01.

    Answer 
    netexec ldap dc01 -u j.smith -p 'Pass#' -d corp.local --laps

    Outputs computer name and plaintext for each readable entry. Add --users <user> to query for a specific computer rather than enumerating all.

    Card 3: Direct LDAP Read of ms-Mcs-AdmPwd

    Q: Write the ldapsearch query to read ms-Mcs-AdmPwd from computer WS-ENG-A7F3 in corp.local.

    Answer 
    ldapsearch -x -LLL -H ldap://dc01 \
  -D "CORP\j.smith" -w 'Pass#' \
  -b "DC=corp,DC=local" \
  "(name=WS-ENG-A7F3)" ms-Mcs-AdmPwd

    If you cannot read the attribute, the response omits it (no error). If you can, the value appears as a string.

    Card 4: Find-AdmPwdExtendedRights

    Q: How does a defender enumerate every principal with LAPS read on a given OU?

    Answer 
    Find-AdmPwdExtendedRights -Identity "OU=Workstations,DC=corp,DC=local"

    From the AdmPwd.PS module. Output should show only the intended helpdesk groups. Any unexpected principal (especially Domain Users, Authenticated Users, or unfamiliar admin groups) is a finding. Run quarterly; baseline the output and alert on changes.

    Card 5: DPAPI-NG and Windows LAPS

    Q: Windows LAPS encryption changes the trust boundary from "anyone with attribute read" to what?

    Answer

    "The specific principal authorized to decrypt." DPAPI-NG (Data Protection API: Next Generation) encrypts the password to a named principal (user, group, or computer SID); only that principal can decrypt with their key. An attacker with attribute read but without the principal's keys gets ciphertext, not plaintext. The encryption lets an organization grant attribute-read more widely (for inventory tools or backup) while keeping plaintext recovery tightly scoped. Defender check: ensure msLAPS-EncryptedPassword is the populated attribute, not msLAPS-Password.
