    Exercise OTSOC-2.4: The Anonymous OPC-UA Server

    Engagement Status

    Client Pecan Creek Creamery (fictional)
    Role OT SOC Analyst, Supervisory Layer
    Phase Visibility Protocol Analysis Detection
    Priority order Safety, then Integrity, then Availability, then Confidentiality

    What you know so far: You have read the legacy plant protocols (Modbus, S7comm) and the modern cold-side protocols (CIP, DNP3). The newest layer is an OPC-UA supervisory server the plant added last year. OPC-UA was designed with security in mind, which makes its most common real-world finding instructive: a server deployed with all the security turned off.

    Scenario

    You are an OT SOC analyst at Pecan Creek Creamery. The plant added a modern OPC-UA supervisory server last year. The vendor left it with SecurityPolicy None (no signing, no encryption) and Anonymous access allowed, which is the single most common OPC-UA finding in the field. The target is opcua.pcc.local on port 4840, endpoint opc.tcp://opcua.pcc.local:4840/pcc/supervisory/, namespace http://pecancreek.local/plant/.

    You will connect as an anonymous client with the asyncua library, confirm the endpoint advertises SecurityPolicy None and Anonymous, then browse the address space under Objects/PecanCreek. The tree mirrors a handful of plant tags (Mix, Pasteurizer, Freezer, Ammonia) plus a Commissioning object. You will read the Commissioning/CommissioningToken node, which is readable only because anonymous access is enabled, and that read is the proof of the misconfiguration. You are demonstrating the finding, not exploiting anything. Then you document it the way an architecture review expects: what is exposed, why None plus Anonymous is a problem, and what the secure configuration would be.

    Why this matters

    OPC-UA is the protocol the OT industry chose to fix the sins of the legacy dialects: it has authentication, signing, and encryption built into the standard. The catch is that those protections are configurable, and a server shipped with them off is no safer than classic Modbus, while everyone assumes it is safe because it is the modern protocol.

    Three concrete reasons the skill matters. First, recognizing the None-plus-Anonymous misconfiguration is the highest-value OPC-UA finding you will report. A server in that state lets any host on the segment connect with no credentials and read the entire address space, which on a supervisory server can include recipes, batch records, and commissioning material. The finding is common precisely because the secure setup requires certificate management that vendors skip during commissioning. Second, browsing an OPC-UA address space is a transferable enumeration skill. The tree of objects and variables maps directly to the plant's process model, so an analyst who can browse it understands what the supervisory layer knows, which is the same understanding an attacker would build before manipulating it. Third, knowing the secure configuration turns the finding into a fundable recommendation. Saying "OPC-UA is insecure" is wrong and useless; saying "the endpoint advertises only SecurityPolicy None with Anonymous, and it should advertise Basic256Sha256 with certificate or username authentication" is a finding a plant can act on.

    The commissioning token you read is a training artifact. The skill of confirming an endpoint's security policy and browsing its namespace is permanent.

    Before You Begin: Read Your Target IP

    The OPC-UA server gets a fresh address every spawn. Open the Exercise Network panel and read the IP for opcua.pcc.local into a shell variable. Replace the placeholder below with the value from your own panel.

    Kali - set the OPC-UA target variable

    OPCUA=<opcua ip from the Exercise Network panel>
echo "opc-ua server = $OPCUA:4840"
echo "endpoint      = opc.tcp://$OPCUA:4840/pcc/supervisory/"

    Confirm the server answers on port 4840 before you try to connect.

    Kali - confirm the OPC-UA port is open

    nc -zv "$OPCUA" 4840

    Expected output

    Connection to <OPCUA> 4840 port [tcp/*] succeeded!

    A succeeded! line confirms the supervisory server is listening. Fix connectivity first if it fails.

    Walkthrough

    Step 1: Enumerate the advertised endpoints

    Before connecting, ask the server what security it offers. OPC-UA exposes a get_endpoints call that lists every endpoint with its SecurityPolicy and the token types it accepts, and you can read it without authenticating. The presence of a None policy with an Anonymous token type is the misconfiguration in plain sight.

    Kali - list endpoints and their security policies

    python3 - <<'PYEOF'
import os, asyncio
from asyncua import Client

async def main():
    url = f"opc.tcp://{os.environ['OPCUA']}:4840/pcc/supervisory/"
    c = Client(url)
    eps = await c.connect_and_get_server_endpoints()
    for ep in eps:
        policy = ep.SecurityPolicyURI.split("#")[-1]
        modes = [t.TokenType.name for t in ep.UserIdentityTokens]
        print(f"policy={policy:16} mode={ep.SecurityMode.name:12} tokens={modes}")

asyncio.run(main())
PYEOF

    Expected output

    policy=None             mode=None_        tokens=['Anonymous']

    The only advertised policy is None with security mode None and an Anonymous user-identity token. No signing, no encryption, and no credential required. An endpoint list that offers a real policy such as Basic256Sha256 alongside None would be a partial finding; a server that offers only None is fully exposed.

    Step 2: Connect anonymously

    Confirming the policy is one thing; demonstrating that you can connect with no credentials makes the finding undeniable. Connect to the endpoint with no username, password, or certificate. A clean session proves anonymous access is live.

    Kali - connect as an anonymous client

    python3 - <<'PYEOF'
import os, asyncio
from asyncua import Client

async def main():
    url = f"opc.tcp://{os.environ['OPCUA']}:4840/pcc/supervisory/"
    async with Client(url) as c:           # no credentials supplied
        srv = await c.nodes.server.read_browse_name()
        print("connected anonymously; server node browse name =", srv.Name)

asyncio.run(main())
PYEOF

    Expected output

    connected anonymously; server node browse name = Server

    The session opened with no credentials at all, which confirms the Anonymous token type the endpoint advertised. Any host that can reach port 4840 can do the same.

    Step 3: Browse the address space

    OPC-UA organizes data as a tree of nodes under Objects. Browsing that tree is your enumeration step: it shows you exactly what the supervisory server publishes, which mirrors the plant's process model. Resolve the plant namespace index first, then walk the tree under PecanCreek.

    Kali - browse the PecanCreek object tree

    python3 - <<'PYEOF'
import os, asyncio
from asyncua import Client

async def main():
    url = f"opc.tcp://{os.environ['OPCUA']}:4840/pcc/supervisory/"
    async with Client(url) as c:
        idx = await c.get_namespace_index("http://pecancreek.local/plant/")
        root = await c.nodes.objects.get_child(f"{idx}:PecanCreek")
        for child in await root.get_children():
            bn = await child.read_browse_name()
            print(f"{idx}:{bn.Name}")
            for leaf in await child.get_children():
                lbn = await leaf.read_browse_name()
                print(f"    {idx}:{lbn.Name}")

asyncio.run(main())
PYEOF

    Expected output

    2:Mix
    2:RecipeId
    2:SugarPct
2:Pasteurizer
    2:HoldTempC
2:Freezer
    2:BarrelTempC
2:Ammonia
    2:SuctionPsig
2:Commissioning
    2:CommissioningToken

    The tree mirrors the plant: Mix, Pasteurizer, Freezer, and Ammonia each expose a few process variables, and a Commissioning object holds a CommissioningToken node. An anonymous reader sees the entire supervisory model of the plant, which is exactly the reconnaissance an attacker would perform.

    Step 4: Read the commissioning token

    The CommissioningToken node is readable only because anonymous access is enabled. Reading it is the proof of the misconfiguration and the source of the flag. On a properly secured server this read would fail with a credential or security error. Navigate to the node and read its value.

    Kali - read the CommissioningToken node

    python3 - <<'PYEOF'
import os, asyncio
from asyncua import Client

async def main():
    url = f"opc.tcp://{os.environ['OPCUA']}:4840/pcc/supervisory/"
    async with Client(url) as c:
        idx = await c.get_namespace_index("http://pecancreek.local/plant/")
        node = await c.nodes.objects.get_child(
            [f"{idx}:PecanCreek", f"{idx}:Commissioning", f"{idx}:CommissioningToken"])
        print("CommissioningToken =", await node.read_value())

asyncio.run(main())
PYEOF

    Expected output (value masked)

    CommissioningToken = pcc_opcua_anon_<masked>

    The token value reads back over an unauthenticated session. On a server configured with a signed-and-encrypted policy and certificate or username authentication, this read returns an access-denied or security error instead. The fact that it succeeds anonymously is the finding.

    Output Interpretation

    • get_endpoints lets you read a server's advertised SecurityPolicy and token types before connecting. A server that advertises only None with Anonymous is fully exposed.
    • Connecting with no credentials proves the Anonymous token type is live, not merely advertised.
    • The OPC-UA address space is a tree under Objects; browsing it mirrors the plant's process model and is the core enumeration skill.
    • The CommissioningToken reads back only because anonymous access is enabled. On a secured server the same read fails, which is what makes the successful read the proof of the misconfiguration.

    Analysis Questions

    1. OPC-UA was designed to be secure. Why is None-plus-Anonymous so common in the field?

    Reveal answer

    The secure configuration requires certificate management: the server and each client need certificates, and an administrator must establish trust between them. During commissioning, integrators under time pressure frequently turn security off to get the system talking, intending to harden it later, and "later" never arrives. The result is a modern protocol running with no signing, no encryption, and no authentication, which is no safer than the legacy dialects it was meant to replace. The protocol is not the problem; the deployment is.

    2. You connected with no credentials and read the whole tree. What is the realistic worst case on a real supervisory server?

    Reveal answer

    A real supervisory OPC-UA server aggregates data from across the plant: recipes, batch records, production counts, setpoints, and sometimes write access to those setpoints. An anonymous reader gets the entire production picture for reconnaissance, and if the server also allows anonymous writes, an attacker can change setpoints from a single unauthenticated session. Even read-only exposure leaks proprietary recipes and batch data, which is a confidentiality and competitive loss on top of the security risk.

    3. What is the secure configuration you would recommend, specifically?

    Reveal answer

    Disable the None security policy and the Anonymous identity token entirely. Configure the endpoint to advertise a signed-and-encrypted policy such as Basic256Sha256 with security mode SignAndEncrypt, and require either certificate-based or username-and-password authentication for client identity. Establish a certificate trust list so only known clients (the HMI, the historian, the engineering workstation) can connect, and place the server in a conduit reachable only from those hosts. Name the specific policy and mode in the finding so the plant can verify the change.

    4. How would your SOC detect an attacker abusing this server, given it is misconfigured?

    Reveal answer

    Until the server is hardened, the detection is connection-based: alert on any OPC-UA session from a source that is not the known HMI, historian, or engineering workstation, because a legitimate plant has a small, fixed set of clients. Watch for browse and read activity that walks the whole address space quickly, which is enumeration rather than the targeted polling a real client does. The durable fix is to require authentication so unknown clients cannot connect at all, but until then, a tight allowlist on the session source is your best signal.

    Capture the Flag

    The flag is the CommissioningToken node value you read in Step 4, wrapped as OCR{...}. The node is readable only because anonymous access is enabled, so recovering it is itself the demonstration of the misconfiguration. Build the flag from the value you read rather than typing it by hand.

    Kali - assemble the flag from the token

    python3 - <<'PYEOF'
import os, asyncio
from asyncua import Client

async def main():
    url = f"opc.tcp://{os.environ['OPCUA']}:4840/pcc/supervisory/"
    async with Client(url) as c:
        idx = await c.get_namespace_index("http://pecancreek.local/plant/")
        node = await c.nodes.objects.get_child(
            [f"{idx}:PecanCreek", f"{idx}:Commissioning", f"{idx}:CommissioningToken"])
        token = await node.read_value()
        print("flag = OCR{" + token + "}")

asyncio.run(main())
PYEOF

    Expected output (flag masked)

    flag = OCR{pcc_opcua_anon_<masked>}

    Key Takeaways

    • OPC-UA ships with authentication, signing, and encryption, but they are configurable, and a server with them off is no safer than classic Modbus.
    • get_endpoints reveals a server's security posture before you connect; an endpoint offering only None with Anonymous is the highest-value OPC-UA finding.
    • Browsing the address space mirrors the plant's process model and is the enumeration skill an attacker uses first.
    • A defensible finding names the specific secure policy (Basic256Sha256, SignAndEncrypt, certificate or username auth), not just "turn on security."
