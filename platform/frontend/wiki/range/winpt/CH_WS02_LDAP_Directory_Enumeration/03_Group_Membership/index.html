    Exercise WS-2.3: Group Membership Mapping

    Before You Begin

    Exercise WS-2.2 enumerated user accounts across the domain, revealing logon names, freeform attributes, and preliminary group memberships through the memberOf attribute on each user object. Exercise WS-2.3 approaches group membership from the opposite direction; querying group objects directly to extract their member lists. You will need the same Kali Linux machine with anonymous Lightweight Directory Access Protocol (LDAP) access to dc01.

    Prerequisites

    • Exercise WS-2.2 completed (user accounts enumerated)
    • VPN active and dc01 reachable
    • ldapsearch available (ldap-utils package)
    • Your user account list from Exercise WS-2.2

    Scenario

    User enumeration in Exercise WS-2.2 revealed interesting accounts, including some that appeared in administrative groups. Exercise WS-2.3 takes the next logical step: map every security group and its members to understand who holds elevated access. In Active Directory (AD), permissions are primarily assigned through group membership rather than directly to individual users, so a complete group map is the key to understanding the domain's access model.

    Your Objectives

    • Enumerate all security groups in the domain using an LDAP search filter
    • Map group memberships by reading the member attribute on each group object
    • Identify the Domain Admins group and other high-privilege groups
    • Locate the lab flag hidden in the description attribute of a specific group

    Background: Security Groups and Privilege in Active Directory

    Active Directory uses two categories of groups: security groups and distribution groups. Security groups are the ones that matter for access control; they can be assigned permissions on files, shares, services, and other resources. Distribution groups exist only for email distribution lists and carry no security permissions. Both types share the group objectClass, but security groups have a groupType attribute value that includes a flag marking them as security-enabled.

    The member attribute on a group object lists the Distinguished Names (DNs) of every object that belongs to that group. Reading the member attribute on the Domain Admins group, for example, gives you the DN of every user (or nested group) with full administrative control over the domain. Groups can also be members of other groups; a pattern called nested group membership: which means a user can inherit privileges from groups they do not directly belong to.

    Several built-in groups carry significant default privileges. Domain Admins members have unrestricted access to every domain-joined machine. Enterprise Admins members control the entire AD forest. Account Operators can create and modify user accounts. Server Operators can log on to domain controllers. Identifying which accounts belong to these groups is one of the highest-priority tasks during directory enumeration.

    Tool Primer: ldapsearch for Group Objects

    The command below queries every group object in the domain and returns the group's common name, description, and member list.

    ldapsearch -x -H ldap://dc01 -b "DC=corp,DC=ocr-range,DC=lab" "(objectClass=group)" cn description member

    A typical group entry in the output looks like the following.

    # Domain Admins, Users, corp.ocr-range.lab
dn: CN=Domain Admins,CN=Users,DC=corp,DC=ocr-range,DC=lab
cn: Domain Admins
description: Designated administrators of the domain
member: CN=Administrator,CN=Users,DC=corp,DC=ocr-range,DC=lab
member: CN=Admin User,OU=IT,DC=corp,DC=ocr-range,DC=lab

    Each member: line lists one member's full DN. Groups with many members will have many member: lines. Groups with no members will omit the member attribute entirely.

    Attribute What It Reveals
    cn The group's common name; its display name in the directory
    description Admin-written notes about the group's purpose
    member Full DN of every direct member (user, computer, or nested group)

    Walkthrough

    Step 1: Enumerate All Groups

    Enumerate all security groups

    Run the group enumeration query and save the results to a file for analysis. The domain may contain dozens of groups, including both custom groups created by administrators and built-in default groups.

    ldapsearch -x -H ldap://dc01 -b "DC=corp,DC=ocr-range,DC=lab" "(objectClass=group)" cn description member > /tmp/groups.ldif

    Check the entry count at the end of the output or count the DN lines.

    grep -c "^dn:" /tmp/groups.ldif

    Record the total number of groups discovered.

    Step 2: Identify High-Privilege Built-in Groups

    Identify high-privilege built-in groups

    Search the saved output for groups with well-known names that carry elevated privileges. The following command highlights the most critical built-in groups.

    grep -A2 "^cn: Domain Admins\|^cn: Enterprise Admins\|^cn: Administrators\|^cn: Account Operators\|^cn: Server Operators\|^cn: Backup Operators" /tmp/groups.ldif

    The -A2 flag shows two lines after each match, which often includes the first member: line. For a complete view of any group's membership, search for the group's DN block and read all member: lines.

    Step 3: Extract Domain Admins Membership

    Extract Domain Admins membership

    The Domain Admins group is the single most important group to audit. Extract its full entry from the saved output.

    ldapsearch -x -H ldap://dc01 -b "CN=Domain Admins,CN=Users,DC=corp,DC=ocr-range,DC=lab" -s base "(objectClass=*)" member

    The -s base scope flag tells ldapsearch to return only the object at the exact DN specified, without searching below it. Record every member DN that appears. Cross-reference these DNs with the user accounts you enumerated in Exercise WS-2.2 to match usernames to their Domain Admin membership.

    Step 4: Identify Custom Administrative Groups

    Identify custom administrative groups

    Organizations frequently create custom groups to manage access for specific teams; names like IT-Admins, Server-Admins, DB-Admins, or HelpDesk-Elevated are common patterns. Search the group list for names that suggest administrative or elevated access.

    grep -i "^cn:.*admin\|^cn:.*elevated\|^cn:.*privileged\|^cn:.*operator" /tmp/groups.ldif

    For each custom admin group you find, extract its members using the same approach as Step 3; query the group's DN directly and read the member attribute.

    Step 5: Build a Group Membership Map

    Using the data from Steps 2 through 4, create a membership map that links groups to their members. The map should highlight which users appear in multiple privileged groups, as those accounts represent the highest-value targets.

    Domain Admins
├── Administrator
└── [admin username]

IT-Admins
├── [username]
├── [username]
└── [username]

[Other groups...]

    Fill in actual usernames by extracting the Common Name (CN) portion from each member's DN. The CN appears as the first component; for example, CN=John Smith,OU=IT,... has a CN of "John Smith."

    Step 6: Examine Group Descriptions

    Examine group descriptions

    Search the saved output for all description values on group objects. Group descriptions often state the group's purpose and intended scope, providing context that helps you understand the access model.

    grep -B1 "^description:" /tmp/groups.ldif

    The -B1 flag shows the line before each match, which is typically the cn: line, letting you pair each description with its group name. Read every description carefully. The flag for this exercise is stored in the description attribute of the IT-Admins group.

    Step 7: Check for Empty Groups

    Groups with no members appear in the output without any member: lines. Empty security groups are worth noting because they may represent groups that were created for a future purpose, groups whose members were removed during a cleanup, or staging groups that will gain members during a migration.

    To find groups that have no members, look for group blocks that jump from description: (or cn:) directly to the next entry's comment line without any member: lines in between.

    Step 8: Interpret the Results

    Review your membership map with an eye toward attack paths. Users who belong to Domain Admins or multiple privileged groups represent the shortest path to full domain compromise; if an attacker can obtain their credentials, the entire domain is controlled. Service accounts in administrative groups are particularly concerning because they may authenticate non-interactively and have credentials stored in configuration files or scripts.

    Consider the defensive perspective as well. Are there more Domain Admins than necessary? Do custom admin groups follow the principle of least privilege, or do they grant broad access? Empty groups that were intended to restrict membership may indicate an incomplete security configuration.

    Step 9: Find and Submit the Flag

    The flag for this exercise is located in the description attribute of the IT-Admins group. If you completed Step 6, you should have already spotted the flag while reviewing group descriptions. The flag follows the standard OCR{...} format.

    The flag follows the standard OCR{...} format. Submit it on the platform to complete the exercise.

    Analysis Questions

    1. Why do organizations assign permissions through groups rather than directly to individual user accounts?

    Reveal Answer

    Group-based permissions are far easier to manage at scale. When an employee changes roles, an administrator updates their group memberships rather than modifying permissions on every resource. Groups also make auditing clearer; reviewing a group's member list shows at a glance who has access, rather than checking each resource's access-control list individually.

    2. What risk does nested group membership create, and how can it complicate auditing?

    Reveal Answer

    Nested groups allow a user to inherit privileges indirectly. If Group A is a member of Group B, every member of Group A gains Group B's permissions without appearing directly in Group B's member list. An auditor reviewing Group B may not realize that an entire set of users has inherited access through the nested group. Attackers can exploit these hidden trust paths to escalate privileges.

    3. You found the flag in a group's description attribute. How is finding sensitive data in a group description similar to the finding in Exercise WS-2.1?

    Reveal Answer

    Both findings demonstrate the same pattern: administrators storing information in freeform text attributes that are readable via anonymous LDAP. In Exercise WS-2.1 the data was in an OU description; in Exercise WS-2.3 the data was in a group description. The lesson is consistent; any attribute exposed through LDAP should be treated as publicly readable and audited regularly.

    4. An attacker discovers a service account in the Domain Admins group. Why is that finding more dangerous than a regular user in Domain Admins?

    Reveal Answer

    Service accounts often have passwords that are set once and rarely changed, sometimes stored in scripts or configuration files in plaintext. Unlike interactive user accounts, service accounts may not trigger the same monitoring alerts when accessed from unexpected locations. An attacker who compromises a service account in Domain Admins gains persistent, high-privilege access that is harder for defenders to detect and remediate.

    Key Takeaways

    • Security groups are the mechanism through which Active Directory assigns permissions, making group enumeration essential for understanding the domain's access model.
    • The member attribute on group objects provides a complete roster of direct members, while nested groups can hide indirect membership from casual inspection.
    • Domain Admins and other built-in privileged groups should have minimal membership; a large number of members indicates poor privilege hygiene.
    • Group descriptions, like OU and user descriptions, are readable through LDAP and may contain sensitive notes or metadata.
    • With group memberships mapped, Exercise WS-2.4 will enumerate computer accounts to catalog the infrastructure and identify potential targets for lateral movement.
