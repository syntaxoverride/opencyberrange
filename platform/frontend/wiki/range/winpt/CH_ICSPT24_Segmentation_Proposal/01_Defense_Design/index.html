    Exercise ICSPT-6.2: Segmentation Proposal

    Engagement Status

    Client Masa Foods, Inc. (fictional)
    Role OT Security Engineer, All Plants
    Phase Discovery Detection Rules Defense (segmentation design) Capstone

    What you know so far: Exercise 6.1 produced detection rules for the three attack patterns you exploited across Levels 1 through 5. Detection is reactive. Reyna Alvarado now wants a proactive defense: a network segmentation proposal that would have prevented lateral movement between plants in the first place. Exercise 6.2 is an independent exercise with no step-by-step walkthrough. You write the proposal, submit it to the rubric checker, and iterate until it passes.

    Environment Checklist

    Exercise 6.2 uses the rubric checker server. Verify connectivity before starting.

    Kali

    curl -s http://rubric.masa.local:8080/rubric | head -30

    The server should return a JSON object describing the rubric requirements. If the connection fails, check the OCR platform session view for the rubric server IP and add it to /etc/hosts.

    Scenario

    The Masa Foods CISO has read your penetration test findings from Levels 1 through 5 and wants a written network segmentation proposal before the next board meeting. The proposal must cover all three plants, reference the Purdue model, and include specific firewall rules, authentication controls, and monitoring recommendations. A rubric checker at rubric.masa.local:8080 scores your submission against the CISO's requirements. Your job is to write the proposal as a plain-text document, submit it via curl, review the score, and revise until the rubric checker accepts it.

    Why this matters

    Penetration test reports identify vulnerabilities. Segmentation proposals fix them. Every OT security engagement ends with a recommendation section, and the most common recommendation in ICS environments is network segmentation. Writing a segmentation proposal that references the Purdue model, specifies per-plant firewall rules, and addresses authentication gaps is a core deliverable for any OT security consultant. The rubric checker simulates a demanding client who rejects vague recommendations and requires specifics.

    The professional skill Exercise 6.2 builds is translating technical findings into an actionable architectural document. A proposal that says "segment the network" is useless. A proposal that says "deploy a firewall between the Plant 1 Modbus segment (10.1.x.0/24) and the corporate LAN, permitting only TCP/502 from the authorized HMI at 10.1.x.5" is useful.

    Background: The Purdue Model and OT Segmentation

    The Purdue Enterprise Reference Architecture (PERA) divides an industrial network into six levels. Segmentation proposals for ICS environments reference these levels to establish trust boundaries.

    Level Name Masa Foods Examples
    0 Physical Process Ovens, conveyors, water treatment tanks, packaging lines
    1 Basic Control PLCs (Modbus, S7, CIP controllers)
    2 Area Supervisory HMIs, SCADA servers, historians
    3 Site Operations Engineering workstations, patch servers
    3.5 DMZ Jump servers, data diodes, file transfer servers
    4-5 Enterprise Corporate IT, email, ERP, internet access

    The critical segmentation boundary is between Level 3 and Level 4 (the IT/OT DMZ at Level 3.5). A second critical boundary separates each plant's Level 1/2 network from every other plant. The attacks you executed in Levels 1 through 5 all crossed at least one of these boundaries.

    What the rubric checker looks for

    The rubric checker at rubric.masa.local:8080 evaluates your proposal against specific criteria. Retrieve the full list with GET /rubric. Common requirements include:

    • Plant-specific firewall rules (not generic "add a firewall" statements)
    • Explicit Purdue model references with level assignments for Masa assets
    • Authentication controls for OT protocol access (Modbus, S7, CIP)
    • Monitoring and logging recommendations per plant
    • Firmware update and patch management strategy

    Submission format

    The rubric checker accepts a plain-text proposal via POST /check. Submit the proposal as the request body. The response includes a score, pass/fail status, and feedback on missing criteria.

    Suggested Methodology

    Exercise 6.2 is an independent exercise. No step-by-step walkthrough is provided. Instead, here are the stages a methodical assessor would follow.

    Stage 1: Retrieve the Rubric

    Query the rubric endpoint to understand exactly what the checker expects. Read every requirement carefully before writing a single line of the proposal. Missing even one required section will cause a rejection.

    Kali

    curl -s http://rubric.masa.local:8080/rubric | jq .

    Record each requirement as a checklist item. Your proposal must address every item on the list.

    Stage 2: Draft the Proposal

    Create a plain-text file that addresses each rubric requirement. Structure the proposal with clear section headers so the rubric checker can find each required element. A recommended structure:

    1. Executive Summary: One paragraph stating the purpose and scope
    2. Current State: Brief description of the flat network and the risks you identified
    3. Purdue Model Mapping: Assign each Masa asset to a Purdue level
    4. Plant-Specific Firewall Rules: Separate subsection per plant with source, destination, port, and action
    5. Authentication Controls: Per-protocol authentication recommendations
    6. Monitoring and Logging: IDS placement, log collection, alerting
    7. Firmware and Patch Management: Update cadence and change control

    Be specific. Name protocols (Modbus TCP/502, S7comm TCP/102, CIP TCP/44818), name assets (Plant 1 oven PLC, Plant 2 water treatment PLCs, Plant 3 packaging PLC and warehouse RTU), and name Purdue levels.

    Stage 3: Submit and Review Feedback

    Submit the proposal to the rubric checker and examine the response. The checker returns structured feedback indicating which criteria passed and which are missing.

    Kali

    curl -s -X POST http://rubric.masa.local:8080/check \
  -H "Content-Type: text/plain" \
  --data-binary @proposal.txt | jq .

    Read every feedback item. Each missing criterion tells you exactly what to add or revise.

    Stage 4: Iterate Until Accepted

    Revise the proposal based on the feedback, resubmit, and repeat until the checker returns a passing score and the flag. Most proposals require two to three iterations. Focus on the specific feedback rather than rewriting the entire document.

    Stage 5: Record the Flag

    When the rubric checker accepts the proposal, the response includes the flag. Record it and submit.

    Output Interpretation

    • A response with "pass": false includes a feedback array listing every missing criterion. Address each one before resubmitting
    • A response with "pass": true includes the flag in the response body
    • If the checker rejects your proposal for "missing plant-specific firewall rules," verify that each plant section includes explicit source IP, destination IP, port, and allow/deny action
    • If the checker rejects for "missing Purdue model reference," verify that you explicitly assign Masa assets to numbered Purdue levels (Level 0 through Level 5), not just mention the Purdue model in passing
    • A connection refused error means the rubric server container is not running. Return to the Environment Checklist

    Analysis Questions

    1. The rubric requires plant-specific firewall rules rather than a single global policy. Why is per-plant segmentation necessary?

    Reveal answer

    Each Masa Foods plant runs a different ICS protocol (Modbus, S7comm, CIP) with different authorized endpoints, different port numbers, and different traffic patterns. A global firewall policy that permits TCP/502 everywhere would leave Plant 2 and Plant 3 unprotected against unauthorized Modbus traffic on their segments. Per-plant rules ensure that only the correct protocol is permitted on each segment and only from authorized sources. The attacks in Levels 1 through 5 demonstrated that an attacker on one plant's network could reach other plants precisely because no per-plant boundaries existed.

    2. Where does the IT/OT DMZ (Purdue Level 3.5) sit in the Masa Foods network, and what devices belong there?

    Reveal answer

    The DMZ sits between the corporate IT network (Levels 4 and 5) and the plant operations network (Levels 0 through 3). Devices that belong in the DMZ include jump servers (for remote access to OT systems), historians that replicate data from Level 2 to the enterprise, patch distribution servers, and any file transfer mechanisms. The DMZ should permit no direct connections from Level 4/5 to Level 1/2. All cross-boundary traffic must pass through a DMZ intermediary. The attacker in Exercise 3.1 pivoted from the corporate web server directly into the OT network because no DMZ existed.

    3. The Purdue model was published in the 1990s. Is it still relevant for modern ICS environments that include cloud connectivity and remote access?

    Reveal answer

    The Purdue model's core principle (hierarchical trust zones with strict boundary enforcement) remains relevant even in cloud-connected environments. Modern extensions like IEC 62443 build on the same zone-and-conduit architecture. Cloud connectivity adds a new trust boundary above Level 5 that requires its own set of controls (encrypted tunnels, identity federation, API gateways). The model does not mandate physical separation at every level; logical segmentation via VLANs and firewalls satisfies the architecture. The model's value is the structured thinking it enforces, not the specific technology it prescribes.

    4. Your proposal includes authentication recommendations for Modbus, S7, and CIP. Which of these three protocols has the weakest native authentication support?

    Reveal answer

    Modbus TCP has no native authentication at all. The protocol specification includes no mechanism for the server to verify the identity of a client. Any device that can reach TCP/502 can read and write registers without credentials. S7comm has protection levels (as explored in Exercises 4.5 and 4.6) that provide varying degrees of write protection. CIP supports CIP Security (TLS-based authentication) on newer devices. Modbus environments must rely entirely on network-layer controls (firewalls, segmentation) because the protocol itself offers nothing.

    Defensive Recommendations to Masa

    Finding Risk Mitigation
    Flat network allows lateral movement between all three plants Critical Implement per-plant VLANs with inter-plant firewalls permitting only documented, protocol-specific traffic
    No IT/OT DMZ exists between corporate and plant networks Critical Deploy a Level 3.5 DMZ with jump servers for all remote OT access and historians for data replication
    Modbus, S7, and CIP endpoints accept connections from any source High Restrict each protocol port to authorized HMI and engineering workstation IPs via firewall rules
    No firmware update or patch management process for PLCs and RTUs High Establish a quarterly firmware review cycle with change control documentation and rollback procedures

    Key Takeaways

    • A segmentation proposal is the highest-value deliverable from an OT penetration test because it directly addresses the root cause of lateral movement
    • The Purdue model provides a standard vocabulary (Levels 0 through 5, DMZ at 3.5) that makes proposals readable by both IT and OT teams
    • Per-plant firewall rules must specify source, destination, port, and action. Generic statements like "add a firewall" are not actionable
    • Iterative submission against a rubric checker mirrors the real consulting workflow where clients review, reject, and request revisions on deliverables
    • Modbus has zero native authentication, making network segmentation the only effective access control for Plant 1
