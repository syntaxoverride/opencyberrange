    Exercise 1.1: First Contact

    Before You Begin

    Active Directory is the identity backbone of nearly every enterprise Windows environment in the world. Before you attack it, you must learn to read it. Exercise 1 gives you a single low-privileged credential and asks you to produce an organized inventory of the domain. No exploitation. No clever tricks. Just a clean, methodical first pass with the standard tools every consultant carries.

    You will work entirely from your Kali workstation. The target is a single Windows Server 2022 domain controller running corp.nordport.local plus one member file server. Both are reachable from your VPN.

    Tools required: rpcclient, ldapsearch, netexec (the modern fork of crackmapexec), smbclient, nmap. All are pre-installed on your Kali workstation.

    Scenario

    You are a junior consultant at Tidewater Security. Nordport Industries hired the firm to assess their Active Directory after a phishing-driven incident last quarter. Your senior consultant, Marcus Bell, has staged you on the Nordport corporate network with one set of credentials.

    Marcus's instructions are short: build a baseline picture before doing anything else. He wants to see your enumeration notes before you touch any further attack work. The flag for this exercise is concealed in the description field of one user account. Marcus is not going to tell you which user. Reading the directory thoroughly is the entire point.

    Credentials:

    Username Password Purpose
    j.chen Welcome2026# Standard low-privileged domain user (IT Help Desk)

    Domain: corp.nordport.local Domain controller hostname: corp-dc01

    Where Your Data Lives

    LDAP serves a hierarchical tree. Every account, group, and computer is a leaf or container under the domain root. The diagram below maps the directory you are about to read.

    flowchart TD
    Root["DC=corp,DC=nordport,DC=local"]
    Root --> Users["CN=Users<br/>(default container)"]
    Root --> Computers["CN=Computers"]
    Root --> IT["OU=IT"]
    Root --> Eng["OU=Engineering"]
    Root --> Fin["OU=Finance"]
    Root --> Svc["OU=ServiceAccounts"]
    Users --> DA["CN=Domain Admins (group)"]
    IT --> JC["CN=Jason Chen (user)<br/>sAMAccountName=j.chen"]

    Your Objectives

    • Authenticate to the domain as j.chen
    • Enumerate users, groups, organizational units, and computers
    • Read user attributes thoroughly (description, info, extensionAttribute1)
    • Find the flag in a single user's description field
    • Save your enumeration output for use in later exercises

    Background: How LDAP and AD Talk to You

    Active Directory exposes its data over the Lightweight Directory Access Protocol (LDAP). Every user, group, computer, organizational unit, and policy object is an LDAP entry under a hierarchical tree rooted at the distinguished name of the domain.

    For corp.nordport.local, the root DN is:

    DC=corp,DC=nordport,DC=local

    Every object has a fully qualified distinguished name (DN) that traces its location, for example:

    CN=Jason Chen,OU=IT,DC=corp,DC=nordport,DC=local

    Some attributes you will care about constantly:

    Attribute Meaning
    sAMAccountName The classic short username (e.g., j.chen)
    userPrincipalName The email-style logon name (e.g., j.chen@corp.nordport.local)
    description Free-form one-liner. Operators frequently leak credentials and notes here.
    info Free-form multi-line notes field. Often used internally by IT teams.
    userAccountControl Bit-flag integer that encodes account state (disabled, no preauth, password never expires, etc.).
    memberOf The groups this object belongs to.
    pwdLastSet Last password change time. Old timestamps signal stale accounts.
    lastLogonTimestamp Approximate last successful logon. Helps identify dormant accounts.
    servicePrincipalName List of SPNs registered against this account. Crucial for Kerberoasting.

    You do not need to memorize every attribute. You do need to know that all of this is readable by any authenticated domain user by default. That is a feature of AD, not a bug, and it is the foundation of every offensive recon technique in this track.

    Authentication shortcuts

    Most enumeration tools accept credentials in one of three forms:

    DOMAIN\username           -- NetBIOS-style
username@DOMAIN.tld       -- UPN-style
domain.tld/username       -- Impacket-style

    When in doubt, try j.chen@corp.nordport.local. It is the most universally accepted form.

    Tool Primer

    rpcclient

    A Samba utility that speaks the same Microsoft RPC interfaces the Windows tools use. You authenticate once, then issue interactive commands.

    rpcclient -U "CORP\j.chen%Welcome2026#" <dc_ip>

    The -U "DOMAIN\user%password" form bundles the credential inline. At the prompt, useful commands:

    Command Effect
    enumdomusers List all domain users with their RIDs
    enumdomgroups List all domain groups
    queryuser <rid> Detailed user info by RID
    querygroup <rid> Group details
    lsaenumsid Enumerate domain SIDs
    srvinfo Server info

    ldapsearch

    A pure LDAP client that returns raw attributes. Verbose, but it shows you exactly what is in the directory.

    ldapsearch -x -H ldap://<dc_ip> \
  -D "CORP\j.chen" -w 'Welcome2026#' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(objectClass=user)" sAMAccountName description info
    Flag Effect
    -x simple bind (over plaintext or TLS, not SASL)
    -H LDAP server URL
    -D bind DN (the user authenticating); DOMAIN\user works for AD
    -w password (use -W to be prompted instead)
    -b search base (the root of where the search starts)
    - The query (objectClass=user) returns user objects
    - The trailing attribute names limit the output to those fields

    netexec

    The modern, maintained fork of crackmapexec. It speaks SMB, LDAP, MSSQL, WinRM, RDP, FTP, SSH and presents results in clean tables.

    netexec ldap <dc_ip> -u j.chen -p 'Welcome2026#' -d corp.nordport.local --users

    Useful flags for this exercise:

    Flag Effect
    --users List all domain users in a clean table
    --groups List all groups
    --computers List all domain-joined computers
    --shares (over SMB) list shares
    --pass-pol Domain password policy

    smbclient

    Old-school SMB client. Not strictly an LDAP tool, but useful for listing shares and reading files.

    smbclient -L //<dc_ip>/ -U "j.chen%Welcome2026#"

    Walkthrough

    Step 1: Launch the Exercise

    Open the OpenCyberRange platform in your browser, navigate to the AD Penetration Track, and launch First Contact. Wait for the status to flip to Running. The Active Lab View shows two target IPs labeled corp-dc01 (DC) and file01.

    Note both IPs. For the rest of the walkthrough, replace <dc_ip> and <fileserver_ip> with the values shown.

    Step 2: Confirm the Targets Are Up

    Before authenticating, prove the targets respond and the expected services are listening. If port 389 (LDAP) or 445 (SMB) is closed, every other tool you reach for in this exercise will hang or refuse; better to find out now than after typing a 200-character ldapsearch command.

    We use nmap because it gives us four pieces of information per probe in one pass: is the port reachable, is something listening, what does the service banner look like, and how does the host respond to malformed packets.

    Kali - Verify domain controller services

    nmap -Pn -p 53,88,135,389,445,636,3268,5985 <dc_ip>

    What each option does:

    • -Pn skip ICMP host-discovery and assume the host is up. Required because most production firewalls drop ICMP, and even some lab nets do. Without -Pn, nmap silently skips hosts it cannot ping.
    • -p 53,88,135,389,445,636,3268,5985 scan ONLY these eight ports rather than the default 1000. Faster, and these are exactly the ports a Windows DC is supposed to expose: DNS (53), Kerberos (88), RPC endpoint mapper (135), LDAP (389), SMB (445), LDAPS (636), Global Catalog (3268), WinRM-HTTP (5985).
    • <dc_ip> target IP shown in the lab dashboard.

    Read the output line by line. Each port should show STATE open. The presence of port 88 + 389 together is the canonical "this is an Active Directory Domain Controller" fingerprint; no other Windows role co-exposes both. WinRM (5985) confirms remote-management is enabled, which we will use in later exercises.

    Kali - Verify file server

    nmap -Pn -p 445,5985 <fileserver_ip>

    Same flags. Smaller port list because file01 is a member server, not a DC; only SMB and WinRM are expected to be open.

    Step 3: First Authenticated Touch

    Before pulling thousands of LDAP records, prove the credential actually works. A bad password against AD will silently lock the account if you exceed the lockout threshold (5 failures in 15 min on this domain). Validating once with netexec gives you a definitive yes/no without burning attempts in a heavier tool.

    Kali - Validate the j.chen credential against SMB

    netexec smb <dc_ip> -u j.chen -p 'Welcome2026#' -d corp.nordport.local

    What each option does:

    • smb the protocol module. netexec ships modules for smb, ldap, winrm, mssql, rdp, ftp, ssh, vnc. Each speaks the protocol natively and surfaces clean tabular output.
    • <dc_ip> target IP. netexec accepts a single IP, a CIDR range (10.0.0.0/24), or a file (-t hosts.txt).
    • -u j.chen username (no domain prefix; the -d flag adds it).
    • -p 'Welcome2026#' password. Quote it so # (a shell comment marker) and ! (history expansion) do not get eaten by bash.
    • -d corp.nordport.local domain realm. Required for Kerberos-aware operations and for proper user-principal-name construction.

    What the output tells you:

    • [+] prefix on the line means authentication succeeded. [-] means failed.
    • (name:DOCKERW-...) is the host's NetBIOS name.
    • (domain:corp.nordport.local) is the FQDN.
    • (signing:True) is the SMB signing requirement: the server demands signed messages. Important to know; it affects whether NTLM relay attacks work later.
    • (SMBv1:None); SMBv1 is disabled (modern best practice).
    • (Null Auth:True); anonymous (null-session) bind is allowed for SOME operations. Doesn't mean every share is reachable anonymously, just that the protocol negotiation succeeds.

    If you see [-] STATUS_LOGON_FAILURE: wrong password. If you see [-] STATUS_ACCOUNT_LOCKED_OUT: the account is locked from prior failed attempts; wait 30 min for the policy to reset.

    Step 4: Enumerate Domain Users

    Three tools, three different views of the same directory. They are not redundant; each surfaces something the others hide. Run all three and compare.

    4a. rpcclient interactive; RPC view

    rpcclient is a Samba utility that speaks the same MS-RPC interfaces Windows tools use. It connects once, then accepts interactive commands at a rpcclient $> prompt. RPC enumeration was the original way Windows administrators listed users before LDAP became dominant; many old Microsoft tools (and some still-used third-party AV products) still hit these RPC endpoints.

    Kali - rpcclient interactive enumeration

    rpcclient -U "CORP\j.chen%Welcome2026#" <dc_ip>

    What each option does:

    • -U "CORP\j.chen%Welcome2026#" bundles credentials in DOMAIN\user%password form. The \ is escaped to bash; PowerShell-style \\ not needed because we're in a quoted string. Alternative form: -U j.chen%Welcome2026# -W CORP.
    • <dc_ip> target. rpcclient uses port 445 (SMB) to negotiate the RPC interface.

    Once you see the rpcclient $> prompt, issue commands one at a time:

    enumdomusers
enumdomgroups
querydominfo
exit

    What each does:

    • enumdomusers; calls SAMR EnumDomainUsers. Returns a numeric RID (relative ID, the last segment of the user's SID) and the sAMAccountName for every user in the domain. The RID is a stable handle that survives renames; useful when you need to reference a user by its SID later.
    • enumdomgroups; calls SAMR EnumDomainGroups. Same idea for groups.
    • querydominfo; returns domain-wide metadata: domain SID, role of the host you connected to (DC vs. member), domain server type flags. The domain SID prefix (S-1-5-21-XXXX-YYYY-ZZZZ) is what every per-user/per-group SID is derived from; copy it down for later.
    • exit; quit the prompt cleanly.

    Common gotcha: the ? command at the prompt lists all available rpcclient subcommands (~150 of them). Unix-style commands like ls do NOT work here; this is rpcclient's own tiny shell.

    4b. ldapsearch for full attributes; the canonical view

    ldapsearch is a pure LDAP client that returns raw attributes. Verbose output, but it shows you exactly what the directory holds. As a raw client, ldapsearch hides nothing; every other AD tool is a wrapper around this same protocol.

    Kali - Pull every user's description and info via LDAP

    ldapsearch -x -LLL -H ldap://<dc_ip> \
  -D "CORP\j.chen" -w 'Welcome2026#' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(objectClass=user)" sAMAccountName description info \
  > users_attrs.txt

    What each option does:

    • -x use simple bind (username + password over the wire) instead of SASL (which would require a Kerberos ticket). Simple is fine over LDAP-over-TLS or inside a trusted lab; in production prefer SASL/GSSAPI.
    • -LLL strip LDIF format noise: no version line, no comments, no blank trailing line. Stripping the noise makes the output easy to grep. The flag is literally three Ls.
    • -H ldap://<dc_ip> LDAP URL. Use ldaps:// for the encrypted variant on port 636.
    • -D "CORP\j.chen" bind DN, the identity authenticating. AD accepts both DOMAIN\user and full DN syntax (CN=Jason Chen,OU=IT,DC=corp,DC=nordport,DC=local); the short form is friendlier.
    • -w 'Welcome2026#' password literal. Use -W instead to be prompted (more secure if anyone is shoulder-surfing).
    • -b "DC=corp,DC=nordport,DC=local" search base; the root of the subtree to search. The pattern DC=x,DC=y,DC=z mirrors the dotted FQDN x.y.z reversed.
    • "(objectClass=user)" LDAP search filter. Returns only objects whose objectClass includes user (which means User AND Computer accounts; computers also have objectClass: user for legacy reasons).
    • sAMAccountName description info attribute list. Without this, ldapsearch returns ALL attributes per object (~50+ each) which makes the dump enormous. Listing specific attributes keeps the output tight.
    • > users_attrs.txt redirect output to a file so you can grep without re-running the query.

    Once the file is written, search for the flag pattern. We filter to description: lines specifically because for Exercise 1.1 the flag lives there:

    Kali - Search the LDAP dump for the flag pattern in description

    grep -B1 -E '^description:.*OCR\{' users_attrs.txt

    What each option does:

    • -B1 print one line of context BEFORE each match. Because LDIF orders attributes and the sAMAccountName for an entry comes immediately before its description, this lets you see WHICH user the flag belongs to.
    • -E interpret the pattern as extended regex (so \{ is a literal brace).
    • '^description:.*OCR\{' match lines that start with description: and contain OCR{ somewhere. The ^ anchors to start-of-line so we ignore description appearing as substring elsewhere.

    The grep returns the user whose description field contains this exercise's OCR{...} flag. Take note of both the username (the matching sAMAccountName line above) and the flag itself.

    Note on multiple flags: as you enumerate the directory you may encounter OCR{...} strings in other attributes (e.g. info) on different user objects. Those belong to LATER exercises and the platform will reject them here. The 1.1 flag lives ONLY in the description field of a user account. The flag value itself encodes the exercise theme (something like OCR{<welcome>_<to>_<the>_<domain>} in leetspeak, clearly orientation-related) so you can sanity-check before submitting.

    4c. netexec for tabular output; the operator's friend

    netexec is the modern fork of crackmapexec (which itself replaced the older cme). Same data as ldapsearch, formatted as a clean table you can scroll. Use it as a sanity check after the LDAP dump and as your daily driver for ad-hoc enumeration.

    Kali - Tabular user list with netexec

    netexec ldap <dc_ip> -u j.chen -p 'Welcome2026#' -d corp.nordport.local --users \
  | tee users_table.txt

    What each option does:

    • ldap protocol module; netexec also has SMB, WinRM, MSSQL etc. Choosing ldap connects on port 389/636 and uses LDAP-native enumeration paths.
    • <dc_ip> target.
    • -u/-p/-d same meaning as the SMB call earlier.
    • --users request the user list. Other useful flags on the LDAP module: --groups, --computers, --pass-pol (domain password policy), --asreproast (find DONT_REQ_PREAUTH users), --kerberoasting (find SPN-bearing accounts).
    • | tee users_table.txt pipe stdout to both the terminal AND a file. tee lets you watch progress live while preserving the output for later reuse.

    What the columns mean:

    • sAMAccountName; the short username.
    • pwdLastSet; when the password was last changed. Old timestamps signal stale or service accounts.
    • lastLogon; last successful authentication. Empty or very old means dormant accounts (high-value spray targets in Level 3).
    • memberOf (with --groups modifier); what groups the user is in.

    Save the file. The full user list is the foundation for later password-spray exercises (Level 3.4) and for BloodHound's SharpHound collector (Level 1.2).

    Step 5: Enumerate Groups

    Groups in AD govern privileges. Knowing the group landscape now will save you hours later when BloodHound asks you to interpret an attack path.

    Kali - List all groups

    netexec ldap <dc_ip> -u j.chen -p 'Welcome2026#' -d corp.nordport.local --groups

    Same flags as before; --groups swaps the LDAP filter that netexec sends from (objectClass=user) to (objectClass=group) and prints results in a tabular format.

    What to look for in the output:

    • Anything ending in Admins; these grant elevated rights somewhere. Domain Admins and Enterprise Admins are the obvious Tier-0 prizes.
    • Anything starting with Tier; Microsoft's own tiered-administration model uses Tier0_Admins, Tier1_Admins, Tier2_Admins. Mature shops follow this convention.
    • The built-ins: Schema Admins, Backup Operators, Server Operators, Account Operators. These are sleeper paths to Domain Admin equivalence; non-empty membership is suspicious.
    • Any group with a name suffix like _<token> (e.g. Backup_Operators_j001). Those are per-student per-exercise groups; you will see them in later levels.

    To see who belongs to a specific group, use a custom LDAP filter. The interesting bit here is the OID:

    Kali - Members of Domain Admins (transitive)

    netexec ldap <dc_ip> -u j.chen -p 'Welcome2026#' -d corp.nordport.local \
  --query "(memberof:1.2.840.113556.1.4.1941:=CN=Domain Admins,CN=Users,DC=corp,DC=nordport,DC=local)" \
  sAMAccountName

    What each piece of the query does:

    • --query "..." send a custom LDAP filter rather than netexec's built-in shortcut.
    • (memberof:1.2.840.113556.1.4.1941:=...) the matching rule. The OID 1.2.840.113556.1.4.1941 is LDAP_MATCHING_RULE_IN_CHAIN, more commonly called the "transitive membership" matching rule. Without this OID, the memberof attribute returns only DIRECT members of the group; with it, you also get members of nested groups.
    • The right-hand side after := is the full DN of the target group. Domain Admins lives in CN=Users (the legacy Users container, not an OU) so the DN is CN=Domain Admins,CN=Users,DC=corp,DC=nordport,DC=local.
    • sAMAccountName trailing argument restricts the returned attributes to just the username.

    Why memorize this OID: every time you ask "is X transitively a member of group Y?" in AD, this is the answer. Real engagements hit it multiple times per day. There are exactly two AD matching-rule OIDs worth remembering: 1.2.840.113556.1.4.1941 (in chain) and 1.2.840.113556.1.4.803 (bitwise AND, used for userAccountControl flag tests in later exercises).

    Step 6: Enumerate Organizational Units

    OUs are the organizational containers AD uses to group objects for delegation, GPO targeting, and audit scope. Knowing the OU layout tells you where the high-value populations live (admins, service accounts, HR data) before you spend time enumerating every user.

    Kali - List OUs

    ldapsearch -x -LLL -H ldap://<dc_ip> \
  -D "CORP\j.chen" -w 'Welcome2026#' \
  -b "DC=corp,DC=nordport,DC=local" \
  "(objectClass=organizationalUnit)" name distinguishedName

    What changed from the user query:

    • "(objectClass=organizationalUnit)"; different filter, same syntax. Returns only OU objects.
    • name distinguishedName; we want only the name and the full DN per OU. The DN reveals the nesting (e.g. OU=Engineering,DC=corp,... is top-level; OU=Build,OU=Engineering,DC=corp,... would be nested under Engineering).

    Read the output and sketch the tree on paper. Nordport's OU structure mirrors the company org chart: Engineering, Finance, HR, Operations, IT, ServiceAccounts. Each OU has different account types and different threat models. ServiceAccounts is where the noisy crackable accounts live; IT is where the privileged humans live.

    Step 7: Enumerate Computers

    Computer objects in AD represent every domain-joined machine; workstations, member servers, DCs themselves. Each computer has a machine account with a 240-byte random password that rotates every 30 days. From an offensive perspective, computer enumeration tells you where to focus reconnaissance after the initial directory dump: which hosts run interesting services, which are running old or unusual OSes, which look like servers vs workstations.

    Kali - List domain computers

    netexec ldap <dc_ip> -u j.chen -p 'Welcome2026#' -d corp.nordport.local --computers

    --computers swaps the filter to (objectClass=computer) and includes the OS string in the output.

    What the columns mean:

    • Hostname; short NetBIOS name of the machine.
    • operatingSystem; version string. Server 2008 / Windows 7 / etc. surface here. Old OS versions are over-represented in pwnage statistics because they lack modern memory protections, secure boot, and recent security patches.
    • operatingSystemVersion; build number (e.g. 10.0 (20348) for Server 2022 21H2).
    • dnsHostName; the FQDN. Use this rather than the short name when crafting Kerberos service tickets later.

    Save the output. The list of domain-joined hosts becomes your target inventory for everything from RDP testing to LAPS retrieval to RBCD targeting in Level 4.

    Step 8: Submit the Flag

    Take the OCR{...} value you discovered in Step 4b and paste it into the Submit Flag form on the platform.

    Blue Team Perspective

    Authenticated LDAP enumeration is hard to detect because it looks like normal directory traffic. Defenders rely on volume thresholds and on flagging atypical attribute patterns rather than blocking the queries outright. The table below maps each tool you ran to the events a SOC analyst could pivot on.

    Activity Windows event Log location
    LDAP bind from j.chen 4624 (logon type 3), 4662 DC Security log
    Bulk SAMR enumeration via rpcclient 4661 (handle to SAM), 4662 DC Security log
    Wide LDAP queries ((objectClass=user)) LDAP Diagnostic event 1644 DC Directory Services log
    netexec SMB probe 4624, 4625, 5140 DC and member-server Security log

    What gets noticed first

    SOC tooling does not usually alert on individual reads, but BloodHound-style collection lights up Microsoft Defender for Identity ("Reconnaissance using directory services queries") within seconds because the collector pulls thousands of attributes back to back. Pacing your queries lower and using attribute-scoped filters (the way ldapsearch ... sAMAccountName description info does) tends to stay under behavioral baselines.

    Hardening Note

    Defenders rarely block authenticated reads because doing so breaks legitimate clients, but they can shrink the blast radius. A reasonable hardening checklist includes the points below.

    Practical mitigations

    • Set dsHeuristics bit 0 to 1 to disable anonymous LDAP bind on the forest root.
    • Audit and clear all description, info, and extensionAttribute* fields for embedded credentials with a scheduled scan.
    • Add deny ACEs on the Authenticated Users principal for sensitive OUs (e.g., Tier 0 admin OU) so low-privileged enumeration cannot read them.
    • Enable Microsoft Defender for Identity on every domain controller; it baselines normal LDAP volumes per identity and pages on outliers.
    • Send DC Security logs and event 1644 to your SIEM with retention long enough to catch slow-burn recon (30+ days).

    Analysis Questions

    1. Why does any authenticated domain user have read access to so many attributes on every other user, group, and computer in the domain?

    Reveal Answer

    Active Directory is designed as an identity service. By default, every authenticated user can read most of the directory because the directory itself is what tells clients where to find services, who is in what group, and how to authenticate. If reads required elevated privilege, ordinary domain logon would not work. The default ACLs on AD objects grant Authenticated Users read on most attributes, including description, memberOf, userAccountControl, and servicePrincipalName. That permissive default is why offensive enumeration is so productive in default-configured AD environments. Locking down read access is possible (delegated OUs, custom ACLs) but rarely done because it breaks legitimate tooling.

    2. You found a credential leaked in a description field. What other attributes commonly leak similar information, and where else in AD do operators historically leak credentials?

    Reveal Answer

    Common attribute-level leaks: description, info, comment, and the extensionAttribute1 through extensionAttribute15 fields used by some HRIS sync products. The userParameters and userPassword (legacy) fields are also worth searching. Outside of attributes, the classic leak locations are: SYSVOL Groups.xml (GPP cpassword); SYSVOL scripts (logon scripts hardcoding service account credentials); SMB shares (especially anything called IT-Tools, Helpdesk, or Onboarding); the WSUS configuration on management servers; LAPS attributes if the requesting account has the wrong delegations; and machine account passwords in restored backups. The pattern: any place where humans wrote text that machines read.

    3. The userAccountControl attribute is a 32-bit integer that encodes a dozen account flags. Which two flags would make your day if you saw them set on a user?

    Reveal Answer

    DONT_REQ_PREAUTH (0x400000, decimal 4194304) means the account does not require Kerberos pre-authentication, which makes it ASREPRoastable from any unauthenticated context. TRUSTED_FOR_DELEGATION (0x80000, decimal 524288) means the account is configured for unconstrained delegation; if you can compromise that account, you can capture TGTs of any user who authenticates to it. Both are findable with one LDAP query each: (userAccountControl:1.2.840.113556.1.4.803:=4194304) for ASREPRoast candidates, (userAccountControl:1.2.840.113556.1.4.803:=524288) for unconstrained delegation. Memorize these two queries; you will run them on every engagement.

    Key Takeaways

    • Authenticated domain users can read most of the directory by default. Enumeration is the highest-leverage activity at the start of any AD engagement.
    • rpcclient, ldapsearch, and netexec give you three different views of the same data; use all three.
    • The description, info, and extensionAttribute* fields are common credential-leak surfaces.
    • The transitive group membership LDAP OID (1.2.840.113556.1.4.1941) returns nested members, not just direct ones.
    • The root DN format DC=corp,DC=nordport,DC=local mirrors the dotted FQDN; you will write this string a lot, so commit it to muscle memory.

    Cheat Sheet Recap

    The five commands below cover most first-touch enumeration on any engagement. Pin this card; you will reuse it on every box from Level 1 through the capstones.

    Goal Command
    Validate creds and probe SMB netexec smb <dc> -u <user> -p '<pw>' -d <domain>
    Tabular user list netexec ldap <dc> -u <user> -p '<pw>' -d <domain> --users
    Raw user attributes (descriptions, info) ldapsearch -x -LLL -H ldap://<dc> -D "<DOMAIN>\<user>" -w '<pw>' -b "<DN>" "(objectClass=user)" sAMAccountName description info
    Members of Domain Admins (transitive) netexec ldap <dc> -u <user> -p '<pw>' -d <domain> --query "(memberof:1.2.840.113556.1.4.1941:=CN=Domain Admins,CN=Users,<DN>)" sAMAccountName
    Find ASREPRoast candidates netexec ldap <dc> -u <user> -p '<pw>' -d <domain> --query "(userAccountControl:1.2.840.113556.1.4.803:=4194304)" sAMAccountName

    Spaced Repetition

    Card 1: Domain User LDAP Bind

    Q: Write the full ldapsearch command to authenticate to corp.local at 10.10.10.10 as j.smith with password Pass123# and return every user's sAMAccountName and description.

    Answer 
    ldapsearch -x -LLL -H ldap://10.10.10.10 \
  -D "CORP\j.smith" -w 'Pass123#' \
  -b "DC=corp,DC=local" \
  "(objectClass=user)" sAMAccountName description

    The -x flag forces simple bind. -LLL strips LDIF version noise. The bind DN can also be the UPN form j.smith@corp.local.

    Card 2: rpcclient User Enumeration

    Q: After rpcclient -U "CORP\user%pass" 10.10.10.10 succeeds, name three commands that produce useful enumeration output.

    Answer

    enumdomusers lists every domain user with RID. enumdomgroups lists every group. querydominfo returns domain metadata including the SID and the role of the host you are talking to. Bonus: lsaenumsid enumerates SIDs of all object types.

    Card 3: Transitive Group Membership Filter

    Q: What is the LDAP OID that converts a memberof filter into a transitive (nested) match, and what is the full filter to find every user who is transitively in Domain Admins of corp.local?

    Answer

    OID: 1.2.840.113556.1.4.1941. Filter: (memberof:1.2.840.113556.1.4.1941:=CN=Domain Admins,CN=Users,DC=corp,DC=local). Without the OID, you only get direct members; with it, you get members of nested groups too.

    Card 4: Two userAccountControl Flags Worth Memorizing

    Q: Name the two userAccountControl flag values most worth searching for, what they enable, and the LDAP filter for each.

    Answer

    4194304 (DONT_REQ_PREAUTH) makes the account ASREPRoastable. Filter: (userAccountControl:1.2.840.113556.1.4.803:=4194304). 524288 (TRUSTED_FOR_DELEGATION) makes the account configured for unconstrained delegation. Filter: (userAccountControl:1.2.840.113556.1.4.803:=524288). The OID 1.2.840.113556.1.4.803 is the bitwise-AND match operator.

    Card 5: netexec One-Liner User List

    Q: Write the netexec command that produces a clean tabular list of all domain users for corp.local at 10.10.10.10 using credentials j.smith / Pass123#.

    Answer 
    netexec ldap 10.10.10.10 -u j.smith -p 'Pass123#' -d corp.local --users

    Swap --users for --groups, --computers, or --pass-pol for the matching enumerations.
