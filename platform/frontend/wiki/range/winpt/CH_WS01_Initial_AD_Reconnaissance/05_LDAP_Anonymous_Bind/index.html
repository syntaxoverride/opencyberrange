    Exercise WS-1.5: LDAP Anonymous Bind Reconnaissance

    Before You Begin

    Exercises WS-1.1 through WS-1.4 established the DC's identity through port scanning, DNS enumeration, and SMB queries. Exercise WS-1.5 completes the unauthenticated reconnaissance phase by querying LDAP (Lightweight Directory Access Protocol) on port 389; the protocol that provides direct access to the Active Directory database.

    Prerequisites:

    • Exercises WS-1.1 through WS-1.4 completed
    • Active VPN connection to the Open Cyber Range
    • The ldapsearch command available on your Kali Linux attack box (part of the ldap-utils package)

    Scenario

    Your reconnaissance has revealed that LDAP (port 389) is open on dc01. LDAP is the primary protocol for querying Active Directory. If anonymous binds are permitted, an attacker can extract the directory structure; including the base Distinguished Name (DN), naming contexts, and domain-level attributes; without providing any credentials. Your task is to determine whether anonymous LDAP access is allowed and to extract as much directory information as possible.

    Your Objectives

    1. Perform an anonymous LDAP bind against dc01
    2. Extract the Root DSE (Directory Server Agent-Specific Entry) to discover the base DN and naming contexts
    3. Query domain-level attributes for additional information
    4. Retrieve the flag from an LDAP attribute on the domain root object

    Background: LDAP and the Active Directory Database

    Active Directory stores its data in a hierarchical database accessed primarily through LDAP. Every object in the directory; users, computers, groups, organizational units; has a Distinguished Name (DN) that specifies its location in the hierarchy. For example, a user named "jsmith" in the "Users" container of the corp.ocr-range.lab domain has the DN:

    CN=jsmith,CN=Users,DC=corp,DC=ocr-range,DC=lab

    The base of the hierarchy is the domain's root DN, which is derived from the domain name. For corp.ocr-range.lab, the root DN is DC=corp,DC=ocr-range,DC=lab. Every LDAP query starts from a base DN and searches downward through the tree.

    An anonymous bind connects to the LDAP server without authentication. By default, Windows Server 2003 and later restrict anonymous LDAP queries to the Root DSE (also called the rootDSE); a special entry at the top of the directory that describes the server's capabilities. The rootDSE contains the base DN, the naming contexts (the top-level partitions of the directory), the LDAP version supported, and other metadata.

    When anonymous binds are configured more permissively (a misconfiguration), the attacker can query beyond the rootDSE and enumerate user accounts, group memberships, computer objects, and other directory data without credentials.

    Tool Primer: ldapsearch

    The ldapsearch command queries LDAP directories from the command line. The tool is part of the OpenLDAP utilities (ldap-utils package on Debian/Kali).

    Basic syntax for an anonymous query:

    ldapsearch -x -H ldap://<target> -b "<base-dn>" -s <scope> "<filter>" [attributes]
    Flag Purpose
    -x Use simple authentication (required for anonymous binds)
    -H ldap://<target> The LDAP server URI
    -b "<base-dn>" The base DN to start the search from
    -s <scope> Search scope: base (single object), one (immediate children), sub (entire subtree)
    "<filter>" LDAP search filter (e.g., "objectClass=*" matches everything)
    [attributes] Optional list of specific attributes to return

    To query the rootDSE, use an empty base DN (-b "") with base scope (-s base):

    ldapsearch -x -H ldap://dc01 -b "" -s base "objectClass=*"

    The rootDSE response includes several important attributes:

    Attribute What It Reveals
    defaultNamingContext The domain's base DN (e.g., DC=corp,DC=ocr-range,DC=lab)
    rootDomainNamingContext The forest root domain's base DN
    configurationNamingContext The configuration partition DN
    schemaNamingContext The schema partition DN
    namingContexts All naming contexts (partitions) in the directory
    dnsHostName The FQDN (Fully Qualified Domain Name) of the DC
    ldapServiceName The Kerberos service principal name

    Walkthrough

    Step 1: Query the Root DSE

    Query the Root DSE with an anonymous bind

    Run the following command to perform an anonymous bind and retrieve the rootDSE from dc01.

    ldapsearch -x -H ldap://dc01 -b "" -s base "objectClass=*"

    The output contains the server's metadata attributes. Look for defaultNamingContext, namingContexts, and dnsHostName in the response. The defaultNamingContext value is the base DN you will need for all subsequent LDAP queries in this exercise and in future labs.

    A typical rootDSE response includes lines similar to the following:

    defaultNamingContext: DC=corp,DC=ocr-range,DC=lab
configurationNamingContext: DC=Configuration,DC=corp,DC=ocr-range,DC=lab
dnsHostName: dc01.corp.ocr-range.lab
...
(additional attributes omitted; review your own output for the full list)

    Step 2: Request Only the Naming Contexts

    Request only the naming contexts

    You can request specific attributes to reduce the output. Run the following command to retrieve only the naming contexts.

    ldapsearch -x -H ldap://dc01 -b "" -s base "objectClass=*" namingContexts

    The output should list all five naming contexts. Each naming context represents a separate partition of the Active Directory database:

    • Domain partition (DC=corp,DC=ocr-range,DC=lab); Contains users, groups, computers, and OUs (Organizational Units)
    • Configuration partition: Contains site topology, service connection points, and replication settings
    • Schema partition: Defines the classes and attributes available in the directory
    • DomainDnsZones: Holds DNS zone data for the domain
    • ForestDnsZones: Holds DNS zone data replicated across the entire forest

    Step 3: Query the Domain Root Object

    Query the domain root object

    Use the base DN from Step 1 to query the domain root object. The domain root is the top-level object in the domain partition and contains domain-wide attributes.

    ldapsearch -x -H ldap://dc01 -b "DC=corp,DC=ocr-range,DC=lab" -s base "objectClass=*"

    The output shows all attributes of the domain root object. Look for attributes like distinguishedName, objectClass, whenCreated, and any custom attributes that may have been set by the administrator.

    Step 4: Query for the adminDescription Attribute

    Query the adminDescription attribute

    The adminDescription attribute on the domain root object is a free-text field that administrators sometimes use for documentation. Query the attribute specifically.

    ldapsearch -x -H ldap://dc01 -b "DC=corp,DC=ocr-range,DC=lab" -s base "objectClass=*" adminDescription

    The output should include the adminDescription attribute with its value. The flag for this exercise is stored in the adminDescription attribute of the domain root object.

    Step 5: Interpret the Results

    The LDAP queries you performed reveal the internal structure of the Active Directory database. Consider the following as you review your findings:

    • The defaultNamingContext is the starting point for all directory queries. Every search for users, groups, or computers in the domain begins at the base DN: DC=corp,DC=ocr-range,DC=lab.
    • The five naming contexts represent the partitions of the AD database. Each partition replicates independently, and some partitions (Configuration, Schema) replicate across the entire forest, not a single domain.
    • The dnsHostName attribute confirms the FQDN of the DC, matching the information you obtained from DNS in earlier labs. Cross-referencing data from multiple protocols strengthens your confidence in the findings.
    • The fact that the adminDescription attribute was readable through an anonymous bind is a misconfiguration. In a hardened environment, anonymous binds should be limited to the rootDSE only.

    Step 6: Find and Submit the Flag

    The adminDescription attribute query in Step 4 returned the flag for this exercise. Enter the value in OCR{...} format on the submission page.

    Analysis Questions

    1. What is the Root DSE, and why is it always accessible through an anonymous bind?

    Reveal Answer

    The Root DSE (rootDSE) is a special LDAP entry with an empty DN that describes the capabilities and configuration of the LDAP server. Microsoft's implementation of LDAP in Active Directory exposes the rootDSE to anonymous clients by design because client applications need the information to construct proper LDAP queries; specifically the base DN and supported LDAP versions. Without rootDSE access, a client would need to know the base DN in advance, which limits interoperability.

    2. What is the difference between the defaultNamingContext and the configurationNamingContext?

    Reveal Answer

    The defaultNamingContext points to the domain partition, which contains the domain's user accounts, computer accounts, groups, organizational units, and Group Policy Objects. The configurationNamingContext points to the configuration partition, which contains forest-wide settings: site definitions, subnet-to-site mappings, replication topology, and service connection points. The domain partition is unique to each domain, while the configuration partition is replicated across every DC in the forest.

    3. How could a defender detect anonymous LDAP enumeration?

    Reveal Answer

    Defenders can enable LDAP diagnostic logging on the Domain Controller (Event IDs 2889 and 2887 in the Directory Services event log track unsigned and unencrypted LDAP binds, including anonymous ones). Network monitoring tools can flag LDAP traffic from non-domain-joined IP addresses. Configuring the DC to require LDAP signing (LDAPServerIntegrity = 2) forces clients to authenticate, although the rootDSE remains accessible. Disabling anonymous LDAP access beyond the rootDSE is the most direct mitigation.

    4. Why is the base DN (DC=corp,DC=ocr-range,DC=lab) derived from the domain's DNS name?

    Reveal Answer

    Active Directory tightly integrates with DNS. When a new AD domain is created, the installer converts the DNS domain name into LDAP naming components by splitting the name at each dot and prefixing each component with DC=. The domain corp.ocr-range.lab becomes DC=corp,DC=ocr-range,DC=lab. The consistent naming convention means an attacker who knows the DNS domain name can immediately construct the LDAP base DN without querying the rootDSE first.

    Key Takeaways

    • Anonymous LDAP binds are permitted against the rootDSE by default on all Active Directory Domain Controllers. The rootDSE reveals the base DN, naming contexts, and server capabilities.
    • The base DN (DC=corp,DC=ocr-range,DC=lab) is the starting point for all LDAP queries against the domain partition. Knowing the base DN is a prerequisite for user and group enumeration in later exercises.
    • Five naming contexts exist in a standard AD forest: domain, configuration, schema, DomainDnsZones, and ForestDnsZones. Each partition serves a different purpose and replicates independently.
    • Misconfigured anonymous access can expose domain-level attributes (like adminDescription) that should require authentication. Defenders should restrict anonymous LDAP queries to the rootDSE.
    • ldapsearch is the standard command-line tool for LDAP queries. The -x flag enables simple (anonymous) authentication, -b sets the search base, and -s base restricts the query to a single object.
    • Exercise WS-1.5 completes the unauthenticated reconnaissance phase. You have surveyed the DC from five angles: port scanning, forward DNS, reverse DNS, SMB, and LDAP. Chapter WS02 will build on this foundation with authenticated enumeration techniques.
