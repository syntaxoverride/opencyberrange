    Exercise WS-3.1: SRV Record Discovery

    Before You Begin

    Active Directory relies on DNS more than any other service. If you completed the WS01 DNS labs, you already know how to query A records and basic zone data. Exercise WS-3.1 goes deeper by querying SRV (Service) records; the mechanism AD uses to advertise Domain Controllers, Kerberos servers, and Global Catalog endpoints.

    • Confirm your VPN connection is active and you can reach dc01.
    • No credentials are needed for DNS queries; all SRV records are publicly resolvable within the domain.
    • You should be comfortable running dig commands from a Linux terminal.

    Scenario

    Your security team is assessing the corp.ocr-range.lab Active Directory (AD) environment. The domain controller dc01 runs Windows Server 2022 and hosts the primary DNS zone. AD-integrated DNS contains SRV (Service Location) records that domain-joined clients query to locate critical infrastructure; Kerberos Key Distribution Centers (KDCs), Lightweight Directory Access Protocol (LDAP) servers, and Global Catalog (GC) endpoints. Your task is to enumerate these standard SRV records and determine whether any non-standard SRV entries exist that might reveal undocumented services.

    Your Objectives

    • Query standard AD SRV records for Kerberos, LDAP, and Global Catalog services
    • Understand the SRV record format and what each field communicates
    • Discover non-standard SRV records that may expose hidden services
    • Follow the chain from a non-standard SRV entry to retrieve the flag

    Background: SRV Records in Active Directory

    DNS SRV records define the location of servers for specific services. Unlike A records that map hostnames to IP addresses, SRV records map a service name to a host, port, priority, and weight. Every AD domain creates SRV records automatically when a Domain Controller is promoted. Without these records, domain-joined clients cannot locate the services they need to authenticate and function.

    The SRV record format follows a specific naming convention:

    _service._protocol.domain.  TTL  IN  SRV  priority  weight  port  target

    Each field serves a distinct purpose. The _service label identifies what the record advertises (such as _kerberos or _ldap). The _protocol label specifies TCP or UDP. Priority and weight allow administrators to control failover and load balancing when multiple servers provide the same service. The target field contains the fully qualified domain name (FQDN) of the server hosting that service.

    AD creates several well-known SRV records during domain controller promotion. The three most significant categories are Kerberos authentication (_kerberos._tcp), LDAP directory services (_ldap._tcp), and Global Catalog lookups (_gc._tcp). Querying these records reveals every DC in the domain, including DCs in child domains or sites. Penetration testers use SRV enumeration to build a list of high-value targets without scanning a single port.

    Non-standard SRV records present a different opportunity. Administrators sometimes create custom SRV entries for internal applications, monitoring systems, or services that need automated discovery. These records may not appear in documentation, but they are visible to anyone who can query DNS. A non-standard SRV record is a signpost pointing to infrastructure the organization may have forgotten about.

    Tool Primer: dig for SRV Queries

    The dig (Domain Information Groper) command is a DNS lookup tool that supports all standard record types. Querying SRV records requires specifying the record type explicitly.

    Syntax for SRV queries:

    dig SRV _service._protocol.domain @nameserver

    Key flags and options:

    Option Purpose
    SRV Specifies the query type as SRV
    TXT Specifies the query type as TXT (text records)
    @nameserver Directs the query to a specific DNS server
    +short Returns only the answer, no extra sections
    +noall +answer Shows only the answer section with full detail

    Sample SRV output:

    ;; ANSWER SECTION:
_kerberos._tcp.corp.ocr-range.lab. 600 IN SRV 0 100 88 dc01.corp.ocr-range.lab.

    Reading left to right: the service is Kerberos over TCP in the corp.ocr-range.lab domain. The Time to Live (TTL) is 600 seconds. The priority is 0 (highest), the weight is 100, the port is 88, and the target server is dc01.corp.ocr-range.lab. Kerberos uses port 88 by default, so the SRV record confirms dc01 is the KDC for the domain.

    Sample TXT output:

    ;; ANSWER SECTION:
example.corp.ocr-range.lab. 600 IN TXT "some text value here"

    TXT records store arbitrary text strings. Administrators use them for SPF records, domain verification, and occasionally for storing metadata. In a lab context, TXT records may contain flags or clues.

    Walkthrough

    Step 1: Launch the Lab and Verify Connectivity

    Navigate to Exercises, then Windows Server, then Level 3, and launch Exercise WS-3.1. Wait for the environment status to show Running and note the target information. The target for all DNS queries is dc01 at corp.ocr-range.lab.

    Verify DNS connectivity to dc01

    Verify you can reach the DNS server with a simple A record lookup. The +short flag trims the output to just the answer so you can confirm resolution at a glance.

    dig +short A dc01.corp.ocr-range.lab @dc01

    You should receive an IP address in response. If the query times out, check your VPN connection before proceeding.

    Step 2: Query Kerberos SRV Records

    Kerberos is the primary authentication protocol for AD. Every DC runs a Kerberos KDC on port 88. Querying the _kerberos._tcp SRV record reveals which servers handle authentication for the domain.

    Query Kerberos SRV records

    Run the following query to ask dc01 which servers advertise the Kerberos service. The _kerberos._tcp label is the well-known SRV name every DC registers when it is promoted.

    dig SRV _kerberos._tcp.corp.ocr-range.lab @dc01

    Examine the ANSWER SECTION of the output. You should see one or more SRV records listing dc01 as the Kerberos server. Note the priority, weight, and port values.

    The port field should show 88; the standard Kerberos port. If multiple DCs existed in the domain, each would appear as a separate SRV record with its own priority and weight values, allowing clients to select the best server.

    Step 3: Query LDAP SRV Records

    LDAP is how domain-joined machines locate directory services. Clients query _ldap._tcp to find DCs that accept LDAP connections on port 389.

    Query LDAP SRV records

    Run the following query to find the DCs that accept LDAP connections. Domain-joined machines resolve this record to locate directory services on port 389.

    dig SRV _ldap._tcp.corp.ocr-range.lab @dc01

    The output should show dc01 advertising LDAP on port 389. Compare the priority and weight values with the Kerberos SRV record from Step 2; in a single-DC environment, they are typically identical.

    Query LDAPS SRV records

    You can also query for LDAP over Secure Sockets Layer (SSL) on port 636. The presence of an _ldaps record signals that the DC accepts encrypted LDAP.

    dig SRV _ldaps._tcp.corp.ocr-range.lab @dc01

    The presence or absence of an _ldaps SRV record tells you whether the DC is configured for encrypted LDAP connections. Not all environments configure LDAPS.

    Step 4: Query Global Catalog SRV Records

    The Global Catalog (GC) is a read-only copy of all objects across an AD forest, served on port 3268. Multi-domain forests rely on the GC for cross-domain searches.

    Query Global Catalog SRV records

    Query the GC SRV record to find the servers that answer forest-wide searches. The Global Catalog listens on port 3268, distinct from the LDAP port.

    dig SRV _gc._tcp.corp.ocr-range.lab @dc01

    The target should again be dc01, but the port field should show 3268 instead of 389. The GC contains a partial attribute set for every object in the forest, making it a high-value target for enumeration.

    Step 5: Compile Standard SRV Records

    At this point you have queried three standard AD SRV record types. Compiling the results into a single view provides a baseline map of AD infrastructure.

    Compile all standard SRV records

    You can query all three at once using short output for a quick summary. The +short flag collapses each answer to one line so the three results read as a compact baseline.

    dig +short SRV _kerberos._tcp.corp.ocr-range.lab @dc01
dig +short SRV _ldap._tcp.corp.ocr-range.lab @dc01
dig +short SRV _gc._tcp.corp.ocr-range.lab @dc01

    Record the server names, ports, and priorities. In larger environments, you would see multiple DCs here, each with different site affiliations and priority values.

    Step 6: Discover Non-Standard SRV Records

    Standard SRV records reveal the expected AD infrastructure. Non-standard records reveal what administrators have added beyond the defaults. Querying for custom service names can uncover applications, monitoring systems, or test entries.

    Probe for non-standard SRV records

    If the zone transfer from Step 2 succeeded, review the output for SRV records with non-standard service names; entries that do not match the well-known AD services (_kerberos, _ldap, _gc, etc.). If the zone transfer was denied, try querying common non-standard service names such as _http, _sip, or other short keywords that an administrator might use for custom services. Replace <service_name> with each candidate keyword.

    dig SRV _<service_name>._tcp.corp.ocr-range.lab @dc01

    When you find a non-standard SRV record, the ANSWER SECTION will contain an entry pointing to a hostname you have not seen before. Note the target hostname; the SRV record functions as a pointer, directing you to the server that hosts that service.

    Non-standard SRV records like this one would not appear in a port scan. Only DNS enumeration reveals them, which is why SRV record discovery is a required step in any AD assessment.

    Step 7: Follow the SRV Record to the Flag

    The non-standard SRV record from Step 6 points to a hostname. That hostname holds additional DNS records containing the flag. SRV records often serve as the first link in a chain; the record tells you where to look, and further queries at that location reveal the data.

    Query the TXT record at the SRV target

    Query the TXT record at the hostname referenced by the SRV entry you discovered in Step 6. Replace <target_hostname> with the target from the non-standard SRV record.

    dig TXT <target_hostname> @dc01

    The TXT record in the ANSWER SECTION contains the flag value. Read the quoted string in the response.

    Analysis Questions

    1. Why does Active Directory create SRV records automatically during DC promotion?

    Reveal Answer

    Domain-joined clients need a way to locate DCs, Kerberos KDCs, and GC servers without hardcoding IP addresses. SRV records provide a standard DNS mechanism for service discovery. When a DC is promoted, the Netlogon service registers SRV records so clients can find the DC through standard DNS queries.

    2. What is the security risk of non-standard SRV records in a production AD environment?

    Reveal Answer

    Non-standard SRV records expose the existence and location of services that may not be documented or monitored. An attacker who discovers a custom SRV entry gains knowledge of infrastructure that might be overlooked during security reviews. The SRV record itself does not grant access, but it directs the attacker to a target they would not have found through port scanning alone.

    3. How do priority and weight values affect client behavior when multiple SRV records exist for the same service?

    Reveal Answer

    Clients prefer SRV records with lower priority values. When multiple records share the same priority, the weight value determines how traffic is distributed; higher-weight records receive more connections. Administrators use these fields to implement failover (priority) and load balancing (weight) across multiple servers.

    4. What other non-standard SRV record names might an attacker look for in an AD environment?

    Reveal Answer

    Attackers commonly query for _sip._tcp (Voice over IP), _xmpp._tcp (messaging), _http._tcp (internal web apps), _ntp._udp (time servers), and any application-specific service names. Automated tools can brute-force common service names against the DNS server to build a full list.

    Key Takeaways

    • SRV records map services to hosts: they provide the service name, protocol, port, priority, weight, and target server in a single DNS entry
    • Standard AD SRV records for _kerberos, _ldap, and _gc reveal every DC in the domain without port scanning
    • Non-standard SRV records expose custom or undocumented services that administrators may have forgotten about
    • SRV records can form chains: one record points to a hostname where additional records (TXT, A, CNAME) contain further information
    • DNS enumeration is prerequisite to network mapping: later exercises in this chapter build on the DNS data gathered here
