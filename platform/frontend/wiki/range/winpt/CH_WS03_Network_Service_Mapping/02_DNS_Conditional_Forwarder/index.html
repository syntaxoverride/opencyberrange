    Exercise WS-3.2: DNS Conditional Forwarder Detection

    Before You Begin

    Exercise WS-3.1 demonstrated how SRV records reveal the internal services that Active Directory (AD) advertises. Exercise WS-3.2 shifts focus from internal service discovery to external relationships. DNS conditional forwarders are configured when an organization needs to resolve domain names belonging to a partner, subsidiary, or trusted domain. Detecting these forwarders exposes business relationships and potential trust paths that extend beyond the primary domain.

    • Confirm your VPN connection is active and you can reach dc01.
    • No credentials are needed; all queries in this exercise are unauthenticated DNS lookups.
    • You should be comfortable with dig syntax from Exercise WS-3.1.

    Scenario

    Your assessment of corp.ocr-range.lab continues. During SRV record enumeration, you mapped the internal AD services. Now your team lead wants to know whether dc01 resolves names for any domains outside corp.ocr-range.lab. Conditional forwarders configured on a Domain Controller (DC) indicate that the organization has a relationship with another domain; possibly a business partner, acquired company, or federated identity provider. Your task is to identify any conditional forwarders on dc01, query the forwarded zone, and determine what information the partner domain exposes.

    Your Objectives

    • Attempt a DNS zone transfer to enumerate all records in the corp.ocr-range.lab zone
    • Identify references to additional DNS zones that suggest conditional forwarders
    • Query the forwarded zone to confirm resolution through dc01
    • Retrieve the flag from a TXT record in the partner domain

    Background: DNS Conditional Forwarders

    A standard DNS forwarder sends all unresolvable queries to a designated upstream server; typically an Internet Service Provider (ISP) or public DNS resolver. A conditional forwarder is more specific: it forwards queries for a particular domain to a designated DNS server, while all other queries follow the normal resolution path. Windows Server administrators configure conditional forwarders through the DNS Manager console or PowerShell.

    Conditional forwarders serve a practical purpose. When two organizations establish a trust relationship, each domain needs to resolve the other's hostnames. Rather than creating a secondary zone or replicating DNS data, the administrator configures a conditional forwarder that sends queries for partner.local to the partner's DNS server. From the client's perspective, the resolution is transparent; they query their own DC, and the DC silently forwards the request.

    From a security assessment perspective, conditional forwarders are valuable intelligence. Each forwarder reveals a domain that the organization communicates with. The forwarded domain may host shared applications, federated authentication endpoints, or trust relationships that extend access across organizational boundaries. An attacker who discovers a conditional forwarder gains a new target domain to investigate, and the forwarder itself may resolve records that the partner never intended to expose externally.

    Tool Primer: dig for Zone Transfers and Multi-Type Queries

    Zone transfers replicate an entire DNS zone from server to client. The AXFR query type requests a full zone transfer. While many production DNS servers deny zone transfers to unauthorized clients, attempting one is a standard enumeration step because misconfigured servers will return every record in the zone.

    Zone transfer syntax:

    dig AXFR domain @nameserver

    ANY query syntax:

    The ANY query type asks the DNS server to return all record types for a given name. Some servers restrict ANY queries, but many respond with the full set of records.

    dig ANY name @nameserver

    Key flags for this exercise:

    Option Purpose
    AXFR Request a full zone transfer
    ANY Request all record types for a name
    TXT Request TXT (text) records specifically
    +short Display only the answer data without extra sections
    +tcp Force DNS query over TCP (required for AXFR)

    Sample zone transfer output (truncated):

    corp.ocr-range.lab.     600  IN  SOA   dc01.corp.ocr-range.lab. ...
corp.ocr-range.lab.     600  IN  NS    dc01.corp.ocr-range.lab.
dc01.corp.ocr-range.lab. 600 IN  A     <dc01_ip>
_kerberos._tcp.corp.ocr-range.lab. 600 IN SRV 0 100 88 dc01.corp.ocr-range.lab.

    A successful zone transfer returns the Start of Authority (SOA) record, Name Server (NS) records, A records, SRV records, and any other entries in the zone. Look for hostnames or TXT records that reference other domains; these hints suggest conditional forwarders.

    Walkthrough

    Step 1: Launch the Lab and Verify DNS Access

    Navigate to Exercises, then Windows Server, then Level 3, and launch Exercise WS-3.2. Wait for the environment status to show Running.

    Confirm DNS access with an SOA query

    Confirm you can query dc01's DNS service by asking for the zone's Start of Authority record. The +short flag keeps the response to a single line.

    dig +short SOA corp.ocr-range.lab @dc01

    The SOA record confirms dc01 is authoritative for the corp.ocr-range.lab zone. If the query returns no answer or times out, verify your VPN connection.

    Step 2: Attempt a Zone Transfer

    A zone transfer returns every DNS record in a zone at once. Attempting an AXFR query against dc01 may or may not succeed; Windows DNS servers can be configured to allow or deny transfers. The attempt is worth making because a successful transfer provides a complete inventory of the zone.

    Attempt a full zone transfer

    Run the zone transfer. The AXFR query type requests every record in the zone at once, which a misconfigured server will return in full.

    dig AXFR corp.ocr-range.lab @dc01

    If the transfer succeeds, you will see a list of all records in the corp.ocr-range.lab zone. Scan the output for any references to domains other than corp.ocr-range.lab. Hostnames, TXT records, or CNAME records that mention a different domain name are indicators of cross-domain relationships.

    If the transfer fails with a "Transfer failed" message, dc01 is configured to deny AXFR requests. Proceed to Step 3 to use alternative discovery methods.

    Step 3: Probe for the Partner Domain

    Conditional forwarders are not stored as DNS records within the primary zone; they are server-level configurations. However, references to the forwarded domain sometimes appear in TXT records, CNAME aliases, or documentation entries within the primary zone.

    Probe for the forwarded partner domain

    Examine the zone transfer output from Step 2 for any references to domains other than corp.ocr-range.lab; look for TXT records, CNAME aliases, or hostnames that mention a different domain name. If the zone transfer was denied, try probing common trust-related naming patterns such as partner, trust, or subsidiary-style domains (e.g., .local suffixes). Query any candidate domain through dc01 and replace <candidate_domain> with each guess.

    dig ANY <candidate_domain> @dc01

    If dc01 has a conditional forwarder configured for that domain, the query will succeed and return records from the forwarded zone. If no forwarder exists, the query will return NXDOMAIN (non-existent domain) or SERVFAIL.

    A successful response confirms the conditional forwarder. Note the record types and values returned; they reveal what the partner domain exposes through the forwarder.

    Step 4: Enumerate the Partner Domain

    Now that you have confirmed the conditional forwarder, enumerate the partner domain further. Query specific record types to understand what the partner zone contains.

    Identify the partner's authoritative server

    Start with the SOA record to identify the partner's authoritative server. The query travels through dc01's conditional forwarder to the partner's DNS infrastructure.

    dig +short SOA partner.local @dc01

    The SOA answer names the partner's primary name server and confirms the forwarder is resolving the partner zone.

    List the partner's name servers

    Query for NS records to see which name servers the partner domain uses.

    dig +short NS partner.local @dc01

    These queries flow through dc01's conditional forwarder. Every response you receive is data from the partner's DNS infrastructure, resolved transparently through the forwarder. In a real engagement, the partner organization may not realize their DNS data is accessible through the trust relationship.

    Step 6: Query for Specific Records in the Partner Zone

    With the conditional forwarder confirmed, search the partner domain for records that contain assessment-relevant data. TXT records are a common location for metadata, verification strings, and in lab environments, flags.

    Query TXT records in the partner zone

    Enumerate TXT records in the discovered partner zone. Try querying for common hostnames such as flag, info, or test within the partner domain, or attempt a zone transfer against the partner zone through dc01 to list all available records. Replace <hostname> and <partner_domain> with your candidates.

    dig TXT <hostname>.<partner_domain> @dc01

    The response should contain a TXT record with a quoted string value. Read the value carefully; the flag is embedded in the TXT record data.

    Verify the TXT record with short output

    You can also verify the record using the short output format, which is easier to copy.

    dig +short TXT <hostname>.<partner_domain> @dc01

    The short format strips away the extra sections and displays only the answer, making the TXT string easier to read.

    Analysis Questions

    1. What is the difference between a standard DNS forwarder and a conditional forwarder?

    Reveal Answer

    A standard forwarder sends all unresolvable queries to a single upstream DNS server, regardless of domain. A conditional forwarder routes queries for a specific domain to a designated DNS server. Standard forwarders handle general resolution; conditional forwarders target specific domains based on organizational relationships.

    2. Why would discovering a conditional forwarder matter during a penetration test?

    Reveal Answer

    A conditional forwarder reveals that the target organization has a relationship with another domain. The forwarded domain may be a business partner, subsidiary, or acquired company. The trust relationship behind the forwarder could allow cross-domain authentication, making the partner domain a potential lateral movement target. The forwarder also grants DNS-level visibility into the partner's infrastructure.

    3. Can a conditional forwarder exist without an AD trust relationship?

    Reveal Answer

    Yes. A conditional forwarder only configures DNS name resolution; it does not create an AD trust. Administrators sometimes configure conditional forwarders for name resolution without establishing a trust. However, in practice, environments that need to resolve a partner domain often also need cross-domain authentication, so a trust relationship frequently accompanies the forwarder.

    Key Takeaways

    • Zone transfers (AXFR) attempt to retrieve all records from a DNS zone and should always be tested during an assessment
    • Conditional forwarders route DNS queries for specific domains to designated servers, revealing cross-organizational relationships
    • Forwarders indicate trust paths: the DNS resolution path often parallels an AD trust relationship that enables cross-domain authentication
    • Partner domain records become accessible through the forwarder, exposing the partner's DNS data to anyone who can query the forwarding server
    • TXT records in forwarded zones may contain sensitive metadata, verification tokens, or configuration details that administrators assume are private
