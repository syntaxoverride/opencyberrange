    Exercise OTSOC-2.2: The Cleartext Password

    Engagement Status

    Client Pecan Creek Creamery (fictional)
    Role OT SOC Analyst, Capture Review
    Phase Visibility Protocol Analysis Detection
    Priority order Safety, then Integrity, then Availability, then Confidentiality

    What you know so far: Exercise 2.1 taught you to read classic S7comm and tell a Read Var from a Write Var. Now you turn that skill on a real capture: an engineering workstation opened a maintenance session to a plant PLC, your sensor caught it, and something in that session leaked a credential. Your job is to find it and explain why the protocol let it happen.

    Scenario

    You are an OT SOC analyst at Pecan Creek Creamery. During a scheduled maintenance window, an engineering workstation opened a classic S7comm session to a plant PLC and your passive sensor captured the whole conversation. Classic S7comm has no transport security, so when the engineer set or cleared a PLC protection password during that session, the password material crossed the wire as a plaintext string.

    The capture is served by the pcap host pcaphost.pcc.local on port 80, which presents an HTTP index of curated captures. You will download s7-engineering-session.pcap, walk the S7comm function calls, recover the cleartext PLC protection password, and write up why classic S7comm exposed it and what the modern protocol generation would have done differently. No live PLC is in scope. You are analyzing a capture only.

    Why this matters

    Credential exposure in OT is rarely a fancy attack. It is usually a protocol that predates the idea of transport security carrying a secret in the clear, and an analyst who knows where to look catches it in minutes.

    Three concrete reasons the skill matters. First, classic S7comm, like classic Modbus, was designed for a trusted serial bus and never gained authentication or encryption. When a vendor or integrator sets a PLC protection password over that protocol, the password travels as readable bytes. If you can follow a TCP stream you can read it, and so can any adversary already on the segment. Recognizing that exposure is the difference between an analyst who trusts "the PLC is password protected" and one who knows the password is only as private as the network path. Second, capture review is the core OT IR skill. Most of what an OT SOC investigates arrives as a PCAP, because you cannot run an agent on a thirty-year-old PLC. The ability to open a capture, filter to the protocol, and pull the meaningful bytes out is what makes you useful during an incident. Third, knowing what the modern protocol generation fixed lets you give the plant a real recommendation. S7comm-plus added a challenge-response handshake and session encryption precisely because the classic dialect leaked. Naming that upgrade path turns a finding into an action item the plant can fund.

    The password you recover is a training artifact. The skill of finding a plaintext secret in a control-protocol capture is permanent.

    Before You Begin: Read Your Target IP

    The pcap host gets a fresh address every spawn, so do not paste a literal subnet. Open the Exercise Network panel and read the IP shown for pcaphost.pcc.local, then store it in a shell variable. Replace the placeholder below with the IP from your own panel.

    Kali - set the pcap host variable

    PCAPHOST=<pcaphost ip from the Exercise Network panel>
echo "capture host = $PCAPHOST:80 (HTTP index)"

    Confirm the host answers on port 80 before you try to download anything.

    Kali - confirm the pcap host is up

    curl -s -o /dev/null -w 'HTTP %{http_code}\n' "http://$PCAPHOST/"

    Expected output

    HTTP 200

    An HTTP 200 means the capture index is being served and you can list it. Anything else is a connectivity problem to resolve before continuing.

    Walkthrough

    Step 1: Find and download the capture

    The pcap host serves a directory of curated captures. List the index so you know the exact filename, then pull the engineering-session capture down to the RangeBox. Working on a local copy keeps your analysis repeatable and avoids hammering the host.

    Kali - list the capture index

    curl -s "http://$PCAPHOST/" | grep -oiE 'href="[^"]*\.pcap"'

    Expected output

    href="baseline.pcap"
href="attack-mix.pcap"
href="s7-engineering-session.pcap"
href="pasteurizer-divert.pcap"

    The file you want is s7-engineering-session.pcap. Download it to a known path so the rest of the steps can reference it.

    Kali - download the engineering session

    curl -s -o /tmp/s7-engineering-session.pcap \
  "http://$PCAPHOST/s7-engineering-session.pcap"
ls -l /tmp/s7-engineering-session.pcap

    Expected output

    -rw-r--r-- 1 kali kali  ... /tmp/s7-engineering-session.pcap

    A non-zero file size confirms the download. You now have a local copy to analyze.

    Step 2: Confirm it is an S7comm session

    Before hunting for the password, confirm the capture is what you expect: a TCP/102 conversation carrying S7comm. A quick protocol summary tells you the endpoints and the function calls involved. The engineering workstation is the client, the PLC is the server on port 102.

    Kali - summarize the S7comm conversation

    tshark -r /tmp/s7-engineering-session.pcap -Y 's7comm' \
  -T fields -e frame.number -e ip.src -e ip.dst \
  -e s7comm.header.rosctr -e s7comm.param.func | head -20

    Expected output

    ...  <EWS>  <PLC>  0x01  0x04
...  <PLC>  <EWS>  0x03  0x04
...  <EWS>  <PLC>  0x07  ...
...

    You see a job request and acknowledgement pattern between the engineering workstation and the PLC. The ROSCTR 0x07 userdata messages are where setup, security, and protection functions live, and that is where the protection password will be.

    Step 3: Follow the TCP stream

    Classic S7comm carries the protection-password material as a plaintext string inside the userdata payload, so following the single TCP/102 conversation surfaces it directly. The fastest way to find the conversation is to ask tshark for the TCP stream index, then dump that stream as ASCII.

    Kali - identify the TCP/102 stream

    tshark -r /tmp/s7-engineering-session.pcap -Y 'tcp.port == 102' \
  -T fields -e tcp.stream | sort -u

    Expected output

    0

    A single stream index (here 0) means the whole session is one TCP conversation. Now dump that stream as ASCII and look for printable credential material. The follow output prints both directions of the conversation as text.

    Kali - follow the stream as ASCII

    tshark -r /tmp/s7-engineering-session.pcap -q \
  -z follow,tcp,ascii,0 | grep -iaE 'pcc|pass|protect'

    Expected output

    ...PCCpast#2026...

    The printable string in the userdata payload is the PLC protection password the engineer set during the session. Because classic S7comm does not encrypt the payload, the password sits in the packet bytes for anyone watching the conversation to read.

    Step 4: Confirm with strings

    A second, lower-tech path gets you the same answer and is worth knowing because it works even when a dissector does not parse a dialect. Running strings over the capture and grepping for the plant prefix pulls the printable password straight out of the file. Use it as a cross-check against the stream follow.

    Kali - cross-check with strings

    strings /tmp/s7-engineering-session.pcap | grep -i 'pcc'

    Expected output

    PCCpast#2026

    The same value appears, so both methods agree. The capture embeds the cleartext password PCCpast#2026, which is the PLC protection password set during the maintenance window.

    Step 5: Normalize the password into the flag

    The flag is the recovered password normalized to the ascii-underscore form and wrapped as OCR{...}. Lowercase the recovered string and replace each non-alphanumeric character with an underscore. The # in the password becomes _. Build it from your captured value rather than typing it by hand so you carry your own evidence forward.

    Kali - normalize the recovered password

    PW=$(strings /tmp/s7-engineering-session.pcap | grep -i 'pcc' | head -n1 | tr -d '[:space:]')
FLAG="OCR{$(echo "$PW" | tr 'A-Z' 'a-z' | tr -c 'a-z0-9' '_' | sed 's/_*$//')}"
echo "recovered = $PW"
echo "flag      = $FLAG"

    Expected output (flag masked)

    recovered = PCCpast#2026
flag      = OCR{pccpast_<masked>}

    The normalization lowercases the string and turns the # separator into an underscore, producing the lowercase underscore-only flag form. Submit it in the exercise panel.

    Output Interpretation

    • Classic S7comm carries protection-password material as a plaintext string in the ROSCTR 0x07 userdata payload. No decryption is needed because there is no encryption.
    • Follow TCP Stream and strings are two paths to the same secret. Follow gives you protocol context (which direction, which message); strings works even when a dissector cannot parse the dialect.
    • A single TCP stream index for the whole session tells you it is one continuous engineering conversation, not several reconnections.
    • The flag normalization replaces the # in the password with an underscore. The recovered password and the flag are the same secret in two encodings.

    Analysis Questions

    1. Why did the password appear in cleartext when the PLC was supposedly password protected?

    Reveal answer

    The PLC protection password controls who may change the program once it is set, but classic S7comm has no transport security, so the act of setting that password transmits it as plaintext bytes. The protection is real against an attacker who arrives after the session and tries to write logic, but it is worthless against an attacker who was already capturing traffic during the maintenance window. The password is only as private as the network path it crossed.

    2. Follow TCP Stream and strings both found the password. When would you reach for strings over the dissector?

    Reveal answer

    Reach for strings when the Wireshark dissector does not parse the dialect or the vendor extension, when the capture is truncated or malformed enough to confuse the dissector, or when you just want a fast first look without loading the GUI. The cost is that strings gives you no protocol context: you see the bytes but not which message, which direction, or which function carried them. Use strings to confirm a secret exists and the dissector or a stream follow to understand how it got there.

    3. What would S7comm-plus have done differently?

    Reveal answer

    S7comm-plus, the protocol generation used by the S7-1200 and S7-1500 families, added a challenge-response authentication handshake and session-layer encryption. A password is never sent as a recoverable plaintext string; instead the client proves knowledge of the secret against a server-issued challenge, and the session payload is encrypted so a passive capture yields ciphertext, not credentials. An attacker capturing an S7comm-plus maintenance session sees an opaque conversation rather than a readable password.

    4. The engineer did nothing wrong procedurally. So what is the actual finding here?

    Reveal answer

    The finding is architectural, not human. Setting a protection password is good practice, and the engineer followed it. The exposure comes from running a security-relevant operation over a cleartext protocol on a segment where a passive sensor, and therefore potentially an adversary, can read the conversation. The fix is to isolate the engineering path so only the workstation and PLC share it, to migrate to a controller generation that uses S7comm-plus where feasible, and to treat any credential that ever crossed a classic S7comm link as compromised and rotate it.

    Key Takeaways

    • A PLC protection password is only as private as the network path it crossed; on a cleartext protocol it is not private at all.
    • Capture review is the core OT IR skill because you usually cannot run an agent on the PLC itself.
    • Follow TCP Stream gives protocol context; strings is the dissector-independent fallback. Use both.
    • The defensible answer to a cleartext-protocol exposure is segmentation plus migration to an authenticated protocol generation, and rotation of any exposed credential.
