    Exercise 8: Password Hash Cracking

    Before You Begin

    Week 7 introduced SUID (Set User ID) escalation, where a misconfigured binary gave you root-level execution on a target. The lab you are about to start takes privilege escalation in a different direction: cracking password hashes recovered from backup files. Your VPN must be connected and your terminal ready before you proceed.

    Password attacks target the credentials themselves rather than a specific binary or service. When an attacker obtains hashed passwords from a system file, the attacker can run an offline cracking tool against those hashes without triggering any account lockout or generating login alerts on the target.

    Scenario

    Ironforge Systems, a managed hosting provider in Denver, recently lost its senior sysadmin. The former employee's backup scripts are still running on a production server, and management suspects the scripts may be copying sensitive files to insecure locations. Rachel Kim, Ironforge's Security Manager, has asked you to conduct an internal assessment.

    Rachel has given you low-privilege SSH (Secure Shell) access as the "technician" account. Your goal is to find exposed password hashes, crack them offline, and demonstrate how a weak password leads to full privilege escalation. Rachel's words: "Our sysadmin left last month. I know his backup scripts were sloppy, but I want to see exactly how bad it is. Show me the worst case."

    Your Objectives

    • Discover exposed password hash files through filesystem enumeration
    • Identify the hash type and select an appropriate cracking tool
    • Use John the Ripper to crack weak password hashes with a dictionary attack
    • Escalate privileges using cracked credentials
    • Capture the flag

    Background: Password Hashes and Offline Cracking

    Linux systems store user passwords in /etc/shadow, a file readable only by root. Each line in the shadow file contains a username, a hashed password, and several fields related to password aging. The password field uses a structured format that identifies the hashing algorithm.

    A typical shadow entry looks like the following:

    sysadmin:$6$randomsalt$longhashvalue:19500:0:99999:7:::

    The $6$ prefix indicates SHA-512 hashing. Other common prefixes include $1$ for MD5 and $5$ for SHA-256. The salt (the value between the second and third $ signs) makes each hash unique even when two users choose the same password.

    Offline cracking works by hashing every word in a dictionary with the same algorithm and salt, then comparing the result to the stolen hash. When a match occurs, the tool has recovered the plaintext password. Weak passwords like common dictionary words, pet names, or short numeric strings crack in seconds because they appear early in standard wordlists. Strong passwords with length, complexity, and randomness resist dictionary attacks because no wordlist entry will match.

    Tool Primer: John the Ripper

    John the Ripper (commonly called "john") is an open-source password cracking tool that supports many hash formats, including Linux shadow file hashes. The tool reads a hash file, detects the algorithm automatically, and tests candidate passwords from a wordlist.

    The basic syntax for cracking a shadow-format file is shown below.

    Crack a shadow-format hash file with John

    Run John against the hash file using a dictionary. The rockyou.txt wordlist is the standard first choice because it holds millions of real leaked passwords.

    john --wordlist=/usr/share/wordlists/rockyou.txt <hash_file>

    John loads the hashes, auto-detects the algorithm, and prints each cracked password next to its account as it finds a match.

    • --wordlist= specifies the dictionary file to use. The rockyou.txt wordlist contains over 14 million real passwords leaked from a 2009 breach, making it the standard first choice for dictionary attacks.
    • <hash_file> is the path to the file containing the hashes you want to crack. John expects the file to follow the /etc/shadow line format.

    Reading the output:

    Loaded 2 password hashes with 2 different salts (sha512crypt [SHA512 256/256 AVX2 4x])
Press 'q' or Ctrl-C to abort, almost any other key for status
dragon           (sysadmin)
1g 0:00:00:03 DONE (2026-03-05 10:15) 0.3125g/s 1200p/s 1200c/s 1200C/s

    The line dragon (sysadmin) shows that John found a match: the sysadmin account's password hashes to the dictionary word shown. The timing line shows how long the attack took and the cracking speed.

    To display previously cracked passwords without re-running the attack, use the --show flag.

    Display already-cracked passwords

    Use --show to reprint results from John's pot file without repeating the attack.

    john --show <hash_file>

    The output lists each cracked account and its recovered password in username:password format.

    Walkthrough

    Step 1: Launch the Exercise

    Open the platform in your browser and start the exercise environment. The target containers must be running before you can connect.

    • Navigate to Exercises and select the Linux track
    • Find Exercise 8; Password Hash Cracking under Week 8
    • Click Launch and wait for the status to change to Running
    • Note the target IP displayed in the Active Lab View

    Step 2: Connect via SSH as the Technician

    Your initial access uses the low-privilege technician account. SSH provides a remote terminal session on the target server.

    Open your terminal and connect.

    SSH into the target as technician

    Replace <target_ip> with the IP address shown in the Active Lab View. Enter the technician credential when prompted.

    ssh technician@<target_ip>

    When prompted for a password, enter:

    Ir0nf0rg3_T3ch#

    A shell prompt indicates you are logged in as technician on the target.

    Confirm your identity

    Check the account and group memberships on the target shell.

    whoami
id

    The whoami output should read technician, and id shows your group memberships; note that you have no special privileges yet.

    Step 3: Discover the Exposed Shadow Backup

    The former sysadmin's backup scripts may have copied sensitive files to world-readable locations. Common backup directories include /opt, /var/backups, /tmp, and user home directories. Your goal is to find any copies of the shadow file.

    Explore the filesystem.

    Browse the backup directory tree

    Walk down through the /opt tree on the target to locate the backup directory the scripts wrote to.

    ls -la /opt/
ls -la /opt/ironforge/
ls -la /opt/ironforge/backups/

    You should find a file named shadow.bak in /opt/ironforge/backups/.

    Check the backup file permissions

    Inspect the permissions on the shadow backup to confirm it is exposed.

    ls -la /opt/ironforge/backups/shadow.bak

    The file is world-readable; any user on the system can read it. A properly secured shadow file has permissions 640 and is owned by root. The backup script copied the file without preserving these restrictive permissions, creating the vulnerability Rachel suspected.

    View the shadow backup contents

    Print the backup so you can pick out the crackable hashes.

    cat /opt/ironforge/backups/shadow.bak

    Look for lines that contain a $6$ hash in the second field. These are accounts with SHA-512 hashed passwords that you can attempt to crack.

    Step 4: Extract the Assessment Token

    The backup directory contains more than the shadow file. Look for an assessment token that forms part of your final flag.

    Read the assessment token

    List the backup directory again and print the token file it contains.

    ls -la /opt/ironforge/backups/
cat /opt/ironforge/backups/assessment_token.txt

    Record the token value you find. You will combine the token from the backup directory with a second piece found later to form the complete flag in OCR{...} format.

    Step 5: Crack the Hashes with John the Ripper

    All tools needed for this step are pre-installed on the target. Copy both the passwd and shadow backups to a working location. John the Ripper needs the passwd file combined with the shadow file to correctly parse the hashes. The unshadow utility merges the two files into a format that John can process.

    Merge the backups with unshadow

    Copy both backups to /tmp and combine them so John can map each hash to a username.

    cp /opt/ironforge/backups/shadow.bak /tmp/shadow.bak
cp /opt/ironforge/backups/passwd.bak /tmp/passwd.bak
unshadow /tmp/passwd.bak /tmp/shadow.bak > /tmp/hashes.txt

    The merged file at /tmp/hashes.txt now pairs each user with the hash John needs to crack.

    Run John against the merged hashes

    Launch John with the rockyou wordlist against the combined file.

    john --wordlist=/usr/share/wordlists/rockyou.txt /tmp/hashes.txt

    John will load the hashes, detect the SHA-512 algorithm, and begin testing candidates from the wordlist. Watch the output for cracked passwords; weak passwords will appear within seconds.

    Display the cracked passwords

    Reprint the results once the run finishes.

    john --show /tmp/hashes.txt

    Note which accounts cracked and what their passwords are. The sysadmin account's password should appear in the output.

    Step 6: Escalate Privileges with the Cracked Password

    Now that you have the sysadmin password, use su (substitute user) to switch to that account. The su command starts a new shell running as the specified user.

    Switch to the sysadmin account

    Run su on the target and enter the cracked password when prompted.

    su sysadmin

    A new shell opens running as sysadmin once the password is accepted.

    Confirm the new identity

    Verify the account switch took effect.

    whoami
id

    You should now be operating as sysadmin with elevated privileges on the system.

    Step 7: Read the Flag

    The sysadmin's home directory contains the second piece of the flag. Navigate there and read the flag file.

    Read the sysadmin flag

    Print the flag file from the sysadmin home directory, now readable as the sysadmin user.

    cat /home/sysadmin/flag.txt

    Combine the token from Step 4 with the value from the flag file to assemble the complete flag in OCR{...} format.

    Step 8: Interpret the Results

    Review what you discovered and consider the full attack chain. You started with low-privilege technician access and ended with sysadmin credentials; all because of two failures.

    The first failure was insecure file permissions on the backup. The backup script copied /etc/shadow to a world-readable directory, exposing password hashes to every user on the system. A properly written script would preserve the original file permissions or store backups in a root-only directory.

    The second failure was a weak password. The sysadmin account used a common dictionary word that appears near the top of the rockyou.txt wordlist. A strong password; long, random, and not based on any dictionary word; would have resisted the cracking attempt entirely.

    Together, these two failures created a privilege escalation path: exposed hashes plus a weak password equals compromised accounts.

    Flag Format

    Assemble the flag using the tokens in the order you discovered them:

    OCR{________}

    Where token1 is from the backup assessment token file, and token2 is from the user flag after cracking the password.

    Paste the complete OCR{...} flag into the Submit Flag form on the platform and click Submit. The platform will validate your submission and mark the lab as complete.

    Analysis Questions

    Consider the following questions to deepen your understanding of password hash cracking and its implications.

    1. Why is offline cracking more dangerous than an online brute-force attack against a login prompt?

    Reveal Answer

    An offline attack runs entirely on the attacker's machine, so there are no failed-login alerts, no account lockouts, and no rate limiting. The attacker can test millions of candidates per second without the target system ever knowing. An online brute-force attack, by contrast, generates log entries for every attempt and can be stopped by lockout policies after a few failures.

    2. The sysadmin password cracked in seconds. What characteristics would make a password resistant to a dictionary attack using rockyou.txt?

    Reveal Answer

    A resistant password would be long (12 or more characters), contain a mix of uppercase and lowercase letters, numbers, and special characters, and would not be based on any real word, name, or common pattern. Randomly generated passphrases or password manager output resist dictionary attacks because no wordlist entry will match the exact combination.

    3. Beyond fixing file permissions on the backup, what other controls could prevent the attack chain you demonstrated?

    Reveal Answer

    The organization could enforce password complexity policies to prevent weak passwords, use multi-factor authentication (MFA) so that a cracked password alone is not sufficient, restrict su access to specific groups, monitor for unauthorized file access in sensitive directories, and rotate passwords regularly. Encrypting backups would also prevent hash extraction even if the backup file were accessible.

    Key Takeaways

    • Offline password cracking allows an attacker to test millions of password candidates per second without triggering any alerts on the target system
    • File permissions on sensitive files like /etc/shadow are a critical security control; a single misconfigured backup script can expose every password hash on the system
    • Weak passwords based on dictionary words crack in seconds regardless of the hashing algorithm; password strength is the last line of defense after hashes are exposed
    • Privilege escalation through credential reuse demonstrates why each account should have a unique, strong password; one cracked password can unlock access to higher-privilege accounts
    • John the Ripper with the rockyou.txt wordlist is a standard first step in any password audit; Week 9 will combine hash cracking with earlier techniques in a multi-stage assessment
