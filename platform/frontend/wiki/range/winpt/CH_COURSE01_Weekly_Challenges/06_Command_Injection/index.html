    Exercise 6: Command Injection

    Before You Begin

    Week 5 introduced API (Application Programming Interface) testing, where you crafted requests to interact with backend services and extract data through application logic flaws. Week 6 escalates from data extraction to code execution; instead of reading information the application was not meant to expose, you will execute operating system commands on the server itself. Your VPN must be connected and your terminal open before continuing.

    Scenario

    CloudPing Diagnostics offers a web-based network diagnostic tool that customers use to test connectivity to their cloud infrastructure. The tool accepts a hostname or IP address and runs a ping test, displaying the results in the browser.

    Tom Bradley (Lead Developer) built the tool as a weekend project: "It is a wrapper around the ping command. Takes the hostname, runs ping, shows the output. Nothing fancy."

    Your assessment scope covers the diagnostic tool and the underlying server. Two tokens have been placed on the system; one accessible through basic command injection and one requiring deeper filesystem access. Your job is to determine whether the ping feature can be abused to run arbitrary commands.

    Your Objectives

    The CloudPing diagnostic tool presents a specific attack surface worth investigating. Your goals for the assessment are listed below.

    • Identify a web application feature that interacts with the operating system
    • Test for OS (Operating System) command injection using shell metacharacters
    • Exploit command injection to execute arbitrary commands on the server
    • Read restricted files through injected commands
    • Assemble and submit the flag in OCR{...} format

    Background: OS Command Injection

    Web applications sometimes need to interact with the underlying operating system. A network diagnostic tool might call the system's ping command, a file converter might invoke ffmpeg, or a monitoring dashboard might run df to check disk usage. When an application takes user input and passes it directly to a system shell without sanitization, attackers can inject additional commands that the server executes blindly.

    Shell interpreters like bash and sh treat certain characters as metacharacters; symbols that change how a command line is parsed. The semicolon (;) separates two independent commands, so ping 127.0.0.1; id runs ping first and then runs id. The pipe (|) sends the output of one command into another. Double ampersand (&&) runs the second command only if the first succeeds, and double pipe (||) runs the second command only if the first fails. An attacker who controls part of a command string can use any of these metacharacters to append their own commands.

    Input sanitization is the primary defense against command injection. A secure application validates that the user's input matches the expected format (for example, an IP address should contain only digits and dots), uses allowlists to restrict acceptable input, or avoids calling system commands entirely by using language-native libraries. Without these controls, any command the web server process can execute is available to the attacker.

    Tool Primer: curl POST Requests

    Previous labs used curl for GET requests, where data travels in the URL. The CloudPing diagnostic tool accepts input through an HTTP (Hypertext Transfer Protocol) POST request, where data travels in the request body instead. The -X POST flag tells curl to use the POST method, and the -d flag attaches form data to the request body.

    Send a basic POST request with form data

    The -d flag sends the string host=127.0.0.1 as URL-encoded form data. The server receives the value 127.0.0.1 in the host parameter and uses it to run the ping command.

    curl -X POST http://<target>/ping -d 'host=127.0.0.1'

    The response returns the ping output the server produced for the value you supplied.

    Send an injection payload

    The semicolon after the IP address tells the shell to run a second command (id) after the ping.

    curl -X POST http://<target>/ping -d 'host=127.0.0.1;id'

    If the server is vulnerable, the response will contain both the ping output and the output of the id command.

    URL-encode special characters when needed

    Some characters need URL encoding when sent in POST data. The semicolon (;) works without encoding in most cases, but if a payload is not working, try encoding special characters. For example, a space becomes %20 and a semicolon becomes %3B. The --data-urlencode flag handles encoding automatically.

    curl -X POST http://<target>/ping --data-urlencode 'host=127.0.0.1;cat /etc/passwd'

    Encoding the payload helps when raw metacharacters get stripped or mangled in transit.

    Walkthrough

    Step 1: Launch the Exercise

    Open the platform in your browser and start the exercise environment. You need running containers before any web requests will reach the target.

    • Navigate to Exercises and locate Exercise 6; Command Injection
    • Click Launch and wait for the status to change to Running
    • Note the target IP displayed in the Active Lab View

    Step 2: Use the Ping Tool Normally

    Before testing for vulnerabilities, observe how the application behaves with legitimate input. Sending a normal request first establishes a baseline so you can recognize when output changes.

    Run a valid ping request using the loopback address.

    Send a baseline ping request

    Replace <target> with the IP address shown in the Active Lab View. Sending a clean request first establishes a baseline so you can recognize when the output changes.

    curl -X POST http://<target>/ping -d 'host=127.0.0.1'

    The response should contain standard ping output; lines showing bytes from 127.0.0.1 with round-trip times. The application took your input, passed it to the system ping command, and returned the results.

    Step 3: Test for Command Injection

    Now test whether the application sanitizes user input before passing it to the shell. The semicolon (;) is the most common metacharacter for separating commands in a Linux shell. Appending ; id after a valid IP address will reveal whether the server executes a second command.

    Inject the id command

    Append ;id to the host value so the shell runs id after the ping completes.

    curl -X POST http://<target>/ping -d 'host=127.0.0.1;id'

    Examine the response carefully. If command injection is possible, you will see the normal ping output followed by a line containing uid=, gid=, and groups=: the output of the id command. The presence of the id output confirms that the server executed your injected command.

    Confirm with whoami

    Run a simpler payload to double-check the injection point.

    curl -X POST http://<target>/ping -d 'host=127.0.0.1;whoami'

    The response should include a username (such as root or www-data) after the ping output. Both tests confirm the same vulnerability; the application passes your input directly to a shell without any filtering.

    Step 4: Read the Application Token

    With command injection confirmed, you can use it to read files on the server. The first assessment token is stored in the application's configuration directory. Use cat to read the file contents through your injection payload.

    Read the application config token

    Inject a cat command that prints the token file from the application's config directory.

    curl -X POST http://<target>/ping -d 'host=127.0.0.1;cat /opt/cloudping/config/token.txt'

    The response will include the ping output followed by the contents of token.txt. Record the token value; you will need it to assemble the final flag.

    Step 5: Read the Root Flag

    The second token requires reading a file in the /root directory. Use the same injection technique to read the flag file.

    Read the root flag file

    Inject a cat command that reads the flag from the /root directory, which only works because the web process runs with elevated privileges.

    curl -X POST http://<target>/ping -d 'host=127.0.0.1;cat /root/flag.txt'

    The response will contain the second token value after the ping output. Record the token value alongside the first one.

    Step 6: Interpret the Results

    Review the evidence you collected in the previous steps. Each finding tells you something about the security posture of the CloudPing application.

    • The id or whoami output: confirms that user input reaches a system shell without sanitization. The user account shown (e.g., root) also reveals the privilege level of the web application process. Running a web application as root means any injected command has full system access.
    • Token 1 from /opt/cloudping/config/token.txt: demonstrates that command injection grants read access to application configuration files. Configuration files often contain database credentials, API keys, and internal service URLs.
    • Token 2 from /root/flag.txt: demonstrates that the web process runs with elevated privileges, allowing access to files that should be restricted to the root user only.

    Combine the two tokens into the flag format OCR{...} as indicated by the lab instructions. Paste the assembled flag into the Submit Flag form on the platform and click Submit.

    Analysis Questions

    The following questions ask you to think beyond the mechanics of the attack and consider the broader implications of command injection vulnerabilities.

    1. The CloudPing application runs the ping command by passing user input to a system shell. What alternative approach could the developer use to avoid command injection entirely?

    Reveal Answer

    The developer could use a programming language's native networking library to send ICMP (Internet Control Message Protocol) echo requests instead of calling the system ping command through a shell. Python's subprocess module with a list of arguments (rather than a shell string) also prevents injection, because each argument is passed directly to the process without shell interpretation. Avoiding the shell entirely eliminates the injection vector.

    2. You confirmed injection by appending ; id after the IP address. Name two other shell metacharacters that could achieve the same result, and explain how each one works.

    Reveal Answer

    The pipe character (|) sends the output of the first command as input to the second command, so 127.0.0.1 | id would run id and display its output. The double ampersand (&&) runs the second command only if the first succeeds, so 127.0.0.1 && id would run id after a successful ping. The double pipe (||) runs the second command only if the first fails, which can be useful when the first command produces an error.

    3. The web application process runs as root. Why does running a web application with root privileges make command injection significantly more dangerous?

    Reveal Answer

    A process running as root has unrestricted access to every file and service on the system. Command injection under a limited user account (such as www-data) would restrict the attacker to files readable by that user. Running as root means the attacker can read /etc/shadow (password hashes), install persistent backdoors, modify system configurations, pivot to other machines on the network, and effectively control the entire server.

    Key Takeaways

    • OS command injection occurs when a web application passes unsanitized user input to a system shell, allowing attackers to append arbitrary commands using metacharacters like ;, |, &&, and ||
    • Input validation is the primary defense; applications should restrict input to expected formats, use allowlists, or avoid shell calls entirely by using language-native libraries
    • Privilege escalation through process context means that a web application running as root gives an attacker full system control the moment command injection is discovered
    • POST-based injection works the same way as GET-based injection; the delivery mechanism changes, but the underlying vulnerability (unsanitized input reaching a shell) is identical
    • Week 7 builds on code execution by exploring reverse shells and persistence, where attackers use injection points to establish ongoing access rather than running one-off commands
