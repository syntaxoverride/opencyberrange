    Exercise 13: Packet Capture Analysis

    Before You Begin

    Over the past three weeks (Weeks 10-12), you have been building skills in credential discovery, lateral movement, and multi-stage attack chains. Week 13 marks a shift from offensive techniques to defensive analysis: instead of attacking a target, you will examine evidence left behind by an attacker. Your VPN must be connected and your terminal ready for SSH access to the analysis workstation.

    Scenario

    Avalon Biotech, a pharmaceutical research company in San Diego, California, has flagged suspicious network activity on their internal network. Their SIEM (Security Information and Event Management) system triggered alerts for unusual outbound connections from a workstation in the R&D department (10.20.1.105) to multiple external IP addresses over the past 48 hours.

    The incident response team captured a 5-minute segment of the workstation's network traffic before the employee; Mark Sullivan, Research Associate; was informed. The capture has been placed on an analysis workstation for your review.

    Dr. Priya Sharma (CISO) needs your analysis: "We need to know exactly what happened. What data was accessed? What credentials were used? How was the data moved out? If Mark is exfiltrating our proprietary drug trial data, we need evidence for legal. Pull everything you can from that capture."

    Your job is to analyze the PCAP (Packet Capture) file at /home/analyst/evidence/capture.pcap, extract three indicators of compromise (IOCs), and reconstruct the attack timeline.

    Credentials

    Analysis Workstation SSH: analyst / Av4l0n_S0C#

    Your Objectives

    The evidence file contains traffic from three distinct attack vectors. You will need to find each one and extract the associated IOC marker.

    • Analyze a network packet capture using command-line tools (tcpdump, tshark)
    • Identify suspicious HTTP traffic and extract leaked credentials from POST requests
    • Reconstruct FTP (File Transfer Protocol) sessions to discover data exfiltration activity
    • Detect DNS (Domain Name System)-based data exfiltration techniques
    • Assemble the IOC markers and capture the flag

    Background: Network Forensics and Packet Analysis

    Network forensics is the practice of capturing, recording, and analyzing network traffic to detect intrusions, reconstruct incidents, and gather evidence. Every packet that crosses a network carries metadata; source and destination addresses, protocol information, timestamps; and often carries payload data such as login credentials, file contents, or command sequences. When an attacker moves data across a network, that activity leaves traces in the captured traffic.

    A PCAP file is the standard format for storing captured network traffic. Tools like tcpdump and Wireshark write PCAP files, and analysts can replay them later to examine every packet in detail. Each packet in a PCAP contains the full protocol stack: Ethernet frame headers, IP headers, transport-layer headers (TCP or UDP), and the application-layer payload (HTTP requests, FTP commands, DNS queries, and so on).

    Network traffic is evidence because attackers cannot avoid generating packets. Whether they are logging into a web application, transferring files, or tunneling data through DNS, the packets record what happened. Your role as an analyst is to filter, decode, and interpret those packets to build a picture of the incident.

    Tool Primer: tshark and tcpdump

    Two command-line tools dominate PCAP analysis on Linux: tcpdump and tshark. Both can read PCAP files and apply filters, but they differ in their strengths. tcpdump excels at quick, raw packet inspection, while tshark (the terminal version of Wireshark) provides powerful protocol dissection and field extraction.

    Reading a PCAP with tcpdump:

    tcpdump -r capture.pcap -n | head -50
    • -r capture.pcap: read from a file instead of a live interface
    • -n: do not resolve hostnames (show raw IP addresses)
    • | head -50: display only the first 50 packets for a quick overview

    Reading a PCAP with tshark:

    tshark -r capture.pcap -q -z conv,ip
    • -r capture.pcap: read from a file
    • -q: quiet mode (suppress per-packet output)
    • -z conv,ip: show a summary table of IP conversations

    Filtering by protocol; HTTP traffic:

    tshark -r capture.pcap -Y "http.request.method==POST" -T fields -e http.file_data

    The -Y flag applies a display filter. The -T fields -e flags extract specific protocol fields from matching packets.

    Filtering by protocol; FTP commands:

    tshark -r capture.pcap -Y "ftp.request.command==PASS" -T fields -e ftp.request.arg

    FTP sends credentials in plaintext. The PASS command carries the password, and tshark can extract the argument directly.

    Filtering by protocol; DNS queries:

    tshark -r capture.pcap -Y "dns.qry.type==16" -T fields -e dns.qry.name

    DNS TXT record queries (type 16) are a common channel for data exfiltration. Attackers encode stolen data as subdomain labels and send DNS lookups to a server they control.

    Alternative tcpdump approach; searching for strings:

    tcpdump -r capture.pcap -A port 80 | grep token=

    The -A flag prints packet payloads in ASCII, making it possible to search for specific strings with grep.

    Start with a broad view of the traffic before diving into specific protocols. Understanding the volume, duration, and protocol distribution helps you know where to focus.

    Run a conversation summary to see which IP addresses are communicating:

    Summarize IP conversations

    Look for connections from the suspect workstation (10.20.1.105) to external IP addresses.

    Preview the first 50 packets

    tcpdump -r /home/analyst/evidence/capture.pcap -n | head -50

    Note which protocols appear; HTTP, FTP, and DNS are the three you need to investigate.

    Step 5: Extract HTTP POST Data

    HTTP POST requests carry form data in their body, which can include usernames, passwords, and session tokens. An attacker who submits credentials to an external server leaves that data visible in the PCAP.

    Filter the capture for HTTP POST requests and extract the body content:

    Extract HTTP POST bodies with tshark

    Apply a display filter for POST requests and pull the body field. The -Y flag is the display filter and -T fields -e extracts a single named field.

    tshark -r /home/analyst/evidence/capture.pcap -Y "http.request.method==POST" -T fields -e http.file_data

    Grep POST traffic with tcpdump

    Alternatively, dump port 80 payloads in ASCII and search for the field name directly.

    tcpdump -r /home/analyst/evidence/capture.pcap -A port 80 | grep token=

    Look for a token= field in the POST body. The value after token= is your first IOC marker. Record it before moving on.

    Step 6: Extract FTP Credentials

    FTP (File Transfer Protocol) transmits everything in cleartext, including usernames and passwords. The PASS command contains the password sent during authentication. An FTP session to an external IP from the suspect workstation is strong evidence of data exfiltration.

    Extract the FTP PASS command from the capture:

    Extract the FTP PASS argument

    Filter for the FTP PASS command and extract its argument, which is the cleartext password the attacker sent.

    tshark -r /home/analyst/evidence/capture.pcap -Y "ftp.request.command==PASS" -T fields -e ftp.request.arg

    Grep FTP traffic with tcpdump

    Alternatively, dump port 21 payloads and search for the PASS line.

    tcpdump -r /home/analyst/evidence/capture.pcap -A port 21 | grep PASS

    The password value is your second IOC marker. Record it alongside the first.

    Step 7: Analyze DNS Queries for Data Exfiltration

    DNS-based data exfiltration is a technique where an attacker encodes stolen data into subdomain labels and sends DNS queries to a command-and-control (C2) server. Because DNS traffic is rarely blocked or inspected, attackers use it to bypass firewalls and data loss prevention systems.

    For example, a query to encoded-data.data.evil-c2.net hides the stolen content in the subdomain encoded-data. The attacker's DNS server receives the query and logs the subdomain as exfiltrated data.

    Filter the capture for DNS TXT record queries (query type 16):

    Extract DNS TXT query names

    Filter for DNS TXT queries (type 16) and print the query names, which carry the encoded exfiltration data in their subdomain labels.

    tshark -r /home/analyst/evidence/capture.pcap -Y "dns.qry.type==16" -T fields -e dns.qry.name

    Look for queries directed at a suspicious domain. Among the exfiltration traffic, one query has a subdomain prefixed with token_. The value after token_ (before the first dot) is your third IOC marker. Record it with the other two.

    Step 8: Interpret the Results

    Now that you have extracted all three IOC markers, step back and reconstruct the full attack timeline. Understanding the sequence of events matters as much as finding the individual artifacts.

    The suspect workstation (10.20.1.105) made outbound connections using three different protocols:

    • HTTP POST to an external server (198.51.100.47): the attacker submitted credentials or tokens to a remote web endpoint. The POST body contained the first IOC marker, suggesting the attacker authenticated to an external service or exfiltrated authentication tokens.
    • FTP session to another external server (203.0.113.22): the attacker connected to an FTP server and authenticated with a password containing the second IOC marker. FTP is commonly used to transfer files in bulk, pointing to data exfiltration of larger assets.
    • DNS TXT queries to a C2 domain: the attacker sent multiple DNS queries to a C2 domain, encoding exfiltrated data as subdomain labels. One of those queries is tagged with a token_ prefix, marking it as the third IOC. DNS exfiltration is a covert channel; most organizations do not inspect DNS query content, making it an effective way to smuggle small amounts of data past security controls.

    The three markers combine to form the flag in OCR{...} format, with underscores separating each marker.

    Flag Format

    Assemble the flag using the tokens in the order you discovered them:

    OCR{<httptoken>_<ftptoken>_<dnstoken>}

    Where httptoken is from the HTTP POST token= parameter, ftptoken is from the FTP PASS command, and dnstoken is the value after token_ in the DNS TXT query subdomain.

    Combine the three IOC markers you extracted into the flag format: OCR{...}. The markers are joined with underscores in the order you found them (HTTP, FTP, DNS). Paste the assembled flag into the Submit Flag form on the platform and click Submit.

    Analysis Questions

    Take a moment to think through these questions. They build on what you observed in the packet capture and connect to broader network security concepts.

    1. Why is FTP considered a security risk compared to protocols like SFTP or SCP?

    Reveal Answer

    FTP transmits all data in cleartext, including usernames and passwords. Anyone with access to the network path; whether through a packet capture, a man-in-the-middle position, or a compromised switch; can read every credential and file transferred. SFTP and SCP encrypt the entire session, making captured packets unreadable without the encryption keys.

    2. How does DNS-based data exfiltration bypass traditional security controls, and what defenses can detect it?

    Reveal Answer

    Most firewalls allow DNS traffic (port 53) outbound without inspection because DNS is essential for normal network operations. Attackers exploit that permissiveness by encoding data in subdomain labels. Defenses include DNS query logging and analysis, monitoring for unusually long subdomain labels, tracking query volume per domain, and deploying DNS-aware security tools that inspect query content for encoded or anomalous patterns.

    3. An analyst finds HTTP POST traffic to an external IP but the POST body is encrypted with TLS. How does TLS change the analyst's ability to reconstruct the incident?

    Reveal Answer

    TLS (Transport Layer Security) encrypts the HTTP payload, so the analyst would see the connection metadata (source IP, destination IP, destination port, timing) but not the POST body content. Reconstructing the incident would require access to the TLS session keys (sometimes logged by endpoint agents), a TLS-intercepting proxy that decrypts and re-encrypts traffic, or endpoint forensic artifacts like browser history and process memory. Without decryption, the analyst can prove a connection occurred but cannot determine what data was sent.

    Key Takeaways

    • PCAP files are the foundation of network forensics; they record every packet and allow analysts to reconstruct exactly what happened on the wire
    • Protocol-specific filters in tshark and tcpdump let you isolate HTTP, FTP, DNS, and other traffic types from large captures, turning thousands of packets into targeted evidence
    • Cleartext protocols like HTTP and FTP expose credentials and data to anyone who captures the traffic; encrypted alternatives (HTTPS, SFTP) prevent that exposure
    • DNS exfiltration is a covert channel that abuses the ubiquity of DNS to smuggle data past firewalls and security controls, making DNS query analysis an essential defensive skill
    • Attack timeline reconstruction ties individual artifacts together into a coherent narrative, which is the deliverable that incident response teams and legal counsel need; Week 14 builds on these forensic skills with log analysis and correlation techniques
