    Exercise WS-4.1: Authenticated Share Enumeration

    Before You Begin

    In previous chapters, you explored Server Message Block (SMB) shares using anonymous and null-session access. Those techniques revealed publicly accessible shares, but many shares on a domain controller are hidden from unauthenticated users. Authenticated share enumeration uses valid domain credentials to reveal the full list of shares and access files that require domain membership.

    Scenario

    During earlier LDAP enumeration of the corp.ocr-range.lab domain, you discovered the guest.user account. You have confirmed the password Guest2024# through credential testing. Your task is to authenticate to the domain controller dc01 and enumerate all available SMB shares. Comparing authenticated results against anonymous results will demonstrate the gap between what unauthenticated attackers see and what a domain user can access.

    Your Objectives

    • Authenticate to SMB on dc01 using the guest.user domain credentials
    • List all shares visible to an authenticated domain user, including hidden administrative shares
    • Compare the authenticated share list against an anonymous (unauthenticated) share list
    • Browse and retrieve files from shares that require domain authentication
    • Locate and submit the flag from a restricted share

    Background: Anonymous vs. Authenticated SMB Access

    SMB share visibility depends on the caller's authentication level. Windows Server exposes different sets of shares depending on whether the connection is anonymous, authenticated as a regular user, or authenticated as an administrator. Understanding these access tiers is essential for thorough SMB enumeration.

    The table below summarizes what each access level typically reveals on a Windows domain controller:

    Access Level Shares Visible File Access
    Anonymous (no creds) IPC$, sometimes a few public shares Minimal; usually limited to IPC$
    Authenticated (domain user) NETLOGON, SYSVOL, all custom shares, hidden shares Full read access to non-admin shares
    Administrative (Domain Admin) All shares including C$, ADMIN$ Full read/write to everything

    Hidden shares are shares whose names end with a dollar sign ($). Windows creates several hidden administrative shares by default (C$, ADMIN$, IPC$). Administrators can also create custom hidden shares. Anonymous connections typically cannot even see these shares in a listing, but authenticated users can see them and may have read access depending on the share permissions.

    The NETLOGON and SYSVOL shares are special shares that exist on every domain controller. NETLOGON stores logon scripts, and SYSVOL stores Group Policy templates. Both are readable by any authenticated domain user; a design requirement for domain-joined machines to function.

    Tool Primer: smbclient with Authentication

    The smbclient tool supports authenticated connections through the -U flag. Credentials can be supplied in username%password format to avoid interactive password prompts, which is useful for scripting and documentation.

    Authenticated share listing:

    smbclient -L dc01 -U 'guest.user%Guest2024#'

    Anonymous share listing (for comparison):

    smbclient -L dc01 -N

    Connecting to a specific share:

    smbclient //dc01/ShareName -U 'guest.user%Guest2024#'

    Running a single command without entering the interactive shell:

    smbclient //dc01/ShareName -U 'guest.user%Guest2024#' -c 'ls'

    The key flags used in this exercise serve the following purposes:

    Flag Purpose
    -L List shares on the specified host
    -U 'user%pass' Authenticate with the given username and password
    -N Suppress password prompt (anonymous/null session)
    -c 'command' Execute a single command and exit

    When using the -c flag, you can chain multiple commands separated by semicolons. Common smbclient commands include ls (list files), cd (change directory), get (download a file), and cat (display file contents). The special syntax get filename - prints file contents to standard output instead of saving to disk.

    Walkthrough

    Step 1: Launch the Lab

    Open the Open Cyber Range platform in your browser and start the lab environment.

    • Navigate to Exercises, then Windows Server, then Level 4
    • Click Launch on "Authenticated Share Enumeration"
    • Wait for the status to change to Running
    • Note the target IP displayed in the Active Lab View

    Step 2: List Shares with Anonymous Access

    List shares with anonymous access

    Before using credentials, establish a baseline by listing shares without authentication. The -N flag suppresses the password prompt so the connection runs as a null session.

    smbclient -L dc01 -N

    Record the shares that appear in the output. Pay attention to which shares are listed and note any "ACCESS_DENIED" or "NT_STATUS_ACCESS_DENIED" messages. Anonymous access on a hardened domain controller typically shows very few shares.

    Expected output (approximate):

    Anonymous login successful

    Sharename       Type      Comment
    ---------       ----      -------
    IPC$            IPC       Remote IPC

    The anonymous listing may show only IPC$ or a small set of public shares. Keep this result for comparison in the next step.

    Step 3: List Shares with Authenticated Access

    List shares with authenticated access

    Now authenticate as guest.user and list shares again. The -U 'user%pass' syntax supplies the domain credentials inline so no interactive prompt appears.

    smbclient -L dc01 -U 'guest.user%Guest2024#'

    The authenticated listing should return significantly more shares than the anonymous listing. Compare the two results side by side.

    Expected output (approximate):

        Sharename       Type      Comment
    ---------       ----      -------
    ADMIN$          Disk      Remote Admin
    C$              Disk      Default share
    IPC$            IPC       Remote IPC
    IT-Tools        Disk
    NETLOGON        Disk      Logon server share
    SYSVOL          Disk      Logon server share

    Several shares that were invisible to the anonymous connection now appear. The NETLOGON, SYSVOL, and custom shares like IT-Tools become visible because the server recognizes guest.user as a valid domain member.

    Step 4: Identify the Differences

    Document the gap between anonymous and authenticated share listings. The difference demonstrates why credential-based enumeration is a critical step in any Active Directory assessment.

    Shares that appear only with authentication typically include:

    • NETLOGON: logon scripts and domain-wide configuration files
    • SYSVOL: Group Policy templates (explored in detail in Exercise WS-4.2)
    • Custom shares: department-specific file shares created by administrators
    • Administrative shares (ADMIN$, C$); visible in the listing but accessible only to administrators

    The IT-Tools share is particularly interesting because custom shares often contain operational scripts, configuration files, and internal documentation that administrators did not intend to expose to every domain user.

    Step 5: Browse the IT-Tools Share

    Browse the IT-Tools share

    List the contents of the IT-Tools share to see what files are available to your authenticated session. The -c 'ls' flag runs a single directory listing and exits without entering the interactive shell.

    smbclient //dc01/IT-Tools -U 'guest.user%Guest2024#' -c 'ls'

    Examine the directory listing for files and subdirectories. Note file names, sizes, and timestamps. Files in IT-related shares frequently contain scripts, tools, documentation, and configuration files that reveal infrastructure details.

    Step 6: Retrieve Files from the Share

    Download files of interest from the IT-Tools share. The get command with - as the destination prints file contents to your terminal instead of saving to disk:

    Print a file to the terminal

    Use the get command with - as the destination to print a file's contents to your terminal. Download the file you identified in the previous step and review its content for the lab flag. Replace <filename> with the file you found in Step 5.

    smbclient //dc01/IT-Tools -U 'guest.user%Guest2024#' -c 'get <filename> -'

    The get <filename> - syntax retrieves the specified file and writes its contents to standard output. Review the output for the lab flag.

    Save a file to disk instead

    If you want to save the file locally instead, omit the trailing dash so smbclient writes it to disk.

    smbclient //dc01/IT-Tools -U 'guest.user%Guest2024#' -c 'get <filename>'

    The file will be saved to your current working directory on the Kali machine.

    Step 7: Test Access to Administrative Shares

    Test access to an administrative share

    Verify that your low-privilege account cannot access administrative shares. Attempt to list the contents of C$, the hidden share that maps the server's system drive.

    smbclient //dc01/C$ -U 'guest.user%Guest2024#' -c 'ls'

    The expected result is an NT_STATUS_ACCESS_DENIED error. Administrative shares require membership in the Domain Admins group or equivalent privileges. Confirming that access is denied validates the privilege boundary between a standard domain user and an administrator.

    Step 8: Browse NETLOGON

    Browse the NETLOGON share

    Check the NETLOGON share for logon scripts and configuration files. Any authenticated domain user can read this share by design.

    smbclient //dc01/NETLOGON -U 'guest.user%Guest2024#' -c 'ls'

    The NETLOGON share contains scripts that run when users log on to domain-joined machines. Logon scripts may contain mapped drive letters, server names, file paths, and occasionally hardcoded credentials. Record any files you find for analysis in later exercises.

    Analysis Questions

    1. Why does Windows expose more shares to authenticated users than to anonymous connections?

    Reveal Answer

    Windows Server is designed to support domain operations. Shares like NETLOGON and SYSVOL must be readable by every domain-joined machine so those machines can apply logon scripts and Group Policy settings. Anonymous access restrictions exist to prevent information leakage to external attackers, but once an attacker obtains even a single low-privilege domain account, those protections no longer apply. The design assumes that domain membership implies a baseline level of trust.

    2. What is the security risk of custom shares like IT-Tools being readable by all domain users?

    Reveal Answer

    Administrators often create departmental shares and assign broad read permissions for convenience. Shares intended for IT staff may contain deployment scripts with hardcoded credentials, network diagrams, configuration files with internal IP addresses, or administrative tools that reveal infrastructure details. When every domain user can read these shares, a compromised low-privilege account gains access to information that should be restricted to specific teams.

    3. How does comparing anonymous and authenticated share listings help during a penetration test?

    Reveal Answer

    The comparison quantifies what an attacker gains from obtaining domain credentials. A small set of anonymous shares tells you the organization has restricted unauthenticated access, but a much larger set of authenticated shares shows the post-compromise attack surface. The delta between the two listings helps prioritize credential-focused attacks: if authenticated access reveals many sensitive shares, investing time in password spraying or phishing becomes a high-value strategy.

    4. You confirmed that C$ is visible but not accessible. What does that tell you about administrative share security?

    Reveal Answer

    The visibility of C$ in the share listing confirms that the server advertises administrative shares to authenticated users, but access control enforcement prevents non-administrators from connecting. The share-level permissions and NTFS permissions on C$ restrict access to Domain Admins and equivalent groups. Seeing the share in the listing without being able to access it confirms that privilege boundaries are functioning, and it identifies a target for privilege escalation; if you can obtain Domain Admin credentials, full file system access through C$ becomes available.

    Key Takeaways

    • Authenticated SMB enumeration reveals significantly more shares than anonymous access
    • Domain user credentials unlock access to NETLOGON, SYSVOL, and custom shares by design
    • Custom shares created by administrators often contain sensitive operational data
    • The -U 'user%password' syntax provides non-interactive authentication for scripting
    • Comparing anonymous and authenticated results quantifies the value of compromised credentials
    • Administrative shares (C$, ADMIN$) are visible but not accessible to standard domain users
    • Exercise WS-4.2 explores the SYSVOL share in depth, examining Group Policy templates and their security implications
